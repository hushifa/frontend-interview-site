怎样避免加载、成功和失败状态互相矛盾？

不要用 loading、success、error 几个独立布尔值，改成一个 status 字段表示互斥状态，用纯状态转换函数集中处理事件，并拒绝过期请求的完成事件。刷新中保留旧数据要单独表达，外部副作用不归状态机管。

参考答案

简答

很多人写请求界面，会用 loading、success、error 三个布尔值。问题是它们能组合出业务上不可能的状态，比如页面上同时显示错误提示和上一次的结果。

改法是只用一个 status 字段，取值是互斥的几种状态，每种状态只带自己需要的数据。状态怎么变，集中写在一个纯函数里，只有在合法状态下、收到属于当前请求的事件，才改变状态。

这样按钮要不要禁用、要不要显示重试，都可以直接从状态推出来，不用另外存一份，也就不会不一致。

要注意，“已经有旧数据、同时正在刷新”是合法的组合，应该用单独的维度或嵌套状态来表达，不能为了只留一个字段就把旧数据清掉。

几个布尔值为什么会互相矛盾

常见写法是：请求开始时 setLoading(true)，成功后 setSuccess(true)，失败时 setError(e)，最后在 finally 里 setLoading(false)。

可是如果失败分支忘了把 success 清掉，上一次的结果和这次的错误就会同时出现在页面上。

原因在于，三个布尔值一共有 8 种组合，真正合法的只有 4 种。每条更新路径都得记着去清理别的标志，漏掉一处，就会出现不该存在的组合。

每个状态只带自己的数据

换成一个 status 字段，每种状态各带各的数据：

text
{ status: 'idle' }
{ status: 'loading', requestId: 2 }
{ status: 'success', data: [...] }
{ status: 'error', message: '网络错误' }

读数据之前先看 status。这样根本就不存在“data 有值，但已经失败了”这种情况。用 TypeScript 的话，可以写成可辨识联合，也就是用一个共同的字段区分几种类型，让编译器帮你检查这些约束。

把状态转换集中写在一个函数里

下面这个函数接收当前状态和一个事件，返回新状态。注意看它怎样处理旧请求的事件。

JavaScript
function reduceRequest(state, event) {
  if (event.type === 'start') {
    return { status: 'loading', requestId: event.requestId };
  }

  if (state.status !== 'loading' || event.requestId !== state.requestId) {
    return state;
  }

  switch (event.type) {
    case 'succeed':
      return { status: 'success', data: event.data };
    case 'fail':
      return { status: 'error', message: event.message };
    case 'cancel':
      return { status: 'idle' };
    default:
      return state;
  }
}

假设依次发生 start(1)、start(2)、succeed(1)、succeed(2)。第三个事件来自请求 1，可当前请求已经是 2 了，所以状态保持不变；第四个事件才让状态进入 success。之后要是再收到重复的完成事件，状态已经不是 loading，也会被忽略。

为什么要强调它是纯函数？因为它不发请求、不读时钟、不修改传入的对象，同样的输入永远得到同样的输出，可以直接写单元测试。发请求和取消请求的那一侧，见《事件驱动 UI 怎样避免状态互相覆盖？》。

转换规则一览

当前状态事件结果
任意start新请求的 loading
loading当前请求 succeedsuccess
loading当前请求 failerror
loading当前请求 cancelidle
loading旧请求的任何事件不变
非 loadingsucceed / fail / cancel不变

这些规则是本例的选择，不是唯一答案。取消后是回到 idle、保留旧结果，还是显示“已取消”，要看产品需求。重要的是规则集中写在一处，而不是散在各个回调里。

刷新时怎样保留旧数据

用户已经看到了列表，后台又在刷新。这时“有数据”和“正在请求”同时成立，是完全合理的。

可以把它拆成两个维度：

JavaScript
{ data: [...], refresh: { status: 'loading', requestId: 5 } }

也可以在 success 状态里面再分 idle、refreshing、refreshError 三种。不要为了只保留一个 status 字段，每次刷新都把列表清空，那样用户会看到内容闪一下消失。

状态机管不到的事

状态变回 idle，并不会终止网络请求。真正取消请求要用 AbortController。

支付、提交这类写操作更要小心。前端显示“已取消”，不代表服务端已经撤销了。需要查询最终状态，或者依靠幂等设计，也就是同一个操作重复提交多次，结果和提交一次一样。

常见追问

什么时候需要 XState 这类库？

流程有多步、有并行区域、有超时和守卫条件时，用可视化的状态图更好维护。只是单个请求的话，上面这个 reducer 就够了。

在 React 里怎么用？

把 reduceRequest 传给 useReducer，组件根据 state.status 渲染不同的界面。
