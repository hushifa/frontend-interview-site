怎样避免加载、成功和失败状态互相矛盾？

从合法业务状态与转换出发组织请求界面，给出能拒绝过期完成事件的纯状态转换函数，并区分互斥状态、刷新中的旧数据和外部副作用。

参考答案

三个布尔值 loading、success、error 可以表达很多组合，但“同时正在首次加载、已经成功、又失败”未必是业务允许的界面。代码每多一条更新路径，就要记得同步清理其他标志，遗漏后容易出现错误提示和成功结果一起显示。

可以先列出这个流程真实允许的状态，再定义哪些事件能改变它。简单的一次性加载可能只有 idle、loading、success、error；状态机的价值在于约束转换，不在于必须安装某个库。

先把每个状态需要的数据放在一起

idle 不需要结果，loading 需要知道当前是哪次请求，success 携带数据，error 携带错误说明。这样读取成功数据前先判断 status，就不必猜 data、loading 和 error 三个独立字段是否已经同步。

在 TypeScript 中可以用可辨识联合进一步表达这些约束；在 JavaScript 中，也可以保持相同的对象结构，并在数据入口做必要校验。

按钮是否禁用、是否显示重试，通常可以由当前状态推导。若再各自保存一份布尔值，就重新引入了不同步的机会。

只在合法状态接收对应结果

下面是一个请求状态转换函数。事件由应用内部产生，requestId 用于标识当前尝试；新的 start 可以取代旧请求，旧结果不再有资格更新界面。

JavaScript
function reduceRequest(state, event) {
  if (event.type === 'start') {
    return { status: 'loading', requestId: event.requestId };
  }

  if (state.status !== 'loading' || event.requestId !== state.requestId) {
    return state;
  }

  switch (event.type) {
    case 'succeed':
      return { status: 'success', data: event.data };
    case 'fail':
      return { status: 'error', message: event.message };
    case 'cancel':
      return { status: 'idle' };
    default:
      return state;
  }
}

它只计算下一个状态，不发请求、不读取时钟，也不创建计时器。调用方从 { status: 'idle' } 开始，把经过校验的内部事件传入，并保存返回的状态。

假设依次发生 start(1)、start(2)、succeed(1)、succeed(2)：第三个事件不会把第二次请求的 loading 覆盖掉，最后才展示第二次请求的数据。已经成功后重复收到完成事件，也不会再次改变状态。

这里的 start 代表应用明确接受的新操作，不是把任意外部消息直接当成新请求。请求编号应由发起层可靠生成；如果输入来自消息通道，还需要协议与重复事件检查。

可以用转换表检查遗漏

当前情况事件示例的处理
任意已有状态新的 start进入新请求的 loading
loading当前请求 succeed进入 success
loading当前请求 fail进入 error
loading当前请求 cancel回到 idle
loading旧请求完成保持当前状态
非 loading重复完成或取消保持当前状态

表里的规则是本例的选择，不是所有产品的统一答案。比如取消后是否回到 idle、保留旧结果，还是显示 canceled，应该根据实际流程决定。

重要的是这些决定集中且可测试，而不是散在多个 catch、finally 和组件 effect 中，各自修改一部分布尔值。

“有数据，同时正在刷新”可能完全合法

不是所有看起来并存的状态都是矛盾。用户已经看到列表，后台刷新正在进行，这时 data 存在且 fetching 为 true 很合理；刷新失败也可能继续展示旧数据并附加错误提示。

可以把“是否已有可用数据”与“刷新任务状态”分成真正独立的维度，或建立嵌套状态，例如 ready 状态内部再有 idle、refreshing、refreshError。

不要为了只有一个 status 字段，就每次刷新都清空旧内容；也不要为了支持后台刷新，让首次加载的模型出现任意组合。状态结构应表达产品允许的情形。

状态转换不能替代取消和清理

把状态改成 idle，并不会自动终止 fetch。上面的 requestId 检查能防止旧结果进入当前 UI，但旧请求仍可能占用网络或在服务器产生副作用。

发起层还应管理 AbortController、计时器和资源释放。finally 中也要判断是否仍属于当前请求，避免旧请求结束时把新请求的加载状态清掉。

对于支付、提交等写操作，前端显示 canceled 不等于服务器已经撤销。需要依照业务协议查询最终状态或处理幂等，不能只靠 UI 状态机保证服务端一致性。

什么时候需要更完整的状态机工具

单个请求用这样的 reducer 往往足够。多步审批、并行上传、超时恢复和嵌套弹层等流程，如果事件与分支越来越多，可以使用显式状态图或成熟状态机工具表达进入动作、守卫条件和并行区域。

工具不会替你决定业务规则。先说明事件的含义、允许的转换、过期事件的处理和失败后的下一步，再选择实现方式，通常比先引入库后把原来的布尔值全部搬进去更有效。
