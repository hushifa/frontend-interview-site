什么是长任务，为什么会影响交互响应？怎样观测和拆分？

主线程上连续执行 50ms 以上的任务就是长任务。它执行期间用户输入只能排队、渲染也被推迟，表现为点了没反应、INP 变差。可以用 PerformanceObserver 观察 longtask 或更详细的 long-animation-frame 来定位，再通过减少工作、分片让出主线程或移到 Worker 来优化。

参考答案

简答

浏览器的主线程要同时负责跑 JavaScript、处理输入事件、算样式、布局和绘制。一个任务连续占着主线程 50 毫秒以上，就叫长任务。

长任务的问题是，它执行期间用户点了什么都只能排队，页面也没法渲染。所以用户会觉得点了没反应，这段等待会计入 INP 的输入延迟。

观测可以用 PerformanceObserver 观察 longtask。在 Chromium 里更推荐 Long Animation Frames，也就是 long-animation-frame，它以帧为单位，还能归因到具体脚本。

优化的顺序是：先减少不必要的工作；再把任务切成小片，每片之间让出主线程，优先用 scheduler.yield()，不支持就退回 setTimeout；纯计算挪到 Worker。要注意，await Promise.resolve() 只是进了微任务队列，浏览器在中间既不会处理输入，也不会渲染。

为什么一个任务太长，点击就没反应

事件循环里，浏览器一次只执行一个任务，执行完才能去处理下一个，比如用户的点击，或者渲染下一帧。所以一个任务跑了 200ms，这 200ms 里用户的点击只能干等。

50ms 这个数字来自 RAIL 模型：要在 100ms 内响应用户输入，留一半时间给浏览器做其他工作。它只是观测阈值，不代表低于 50ms 就一定流畅。

怎样观测长任务

下面的代码观察所有长任务，记下时长和它来自哪个容器：

JavaScript
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    // containerSrc 可能带查询参数等敏感信息，上报前只保留来源
    const src = entry.attribution[0]?.containerSrc;
    const origin = src ? new URL(src, location.href).origin : 'self';
    report({ duration: Math.round(entry.duration), startTime: entry.startTime, origin });
  }
}).observe({ type: 'longtask', buffered: true });

看完会发现，Long Tasks API 能告诉你的其实很少，它只说“这里有一段时间被占用了”。attribution 只能指到容器，也就是哪个 iframe 或窗口，不是调用栈。buffered: true 也只能拿到时间线缓冲区里还保留着的条目，不是完整历史。

那怎么判断某个长任务有没有影响到用户？可以在用户操作的地方打 performance.mark()，再拿长任务的 startTime 去对齐比较。

如果要知道是哪个脚本、有没有发生强制布局，就要用 LoAF，见《如何用 Long Animation Frames API 定位卡顿来源？》。LoAF 目前不是 Baseline，所以两种条目都要先用 PerformanceObserver.supportedEntryTypes.includes('longtask') 或 'long-animation-frame' 检测，再去观察。

怎样把长任务切开

await 一个已完成的 Promise 为什么没用

很多人想到的第一个办法是在循环里 await 一下。先看这样做会发生什么：

JavaScript
setTimeout(() => console.log('定时器（代表输入和渲染的机会）'), 0);

async function work() {
  for (let i = 0; i < 3; i += 1) {
    console.log('处理第', i, '片');
    await Promise.resolve();
  }
}
work();
// 处理第 0 片
// 处理第 1 片
// 处理第 2 片
// 定时器（代表输入和渲染的机会）

代码确实停了三次，可是定时器回调一直等到所有片都处理完才执行。原因是 await 后面的代码进的是微任务队列，而浏览器要把微任务全部清空，才会去处理下一个任务。所以这几片在浏览器看来还是同一个长任务，用户的点击和渲染照样插不进来。

改法是让出到任务层面，也就是真正把控制权还给浏览器。

真正让出主线程

下面的写法每处理约 8ms 就让出一次：

JavaScript
function yieldToBrowser() {
  if (globalThis.scheduler?.yield) return globalThis.scheduler.yield();
  return new Promise((resolve) => setTimeout(resolve, 0));
}

async function processInChunks(items, visit, signal) {
  let sliceStart = performance.now();
  for (let i = 0; i < items.length; i += 1) {
    signal?.throwIfAborted();
    visit(items[i]);
    if (performance.now() - sliceStart > 8) {
      await yieldToBrowser();
      sliceStart = performance.now();
    }
  }
}

8ms 是给输入和渲染留出机会的一个经验值，可以按设备调整。

为什么优先用 scheduler.yield()？因为它返回以后，剩下的工作会排在同优先级普通任务的前面，不容易被别的任务插队。如果是在 scheduler.postTask() 的回调里调用，还会继承那个任务的优先级。MDN 标注它为有限可用，所以要特性检测。

退回到 setTimeout 也能让出，但浏览器可能对它节流，后台标签页里延迟会更大。

代码里的 signal 是做什么的？用户发起了新操作时，用 AbortSignal 取消旧任务，避免旧结果覆盖新状态。

除了切片还有哪些办法

最根本的是减少工作。不要每次输入都全量重新算，能缓存就缓存，输入可以防抖。

纯计算，比如排序、解析、压缩，可以放到 Worker 里，它跑在另一个线程上，不占主线程。不过数据传过去要复制一份，大数据可以用 Transferable 直接转移所有权。

渲染成本也要控制。大量 DOM 用虚拟列表；不要读写布局交替进行，否则会触发强制同步布局。

页面加载阶段的长任务，主要靠拆分打包产物、推迟非关键脚本来解决。

长任务、TBT、INP 有什么区别

长任务是原始的观测数据，指单个超过 50ms 的任务。

TBT，总阻塞时间，是实验室指标，把加载期间每个长任务超过 50ms 的部分加起来。

INP 是现场指标，统计真实交互从输入到下一帧绘制的耗时。长任务是 INP 变差的常见原因，可是如果长任务期间用户没有操作，它就不会影响 INP。

常见追问

50ms 是怎么来的？

来自 RAIL 模型，目标是在 100ms 内响应输入，留一半时间给浏览器的其他工作。它是一个观测阈值，不代表低于 50ms 就一定流畅。

多个 30ms 的任务连在一起会怎样？

单个都不算长任务，Long Tasks API 也不会报。但它们可能一起让一帧超过 50ms，这种情况 LoAF 能发现。
