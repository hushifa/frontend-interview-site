什么是长任务，为什么会影响交互响应？怎样观测和拆分？

主线程上连续执行 50ms 以上的任务是长任务。执行期间用户输入只能排队，渲染也被推迟，表现为点击没反应、INP 变差。可以用 PerformanceObserver 观察 longtask 或更详细的 long-animation-frame 定位，再通过减少工作、分片让出主线程或移到 Worker 来优化。

参考答案

简答

  • 主线程同时负责 JavaScript、输入事件、样式、布局和绘制，一个任务连续占用 50ms 以上就是长任务。
  • 用户在长任务期间的点击要等它结束才能处理，这段等待计入 INP 的输入延迟。
  • 观测：PerformanceObserver 观察 longtask；Chromium 中优先用 Long Animation Frames（long-animation-frame），它以帧为单位，并能归因到具体脚本。
  • 优化顺序：先减少不必要的工作，再分片并在片之间让出主线程（scheduler.yield()，不支持时退回 setTimeout），纯计算移到 Worker。
  • await Promise.resolve() 只进入微任务队列，不会让浏览器处理输入或渲染。

观测

JavaScript
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log('长任务', Math.round(entry.duration), 'ms', entry.attribution[0]?.containerSrc);
  }
}).observe({ type: 'longtask', buffered: true });

Long Tasks API 只告诉你"有一段长时间占用"，归因只到容器（哪个 iframe 或窗口），不提供函数调用栈。需要知道是哪个脚本、是否发生强制布局时，用 LoAF，见《如何用 Long Animation Frames API 定位卡顿来源？》。LoAF 目前不是 Baseline，使用前做特性检测。

分片让出主线程

JavaScript
function yieldToBrowser() {
  if (globalThis.scheduler?.yield) return globalThis.scheduler.yield();
  return new Promise((resolve) => setTimeout(resolve, 0));
}

async function processInChunks(items, visit, signal) {
  let sliceStart = performance.now();
  for (let i = 0; i < items.length; i += 1) {
    signal?.throwIfAborted();
    visit(items[i]);
    if (performance.now() - sliceStart > 8) {
      await yieldToBrowser();
      sliceStart = performance.now();
    }
  }
}
  • 每处理约 8ms 让出一次，给输入和渲染机会，数值按设备调整。
  • scheduler.yield() 返回后的续作排在同优先级普通任务之前，不容易被其他任务插队；在 scheduler.postTask() 回调中调用时会继承该任务的优先级。MDN 标注其为有限可用，需要特性检测。
  • setTimeout 降级可能被浏览器节流，后台标签页里延迟更大。
  • 用户发起了新操作时，用 AbortSignal 取消旧任务，避免旧结果覆盖新状态。

其他手段

  • 减少工作：避免每次输入都全量重新计算，缓存结果，对输入防抖。
  • Worker：排序、解析、压缩这类纯计算放到 Worker，注意数据传输的克隆成本，大数据用 Transferable 转移。
  • 渲染成本：大量 DOM 用虚拟列表，避免读写布局交替导致强制同步布局。
  • 页面加载阶段：拆分打包产物，推迟非关键脚本。

常见追问

  • 50ms 是怎么来的？来自 RAIL 模型：在 100ms 内响应输入，留一半给浏览器的其他工作。它是观测阈值，不代表低于 50ms 就一定流畅。
  • 多个 30ms 的任务连在一起会怎样？单个都不算长任务，但可能共同让一帧超过 50ms，LoAF 能发现这种情况。
