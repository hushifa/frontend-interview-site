如何用 Long Animation Frames API 定位卡顿来源？

Long Animation Frames（LoAF）记录超过 50ms 才渲染完的帧，带上渲染、样式布局的开始时间和这一帧里跑过的脚本列表。每个脚本给出调用者、来源 URL、函数名和强制布局耗时，比 Long Tasks API 更能回答“是谁让这一帧变慢”。它不是 Baseline，要做特性检测。

参考答案

简答

页面卡了，我们想知道是哪段脚本干的。Long Animation Frames，简称 LoAF，就是浏览器把超过 50 毫秒才完成渲染的帧记下来，并且告诉你这一帧里跑过哪些脚本。

它和 Long Tasks API 的区别是，长任务只看单个任务，LoAF 看的是一整帧。比如两个 30 毫秒的任务落在同一帧里，单个都不算长任务，但这一帧已经超过 50 毫秒了，LoAF 能发现。

每个条目里有整帧耗时 duration、阻塞时间 blockingDuration、渲染开始时间 renderStart、样式布局开始时间 styleAndLayoutStart，还有 scripts 列表。列表里每个脚本都有调用者 invoker、来源文件 sourceURL、函数名 sourceFunctionName、耗时，以及强制布局耗时 forcedStyleAndLayoutDuration，能直接定位到具体脚本。

要注意，MDN 标注它为实验性、有限可用，所以要先做特性检测，不支持时退回 Event Timing 和实验室录制。

怎样采集

先检测浏览器支不支持，再用 PerformanceObserver 观察 long-animation-frame，把需要的字段挑出来上报：

JavaScript
function observeLoAF(report) {
  if (!PerformanceObserver.supportedEntryTypes?.includes('long-animation-frame')) return () => {};

  const observer = new PerformanceObserver((list) => {
    for (const frame of list.getEntries()) {
      report({
        duration: Math.round(frame.duration),
        blocking: Math.round(frame.blockingDuration),
        scripts: frame.scripts.map((script) => ({
          invoker: script.invoker,
          type: script.invokerType,
          source: script.sourceURL,
          fn: script.sourceFunctionName,
          duration: Math.round(script.duration),
          forcedLayout: Math.round(script.forcedStyleAndLayoutDuration),
        })),
      });
    }
  });
  observer.observe({ type: 'long-animation-frame', buffered: true });
  return () => observer.disconnect();
}

invoker 告诉你是谁调起了这段脚本，比如 BUTTON#submit.onclick 就是提交按钮的点击回调；invokerType 说明调用方式，比如事件监听还是定时器。

blockingDuration 是怎么算的

duration 是整帧的时间，可是一帧长并不全是坏事，用户真正受影响的是主线程被堵住的那部分。blockingDuration 就是在算这个。

规则是：取帧里每个超过 50ms 的任务，各自减去 50ms 再求和；其中最长的那个任务，还要先加上渲染时间再减。比如一帧里有 70ms 和 120ms 两个任务、渲染用了 20ms，结果是 (70 − 50) + (120 + 20 − 50) = 110ms。

从字段看出是什么问题

拿到数据以后，不同字段异常指向不同的原因：

现象指向的问题方向
某个 invoker 的 duration 很大事件处理或回调里做了大量同步工作减少工作、分片、Worker
forcedStyleAndLayoutDuration 很大写 DOM 后立即读布局属性（布局抖动）先批量读再批量写
sourceURL 是第三方域名第三方脚本在交互时执行延迟加载或隔离第三方，见《第三方脚本怎样接入，才能控制性能和安全风险？》
脚本时间不多，renderStart 到结束很长样式计算和布局成本高缩小 DOM、简化选择器、content-visibility

其中强制布局最容易被忽略。脚本改了 DOM，浏览器本来可以等到这一帧最后再统一算布局；可如果脚本紧接着读 offsetHeight 这类属性，浏览器只能马上算一遍，这段时间就记在 forcedStyleAndLayoutDuration 里。

和长任务、INP 是什么关系

Long Tasks API 只能告诉你“有长任务”，归因只到 iframe 这一级，不知道是哪段脚本，见《什么是长任务，为什么会影响交互响应？怎样观测和拆分？》。

Event Timing 和 INP 能告诉你哪次交互慢、慢在输入延迟、处理还是呈现。所以实际排查时，先用 INP 找到慢交互的时间段，再看同一时间段的 LoAF，就能找到具体脚本，见《INP 很高时，如何定位到底是哪一段交互变慢？》。

上报时要注意什么

sourceURL 是打包后的文件地址，要配合版本号和 Source Map 在服务端还原，Source Map 本身不要公开。

上报量也要控制。只报超过阈值的帧并且采样，观察回调里不要做重活，否则监控本身又制造了卡顿。页面隐藏时用 navigator.sendBeacon() 批量发出去。

常见追问

为什么有时 scripts 是空的？

很短的脚本不会单独记录。另外这一帧的时间也可能主要花在样式、布局和绘制上，本来就没什么脚本。

不支持 LoAF 的浏览器怎么办？

用 Event Timing、自己打的交互标记和 DevTools 录制来代替。
