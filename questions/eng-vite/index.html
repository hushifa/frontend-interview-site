Vite 开发模式为什么启动快，生产环境为什么仍需要构建？

从按需模块处理、依赖优化和 HMR 解释开发体验，再说明生产打包的网络与缓存目标，并区分 Vite 8 的工具链与旧版本实现。

参考答案

简答

  • 开发时 Vite 不先打包整个应用，而是让浏览器通过原生 ES 模块按需请求文件，服务器只转换被请求到的模块。
  • 第三方依赖会预先打包成少量 ESM 文件并缓存，避免浏览器请求成百上千个小文件。
  • 热更新只替换改动的模块及其边界，速度不随应用规模明显变慢。
  • 生产环境仍要打包：合并请求、tree shaking、压缩、代码分割和带哈希的缓存文件名都需要构建完成。
  • Vite 8 的生产构建使用 Rolldown；Vite 7 及之前开发时用 esbuild、生产构建用 Rollup。当前版本要求 Node.js 20.19+ 或 22.12+。

开发服务器做了什么

传统打包工具启动时要先分析和打包所有模块，应用越大启动越慢。Vite 启动时几乎不处理业务代码：

  1. 浏览器加载 index.html，遇到 <script type="module" src="/src/main.ts">。
  2. 浏览器请求 /src/main.ts，Vite 把 TypeScript 去掉类型、改写导入路径后返回。
  3. 浏览器根据其中的 import 继续请求下一批模块。

没访问到的路由，代码根本不会被转换。

依赖预构建

node_modules 里的包存在两个问题：很多仍是 CommonJS，浏览器无法直接执行；一个包可能拆成几百个内部模块，逐个请求很慢。Vite 首次启动时扫描依赖，把它们转换并合并成少量 ESM 文件，放到 node_modules/.vite 中缓存。依赖或锁文件变化时会重新预构建。

热更新

修改一个文件后，Vite 沿导入关系向上找到接受热更新的边界（例如一个 React 或 Vue 组件），只让浏览器重新请求这部分模块，同时保留页面状态。找不到边界时才整页刷新。

为什么生产还要打包

  • 请求数量：未打包的应用首屏可能要发起几百个模块请求，导入链越深，往返次数越多，即使用 HTTP/2 也明显变慢。
  • 体积：tree shaking 去掉未使用的代码，压缩器减小文件，开发模式都不做这些。
  • 缓存：文件名带内容哈希，未改动的块可以长期缓存。
  • 兼容性：按 build.target 降级语法，处理 CSS 和静态资源。默认值 'baseline-widely-available' 对应每个大版本固定日期时的 Baseline 广泛可用浏览器，Vite 8 以 2026-01-01 为准（Chrome 111、Firefox 114、Safari 16.4 等）。

Vite 8 的生产构建由 Rolldown 完成；Vite 7 及之前开发时用 esbuild、生产构建用 Rollup。Vite 8 要求 Node.js 20.19+ 或 22.12+。

开发和生产的差异

开发与生产走的是不同的处理路径，个别问题只在一种模式下出现，例如 CommonJS 互操作、CSS 顺序、动态导入路径。提交前运行 vite build 并用 vite preview 在本地检查产物。

常见追问

  • 为什么首次启动或依赖变化后会慢一些？需要重新预构建依赖，之后命中缓存就快了。
  • Vite 能用于非浏览器场景吗？可以用 SSR 模式和库模式构建，但开发服务器的"按需请求"优势主要体现在浏览器应用上。
