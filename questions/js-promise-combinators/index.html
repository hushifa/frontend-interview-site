Promise.all、allSettled、race 和 any 如何选择？

Promise 组合方法定义的是一组结果的完成条件，不负责启动限流或自动取消。all 要求全成功，allSettled 收集所有状态，race 跟随首个敲定，any 等首个成功；空输入和错误结果也各有明确规则。

参考答案

选择 Promise 组合方法前，先问业务怎样才算完成：两个接口缺一不可，还是失败也要展示各自状态？多个镜像地址里最快失败是否应该结束等待，还是一定要等到某一个成功？

这四个方法把不同答案编码成 Promise 的完成规则。它们都接收可迭代输入，普通值与 thenable 也能按 Promise 解析规则参与，但不会自动把传入的函数当成任务调用。

方法何时兑现何时拒绝典型用途
all所有输入兑现，得到值数组某项拒绝后整体拒绝多个必要结果必须齐全
allSettled每项都敲定，得到状态数组通常不因单项拒绝而拒绝，但输入迭代等仍可能出错批量操作汇总各项成功与失败
race第一个被观察到的敲定结果为兑现第一个被观察到的敲定结果为拒绝采用首个结果，或组合等待上限
any某项首次兑现全部拒绝时得到 AggregateError多个替代来源中任意一个成功即可

“敲定”包括兑现和拒绝。race 不关心第一名是成功还是失败，any 则会忽略早到的拒绝，继续等成功机会。

用同一组结果对照四种策略

JavaScript
async function compare() {
  const tasks = [
    Promise.reject(new Error('A失败')),
    Promise.resolve('B成功'),
  ];

  try {
    await Promise.all(tasks);
  } catch (error) {
    console.log(`all:${error.message}`); // all:A失败
  }

  const settled = await Promise.allSettled(tasks);
  console.log(settled.map(item => item.status).join(',')); // rejected,fulfilled
  console.log(settled.map(item =>
    item.status === 'fulfilled' ? item.value : item.reason.message,
  ).join('|')); // A失败|B成功

  try {
    await Promise.race(tasks);
  } catch (error) {
    console.log(`race:${error.message}`); // race:A失败
  }

  console.log(`any:${await Promise.any(tasks)}`); // any:B成功
}

compare();

本例为了对比，重复观察同一组已经敲定的结果，相关反应按连接顺序排队，所以 race 选择了输入中靠前的拒绝。真实异步请求的竞速则取决于结果何时被观察到，不能从这里推断 race 永远返回第一个数组元素。

allSettled 的成功项有 status 和 value，失败项有 status 和 reason。应先根据 status 区分，再读取对应字段；失败项没有一个会自动填成正常结果的 value。

all 的结果顺序不会随完成速度重排

JavaScript
async function collect() {
  let finishFirst;
  const first = new Promise(resolve => { finishFirst = resolve; });
  const second = Promise.resolve('第二项');
  const pending = Promise.all([first, second, 3]);

  finishFirst('第一项');
  console.log((await pending).join(',')); // 第一项,第二项,3
}

collect();

第二项先具备结果，但仍然放在结果数组的第二个位置。all 和 allSettled 都保留输入遍历顺序，适合把结果重新对应到原始任务。它们不会按完成顺序 push 出一个难以映射的列表。

all 的“快速失败”表示不必等待所有任务都完成才拒绝，不表示它在当前同步栈中直接 throw，也不表示其他操作已经停止。如果你需要在全部任务结束后统一释放某组资源，单独等待 all 的拒绝未必足够。

any 全失败时，原因保存在 errors 中

JavaScript
async function failEverywhere() {
  try {
    await Promise.any([
      Promise.reject(new Error('主站不可用')),
      Promise.reject(new Error('备站不可用')),
    ]);
  } catch (error) {
    console.log(error.name); // AggregateError
    console.log(error.errors.map(item => item.message).join(','));
    // 主站不可用,备站不可用
  }
}

failEverywhere();

errors 按输入顺序保存拒绝原因，不按失败时间重新排序。原因本身不一定总是 Error 对象，真实代码应根据任务契约或安全格式化方式处理；示例明确让所有任务拒绝为 Error，所以能读取 message。

any 兑现时只返回获胜值，不会附送是哪一个输入。需要来源信息时，可以让每个任务兑现为 { source, value } 这样的结构，前提是不要把本应拒绝的失败包装成“成功返回一个错误对象”，否则 any 会把它误判为成功。

空输入与微任务行为

空输入下，all 和 allSettled 返回已兑现、值为 [] 的 Promise；any 返回以空 errors 列表的 AggregateError 拒绝的 Promise；race 则保持待定。

即便得到的是已经兑现的 Promise，then 回调仍然不会同步插入当前代码。非空输入即使都是普通值或已敲定 Promise，组合结果的观察也仍涉及异步反应过程。

race 为空会一直待定，可能让一次没有候选项的“竞速”流程永远等下去。输入可能为空的业务，应明确是立即返回默认值、报错，还是确实需要保持等待。

这些方法都不是并发池，也不是取消器

写 urls.map(url => fetch(url)) 时，请求已经随着 map 的执行启动。再把数组传给 all、race 或 any，并不会重新安排启动时间。需要限制最多几个请求在途，应把尚未启动的任务函数交给调度逻辑，而不是只改变组合方法。

同样，race 得到一个超时拒绝，也不会自动停止原请求；any 已经选出成功镜像，也不会自动终止其他来源。要取消需要让操作支持 AbortSignal 等机制，并决定哪些操作允许取消。

如果自己创建超时计时器，任务提前结束时还要清除计时器，避免无用工作。超时也只是调用方停止等待的一种策略，不能据此确认服务端写入没有完成。

最后，allSettled 不是“永远不可能拒绝”的保障。传入不可迭代值、迭代过程抛错或其他协议边界错误，仍可能让组合操作拒绝。区别在于它把正常输入项的单项拒绝当成要收集的结果，而不是把所有 JavaScript 错误都吞掉。
