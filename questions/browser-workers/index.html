Web Worker 可以解决哪些主线程卡顿？

Web Worker 在另一个线程里跑脚本，适合解析、压缩、加密、大数据计算这类耗 CPU 的活。它不能碰 DOM，和主线程只能靠 postMessage 传数据。

参考答案

简答

用户上传一个 50MB 的 JSON 文件，直接在主线程 JSON.parse，解析的那几秒页面完全点不动。Web Worker 能把这种计算挪到后台线程去做，主线程照样响应输入、渲染页面。

Worker 不能操作 DOM，算完的结果要交回主线程，由主线程更新界面。两边用 postMessage 通信，数据默认被复制一份过去，这叫结构化克隆；ArrayBuffer 这类数据还可以直接转移所有权，省掉复制。

它适合 JSON 解析、图片处理、压缩加密、搜索索引这类耗 CPU 的任务。

要注意，网络请求本身就是异步的，不占主线程，放进 Worker 通常没有收益。另外传数据也有成本，对象很大时，光是复制就可能花几十毫秒。

先看一个解析文件的例子

主线程把文件内容交给 Worker，等结果回来再渲染：

JavaScript
// main.js
const worker = new Worker(new URL('./parse.worker.js', import.meta.url), { type: 'module' });

worker.onmessage = (event) => render(event.data);
worker.onerror = (event) => console.error(event.message);

const buffer = await file.arrayBuffer();
worker.postMessage(buffer, [buffer]);

Worker 里解码、解析，再把结果发回去：

JavaScript
// parse.worker.js
self.onmessage = (event) => {
  const text = new TextDecoder().decode(event.data);
  self.postMessage(JSON.parse(text));
};

注意 postMessage(buffer, [buffer]) 的第二个参数。它表示把 buffer 的所有权转移给 Worker，而不是复制一份。转移之后，主线程里的 buffer 就被清空了，不能再用。

可以用 structuredClone 在 Node 里看到同样的效果，它和 postMessage 用的是同一套规则：

JavaScript
const buffer = new ArrayBuffer(8);
const copy = structuredClone(buffer, { transfer: [buffer] });
console.log(buffer.byteLength, copy.byteLength); // 0 8

原来的 buffer 长度变成 0，数据全部到了新的那一边。

传数据为什么也会卡

结构化克隆要把数据整个遍历一遍再复制。传一个很大的对象，光复制就可能花几十毫秒，而且这部分时间花在发送方的线程上。如果是主线程在发，主线程还是会卡一下。

结果传回来也要再克隆一次。所以数据量大时，尽量传 ArrayBuffer 并转移所有权，或者只把主线程真正需要的部分传回来。

还有些东西根本传不过去：函数、DOM 节点、类实例上的方法都没法克隆。

Worker 有哪几种

Dedicated Worker 只属于创建它的页面，最常用，上面的例子就是。SharedWorker 被同源的多个页面共享一个实例。Service Worker 用来拦截网络请求，做离线缓存和推送，它的生命周期由浏览器管理。

常见追问

Worker 里能用哪些 API？

能用 fetch、IndexedDB、WebSocket、OffscreenCanvas、定时器等。document、window 和 localStorage 都用不了。

怎样取消 Worker 里正在跑的任务？

调用 worker.terminate() 会立刻终止整个线程。如果只想取消其中一个任务，就在消息里带上任务 ID，Worker 在循环里检查有没有收到取消标记。任务多时，可以按 navigator.hardwareConcurrency 创建固定数量的 Worker 组成池来调度。
