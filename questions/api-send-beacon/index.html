sendBeacon 返回 true 就代表上报成功了吗？页面离开时怎样发送统计？

不代表。返回 true 只说明浏览器把数据放进了发送队列，服务端收没收到页面不知道。页面离开时在 visibilitychange 变成 hidden 时发送，服务端要能接受重复和丢失。

参考答案

简答

不代表。navigator.sendBeacon(url, data) 会发一个 POST 请求，页面关掉以后请求还能继续发。它返回 true，只表示数据进了浏览器的发送队列；返回 false 通常是数据太大，排队总量限制为 64 KiB（65,536 字节）。服务端到底收没收到、返回了什么，页面都没法知道。

发送时机要选 visibilitychange 变成 hidden 的时候。unload 和 beforeunload 在手机上经常不触发，而且注册了 unload 监听，页面还没法进入 bfcache（往返缓存）。

如果要自定义请求头，或者发 JSON 类型，可以用 fetch(url, { method: 'POST', keepalive: true })。它和 sendBeacon 共用同一份 64 KiB 的配额。

因为没法确认送达，统计数据要设计成可以丢、可以去重，比如每条带一个唯一 ID。

写一个上报队列

下面平时把事件攒在队列里，页面隐藏时一次性发出去。

JavaScript
const queue = [];

function track(event) {
  queue.push({ id: crypto.randomUUID(), time: Date.now(), ...event });
}

function flush() {
  if (queue.length === 0) return;
  const body = JSON.stringify(queue.splice(0, queue.length));
  const blob = new Blob([body], { type: 'application/json' });
  // 失败多半是超出共享配额，keepalive 回退同样会失败，所以平时就要分批 flush，控制单次大小
  if (!navigator.sendBeacon('/api/collect', blob)) {
    console.warn('上报数据过大，未能排队');
  }
}

document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') flush();
});

sendBeacon 返回 false 时为什么不用 fetch keepalive 再试一次？因为失败多半是超了配额，而两者共用同一份配额，换一个也会失败。所以更好的做法是平时就定时或攒够一定数量发一次，页面离开时只发剩下的，单次数据小。

每条事件带 crypto.randomUUID() 生成的 ID，服务端按 ID 去重。

跨源上报要注意什么

例子里 Blob 的类型是 application/json。它不是 text/plain 这类 CORS 安全类型，跨源发送时，不同浏览器的行为不一致。所以跨源上报最稳妥的是用 text/plain 发 JSON 字符串，服务端按文本解析。

sendBeacon 也不能设置自定义请求头，鉴权只能靠 Cookie 或 URL 里的参数。

为什么用 hidden 而不是 unload

在手机上，用户切到后台，再从任务列表把应用划掉，页面根本收不到 unload。visibilitychange 变成 hidden 是最后一个能可靠执行代码的时机。

不过一个会话里，页面可能多次隐藏又恢复。所以每次隐藏都把当前队列发出去，服务端按 ID 去重就行。

常见追问

为什么不在离开时用同步 XHR 发送？

同步 XHR 会阻塞页面关闭，用户体验很差。浏览器已经限制在卸载事件里使用同步 XHR 了。

fetchLater() 是什么？

这是 Chromium 里的新 API，让浏览器在页面离开时自动把延迟请求发出去。其他浏览器还不支持，用之前要做特性检测。
