sendBeacon 返回 true 就代表上报成功了吗？它发出的是什么样的请求？

不代表。返回 true 只说明浏览器把数据放进了发送队列，返回 false 多半是超出 64 KiB 的排队配额。它固定发 POST、带 Cookie、不能加请求头、读不到响应；数据类型不是 CORS 安全类型时，跨源会先发预检请求。

参考答案

简答

不代表。navigator.sendBeacon(url, data) 返回 true，只表示浏览器把数据放进了发送队列，之后什么时候发、服务端有没有收到、返回了什么，页面都无从得知。

返回 false 表示没能排队，常见原因是数据太大。规范给排队中的数据设了总量限制，MDN 写的是 64 KiB（65,536 字节），而且这份配额和 fetch 的 keepalive 请求共用。

它发出的请求是固定的：方法只能是 POST，会带上 Cookie，不能加自定义请求头，响应会被丢掉。请求的 Content-Type 由 data 的类型决定。

跨源时要看 Content-Type。没有数据，或者类型是 text/plain 这类 CORS 安全类型，请求用 no-cors 模式直接发出；如果是 application/json，浏览器会先发 CORS 预检，服务端要放行才行。

返回值到底说明了什么

先看最常见的误解：

JavaScript
const ok = navigator.sendBeacon('/api/collect', 'hello');
if (ok) {
  // 这里只能说明“已经排上队”，不能说明“服务端已收到”
}

sendBeacon 的设计目标就是不拖住页面：它不返回 Promise，也没有回调，浏览器在合适的时候把数据异步发出去，页面关闭后请求还能继续。代价就是页面拿不到任何结果。所以返回值只能用来判断“这次有没有塞进队列”。

那 false 时该怎么办？因为最常见的原因是配额满了，换成 fetch 的 keepalive 再试也会失败，二者共用配额。合理的做法是控制每次发送的体积，分批发送。分批和发送时机的整体方案见《页面关闭时怎样可靠上报？sendBeacon 和 keepalive 怎么选？》。

data 的类型决定请求长什么样

data 可以是字符串、Blob、FormData、URLSearchParams、ArrayBuffer 等。浏览器按 Fetch 规范从它提取请求体和 Content-Type：

data 类型Content-Type跨源时
字符串text/plain;charset=UTF-8不预检
URLSearchParamsapplication/x-www-form-urlencoded;charset=UTF-8不预检
FormDatamultipart/form-data; boundary=...不预检
BlobBlob 自己的 type看 type 是否是 CORS 安全类型

想发 JSON 时，常见写法是 new Blob([json], { type: 'application/json' })。这在同源下没问题，跨源时就会触发预检。规范的处理是：Content-Type 是 CORS 安全的值，就用 no-cors 模式；否则用 cors 模式，服务端得返回对应的 CORS 响应头。如果不想处理预检，可以直接传 JSON 字符串，让它以 text/plain 发出，服务端按文本解析。

JavaScript
const body = JSON.stringify({ id: crypto.randomUUID(), type: 'click' });
navigator.sendBeacon('https://log.example.com/collect', body); // 以 text/plain 发出，跨源不预检

不能改的部分

规范里 sendBeacon 的请求参数是写死的：方法 POST、凭据模式 include（会带 Cookie）、keepalive 打开。开发者没法加请求头，所以不能用 Authorization 做鉴权，只能靠 Cookie 或者 URL 里的参数。

MDN 也写明了：如果要用 POST 以外的方法、改请求属性或者读响应，应该改用带 keepalive: true 的 fetch()。

常见追问

sendBeacon 一定会把数据发出去吗？

不一定。它只保证页面卸载不会取消已经排队的请求，网络失败、服务端出错时页面都不知道，也不会重试。所以统计数据要允许丢失，每条带唯一 ID 方便服务端去重。

为什么带了 Cookie 还要担心跨站？

凭据模式是 include，但 Cookie 能不能带上还受 SameSite 等规则约束。跨站上报时第三方 Cookie 可能被浏览器拦截，用请求体里的匿名 ID 更稳妥。
