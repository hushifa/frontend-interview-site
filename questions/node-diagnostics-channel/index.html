Node.js 的 diagnostics_channel 适合解决什么问题？

diagnostics_channel 是进程内的命名发布订阅通道，库在关键操作处发布诊断事件，APM 和日志工具订阅这些事件，不需要给库打补丁。没有订阅者时发布几乎没有开销；tracingChannel 为一次调用统一提供开始、结束和错误事件。

参考答案

简答

监控工具想知道数据库查询花了多久、缓存有没有命中，以前常见的办法是去改写库里的函数，也就是打补丁。diagnostics_channel 换了个思路：库在关键位置往一个有名字的通道里发布事件，监控工具订阅同名通道，两边不需要互相依赖。它是进程内的发布订阅。

没人订阅的时候，发布几乎没有开销。发布前还可以用 channel.hasSubscribers 判断一下，没人听就连消息都不用构造。

如果要统计一次调用的耗时，可以用 tracingChannel，它为一次调用提供 start、end、asyncStart、asyncEnd、error 五个事件。它自 Node.js 19.9.0、18.19.0 提供，26.8.0 起标为稳定。

要注意，订阅回调是同步执行的，回调里抛错会触发 uncaughtException，回调慢了也会拖慢发布方，所以订阅者只做轻量的提取。另外通道只在当前进程内有效，没有历史记录，订阅之前发布的事件收不到。

发布和订阅是怎么写的

库这边创建一个通道，在缓存未命中时发布事件：

JavaScript
import diagnosticsChannel from 'node:diagnostics_channel';

const cacheMiss = diagnosticsChannel.channel('app.cache.miss');

export function getFromCache(key) {
  const value = cache.get(key);
  if (value === undefined && cacheMiss.hasSubscribers) {
    cacheMiss.publish({ key: key.split(':')[0] });
  }
  return value;
}

观测模块那边订阅同一个名字：

JavaScript
// 观测模块
diagnosticsChannel.subscribe('app.cache.miss', ({ key }) => {
  missCounter.add(1, { prefix: key });
});

两段代码之间没有任何 import 关系，靠的只是通道名 app.cache.miss。

你可能注意到，示例只发布了键的前缀，没有发布完整的键。因为完整的键里可能有用户 ID，变成指标标签以后取值太多（这叫高基数），也可能把敏感数据带进日志。消息里只放统计需要的字段。

Node.js 的内置模块自己也发布诊断事件，例如 http.client.request.start、undici:request:create。OpenTelemetry 等工具就是订阅这些通道来采集 HTTP 请求的，不用改应用代码。可用的通道名和消息结构以对应版本的文档为准。

怎样统计一次调用的耗时

只有一个事件的话，没法知道调用什么时候开始、什么时候结束。tracingChannel 把一次调用拆成了几个固定的事件：

JavaScript
const queryChannel = diagnosticsChannel.tracingChannel('app.db.query');

function query(sql) {
  return queryChannel.tracePromise(() => db.execute(sql), { sql });
}

queryChannel.subscribe({
  start(context) {
    context.startedAt = performance.now();
  },
  asyncEnd(context) {
    histogram.record(performance.now() - context.startedAt, {
      status: context.error ? 'error' : 'ok',
    });
  },
  end() {},
  asyncStart() {},
  error() {},
});

tracePromise 会把同一个 context 对象传给这五个事件。所以订阅者可以在 start 里往 context 上记一个开始时间，到 asyncEnd 里再读出来算耗时。调用失败时，context 上会带着 error。同步调用和回调式调用，分别用 traceSync 和 traceCallback。

它和日志、指标、追踪怎么分工

机制用途
diagnostics_channel进程内事件入口，连接库和观测工具
日志需要人阅读的事实和错误详情
指标计数、延迟、错误率的聚合和告警
追踪跨服务关联一次请求
审计记录支付、权限变更等必须留存的业务事实

诊断通道完全可能没有订阅者，事件发了也就丢了，所以审计记录不能依赖它。需要关联请求时，订阅者在回调里通过 AsyncLocalStorage 读当前请求 ID，见《AsyncLocalStorage 如何在 Node.js 请求链路中传递上下文？》。

常见追问

订阅者怎样避免影响业务请求？

回调里只提取字段，放进一个有上限的队列，由后台批量发送；回调内部自己捕获异常，不让错误冒出去。

测试里要注意什么？

每个用例结束时调用 unsubscribe，否则后面的用例会重复收到事件。

浏览器里有这个模块吗？

没有。同时跑在浏览器和 Node.js 里的库，应该把诊断代码做成可选的。
