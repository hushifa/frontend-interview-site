Playwright 接口模拟怎样覆盖成功和失败场景？

用 page.route 在请求发出前拦截，fulfill 返回假数据，abort 模拟断网，continue 或 fallback 放行。多个处理器按注册的相反顺序执行，route.fetch 可以拿到真实响应再改。

参考答案

简答

写端到端测试时，我们经常不想依赖真实后端，就用 page.route 把某个接口拦下来，自己决定它返回什么。拦截要在 page.goto() 或触发请求的操作之前注册，不然请求已经发出去了。

拦下来以后有四种处理：fulfill 直接返回一份自定义响应，不走网络；abort 让请求失败，模拟断网；continue 放它去真实网络；fallback 交给前面注册的另一个处理器。

同一个请求匹配多个处理器时，后注册的先执行。所以可以在 beforeEach 里放一个默认的成功响应，个别测试再注册一个失败响应把它盖掉。

要注意，服务端返回 500 和网络根本没通是两种情况，前端的提示通常也不一样，要分开测。另外 page.route 只管当前页面，context.route 还能管到弹出窗口；页面注册了 Service Worker 时请求可能绕过拦截，可以把 serviceWorkers 设成 'block'。

怎样分别测成功、服务端错误和断网

下面三个测试共用一个默认的成功响应，后两个各自换成失败情况。

TypeScript
import { test, expect } from '@playwright/test';

test.beforeEach(async ({ page }) => {
  await page.route('**/api/orders', (route) =>
    route.fulfill({ json: [{ id: 1, title: '键盘' }] }),
  );
});

test('显示订单', async ({ page }) => {
  await page.goto('/orders');
  await expect(page.getByText('键盘')).toBeVisible();
});

test('服务端错误时显示重试按钮', async ({ page }) => {
  await page.route('**/api/orders', (route) =>
    route.fulfill({ status: 500, json: { message: 'internal error' } }),
  );
  await page.goto('/orders');
  await expect(page.getByRole('button', { name: '重试' })).toBeVisible();
});

test('断网时提示检查网络', async ({ page }) => {
  await page.route('**/api/orders', (route) => route.abort('internetdisconnected'));
  await page.goto('/orders');
  await expect(page.getByText('网络连接失败')).toBeVisible();
});

你可能会问，beforeEach 里已经注册过成功响应了，后面两个测试为什么还能拿到失败？因为同一个请求匹配多个处理器时，后注册的先执行。测试里新注册的处理器直接返回了结果，beforeEach 里那个就轮不到了。

status: 500 和 abort() 的区别在于，前者是请求到了服务器、服务器说出错了，fetch 会正常拿到一个 ok 为 false 的响应；后者是请求根本没完成，fetch 会直接抛错。前端往往一个显示“重试”，一个显示“检查网络”，所以要各写一个用例。

怎样检查前端发出去的请求对不对

有时要验证的不是页面显示，而是前端提交的数据。这时监听请求本身：

TypeScript
test('提交订单时发送正确的数据', async ({ page }) => {
  await page.goto('/checkout');
  const requestPromise = page.waitForRequest('**/api/orders');
  await page.getByRole('button', { name: '提交' }).click();
  const request = await requestPromise;
  expect(request.postDataJSON()).toMatchObject({ productId: 1, quantity: 2 });
});

注意 waitForRequest 写在点击之前。如果先点击再开始等，请求可能在监听开始前就已经发完了，测试就会一直等到超时。

怎样在真实响应上只改一个字段

如果只想改真实接口里的某个字段，可以先用 route.fetch() 把请求发出去，拿到真实响应，再改完返回：

TypeScript
await page.route('**/api/profile', async (route) => {
  const response = await route.fetch();
  const json = await response.json();
  await route.fulfill({ response, json: { ...json, vip: true } });
});

这种写法依赖真实后端可用，适合在测试环境里看某个字段对界面的影响，比如把用户临时变成 VIP。

处理器写错了会怎样

每个处理器最后都必须调用 fulfill、abort、continue、fallback 中的一个。忘了调用，请求就一直挂着，页面也一直在加载。为了模拟慢响应而故意攒着的延迟 Promise，测试结束时也要放掉。

continue 和 fallback 容易混。一个处理器发现这个请求不归自己管时，应该用 fallback，交给前面注册的默认模拟；用 continue 会直接去真实网络，把其他模拟都绕过去。两者都可以改写请求方法、请求体和部分请求头，但受限的请求头不能随便改，Cookie 要用上下文的 Cookie API 设置。

还有几条规则要记住。同一个请求同时匹配页面级和上下文级路由时，页面级优先。开启路由会禁用浏览器的 HTTP 缓存，所以这类测试不能用来判断真实的缓存行为。移除规则用 page.unroute() 或 page.unrouteAll()，后者的 behavior 选项决定要不要等正在执行的处理器：'wait' 等它们完成，'ignoreErrors' 不等并吞掉之后的错误，默认是不等。

模拟数据有什么风险

模拟数据是手写的，后端接口改了，测试照样通过。可以从 OpenAPI 生成模拟数据，或者用契约测试保证前后端一致，见《前端契约测试应该验证什么？》。也可以用 routeFromHAR 把录下来的真实流量当作模拟数据回放。

常见追问

Playwright 的 route 和 MSW 有什么区别？

MSW 在应用内部拦截，浏览器里靠 Service Worker，Node 里靠拦截请求模块，所以同一套模拟能同时用在开发环境、单元测试和端到端测试里。Playwright 的 route 只能在 Playwright 测试里用，但它在浏览器层拦截，任何请求都能管到，包括第三方资源。
