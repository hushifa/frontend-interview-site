CSP Report-Only 和违规报告怎样用于安全治理？

通过 Content-Security-Policy-Report-Only 观察潜在违规，再逐步收紧策略，避免上线即阻断真实资源。

参考答案

Content-Security-Policy-Report-Only 只报告违规，不阻止资源执行，适合在正式启用前发现脚本、样式、图片和第三方服务依赖。正式 CSP 才会真正限制浏览器行为。

策略应从明确的资源来源开始收紧，逐步处理内联脚本、动态代码、nonce/hash、第三方分析和 iframe。报告端点会收到浏览器生成的数据，必须限制日志大小、做去重和脱敏，不能把报告内容直接当成可信输入。

Report-Only 发现“没有报告”也不代表策略完整；浏览器支持、未覆盖的页面和未触发的路径都可能隐藏问题。部署正式策略后仍应监控误报、业务失败和新依赖。

安全问题先画出数据流和信任边界：哪些值来自用户、第三方页面、接口响应或浏览器存储，哪些代码拥有真正的权限。防护措施应放在能控制风险的边界上，客户端校验主要用于改善体验，不能代替服务端校验和授权。

验证修复时要覆盖正常流程、攻击输入、错误提示和日志脱敏。安全配置还会受到部署代理、响应头、Cookie 属性和跨域策略影响，不能只在组件代码里判断“已经安全”。

实际落地时，攻击输入往往会经过多个层：URL、表单、接口响应、富文本和第三方窗口。每一层都应明确编码、解析和授权责任，不能因为上游做过一次校验就把数据标记为可信。
