CSP Report-Only 和违规报告怎样用于安全治理？

新策略先用 Report-Only 下发，只收集违规、不拦截；把报告按页面、指令和资源归类，改完代码再切换成强制执行。正式策略和下一版的 Report-Only 策略可以同时存在。

参考答案

简答

直接上线一条严格的 CSP，很可能把某个页面的脚本拦掉，业务就挂了。所以先用 Content-Security-Policy-Report-Only 下发，它不拦截任何资源，只在违规时报告，可以在不影响业务的情况下验证策略。

报告发到哪里，用 Reporting-Endpoints 响应头定义端点，策略里用 report-to 引用。旧的 report-uri 已经废弃，过渡期可以两个都写，支持 report-to 的浏览器会忽略 report-uri。

收到报告后，按页面版本、effectiveDirective 和被阻止的资源归类。浏览器扩展和旧缓存会产生大量噪声，要筛掉。一个一个修完，再切换为强制执行。

要注意，没收到报告不代表策略没问题，可能是低频页面没人访问，也可能是报告链路本身没工作。另外 Report-Only 只能通过响应头下发，写在 <meta> 里无效。

怎么配置

http
Reporting-Endpoints: csp="https://reports.example.com/csp"
Content-Security-Policy-Report-Only: script-src 'nonce-R4nd0m' 'strict-dynamic'; object-src 'none'; base-uri 'none'; report-to csp

第一行给端点起名叫 csp，第二行的 report-to csp 就是引用这个名字。

已经有正式策略的网站，可以让正式策略和观察中的下一版同时存在：

http
Content-Security-Policy: script-src 'self'; report-to csp
Content-Security-Policy-Report-Only: script-src 'nonce-R4nd0m' 'strict-dynamic'; report-to csp

浏览器按第一行实际拦截，同时按第二行检查并报告。这样新策略可以在线上观察，不会影响现有的保护。

报告里有什么

Reporting API 发来的报告体里，有几个字段最常用。documentURL 是发生违规的页面。effectiveDirective 是被违反的指令，比如 script-src-elem、connect-src。blockedURL 是被阻止的资源，内联脚本显示为 inline，eval 显示为 eval。sourceFile 和 lineNumber 是触发的位置。disposition 区分来源，report 表示来自 Report-Only，enforce 表示已经实际拦截了。

旧的 report-uri 发来的格式不一样，是一个 csp-report 对象，字段名也不同，比如 violated-directive。所以过渡期接收端要两种都能解析。

从观察到强制执行的流程

  1. 部署 Report-Only，收集一到两周。
  2. 按指令和资源归类，区分业务资源、第三方脚本和浏览器扩展（常见 chrome-extension: 来源）。
  3. 修改代码：内联脚本加 nonce，内联事件改成 addEventListener，补上缺失的合法来源。
  4. 主动走一遍登录、支付、错误页等关键路径，并制造一个受控的违规，确认报告能到达。
  5. 切换为强制执行，保留报告继续监控。

第 4 步为什么要故意制造违规？因为前面说过，没有报告可能是链路坏了。自己触发一次、确认收到，才能相信“没报告”真的是没问题。

接收端本身也要防

报告是客户端发来的，任何人都可以伪造。所以接收端要限制请求体大小和频率，在后台展示时要对报告内容编码，否则报告系统自己就可能被 XSS。documentURL 可能带着查询参数里的个人信息，存储前要脱敏。

常见追问

违规报告太多怎么办？

不要为了让报告清零就放开 * 或 'unsafe-inline'，那样策略就没意义了。先按影响面排序，从影响最大的开始处理。

报告是实时发送的吗？

不是。浏览器可能攒一批再发，也可能延迟发，网络失败时还可能丢失。所以报告适合看趋势，不能当成完整的记录。
