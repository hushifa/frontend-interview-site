React 的渲染阶段与提交阶段有什么区别？

渲染阶段调用组件函数，计算出新的元素树并和上一次比较；提交阶段把差异应用到 DOM，再运行 Effect。渲染可能被中断、重复或丢弃，所以必须是纯计算；副作用只能放在提交之后。

参考答案

简答

  • 一次更新分三步：触发（初次渲染或 setState）→ 渲染（调用组件函数，计算新元素树并找出差异）→ 提交（修改 DOM，执行 ref 和 Effect）。
  • "组件重新渲染"指函数被重新调用，不等于 DOM 被重建；React 只修改有差异的节点。
  • 并发渲染中，渲染阶段可以被更高优先级的更新打断、重新开始，结果也可能被丢弃，只有提交阶段一定一次性完成。
  • 所以组件函数必须是纯函数：相同输入返回相同结果，不修改外部变量、不发请求、不操作 DOM。
  • 严格模式在开发环境会调用组件函数两次，用来暴露不纯的渲染逻辑。

一次更新的流程

JSX
function Counter() {
  const [count, setCount] = useState(0);
  console.log('render', count); // 渲染阶段
  useEffect(() => {
    console.log('effect', count); // 提交之后
  });
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}

点击后：setCount 安排更新 → React 调用 Counter 打印 render 1 → 比较发现只有按钮文字变了 → 提交时只更新这个文本节点 → 浏览器绘制，Effect 通常在此后打印 effect 1。

不纯渲染的问题

JSX
let renderCount = 0;

function Item({ title }) {
  renderCount++; // 错误：渲染时修改外部变量
  return <li>{title}（第 {renderCount} 次）</li>;
}

严格模式下每次渲染会执行两次，被中断重来的渲染也会计数，显示的数字和实际提交次数对不上。需要记录次数时用 ref 并在 Effect 里修改，需要显示就放进 state。

父组件渲染会带动子组件

父组件重新渲染时，默认会重新调用所有子组件函数，即使子组件的 props 没变。这通常很快，因为最终 DOM 改动很少。确实有性能问题时，用 memo 跳过子组件，或者启用 React Compiler，详见《memo、useMemo、useCallback 各自优化什么？》。

提交阶段的顺序

  1. 应用 DOM 变更。
  2. 设置 ref，执行 useLayoutEffect（同步，阻塞绘制）。
  3. 浏览器绘制。
  4. 执行 useEffect（通常在绘制之后）。

常见追问

  • 什么叫"协调"（reconciliation）？就是渲染阶段比较新旧元素树、决定如何更新的过程：类型不同就替换整棵子树，类型相同就复用并更新属性，列表按 key 匹配。
  • 渲染阶段能调用 setState 吗？只能在"根据 props 调整自身 state"这类特殊场景下有条件地调用，常规情况会造成无限循环。
