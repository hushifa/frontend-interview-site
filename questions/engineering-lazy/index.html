代码分割与懒加载适合哪些场景？

区分拆成多个文件与延后启动加载，用动态导入示例说明模块缓存、取消边界和生命周期，并解释预加载、错误恢复与旧版本资源问题。

参考答案

用户第一次打开文章页面，并不一定马上需要大型编辑器或图表模块。把这些低频功能留到需要时再获取，可以减少初始下载和执行压力。

代码分割决定代码怎样拆成不同资源块，懒加载决定什么时候开始取得或使用它们。一个应用虽然生成了多个文件，却仍可能在首屏一次加载全部文件，因此“分包了”不等于“懒加载了”。

动态导入怎样建立边界

下面的入口在用户需要备注编辑器时才导入相应模块：

JavaScript
export async function openNotes(container, { signal } = {}) {
  signal?.throwIfAborted();
  const { mountNotes } = await import('./notes-editor.js');
  signal?.throwIfAborted();
  return mountNotes(container);
}

notes-editor.js 提供实际的挂载与清理：

JavaScript
export function mountNotes(container) {
  const input = document.createElement('textarea');
  input.setAttribute('aria-label', '备注');
  container.replaceChildren(input);
  return () => input.remove();
}

构建器可以识别静态明确的动态导入路径，并生成相应异步块。调用方需要处理 openNotes 返回 Promise 的失败，获得清理函数后，在不再使用时调用它。

示例只展示加载与挂载边界，完整界面还需要加载提示、重复点击管理和失败后的操作入口。不要让用户点击后没有反馈地等待下载。

取消等待意图，不等于取消模块下载

原生 import() 没有通用的 AbortSignal 下载取消参数。示例在导入前后检查信号，是为了用户关闭功能后不再挂载旧界面，不是让传输中的 JavaScript 一定停止下载。

若调用者没有把组件生命周期与信号或版本检查关联起来，模块加载完成后仍可能覆盖已经变化的页面。已经挂载后又离开，则还需要调用返回的清理函数。

同一功能多次打开时，也应明确是否复用实例、是否先卸载旧实例。模块缓存与界面实例生命周期不是同一件事。

模块通常会缓存，但不是所有失败都能原样重试

同一个模块标识在同一执行环境中成功加载和执行后，后续 import 通常复用相应模块，不会每次重新执行全部顶层代码。再次调用导出的 mountNotes，仍可以创建新的界面实例。

加载、链接与执行是不同阶段。网络加载失败可能有再次获取机会，但模块执行时抛出的错误会按模块机制缓存，重复导入相同标识不等于重新从头执行。

把保存的 Promise 设回 undefined，不能保证修复所有动态导入失败。也不要不断附加随机查询参数强行绕过缓存，否则可能增加内存、重复执行副作用并破坏版本管理。

哪些边界通常值得考虑

非首屏路由、大型编辑器、低频弹窗、不同语言或格式的处理器，通常比一组很小的基础函数更适合作为边界。首屏主要内容和马上需要的交互，则不宜机械地全部推迟。

依赖也要一起分析。若主入口已经静态导入了同一个大库，后来给某个功能增加 import()，并不保证它就从初始路径消失。

动态路径需要让构建器能够识别候选范围，或者通过明确映射和相应工具能力建立白名单。任意运行时字符串并不保证都能被打包成正确的本地资源。

预取可以减少首次点击等待，但会重新占用资源

用户接近入口、明确表现出使用意图或页面有合适空闲机会时，可以提前准备可能需要的代码。这样是在初始成本和后续等待之间做取舍，不是免费加速。

如果把所有懒块都立即预加载，就可能重新引入原本希望减少的首屏流量。网络条件、设备资源和命中概率不同，策略也应有界。

框架的 lazy、Suspense 或路由加载能力可以帮助表达等待，但数据加载、资源错误和重试仍需要对应处理，不能只有一个永远不退出的 loading。

发布新版本后，旧页面可能还引用旧块

已经打开的页面可能持有旧入口，其中动态导入地址仍是旧哈希文件。如果部署时删除旧资源，用户稍后打开那个功能就可能遇到 404。

项目可以根据发布策略选择提供版本窗口，或明确检测加载失败并引导安全刷新；若选择只保留最新产物，也需要理解这种已打开页面的恢复问题。刷新前应考虑未保存输入，不能无限自动刷新来掩盖错误。

服务工作线程和 CDN 缓存还可能增加版本组合，入口、异步块与缓存策略应一起验证。

最后同时看两种等待

一方面检查初始 JS 与首屏关键路径是否减少，另一方面检查首次打开懒功能要等多久。拆成更多块也可能增加请求、重复模块或调度成本，不能只看某一个文件缩小了多少。

懒加载的目标是让用户先承担当前真正需要的成本，并在后续需要时可靠地提供功能，而不是单纯追求更多 chunk 文件。
