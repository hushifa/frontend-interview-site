如何用拓扑排序解析前端任务和模块依赖？

拓扑排序把有依赖关系的任务排成一个序列，使每个任务都排在它依赖的任务之后，常见于构建任务编排、插件加载和 monorepo 包构建。Kahn 算法统计每个节点的入度，从无依赖的节点开始逐层输出，剩余节点无法输出时说明存在循环依赖。

参考答案

简答

  • 拓扑排序适用于有向无环图，输出中每个节点都排在它依赖的节点之后，结果通常不唯一。
  • Kahn 算法：入度表示一个节点还有几个依赖没完成，入度为 0 的节点进入队列；每输出一个节点，就把依赖它的节点入度减 1。
  • 用队列下标代替 shift()，时间复杂度是 O(V + E)，V 是节点数，E 是依赖边数。
  • 所有节点处理完后，输出数量少于节点数，剩下入度大于 0 的节点就处在环上或依赖环上的节点。
  • 同一批入度为 0 的节点之间没有依赖，可以并行执行，这是 Turborepo、Nx 这类工具调度构建的基础。

建模

输入写成"节点 → 它依赖的节点"：

JavaScript
const tasks = new Map([
  ['build', ['lint', 'types']],
  ['lint', ['install']],
  ['types', ['install']],
  ['install', []],
  ['deploy', ['build']],
]);

build 依赖 lint 和 types，所以它们必须排在 build 前面。算法内部需要反向的映射"节点 → 依赖它的节点"，在某个节点完成时找到下一批可以开始的节点。

Kahn 算法

JavaScript
function orderByPrerequisites(dependencies) {
  const indegree = new Map();
  const dependents = new Map();
  for (const name of dependencies.keys()) {
    indegree.set(name, 0);
    dependents.set(name, []);
  }

  for (const [name, required] of dependencies) {
    // 去重，避免同一依赖写两次导致入度多算。
    for (const dependency of new Set(required)) {
      if (!dependencies.has(dependency)) {
        throw new Error(`缺少依赖：${name} 需要 ${dependency}`);
      }
      indegree.set(name, indegree.get(name) + 1);
      dependents.get(dependency).push(name);
    }
  }

  const queue = [...indegree].filter(([, count]) => count === 0).map(([name]) => name);
  const order = [];
  for (let head = 0; head < queue.length; head++) {
    const current = queue[head];
    order.push(current);
    for (const next of dependents.get(current)) {
      const count = indegree.get(next) - 1;
      indegree.set(next, count);
      if (count === 0) queue.push(next);
    }
  }

  if (order.length !== dependencies.size) {
    const blocked = [...indegree].filter(([, count]) => count > 0).map(([name]) => name);
    throw new Error(`存在循环依赖：${blocked.join(', ')}`);
  }
  return order;
}

console.log(orderByPrerequisites(tasks));
// ['install', 'lint', 'types', 'build', 'deploy']

实测覆盖了空图、重复依赖、缺失依赖、a ↔ b 环，并用 500 个随机生成的无环图校验"每个依赖都排在使用者之前"。

复杂度：建图时每条边处理一次，出队循环中每个节点出队一次、每条边减一次入度，合计 O(V + E)。如果用 queue.shift()，每次出队要移动数组元素，最坏会退化成 O(V²)；需要输出顺序稳定时对就绪节点排序，又会多出排序成本。

环检测的结果

a → b → a 之外还有一个独立的 c 时，算法会输出 c，然后报告 a, b 无法排序。blocked 里的节点不一定都在环上：依赖了环上节点的节点同样入度无法归零。需要准确报告环的路径时，可以用 DFS 的"访问中"状态找出回边，见《前端场景中的图遍历应该怎样建模？》。

并行调度

按"层"处理就能得到并行计划：第一层是 install，第二层是 lint 和 types，它们可以同时运行。实际调度器在某个任务完成时立即把新变为 0 入度的任务放进执行池，并限制同时运行的数量，不必等整层结束。

常见追问

  • 为什么结果不唯一？ 同时就绪的多个节点之间没有先后要求，先处理哪个都正确。需要可复现的顺序（例如生成稳定的构建日志）时，对就绪队列按名称排序。
  • npm 安装依赖也是拓扑排序吗？ 包的安装顺序和生命周期脚本的执行要满足依赖关系；但 npm 允许循环依赖，需要先打破环再排序，不能直接报错。
