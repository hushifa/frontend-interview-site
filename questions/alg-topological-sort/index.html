如何用拓扑排序解析前端任务和模块依赖？

拓扑排序是把有依赖关系的任务排成一列，保证每个任务都排在它依赖的任务后面，常用在构建任务编排、插件加载、monorepo 包构建。Kahn 算法先数清每个节点还有几个依赖没完成，从没有依赖的开始一层层输出，最后还剩节点排不出来，就说明有循环依赖。

参考答案

简答

拓扑排序就是给有依赖关系的任务排个先后：每个任务都要排在它依赖的任务后面。比如 build 依赖 lint，lint 就得先跑。它只适用于没有环的有向图，结果通常不唯一。

常用的是 Kahn 算法。每个节点有一个入度，表示它还有几个依赖没完成。入度为 0 的节点可以开始了，放进队列；每输出一个节点，就把依赖它的那些节点的入度减 1，减到 0 的也放进队列。用下标读队列而不是 shift()，时间复杂度是 O(V + E)，V 是节点数，E 是依赖关系的条数。

怎么发现循环依赖？全部处理完以后，如果输出的数量比节点总数少，剩下那些入度还大于 0 的节点，要么在环上，要么依赖了环上的节点。

还有一个实际用处：同一批入度为 0 的节点之间没有依赖，可以并行跑。Turborepo、Nx 这类工具调度构建，就是基于这一点。

先把依赖写成图

输入写成“节点 → 它依赖哪些节点”：

JavaScript
const tasks = new Map([
  ['build', ['lint', 'types']],
  ['lint', ['install']],
  ['types', ['install']],
  ['install', []],
  ['deploy', ['build']],
]);

build 依赖 lint 和 types，所以它俩要排在 build 前面。

可是算法运行时，需要的是反过来的信息。某个节点做完了，我们要马上知道“谁在等它”，好把它们的入度减 1。所以算法内部会再建一张反向的表：“节点 → 依赖它的节点”。

Kahn 算法

JavaScript
function orderByPrerequisites(dependencies) {
  const indegree = new Map();
  const dependents = new Map();
  for (const name of dependencies.keys()) {
    indegree.set(name, 0);
    dependents.set(name, []);
  }

  for (const [name, required] of dependencies) {
    // 去重，避免同一依赖写两次导致入度多算。
    for (const dependency of new Set(required)) {
      if (!dependencies.has(dependency)) {
        throw new Error(`缺少依赖：${name} 需要 ${dependency}`);
      }
      indegree.set(name, indegree.get(name) + 1);
      dependents.get(dependency).push(name);
    }
  }

  const queue = [...indegree].filter(([, count]) => count === 0).map(([name]) => name);
  const order = [];
  for (let head = 0; head < queue.length; head++) {
    const current = queue[head];
    order.push(current);
    for (const next of dependents.get(current)) {
      const count = indegree.get(next) - 1;
      indegree.set(next, count);
      if (count === 0) queue.push(next);
    }
  }

  if (order.length !== dependencies.size) {
    const blocked = [...indegree].filter(([, count]) => count > 0).map(([name]) => name);
    throw new Error(`存在循环依赖：${blocked.join(', ')}`);
  }
  return order;
}

console.log(orderByPrerequisites(tasks));
// ['install', 'lint', 'types', 'build', 'deploy']

跟着例子走一遍。一开始只有 install 入度是 0，先输出它。lint 和 types 都只依赖 install，入度从 1 减到 0，进队列。输出 lint，build 的入度从 2 减到 1，还不能开始；再输出 types，build 减到 0，进队列。最后是 build 和 deploy。

建图时为什么要 new Set(required) 去重？如果有人把同一个依赖写了两遍，入度就会多算 1，而这个依赖完成时只会减一次，这个节点就永远等不到 0，被误报成循环依赖。

实测覆盖了空图、重复依赖、缺失依赖、a ↔ b 这样的环，并用 500 个随机生成的无环图检查“每个依赖都排在使用者前面”，都通过了。

复杂度方面，建图时每条边处理一次；出队循环里每个节点出队一次，每条边减一次入度，加起来是 O(V + E)。如果用 queue.shift()，每次出队都要挪动整个数组，最坏会变成 O(V²)。另外，如果要求输出顺序固定，还要对就绪的节点排序，又会多出排序的开销。

发现环以后，报告的是什么

假设有 a → b → a 这个环，另外还有一个独立的 c。算法会正常输出 c，然后报告 a, b 排不出来。

要注意，blocked 里的节点不一定都在环上。一个节点如果依赖了环上的节点，它的入度也永远降不到 0，也会出现在 blocked 里。如果需要准确地报出环的路径，可以用 DFS 的“访问中”状态去找绕回来的那条边，见《前端场景中的图遍历应该怎样建模？》。

怎么并行调度

按“层”来看，就是一份并行计划：第一层是 install，第二层是 lint 和 types，它俩可以同时跑。

实际的调度器还能做得更好：不必等整层结束，某个任务一完成，就马上把新变成入度 0 的任务放进执行池，同时限制同时运行的数量。

常见追问

为什么结果不唯一？

同时就绪的几个节点之间没有先后要求，先处理哪个都对。如果需要每次结果都一样，比如要生成稳定的构建日志，就对就绪队列按名称排个序。

npm 安装依赖也是拓扑排序吗？

包的安装顺序和生命周期脚本的执行要满足依赖关系，这点是一样的。但 npm 允许循环依赖，它要先把环打破再排序，不能像上面那样直接报错。
