Node.js 的子进程、Worker 和集群应该怎样选择？

Worker Threads 在同一进程里运行 CPU 密集的 JavaScript；child_process 启动独立进程执行外部命令或隔离代码；cluster 复制多个服务进程共享端口来利用多核。三者的隔离程度、通信成本和出故障时的影响范围不同。

参考答案

简答

这三个东西解决的是三种不同的问题。一个请求里有一段很重的计算，比如压缩、加密，用 Worker Threads，它是同一进程里的另一个线程，启动和通信成本最低，可它崩溃或内存泄漏会影响整个进程。

要调用外部程序，比如 ffmpeg、git、图片工具，用 child_process。它启动的是独立进程，子进程崩溃不会拖垮主进程，所以也适合隔离不稳定的代码。

想让一个 HTTP 服务用满多核 CPU，用 cluster，或者在容器层面多跑几个实例。每个进程都是一份完整的服务副本。

要注意，这三者都不是安全沙箱，子进程默认继承当前用户的全部权限。

区别的关键在“是不是同一个进程”。Worker 和主线程在同一个进程里，所以通信便宜，但一损俱损；子进程和 cluster 的工作进程是独立的，内存不共享，通信要走管道或 IPC，代价是隔离更好。

调用外部命令要注意什么

下面用 execFile 读取最近一次提交的哈希：

JavaScript
import { execFile } from 'node:child_process';
import { promisify } from 'node:util';

const run = promisify(execFile);

const { stdout } = await run('git', ['log', '-1', '--format=%h'], {
  timeout: 5000,
  maxBuffer: 1024 * 1024,
});

为什么不用更简单的 exec？因为 exec 会把整条命令交给 shell 解析，如果把用户输入拼进命令字符串，用户就能塞进 ; 之类的符号执行别的命令，这叫命令注入。execFile 或 spawn 用数组传参，参数不经过 shell。

timeout 和 maxBuffer 也不是摆设，它们防止外部程序卡住不返回，或者输出太多把服务的内存撑爆。

输出量很大或者需要边读边处理时，用 spawn。它通过流返回 stdout，不会把全部输出攒在内存里。

cluster 和容器怎么选

cluster 的做法是主进程监听端口，再把连接分给多个工作进程；某个工作进程挂了，主进程可以重新 fork 一个。

在 Kubernetes 这类容器平台上，更常见的是每个容器只跑一个 Node.js 进程，扩缩容和重启交给平台。这样监控、日志和资源限制都按容器来管，比较清楚。

不管哪种方式，多个进程之间都不共享内存。会话、限流计数、缓存这些状态要放到 Redis 等外部存储里。否则同一个用户的请求落到不同进程，会看到不同的数据。

Worker 的通信与任务池细节？

见《Node.js Worker Threads 适合解决什么问题？》和《Node.js 为什么要用 Worker Threads 任务池？》。

怎样限制子进程的权限？

用操作系统层面的隔离，比如低权限用户、容器、seccomp。Node.js 的权限模型（--permission，v22.13.0 和 v23.5.0 起稳定）开启后，默认禁止访问文件系统、创建子进程和 Worker，需要用 --allow-fs-read、--allow-child-process、--allow-worker 等参数逐项放开。它防的是代码误用权限，代替不了操作系统隔离。
