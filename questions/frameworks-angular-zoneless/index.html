Angular Zoneless 模式会改变哪些更新假设？

Zoneless 不再依赖 Zone.js 广泛拦截异步任务，而是根据 Signal、事件、输入和显式通知判断哪些视图需要更新。外部回调、SSR 稳定性和测试写法都要重新检查。

参考答案

变化的是通知来源，不是异步任务消失

依赖 Zone.js 时，Angular 可以借助异步任务拦截安排更广泛的检查；Zoneless 更依赖框架能识别的更新通知。外部回调仍然会执行，但普通字段被修改后，框架不一定知道哪个视图需要重新检查。

项目要先确认 Angular 版本和启动配置。官方版本的默认行为会变化，旧项目也可能显式保留 Zone 配置。不能只看 package.json 是否存在 zone.js 就判断真实运行模式。

用 Signal 或明确通知连接外部状态

模板读取的 Signal 发生变化、Angular 管理的事件回调、ComponentRef.setInput、markForCheck 和 AsyncPipe 等都能提供视图更新信号：

TypeScript
@Component({
  selector: 'app-status',
  standalone: true,
  template: `<p>{{ status() }}</p>`,
})
export class StatusComponent {
  readonly status = signal('等待结果');

  receiveExternalResult(value: string) {
    this.status.set(value);
  }
}

如果第三方 SDK 只修改普通字段，不能依赖过去的 Zone 行为自动刷新。可以把外部结果写入 Signal，使用 AsyncPipe，或在明确场景调用 ChangeDetectorRef.markForCheck。不要用全局 detectChanges() 到处补洞，它会扩大检查范围并掩盖状态边界。

OnPush 和 Zoneless 不是一回事

OnPush 是组件的检查策略，Zoneless 是框架如何获得更新通知。OnPush 的不可变输入、明确状态和局部更新习惯通常有帮助，但不是把所有组件改成 OnPush 就等于启用 Zoneless，也不是必须依赖 OnPush 才能工作。

即使一次点击偶然让旧字段显示出来，也不能证明外部更新路径正确。要确认数据来源、模板读取和通知之间存在稳定关系。

第三方回调是迁移的主要风险

图表、编辑器、原生 DOM 监听、WebSocket 和定时器都可能在 Angular 外部回调。逐个检查它们是否把结果交给 Signal、Observable + AsyncPipe 或显式通知，而不是只删除 Zone.js 后观察首页能否打开。

依赖 NgZone.onStable 推断任务结束的旧代码也要重新评估；没有 Zone 时，它不再描述相同的生命周期。runOutsideAngular 也不是唯一的性能边界，先明确哪些状态需要更新，再选择最小通知。

SSR 和 hydration 还需要管理异步稳定性

客户端看到更新，不代表服务端在生成 HTML 时等待了同一任务。移除 Zone 后，自定义异步工作不能自动假设会被 SSR 稳定性捕获，需要按 Angular 的 PendingTasks 或框架集成机制登记必须完成的工作。

路由、数据加载和 hydration 有各自的协作协议。要分别测试服务端初始 HTML、客户端接管、异步数据到达和失败恢复，不能用浏览器刷新结果推断 SSR 正确。

测试不要用手动刷新掩盖缺失通知

如果每个测试动作后都调用 fixture.detectChanges()，可能让测试通过，但真实页面在缺少通知时不会更新。测试应尽量按实际交互等待可观察结果，只有在需要诊断时才手动触发检查。

迁移还要检查 polyfills、zone testing、假计时器和第三方库要求。去掉 Zone 之前先确认所有运行和测试路径都不再依赖它。Zoneless 能减少不必要的拦截并让更新来源更明确，但不会自动优化昂贵模板、大列表和重复计算，仍需用真实交互和性能数据验证收益。
