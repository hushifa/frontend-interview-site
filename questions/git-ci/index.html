GitHub Actions 中 workflow、job、step 和 runner 是什么关系？

用一个前端检查流程讲清 workflow、job、step、runner 四个层级：workflow 由 push、pull_request 等事件触发，job 默认并行、各占一台全新的 runner，step 在同一个 job 里按顺序执行并共享文件；再用 strategy.matrix 一次在多个系统和 Node 版本上跑测试。

参考答案

简答

workflow 是一整条自动化流程，写在 .github/workflows/ 下的一个 YAML 文件里，由 push、pull_request、定时等事件触发。

一个 workflow 里有多个 job，job 默认并行执行，要排先后就用 needs。每个 job 跑在一台独立的 runner 上，runner 就是实际执行的虚拟机或容器，所以 job 之间不共享文件。job 里面是一串按顺序执行的 step，每个 step 运行一条 shell 命令或者调用一个现成的 action，同一个 job 里的 step 共享工作目录。

要在多个 Node 版本或系统上跑同一套测试，用 strategy.matrix 列出取值，GitHub 会为每个组合启动一个 job。

要注意，job 之间传文件要靠产物（artifact）上传和下载，检查跑通了也不等于网站已经部署。缓存与产物的区别和部署阶段的设计见《前端 CI/CD 流水线怎样设计？》。

一个前端检查流程

下面的 workflow 有两个 job：check 负责检查和构建，e2e 拿构建结果跑端到端测试。

yaml
# .github/workflows/ci.yml
name: 检查与构建
on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - run: npm run format:check
      - run: npm run check
      - run: npm run build
      - uses: actions/upload-artifact@v7
        with:
          name: dist
          path: dist

  e2e:
    needs: check
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/download-artifact@v8
        with:
          name: dist
          path: dist
      - run: npx playwright test

你可能会奇怪，e2e 为什么又要 checkout 一遍代码？因为它跑在另一台全新的 runner 上，check 那台机器上的文件它一个都看不到。同样的道理，dist 也不能直接用，要靠 check 上传成产物，e2e 再下载下来。

needs: check 让 e2e 等 check 成功后再开始。没写 needs 的话，两个 job 会同时启动。

四个层级的关系

层级作用隔离性
workflow定义何时触发、包含哪些 job每次触发是一次独立运行
job一组在同一台机器上执行的步骤每个 job 一台全新的 runner
step一条命令或一个 action同一 job 内共享文件和环境
runner实际执行的机器GitHub 托管或自托管

某个 step 失败后，后面的 step 默认跳过，这个 job 失败，依赖它的 job 也不会运行。所以上例里格式检查没过，就不会去构建，也不会跑端到端测试。

什么事件会触发 workflow

on 决定 workflow 什么时候运行。上例写了两种事件：pull_request 在合并请求创建或更新时触发，push 加上 branches: [main] 只在推送到 main 分支时触发。常见的还有 schedule，用 cron 语法定时运行；workflow_dispatch，在仓库的 Actions 页面上手动点按钮运行。

一次触发对应一次 workflow 运行（run），运行页面上能看到每个 job 和每个 step 的日志。

矩阵怎样一次跑多个环境

想同时在 Node 22 和 24 上跑测试，不用复制两个 job，用 strategy.matrix 声明变量的取值，GitHub 会为每个取值组合启动一个独立的 job：

yaml
jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      matrix:
        os: [ubuntu-latest, windows-latest]
        node: [22, 24]
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: ${{ matrix.node }}
      - run: npm ci
      - run: npm test

两个系统乘两个版本，一共 4 个 job，默认并行执行。每个 job 里用 ${{ matrix.node }} 读到自己那一组的值。矩阵里某个 job 失败时，默认会取消同一矩阵里其他还在跑的 job，想让它们都跑完可以设置 fail-fast: false。

和部署流水线的分工

上面的 workflow 只做检查和构建，没有把产物放到任何网站上，所以检查成功不等于已经部署。缓存和产物该怎样分工、部署凭证怎样管理、检查和部署阶段怎样拆开，见《前端 CI/CD 流水线怎样设计？》。

常见追问

job 之间怎样传一个字符串值？

在上游 job 里用 outputs 声明输出，下游 job 通过 needs.<job>.outputs.<name> 读取。传文件要用产物，因为两个 job 不在同一台 runner 上。

runner 一定是 GitHub 提供的吗？

不一定。runs-on: ubuntu-latest 用的是 GitHub 托管的 runner，每个 job 一台全新的虚拟机。也可以在自己的机器上安装 runner 程序，注册成自托管 runner，适合需要特殊硬件或内网访问的场景。
