GitHub Actions 中 workflow、job、step 和 runner 是什么关系？

用一个前端检查流程讲清 workflow、job、step、runner 四个层级，执行环境怎样隔离、数据怎样传递，区分顺序、缓存与产物，并说明检查成功不等于已经部署。

参考答案

简答

workflow 是一整条自动化流程，写在 .github/workflows/ 下的一个 YAML 文件里，由 push、pull_request、定时等事件触发。

一个 workflow 里有多个 job，job 默认并行执行，要排先后就用 needs。每个 job 跑在一台独立的 runner 上，runner 就是实际执行的虚拟机或容器，所以 job 之间不共享文件。job 里面是一串按顺序执行的 step，每个 step 运行一条 shell 命令或者调用一个现成的 action，同一个 job 里的 step 共享工作目录。

数据传递要分清缓存和产物。缓存用来让依赖安装更快，产物（artifact）用来在 job 之间或者流水线结束后传递构建结果。

还要注意，检查流程跑通了，不等于网站已经部署。部署要另外的步骤或 workflow。

一个前端检查流程

下面的 workflow 有两个 job：check 负责检查和构建，e2e 拿构建结果跑端到端测试。

yaml
# .github/workflows/ci.yml
name: 检查与构建
on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - run: npm run format:check
      - run: npm run check
      - run: npm run build
      - uses: actions/upload-artifact@v7
        with:
          name: dist
          path: dist

  e2e:
    needs: check
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/download-artifact@v8
        with:
          name: dist
          path: dist
      - run: npx playwright test

你可能会奇怪，e2e 为什么又要 checkout 一遍代码？因为它跑在另一台全新的 runner 上，check 那台机器上的文件它一个都看不到。同样的道理，dist 也不能直接用，要靠 check 上传成产物，e2e 再下载下来。

needs: check 让 e2e 等 check 成功后再开始。没写 needs 的话，两个 job 会同时启动。

四个层级的关系

层级作用隔离性
workflow定义何时触发、包含哪些 job每次触发是一次独立运行
job一组在同一台机器上执行的步骤每个 job 一台全新的 runner
step一条命令或一个 action同一 job 内共享文件和环境
runner实际执行的机器GitHub 托管或自托管

某个 step 失败后，后面的 step 默认跳过，这个 job 失败，依赖它的 job 也不会运行。所以上例里格式检查没过，就不会去构建，也不会跑端到端测试。

缓存和产物有什么区别

缓存是为了快。setup-node 的 cache: npm 按锁文件的哈希缓存 npm 的下载目录，下次命中了，安装就快很多。但是缓存可能失效或被清掉，流程不能依赖它一定存在。

产物是为了传结果。upload-artifact 把构建结果保存下来，后面的 job 可以下载，也可以在运行页面上手动下载。上例中 e2e 直接用 check 构建出的 dist，避免重复构建。

检查成功为什么不等于已部署

这个 workflow 只做检查和构建，产物在运行结束后按保留期过期，没有被放到任何网站上。部署需要单独的步骤或 workflow，比如推送到托管仓库、上传到对象存储，或者用 GitHub Pages 的部署 action，通常还会配置环境（environment）审批和单独的权限。

权限和安全要注意什么

用 permissions 把默认的 GITHUB_TOKEN 权限降到最低，只在确实需要时才给写权限，上例就只给了 contents: read。

来自 fork 的 pull_request 默认拿不到仓库的 secrets。不要为了方便改用 pull_request_target 去运行不可信的代码，那样外部代码就能接触到 secrets。

第三方 action 可以固定到提交哈希，防止有人把标签改指到恶意代码上。

常见追问

怎样同时在多个 Node 版本上测试？

用 strategy.matrix 声明版本列表，GitHub 会为每个组合启动一个 job。

job 之间怎样传一个字符串值？

在上游 job 里用 outputs 声明输出，下游 job 通过 needs.<job>.outputs.<name> 读取。
