MCP、模型工具调用和聊天界面是什么关系？

MCP 规定宿主、客户端与服务器交换工具、资源和提示的协议；模型只提出调用建议，应用仍负责授权、参数校验、执行状态、用户确认和结果恢复。

参考答案

三个概念解决不同问题

MCP 解决 AI 应用如何接入外部能力；模型工具调用表达“我建议使用哪个工具和参数”；聊天或 Agent 界面负责让用户看到过程、确认风险和查看结果。接入 MCP 服务器不会自动生成完整 Agent，也不会让模型获得用户权限。

典型链路是：

text
用户任务
  → 宿主选择允许的能力
  → 模型提出工具调用
  → 应用校验参数与授权
  → MCP Client 调用 Server
  → 应用检查结果并更新界面/继续任务

模型不是拿到一个可以直接执行的系统函数指针。应用决定哪些工具描述进入上下文，执行端再决定调用是否真的允许。

Host、Client、Server 的职责边界

Host 是协调模型、用户体验和连接的宿主应用，可以管理多个 MCP Client；每个 Client 与对应的 MCP Server 建立协议连接；Server 暴露工具、资源和提示能力。Server 描述的是协议角色，不代表一定部署在云端，Client 也不一定运行在浏览器。

宿主负责认证、服务器选择、上下文隔离和授权边界，不能把发现到的所有工具无条件交给模型。工具列表变化、连接重建和用户切换租户时，都要重新核对允许范围。

工具、资源和提示模板不是同一种东西

工具通常表示可以调用的操作；资源提供待分析的上下文；提示模板帮助组织输入。资源中的文字仍是数据，工具描述不能扩展权限，提示模板也不能覆盖用户当前指令。

初始化和能力协商决定双方实际支持的功能。某个 SDK 版本支持某字段，不代表远端服务器也支持；应用要处理能力缺失、Schema 差异、协议错误和版本升级，而不是把不支持当成空结果。

权限和审批必须在应用层执行

工具描述中的“只读”“安全”或“破坏性”提示可以帮助界面展示，但不能代替执行端的权限检查。应用要校验当前用户、租户、资源、参数、版本和网络目标；高风险副作用还要绑定调用 ID、参数摘要和用户审批。

模型返回的 approved: true、role: admin 或工具结果中的“请发送密钥”都不能成为授权。资源和工具结果可能包含提示词注入，仍应按不可信外部内容处理。

调用 ID、运行 ID 和幂等键应贯穿请求、结果、重试和审计。超时或连接断开时，先查询服务端实际状态，再决定是否重试，不能因为没有收到响应就假定工具没有执行。

浏览器与本机宿主的能力不同

本机宿主在明确授权下可以通过 stdio 启动本地 MCP Server；普通网页不能随意启动进程、读取本地文件或访问用户任意目录。远程 MCP 可能使用 Streamable HTTP 等传输，浏览器接入还要考虑 CORS、短期认证、令牌存储和跨租户隔离。

长期凭据和本地工具启动逻辑通常应放在后端、桌面宿主或受控代理中，不应因为协议支持浏览器就直接搬进前端。传输、通知、取消和恢复能力要按实际协议版本核对，不能把旧 SSE 示例当成所有部署的固定形式。

界面要反映连接和调用的真实状态

服务器连接成功不代表工具调用成功；调用超时不代表服务端没有执行；取消请求也不保证已经完成的副作用被撤销。界面应区分连接、参数准备、待审批、执行中、成功、失败和结果未知，并显示结果来源。

恢复时按运行 ID 和事件游标补齐状态，重复事件幂等；历史展示不应重新执行工具。MCP 减少了每种工具的接入成本，但任务规划、权限、审计、重试和用户体验仍由应用负责。
