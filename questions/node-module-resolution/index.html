Node.js 怎样解析一个包的导入路径？require(esm) 有什么限制？

Node.js 解析裸说明符时，先在 node_modules 里找到包，有 exports 就只按 exports 匹配，按书写顺序检查 import、require、node、default 等条件，没列出的子路径抛出 ERR_PACKAGE_PATH_NOT_EXPORTED。选中文件后，格式由扩展名和最近的 package.json 的 type 决定。Node.js 20.19+、22.12+ 默认允许 require() 同步加载 ESM，模块图里有顶层 await 时抛出 ERR_REQUIRE_ASYNC_MODULE。

参考答案

简答

写 import 'demo-kit/format' 时，Node.js 要回答三个问题：包在哪、选哪个文件、按什么格式执行。先从当前目录往上逐级找 node_modules/demo-kit；找到后读它的 package.json，有 exports 就只按 exports 匹配，没列出的子路径抛出 ERR_PACKAGE_PATH_NOT_EXPORTED，main 不再起作用。exports 和 imports 字段具体怎样写，见《package.json 的 exports 和 imports 分别解决什么问题？》。

匹配时，条件按对象键的书写顺序检查，第一个满足的生效。import 语句满足 import 条件，require() 满足 require 条件，所以同一个入口可以给出不同文件。

选中文件以后，格式由扩展名和最近的 package.json 里的 type 决定，exports 不改变文件格式。Node.js 原生 ESM 里的相对导入还必须写完整的扩展名。

Node.js 20.19+、22.12+ 默认允许 require() 加载 ES 模块，但模块图里有顶层 await 时会抛出 ERR_REQUIRE_ASYNC_MODULE。

用一个包走一遍解析

下面这个包同时给 ESM 和 CommonJS 用户提供入口：

json
{
  "name": "demo-kit",
  "type": "module",
  "exports": {
    ".": {
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    },
    "./format": "./dist/format.js"
  }
}

在 Node.js 22 中实测：

导入方式结果
import 'demo-kit'加载 dist/index.js
require('demo-kit')加载 dist/index.cjs
import 'demo-kit/format'加载 dist/format.js
import 'demo-kit/dist/internal.js'ERR_PACKAGE_PATH_NOT_EXPORTED

以 require('demo-kit') 为例：Node.js 找到 node_modules/demo-kit，读到 exports，子路径是 .，进入它的条件对象，import 不满足，require 满足，选中 dist/index.cjs；扩展名是 .cjs，按 CommonJS 执行。最后一行文件明明在包里，却因为 exports 没列出而导入不了。

不过 exports 只是模块解析层面的封装。代码仍然可以用绝对路径直接读取包里的文件，所以它不能用来藏秘密。

条件是按什么规则匹配的

Node.js 内置认识 import、require、module-sync、node、default 等条件。解析时从上往下检查对象键，第一个匹配的条件生效，后面的就不看了。default 总能匹配，如果放在前面，后面的分支就永远选不中。

打包工具还会额外识别 browser、development 等条件。所以同一个包在 Vite 里能用，不代表 Node.js 直接运行时会选到同一个文件，发布前要在两种环境里分别测试。

文件格式由谁决定

.mjs 总是 ESM，.cjs 总是 CommonJS，.js 看最近的 package.json 里的 type。把一个 ESM 文件放在 require 条件下面，它并不会因此变成 CommonJS。

那 CommonJS 代码能不能直接 require 一个 ES 模块？Node.js 20.19+ 和 22.12+ 默认允许同步加载，可以用 process.features.require_module 检测：

JavaScript
// sync.mjs: export const v = 2;
// tla.mjs:  export const v = await Promise.resolve(1);
require('./sync.mjs').v; // 2
require('./tla.mjs');    // 抛出 ERR_REQUIRE_ASYNC_MODULE

require 是同步的，可顶层 await 要异步等待，两者没法兼容，所以带顶层 await 的模块会报错。

有了这个能力，很多库可以只发布 ESM，只有还要支持更早版本时，才需要同时提供 CommonJS 产物。同时发布两种格式要注意“双包风险”：同一个进程里 import 和 require 可能各加载一份实现，模块级状态、单例和 instanceof 判断都会出现两套。

常见追问

为什么 ESM 必须写扩展名？

Node.js 的 ESM 按 URL 规则查找文件，写什么就找什么，不会像 CommonJS 那样依次尝试 .js、.json 和目录下的 index.js。

发布前怎样验证 exports？

建一个独立的消费项目，分别用 import、require 和 TypeScript 导入每个公开路径，再确认被排除的路径确实会报错。
