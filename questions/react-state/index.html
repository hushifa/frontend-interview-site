为什么调用 setState 后，当前变量还是旧值？

每次渲染得到的是当前状态快照，setter 排队的是下一次状态更新，不会修改已经执行中的局部变量。替换值和函数式更新具有不同的队列含义，批处理也不等于 JavaScript 变量被异步赋值。

参考答案

函数组件执行时，useState 返回这一轮渲染使用的状态值。事件处理器是在这一轮中创建的，因此也能访问这一份快照。调用 setter 是请求 React 用新状态继续渲染，不会把当前函数作用域里的 count 变量原地改掉。

所以 setter 后立即读取 count 仍然得到旧值，首先是快照与闭包语义，而不只是一个模糊的“setState 是异步的”。

三次替换和三次累加不是同一种更新

JSX
import { useState } from 'react';

export default function Counter() {
  const [count, setCount] = useState(0);

  function replaceThreeTimes() {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);
    console.log('本次处理器看到的值：', count);
  }

  function incrementThreeTimes() {
    setCount(current => current + 1);
    setCount(current => current + 1);
    setCount(current => current + 1);
  }

  function replaceThenIncrement() {
    setCount(count + 5);
    setCount(current => current + 1);
  }

  return (
    <section>
      <output aria-label="计数">{count}</output>
      <button type="button" onClick={replaceThreeTimes}>三次替换更新</button>
      <button type="button" onClick={incrementThreeTimes}>三次函数更新</button>
      <button type="button" onClick={replaceThenIncrement}>替换后递增</button>
    </section>
  );
}

初始 count 为 0 时，第一种写法三次都先用同一快照算出 1，再把“替换为 1”排进队列，因此最终是 1，处理器里的日志仍然是 0。

函数式更新排入的是三个计算过程。React 处理时把前一次结果交给下一次，得到 0→1→2→3。如果在前面已经加到 1 后再点这个按钮，则从 1 连续更新到 4，而不是重新从 0 开始。

第三种写法说明队列中可以混合替换与更新：先替换成当前快照加 5，再对队列中的结果加 1。初始为 0 时最终为 6；不是因为写了函数式更新，其他替换操作就会被忽略。

批处理减少重复工作，不改变快照含义

React 会在相应边界批处理状态更新，避免同一个交互过程中每调用一次 setter 就立刻完整更新页面。现代 React 在许多异步回调场景中也支持自动批处理，不能继续把它简单限定为旧版本的某一种事件处理器。

但批处理不是把所有用户交互无限合并。React 需要在合理边界保证后续交互看到一致状态，具体调度还受更新优先级等影响。不要依赖 setter 后“过某个固定毫秒就更新”这种猜测。

setter 不返回一个表示渲染完成的 Promise，因此 await setCount(...) 不是等待新状态提交的通用方式。即使用某些强制刷新机制让 DOM 提前更新，当前处理器捕获的局部 count 也不会变成另一次渲染的变量。

更新函数必须是纯计算

current => current + 1 应该只根据输入计算下一状态，不应在里面发请求、写日志作为业务依据、修改外部对象或产生一次性副作用。

React 可能为检查纯度或调度需要再次调用相应计算。尤其开发环境的 Strict Mode 会暴露不纯更新，因此不能把“这个 updater 只会执行一次”当成业务保证。

如果一次点击需要发送请求，应在事件处理器或合适的同步机制中完成，状态 updater 只计算状态。需要同时维护多个严格相关的字段时，可以考虑统一对象状态或 reducer，让一次更新表达完整关系。

延迟回调也会保留创建时的状态

在当前处理器里注册一个定时器，回调若直接读取 count，通常仍然读取创建它的这轮快照。后来页面重新渲染，不会自动替已经保存的旧函数更换作用域。

如果目标是“无论之前值是什么，再加 1”，函数式更新可以让 React 把处理队列时的前值交进来。如果目标是访问某项最新外部状态，则需要根据用途选择正确依赖、重新建立回调、Effect Event 或 ref 等机制，而不是认为函数式更新能自动读取所有最新变量。

ref 更新不会触发重新渲染，适合保存不直接决定 UI 的可变信息；不能为了读取方便就把所有本应驱动显示的状态都放进 ref。

对象状态还要注意身份与更新方式

useState 的 setter 采用新的状态值，不会像某些旧式类组件 setState 用法那样自动浅合并对象。要保留未改字段，应显式构造完整下一状态。

直接修改旧对象后再把同一引用传回去，可能因为 Object.is 等比较被视为没有新的状态变化，也会破坏已有快照与共享数据的预期。通常应复制实际修改路径，保留未变部分的引用，而不是每次深拷贝所有内容。

如果只是根据 props 和 state 算一个显示值，例如筛选后的列表或数量，优先在渲染中推导。再额外存一份并用 Effect 同步，会增加状态不一致的机会，也让“为什么这次还是旧值”更难分析。

理解快照之后，问题可以分成三步：当前函数拿到哪一轮状态，队列中放的是替换值还是计算函数，React 何时把计算结果提交给界面。这样比用一句“异步更新”概括所有现象更精确。
