Node.js 服务如何实现优雅退出？

容器滚动发布时，旧进程收到 SIGTERM 后先让 readiness 检查失败，等负载均衡器摘除实例，再停止接收新连接、等待在途请求完成、关闭数据库和队列等资源；整个过程有一个截止时间，超时后强制退出。

参考答案

简答

发布新版本时，平台会给旧进程发一个 SIGTERM 信号让它退出。如果直接退，正在处理的请求就断了，用户看到报错。优雅退出就是先把手头的活干完再走。

顺序是这样的：先让 readiness 健康检查返回 503，等一小段时间让负载均衡器把这个实例摘掉，不再给它派新请求；然后调用 server.close()，它停止接收新连接，等在途请求处理完再回调，Node.js 19 起还会顺手关掉空闲的 keep-alive 连接；最后关闭数据库连接池、停掉队列消费。

整个流程要设一个截止时间，到期还没完成，就调用 server.closeAllConnections() 和 process.exit(1) 强制结束。截止时间要比平台的终止宽限期短。在途请求本身也要有超时，否则一个卡住的请求会让退出无限期地等下去。

要注意，正常退出时不要先调 process.exit()，让事件循环自然清空就行。提前调用会截断还没写完的响应和日志。

为什么不能收到信号就立刻关闭

收到 SIGTERM 的那一刻，负载均衡器还不知道这个实例要下线，还在往这里派新请求。如果马上 server.close()，这些新请求就会被直接拒绝。所以退出要按下面的顺序来：

  1. 标记正在关闭，readiness 检查开始返回 503。
  2. 等待负载均衡器发现并摘除实例，这段延迟取决于健康检查间隔。
  3. server.close()，停止接新连接，等待在途请求完成。
  4. 关闭数据库连接池、停止队列消费、清理定时器。
  5. 超过截止时间仍未完成，记录原因并强制退出。

代码怎么写

下面的实现里，/ready 是健康检查接口，shutdown 按上面的顺序执行：

JavaScript
import http from 'node:http';

let shuttingDown = false;
let shutdownPromise;

const server = http.createServer(async (request, response) => {
  if (request.url === '/ready') {
    response.writeHead(shuttingDown ? 503 : 200).end();
    return;
  }
  await handle(request, response);
});
server.listen(3000);

function shutdown(signal, { drainDelayMs = 5_000, deadlineMs = 25_000 } = {}) {
  // 重复收到信号时复用同一个流程。
  if (shutdownPromise) return shutdownPromise;
  shuttingDown = true;
  console.log(`收到 ${signal}，开始关闭`);

  shutdownPromise = (async () => {
    const deadline = setTimeout(() => {
      console.error('超过截止时间，强制退出');
      server.closeAllConnections();
      process.exit(1);
    }, deadlineMs);
    deadline.unref();

    await new Promise((resolve) => setTimeout(resolve, drainDelayMs));
    await new Promise((resolve, reject) =>
      server.close((error) => (error ? reject(error) : resolve())),
    );
    await db.close();
    clearTimeout(deadline);
  })();

  return shutdownPromise;
}

for (const signal of ['SIGTERM', 'SIGINT']) {
  process.once(signal, () => {
    shutdown(signal).catch((error) => {
      console.error(error);
      process.exitCode = 1;
    });
  });
}

本地实测（去掉等待和数据库部分）：关闭开始时一个耗时 300 毫秒的请求正在处理，它正常返回 ok 后 server.close() 才回调，此后的新连接被拒绝，进程以退出码 0 结束。

截止计时器调用了 unref()，你可能会问这是做什么的。一个活着的定时器会让进程一直不退出；unref() 以后，它就不再拦着进程。这样正常排空后进程可以直接退出，不用等满 25 秒。

正常路径里没有调用 process.exit()。资源全部关闭以后事件循环里没有事情了，进程会自己退出。

SIGINT 是本地按 Ctrl+C 时收到的信号，按同样的流程处理。截止时间设成 25 秒，是因为 Kubernetes 的 terminationGracePeriodSeconds 默认 30 秒，到期后会直接发 SIGKILL，那时就来不及做任何清理了。

长连接和后台任务怎么处理

类型处理方式
普通请求设置请求级超时，并把 AbortSignal 传给下游 fetch 和数据库查询
空闲 keep-alive 连接Node.js 19 起 server.close() 会关闭；更早的版本要调用 server.closeIdleConnections()
WebSocket、SSEserver.close() 不会结束它们，closeAllConnections() 也不会关闭已升级的 WebSocket；应用要主动通知客户端重连并关闭这些连接
队列消费者先停止拉取新消息，等已取出的消息处理完再确认；被强制中断的消息会重新投递，处理逻辑必须幂等

closeAllConnections() 会把正在传输的请求也一起中断，所以只在截止阶段使用。

常见追问

为什么不在收到信号后立刻 server.close()？

那时负载均衡器还没摘除实例，新请求会继续到达，这些请求会被直接拒绝。先让 readiness 失败、等一段时间，能减少这类错误。

优雅退出能保证数据一致吗？

不能。进程可能被 SIGKILL 或者直接崩溃，一致性要靠事务、幂等和重试。优雅退出只是减少正常发布时的中断。

readiness 和 liveness 有什么区别？

readiness 表示能不能接收流量，关闭时要返回失败。liveness 表示进程是否还活着，关闭过程中仍应返回成功，否则平台可能以为进程挂了，提前把容器重启掉。
