Electron 的主进程、渲染进程、preload 和 utility 进程分别负责什么？

Electron 是多进程模型：主进程管应用生命周期和窗口，渲染进程显示网页，preload 在两者之间暴露有限的 API，utility 进程承担需要 Node.js 的重任务。各进程的可用 API 和生命周期不同，长计算按情况放到 utility 进程或 Web Worker。

参考答案

简答

一个 Electron 应用跑起来，其实是好几个进程。主进程每个应用只有一个，运行在 Node.js 环境里，负责应用的生命周期（app）、创建和管理窗口（BrowserWindow），以及菜单、对话框、托盘这些原生能力。

每个窗口里的网页跑在自己的渲染进程里，按 Web 标准运行 HTML、CSS 和 JS，默认不能用 require 和 Node.js API。页面要用系统能力怎么办？靠 preload 脚本。它在页面内容加载前运行在渲染进程里，通过 contextBridge.exposeInMainWorld 把有限的几个 API 暴露给页面；开启沙箱后，它只能 require electron 模块里的一部分 API。

还有 utility 进程，由主进程用 utilityProcess.fork 创建，拥有完整的 Node.js 能力，接口和 child_process.fork 相似，还能通过 MessagePort 和渲染进程直接通信。CPU 密集的任务、不可信的服务、容易崩溃的组件，都适合放在这里。

进程之间通过 IPC 或 MessagePort 通信。要注意的是主进程必须保持空闲，不能在里面做长时间的同步计算。

Electron 为什么是多进程

Electron 继承了 Chromium 的多进程架构。Chromium 把每个页面放进单独的渲染进程，一个页面卡死或崩溃，不会拖垮整个浏览器。Electron 在这个基础上，加了一个运行 Node.js 的主进程来管理整个应用。

主进程做什么

应用入口，也就是 package.json 里的 main，在主进程执行，可以使用全部 Node.js API。

主进程用 BrowserWindow 创建窗口，每个窗口在独立的渲染进程里加载页面，主进程通过窗口的 webContents 控制它。窗口销毁时，对应的渲染进程也会结束。退出、Dock 图标这些生命周期行为通过 app 模块控制，原生界面通过 Menu、dialog、Tray 等模块使用。

所有窗口的事件分发和进程间通信都经过主进程。所以它一旦被阻塞，整个应用的所有窗口都会失去响应。

渲染进程做什么

渲染进程的代码和普通网页一样：入口是 HTML，用 <script> 加载 JS，用打包工具引入 npm 包。

出于安全考虑，渲染进程默认不再拥有 Node.js 能力。nodeIntegration 默认关闭，沙箱自 Electron 20 起默认开启。

preload 脚本怎样把能力交给页面

JavaScript
// main.js
new BrowserWindow({
  webPreferences: { preload: path.join(__dirname, 'preload.js') },
});

// preload.js
const { contextBridge, ipcRenderer } = require('electron');
contextBridge.exposeInMainWorld('api', {
  openFile: () => ipcRenderer.invoke('dialog:openFile'),
});

页面里调用 window.api.openFile()，preload 再通过 IPC 交给主进程。

你可能会问，preload 直接给 window.api 赋值不就行了？不行。contextIsolation 默认开启，preload 和页面处在两个不同的 JS 上下文里，preload 直接改 window，页面是看不到的，必须通过 contextBridge 暴露。

沙箱模式下，preload 只能 require('electron')，可用的有 contextBridge、crashReporter、ipcRenderer、nativeImage、webFrame、webUtils，不能用 Node.js 内置模块。所以文件读写这类操作，要通过 IPC 交给主进程。

utility 进程适合做什么

JavaScript
// main.js，需要在 app 的 ready 事件之后调用
const { utilityProcess } = require('electron');

const child = utilityProcess.fork(path.join(__dirname, 'worker.js'), [], {
  serviceName: 'Image Worker',
});
child.postMessage({ type: 'resize', file });
child.on('message', (result) => { /* 处理结果 */ });
child.on('exit', (code) => { /* 崩溃或退出后决定是否重启 */ });

// worker.js
process.parentPort.on('message', (e) => {
  process.parentPort.postMessage(doHeavyWork(e.data));
});

utility 进程基于 Chromium 的 Services API 启动，接口和 child_process.fork 相似。和 child_process.fork 相比，主要区别是它可以通过 MessagePort 和渲染进程直接建立通信通道。

serviceName 会出现在 app.getAppMetrics() 和 child-process-gone 事件里，方便监控和定位是哪个进程出了问题。另外，utility 进程只有 stdout 和 stderr 可以配置，stdin 必须是 ignore。

一个任务该放在哪个进程

任务推荐位置
界面渲染、交互逻辑渲染进程
页面内的长计算（解析、压缩）渲染进程中的 Web Worker
文件系统、原生对话框、窗口管理主进程，经 IPC 调用
需要 Node.js 的重计算、第三方原生模块、可能崩溃的服务utility 进程

常见追问

多个窗口怎么共享状态？

由主进程或 utility 进程持有状态，再通过 IPC 广播；或者用 MessagePort 让窗口之间直接通信，通信方式见《Electron 的 IPC 和 contextBridge 怎样设计？》。

为什么不在 preload 里直接做文件操作？

沙箱开启后，preload 拿不到 fs。就算关掉沙箱，把文件能力放进渲染进程也会扩大 XSS 的影响，安全细节见《Electron 应用的主进程、渲染进程和 IPC 有哪些安全边界？》。
