strict、noUncheckedIndexedAccess 和 target 如何配置？

tsconfig 管几件不同的事：检查有多严、输出什么版本的语法、能用哪些内置 API 的类型、模块怎么解析。target 和 lib 只影响类型和语法转换，不会补上运行时缺的 API。

参考答案

简答

tsconfig 里的选项分几类，各管一件事。strict 是一组检查的总开关，包括 strictNullChecks、noImplicitAny、strictFunctionTypes 等，TypeScript 6.0 起默认开启。但 noUncheckedIndexedAccess、exactOptionalPropertyTypes 不在这组里，要单独开。

target 决定输出什么版本的语法，lib 决定能用哪些内置 API 的类型，两者都不会补上运行时缺的 API。module 和 moduleResolution 要跟真实运行环境一致：交给打包工具就用 bundler，Node.js 直接运行就用 nodenext。

版本变化也要知道。TypeScript 6.0 改了一批默认值，比如 types 默认变成 []，Node、测试框架的全局类型要在 types 里显式列出。6.0 弃用的 target: es5、moduleResolution: node10/classic、baseUrl、downlevelIteration、module: amd/umd/system/none 到 TypeScript 7.0 不再支持，esModuleInterop、alwaysStrict 也不能再设为 false；outFile 在 6.0 就已经移除。

最后，Vite、esbuild 这类工具只删类型、不做检查，构建成功不代表类型正确，CI 里要单独跑 tsc --noEmit。

打包工具项目可以从这里起步

json
{
  "compilerOptions": {
    "target": "es2022",
    "lib": ["es2023", "dom", "dom.iterable"],
    "module": "esnext",
    "moduleResolution": "bundler",
    "types": ["vite/client"],
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "verbatimModuleSyntax": true,
    "noEmit": true
  },
  "include": ["src"]
}

noEmit: true 表示 tsc 只做类型检查，不输出文件，转换交给 Vite 或 esbuild。6.0 起 strict 已经默认开启，这里还写出来，是为了兼容 6.0 之前的版本。

读数组为什么会漏掉 undefined

TypeScript
const list: string[] = [];
const first = list[0];
first.toUpperCase();

数组是空的，list[0] 明明是 undefined，可默认配置下 first 的类型是 string，这段代码能通过检查，运行时却抛错。原因是 TypeScript 默认假设按下标读一定能读到值。

开启 noUncheckedIndexedAccess 后，first 的类型变成 string | undefined，必须先判断才能用。它对 Record<string, T> 的读取也一样生效；for...of 和数组方法回调里的参数不受影响，因为那些值一定存在。

“没有这个属性”和“属性是 undefined”一样吗

TypeScript
type P = { name?: string };
const p: P = { name: undefined }; // exactOptionalPropertyTypes 下报错

默认情况下，可选属性既可以不写，也可以显式写成 undefined，两者被当成一回事。开启 exactOptionalPropertyTypes 后，它们被区分开，name?: string 只表示“可以没有”，不允许显式赋 undefined。

这个区别在实际中有影响：'name' in p、Object.keys 的结果不一样，PATCH 请求里“不修改”和“清空”的含义也不一样。确实需要显式 undefined 时，写成 name?: string | undefined。

target 和 lib 管不了运行时

target: es2022 时，可选链、类字段这些语法原样输出；改成 es2015，它们会被转换成旧写法。可 target 只转换语法，不补 API。

lib 也一样。lib 里有 es2023，只说明你可以写 findLast 而不报类型错误；目标浏览器没有这个方法，运行时照样出错，这得靠 core-js 等 polyfill 补上。另外，不写 lib 时会根据 target 推出默认值；一旦写了就完全替换默认值，DOM 项目别忘了加 dom。

TypeScript 6 和 7 改了哪些默认值

选项6.0 前默认6.0 起默认
strictfalsetrue
targetes5最新的稳定 ES 版本（6.0 发布时为 es2025）
module视 target 而定esnext
types自动包含所有 @types/*[]（写 ["*"] 恢复旧行为）
rootDir推断tsconfig 所在目录
noUncheckedSideEffectImportsfalsetrue

6.0 弃用了前面提到的那批选项，可以先用 "ignoreDeprecations": "6.0" 暂时屏蔽弃用错误；到 7.0 这些选项直接报错：整个选项被删的报 TS5102，某个取值被删的（如 target=es5）报 TS5108。迁移 baseUrl 的办法是把 paths 改成相对 tsconfig 的路径，或者改用 package.json 的 imports（#src/*）。

还有一个小变化：在有 tsconfig 的目录里执行 tsc foo.ts 会报 TS5112，需要加 --ignoreConfig。

检查和构建要分开

Vite、esbuild、SWC 转换 TS 时只删掉类型，不做类型检查，所以构建成功不代表类型正确。CI 里要单独运行 tsc --noEmit，多项目仓库用 tsc -b。

常见追问

skipLibCheck 要不要开？

大多数应用项目会开，它跳过 node_modules 里 .d.ts 的检查，速度更快。库作者最好关掉，这样能发现自己声明里的错误。

用 Node.js 直接运行 TS，需要哪些选项？

主要是 erasableSyntaxOnly、verbatimModuleSyntax、module: nodenext 和 rewriteRelativeImportExtensions，详见《import type 和 verbatimModuleSyntax 如何影响模块输出？》。
