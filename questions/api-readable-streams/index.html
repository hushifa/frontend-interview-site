怎样正确消费 Fetch 返回的 ReadableStream？

响应的 body 可以是 ReadableStream，通过 reader.read 逐块获取 value 和 done，或在支持的环境中使用异步迭代。取得 reader 会锁定流，因此不能同时让另一消费者随意读取同一响应体。

参考答案

fetch 返回 Response 时，响应体不一定已经全部下载完。response.body 可以作为 ReadableStream 持续提供字节块，让应用边接收边处理，而不是先把全部内容放进内存。

逐块消费并不代表“每个块是一条消息”。网络、解压和浏览器缓冲决定分块位置，业务协议还需要自己的解码与边界处理。

一个安全消费 UTF-8 文本的基础循环

下面的 onText 是处理已解码文本片段的回调，可以返回 Promise；示例假设响应使用 UTF-8，并限制累计消费字节数：

JavaScript
async function consumeText(response, onText, maxBytes = 1024 * 1024) {
  if (!Number.isSafeInteger(maxBytes) || maxBytes < 0) {
    throw new RangeError('字节上限必须是非负安全整数');
  }
  if (!response.ok) {
    await response.body?.cancel();
    throw new Error(`请求失败：${response.status}`);
  }
  if (!response.body) return;

  const reader = response.body.getReader();
  const decoder = new TextDecoder('utf-8', { fatal: true });
  let bytes = 0;
  let completed = false;
  try {
    while (true) {
      const { value, done } = await reader.read();
      if (done) {
        const tail = decoder.decode();
        if (tail) await onText(tail);
        completed = true;
        break;
      }
      bytes += value.byteLength;
      if (bytes > maxBytes) throw new Error('响应体超出读取上限');
      const text = decoder.decode(value, { stream: true });
      if (text) await onText(text);
    }
  } finally {
    try {
      if (!completed) await reader.cancel();
    } finally {
      reader.releaseLock();
    }
  }
}

stream: true 让解码器保留跨块的不完整字符，最后无参数 decode 完成收尾。fatal: true 使非法编码抛错；若业务选择容忍坏数据，可以使用替换字符策略，但要明确取舍。

maxBytes 限制的是消费到的响应体字节，不是精确的线上压缩传输量，也不是整个进程内存上限。已经收到的单个块仍占内存，onText 自己若无限累积全部字符串，也会重新造成全量占用。

reader 锁与取消是两件事

getReader 会锁定流。持有锁时，不能再同时 response.text 或让另一个 reader 消费同一 body。响应体被消费后，也不能随意从头再读。

releaseLock 只是释放读取器对流的占有，不表示终止底层数据源。仍有未完成 read 时释放锁会使这些读取拒绝，未消费数据也不因此自动被清空。若不再需要结果，应调用 reader.cancel 或取消相关请求，再释放锁。

示例在异常时取消剩余读取，包括字节超限、解码失败或 onText 抛错。清理自身也可能失败，正式业务可以进一步保留原始异常与清理异常，避免丢失诊断信息。

文本片段还不是协议消息

一条 JSON 可能跨两个文本片段，也可能一个片段包含多条消息。NDJSON 通常需要保留未完成的一行；SSE 还涉及空行分隔、多个 data 字段、CRLF 等协议规则。

因此不能对每个 value 直接 JSON.parse，也不能只用一次 split 后丢掉末尾残片。应采用经过验证的协议解析器，并设置单条消息或残片长度上限，避免对方一直不发送分隔符导致内存增长。

TextDecoderStream 可以把字节流转换成文本流，但它同样不负责解析 JSON、SSE 或业务事件。

背压与并发消费需要明确

示例 await onText 后再继续 read，让下游处理速度影响消费节奏。若每次 onText 都启动异步任务却不等待，可能很快堆积大量未完成工作。

ReadableStream 可以通过 pipeThrough、pipeTo 组合转换与目标流，但取消、错误传播和信号仍需按管道语义配置。clone 或 tee 将数据分成多个消费者时，较慢分支可能产生额外缓冲，不应把它当作没有内存成本的复制。

选择流的依据是能否增量处理和控制缓冲。若最终仍必须拿到全部小型 JSON，response.json 更简单；若需要长连接、渐进展示或大文件处理，就需要完整考虑消息边界、取消与错误收尾。
