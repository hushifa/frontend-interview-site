为什么 Vue 提倡 props 单向数据流？

props 把父级状态传给子组件，事件把子组件的修改意图交回所有者。只读绑定、嵌套对象共享、本地草稿和 Vue 3.5 的 props 解构转换各有边界，不能只记成一句“子组件不能修改数据”。

参考答案

单向数据流的重点是明确谁拥有状态。父组件负责提供当前值，也可以负责校验、限制、保存和重置；子组件展示数据，并通过事件表达用户希望发生的操作。

这样发生变化时，可以找到一个明确的决策位置，而不是多个组件都直接修改同一个对象，最后很难判断谁覆盖了谁。

子组件提出请求，父组件决定是否接受

vue
<!-- CounterButton.vue -->
<script setup>
const props = defineProps({
  count: { type: Number, required: true },
  step: { type: Number, default: 1 },
});
const emit = defineEmits(['increment']);

function requestIncrement() {
  emit('increment', props.step);
}
</script>

<template>
  <button type="button" @click="requestIncrement">
    当前 {{ props.count }}，申请增加 {{ props.step }}
  </button>
</template>
vue
<!-- Parent.vue -->
<script setup>
import { ref } from 'vue';
import CounterButton from './CounterButton.vue';

const count = ref(0);
const message = ref('');

function increment(amount) {
  if (!Number.isFinite(amount) || count.value + amount > 2) {
    message.value = '本例最多允许增加到 2。';
    return;
  }
  count.value += amount;
  message.value = '';
}

function reset() {
  count.value = 0;
  message.value = '';
}
</script>

<template>
  <section>
    <CounterButton :count="count" :step="1" @increment="increment" />
    <button type="button" @click="reset">重置</button>
    <p role="status">{{ message }}</p>
  </section>
</template>

子组件没有修改 count，而是发出 increment。父组件可以接受，也可以拒绝超过上限的操作。即使按钮一直被点击，实际值仍由父级决定，再通过 prop 传回展示。

这里的限制只是演示父级决策，不是服务端安全校验。事件校验和 props 类型声明同样不能替代跨网络的业务验证。

只读 prop 不等于整个对象图都被深冻结

子组件不应重新给 props.count 赋值。父级刷新时会继续提供自己的值，直接改 prop 既违反所有权，也容易被后续更新覆盖。

但对象、数组作为 prop 传入时，子组件可能持有同一个嵌套对象的引用。修改 props.user.name 在技术上可能影响父级对象，并不因为没有给 props.user 重新赋值就变成清楚的数据流。

除非父子组件明确约定紧密共享可变结构，否则通常应发出具体更新事件，或由父级提供明确的操作函数。是否能够修改，与是否应该把修改权暴露出去，是两件不同的事。

本地编辑草稿需要单独的同步策略

有些组件需要先编辑、再保存或取消，此时可以从 prop 初始化一份本地草稿。草稿与已保存值是不同状态，不应在用户每次输入时都无条件写回父级。

但 ref(props.initialValue) 通常只采用初始化时的值，父级以后更新不会自动重置这份 ref。若需要跟随记录切换或外部刷新，应明确什么时候覆盖草稿，是否先提示未保存修改，以及保存成功后怎样收敛。

反过来，一个无条件 watch 每次父值变化都覆盖草稿，也可能抹掉用户正在编辑的内容。简单显示转换通常用 computed 更合适，不需要复制出一份独立状态。

props 解构有 Vue 3.5 的编译期例外

下面的 script setup 示例面向 Vue 3.5 及以上：

vue
<!-- DestructuredCount.vue -->
<script setup>
import { watchEffect } from 'vue';
const { count } = defineProps({ count: Number });

watchEffect(() => {
  console.log('收到计数：', count);
});
</script>

<template>
  <p>{{ count }}</p>
</template>

在这一特定语法中，编译器会把同一 script setup 作用域内对解构变量的相应访问转换为 props 属性读取。因此父级 count 变化时，watchEffect 可以重新执行。

Vue 3.4 及更早版本对这个写法并没有同样行为；而普通 JavaScript 从 reactive 对象中解构原始值，也不会因为升级到 3.5 就自动变成响应式。

把解构值交给其他函数时，还要保留访问方式。watch(count, ...) 仍然可能只是传一个当前数字，应该使用 getter，例如 watch(() => count, ...)。需要给组合函数持续读取的来源，也应按它支持的 getter/ref 接口传递，而不是只给一个值快照。

默认值与校验不负责创造额外业务保证

props 的 required、type、validator 等声明有助于文档化和开发期发现误用，但警告不等于把错误数据自动转换成安全值。对象或数组默认值也要按对应声明方式避免无意共享可变实例。

父级没有提供某个值时，子级默认值可以影响本地展示，但不自动意味着父级状态也被写入同一个值。特别是模型绑定与异步初始化场景，双方需要对空值和默认值有一致约定。

事件、v-model 与共享状态各有适用范围

组件事件通常表达直接父子之间的沟通，不会像原生 DOM 事件一样自动沿组件祖先无限冒泡。多个层级共享状态时，可以考虑提供/注入或状态库，但仍要有明确的修改入口。

组件 v-model 把 prop 与更新事件的约定写得更简洁，不是取消单向数据流。复杂操作也不一定都适合一个 update 事件，保存、取消、提交草稿等意图可以有更具体的接口。

好的 props 设计应让调用方知道：传入的是当前状态还是初始值，子组件是否持有草稿，哪些动作会请求更新，以及父级什么时候有权拒绝或重置。把这些关系说明白，组件复用才不会依赖隐蔽的共享修改。
