WebSocket 适合什么场景，连接断开后怎样恢复？

WebSocket 适合聊天、协同编辑这类低延迟、双向、高频的通信。它不自带重连和消息确认，恢复要两步：先退避重连把连接接上，再按消息序号补齐断线期间的数据。

参考答案

简答

WebSocket 先用一次 HTTP 请求做 Upgrade 握手，之后这条连接就变成双向的，浏览器和服务器都能随时发文本或二进制消息。所以它适合聊天、协同编辑、游戏这种低延迟、两边都要频繁说话的场景。

它不管断线重连，要自己写。一般用指数退避加随机抖动，也就是每次失败等待时间翻倍，再随机打点折扣，免得服务器重启后所有客户端同一秒涌进来。

还要分清楚，连接恢复了不等于数据恢复了。客户端要记下最后收到的消息序号，重连后让服务器补发；自己发出的消息要等服务器确认，超时就重发，用消息 ID 去重。

如果只需要服务器推、不需要双向，SSE 更简单，见《SSE 与 WebSocket 有什么区别？》。

握手长什么样

浏览器发的是一个普通的 GET，只是多了几个头：

http
GET /chat HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Origin: https://app.example

服务器同意就回 101 Switching Protocols，之后这条连接就不再是 HTTP 了。

这里有个安全问题。WebSocket 不受 CORS 约束，任何网站的脚本都能连你的服务器，而且浏览器会带上用户的 Cookie。所以服务器必须自己检查 Origin，不然恶意网站就能借用户身份建立连接，这叫跨站 WebSocket 劫持。

带重连和补发的客户端

下面这个客户端做了三件事：断线后退避重连，重连时带上最后的序号，收到重复消息就丢掉。

JavaScript
function connect(url, onMessage) {
  let socket;
  let attempt = 0;
  let lastSeq = 0;
  let stopped = false;

  function open() {
    socket = new WebSocket(`${url}?since=${lastSeq}`);

    socket.onopen = () => {
      attempt = 0;
    };

    socket.onmessage = (event) => {
      const message = JSON.parse(event.data);
      if (message.seq <= lastSeq) return; // 重复消息
      lastSeq = message.seq;
      onMessage(message);
    };

    socket.onclose = (event) => {
      if (stopped || event.code === 1000) return;
      const delay = Math.min(30_000, 1000 * 2 ** attempt) * (0.5 + Math.random() / 2);
      attempt += 1;
      setTimeout(open, delay);
    };
  }

  open();
  return {
    send: (data) => socket.readyState === WebSocket.OPEN && socket.send(JSON.stringify(data)),
    close: () => {
      stopped = true;
      socket.close(1000);
    },
  };
}

重连地址里带着 since=${lastSeq}，服务器据此补发断线期间的消息。补发的和新来的可能重叠，所以 onmessage 里序号不大于 lastSeq 的直接跳过。

等待时间是 1 秒、2 秒、4 秒这样翻倍，最多 30 秒，再乘上 0.5 到 1 之间的随机数。连上以后 attempt 清零。关闭码 1000 表示正常关闭，这时不重连，用户主动调用 close 也是。

为什么还要心跳

TCP 连接可能已经断了，两端却都不知道，比如手机进了电梯。NAT 和代理也会把长时间没动静的连接清掉。

浏览器的 API 发不了协议层的 ping 帧，所以常见做法是每隔 20 到 30 秒发一条应用层的心跳消息，一段时间收不到回应，就主动关掉重连。另外，页面从后台切回来（visibilitychange）或者网络恢复（online 事件）时，可以马上检查一下连接。

发得太快怎么办

send() 不会阻塞，数据先放进浏览器的缓冲区再慢慢发。如果一直猛发大量数据，缓冲区会越积越多。这时看 socket.bufferedAmount，超过阈值就先停一停，这叫背压。

常见追问

消息顺序有保证吗？

单个连接内是有序的。但重连后补发的消息和新消息可能交错，所以要按序号处理。

怎样鉴权？

握手时带 Cookie，或者连上以后第一条消息发一个短期令牌。不要把长期令牌放在 URL 查询参数里，它会被写进服务器日志。
