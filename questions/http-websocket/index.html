WebSocket 适合什么场景，连接断开后怎样恢复？

从聊天消息的发送与确认理解 WebSocket 的双向通信，区分连接恢复和业务恢复，并说明心跳、退避重连、消息去重与缓冲区限制。

参考答案

聊天页面如果每隔两秒请求一次“有没有新消息”，即使没人说话，也要不断发送请求；刚好在一次查询之后到达的消息，还得等下一次查询。WebSocket 则先建立一条持续的双向连接：用户可以随时发消息，服务端有新消息时也可以主动推送，不必等浏览器再次询问。

它适合聊天、多人协作、实时游戏指令和频繁变化的状态。只有服务端持续向页面推送文本时，SSE 往往更简单；数据几分钟才变化一次时，普通请求或低频轮询也可能足够。长连接需要维护连接状态、容量和恢复逻辑，并不是使用它就一定更快、更省资源。

建立连接后，传输的是消息

在常见的 HTTP/1.1 场景中，客户端发起带 Upgrade: websocket 的握手，服务端同意后返回 101 Switching Protocols，随后双方使用 WebSocket 帧传输数据。支持相应扩展的 HTTP/2、HTTP/3 也可以通过扩展 CONNECT 承载 WebSocket，不能把“必须收到 101”当成所有传输版本的通用规则。

浏览器使用 WebSocket API，通常不需要自己拼接握手头。线上 HTTPS 页面应连接 wss://，由 TLS 保护通信。

WebSocket 保留消息边界，浏览器的 message 事件交付一条完整消息，不需要像处理原始字节流那样自己判断 JSON 在哪里结束。不过，消息内容是什么格式仍由业务约定：它可以是文本，也可以是二进制，协议并不要求必须使用 JSON。文本消息的 event.data 是字符串；二进制消息通常是 Blob，也可以通过 binaryType = 'arraybuffer' 接收 ArrayBuffer。

一个只负责单次连接的客户端

下面假设服务端发送的聊天消息格式为 { type: 'message', id: '消息编号', text: '正文' }。示例只实现连接、收发和释放，重连后的历史恢复另行设计。

JavaScript
function openChat(url, onMessage) {
  const socket = new WebSocket(url);
  const encoder = new TextEncoder();
  const maxQueuedBytes = 256 * 1024;
  let disposed = false;

  socket.addEventListener('message', (event) => {
    if (disposed || typeof event.data !== 'string') return;

    let message;
    try {
      message = JSON.parse(event.data);
    } catch {
      console.warn('收到无法解析的聊天消息');
      return;
    }

    if (
      !message ||
      message.type !== 'message' ||
      typeof message.id !== 'string' ||
      typeof message.text !== 'string'
    ) {
      return;
    }

    onMessage(message);
  });

  socket.addEventListener('error', () => {
    console.warn('聊天连接发生错误');
  });

  socket.addEventListener('close', (event) => {
    if (!disposed) {
      console.info('聊天连接已关闭', event.code, event.reason);
    }
  });

  return {
    send(text, clientMessageId) {
      if (disposed || socket.readyState !== WebSocket.OPEN) return false;
      if (typeof text !== 'string' || typeof clientMessageId !== 'string') {
        throw new TypeError('消息正文和客户端消息编号必须是字符串');
      }

      const payload = JSON.stringify({ type: 'send', clientMessageId, text });
      if (socket.bufferedAmount + encoder.encode(payload).byteLength > maxQueuedBytes) {
        return false;
      }

      socket.send(payload);
      return true;
    },
    dispose() {
      disposed = true;
      socket.close(1000, '页面离开');
    },
  };
}

new WebSocket() 返回时，连接可能还处于 CONNECTING，不能立即假定它已经可发送。界面可以监听 open 更新连接提示，也可以像示例一样，在真正发送时检查 readyState。返回 false 时，应向用户显示尚未连接或发送繁忙，不能悄悄丢掉输入内容。

send() 返回 true 在这里只表示数据已交给浏览器发送，不表示服务器已收到，更不表示消息已经入库。bufferedAmount 是尚未发出的应用数据字节数，也不是服务器的确认计数。若要显示“已送达”，需要服务端处理消息后返回对应 clientMessageId 的业务确认。

示例限制的是发送缓冲，且阈值只是演示值。传统 WebSocket 没有标准的接收背压接口：把 message 回调写成 async，浏览器也不会等待它完成才交付下一条消息。大量行情或协同事件应控制订阅量、合并可以替换的状态，并约定服务端限速；把所有消息无限堆进数组只是把压力搬进了 JavaScript 内存。

为什么网络断了，页面可能还显示“已连接”

正常关闭通常能收到 close。但 Wi-Fi 突然中断、网络设备丢失连接状态时，本机不一定立刻知道远端已不可达，连接状态可能暂时没有变化。

这时可以由服务端发送协议层 ping 并检测 pong，或由双方约定应用层心跳，例如客户端发送 { type: 'ping', time }，服务端回复对应响应。浏览器原生 WebSocket API 不提供直接发送协议 ping 帧的方法，应用层 JSON 心跳与协议控制帧不能混为一谈。

超时阈值要考虑网络延迟和后台页面计时器节流。短时间没收到心跳只能说明连接值得怀疑，不能证明某条写入一定失败。navigator.onLine 也只能作为辅助信号，无法证明你的 WebSocket 服务可访问。

重连成功，还需要补齐断线期间的状态

假设客户端最后处理了房间事件 120，掉线时服务端产生了 121 到 125。新连接建立后如果直接开始接收 126，页面仍然缺失五次变更。因此恢复通常包括两件事：

  1. 重新建立连接、恢复认证和订阅。
  2. 带上最后成功应用的游标，请求重放后续事件；若游标过期、历史已清理，就获取完整快照，再从快照对应的版本继续订阅。

游标的作用域必须明确，例如“这个房间的事件序号”。不要把不同房间或不同服务器随意生成的编号直接比较。重放期间也可能收到重复事件，客户端要按事件编号去重，或者采用本身可重复应用的状态更新。

另一个情况是：服务端已保存用户发送的消息，但确认在断线时丢失了。此时盲目重发会产生重复消息。可让客户端为一次用户操作生成稳定的 clientMessageId，重试沿用同一个编号，服务端在相应用户或会话范围内做幂等处理，再返回原结果。更换连接不会自动获得这种保证。

重连间隔一般逐步增加，并加入随机抖动，例如先在短延迟范围内随机等待，连续失败后扩大范围，并设置上限。这样服务重启时，大批客户端不会在完全相同的时刻一起重试。认证失败、用户退出和主动关闭应有不同处理；组件卸载时要取消待执行的重连定时器，防止页面已经离开却又建立连接。

长连接也需要逐项授权

浏览器 WebSocket 构造函数不能任意添加 Authorization 等请求头。认证可以结合受保护的 Cookie、短期连接凭证或握手后的应用协议设计；不要把长期密钥放进 URL，因为 URL 可能进入日志。

WebSocket 的握手不使用普通 fetch 那套 CORS 预检流程，返回 Access-Control-Allow-Origin 不能代替服务端的来源检查。服务端应校验浏览器握手的 Origin，并验证用户身份、房间订阅权限和每条消息的操作权限；Origin 自身又不是用户身份证明。即使用户已连接，也不能允许他随意订阅其他人的私密房间。
