package.json 的 exports 和 imports 分别解决什么问题？

用一个双入口工具包解释公开子路径、包内别名和条件匹配，说明它们与 main、type、类型声明及文件安全的关系。

参考答案

简答

  • exports 定义包对外公开哪些入口；声明后，使用者只能导入列出的路径，内部文件不再能被深层引用。
  • 条件导出按 import、require、types、browser、default 等条件选择不同文件，同一个入口可以同时提供 ESM 和 CommonJS 版本。
  • imports 定义只在包内部使用的 # 开头别名，替代冗长的相对路径。
  • 存在 exports 时，Node.js 和现代打包工具都优先使用它，main 只作为旧工具的回退。
  • 增加或删除 exports 条目会改变可导入的路径，属于需要谨慎处理的 API 变更。

一个双入口包

json
{
  "name": "@acme/utils",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    },
    "./date": {
      "types": "./dist/date.d.ts",
      "import": "./dist/date.js",
      "require": "./dist/date.cjs"
    },
    "./package.json": "./package.json"
  },
  "imports": {
    "#internal/*": "./src/internal/*.js"
  },
  "main": "./dist/index.cjs"
}
  • import { x } from '@acme/utils' 得到 dist/index.js；require('@acme/utils') 得到 dist/index.cjs。
  • import '@acme/utils/date' 可用；import '@acme/utils/dist/internal.js' 会报 ERR_PACKAGE_PATH_NOT_EXPORTED。
  • 包内代码写 import { helper } from '#internal/helper'，不需要 ../../ 相对路径。

条件的顺序

条件按对象中书写的顺序匹配，第一个满足的生效。因此：

  • types 放在第一位，TypeScript 才能找到声明文件。
  • default 放在最后，作为兜底。
  • node、browser、development、production 等条件由运行环境或打包工具决定是否满足，Vite 会根据目标环境设置相应条件。

TypeScript 要按 exports 解析，需要 moduleResolution 为 node16、nodenext 或 bundler。

和 type、main 的关系

  • "type": "module" 让 .js 文件按 ESM 解析，CommonJS 文件用 .cjs 扩展名；反之 "type": "commonjs" 时 ESM 文件用 .mjs。
  • main 是旧的单入口字段。有 exports 时它被忽略，保留它只是为了兼容不支持 exports 的旧工具。

双版本的风险

同一个包的 ESM 和 CommonJS 版本可能在一个应用中被同时加载，各自持有一份模块状态（例如单例、缓存、instanceof 判断的类）。如果包有模块级状态，可以让两个入口共用同一份实现，或者只提供 ESM。Node.js 22.12+ 和 20.19+ 已支持 require() 同步 ESM 模块，新包只发布 ESM 的成本比以前低。

常见追问

  • 为什么加了 exports 后别人的代码报错？对方深层导入了未公开的文件，需要把这些路径加进 exports，或者作为破坏性变更发布大版本。
  • ./package.json 为什么要单独导出？有些工具会读取包的 package.json，不导出时会被拒绝访问。
