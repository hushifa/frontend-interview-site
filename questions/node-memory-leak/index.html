Node.js 服务内存泄漏怎样排查？

先用监控确认内存持续上涨、不回落，再用 --inspect 连 Chrome DevTools，或用 --heapsnapshot-signal、v8.writeHeapSnapshot() 拿堆快照；在怀疑泄漏的操作前后各拍一张，用 Comparison 视图找数量持续增长的对象和引用它们的链。常见原因是无上限的缓存、没移除的事件监听、没清除的定时器和挂在全局上的数据。

参考答案

简答

典型现象是服务内存几天里一直往上涨，涨到上限后进程崩溃、被进程管理器重启，重启时一部分请求失败，负载均衡返回 502。Node.js 是有垃圾回收的语言，泄漏的原因是有引用一直拿着对象不放，垃圾回收器没法回收它们。

排查分两步。先用监控或 process.memoryUsage() 确认 heapUsed 持续上涨、不回落，而不是正常的波动。然后拿堆快照：本地用 --inspect 启动，在 Chrome DevTools 的 Memory 面板里拍；线上可以用 --heapsnapshot-signal=SIGUSR2 启动，需要时发信号让进程写出快照，或者在代码里调用 v8.writeHeapSnapshot()。

找泄漏的方法是对比。先跑一会儿怀疑泄漏的功能，拍一张，再继续跑一段时间，拍第二张，在 DevTools 里切到 Comparison 视图，看哪类对象数量一直在增加，再顺着引用链找到是谁拿着它们。常见的元凶是没有上限的缓存、没移除的事件监听、没清掉的定时器，以及挂在模块级变量或全局对象上越积越多的数据。

要注意，拍快照时主线程会停住，可能超过一分钟，生成快照还可能让堆占用翻倍，内存不够时进程会直接崩溃。所以线上拍快照要选一个崩了也不影响可用性的实例，--inspect 也不能绑定到公网地址。

先确认是不是真的泄漏

Node.js 官方诊断指南描述的泄漏现象是：内存持续增长，可能很快，也可能慢到几天甚至几周，最后进程崩溃重启；同时垃圾回收越来越频繁，CPU 升高、响应变慢。

内存涨一下不等于泄漏。处理一批大请求时堆会变大，垃圾回收后会落回来；泄漏是在负载差不多的情况下，回收后的底线还一路抬高。观察时可以定期记录 process.memoryUsage()，它返回 rss、heapTotal、heapUsed、external、arrayBuffers 几个数。heapUsed 一直涨说明是 JavaScript 对象没释放；heapUsed 平稳而 rss 或 external 一直涨，问题可能在 Buffer 或原生模块这类堆外内存。

怎样拿到堆快照

官方指南列了四种方式。

  1. 用 --inspect 启动进程，在 Chrome 里打开 chrome://inspect 连上去，在 Memory 面板拍快照。适合本地复现。
  2. 用 --heapsnapshot-signal=SIGUSR2 启动，之后执行 kill -USR2 进程号，进程会在当前目录写出 .heapsnapshot 文件。适合线上，不用重启也不用连调试器。
  3. 在代码里调用 node:v8 的 writeHeapSnapshot()。官方建议通过信号或一个内部的 HTTP 接口触发，并且这个接口不能对外暴露。
  4. 通过 Inspector 协议从进程外发 HeapProfiler.takeHeapSnapshot 命令。

另外还有 --heapsnapshot-near-heap-limit=次数，在堆快到上限时自动写快照，用来抓“快崩溃那一刻”的现场。

为什么 --inspect 不能随手开在线上？因为它默认监听 127.0.0.1:9229，如果绑定到 0.0.0.0 这类公网地址，外部主机连上调试端口就能执行任意代码，官方文档专门写了这条安全警告。

怎样从快照里找到泄漏

单看一张快照，很难分清哪些对象是正常的。官方指南给的方法是对比两张快照，并且尽量让差异干净：

  1. 等进程启动完成，先把怀疑泄漏的功能用几次，让正常的初次分配发生完。
  2. 拍第一张快照。
  3. 只反复使用这个功能一段时间，中间不要跑别的。
  4. 拍第二张快照。
  5. 在 DevTools 的 Memory 面板先加载旧的，再加载新的，选中新的，把视图从 Summary 切到 Comparison。
  6. 找增量大的对象类型，在下方面板查看是谁引用着它们。

最后一步最关键。知道“多了一万个某对象”还不够，要沿着引用链往上看，找到是哪个 Map、哪个事件监听数组、哪个闭包一直拿着它们，那才是要改的地方。

常见的泄漏原因

下面是一个典型例子：用 Map 做缓存，键是请求参数，没有上限。

JavaScript
const cache = new Map();

function getUser(id) {
  if (!cache.has(id)) cache.set(id, { id, loadedAt: id });
  return cache.get(id);
}

for (let i = 0; i < 10000; i++) getUser(i);
console.log(cache.size); // 10000

请求参数五花八门时，缓存只进不出，每个用过的 id 都永久留在内存里。改法是给缓存设上限或过期时间，例如超过上限时删掉最早放进去的键：

JavaScript
const limit = 100;
const cache = new Map();

function getUser(id) {
  if (!cache.has(id)) {
    cache.set(id, { id });
    if (cache.size > limit) cache.delete(cache.keys().next().value);
  }
  return cache.get(id);
}

for (let i = 0; i < 10000; i++) getUser(i);
console.log(cache.size); // 100
console.log(cache.has(0)); // false

Map 按插入顺序迭代，所以 cache.keys().next().value 拿到的是最早插入的键，删掉它就能把大小控制在上限内。

其他常见原因和缓存是同一个道理，都是“长期存在的东西引用了短期数据”：

  • 每个请求都给一个全局的 EventEmitter 加监听，却不移除。Node.js 会在同一事件的监听器超过 10 个时打印 MaxListenersExceededWarning，这个警告往往就是线索，见《Node.js 的 EventEmitter 有哪些需要注意的地方？》。
  • setInterval 没有清除，回调闭包里引用的数据就一直释放不掉，见《什么是闭包？它有哪些实际应用？》。
  • 把请求相关的数据放进模块级数组或全局对象，比如为了统计把每个请求对象 push 进一个数组。

浏览器里的排查思路基本相同，见《前端内存泄漏应该怎样定位？》。

常见追问

内存不够时连快照都拍不出来怎么办？

官方指南提醒，快照在内存里生成，可能让堆占用翻倍。可以先用 --max-old-space-size 给进程更多堆空间，或者在测试环境用较小的堆复现，配合 --heapsnapshot-near-heap-limit 在接近上限时自动写快照。

为什么不直接调大内存上限？

那只是让崩溃来得晚一点。泄漏的对象始终被引用，堆再大也会被慢慢占满，而且堆越大，每次垃圾回收的工作量越大，响应会更慢。
