前端渲染方式怎样影响 SEO 和部署？

爬虫和社交分享服务首先读的是服务器返回的 HTML。CSR 页面的初始 HTML 通常没有正文，要等脚本执行；SSR 每次请求生成完整 HTML，SSG 和预渲染在构建时生成，内容都在初始 HTML 里。部署上，history 路由的 SPA 要配置路径回退，可回退又会让不存在的路径返回 200，需要预渲染已知页面或用 noindex 处理。

参考答案

简答

搜索引擎和分享卡片最先看到的，是服务器返回的那份 HTML。CSR 页面的初始 HTML 通常只有一个空壳，正文要等脚本跑完才出来。Google 能执行 JavaScript，但渲染要排队，有延迟；很多社交平台的卡片抓取器根本不执行 JavaScript，只读初始 HTML 里的 og: 标签。

SSR 在每次请求时生成完整 HTML，SSG 和预渲染在构建时就把每个页面生成好，三者都让正文、标题和链接出现在初始 HTML 里，抓取更可靠。区别在部署：SSR 需要一直运行的服务端，SSG 和预渲染的产物可以放在静态托管上。

部署 SPA 时，要让服务器把未知路径回退到 index.html，否则刷新深层页面会 404；但这样一来所有路径都返回 200，又要想办法让真正不存在的路径返回 404。

要注意，预渲染只能保证内容读得到。能不能收录、排第几，还取决于内容质量、链接和搜索引擎自己的策略。初始 HTML 里具体要放哪些标签，见《前端 SEO 有哪些具体手段？》。

不同渲染方式下，初始 HTML 里有什么

渲染方式HTML 何时生成初始 HTML 里有没有正文部署形态
CSR浏览器执行脚本后通常只有空壳静态托管
SSR每次请求时有需要服务端运行
SSG / 预渲染构建时有静态托管

CSR 的问题不在于“搜索引擎完全看不到”，而是正文依赖一次额外的渲染：Google 要排队执行脚本，脚本失败或超时，抓到的就是空壳；不执行脚本的分享抓取器则一定看不到。SSR 和 SSG 把这一步提前到了服务端或构建时。

不管哪种方式，每个页面的 <title>、description、canonical 都要和正文一起出现在 HTML 里，页面之间用 <a href> 连接。逐项的写法和检查表见《前端 SEO 有哪些具体手段？》。

不存在的页面怎样返回 404

不存在的页面要返回 HTTP 404，而不是返回 200 再显示“未找到”，后者叫软 404。做法取决于渲染方式。SSR 时，如果查出来数据不存在，要在开始渲染前就把状态设成 404，Next.js 里是调用 notFound()。纯静态站点要提供一个 404.html，并确认托管平台对不存在的路径确实返回了 404。

SPA 刷新深层页面为什么会 404

用 history 模式的路由时，地址栏里是 /questions/42 这样的路径。在站内点击跳转没问题，因为是前端路由处理的。可是用户一刷新，浏览器会真的去服务器请求 /questions/42 这个文件，服务器上没有，就 404 了。

所以要让服务器把找不到的路径都回退到 index.html，交给前端路由：

nginx
location / {
  try_files $uri $uri/ /index.html;
}

可这样又带来一个问题：所有不存在的路径也都返回 200 了。更好的做法是预渲染已知的页面，其余路径返回 404 页面；或者由前端路由显示 404，同时加上 <meta name="robots" content="noindex">。

hash 模式，也就是 /#/questions/42，不需要配服务器，因为 # 后面的部分根本不会发给服务器。也正因为这样，它对 SEO 不利。

常见追问

CSR 一定对 SEO 不利吗？

不一定就收录不了，但有渲染延迟和渲染失败的风险，而且分享卡片通常显示不出来。
