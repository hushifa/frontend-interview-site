前端渲染方式怎样影响 SEO 和部署？

爬虫和社交分享服务首先读的是服务器返回的 HTML，而 CSR 页面的初始 HTML 通常没有正文。SSR 和 SSG 能直接提供内容，但还要返回正确的状态码、唯一的 title 和 canonical、提供 sitemap。SPA 部署需要配置路径回退，同时让不存在的路径返回 404。

参考答案

简答

搜索引擎和分享卡片最先看到的，是服务器返回的那份 HTML。CSR 页面的初始 HTML 通常只有一个空壳，正文要等脚本跑完才出来。Google 能执行 JavaScript，但渲染要排队，有延迟；很多社交平台的卡片抓取器根本不执行 JavaScript，只读初始 HTML 里的 og: 标签。所以 SSR 和 SSG 在初始 HTML 里就带上正文、标题和链接，抓取更可靠。

光有内容还不够。不存在的页面要返回 HTTP 404，而不是返回 200 再显示一个“未找到”界面，后者叫软 404。每个页面还要有唯一的 <title>、<meta name="description">，以及指向规范地址的 <link rel="canonical">。

部署 SPA 时，要让服务器把未知路径回退到 index.html，否则刷新深层页面会 404；但这样一来所有路径都返回 200，又要想办法让真正不存在的路径返回 404。

要注意，预渲染只能保证内容读得到。能不能收录、排第几，还取决于内容质量、链接和搜索引擎自己的策略。

初始 HTML 里要有什么

下面是一个题目页的 HTML 应该包含的东西：

HTML
<head>
  <title>HTTP 预检请求怎样工作？｜前端题库</title>
  <meta name="description" content="解释浏览器何时发送 OPTIONS 预检请求……" />
  <link rel="canonical" href="https://example.com/questions/http-preflight" />
  <meta property="og:title" content="HTTP 预检请求怎样工作？" />
</head>
<body>
  <h1>HTTP 预检请求怎样工作？</h1>
  <p>正文……</p>
  <a href="/questions/http-cors">相关：CORS</a>
</body>

注意页面之间是用真正的 <a href> 连起来的。爬虫靠这些链接发现别的页面；如果只用一个按钮加 onClick 跳转，爬虫不会跟过去。

另外可以加结构化数据，也就是 JSON-LD，帮搜索引擎理解这个页面是什么类型。

状态码怎么返回

情况状态码
页面存在200
页面不存在404
永久迁移301 / 308
临时故障503

SSR 时，如果查出来数据不存在，要在开始渲染前就把状态设成 404，Next.js 里是调用 notFound()。纯静态站点要提供一个 404.html，并确认托管平台对不存在的路径确实返回了 404。

SPA 刷新深层页面为什么会 404

用 history 模式的路由时，地址栏里是 /questions/42 这样的路径。在站内点击跳转没问题，因为是前端路由处理的。可是用户一刷新，浏览器会真的去服务器请求 /questions/42 这个文件，服务器上没有，就 404 了。

所以要让服务器把找不到的路径都回退到 index.html，交给前端路由：

nginx
location / {
  try_files $uri $uri/ /index.html;
}

可这样又带来一个问题：所有不存在的路径也都返回 200 了。更好的做法是预渲染已知的页面，其余路径返回 404 页面；或者由前端路由显示 404，同时加上 <meta name="robots" content="noindex">。

hash 模式，也就是 /#/questions/42，不需要配服务器，因为 # 后面的部分根本不会发给服务器。也正因为这样，它对 SEO 不利。

sitemap 和 robots.txt 各管什么

sitemap.xml 列出希望被收录的页面，在 robots.txt 里声明它的位置。

robots.txt 不能用来藏敏感页面。它只是给爬虫的建议，爬虫可以不听，而且这个文件本身谁都能看到，写进去反而暴露了路径。

常见追问

CSR 一定对 SEO 不利吗？

不一定就收录不了，但有渲染延迟和渲染失败的风险，而且分享卡片通常显示不出来。
