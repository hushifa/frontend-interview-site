WebXR 应用需要处理哪些设备与会话边界？

理解 XRSession、参考空间、帧循环和权限，区分沉浸式 VR/AR 与普通 WebGL 画布。

参考答案

普通 WebGL 页面由应用控制相机，绘制到浏览器窗口；WebXR 会话则与设备的姿态、视图、输入和显示调度协作。头显移动后，相机不能仍用页面里写死的位置，否则画面会与用户感知脱节。

因此 WebXR 的核心不只是“画一个 3D 场景”，而是正确管理设备提供的空间与会话生命周期。

先判断模式，再由用户发起会话

常见模式包括 inline、immersive-vr 和 immersive-ar。inline 在普通页面中呈现相应体验，沉浸式模式则涉及设备显示与用户授权。

navigator.xr 存在不代表当前设备支持所有模式。可以通过 isSessionSupported 检查目标模式，再从明确用户操作发起 requestSession。检查返回支持，也不保证实际请求不会因权限、设备占用或状态变化失败。

安全上下文、权限策略和用户激活要求应按模式及平台处理。不要把沉浸式会话在页面加载时自动启动，也不要把用户拒绝当成需要循环重试的异常。

reference space 决定坐标相对于谁

viewer 空间跟随观看者；local 尽量提供相对稳定的局部原点；local-floor 在地面附近建立适合站立场景的坐标；bounded-floor 等还涉及活动边界信息。

不是每个设备都支持所有空间，地面高度也可能是估计值。若业务依赖地面或边界，应在请求能力与空间时明确需求，并处理不可用情况，不能默默把 viewer 空间当成等价替代。

参考空间还可能发生重置或原点调整。应用需要理解坐标变化，避免虚拟物体因跟踪恢复突然出现在错误位置。空间坐标应按 API 约定的单位和轴向使用，不能把 CSS 像素直接当作米。

用 XR 帧调度和设备视图渲染

会话通过自己的 requestAnimationFrame 提供 XRFrame。应用在当前帧中取得相对于参考空间的 viewer pose，再根据各个 view 的投影和视图信息绘制。

不要假定永远只有两个固定视口，应该遍历设备提供的视图集合，并使用对应渲染层的视口信息。XRFrame 的姿态访问具有帧生命周期约束，不能把整个 frame 保存后在任意异步回调里继续当作当前姿态使用。

跟踪暂时不可用时，getViewerPose 可能返回 null。此时要合理跳过或调整显示，而不是访问空对象导致会话循环崩溃。

若采用 WebGL 渲染路径，还需要建立兼容的上下文与 XR 渲染层，按会话要求绑定目标并绘制。普通窗口的 requestAnimationFrame 不应代替沉浸式显示的帧节奏。

输入源不只是一对手柄

XRInputSource 可能代表控制器、凝视或手部输入，能力由 targetRayMode、gripSpace、gamepad、hand 等可用信息表达。设备可能只有其中一部分，输入源也可能在会话中添加或移除。

select、squeeze 等事件表达交互意图，应用仍要做射线命中、目标反馈和状态处理。不要固定读取“第一个手柄的第二个按钮”作为所有设备的确定操作方式。

触摸、鼠标或键盘的二维降级入口也应保留。单靠空间手势不一定适合所有用户，尤其是精细输入和长期操作。

会话会结束，也可能只是暂时不可见

用户退出、设备中断或浏览器策略都可能结束会话，应监听 end 并恢复普通页面状态，清理监听和不再使用的资源。若渲染资源仍被二维预览共享，则应按所有权决定释放，而不是一律删除全部对象。

visibilityState 变化也需要处理，暂时不可见不一定等于会话已经结束。后台或被遮挡时减少无用工作，恢复时重新确认状态，不能假设所有输入与跟踪一直连续。

环境感知、命中测试、手部追踪和深度等能力通常有独立的可用性与权限边界。申请最少必需功能，避免因为可选能力不可用而让整个体验无法启动。

真实验证应覆盖目标设备的帧率、跟踪丢失、输入变化、舒适性和退出恢复。模拟器可以检查逻辑和部分布局，但不能证明头显延迟、真实空间定位或用户眩晕风险已得到验证。
