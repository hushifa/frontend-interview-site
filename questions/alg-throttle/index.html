怎样实现首沿节流？它与尾沿节流、防抖有什么区别？

节流是限制函数在每段时间里最多执行一次。首沿节流在一段时间开始时马上执行，这段时间里的其他调用都丢掉；尾沿节流在这段时间结束时，用最后一次调用的参数执行；防抖则要等调用停下来一段时间才执行。节流只管多久开始执行一次，不等异步操作做完。

参考答案

简答

节流是限制函数的执行频率：每 wait 毫秒最多执行一次。按在什么时候执行，分成首沿和尾沿两种。

首沿节流是第一次调用马上执行，同时开一个 wait 毫秒的窗口，窗口里的调用全部丢掉，窗口结束后，下一次调用又马上执行。尾沿节流是第一次调用只开窗口、不执行，窗口里一直记下最新的参数，窗口结束时执行一次，而且结束时间不会因为新调用往后推。

和防抖的区别在于：防抖每次调用都重新计时，一直有调用就一直不执行；节流就算调用不停，也会按固定节奏执行。

实现首沿节流有个细节：要在调用 fn 之前就把 blocked 设上，这样 fn 内部又调了自己，或者同步抛了错，窗口照样生效。还要知道，节流只控制多久开始一次，fn 返回的 Promise 还没完成，下一个窗口照样会再调它。要限制同时进行的数量，得用并发控制。

三种策略放在一起比

等待时间 100 毫秒，在 0、30、60 毫秒依次调用 A、B、C，之后不再调用：

策略执行典型场景
首沿节流0 毫秒执行 A，B、C 被丢弃按钮防连点、立即响应的快捷键
尾沿节流100 毫秒执行 C滚动时更新位置，需要拿到最新值
尾沿防抖160 毫秒执行 C搜索框输入停止后再请求

尾沿节流和防抖最后执行的都是 C，区别在时间。尾沿节流的窗口从 A 开始算，100 毫秒准时结束；防抖每次调用都往后推，从最后一次 C 的 60 毫秒再等 100 毫秒，到 160 毫秒才执行。

用现成的库之前，要看清它的默认选项。比如 Lodash 的 throttle，默认首沿和尾沿都开，只调用一次的话，只在首沿执行。

首沿节流的实现

JavaScript
function throttle(fn, wait) {
  if (typeof fn !== 'function') throw new TypeError('需要传入函数');
  if (!Number.isInteger(wait) || wait < 0 || wait > 2_147_483_647) {
    throw new RangeError('等待时间必须是计时器范围内的非负整数毫秒');
  }

  let blocked = false;
  let timer;

  function wrapped(...args) {
    if (blocked) return;

    blocked = true;
    timer = setTimeout(() => {
      blocked = false;
      timer = undefined;
    }, wait);

    return fn.apply(this, args);
  }

  wrapped.cancel = () => {
    clearTimeout(timer);
    blocked = false;
    timer = undefined;
  };

  return wrapped;
}

窗口开没开，看的是 blocked。timer 只是为了 cancel 时能把定时器清掉。

为什么 blocked = true 要写在 fn.apply 前面？假设反过来写，先执行 fn，fn 里面又调了一次 wrapped，这时 blocked 还是 false，就会再执行一次，窗口等于没开。fn 同步抛错也一样，抛错后就走不到设 blocked 那一行了。先设好，这两种情况都不怕。

被丢掉的调用返回 undefined，只有真正执行的那次返回 fn 的结果。cancel 会马上结束当前窗口，之后的调用立刻就能执行。

尾沿节流的实现

JavaScript
function throttleTrailing(fn, wait) {
  let timer;
  let lastArgs;
  let lastThis;

  function wrapped(...args) {
    lastArgs = args;
    lastThis = this;
    // 窗口已经开启时只更新参数，不推迟结束时间。
    if (timer !== undefined) return;
    timer = setTimeout(() => {
      const callThis = lastThis;
      const callArgs = lastArgs;
      timer = lastArgs = lastThis = undefined;
      fn.apply(callThis, callArgs);
    }, wait);
  }

  wrapped.cancel = () => {
    clearTimeout(timer);
    timer = lastArgs = lastThis = undefined;
  };

  return wrapped;
}

和防抖比，关键区别就在 if (timer !== undefined) return 这一行。窗口已经开了，就只更新参数，不碰定时器。

实际跑一下：每 25 毫秒调用一次，一共 10 次，等待时间 100 毫秒，结果执行了 3 次，拿到的分别是第 4、8、10 次调用的参数。每个窗口从它的第一次调用开始计时，结束时用的是窗口里最新的参数。

如果把那一行换成“每次都 clearTimeout 再重新计时”，就变成了防抖，调用不停的那段时间里一次都不会执行。

和 requestAnimationFrame 的关系

滚动、拖拽这类跟画面更新有关的事件，还可以用 requestAnimationFrame 来合并：同一帧里只处理最后一次事件，执行频率自动跟屏幕刷新率一致，页面切到后台时还会暂停。这比写死一个毫秒数的节流，更贴合渲染的节奏。

常见追问

节流函数里的 this 怎么保持？

wrapped 要用普通函数定义，调用时用 fn.apply(this, args) 转过去。箭头函数没有自己的 this，不能用来定义 wrapped。

为什么要校验等待时间的范围？

浏览器和 Node.js 的定时器，碰到超过 2147483647 毫秒的延迟，会当成 1 毫秒处理。小数和负数也会有不直观的行为。所以在创建定时器之前，就把这些值拒绝掉。
