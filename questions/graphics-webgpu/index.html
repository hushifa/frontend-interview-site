WebGPU 与 WebGL 的关注点有哪些不同？

WebGPU 是更新、更显式的 GPU 接口，除渲染管线外还提供计算管线，着色器语言是 WGSL。它目前不是 Baseline、只在安全上下文可用，可以用 compatibility 功能级别覆盖较旧的图形后端；是否从 WebGL 迁移取决于设备覆盖和计算需求。

参考答案

简答

WebGL 是一个状态机：你设好一堆全局状态，然后画，边设边画。WebGPU 换了做法，先把管线、资源和绑定提前描述清楚，再把命令录下来一次性提交。它还能做通用计算，不只是画图。着色器语言也换成了 WGSL，GLSL 的代码不能直接拿来用。

用之前要一步步拿设备：先看 navigator.gpu 在不在，再 requestAdapter()，它可能返回 null；最后 requestDevice()，它也可能失败。

支持面要特别注意。MDN 把 WebGPU 标为 Limited availability，不是 Baseline，而且整个 API 只在 HTTPS 这类安全上下文里能用。所以要做特性检测，准备好 WebGL 或 CPU 的回退。

如果想覆盖更旧的设备，可以用 requestAdapter({ featureLevel: 'compatibility' }) 申请兼容模式。它能跑在 OpenGL ES 3.1、Direct3D 11 这些较旧的后端上，代价是功能和限制更少。

怎样拿到 GPU 设备

下面的函数把每一步可能失败的地方都处理了，拿不到就返回 null，让调用方去走回退：

JavaScript
async function initGPU() {
  if (!navigator.gpu) return null; // 不支持或不是安全上下文
  const adapter = await navigator.gpu.requestAdapter();
  if (!adapter) return null; // 没有可用的 GPU 适配器
  const device = await adapter.requestDevice();
  device.lost.then((info) => {
    console.warn('GPU 设备丢失', info.reason);
    // 停止使用旧资源，按需重新初始化
  });
  return device;
}

adapter 可以理解成“一块可用的 GPU”，device 是你和它之间的连接，之后所有资源都从 device 创建。

device.lost 是一个 Promise，设备丢失时会 resolve，比如驱动重置。这时旧资源都不能用了，要停下来，按需重新初始化。

如果要用可选功能或更高的限制，先查 adapter.features 和 adapter.limits，再在 requestDevice() 里申请。申请了不支持的项，requestDevice() 会失败。

计算管线长什么样

下面这段 WGSL 把数组里每个数乘 2：

wgsl
@group(0) @binding(0) var<storage, read_write> values: array<f32>;

@compute @workgroup_size(64)
fn main(@builtin(global_invocation_id) id: vec3<u32>) {
  if (id.x < arrayLength(&values)) {
    values[id.x] = values[id.x] * 2.0;
  }
}

GPU 是成组地跑这个函数的，@workgroup_size(64) 表示一组 64 个。所以 N 个元素要调度 Math.ceil(N / 64) 个工作组。

为什么要判断 id.x < arrayLength(&values)？因为向上取整以后，最后一组可能多出几个，这个判断防止它们越界。

完整的应用还要创建带正确 usage 的缓冲区、绑定组和计算管线，然后调用 dispatchWorkgroups 并提交。

和 WebGL 的主要区别

WebGLWebGPU
编程模型全局状态机，边设状态边绘制预先创建管线，录制命令后提交
计算只能借渲染管线模拟原生计算管线
着色器GLSLWGSL
错误getError() 轮询错误作用域、uncapturederror 事件
支持面几乎所有浏览器仍有主流浏览器不支持

怎样把计算结果读回来

queue.submit() 只表示工作提交了，不代表已经执行完。要读回数据，得把结果复制到一个带 MAP_READ 用途的缓冲区，再 await buffer.mapAsync(GPUMapMode.READ)。

所以 GPU 计算不一定更快。数据量很小、又要频繁读回时，上传和下载的开销可能比计算本身还大，这时直接用 CPU 反而更快。

要不要从 WebGL 迁移

现有的 WebGL 应用跑得好好的、又要覆盖所有用户，就没必要为了新接口重写。

要做 GPU 计算，比如推理、物理模拟、大规模数据处理，或者渲染的瓶颈在 CPU 提交开销上，WebGPU 的收益就比较明显。

Three.js、Babylon.js 这些库已经提供了 WebGPU 渲染器，不支持时还能回退到 WebGL，用它们接入更稳妥。

常见追问

怎样判断当前是不是兼容模式？

检查 device.features.has('core-features-and-limits')，返回 false 就表示是兼容模式。

JavaScript 对象能直接传给 WGSL 结构体吗？

不行。要按 WGSL 的对齐规则写进 ArrayBuffer，每个字段的偏移和填充都要算对。
