WebSocketStream 为什么被认为能改善背压处理？

从慢消费者导致消息积压的问题解释背压，说明 WebSocketStream 的读写流、异步消费方式、关闭与异常处理，以及非标准实验性 API 的使用限制。

参考答案

假设行情服务每秒推送一千条消息，而页面每秒只能完成两百条消息的解析和绘图。只要这种速度差持续存在，剩下的消息就会积压，内存越来越多，用户看到的内容也越来越滞后。

背压解决的是“下游处理不过来时，让上游知道该慢一点”。它不是把处理代码变快，而是让生产和消费的速度能够协调。

传统 WebSocket 使用 message 事件交付数据，没有标准的接收背压接口。即使这样写：

JavaScript
socket.addEventListener('message', async (event) => {
  await saveMessage(event.data);
});

浏览器也不会等待 saveMessage 完成再派发下一条消息。这段代码只是示意事件监听方式，socket 和 saveMessage 需要由业务提供；其中的 await 只暂停当前回调，不会暂停事件源，还可能产生大量并行的保存任务。

WebSocketStream 尝试把 WebSocket 连接接入 Web Streams，让应用通过可读流、可写流表达消费能力。它目前仍是非标准、实验性的 API，支持范围有限，不适合作为面向所有浏览器的唯一通信实现。

接收端通过读取节奏表达处理能力

连接成功后，socket.opened 兑现的对象包含 readable 和 writable。应用从 readable 获取 reader，每处理完一条消息再调用一次 read()，底层流就能结合自身队列和传输实现传递背压。

与给 message 加 async 的关键区别是：下一次读取由应用发起。这样可以避免应用层无节制地创建处理任务，但仍可能存在流队列、网络缓冲和已经到达的数据，不能理解成“永远只有一条消息占用内存”。

下面的订阅示例约定服务端理解 { type: 'subscribe', topic: 'prices' }。handleMessage 接收每条原始消息，可同步处理，也可返回 Promise；服务端正常结束流时函数返回关闭信息。

JavaScript
async function consumeFeed(url, handleMessage) {
  if (!('WebSocketStream' in globalThis)) {
    throw new Error('当前浏览器不支持 WebSocketStream');
  }

  const socket = new WebSocketStream(url, {
    signal: AbortSignal.timeout(5000),
  });

  // 立即观察关闭失败，避免握手失败时漏接另一个 Promise 的拒绝。
  const closedOutcome = socket.closed.then(
    (value) => ({ ok: true, value }),
    (error) => ({ ok: false, error }),
  );

  let reader;
  let writer;
  try {
    const { readable, writable } = await socket.opened;
    reader = readable.getReader();
    writer = writable.getWriter();

    await writer.write(JSON.stringify({ type: 'subscribe', topic: 'prices' }));

    while (true) {
      const { value, done } = await reader.read();
      if (done) break;
      await handleMessage(value);
    }
  } finally {
    reader?.releaseLock();
    writer?.releaseLock();
    socket.close();
  }

  const outcome = await closedOutcome;
  if (!outcome.ok) throw outcome.error;
  return outcome.value;
}

调用方仍要用 try/catch 或 .catch() 处理 consumeFeed() 的失败。例如处理器解析了不合法的 JSON 并抛错时，函数会尝试关闭连接，然后把错误交给调用方；不会继续消费后续消息。

这段代码是顺序消费示例，不是行情业务的完整客户端。它没有实现消息鉴权、重连、页面卸载后的主动取消或历史恢复。用于组件时，应把连接所有权放在组件或独立连接服务中，向清理逻辑暴露 close()，避免组件销毁后仍在等待下一次读取。

写入端也要配合，不能无视 Promise

writer.write(message) 返回 Promise。循环中等待本次写入完成，再生产下一条消息，可以避免生产者不受限制地向可写流排队。需要根据队列压力调度生产时，还可以使用 writer.ready 和 desiredSize 等 Streams 能力。

如果应用把一百万次 writer.write() 全部调用后再一起 Promise.all()，数据仍然会提前创建并排队。流提供了表达压力的机制，但生产代码必须尊重它；“接口返回 Promise”本身不等于自动控制了所有内存。

同样，写入 Promise 兑现只说明这次流写入在传输层相应阶段完成，不代表接收端的业务已经保存数据。订单确认、消息送达仍需要应用协议的确认消息。

传统 WebSocket 的 bufferedAmount 可以帮助应用观察待发送字节量，选择暂缓发送或合并数据，但它不是可等待的读取背压接口，也不能告诉页面接收队列是否安全。

signal、close() 和两个 Promise 各管什么

opened 表示握手成功后可取得读写流，closed 表示连接最终如何结束。握手失败时，两者都可能拒绝；只捕获 opened 而完全不观察 closed，可能留下未处理的 Promise 拒绝。示例因此在创建连接后立即为 closed 安装处理器。

构造函数的 signal 用来在握手完成前取消建立连接，例如实现五秒连接超时。它在连接建立后不起取消作用，不能靠同一个 AbortSignal 关闭已经运行的消息订阅。

已建立的连接需要用 socket.close()，也可以按该 API 的定义通过关闭可写端结束连接。需要指定正常关闭原因时，接口形式是：

JavaScript
socket.close({ closeCode: 1000, reason: '停止订阅' });

这与传统 WebSocket.close(1000, '停止订阅') 的参数形式不同。close() 发起关闭，不返回一个代表关闭完成的 Promise；要了解最终结果，应观察 closed。异常断连时 closed 会拒绝，不能只写成功分支。

releaseLock() 仅释放 reader 或 writer 对流的独占锁，不会因此自动取消业务订阅或关闭网络连接，这也是示例在释放锁后还调用 socket.close() 的原因。

为什么有背压仍然需要业务限流

一个巨大消息在被交给应用前就可能已经占用大量内存，因此仍要限制消息体积。服务端也不能把无法发送的数据永远保存在自己的队列里；慢客户端可能需要降频、合并、断开，或者退回快照更新。

对于行情这样的“只关心最新状态”，跳过过时中间值通常比忠实排队展示更合理。对于交易流水这样的“每条都必须处理”，应有持久化日志和游标恢复，而不是指望一个长连接永久保存所有数据。

即使某个浏览器支持 WebSocketStream，也应验证实际版本行为和服务器互通情况。需要兼容更多浏览器时，可选择传统 WebSocket 并自行设计有界队列、确认窗口或服务端限速。用一个 ReadableStream 包装传统 message 事件，只是改变了应用看到的接口；如果消息源仍不理会消费速度，就没有凭空得到同等的底层背压能力。
