Cookie、localStorage 和 sessionStorage 如何选择？

选择浏览器存储要看服务器是否需要自动收到、数据的生命周期、规模和敏感程度。Cookie、Web Storage 和 IndexedDB 解决的不是同一个问题。

参考答案

简答

  • 选择存储先看四点：服务器是否要自动收到、生命周期、数据规模和敏感程度。
  • Cookie 的价值在于随 HTTP 请求发送，适合会话等服务端需要的小数据。
  • localStorage 适合跨标签保留的小型偏好，sessionStorage 只属于当前页面会话。
  • 大量结构化数据用 IndexedDB；敏感信息和数据丢失后的恢复要单独设计。

先问四个问题

登录会话、深色主题和未完成表单都可以叫“要保存的数据”，但适合的位置不同：

  1. 服务端是否需要在每次请求中自动收到它？
  2. 数据是跨标签页保留，还是只属于当前页面会话？
  3. 数据是否小而简单，能否接受同步访问？
  4. 数据丢失后能否重新生成，是否包含敏感信息？
存储更适合不适合
Cookie少量会话状态、服务器需要参与的状态大对象、用户资料、列表缓存
localStorage小型跨刷新偏好令牌、大文档、事务数据
sessionStorage当前页面会话的临时状态重要草稿和跨标签共享
IndexedDB大型结构化数据、离线数据、事务只保存一个简单主题字符串

浏览器隐私模式、分区策略和用户清理会影响所有本地存储。没有哪种 API 能承诺数据永久存在。

Cookie 的价值是参与 HTTP 请求

服务端可以通过 Set-Cookie 设置 Cookie，浏览器会根据 Domain、Path、Secure、SameSite、过期时间和凭据策略决定是否在请求中携带。Cookie 是少数能让服务端自动获得状态的客户端存储方式。

登录会话通常使用 HttpOnly、Secure 和合适的 SameSite，让 JavaScript 无法直接读取会话值并降低窃取风险。但 Cookie 自动发送仍需要 CSRF 防护、权限校验和服务端失效策略。HttpOnly 不是“所有认证问题都解决了”。

Cookie 有大小和数量限制，自动携带还会增加请求头。不要把完整用户资料或大列表放进去，也不要把 Path 当成真正的权限隔离。没有过期时间的会话 Cookie 也不一定在关闭浏览器后绝对消失，浏览器可能恢复会话。

localStorage 适合小型偏好

Web Storage 只保存字符串，且 API 是同步的。主题偏好可以这样封装：

JavaScript
const KEY = 'frontend-notes:theme:v1';

export function readTheme() {
  try {
    const value = localStorage.getItem(KEY);
    return ['light', 'dark', 'system'].includes(value) ? value : 'system';
  } catch {
    return 'system';
  }
}

export function saveTheme(value) {
  if (!['light', 'dark', 'system'].includes(value)) {
    throw new TypeError('主题值无效');
  }
  try {
    localStorage.setItem(KEY, value);
    return true;
  } catch {
    return false;
  }
}

属性访问和写入都可能因隐私策略、配额或禁用设置失败，因此界面要有默认值和失败路径。对象需要自行 JSON 序列化和读取校验，不能假设字符串会自动变回对象。不要调用 localStorage.clear()，同源下其他功能的键也会被删；使用前缀和版本便于迁移。

它没有内置 TTL。需要过期时保存时间并在读取时判断，同时考虑时钟变化和清理。每次输入都序列化大型文档会阻塞主线程，这种数据应考虑 IndexedDB 或分片保存。

sessionStorage 是页面会话级隔离

sessionStorage 通常按源和顶层浏览上下文区分。刷新同一标签页通常仍能读到它，独立打开的另一个标签页通常拥有不同内容；新页面保留 opener 时，初始值可能被复制，之后又各自独立。

它适合当前标签页的临时筛选、未完成步骤和一次性 UI 状态。重要草稿不能只放在这里，因为标签页结束、会话恢复策略或用户清理都可能让它消失。它也不是权限和过期机制，验证码、会话和授权截止时间应由服务端控制。

跨标签通知不是并发事务

localStorage 改变时，其他符合条件的文档可以收到 storage 事件，执行写入的窗口不会收到自己的那次事件。这个事件只传递变化通知，不提供锁、版本比较或事务；两个标签页都读到旧值再写回，仍会互相覆盖。

需要跨标签广播复杂状态时可以考虑 BroadcastChannel，但并发写入仍需 IndexedDB 事务、版本号、Web Locks 或幂等协议。事件通知不会自动解决数据一致性。

敏感信息和恢复策略要单独设计

脚本可读的 localStorage 和 sessionStorage 都可能被同源 XSS 读取，不适合存放长期密钥和可直接换取高权限的令牌。把令牌从 Cookie 换到 localStorage 并不会自动更安全。

本地数据可能因空间不足、隐私模式、浏览器清理和设备故障而消失。主题和缓存可以回退或重建，重要业务数据应有服务端同步、导出或恢复方案。先按数据的重要性设计丢失后的行为，再选择存储 API。
