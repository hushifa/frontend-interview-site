Cookie、localStorage 和 sessionStorage 如何选择？

Cookie 会自动跟着请求发给服务端，适合放会话标识；localStorage 一直保存，同源的标签页共享；sessionStorage 只在当前标签页里有效，关了就没。

参考答案

简答

三者最大的区别是：Cookie 会自动跟着匹配的请求发给服务端，另外两个不会。所以 Cookie 适合放会话标识这种服务端要读的数据，单个大约 4KB。

localStorage 按源持久保存，同源的所有标签页共享，不手动清除就一直在，容量通常约 5MB。sessionStorage 也按源，但还按标签页隔离，关掉标签页就清除了。

选的时候看谁要用、要存多久。登录会话用服务端设置的 HttpOnly Cookie；主题、语言、草稿用 localStorage；只属于当前标签页的流程状态用 sessionStorage；数据量大或者有二进制，就用 IndexedDB。

要注意，两种 Web Storage 都是同步 API，只能存字符串，页面里任何脚本都能读到，所以不要存令牌这类敏感数据。

为什么登录态要放 HttpOnly Cookie

令牌放在 localStorage 里，页面上任何脚本都能读。一旦页面有 XSS，攻击者注入的脚本一行就能把令牌偷走。

服务端下发 HttpOnly; Secure; SameSite=Lax 的 Cookie 就不一样。HttpOnly 让页面脚本读不到它，XSS 没法直接窃取；请求时浏览器自动带上，前端也不用管。

读写 Web Storage 要处理异常

下面是读 JSON 的一个安全写法：

JavaScript
function readJSON(key, fallback) {
  try {
    const raw = localStorage.getItem(key);
    return raw === null ? fallback : JSON.parse(raw);
  } catch {
    return fallback;
  }
}

为什么一个读取也要包 try？因为存进去的内容可能不是合法 JSON，JSON.parse 会抛错；隐私模式或存储被禁用时，访问 localStorage 本身也可能失败。写入时同样可能抛 QuotaExceededError，所以读写都要处理异常。

两个容易误解的行为

其他同源标签页修改了 localStorage，本页会收到 storage 事件。可是修改的那一页自己收不到。

sessionStorage 在“复制标签页”时会复制一份过去，之后两边各管各的，互相独立。

常见追问

在一个标签页里改了 localStorage，自己能收到 storage 事件吗？

收不到。storage 事件只发给其他同源标签页，修改的那一页自己不会触发。

复制标签页后，sessionStorage 会怎样？

新标签页会拿到一份复制品，内容和原来一样。之后两边独立，改一边不影响另一边。
