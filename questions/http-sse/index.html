SSE 与 WebSocket 有什么区别？

SSE 是服务器单向往浏览器推文本，走普通 HTTP，断线会自动重连续传；WebSocket 是双向连接，能传二进制，但重连和消息确认都要自己做。

参考答案

简答

SSE 是服务器往浏览器单向推消息。浏览器发一个普通请求，服务器不结束响应，一条一条往里写事件。WebSocket 则是一条双向连接，两边都能随时发。

因为 SSE 就是一个 Content-Type: text/event-stream 的普通 HTTP 响应，现有的代理、鉴权、HTTP/2 都能直接用。WebSocket 要先做一次协议升级。

SSE 还有个好处，浏览器的 EventSource 断线后会自动重连，并用 Last-Event-ID 请求头告诉服务器最后收到哪条。WebSocket 没有内置重连。不过 SSE 只能传 UTF-8 文本，WebSocket 文本和二进制都行。

所以通知、进度、AI 流式输出这类只需要推的，用 SSE 或 fetch 流；聊天、协同编辑、游戏这种高频双向的，用 WebSocket。

服务器发出来的事件长什么样

SSE 的格式很简单，每行一个字段，空行表示一个事件结束：

text
id: 42
event: progress
data: {"percent": 60}

data: 第一行
data: 第二行

retry: 5000

第一个事件有编号 42，类型是 progress。第二个事件有两行 data，浏览器会用换行把它们拼成一段。retry 设置断线后多少毫秒重连。

另外，以 : 开头的行是注释，浏览器会忽略。服务器常用它发心跳，防止中间的代理觉得连接空闲把它断掉。

浏览器怎么接收

JavaScript
const source = new EventSource('/api/tasks/7/events');

source.addEventListener('progress', (event) => {
  const { percent } = JSON.parse(event.data);
  console.log('进度', percent, '最后事件 ID', event.lastEventId);
});

source.addEventListener('done', () => source.close());

source.onerror = () => {
  // readyState 为 CONNECTING 表示浏览器正在自动重连
  if (source.readyState === EventSource.CLOSED) console.log('连接已关闭');
};

onerror 触发不代表彻底断了。浏览器在自动重连时 readyState 是 CONNECTING，只有变成 CLOSED 才是真的关了。什么情况会关？服务器返回非 200 状态码，或者 Content-Type 不对，EventSource 就会关闭，不再重连。

EventSource 不够用时怎么办

EventSource 有两个限制：只能发 GET，不能自定义请求头，只能带 Cookie（跨源时设 withCredentials）。

可是调大模型接口这类场景，经常要 POST 请求体或者 Authorization 头。这时就改用 fetch，读 response.body 这个流，自己按上面的格式解析事件。代价是重连和续传也要自己写。

还有一个坑。HTTP/1.1 下浏览器对同一个域名的并发连接数有限，通常是 6 个。每个标签页都开一个 SSE，开多了就把连接占满，别的请求只能排队。HTTP/2 一条连接里能跑很多个请求，就没有这个问题。

常见追问

SSE 怎么保证不丢消息？

服务器给每个事件编号，并保留一段历史。浏览器重连时会带上 Last-Event-ID，服务器按它把漏掉的补发。
