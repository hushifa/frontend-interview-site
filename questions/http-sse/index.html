SSE 与 WebSocket 有什么区别？

SSE 是服务器到浏览器的单向文本事件流，基于普通 HTTP，EventSource 自带断线重连和事件 ID 续传；WebSocket 是全双工连接，支持二进制，重连和消息确认都要自己做。

参考答案

简答

  • 方向：SSE 只能服务器推给客户端，客户端发消息仍用普通请求；WebSocket 双向。
  • 协议：SSE 是 Content-Type: text/event-stream 的普通 HTTP 响应，能直接走现有的代理、鉴权和 HTTP/2；WebSocket 需要协议升级。
  • 重连：EventSource 断线后自动重连，并通过 Last-Event-ID 请求头告诉服务器最后收到的事件；WebSocket 没有内置重连。
  • 数据：SSE 只传 UTF-8 文本；WebSocket 支持文本和二进制。
  • 选择：通知、进度、AI 流式输出用 SSE 或 fetch 流；聊天、协同编辑、游戏这类高频双向场景用 WebSocket。

事件格式

text
id: 42
event: progress
data: {"percent": 60}

data: 第一行
data: 第二行

retry: 5000

每个事件以空行结束；多行 data 会用换行拼接；retry 设置重连间隔（毫秒）；以 : 开头的行是注释，常用来发心跳，防止代理断开空闲连接。

客户端

JavaScript
const source = new EventSource('/api/tasks/7/events');

source.addEventListener('progress', (event) => {
  const { percent } = JSON.parse(event.data);
  console.log('进度', percent, '最后事件 ID', event.lastEventId);
});

source.addEventListener('done', () => source.close());

source.onerror = () => {
  // readyState 为 CONNECTING 表示浏览器正在自动重连
  if (source.readyState === EventSource.CLOSED) console.log('连接已关闭');
};

服务器返回非 200 状态码或错误的 Content-Type 时，EventSource 会关闭且不再重连。

EventSource 的限制和 fetch 流

EventSource 只能发 GET，不能自定义请求头（只能带 Cookie，可设 withCredentials）。需要 POST 请求体或 Authorization 头时（例如调用大模型接口），改用 fetch 读取 response.body，自己解析事件格式，重连和续传也要自己实现。

HTTP/1.1 下浏览器对同一域名的并发连接数有限（通常 6 个），多个标签页各开一个 SSE 会占满连接；HTTP/2 多路复用后没有这个问题。

常见追问

  • SSE 怎么保证不丢消息？服务器为事件编号并保留一段历史，重连时按 Last-Event-ID 补发。
  • WebSocket 的重连怎么做？见《WebSocket 适合什么场景，连接断开后怎样恢复？》。
