页面进入后台后，计时器和动画还会按原速度运行吗？

不会。切到后台后 requestAnimationFrame 会暂停，定时器会被放慢，页面还可能被冻结甚至丢弃。所以时间要按真实时间戳算，状态要在页面隐藏时保存。

参考答案

简答

不会。用户切到别的标签页以后，浏览器为了省电，会让后台页面少干活。requestAnimationFrame 的回调直接停掉，CSS 动画也不再推进到屏幕上。

setTimeout、setInterval 会被节流。Chrome 里通常最多每秒执行一次，隐藏久了还可能合并到每分钟一次。

浏览器还可以把后台页面冻结，也就是暂停它的任务执行。内存紧张时甚至会直接丢弃页面，用户切回来时重新加载。

所以依赖时间的逻辑，比如倒计时，要按真实时间戳计算，页面恢复可见时重新同步，不能假设回调按固定间隔执行。要保存的状态，在页面变成隐藏时就保存。

先看一个会出错的倒计时

很多人这样写倒计时：setInterval 每秒执行一次，每次把剩余秒数减 1。页面在前台时没问题。可是切到后台，定时器被节流成每分钟一次，回来一看，剩余时间比实际多了一大截。

原因是这种写法假设“回调执行了几次，就过去了几秒”，而后台节流打破了这个假设。

改法是不数回调次数，每次都用当前时间减开始时间：

JavaScript
let startedAt = performance.now();

function elapsedSeconds() {
  return Math.floor((performance.now() - startedAt) / 1000);
}

document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') {
    saveDraft();
  } else {
    render(elapsedSeconds());
  }
});

不管回调被延迟多久，performance.now() 的差值都是真实经过的时间。用 Date.now() 算差值也可以。页面重新可见时立刻 render 一次，显示就对上了。

为什么在 hidden 时保存状态

例子里变成 hidden 时调用了 saveDraft()。在移动端，这是最后一个可靠的时机，因为用户可能在后台直接把进程杀掉，之后什么事件都不会再来。

页面重新可见时，也顺手刷新一下可能已经过期的数据。

页面会经历哪些状态

Chrome 文档把页面分成这几个状态：

状态含义
active可见且有输入焦点
passive可见但没有焦点
hidden不可见，仍可执行任务
frozen冻结，任务暂停执行
terminated已卸载
discarded被浏览器丢弃以释放资源

对应的事件有：visibilitychange 表示进出 hidden，freeze 和 resume 表示冻结与恢复，pagehide 和 pageshow 表示离开与返回。其中 freeze、resume 和 document.wasDiscarded 目前只有 Chromium 支持。

常见追问

为什么不在 unload 里保存数据？

因为 unload 在移动端经常不触发，而且注册了它还会让页面进不了 bfcache。应该改用 visibilitychange 和 pagehide。

页面在后台还要实时收消息怎么办？

WebSocket 连接在后台一般还保持着，但处理消息的回调同样可能被延迟。如果需要在后台提醒用户，用 Push API。只需要监听可见性变化的写法，见《Page Visibility API 适合处理哪些页面生命周期场景？》。
