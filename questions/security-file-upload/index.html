前端文件上传有哪些安全边界？

前端的类型和大小检查只是为了体验，攻击者可以绕过页面直接调接口。真正的防线在服务端：限大小、按内容识别、随机命名，并把用户文件放在隔离的域名下，防止被当成页面执行。

参考答案

简答

前端的 accept 属性和 file.type，其实来自文件扩展名或者系统的猜测，把 evil.html 改名成 evil.png，它就说是图片。所以前端检查只能用来提示用户，不能当安全判断，攻击者完全可以绕过页面直接调接口。

真正的防线在服务端。限制大小，扩展名用白名单，按文件内容开头的特征字节（叫魔数）识别类型，图片最好重新编码一遍，去掉隐藏的数据和元信息。存储时用服务端生成的随机名字，原始文件名只当元数据，防止路径穿越和覆盖。

提供下载时，用户文件放在独立的域名下，带上 Content-Disposition: attachment 和 X-Content-Type-Options: nosniff，避免它在主站的源下被当成 HTML 执行。

要注意 SVG，它可以包含脚本。不要把它直接插进页面 DOM，预览时用 <img> 加载，或者在服务端转成位图。

前端能做什么

JavaScript
const MAX_SIZE = 10 * 1024 * 1024;
const ALLOWED = new Set(['image/png', 'image/jpeg', 'image/webp']);

input.addEventListener('change', () => {
  const file = input.files[0];
  if (!file) return;
  if (file.size > MAX_SIZE) return showError('文件不能超过 10 MB');
  if (!ALLOWED.has(file.type)) return showError('只支持 PNG、JPEG、WebP');

  preview.src = URL.createObjectURL(file);
  preview.onload = () => URL.revokeObjectURL(preview.src);
});

这些检查的作用是让用户早点知道文件不合格，不用等上传完才报错。可是它们都发生在用户自己的浏览器里，用户能改代码，也能直接发请求。所以服务端必须再检查一遍，而且要更严格。

服务端要查哪些

风险措施
超大文件、压缩炸弹限制请求体大小、解压后的总大小和文件数
伪装类型按内容识别类型，与扩展名都在白名单内才接受
路径穿越（../../etc/passwd）不用原始文件名作路径
存储型 XSS隔离域名、nosniff、强制下载或安全的 Content-Type
恶意文件病毒扫描，扫描通过前不对外可见
越权访问下载接口校验权限，或使用短期签名链接
元数据泄露去除图片的 EXIF（可能含地理位置）

路径穿越是什么？如果服务端直接用用户给的文件名拼路径，文件名写成 ../../etc/passwd，就可能写到上传目录外面去。用随机名字存储，这个问题就不存在了。

为什么要放在单独的域名

这是最容易被问到的一点。浏览器按源隔离数据。如果用户上传的一个 HTML 文件在主站的源下被打开，它里面的脚本就和主站的代码是“自己人”，能读写主站的 Cookie 和存储，这就成了存储型 XSS。放到 usercontent.example 这样的独立域名下，就算它执行了，也碰不到主站的数据。

nosniff 是另一层保险。它告诉浏览器严格按 Content-Type 处理，不要自己去猜内容是什么类型，避免一个声明为图片的文件被浏览器“猜”成 HTML 执行。

预览时的风险

不要把上传的 HTML 或 SVG 读成字符串写进 innerHTML。SVG 用 <img> 加载时不会执行脚本；可是在新标签页里直接打开 SVG 文件，它会在所在的源下执行，这也是文件要放在隔离域名的原因。PDF、Office 文档的预览同样放在隔离源或沙箱 iframe 里。

常见追问

为什么一定要单独的域名，同域名下换个路径不行吗？

不行。浏览器隔离的单位是源，也就是协议、主机和端口，路径不算。同一个域名下换路径，上传的 HTML 照样能读写主站的 Cookie 和存储。
