为什么 100% 代码覆盖率也可能漏掉严重问题？

覆盖率记录代码是否被执行，包括语句、分支、函数等维度。执行过一行，不代表测试检查了它的正确结果；同一个分支也可能有许多未覆盖的数据边界和执行顺序。

参考答案

覆盖率记录代码是否被执行，包括语句、分支、函数等维度。执行过一行，不代表测试检查了它的正确结果；同一个分支也可能有许多未覆盖的数据边界和执行顺序。

在“为什么 100% 代码覆盖率也可能漏掉严重问题？”这个问题中，先明确用户风险和测试边界，再选择测试层级；成功、失败、取消和恢复都要有可诊断的断言，而不是只追求覆盖率。这里的 测试覆盖率、断言、边界条件 不是孤立的 API 名称，而是会共同影响输入、过程和最终结果。

先写清楚测试对象和失败风险，再决定使用单元、组件、接口、端到端、视觉或无障碍测试。测试应覆盖用户真正关心的成功路径、错误路径、取消和恢复，而不是只追求行覆盖率。

Vitest 支持 V8 和 Istanbul 等覆盖率方案，采集方式、运行环境和版本需要配套。首先应检查统计范围是否包含应测文件，避免只统计已经被测试导入的部分，得到误导性的高数字。

以下属于测试设计建议：从业务风险选择断言，覆盖异常、边界值和状态转换，优先补真实缺陷对应的回归测试。阈值可用于阻止明显退步，但不能代替用例审查；对内部实现写大量重复断言，也可能让数字上升而维护成本更高。

覆盖率报告还可能受到动态导入、生成文件、分支短路和测试环境差异影响。团队应固定统计范围和阈值解释，在代码评审中查看未覆盖区域的风险，而不是追求一个跨项目比较的百分比。

Mock 要限制在必要边界，并保留足够真实的契约。失败信息、测试数据和环境版本要可追溯，这样测试失败时能区分产品缺陷、测试缺陷和环境问题。

实际测试应围绕用户会损失什么来排序。关键流程先覆盖成功、失败、取消和恢复，再补充边界组合；一个无法说明失败原因的高覆盖率测试，维护价值仍然有限。
