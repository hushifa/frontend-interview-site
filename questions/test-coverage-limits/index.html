为什么 100% 代码覆盖率也可能漏掉严重问题？

覆盖率只说明哪些代码在测试里执行过，不说明结果被断言过。没写的分支、边界值、并发和外部系统问题都不在统计范围内，所以它适合找完全没测的代码，不适合当质量目标。

参考答案

简答

覆盖率统计的是测试运行时哪些代码被执行过。执行到不等于验证到：测试调用了函数却不检查返回值，覆盖率照样是 100%。

它还有一个盲区：只能统计已经写出来的代码。比如函数漏了空数组的判断，这段判断根本不存在，报告里也就不会出现“未覆盖”。另外行覆盖率高时分支覆盖率可能很低，a && b 只测了一种情况，这一行也算覆盖了。

所以覆盖率最有用的地方是找出完全没测过的高风险代码。报告只包含测试加载过的文件，没被任何测试导入的文件可能根本不在报告里，要配置 coverage.include 才能看到。

要检查断言是否真的有效，可以用变异测试。并发、浏览器差异、接口契约和性能问题，覆盖率完全看不到。

调用了函数却没检查结果

下面的测试把两个分支都跑到了：

TypeScript
export function discount(price: number, vip: boolean) {
  return vip ? price * 0.8 : price;
}
TypeScript
test('计算折扣', () => {
  discount(100, true);
  discount(100, false);
});

覆盖率报告会显示 100%。可是测试里一个 expect 都没有，把 0.8 改成 0.5，测试还是通过。覆盖率只知道代码“跑过”，不知道结果“对不对”。改法很直接，补上 expect(discount(100, true)).toBe(80) 这样的断言。

没写的代码不会显示为未覆盖

TypeScript
export function average(values: number[]) {
  return values.reduce((sum, v) => sum + v, 0) / values.length;
}

test('求平均值', () => {
  expect(average([1, 2, 3])).toBe(2);
});

这个测试有断言，覆盖率也是 100%。但传一个空数组进去，reduce 的结果是 0，再除以长度 0，得到的是 NaN：

JavaScript
const average = (values) => values.reduce((sum, v) => sum + v, 0) / values.length;
console.log(average([])); // NaN

为什么覆盖率发现不了？因为处理空数组的代码压根没写，没有代码可统计。这类问题只能靠写测试的人主动想边界值，或者用属性测试让工具去生成各种输入。

怎样让没被导入的文件也出现在报告里

TypeScript
// vitest.config.ts
export default defineConfig({
  test: {
    coverage: {
      provider: 'v8',
      include: ['src/**/*.{ts,tsx}'],
      thresholds: { branches: 80 },
    },
  },
});

配了 include 以后，没有被任何测试导入的文件也会出现在报告里，显示为 0%。thresholds 设了门槛，覆盖率明显下降时测试会失败。门槛能防止退步，可是如果单纯追数字，就会催生前面那种“只调用、不断言”的测试。

覆盖率完全看不到哪些问题

有些问题跟哪行代码被执行没有关系。比如两个请求返回的顺序颠倒了，造成竞态；比如某个浏览器上布局错乱；比如前端假设的接口字段和真实后端不一致；再比如性能变差、内存泄漏。这些都要靠端到端测试、契约测试或监控去发现。

常见追问

覆盖率目标定多少合适？

没有统一的数字。核心业务逻辑和工具函数追求高的分支覆盖，界面胶水代码靠组件测试和端到端测试，这比全项目统一要求 100% 更有效。断言质量可以用变异测试检查，见《变异测试如何发现“覆盖率很高但测试没测到重点”？》。
