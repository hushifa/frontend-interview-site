为什么 100% 代码覆盖率也可能漏掉严重问题？

覆盖率只说明哪些代码被执行过，不能证明结果正确、边界完整或异步时序安全。测试质量取决于独立断言、风险场景和统计范围。

参考答案

覆盖率回答的问题很有限

覆盖率报告回答的是“测试运行时经过了哪些代码”。它不能回答“这个结果是否符合需求”“错误输入是否被拒绝”“两个异步请求乱序时是否安全”。

例如实现本应计算总价，却写成了加法：

JavaScript
function lineTotal(unitPrice, quantity) {
  return unitPrice + quantity;
}

test('计算总价', () => {
  expect(lineTotal(10, 3)).toEqual(expect.any(Number));
});

函数体被执行了，覆盖率也会上升，但测试没有验证 30 这个业务结果。更糟的是，如果测试预期值直接照抄实现里的 unitPrice + quantity，代码和测试会一起犯错。正确断言应来自需求、示例或独立的业务规则。

不同覆盖维度有不同盲区

语句覆盖看某行是否执行，函数覆盖看函数是否调用，分支覆盖看条件的不同方向是否走过。分支覆盖比只调用函数更有信息，但仍不能覆盖所有输入组合、状态顺序和数据关系。

价格校验即使测试了正数和负数，也可能漏掉 0、NaN、Infinity、字符串、超大数和小数精度。请求成功和失败都走过，也可能没有测试旧请求晚返回时不能覆盖新结果。

因此覆盖率是“未触达区域”的提示，不是“所有行为已证明”的结论。重要的是测试删掉关键行为后是否会失败。

先确认报告的分母是谁

覆盖率工具可能只统计被测试导入的文件，也可能按配置把整个 src 纳入分母。若一个完全没有测试的模块没有进入统计范围，报告仍可能显示很高：

TypeScript
export default defineConfig({
  test: {
    coverage: {
      include: ['src/**/*.{ts,tsx}'],
      exclude: ['src/**/*.d.ts', 'src/test/**'],
    },
  },
});

具体字段和 provider 要按项目使用的 Vitest 版本核对。生成文件、第三方代码、测试辅助代码是否排除，都应有理由。通过扩大 exclude 或到处添加忽略注释提高百分比，只是改变分母。

断言应从风险反推

付款、权限和数据修改应优先验证正确结果、拒绝路径、重复提交、幂等和恢复；筛选界面要验证空结果、重置、过期响应和键盘操作；底层函数要覆盖边界和必须成立的性质。

测试可以写成外部行为：

JavaScript
it('旧搜索结果不能覆盖较新的查询', async () => {
  const first = deferred();
  const second = deferred();
  const search = createSearch({ request: (q) => q === 'a' ? first.promise : second.promise });

  search.run('a');
  search.run('ab');
  second.resolve(['about']);
  await second.promise;
  first.resolve(['apple']);
  await first.promise;

  expect(search.currentResults()).toEqual(['about']);
});

这个用例验证的是用户能观察到的时序契约，而不是某个内部变量恰好被赋值。重构内部实现但保持行为不变时，好的测试仍应通过。

变异测试和人工审查补足另一层证据

把乘法改成加法、把 > 改成 >=、删除错误分支，看测试是否失败，可以发现断言过弱的问题。变异测试仍有等价变异和运行成本，不能替代测试设计。

审查高覆盖率用例时，可以问：删掉关键行为它会失败吗？错误结果会被发现吗？异常和取消是否有可观察结果？测试是否依赖实现细节？这些问题比追求一个整数百分比更接近测试价值。

覆盖率适合做回归信号和风险提示，不能替代接口契约、浏览器交互、安全验证、性能测试和人工验收。真正可靠的结论来自风险驱动的场景、独立的预期结果和可解释的失败信息。
