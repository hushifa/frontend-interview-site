属性测试和示例测试应该怎样搭配？

用不变量和生成数据覆盖输入空间，同时保留易读的示例测试表达具体业务场景。

参考答案

示例测试给出具体输入和预期输出，例如“空数组分组后仍是空数组”。属性测试则描述一类输入都应满足的规律，让工具生成多组数据尝试推翻它。

它不是随便生成随机值看看会不会报错。真正重要的是生成器定义了什么输入范围，以及断言是否表达了可靠的业务性质。

用数组分组说明两种测试的分工

假设函数按正整数 size 把数组切成多组，最后一组可以更短：

JavaScript
function chunk(items, size) {
  if (!Number.isInteger(size) || size <= 0) {
    throw new RangeError('分组大小必须是正整数');
  }
  const result = [];
  for (let index = 0; index < items.length; index += size) {
    result.push(items.slice(index, index + size));
  }
  return result;
}

示例测试可以明确验证 [1, 2, 3] 按 2 分组得到 [[1, 2], [3]]，以及 size 为 0 时抛错。这些例子可读性高，直接说明接口契约。

属性测试可以检查更广的数组和分组大小：

JavaScript
import fc from 'fast-check';
import assert from 'node:assert/strict';

fc.assert(
  fc.property(
    fc.array(fc.integer(), { maxLength: 100 }),
    fc.integer({ min: 1, max: 20 }),
    (items, size) => {
      const before = [...items];
      const groups = chunk(items, size);
      assert.deepEqual(groups.flat(), before);
      assert.deepEqual(items, before);
      assert.equal(groups.length, Math.ceil(items.length / size));
      for (const group of groups) {
        assert.ok(group.length > 0 && group.length <= size);
      }
      for (const group of groups.slice(0, -1)) {
        assert.equal(group.length, size);
      }
    },
  ),
  { numRuns: 200 },
);

将两个代码块放在同一 Node ESM 文件并安装 fast-check 后运行。断言检查元素顺序和内容没有丢失、输入没有被修改、组数正确、组大小符合约定。

只检查 groups.flat() 等于原数组是不够的：直接返回 [items] 也能满足它，却没有按 size 分组。多个独立性质共同约束结果，才能减少“错误实现也满足测试”的空间。

生成器决定你实际探索了哪里

示例只生成普通整数数组与 1 到 20 的 size，不能据此宣称支持稀疏数组、任意嵌套对象或巨大数据量。无效 size 也不在生成域中，需要另外的示例或属性测试验证拒绝行为。

对字符串业务，应按真实契约覆盖空字符串、Unicode、组合字符和长度边界；对日期业务，要明确时区和合法日期；对状态机，可以生成操作序列，而不仅是单次参数。

过多 filter 会丢弃大量样本，降低效率并削弱反例缩减。更好的生成器往往直接构造合法输入，再用单独用例处理不合法输入。

失败后，缩减让反例更容易理解

当某组数据违反性质，fast-check 会尝试把输入缩减成更简单、仍能触发失败的反例。复杂的 80 项数组可能被缩到几个元素，让越界、重复或空值问题更明显。

缩减结果不保证是数学意义上的全局最小反例，它受生成器和缩减策略影响。应保留失败报告中的 seed、path 和工具版本，以便在相同配置下复现；修改生成器后，相同 seed 不一定仍对应同一输入序列。

修复后可以把这个反例补成清晰的回归示例，属性测试则继续探索其他组合。两者不是二选一。

有限随机检查不是形式化证明

200 次通过只说明这次运行没有找到反例，不证明无限输入空间全部正确。错误的性质、遗漏的生成范围以及替身与真实环境差异，都可能留下漏洞。

异步操作应使用对应的异步属性机制并等待断言完成；共享状态要在每次生成用例之间正确重置，否则失败可能来自前一次污染。网络和 UI 也不能仅靠一个纯函数属性替代真实集成测试。

最适合属性测试的目标通常有清晰规律：编码往返、排序保持元素、分组不丢数据、缓存不超过容量等。先把规律写对，再让生成和缩减帮助寻找人手未想到的组合。
