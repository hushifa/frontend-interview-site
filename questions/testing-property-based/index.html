属性测试和示例测试应该怎样搭配？

示例测试用具体的输入和输出说明接口；属性测试描述对一类输入都成立的规律，由 fast-check 等工具生成大量数据去推翻它，失败时自动缩减成简单反例。前者适合写成可读的契约，后者适合发现没想到的边界。

参考答案

简答

示例测试就是我们平时写的测试，给一个具体输入，检查一个具体输出，比如 chunk([1, 2, 3], 2) 应该得到 [[1, 2], [3]]。它直观好读，但只检查了写测试的人想到的情况。

属性测试换了个思路：不写具体的值，而是写一条对所有输入都应该成立的规律，比如“对任意数组和任意正整数 size，分组结果展平后等于原数组，每组长度不超过 size”。然后让工具生成几百组输入去试，想办法推翻它。

一旦失败，工具会把输入缩减成尽量小的反例，并给出一个 seed，用同一个 seed 就能复现。

要注意两点。一条规律往往约束不住，比如直接返回 [items] 也满足“展平后相等”，要多条规律一起用。另外工具只会生成生成器范围内的输入，范围之外的情况，比如非法参数，还得单独写示例测试。

先看一个例子

下面是一个把数组按固定大小分组的函数：

JavaScript
function chunk(items, size) {
  if (!Number.isInteger(size) || size <= 0) {
    throw new RangeError('分组大小必须是正整数');
  }
  const result = [];
  for (let index = 0; index < items.length; index += size) {
    result.push(items.slice(index, index + size));
  }
  return result;
}

用 fast-check 给它写属性测试。fc.array(fc.integer()) 生成任意整数数组，fc.integer({ min: 1, max: 20 }) 生成合法的分组大小：

JavaScript
import fc from 'fast-check';
import assert from 'node:assert/strict';

fc.assert(
  fc.property(
    fc.array(fc.integer(), { maxLength: 100 }),
    fc.integer({ min: 1, max: 20 }),
    (items, size) => {
      const groups = chunk(items, size);
      assert.deepEqual(groups.flat(), items);
      assert.equal(groups.length, Math.ceil(items.length / size));
      for (const group of groups.slice(0, -1)) {
        assert.equal(group.length, size);
      }
      for (const group of groups) {
        assert.ok(group.length > 0 && group.length <= size);
      }
    },
  ),
);

为什么要写四条断言？因为每一条单独拿出来，都有错误的实现能满足它。第一条检查内容和顺序没变，可是“整个数组当成一组”也能过。第二条检查组数，第三条检查前面每组都是满的，第四条检查每组非空且不超过上限。四条合在一起，错误的实现就很难全部蒙混过去。

常见的规律有哪些

刚开始写属性测试时，最难的是想出规律。下面几种最常用。

往返：decode(encode(x)) 应该等于 x，适合序列化、URL 编码这类成对的函数。

不变量：比如排序以后长度不变、元素还是那些元素、相邻元素有序。

和简单实现对比：优化过的算法，结果应该等于一个朴素实现的结果。

幂等：normalize(normalize(x)) 应该等于 normalize(x)，也就是做两遍和做一遍一样。

生成器怎样写

生成器决定了工具会尝试哪些输入。能直接生成合法输入，就不要先乱生成再用 filter 丢掉大部分，那样效率低，缩减反例的效果也差。

跟字符串有关的业务，要把空字符串、emoji、组合字符都考虑进去，fc.string({ unit: 'grapheme' }) 可以生成由多个码点组成的字符。状态机和交互逻辑可以用 fc.commands 生成一串操作，检查不管按什么顺序操作，状态最后都还是合法的。

属性测试的局限

随机试有限次不等于证明。生成器没覆盖到的输入、只在极小概率下出现的组合，仍然可能藏着问题。所以属性测试找到的反例，应该固定写成一个示例测试，防止以后又出现。
