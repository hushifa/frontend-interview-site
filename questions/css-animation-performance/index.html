transition、animation 和 requestAnimationFrame 怎么选？

transition 描述状态变化的过渡，animation 描述关键帧过程，requestAnimationFrame 适合由 JavaScript 根据时间计算每一帧。选择依据是行为与控制需求，性能则要结合具体属性、工作量和浏览器渲染路径判断。

参考答案

一个按钮悬停后略微上移，和一个根据拖拽速度继续滑行的物体，虽然都在移动，但需要控制的事情不同。前者只要描述前后状态，后者则需要持续计算位置、速度和停止条件。

因此不必先问“CSS 动画一定比 JavaScript 快吗”，而应先决定哪种表达方式最贴合这个行为，再检查它实际触发了哪些浏览器工作。

transition：从旧状态过渡到新状态

CSS
.action {
  transform: translateY(0);
  transition: transform 180ms ease;
}

.action:hover,
.action:focus-visible {
  transform: translateY(-2px);
}

@media (prefers-reduced-motion: reduce) {
  .action,
  .action:hover,
  .action:focus-visible {
    transition: none;
    transform: none;
  }
}

状态改变时，浏览器在可插值的属性值之间生成过渡；状态恢复后，又向原状态过渡。它很适合交互反馈、面板尺寸调整等“有两个明确状态”的情况，不需要维护逐帧回调。

transition 需要发生相应的样式变化，并且属性要有对应的过渡行为。不能给元素写一条 transition，就期待它没有任何状态变化也会自己运动。transition: all 则可能把原本不想动画的布局属性也包含进去，明确列出属性通常更容易维护。

animation：自己定义阶段和重复方式

CSS
@keyframes gentle-pulse {
  0%, 100% { opacity: 1; }
  50% { opacity: 0.5; }
}

.pending-indicator {
  animation: gentle-pulse 1.2s ease-in-out infinite;
}

@media (prefers-reduced-motion: reduce) {
  .pending-indicator {
    animation: none;
  }
}

animation 适合有多个关键帧、需要循环或独立启动的视觉过程。即使禁用动画，页面也应保留“正在处理”这样的实际文字或状态，不能只让一个动起来的小点承担全部反馈。

animation-fill-mode 控制动画活动区间之外怎样应用动画样式，不会永久改写元素的基础 CSS。如果结束后需要某个稳定状态，应明确维护相应 class 或样式，而不是误以为动画已经替业务状态赋值。

rAF：每帧根据时间计算，而不是固定加一点

需要物理计算、Canvas 绘制或与交互连续同步时，可以使用 requestAnimationFrame。它请求浏览器在适当的渲染更新阶段调用一次回调；要继续下一帧，需要在回调里再次申请。

下面是从横向位移 0 移到 distance 的有限动画。它专门控制 transform，会覆盖已有 transform，不是一个可以自动组合所有变换的通用动画库。

JavaScript
function animateTranslate(element, distance, duration = 300) {
  if (!Number.isFinite(distance) ||
      !Number.isFinite(duration) || duration < 0) {
    throw new RangeError('位移必须是有限数值，时长必须是非负有限数值');
  }

  const reduceMotion = matchMedia('(prefers-reduced-motion: reduce)').matches;
  if (duration === 0 || reduceMotion) {
    element.style.transform = `translateX(${distance}px)`;
    return () => {};
  }

  let frameId = null;
  let startedAt;
  let cancelled = false;

  function frame(now) {
    if (cancelled) return;
    startedAt ??= now;
    const progress = Math.min((now - startedAt) / duration, 1);
    element.style.transform = `translateX(${distance * progress}px)`;

    if (progress < 1) frameId = requestAnimationFrame(frame);
    else frameId = null;
  }

  frameId = requestAnimationFrame(frame);
  return function cancel() {
    cancelled = true;
    if (frameId !== null) cancelAnimationFrame(frameId);
    frameId = null;
  };
}

调用时传入实际元素，保存返回的取消函数，在重新启动同一元素的动画或组件卸载时调用它。取消会停在当前位置，不负责恢复起点。多个调用如果同时写一个元素的 transform，会互相覆盖，因此调用方应避免无意的并行动画。

progress 使用时间戳之差除以总时长。60Hz 屏幕回调较少，120Hz 屏幕回调较多，但只要经过相同时间，就能计算相近的位置。如果改成“每帧加 2px”，动画速度就会随着刷新率变化。

回调通常与显示刷新节奏协调，但不是严格固定每秒 60 次。主线程忙时可能丢帧，后台页面通常暂停或显著减少回调。此例恢复后会根据已经流逝的时间赶到对应位置，甚至直接结束；如果业务需要“后台暂停计时”，就要另外记录暂停时段，而不是默认 rAF 帮你冻结进度。

减少动画偏好在本例启动时读取，选择直接落到最终状态。若应用需要在动画过程中响应用户修改偏好，还应监听媒体查询变化并清理相应监听器。

性能关键是每帧做了什么

修改 width、height 或影响排版的位置，可能引发布局；修改背景、阴影等可能需要重新绘制；transform、opacity 在合适条件下可以由合成阶段处理，通常更有利于流畅动画。

但这些是渲染路径上的可能性，不是“写 transform 就永远零成本”。大面积透明层、复杂效果、纹理上传和过多合成层仍然可能占用显存与带宽。will-change 也不是永久开启的加速按钮，只应在测量表明确有需要时有限使用。

在 rAF 中交替读布局、改样式、再读布局，仍可能造成同步布局和抖动。把一帧的必要读取与写入合理组织，比简单地把原有慢代码包进 rAF 更重要。

CSS 动画不一定全部避开主线程，JavaScript 动画也不一定必然很慢。对于需要命令式暂停、反向或等待完成、但不必每帧自行计算的动画，还可以评估 Web Animations API；不必为了有播放控制就把所有逻辑都改成手写循环。

最终用 Performance 面板检查长任务、布局、绘制与合成，在目标设备上检查交互延迟。保持可取消、尊重减少动画偏好、不给用户操作增加等待，同样属于动画实现质量的一部分。
