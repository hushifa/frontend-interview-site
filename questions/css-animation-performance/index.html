动画为什么会卡？transform、will-change 和 requestAnimationFrame 怎样让动画流畅？

动画卡不卡，主要看每一帧改的属性要让浏览器重做哪些步骤：改宽高和位置要重新布局，改颜色要重绘，transform 和 opacity 通常只需要合成，还可能交给合成器线程处理。必须用 JavaScript 逐帧计算时用 requestAnimationFrame，进度按时间戳算；will-change 只在测量后短期使用；开了减少动态效果的用户要给不动的版本。

参考答案

简答

一个侧边栏展开动画，用 width 做就一顿一顿的，换成 transform 就顺了。原因在于浏览器画一帧要经过布局、绘制、合成几步，动画每一帧改的属性决定了要重做哪几步。

改 width、top、margin 每一帧都可能重新布局，后面的绘制和合成也得跟着做；改背景色要重绘；transform 和 opacity 在合适的条件下只需要合成，而且可以交给合成器处理，主线程忙的时候也可能保持流畅。所以位移、缩放、淡入淡出优先用这两个属性。

位置必须靠 JavaScript 算时，比如跟着拖拽走、做物理效果，用 requestAnimationFrame。它在每次渲染前调用一次回调，进度要按时间戳算，不能每帧固定加一个数，否则高刷新率的屏幕上会变快。回调里先集中读布局、再集中写样式，避免强制同步布局。

还要注意，will-change 会占用显存，只在测量后确实需要时短期使用；开了“减少动态效果”的用户，要通过 prefers-reduced-motion 给一个不动的版本。

为什么改 transform 比改 width 流畅

浏览器画一帧大致分三步：先算每个元素的位置和大小，这叫布局；再把颜色、文字画出来，这叫绘制；最后把画好的几层叠到一起，这叫合成。

改 width、top、margin 这类属性，每一帧都可能要重新布局，后面的绘制和合成也得跟着做。transform 和 opacity 在合适的条件下只需要合成，而且由合成器处理，主线程忙的时候动画也可能保持流畅。

到底慢在哪里，用浏览器 Performance 面板看每一帧花在布局、绘制、合成上的时间，再决定要不要改。

CSS 动画写成什么样更省

transition 和 animation 的用法区别见《transition 和 animation 有什么区别？》。从性能角度看，要点是动画的属性尽量只用 transform 和 opacity，而且明确写出来。下面是按钮悬停或键盘聚焦时上移 2px：

CSS
.action {
  transition: transform 180ms ease;
}

.action:hover,
.action:focus-visible {
  transform: translateY(-2px);
}

@media (prefers-reduced-motion: reduce) {
  .action {
    transition: none;
  }
}

为什么不写 transition: all？写成 all，以后有人改了宽度、外边距，这些布局属性也会被带进动画里，既不是本意，又费性能。

媒体查询那一段是给开了“减少动态效果”的用户准备的，直接去掉过渡，状态照样切换，只是不动。

必须用 JavaScript 算时怎样写 requestAnimationFrame

rAF 只会在下一次渲染前调用一次回调。想要继续动，就在回调里再申请下一帧。下面这个函数把元素横向移动 distance 像素，并返回一个取消函数：

JavaScript
function animateTranslate(element, distance, duration = 300) {
  if (!Number.isFinite(distance) ||
      !Number.isFinite(duration) || duration < 0) {
    throw new RangeError('位移必须是有限数值，时长必须是非负有限数值');
  }

  const reduceMotion = matchMedia('(prefers-reduced-motion: reduce)').matches;
  if (duration === 0 || reduceMotion) {
    element.style.transform = `translateX(${distance}px)`;
    return () => {};
  }

  let frameId = null;
  let startedAt;
  let cancelled = false;

  function frame(now) {
    if (cancelled) return;
    startedAt ??= now;
    const progress = Math.min((now - startedAt) / duration, 1);
    element.style.transform = `translateX(${distance * progress}px)`;

    if (progress < 1) frameId = requestAnimationFrame(frame);
    else frameId = null;
  }

  frameId = requestAnimationFrame(frame);
  return function cancel() {
    cancelled = true;
    if (frameId !== null) cancelAnimationFrame(frameId);
    frameId = null;
  };
}

重点看 progress 是怎么来的：已经过去的时间除以总时长。为什么不直接写“每帧加 2px”？因为不同屏幕的刷新率不一样，60Hz 的屏幕一秒 60 帧，120Hz 的一秒 120 帧。每帧加固定值，120Hz 上就会快一倍。按时间算，两种屏幕在同一时刻走到的位置是一样的。

开了减少动态效果或者时长为 0 时，函数直接把元素放到终点，不做动画。

还有一个细节。标签页切到后台时，rAF 通常会暂停。切回来以后，这段代码按已经过去的时间计算，元素会直接跳到对应的位置。如果业务想要“后台时暂停计时”，就要自己记下暂停了多久。

will-change 和读写顺序

will-change 能让浏览器提前创建合成层，但它会占显存，只在测量后确实需要时短期使用。

rAF 回调里还要注意读写顺序。读一下 offsetWidth、写一下样式、再读、再写，浏览器每次读都得先把布局算出来，这叫强制同步布局。应该先集中读，再集中写。

常见追问

CSS 动画一定比 JS 动画快吗？

不一定。两者改的是同样的属性时，成本差不多。差别在于，CSS 动画和 Web Animations API 做 transform、opacity 动画时通常可以交给合成器处理，主线程忙的时候受的影响小得多；而 rAF 的回调本身就跑在主线程上。
