原生表单校验能解决什么，不能解决什么？

HTML 约束和 Constraint Validation API 可以检查必填、格式、范围等规则，并参与表单提交流程。跨字段规则需要补充逻辑，服务端校验和异步业务验证仍不能省略。

参考答案

原生表单校验的价值，是让“字段有什么约束”直接写在控件上，并让浏览器在适当时机检查这些约束。它能减少重复编写的基础校验代码，但不会自动理解“用户名是否已被占用”“这个优惠券属于谁”等业务事实。

例如邮箱输入框写成 type="email" required，就已经表达了“不能为空，且需要符合浏览器接受的邮箱语法”。这比普通文本框配一段只在按钮点击时运行的正则，更容易覆盖键盘提交等入口。

先用对属性，而不是给所有字段写正则

约束常见用途容易误解的地方
required必须提供值或完成指定选择不同控件的规则不同，例如必选复选框与单选组
type="email"、url检查对应的基本语法不保证邮箱存在、URL 可访问
min、max数值、日期等的范围不是字符串长度限制
step数值或日期时间的步进规则number 默认步进通常是 1，小数可能触发不匹配
minlength、maxlength适用文本控件的长度不能用来限制 number 的数字位数
pattern适用文本控件的整个值满足格式空值通常还要靠 required 判定必填

pattern="[0-9]{6}" 表达六位 ASCII 数字，不是“包含某一段六位数字就行”。不要把 JavaScript 正则字面量的斜杠一起写进去，也不要想当然地把所有 JavaScript 正则用法照搬到 HTML pattern；其编译与 Unicode 规则应按当前 HTML 要求核对。

validity、checkValidity 和 reportValidity 有何区别

控件的 validity 提供结果信息，例如 valueMissing、typeMismatch、rangeUnderflow、stepMismatch、patternMismatch 和 customError。validity.valid 表示这些检查是否整体通过，不包含你还没写进去的业务规则。

checkValidity() 执行检查并返回布尔值，失败时可触发 invalid 事件，但不会默认替你展示浏览器交互式错误提示。reportValidity() 除了检查，还会按浏览器行为报告未被取消的校验错误，适合明确要求用户现在修复字段的时机。

两者既可以在单个控件上调用，也可以在 form 上检查相关可校验控件。并非所有控件都参与约束校验，willValidate 可以帮助判断，例如 disabled 控件不应被当作一个正在等待用户填写的必填项。

自定义错误必须同时设计清除路径

下面用“确认密码与密码一致”补充原生规则。HTML 仍负责必填和密码最短长度，JavaScript 只负责两次值是否一致。

HTML
<form id="account-form">
  <label for="password">密码</label>
  <input id="password" name="password" type="password"
         minlength="12" required autocomplete="new-password" />

  <label for="confirmation">确认密码</label>
  <input id="confirmation" name="confirmation" type="password"
         required autocomplete="new-password"
         aria-describedby="confirmation-error" />
  <p id="confirmation-error"></p>

  <button type="submit">创建账户</button>
</form>
JavaScript
const password = document.querySelector('#password');
const confirmation = document.querySelector('#confirmation');
const error = document.querySelector('#confirmation-error');

function updateConfirmation() {
  const mismatch = confirmation.value !== '' &&
    confirmation.value !== password.value;
  const message = mismatch ? '两次输入的密码不一致，请重新确认。' : '';

  confirmation.setCustomValidity(message);
  if (mismatch) confirmation.setAttribute('aria-invalid', 'true');
  else confirmation.removeAttribute('aria-invalid');
  error.textContent = message;
}

password.addEventListener('input', updateConfirmation);
confirmation.addEventListener('input', updateConfirmation);
updateConfirmation();

setCustomValidity('非空消息') 设置一个持续存在的自定义错误。浏览器不会因为用户后来改对了值，就猜出业务规则并自动清掉它。必须在合法时调用 setCustomValidity('')，否则表单会一直被 customError 阻止。

两边都监听 input，是因为用户改完“确认密码”之后，也可能返回去修改第一遍密码。只监听确认框，会让原本相等的两个值变得不等，却仍保留旧的合法状态。

确认框为空时不设置“不一致”，把空值交给 required 处理。这里的文字错误与字段通过 aria-describedby 关联，同时提供了实际可读提示；aria-invalid 只是补充语义，不会替代约束校验。真实产品还应选择适当的提示时机，例如失焦后或首次提交后再展示错误，避免一开始就把整个空表单标红。

校验发生在提交事件之前

正常激活提交按钮或调用 requestSubmit() 时，浏览器会按表单设置进行交互式校验。不通过时通常不会触发正常的 submit 事件，所以不能把“显示所有原生错误”的逻辑全放进 submit 回调后才执行。

novalidate、提交按钮的 formnovalidate 和直接调用 form.submit() 可以改变或绕过这条自动校验路径。它们不意味着字段突然符合要求，也不意味着显式调用 checkValidity() 永远返回 true。

脚本设置值时还要注意规则边界：例如 minlength、maxlength 对用户编辑与程序赋值的检查行为存在区别。不要以为 input.value = 某个值 之后，所有约束都一定按手动输入时完全相同的方式执行。跨字段校验也需要在程序修改值后主动同步，而不是假定一定触发 input 事件。

异步校验和可信验证需要另外处理

检查用户名是否占用，需要服务端响应。输入从 A 变成 B 后，A 的慢响应不能覆盖 B 的校验结果；可以使用请求序号、取消请求和当前值比对来避免过期结果生效。网络失败也不能被当成“用户名肯定可用”。

前端通过校验只说明当前界面按现有规则接受了数据。用户可以修改 HTML、绕过页面直接发送请求，服务器数据也可能在检查后变化。因此服务端仍需检查格式、权限、唯一性与业务约束，并把可修复的错误返回到相应字段。

不要在每次输入时粗暴删除暂时“不合法”的字符。输入法组合过程、负数输入到一半、小数点、粘贴和自动填充都可能产生中间状态。保留用户输入、在合适时机解释怎样修复，通常比悄悄改掉内容更可靠。
