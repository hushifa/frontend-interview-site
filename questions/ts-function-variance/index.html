函数重载、联合参数与泛型怎样选择？

联合参数适合统一处理不同输入，泛型保留输入输出关系，重载描述不同调用形式。函数赋值还要考虑参数方向、返回值和 strictFunctionTypes，不能只看某个参数类型是否更具体。

参考答案

设计函数类型时，先看调用方式与返回关系。如果不同输入都执行同一种操作、返回同一种结果，联合参数通常足够。若需要保留“返回值与传入类型对应”，考虑泛型；若调用形式确实分成几组，可以用重载把它们分别列出。

不要先写一长串重载，再为了让实现通过检查加入 any。类型签名应当把业务接口讲清楚，而不是让调用者猜应该命中哪一条。

同一种返回契约，联合参数最直接

TypeScript
function lengthOf(value: string | readonly unknown[]): number {
  return value.length;
}

console.log(lengthOf('HTML')); // 4
console.log(lengthOf([1, 2])); // 2

字符串和数组都提供 length，返回值统一是 number，不需要分别维护两条重载。调用方如果手里已经是 string | readonly unknown[]，也能直接传入。

如果不同类型需要不同处理，可以在函数体里收窄。联合并不意味着实现必须用同一段代码，只是公共输入可以用同一个契约清楚表达。

需要保留输入类型关系，使用泛型

TypeScript
function wrap<T>(value: T): { value: T } {
  return { value };
}

const wrapped = wrap(12);
console.log(wrapped.value.toFixed(0)); // 12

泛型说明容器内的值与输入是同一种 T。若把返回类型统一写成 { value: unknown }，这层关系就丢失，调用方又需要额外检查。

泛型不一定适合表达所有“输入 A 返回 B，输入 C 返回 D”的情况。条件类型与实现签名过于复杂时，少量清楚的重载可能更容易阅读；但接口有很多组合时，也要防止重载数量不断膨胀。

重载签名面向调用者，实现签名不是额外入口

TypeScript
function convert(value: string): number;
function convert(value: number): string;
function convert(value: string | number): string | number {
  return typeof value === 'string' ? value.length : String(value);
}

console.log(convert('HTML').toFixed(0)); // 4
console.log(convert(12).toUpperCase()); // 12

function forward(value: string | number) {
  // @ts-expect-error 两条公开重载都不单独接受 string | number
  return convert(value);
}

调用者看到前面两条重载，最后一条宽签名用于检查实现。即使实现能接收联合，调用方也不会自动把它当成第三条公共调用形式。

如果确实要接受联合输入，需要增加相应的公开重载，或改用更合适的联合/泛型接口。这也解释了为什么不应在本来只需统一返回类型时过度使用重载。

实现必须兼容所有公开签名，但宽泛的实现返回联合，不一定让编译器证明每个运行时分支都精确符合你承诺的那条重载。字符串输入是否真的返回数字，仍应通过实现与测试保证。

参数数量和可选参数要反映实际调用

有些 API 只允许一参数或三参数形式，重载可以表达这种离散约束；实现里为了共享代码写了两个可选参数，不代表外部就能合法传两个参数。

回调的可选参数也容易写错。如果库保证每次调用都传 index，回调类型应把 index 声明为必需，而不是为了允许调用方只接收 item 就写成 index?:number。JavaScript 函数本来可以忽略多余参数，少写一个形参通常不需要把库的传参保证削弱。

返回 void 的回调契约通常表示调用方不使用返回值，并不等于所有赋进去的函数在运行时都必须返回 undefined。这个规则与函数体显式标注 void 后的返回检查，也需要按具体语境区分。

回调参数更具体，反而可能不能替换更宽的回调

以下示例以 strictFunctionTypes 开启为前提：

TypeScript
type Animal = { name: string };
type Dog = Animal & { bark(): void };
type Handler<T> = (value: T) => void;

const handleAnimal: Handler<Animal> = animal => console.log(animal.name);
const handleDog: Handler<Dog> = dog => dog.bark();

const usableForDog: Handler<Dog> = handleAnimal;

// @ts-expect-error 只会处理 Dog 的函数，不能承诺处理任意 Animal
const unsafeForAnimal: Handler<Animal> = handleDog;

需要处理 Dog 的位置，可以使用能处理所有 Animal 的函数，因为 Dog 也有 name。反过来，只会处理 Dog 的函数会调用 bark，若调用方真的传了一个普通 Animal，就会失败。

这就是参数位置常说的逆变方向：替代函数要能接受接口可能交给它的输入，而不是要求更苛刻的输入。返回值方向则通常相反，一个保证返回 Dog 的函数可以满足“返回 Animal”的需求。

方法语法有兼容性例外，不能据此认定安全

TypeScript
type MethodHandler<T> = {
  handle(value: T): void;
};

const dogMethods: MethodHandler<Dog> = { handle: handleDog };
const widerMethods: MethodHandler<Animal> = dogMethods;

在 TypeScript 的相应规则下，方法与构造器声明并不完全采用普通函数属性相同的严格参数检查，因此这种方法形式可能允许前面函数属性形式拒绝的关系。它是类型系统为兼容现有代码保留的取舍，不是证明 dogMethods 真的能处理任意 Animal。

设计公共回调接口时，要留意 handle(value: T): void 与 handle: (value: T) => void 的差异。不要为了消掉一个合理报错就切换成更宽松的形式，而不修正真实的输入承诺。

最后，选签名时可以写出三类调用：正常使用、应该被拒绝的输入、已经是联合类型的调用方变量。再用严格配置验证推导结果。这样的接口测试比仅检查实现函数能否编译，更能反映公共 API 是否容易正确使用。
