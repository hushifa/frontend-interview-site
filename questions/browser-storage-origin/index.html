同源、同站点与跨域分别是什么意思？

协议、主机、端口都一样才算同源；同站点只看协议和主域名，子域和端口不同也算。平时说的跨域一般就是跨源，是同源策略和 CORS 管的事。

参考答案

简答

一个网址的“源”由三部分组成：协议、主机、端口。三样都一样，才算同源。https://app.example.com 和 https://api.example.com 主机不同，就不是同源。

“站点”的范围更大，只看协议和可注册域，也叫 eTLD+1，比如 example.com。端口不看，子域不同也算同站点，所以上面那两个网址是同站点。平时说的“跨域”，一般指的是跨源。

同源策略限制的是：脚本读取跨源资源的内容、访问跨源窗口的 DOM、读取别的源的存储。

要注意不同机制用的是不同的边界。Cookie 的 SameSite、浏览器的进程隔离按“站点”划分；CORS、localStorage、IndexedDB 按“源”划分。

先看几个例子

以 https://app.example.com 为基准：

URL同源同站点
https://app.example.com/path是是
https://api.example.com否，主机不同是
https://app.example.com:8443否，端口不同是
http://app.example.com否，协议不同否，协议不同
https://example.org否否

路径不影响源。浏览器里每个 URL 都有 origin 属性，只包含协议、主机和端口，可以在 Node 里直接验证：

JavaScript
const base = new URL('https://app.example.com');
for (const url of ['https://app.example.com/path', 'https://api.example.com', 'https://app.example.com:8443', 'http://app.example.com']) {
  console.log(url, new URL(url).origin === base.origin);
}
// https://app.example.com/path true
// https://api.example.com false
// https://app.example.com:8443 false
// http://app.example.com false

可注册域是怎么算的

你可能会想，那 a.github.io 和 b.github.io 是不是同站点？不是。可注册域是按公共后缀列表（Public Suffix List）算的，github.io 在这个列表里，地位和 .com 一样。所以 a.github.io 和 b.github.io 的可注册域分别是它们自己，属于不同站点。

同源策略到底拦什么

它拦的是“读”。脚本用 fetch 请求跨源地址，响应内容读不到，除非服务端用 CORS 头授权。跨源 iframe 或者 window.open 打开的窗口，它的 DOM 和大部分属性访问不了。其他源的 localStorage、IndexedDB 和 Cookie 也读不到，其中 Cookie 按域和路径的规则来。

可是它不拦“加载”和“提交”。<img>、<script>、<link> 照样能加载跨源资源，表单也能提交到跨源地址。正因为表单能跨源提交，还会自动带上 Cookie，才有了 CSRF 攻击。

常见追问

还能用 document.domain 放宽同源限制吗？

不要再依赖它。现代浏览器默认禁止通过修改 document.domain 来放宽同源检查。

跨源的两个窗口怎样安全地通信？

用 postMessage。接收方一定要校验 event.origin，确认消息来自信任的源。跨站 iframe 为什么会放到独立进程，见《浏览器为什么要拆分进程？前端如何理解故障隔离边界？》。
