WebAuthn 和 Passkey 登录的安全边界是什么？

区分公钥凭证、挑战、RP ID 和用户验证，理解前端调用 WebAuthn 不等于完成账号安全设计。

参考答案

传统密码登录让用户提交一个长期秘密，服务器判断是否正确。WebAuthn 则让认证器持有私钥，登录时对本次请求相关的数据签名，服务器用注册时保存的公钥验证。应用不需要读取或保存用户的私钥，也不会收到指纹或面容原始数据。

WebAuthn 是浏览器提供的公钥凭证 API；Passkey 是围绕这类凭证形成的无密码登录体验，通常使用可发现凭证，可能同步到多个设备，也可能绑定设备。不能把 WebAuthn、某种硬件安全钥匙与同步 Passkey 完全画等号。

注册时建立“账号与公钥”的关联

用户在可信的注册或已认证流程中选择添加 Passkey。服务端生成随机 challenge，并提供 RP、用户标识、算法及认证器要求等注册参数。前端把这些参数交给 navigator.credentials.create({ publicKey })，浏览器与认证器完成用户交互和密钥创建。

返回值包含凭证标识、认证器数据和客户端数据等信息。前端把它们发送给服务端，服务端验证注册响应后，才将凭证与正确账号关联。不能只相信前端传来的 userId；否则攻击者可能尝试给别人的账号绑定自己的凭证。

在标准 WebAuthn 调用中，私钥不作为 JavaScript 可读字符串返回。如果 Passkey 支持同步，具体密钥保护和同步由平台或凭证提供方实现，因此也不能笼统声称所有 Passkey 私钥永远不离开单一硬件。

登录时验证的是一次新的挑战

服务端为这次登录生成新 challenge，前端调用 navigator.credentials.get({ publicKey })。用户通过平台界面选择凭证并完成所需确认或用户验证，认证器返回 assertion。服务端用对应公钥验证签名，并检查 challenge、origin、RP ID 相关数据及要求的标志。

challenge 应不可预测、有有效期，并与当前事务关联，成功后不能重复使用。仅仅验证“签名是这把公钥签的”不够，否则旧响应可能被拿来重放。登录成功后仍需建立应用自己的会话，后续请求并不是每次都重新弹出 Passkey 界面。

为什么它能降低钓鱼风险

凭证与 RP ID 绑定，浏览器还会把实际调用来源写入客户端数据。假冒网站不能像骗取密码那样，让用户把同一个秘密手动输入给它；它通常也无法请求真实站点的凭证来完成自己的登录。

服务端仍必须验证预期 origin 和 RP ID hash，不能把这些检查删掉。RP ID 一般是调用站点的有效域名范围，不包含协议或端口；origin 则包含协议、主机和适用的端口。部署多个子域、嵌入式流程或跨来源授权时，应遵循对应协议与浏览器规则，而不是任意填写域名。

抗钓鱼也不意味着网站本身的 XSS 或登录后会话被盗没有影响。认证机制保护登录证明，不能自动保护之后所有业务代码。

用户在场与用户验证不是一回事

用户在场（UP）表示发生了认证器要求的在场确认；用户验证（UV）表示认证器按其能力完成了 PIN、生物识别等验证。一次简单触碰不应被自动解释成已经做了指纹识别。

若业务要求用户验证，应在请求中提出相应要求，并由服务端检查返回的 UV 标志。前端设置 userVerification: 'required' 不能代替服务端验证。注册、后续认证和凭证信任状态还需遵循所选服务端库的完整验证规则。

签名计数器不是每种凭证都严格递增

某些认证器提供签名计数器，用来辅助发现复制或异常使用；也有认证器不支持有意义的计数，或者同步凭证不能表现为所有设备共享一个严格递增的序列。

因此不能写成“下一次计数必须更大，否则一律拒绝所有用户”。服务端应按规范、认证器能力及备份相关标志处理计数异常，将其纳入风险判断。异常可能值得调查，但不能单凭这一项证明凭证一定被克隆。

能登录之外，还要能安全恢复

实际产品要支持多个凭证的添加、命名和撤销，并处理设备丢失、同步账号不可用、用户取消和不支持的浏览器。添加新凭证、删除最后一个凭证等操作通常需要额外身份确认。

账号找回若只依赖一个容易被接管的渠道，仍可能绕过强登录方式。应把恢复流程与正常登录一起设计，同时向用户解释跨设备使用方式。

浏览器 API 返回的二进制数据还需要按协议正确编码和解码，不能直接把普通 JSON 对象当成完整 WebAuthn 参数。优先使用成熟的客户端与服务端库，并在 HTTPS、安全上下文及真实设备上测试；模拟认证器测试可以验证流程，却不能代表指纹、平台同步和跨设备体验已经验证。
