WebAuthn 和 Passkey 登录的安全边界是什么？

WebAuthn 让认证器持有私钥、对服务端的一次性挑战签名，服务端用注册时保存的公钥验证；凭证绑定 RP ID，浏览器写入真实来源，所以钓鱼站点无法使用。Passkey 是基于它的无密码体验，可能跨设备同步。服务端仍要严格验证挑战、来源和标志位，并设计好账号恢复。

参考答案

简答

  • 注册：服务端生成随机 challenge，前端调用 navigator.credentials.create()，认证器生成密钥对，服务端验证响应后保存公钥和凭证 ID。
  • 登录：服务端生成新的 challenge，前端调用 navigator.credentials.get()，认证器签名，服务端用公钥验证签名、challenge、origin 和 RP ID。
  • 抗钓鱼：凭证绑定 RP ID（站点域名），浏览器把真实来源写进签名数据，假冒站点拿不到也用不了真实站点的凭证。
  • 用户在场（UP）只表示有人触碰确认；用户验证（UV）表示完成了 PIN 或生物识别。需要 UV 时服务端必须检查标志位。
  • 服务端从不接触私钥和生物特征；同步型 Passkey 的私钥由平台的密码管理服务加密同步。

登录调用

JavaScript
const options = await fetch('/webauthn/login/options', { method: 'POST' }).then((r) => r.json());

const credential = await navigator.credentials.get({
  publicKey: {
    challenge: base64urlToBytes(options.challenge),
    rpId: 'example.com',
    userVerification: 'required',
    allowCredentials: [], // 为空时使用可发现凭证，用户从列表中选择 Passkey
  },
});

await fetch('/webauthn/login/verify', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify(serializeCredential(credential)),
});

base64urlToBytes 和 serializeCredential 负责二进制与 JSON 的转换，实际项目中使用成熟的客户端库（如 @simplewebauthn/browser）处理。浏览器支持时也可以用 PublicKeyCredential.parseRequestOptionsFromJSON() 和 credential.toJSON()。

服务端必须验证

检查项原因
challenge 与本次会话保存的一致、未过期、只用一次防重放
origin 是自己的站点防钓鱼和跨站调用
rpIdHash 对应自己的 RP ID凭证属于本站
UP、UV 标志符合要求确认用户在场或完成验证
签名用保存的公钥验证通过证明持有私钥

注册时绑定的用户必须来自服务端会话，不能信任前端传来的用户 ID，否则攻击者可以把自己的凭证绑到别人的账号上。

签名计数器：部分认证器提供递增计数，用于发现凭证被复制；同步型 Passkey 通常不提供有意义的计数，计数异常应作为风险信号而不是一律拒绝。

产品层面

  • 允许一个账号注册多个 Passkey，支持命名和删除，删除最后一个凭证前要求再次验证。
  • 账号恢复的强度决定了整体安全：如果仅凭一条短信就能重置并绑定新 Passkey，攻击者会绕过它。
  • 登录成功后仍是应用自己的会话管理，会话 Cookie 被盗与 Passkey 无关。
  • 提供条件式界面：输入框加 autocomplete="username webauthn"，配合 mediation: 'conditional'，在自动填充中展示 Passkey。

常见追问

  • WebAuthn 能防 XSS 吗？不能。XSS 可以在登录后的会话中直接操作，认证方式只保护登录这一步。
  • 只能在 HTTPS 下用吗？是的，需要安全上下文（localhost 例外）。
