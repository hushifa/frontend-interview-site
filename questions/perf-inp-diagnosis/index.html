INP 很高时，如何定位到底是哪一段交互变慢？

INP 衡量点击、轻触和按键到下一帧绘制要多久，≤200ms 良好、>500ms 较差，按 75 分位评估，2024 年取代 FID 成为 Core Web Vitals。每次交互拆成输入延迟、处理时间、呈现延迟三段，用 Event Timing 或 web-vitals 库找到最慢的交互和慢在哪段，再对症优化。

参考答案

简答

INP 衡量的是用户点击、轻触或按键以后，要等多久页面才画出下一帧。200 毫秒以内算良好，200 到 500 毫秒需要改进，超过 500 毫秒算较差，按页面访问的 75 分位评估。滚动和缩放不算在内。

一次交互可以拆成三段。第一段是输入延迟，用户点了，但主线程正忙，事件要排队；第二段是处理时间，事件回调本身在执行；第三段是呈现延迟，回调跑完到浏览器把下一帧画出来。

定位时先找到最慢的那次交互，再看它慢在哪一段。输入延迟高就去找当时占着主线程的长任务；处理时间高就减少回调里的同步工作和更新范围；呈现延迟高就检查样式、布局和 DOM 规模。

线上用 web-vitals 库的 attribution 版本采集这三段，开发时用 DevTools 的 Performance 面板复现。

INP 取的是哪一次交互

页面停留期间会有很多次交互，INP 取的是接近最慢的那一次。为什么说“接近”？因为交互很多的页面，偶尔一次异常慢的可能是噪声。规则是交互达到 50 次及以上的页面取 98 分位，相当于每 50 次交互剔除一个最差值。

所以 INP 变差，通常意味着某一类交互稳定地慢，而不是平均每次都慢一点。

线上怎么采集这三段

web-vitals 库的 attribution 版本会直接给出最慢交互的目标元素、类型和三段耗时：

JavaScript
import { onINP } from 'web-vitals/attribution';

onINP(({ value, rating, attribution }) => {
  sendToAnalytics({
    value: Math.round(value),
    rating,
    target: attribution.interactionTarget,
    type: attribution.interactionType,
    inputDelay: Math.round(attribution.inputDelay),
    processing: Math.round(attribution.processingDuration),
    presentation: Math.round(attribution.presentationDelay),
  });
});

interactionTarget 告诉你用户点的是哪个元素，三个耗时告诉你慢在哪一段。有了这两样，就知道该去看哪段代码了。

不用库的话，也可以直接观察浏览器提供的 Event Timing 条目：

JavaScript
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (!entry.interactionId) continue;
    console.log(entry.name, {
      inputDelay: entry.processingStart - entry.startTime,
      processing: entry.processingEnd - entry.processingStart,
      presentation: entry.startTime + entry.duration - entry.processingEnd,
    });
  }
}).observe({ type: 'event', durationThreshold: 16, buffered: true });

这里的三段就是用时间点相减算出来的：startTime 是用户操作的时刻，processingStart 和 processingEnd 是回调开始和结束，startTime + duration 是下一帧画出来的时刻。

可是为什么生产环境还是推荐用库？因为一次点击会产生 pointerdown、pointerup、click 好几个事件条目，它们共用一个 interactionId，整页 INP 怎么从这些条目里算出来，规则比较复杂。另外 duration 的精度是 8ms，所以三段拆分只是估算。

慢在哪一段，就改哪一段

如果是输入延迟高，说明用户操作的时候主线程正被别的任务占着。要找出交互前后的长任务和长动画帧，见《如何用 Long Animation Frames API 定位卡顿来源？》。然后把初始化逻辑和第三方脚本拆开，非关键的工作推迟到空闲时段。

如果是处理时间高，说明事件回调本身太慢。回调里先更新能立即给用户反馈的状态，其余工作用 scheduler.yield() 或 setTimeout 往后放，见《什么是长任务，为什么会影响交互响应？怎样观测和拆分？》。另外减少一次交互触发的组件重渲染范围，排序、过滤这类纯计算可以挪到 Worker。

如果是呈现延迟高，说明回调结束以后渲染很慢。DOM 太大可以用虚拟列表或 content-visibility。写完样式马上读 offsetHeight 这类布局属性，会逼浏览器立刻重新布局，这叫布局抖动，改成先批量读、再批量写。复杂选择器和大面积重绘也要简化。

INP 好不代表用户等得少

INP 只算到下一帧画出来为止。所以点击以后马上显示一个加载状态，下一帧很快出现，INP 就可能是良好的，哪怕数据两秒以后才回来。

这本身是合理的优化，用户至少知道页面有反应了。但“从点击到真正完成”是另一个业务指标，需要单独测。

常见追问

为什么实验室里测不到很高的 INP？

因为 Lighthouse 这类工具只模拟加载，不会去点页面。INP 必须靠真实用户数据，或者自己在 DevTools 里手动录交互。实验室里可以用总阻塞时间 TBT 作为参考。

只优化事件回调就够了吗？

不够。很多时候输入延迟和呈现延迟才是大头，回调本身并不慢。所以要先拆三段看清楚，再决定改哪里。
