什么是强制同步布局？如何避免布局抖动？

刚改完样式就去读元素尺寸，浏览器只能当场重新算布局，这叫强制同步布局。在循环里一读一写反复这样做，就是布局抖动。改法是先集中读、再集中写。

参考答案

简答

浏览器通常很“懒”：你改了样式，它不会马上算布局，而是攒着，等到下一帧统一算。

可是如果你刚改完样式，马上去读 offsetHeight、getBoundingClientRect() 这类布局值，浏览器为了给你正确的数字，只能当场把布局算一遍。这就叫强制同步布局。

一次两次问题不大。但在循环里写一次、读一次，每次读都会触发一次布局，页面就会明显卡顿，这叫布局抖动（layout thrashing）。

解决办法是先把要读的值集中读完，再集中写；或者把写入放到 requestAnimationFrame 里。

先看一个有问题的写法

下面想把每个子元素的宽度设成容器的一半：

JavaScript
for (const item of items) {
  item.style.width = `${container.offsetWidth / 2}px`;
}

代码看起来只读了一个值，问题在哪？每一轮都先读 offsetWidth，再写 width。写入让布局失效了，下一轮再读 offsetWidth，浏览器只好重新算一次布局。有一百个元素，就算一百次。

改法是先读后写，读只做一次：

JavaScript
const half = container.offsetWidth / 2;
for (const item of items) {
  item.style.width = `${half}px`;
}

现在循环里只有写入，浏览器可以把这些修改攒到一起，最后只算一次布局。

读写分散在不同模块里时，没法这么直接地调整顺序。可以把读取和写入分别排队，在同一帧里先执行所有读，再执行所有写。

哪些读取会触发同步布局

常见的有：offsetTop/Left/Width/Height、clientWidth/Height、scrollTop、scrollHeight、getBoundingClientRect()、用 getComputedStyle() 读布局相关的属性、scrollIntoView()、focus()。

不过前提是“之前有待处理的样式修改”。如果没有改过样式，读这些属性不会额外触发布局，因为现成的布局结果就是对的。

还有哪些办法能减少布局成本

动画优先用 transform 和 opacity，它们通常不触发布局。

用 contain: layout 或 content-visibility: auto，把布局的影响限制在一个范围里，改了里面的东西不会牵连整个页面。

批量插入节点时，先放进 DocumentFragment，再一次性挂到 DOM 上。

想知道元素尺寸什么时候变了，用 ResizeObserver，不要轮询读取。

怎么找到是哪行代码触发的

在 Chrome DevTools 的 Performance 面板录一段。紫色的 Layout 块上如果有 “Forced reflow” 警告，点开调用栈，就能看到是哪一行代码读了布局值。

常见追问

只读布局属性、不改样式，会触发布局吗？

不会额外触发。只有在之前有待处理的样式修改时，读这些属性才会让浏览器当场重新计算。

为什么把写入放进 requestAnimationFrame 能缓解？

因为这样写入被推迟到下一帧渲染前统一执行，读取都在当前代码里先做完了，读和写就不会交替出现。
