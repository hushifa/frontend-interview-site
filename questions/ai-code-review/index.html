AI 生成的前端代码应该怎样审查和验证？

把模型写的代码当成陌生人提交的补丁来审。先把需求写成能检查的条件，再看数据流，跑类型检查、lint 和覆盖失败、取消、竞态的测试，新增依赖也要核实。

参考答案

简答

我会把模型写的代码当成一个陌生人提交的补丁，而不是成品。它常见的问题有：用了过时的 API、忘了取消请求和清理监听、引入不必要的依赖，或者把用户输入直接塞进 HTML。

审之前，先把需求写成能检查的条件，比如出错怎么显示、请求能不能取消、组件卸载时清理什么、允许用哪些依赖。

审的时候先读代码差异和数据流，看用户输入最后流到了哪里，是 DOM、URL、存储还是网络请求，然后才看演示效果。类型检查和 lint 只能发现一部分问题，测试还要覆盖失败、取消、快速切换、卸载后迟到的响应。

新增依赖要特别小心。模型可能编出一个不存在的包名，攻击者可以抢先注册这个名字，装进来的就是恶意代码。

先把需求写清楚

“写一个搜索组件”这种要求太宽泛了，模型写出来的东西看着能用，可你没法判断它对不对。至少要讲明白这几件事：输入防抖多久，旧请求是取消还是丢掉结果；接口出错、没有结果、加载中分别显示什么；组件卸载时要清理哪些监听、定时器和请求；能不能加新依赖，目标浏览器和 TypeScript 是什么版本；键盘和读屏器怎么操作。

有了这些条件，审查时就可以一条条对照，而不是凭感觉说“看起来没问题”。

为什么要先读数据流

先看一行很常见的代码：

JavaScript
preview.innerHTML = modelOutput; // 不可信内容进入 HTML 解析器

演示时这行完全正常，模型输出的文字显示得好好的。可是 innerHTML 会把字符串当 HTML 解析，如果模型输出里带了 <img src=x onerror=...>，脚本就会执行。光看效果是看不出来的，只有顺着数据流看“这个值从哪来、到哪去”才能发现。

改法是：纯文本用 textContent；确实需要富文本，就走白名单净化流程。还要注意，变量叫 safeHtml 不代表它真的被净化过，要往上追到它的来源。URL、文件路径、SQL、权限判断，都按同样的方式追踪。

自动化检查能做什么

先跑项目已有的类型检查、lint、格式检查和构建。如果模型为了让代码通过，加了 any、关了规则或者删了测试，这本身就是要打回的问题。

异步组件的测试至少要覆盖：请求成功、HTTP 报错、返回格式不对、取消、快速切换输入、组件卸载后响应才回来、重复提交、结果为空。

测试也可能是模型写的，所以要检查它是不是只测了成功的情况，mock 出来的接口和真实接口是不是一致。

依赖和运行环境

装新包之前，看一下它的官方仓库、维护状态、下载量和许可证，确认包真实存在、来源可信。

如果让 Agent 直接改代码、跑命令，要限制它能访问的文件和网络，不要给它生产环境的密钥。另外，issue、网页、文档里可能藏着提示词注入，诱导模型关掉校验或者加入恶意依赖，所以 Agent 读到的外部内容也要当成不可信的。

人工审查时重点看什么

监听和 effect 有没有成对清理；loading、空数据、错误、取消有没有分开处理；是不是沿用了项目现有的状态管理和错误处理方式，而不是另起一套；有没有把客户端配置误当成秘密来用。

常见追问

让模型自己审查自己写的代码可行吗？

可以当作辅助，帮着发现一些明显的问题。但它不能替代测试和人工审查，因为它可能带着写代码时同样的错误假设，自己看不出来。

生成代码的版权怎么处理？

先遵守公司的政策。如果生成的代码明显是照搬某个已有项目，要去核对那个项目的许可证。
