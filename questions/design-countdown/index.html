前端倒计时为什么会走慢？怎样用服务端时间校准？

setTimeout/setInterval 只保证不早于指定延迟执行，主线程繁忙和后台标签页节流都会让每秒减一的倒计时越走越慢。应该记住目标时间点，每次重新计算剩余时间，用 performance.now 计时避开系统时钟修改，并通过接口往返估算与服务端的时间差。

参考答案

简答

定时器设成 1000 毫秒，并不是说正好 1000 毫秒后执行，而是“至少等 1000 毫秒”。主线程忙的时候回调会被推迟；定时器嵌套超过 5 层，最小延迟会被限制成 4 毫秒；标签页切到后台，浏览器还会节流，最多每秒执行一次，甚至更少。

所以“每秒回调一次、计数减一”的写法会越走越慢，因为每次的延迟都被累加进去了。正确做法是记住结束的时间点，每次回调都用“结束时间减当前时间”重新算剩余时间，这样某一次晚了，下一次也会自动纠正。

计算经过的时间最好用 performance.now()。Date.now() 依赖系统时钟，用户一改系统时间，倒计时就跳了；performance.now() 是单调时钟，只会往前走，不受系统时钟调整影响。

还要注意，结束时间要以服务端为准。可以通过一次接口往返，估算本地和服务端差了多少，页面切回前台时再校准一次。但像“现在能不能下单”这种关键判断，仍然要服务端在收到请求时自己校验。

每秒减一为什么会越走越慢

很多人第一版会这样写：

JavaScript
// 错误写法：每秒减一，误差随时间累积
let left = 60;
setInterval(() => {
  left -= 1;
  render(left);
}, 1000);

这段代码假设回调正好每 1000 毫秒执行一次。可实际上，每次回调都可能晚几毫秒到几百毫秒，碰上长任务或者页面卡顿会晚得更多。

标签页切到后台以后更明显。Chrome 会把定时器限制成每秒最多检查一次，页面隐藏超过 5 分钟、并且满足其他条件时，还会降到每分钟一次。

这些延迟每一次都被算进了 left。left 减了 60 次，真实时间可能已经过去了 65 秒、70 秒，几分钟以后差距就能看出来了。

改成按目标时间计算

先写一个函数，给定结束时间和当前时间，算出要显示的文字：

JavaScript
const formatRemain = (endAt, now) => {
  const seconds = Math.ceil(Math.max(0, endAt - now) / 1000);
  const mm = String(Math.floor(seconds / 60)).padStart(2, '0');
  const ss = String(seconds % 60).padStart(2, '0');
  return `${mm}:${ss}`;
};

console.log(formatRemain(125000, 0)); // 02:05
console.log(formatRemain(1000, 1500)); // 00:00

剩余 125000 毫秒，显示 02:05。已经过了结束时间，Math.max(0, ...) 让它停在 00:00，不会出现负数。

然后用它驱动倒计时：

JavaScript
function startCountdown(endAt, now, onTick) {
  let timer;
  const tick = () => {
    clearTimeout(timer);
    const current = now(); // 只取一次，显示与调度用同一时刻
    const remain = endAt - current;
    onTick(formatRemain(endAt, current));
    if (remain <= 0) return;
    // 对齐到下一个整秒，减少显示跳秒
    timer = setTimeout(tick, remain % 1000 || 1000);
  };
  tick();
  return { stop: () => clearTimeout(timer), refresh: tick };
}

关键在于每次 tick 都重新读当前时间，用结束时间减它。哪怕某一次回调晚了，下一次显示的剩余时间照样是对的，误差不会累积。

下一次的延迟用 remain % 1000，是为了让回调正好落在剩余时间跨过整秒的时候，减少显示上的跳秒。

页面从后台切回来，也就是 visibilitychange 变回 visible 时，调用返回的 refresh() 立刻刷新一次。它会先清掉旧的定时器，所以不会出现两条计时链同时在跑。

怎样用服务端时间校准

本地时钟可能不准，用户也可能改过，所以结束时间要以服务端为准。思路是请求一次服务端时间，同时记下请求前后的本地时刻：

JavaScript
async function syncOffset() {
  const t0 = performance.now();
  const res = await fetch('/api/time');
  const t1 = performance.now();
  const { serverTime } = await res.json(); // 服务端毫秒时间戳
  // 假设往返延迟对称，响应生成于往返中点
  const serverAtT1 = serverTime + (t1 - t0) / 2;
  return { serverAtT1, perfAtT1: t1 };
}

// 之后任意时刻的服务端时间估算
const serverNow = ({ serverAtT1, perfAtT1 }) => serverAtT1 + (performance.now() - perfAtT1);

服务端返回的时间，是它生成响应那一刻的时间。这里假设请求去和回花的时间一样长，那响应大约生成在往返的中点，所以收到响应时，服务端的时间大约是 serverTime 加上往返时间的一半。

之后要知道服务端“现在”几点，就拿收到响应时的估算值，加上从那以后本地过去了多久。本地经过的时间用 performance.now() 计算，用户改系统时间也不影响。

这个估算有误差，网络去回不对称时尤其明显。可以多请求几次，取往返时间最短的那次，它的误差上限最小。

页面从后台恢复、电脑从休眠唤醒时，要重新校准。MDN 指出，只有 Windows 上的浏览器在系统休眠期间仍然让 performance.now() 继续计时，其他平台休眠时它会停住。

最后，把 serverNow 当成上面 startCountdown 的 now 参数传进去就行。

倒计时管不了的业务边界

前端倒计时只是展示。“到点就能抢购”必须由服务端在请求到达时判断，提前发来的请求应该被拒绝。

大量用户同一时刻点按钮，会形成请求尖峰。可以在开始前几秒随机错开预热请求，或者由服务端排队。

倒计时结束以后，应该从服务端重新拉取状态，而不是想当然地认为状态已经切换了。

定时器相关的测试方法见《前端怎样测试定时器、重试和超时，避免 Fake Timers 造成假通过？》。

常见追问

requestAnimationFrame 会更准吗？

它跟着屏幕刷新执行，后台标签页会暂停，所以不适合做倒计时的时间来源，只适合拿来刷新动画显示。

把定时器放进 Web Worker，能避免节流吗？

不能保证，各浏览器的策略不一样。还是要按目标时间重新计算。

毫秒级的倒计时怎么做？

用 requestAnimationFrame 刷新显示，剩余时间仍然用目标时间去算。
