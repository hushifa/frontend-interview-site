静态托管发布时为什么要检查资源路径和缓存？

静态部署把构建文件交给托管平台，浏览器仍需按正确前缀取得入口、脚本和数据。路径、深链接、缓存和发布版本必须一起验证。

参考答案

构建成功不等于网站可用

构建命令只说明文件生成成功，托管平台接收文件也只说明发布动作完成。用户打开页面时，浏览器还要请求正确的 HTML、JavaScript、CSS、图片和异步数据。只要其中一个路径或版本不对，就可能出现白屏、样式丢失或某个路由打不开。

静态托管不会因为仓库里有 Node 代码，就在每次访问时自动运行服务器。Node 可以在构建阶段生成文件，访问阶段能否执行服务端逻辑取决于托管平台。先区分构建能力和运行时能力，才能选择合适的渲染和 API 方案。

部署前缀必须和站点地址一致

假设站点实际地址是 https://example.github.io/site/，HTML 中的 /assets/app.js 会请求域名根下的 /assets/app.js，不会自动加上 /site/。而 assets/app.js 在 /site/questions/123/ 页面中又可能被解析成 /site/questions/123/assets/app.js。

因此构建工具的 base、路由基路径、静态资源引用和托管地址必须统一。迁移到自定义域名根路径后，原来为仓库子路径设置的前缀也要重新检查。运行时拼接出来的字符串、public 目录文件和第三方资源不一定会被构建器自动改写。

排查时要看浏览器实际请求的完整 URL、状态码和内容类型。请求返回 200 也可能拿到错误页 HTML，随后才表现为模块解析或 MIME 类型错误。

深链接要单独验证

客户端路由在首页里点击通常能工作，但用户直接打开 /questions/123 或刷新这个地址时，托管平台必须能返回入口 HTML 或预生成页面。查询参数通常仍请求同一个静态文件，URL 片段不会发送给服务器，也不会自动生成独立页面。

可以预生成实际页面、配置平台回退规则，或选择适合静态托管的路由方式。GitHub Pages 是否需要 .nojekyll 取决于发布方式；它只影响 Jekyll 处理，不会修复错误的 base，也不会创建不存在的深层文件。

HTML 和哈希资源需要配套缓存

带内容哈希的 JS、CSS 和图片适合长期缓存，因为内容变化通常会产生新地址。HTML 负责引用当前版本资源，需要让用户在发布后能取得新的入口。如果旧 HTML 仍被缓存，而旧哈希资源已经删除，就会出现入口加载但异步块 404 的组合。

已经打开的旧页面也可能继续请求上一版资源。项目可以保留受控的旧资源窗口，或在找不到异步块时提示用户刷新；两种策略的成本不同。不能只加文件哈希，就认为旧页面问题自动消失，也不能用清空所有本地存储代替缓存设计。

具体 HTTP 缓存头能否设置，要看托管平台。HTML 里写变量不会改变 CDN 的缓存行为。

上线验收应从正式地址开始

至少验证：

  1. 正式域名首页能打开，HTTPS 和证书正确。
  2. 一个深层页面可以直接打开并刷新。
  3. JavaScript、CSS、图片、字体和异步块都来自当前版本。
  4. 主要交互能完成，控制台没有资源或模块错误。
  5. canonical、Sitemap 和站点图标没有残留开发地址或旧前缀。

如果只看 dist 文件夹或发布平台显示“部署成功”，仍然无法证明用户拿到的是正确页面。保留源码提交、构建参数和产物版本，才能在路径、缓存、权限和 DNS 问题之间快速定位责任层。
