静态托管发布时为什么要检查资源路径和缓存？

静态部署把构建文件交给托管平台，浏览器仍需按正确前缀取得入口、脚本和数据。路径、深链接、缓存和发布版本必须一起验证。

参考答案

简答

  • 站点部署在子路径（如 https://user.github.io/repo/）时，构建工具的基础路径（Vite 的 base）要设成 /repo/，否则资源会从域名根目录请求导致 404。
  • 单页应用的深链接（如 /repo/users/1）在服务器上没有对应文件，需要回退到 index.html 或在构建时预渲染每个路由。
  • 入口 HTML 用 Cache-Control: no-cache 每次校验，带内容哈希的资源设置长期缓存。
  • 发布新版本时保留旧的哈希资源一段时间，避免停留在旧页面的用户懒加载时 404。
  • 部署后从外部实际访问首页、深链接和懒加载功能，确认路径和缓存都正确。

资源路径

JavaScript
// vite.config.js
export default { base: '/frontend-interview/' };

构建后 HTML 中的引用变为 /frontend-interview/assets/index-3f9a.js。代码中拼接的路径也要基于 import.meta.env.BASE_URL，例如：

JavaScript
fetch(`${import.meta.env.BASE_URL}data/questions.json`);

直接写 /data/questions.json 在本地开发时能工作，部署到子路径后就会失败。

深链接

静态托管平台按 URL 查找文件。用户直接打开 /repo/users/1 或刷新页面时，服务器找不到 users/1/index.html 就返回 404。可选方案：

  • 预渲染：为每个路由生成 HTML 文件，搜索引擎和直接访问都能拿到内容。
  • 回退规则：Netlify、Vercel、Cloudflare Pages 等支持把未知路径重写到 index.html。
  • GitHub Pages：不支持重写规则，常见做法是预渲染，或复制一份 404.html 加载应用（返回状态码仍是 404，不利于搜索收录）。
  • hash 路由：/#/users/1 不会发到服务器，但 URL 不美观，也不利于 SEO。

缓存策略

文件建议
index.html 等入口no-cache，每次向服务器校验
assets/*-[hash].js/cssmax-age=31536000, immutable
无哈希的数据文件较短的 max-age 或 no-cache

入口被长时间缓存时，用户会一直加载旧版本；资源文件名不带哈希又设置长缓存时，用户拿不到更新。GitHub Pages 不允许自定义响应头，需要依赖它的默认缓存时间，或在前面加 CDN。

旧资源 404

每次构建资源文件名都会变化。用户打开旧页面后，点击懒加载功能会请求旧的 chunk 文件。如果部署时删除了旧文件，就会加载失败。部署时保留上一两个版本的资源，或在前端捕获加载失败后提示刷新。

部署后检查

  1. 无缓存打开首页，Network 面板没有 404。
  2. 直接访问一个深链接并刷新。
  3. 触发一个懒加载功能。
  4. 查看入口 HTML 和资源的 Cache-Control 响应头。
