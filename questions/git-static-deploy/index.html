静态托管发布时为什么要检查资源路径和缓存？

静态部署把构建文件交给托管平台，浏览器仍要按正确的路径前缀拿到入口、脚本和数据。资源路径、深链接、缓存和发布版本要一起验证。

参考答案

简答

本地开发好好的，部署到 GitHub Pages 就白屏，最常见的原因是路径前缀。站点放在子路径下，比如 https://user.github.io/repo/，构建工具的基础路径（Vite 里叫 base）就要设成 /repo/，不然浏览器会去域名根目录找资源，全部 404。

第二个坑是深链接。单页应用的地址比如 /repo/users/1，服务器上并没有这个文件，直接打开或刷新就 404。要么让服务器回退到 index.html，要么在构建时给每个路由预渲染一份 HTML。

第三是缓存。入口 HTML 用 Cache-Control: no-cache，每次都去服务器确认；带内容哈希的资源设置长期缓存。发布新版本时，旧的哈希资源要保留一段时间，不然停在旧页面的用户懒加载时会 404。

所以部署完以后，要从外部实际打开首页、深链接，触发一次懒加载，确认路径和缓存都对。

资源路径为什么会错

JavaScript
// vite.config.js
export default { base: '/frontend-interview/' };

设好 base 以后，构建出来的 HTML 里引用会变成 /frontend-interview/assets/index-3f9a.js。可是 base 只管构建工具生成的引用，你在代码里自己拼的路径它管不到，这些也要基于 import.meta.env.BASE_URL：

JavaScript
fetch(`${import.meta.env.BASE_URL}data/questions.json`);

为什么直接写 /data/questions.json 会出问题？本地开发时站点就在根目录，这个路径刚好对。部署到子路径后，开头的 / 指的还是域名根目录，请求就跑到了 https://user.github.io/data/questions.json，当然找不到。

深链接为什么会 404

静态托管平台是按 URL 去找文件的。用户直接打开 /repo/users/1 或者在这个页面刷新，服务器要找 users/1/index.html，找不到就返回 404。单页应用的路由是浏览器里的 JavaScript 处理的，服务器并不知道。可选的办法有这几种：

  • 预渲染：给每个路由生成一份 HTML 文件，搜索引擎和直接访问都能拿到内容。
  • 回退规则：Netlify、Vercel、Cloudflare Pages 等支持把未知路径重写到 index.html。
  • GitHub Pages：不支持重写规则，常见做法是预渲染，或者复制一份 404.html 来加载应用（返回的状态码仍是 404，不利于搜索收录）。
  • hash 路由：/#/users/1 中 # 后面的部分不会发给服务器，但 URL 不好看，也不利于 SEO。

缓存应该怎样设

文件建议
index.html 等入口no-cache，每次向服务器校验
assets/*-[hash].js/cssmax-age=31536000, immutable
无哈希的数据文件较短的 max-age 或 no-cache

这样设的道理是：带哈希的文件，内容一变文件名就变，所以同一个文件名的内容永远不变，可以放心长期缓存。入口 HTML 的文件名不变，必须每次确认，用户才能拿到新版本引用的新文件名。

反过来就会出问题。入口被长时间缓存，用户会一直加载旧版本；资源文件名不带哈希却设了长缓存，用户拿不到更新。GitHub Pages 不允许自定义响应头，只能依赖它默认的缓存时间，或者在前面加一层 CDN。

旧资源为什么不能马上删

每次构建，资源文件名都会变。用户打开旧页面以后，点开一个懒加载的功能，请求的还是旧的 chunk 文件。如果部署时把旧文件删了，这次加载就会失败。所以部署时保留上一两个版本的资源，或者在前端捕获加载失败后提示用户刷新。

部署完怎样检查

  1. 不带缓存打开首页，Network 面板里没有 404。
  2. 直接访问一个深链接，再刷新一次。
  3. 触发一个懒加载的功能。
  4. 查看入口 HTML 和资源的 Cache-Control 响应头。

常见追问

.nojekyll 是做什么的？

GitHub Pages 默认会用 Jekyll 处理站点，Jekyll 会忽略下划线开头的文件和目录。放一个 .nojekyll 文件，就能关掉这个处理。
