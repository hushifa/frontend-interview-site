第三方 Cookie、SameSite 和 Partitioned Cookie 有什么区别？

SameSite 决定跨站请求是否带 Cookie；第三方 Cookie 是否可用还取决于浏览器策略，Chrome 默认允许，Firefox 按顶层站点分区，Safari 默认阻止。Partitioned（CHIPS）让嵌入组件拿到一份按顶层站点隔离的 Cookie，适合不需要跨站共享身份的嵌入场景。

参考答案

简答

  • 第三方上下文：shop.example 嵌入了 pay.widget 的 iframe，pay.widget 的 Cookie 就是第三方 Cookie。
  • SameSite=None; Secure 是在第三方上下文中发送 Cookie 的前提，但浏览器的隐私策略可能仍然阻止。
  • 浏览器现状：Chrome 默认允许，用户可以屏蔽；Firefox 默认把第三方 Cookie 按顶层站点分区；Safari 默认阻止。
  • Partitioned 属性让 Cookie 按"顶层站点"分区：pay.widget 嵌在 shop.example 和嵌在 blog.example 里时是两份互不相通的 Cookie。
  • 需要跨站共享登录态时，用 Storage Access API 请求授权，或用 FedCM 做联合登录。

分区 Cookie 写法

http
Set-Cookie: __Host-widget=abc; Secure; Path=/; SameSite=None; Partitioned
  • 必须有 Secure。
  • 推荐 __Host- 前缀，把 Cookie 绑定到主机名。
  • 分区键是顶层站点（scheme 加可注册域名）。同一个组件在不同网站里得到不同的 Cookie 罐，无法跨站追踪，同一顶层站点内的多次访问可以保持状态。

适合与不适合

场景方案
嵌入式客服、地图、评论，每个网站各自维护会话Partitioned
嵌入的支付页需要用户在支付平台的已有登录态Storage Access API
第三方账号登录FedCM 或顶层跳转登录
跨站追踪用户浏览器正在逐步限制，不要依赖

Storage Access API

JavaScript
// 在嵌入的 iframe 内，由用户手势触发
button.addEventListener('click', async () => {
  if (!(await document.hasStorageAccess())) {
    await document.requestStorageAccess();
  }
  // 获得授权后，请求会带上非分区的第三方 Cookie
});

浏览器可能弹出提示或根据用户与该站点的交互历史自动决定，调用失败时要有降级方案，例如打开顶层窗口完成操作。

迁移检查

  1. 找出所有设置了 SameSite=None 的 Cookie，它们就是依赖第三方上下文的部分。
  2. 在屏蔽第三方 Cookie 的浏览器设置下测试嵌入功能。
  3. 按场景选择 Partitioned、Storage Access API、FedCM，或改为顶层页面完成操作。
  4. Cookie 缺失时给出可用的降级体验，而不是静默失败。

常见追问

  • 分区 Cookie 和 SameSite 能一起用吗？能，分区 Cookie 通常就设 SameSite=None，因为它就是给第三方上下文用的。
  • Chrome 会不会再默认屏蔽第三方 Cookie？目前 Chrome 默认允许，只在无痕模式或用户设置时屏蔽。不要依赖这一点：其他浏览器已默认限制，用户也可以随时关闭。
