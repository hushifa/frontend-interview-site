强缓存与协商缓存如何配合？

浏览器先看缓存是否新鲜，新鲜就直接使用（强缓存）；过期后带上 ETag 或 Last-Modified 发条件请求，服务器回 304 时复用本地正文（协商缓存）。

参考答案

简答

  • 强缓存：响应仍在新鲜期内时，浏览器直接用本地副本，不发请求。新鲜期由 Cache-Control: max-age 决定，同时存在时 max-age 优先于 Expires。
  • 协商缓存：副本过期或带 no-cache 时，浏览器发条件请求 If-None-Match（ETag）或 If-Modified-Since（Last-Modified）。
  • 服务器判断没变就回 304 Not Modified，不带正文，浏览器继续用本地副本并更新新鲜期；变了就回 200 和新正文。
  • 两个条件头同时存在时，服务器以 If-None-Match 为准，ETag 比秒级的修改时间更精确。

判断流程

  1. 响应能否被存储：no-store 不存储；private 只允许浏览器缓存，不允许 CDN 这类共享缓存。
  2. 副本是否新鲜：年龄（Age 加上本地停留时间）小于 max-age（共享缓存优先看 s-maxage）即为新鲜。没有显式新鲜期时，浏览器可以按 Last-Modified 启发式估算，这是很多"没配缓存却被缓存"问题的来源。
  3. 不新鲜或要求验证（no-cache）：带验证器发条件请求。
  4. 根据 304 或 200 更新缓存。

常用配置

资源响应头
带内容哈希的 JS、CSSCache-Control: max-age=31536000, immutable
HTML 入口Cache-Control: no-cache 加 ETag
含个人数据的接口Cache-Control: private, no-store 或按需 private, no-cache

HTML 每次验证，资源文件长期缓存，发布新版本时 HTML 引用新的哈希文件名，既能及时更新又不浪费带宽。各指令的取舍见《Cache-Control 的 immutable、no-store 等指令怎样选？》。

ETag 的细节

  • 强 ETag "abc" 要求字节一致；弱 ETag W/"abc" 表示语义等价，可用于条件 GET，不能用于 Range 请求。
  • 多台服务器各自生成 ETag（例如基于 inode）会导致同一文件 ETag 不同，验证总是失败。
  • 压缩后的表示应有不同的 ETag，否则缓存可能混用编码。

常见追问

  • no-cache 和 no-store 的区别：no-cache 允许存储但每次使用前必须验证；no-store 不允许存储。
  • 用户点刷新会怎样：普通刷新通常会对主文档重新验证；强制刷新（Ctrl+Shift+R）会绕过缓存。
  • 304 算不算请求：算。它省的是正文传输，仍有一次往返。
