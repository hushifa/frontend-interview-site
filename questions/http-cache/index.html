强缓存与协商缓存如何配合？

缓存还新鲜时浏览器直接用本地副本，这是强缓存；过期了就带上 ETag 问服务器有没有变，没变回 304 继续用旧的，这是协商缓存。

参考答案

简答

浏览器拿到一个响应后会存一份副本。下次再要这个资源，它先看副本还新不新鲜，新鲜就直接用，连请求都不发，这叫强缓存。新鲜期一般由 Cache-Control: max-age 决定，它和 Expires 同时存在时以 max-age 为准。

副本过期了，或者响应要求每次都验证（no-cache），浏览器就带着副本的“版本号”去问服务器：If-None-Match 带上 ETag，If-Modified-Since 带上修改时间。这叫协商缓存。

服务器看了觉得没变，就回 304 Not Modified，不带正文，浏览器继续用本地副本并刷新新鲜期；变了就回 200 和新内容。两个条件头都在时，服务器以 If-None-Match 为准，因为 ETag 比精确到秒的修改时间更准。

实际项目里两者配合用：HTML 每次验证，带哈希的 JS、CSS 长期强缓存。要注意 304 也是一次往返，省的只是正文。

浏览器是怎么判断的

浏览器拿到响应后，先问能不能存。no-store 表示不许存；private 表示只能存在用户自己的浏览器里，CDN 这种多人共用的缓存不能存，这类缓存叫共享缓存。

存下来以后，再用时要算副本的“年龄”，也就是 Age 头加上它在本地待的时间。年龄小于 max-age 就算新鲜，直接用。共享缓存会优先看 s-maxage。

这里有个容易踩的坑。响应里根本没写新鲜期时，浏览器可以按 Last-Modified 自己估一个，这叫启发式缓存。很多“明明没配缓存，怎么被缓存了”的问题就是这么来的。

副本不新鲜，或者带了 no-cache，浏览器就发条件请求去验证，再根据 304 还是 200 更新缓存。

常用配置怎么定

资源响应头
带内容哈希的 JS、CSSCache-Control: max-age=31536000, immutable
HTML 入口Cache-Control: no-cache 加 ETag
含个人数据的接口Cache-Control: private, no-store 或按需 private, no-cache

这样配的道理是：HTML 每次都验证，所以发版后用户总能拿到新 HTML；新 HTML 引用的是新哈希文件名，等于一个新 URL，旧缓存自然用不上。资源文件内容和文件名绑定，可以放心缓存一年。既能及时更新，又不浪费带宽。各指令怎么取舍见《Cache-Control 的 immutable、no-store 等指令怎样选？》。

ETag 有哪些细节

ETag 分强弱两种。强 ETag 写作 "abc"，要求字节完全一致；弱 ETag 写作 W/"abc"，只表示意思一样。弱 ETag 能用在普通的条件 GET 上，但不能用于 Range 请求，因为拼接字节时必须保证完全一样。

多台服务器各自生成 ETag 也会出问题。比如按文件 inode 生成，同一个文件在不同机器上 ETag 不同，验证总是失败，每次都回 200。

另外，压缩后的内容和原始内容应该有不同的 ETag，否则缓存可能把 gzip 和 br 的版本混着用。

常见追问

no-cache 和 no-store 有什么区别？

no-cache 允许存，但每次用之前必须先找服务器验证。no-store 是根本不许存。

用户点刷新会怎样？

普通刷新通常会对主文档重新验证。强制刷新，比如 Ctrl+Shift+R，会绕过缓存重新下载。

304 算不算一次请求？

算。它省的是正文的传输，但请求和响应的往返还在。
