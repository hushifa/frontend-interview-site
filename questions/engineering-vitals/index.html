LCP、INP、CLS 分别衡量什么？

分别解释主要内容出现、交互响应和意外布局移动，说明良好阈值、真实用户分位数、实验室诊断与采集限制，并避免把一个分数当成全部体验。

参考答案

简答

  • LCP（最大内容绘制）衡量主要内容多快出现，良好标准是 2.5 秒以内。
  • INP（交互到下一次绘制）衡量页面对点击、按键的响应速度，良好标准是 200 毫秒以内；它在 2024 年 3 月取代了 FID。
  • CLS（累积布局偏移）衡量内容意外移动的程度，良好标准是 0.1 以下。
  • 评估时取真实用户数据的第 75 百分位，桌面和移动端分开看。
  • Lighthouse 等实验室工具适合诊断，但测不出真实用户的 INP，最终以现场数据为准。

三个指标

指标衡量什么良好较差
LCP视口内最大的图片或文本块渲染完成的时间≤ 2.5 s> 4 s
INP页面生命周期内交互延迟的代表值（接近最慢的那次）≤ 200 ms> 500 ms
CLS意外布局偏移的最大会话窗口得分≤ 0.1> 0.25

常见原因和优化方向

LCP：服务器响应慢、LCP 图片被懒加载或发现得晚、渲染阻塞的 CSS/JS、客户端渲染才生成内容。优化方向是缩短 TTFB、用 fetchpriority="high" 和预加载让 LCP 资源尽早下载、避免对首屏图片使用 loading="lazy"。

INP：事件处理里有长任务、一次交互触发大量渲染、主线程被第三方脚本占用。优化方向是拆分长任务并让出主线程、先更新可见反馈再处理其余工作、减少不必要的重新渲染。

CLS：图片和广告位没有预留尺寸、字体切换导致文字重排、在已有内容上方插入横幅。优化方向是设置 width/height 或 aspect-ratio、给动态内容预留空间、用 font-display 和尺寸匹配的备用字体。用户交互后 500 毫秒内发生的偏移不计入 CLS。

采集真实数据

JavaScript
import { onLCP, onINP, onCLS } from 'web-vitals';

function send(metric) {
  navigator.sendBeacon('/vitals', JSON.stringify({
    name: metric.name,
    value: metric.value,
    rating: metric.rating,
    id: metric.id,
  }));
}

onLCP(send);
onINP(send);
onCLS(send);
  • INP 和 CLS 要到页面隐藏或卸载时才能得出最终值，web-vitals 会在页面进入后台时上报，所以用 sendBeacon 而不是普通请求。
  • 同时上报页面路径、设备类型、网络类型，才能定位是哪类用户变慢。
  • Chrome 用户体验报告（CrUX）提供公开站点的真实数据；Safari 和 Firefox 对这些指标的支持不完整，自采数据会偏向 Chromium 用户。

实验室与现场

Lighthouse 在固定设备和网络条件下模拟加载，能稳定复现 LCP、CLS 问题，并用总阻塞时间（TBT）近似反映交互风险。真实用户的设备、网络和交互方式差异很大，两者数值不同是正常的。先用现场数据确定问题，再用实验室工具复现和验证修复。

常见追问

  • 单页应用路由切换算吗？这三个指标都以页面加载为单位，软导航不会重置 LCP；INP 和 CLS 会持续累计到页面卸载。
  • 指标全绿就代表体验好吗？它们只覆盖加载、响应和稳定性，业务关键流程的耗时还需要自定义指标。
