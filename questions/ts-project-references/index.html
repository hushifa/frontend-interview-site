项目引用与 tsc -b 如何管理多包类型构建？

references 声明 TypeScript 项目间的构建依赖，composite 为可引用项目建立明确边界，tsc -b 按依赖处理声明与增量产物。它不负责运行时包解析，也不能代替工作区或打包器配置。

参考答案

一个项目逐渐拆成 core、ui、app 等包后，问题不只是文件变多，还包括谁依赖谁、哪些包需要先构建，以及改动一个包后是否必须重新检查全部代码。

TypeScript 项目引用用 tsconfig 中的 references 表达这些依赖边界。被引用包通常向消费者提供声明产物，构建模式据此决定顺序和需要更新的项目。

一个 core 被 app 使用的最小结构

text
example/
  package.json
  tsconfig.json
  packages/
    core/
      tsconfig.json
      src/index.ts
    app/
      tsconfig.json
      src/main.ts

根 package.json 让本例的 JavaScript 产物按 ESM 解释：

json
{
  "private": true,
  "type": "module"
}

根 tsconfig.json 只收集子项目，不再把全部源码当作自己的输入：

json
{
  "files": [],
  "references": [
    { "path": "./packages/core" },
    { "path": "./packages/app" }
  ]
}

core 的配置负责输出 JavaScript 与声明：

json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "strict": true,
    "composite": true,
    "declaration": true,
    "declarationMap": true,
    "noEmitOnError": true,
    "rootDir": "src",
    "outDir": "dist",
    "tsBuildInfoFile": "dist/tsconfig.tsbuildinfo"
  },
  "include": ["src"]
}

app 使用同样的边界设置，并显式引用 core：

json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "strict": true,
    "composite": true,
    "declaration": true,
    "noEmitOnError": true,
    "rootDir": "src",
    "outDir": "dist",
    "tsBuildInfoFile": "dist/tsconfig.tsbuildinfo"
  },
  "include": ["src"],
  "references": [{ "path": "../core" }]
}

引用关系与实际导入路径都要写清楚

TypeScript
// packages/core/src/index.ts
export function add(left: number, right: number): number {
  return left + right;
}
TypeScript
// packages/app/src/main.ts
import { add } from '../../core/dist/index.js';
console.log(add(2, 3)); // 5

示例直接使用相对产物路径，便于看清运行时实际要加载哪个文件。真实多包仓库通常使用包名、工作区链接与 package.json exports 管理入口，但 references 本身不会替你自动创建这些运行时映射。

在根目录运行 npx tsc -b --verbose，构建器会先处理 core，再构建需要它的 app。完成后可以运行 node packages/app/dist/main.js，得到 5。

单独对 app 执行普通的 tsc -p，不等于会自动把缺失的 core 产物一起构建出来。编辑器可能通过源码重定向提供便利，也不能把编辑器里正常跳转等同于干净环境已经具备产物。

composite 为什么要求更明确的项目边界

composite 让编译器能够推断引用项目的输入与输出。其约束包括明确的实现文件范围、声明输出要求，以及 rootDir 默认行为等。显式列出 rootDir、outDir 和 include，通常比依赖隐含目录关系更容易维护。

消费者通过引用访问库项目时，需要有能表达其公共接口的声明产物。不要把需要向下游提供声明的库随手设为 noEmit，然后期待依赖边界仍然自动成立。纯检查项目的聚合配置与真正依赖声明输出的多包构建，是不同用途，应按工具链分别设计。

declarationMap 让编辑器有机会从声明导航回对应源码，但还取决于源码或映射路径是否可访问。发布包只有映射、却没有可用源码，并不能保证消费者一定获得完整源码跳转体验。

增量构建使用的是状态记录，不是简单跳过命令

.tsbuildinfo 保存编译器的增量状态，可帮助下一次判断哪些项目和文件需要重新处理。再次运行 tsc -b，即使没有变化，仍会检查相应状态，只是可以避免重复完整构建。

缓存应与源码、配置、编译器版本和相关输出保持一致。CI 可以缓存这些文件，但不能只恢复一个状态文件而忽略所需声明产物，再假定消费者必然能编译。

tsc -b --watch 适合持续观察项目图；--force 强制重新构建；--clean 清理编译器管理的对应输出，不等同于清理整个打包器产物目录。排查“为什么没重建”时，先看 verbose 说明，再考虑缓存与路径问题。

出错后是否继续构建，要看版本和策略

较新的 TypeScript 构建模式可以在上游存在错误时继续处理项目图，不能继续沿用“tsc -b 永远在第一个错误处完全停止”的旧结论。

当前版本可使用 --stopBuildOnErrors 控制上游出错后跳过下游构建；具体参数与行为应通过所用版本的 tsc -b --help 核对。noEmitOnError 则控制有错项目自己的输出，两者的职责不同。

即使某些产物已经生成，也必须检查构建退出状态，不能把“dist 里有文件”当作检查成功。旧声明残留还可能让编辑器或局部命令暂时看起来可用，因此干净环境的完整构建很重要。

项目引用不能替代整个多包架构

references 不会安装依赖，不会替 npm/pnpm 配置工作区，也不会自动打包浏览器代码。路径别名、包导出、运行时模块格式和构建器入口仍要分别对应。

项目图应尽量保持清晰的依赖方向，避免互相引用形成循环。粒度也不是越细越好：拆分应体现稳定的模块边界，而不是每个目录都单独建立一个项目增加维护成本。

验证时至少覆盖首次无产物构建、重复增量构建、上游接口变化、上游出错和实际执行产物。只验证仓库里已有缓存时的一次成功，不足以证明项目引用配置能够可靠地支持团队与 CI。
