项目引用与 tsc -b 如何管理多包类型构建？

项目引用就是在 tsconfig 里写明“这个包依赖那个包”，tsc -b 按依赖顺序构建，没变化的包直接跳过。它只管类型检查和 tsc 输出，不管安装依赖、包名解析和打包。

参考答案

简答

一个仓库里有多个包，比如 app 依赖 core。项目引用的做法是每个包一个 tsconfig，在 app 的 tsconfig 里写 references: [{ "path": "../core" }]，声明它依赖 core。根目录的 tsconfig 设 "files": []，只负责把所有子项目列出来。

被引用的项目必须开启 composite。它要求输出声明文件、明确列出输入文件，这样下游通过上游的 .d.ts 了解类型，不用重新检查上游的源码。tsc -b 按依赖顺序构建，用 .tsbuildinfo 记录状态，判断哪些项目已经是最新的，直接跳过。

好处是大仓库只重新检查改动的包和它的下游，依赖方向也被强制下来。

要注意两点。TypeScript 5.6 起，上游有错误时 tsc -b 仍会继续构建下游，CI 里想要旧行为加 --stopOnBuildErrors。另外它只管类型检查和 tsc 输出，import '@acme/core' 解析到哪里，要靠 pnpm、npm 工作区和 package.json 的 exports。

最小的目录结构

text
tsconfig.json          // 根：只聚合
packages/core/tsconfig.json
packages/app/tsconfig.json  // 引用 core

根目录的配置只列出子项目，自己不包含任何文件：

json
// tsconfig.json
{
  "files": [],
  "references": [{ "path": "./packages/core" }, { "path": "./packages/app" }]
}

core 是被引用的一方，必须开 composite：

json
// packages/core/tsconfig.json
{
  "compilerOptions": {
    "module": "nodenext",
    "composite": true,
    "declarationMap": true,
    "rootDir": "src",
    "outDir": "dist"
  },
  "include": ["src"]
}

app 通过 references 声明依赖 core：

json
// packages/app/tsconfig.json
{
  "compilerOptions": {
    "module": "nodenext",
    "composite": true,
    "rootDir": "src",
    "outDir": "dist"
  },
  "include": ["src"],
  "references": [{ "path": "../core" }]
}

composite 会自动打开 declaration，所以 core 构建后会输出 .d.ts，app 检查时读的就是这些声明。declarationMap 额外生成映射文件，在编辑器里点“跳转到定义”时能跳回 core 的源码，而不是停在 .d.ts 上。

常用命令

命令作用
tsc -b按依赖构建所有过期项目
tsc -b --verbose打印每个项目为何构建或跳过
tsc -b --watch监听整个项目图
tsc -b --clean删除 tsc 生成的输出
tsc -b --force忽略缓存，全部重建
tsc -b --stopOnBuildErrors上游出错时跳过下游

一个容易踩的坑：单独对 app 执行 tsc -p packages/app，它不会先去构建 core。core 的声明还没生成时，就会报找不到类型。要按依赖顺序构建，得用 tsc -b。

5.6 改了什么

5.6 之前，tsc -b 相当于隐式开启了 noEmitOnError，遇到第一个有错误的项目就停下来，下游完全不检查。5.6 起它会继续检查和输出下游，错误照常报告，退出码也是非零，并且总是写出 .tsbuildinfo。

所以现在判断构建是否成功，要看退出码，不能看 dist 里有没有文件。上游出错了，dist 里照样可能有东西。

用了以后有什么好处

最直接的是快：大仓库改了一个包，只需要重新检查这个包和依赖它的下游。其次是强制依赖方向，app 只能通过 core 公开的声明使用它，引用了没声明依赖的项目会报错。编辑器也会按项目加载，内存占用更低。

它和其他工具怎么分工

问题负责者
import '@acme/core' 解析到哪个目录工作区链接 + exports
浏览器产物Vite、Rollup 等打包器
类型检查与声明输出tsc -b

项目之间的依赖不能有循环。拆分粒度按稳定的模块边界来，不必每个目录都建一个项目。

常见追问

.tsbuildinfo 能在 CI 里缓存吗？

可以，但必须和输出目录一起缓存。只恢复 .tsbuildinfo，tsc 会以为声明文件已经存在而跳过构建，下游就找不到类型了。

它和 Turborepo、Nx 这些 monorepo 工具是什么关系？

它们负责跨语言的任务编排和缓存，可以在任务里调用 tsc -b，两者并不冲突。
