项目引用与 tsc -b 如何管理多包类型构建？

references 声明 TypeScript 项目之间的依赖，被引用项目开启 composite 并输出声明文件，tsc -b 按依赖顺序构建并通过 .tsbuildinfo 跳过未变化的项目。TypeScript 5.6 起上游出错时 tsc -b 仍继续构建下游，--stopBuildOnErrors 恢复旧行为。它不负责安装依赖、解析包名或打包。

参考答案

简答

  • 每个子包一个 tsconfig，用 references: [{ "path": "../core" }] 声明依赖；根 tsconfig 设 "files": []，只列出所有子项目。
  • 被引用的项目必须开启 composite，它要求输出声明文件、明确列出输入文件，下游通过 .d.ts 了解上游类型，而不是重新检查上游源码。
  • tsc -b 按依赖顺序构建，用 .tsbuildinfo 判断哪些项目已是最新并跳过。
  • TypeScript 5.6 起，上游有错误时 tsc -b 继续构建整个项目图并尽量输出；CI 中需要旧行为时加 --stopBuildOnErrors。
  • 项目引用只管类型检查和 tsc 输出，包名解析靠 pnpm/npm 工作区和 package.json 的 exports。

最小结构

text
tsconfig.json          // 根：只聚合
packages/core/tsconfig.json
packages/app/tsconfig.json  // 引用 core
json
// tsconfig.json
{
  "files": [],
  "references": [{ "path": "./packages/core" }, { "path": "./packages/app" }]
}
json
// packages/core/tsconfig.json
{
  "compilerOptions": {
    "module": "nodenext",
    "composite": true,
    "declarationMap": true,
    "rootDir": "src",
    "outDir": "dist"
  },
  "include": ["src"]
}
json
// packages/app/tsconfig.json
{
  "compilerOptions": {
    "module": "nodenext",
    "composite": true,
    "rootDir": "src",
    "outDir": "dist"
  },
  "include": ["src"],
  "references": [{ "path": "../core" }]
}

composite 会自动开启 declaration；declarationMap 让编辑器从 .d.ts 跳转回源码。

常用命令

命令作用
tsc -b按依赖构建所有过期项目
tsc -b --verbose打印每个项目为何构建或跳过
tsc -b --watch监听整个项目图
tsc -b --clean删除 tsc 生成的输出
tsc -b --force忽略缓存，全部重建
tsc -b --stopBuildOnErrors上游出错时跳过下游

对 app 单独执行 tsc -p packages/app 不会先构建 core，core 的声明不存在时会报错。

5.6 的行为变化

5.6 之前，tsc -b 相当于隐式开启 noEmitOnError，遇到第一个有错误的项目就停止，下游完全不检查。5.6 起会继续检查和输出下游，错误照常报告且退出码非零，并且总是写出 .tsbuildinfo。判断构建成功要看退出码，不能看 dist 里有没有文件。

带来的好处

  • 大仓库只重新检查改动的包及其下游。
  • 强制依赖方向：app 只能通过 core 的公开声明使用它，引用了未声明依赖的项目会报错。
  • 编辑器按项目加载，内存占用更低。

与其他工具的分工

问题负责者
import '@acme/core' 解析到哪个目录工作区链接 + exports
浏览器产物Vite、Rollup 等打包器
类型检查与声明输出tsc -b

依赖关系不能有循环。拆分粒度按稳定的模块边界，不必每个目录一个项目。

常见追问

  • .tsbuildinfo 能在 CI 中缓存吗？可以，但必须连同输出目录一起缓存，只恢复 .tsbuildinfo 会让 tsc 误以为声明已存在。
  • 和 monorepo 任务工具（Turborepo、Nx）的关系？它们负责跨语言的任务编排和缓存，可以调用 tsc -b，两者不冲突。
