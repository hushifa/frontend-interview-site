DataView 怎样读取指定字节序的二进制数据？

DataView 在缓冲区上按字节偏移读取不同数值类型，并允许逐次指定多字节值的字节序。解析时还需要验证长度、符号和视图范围，不能只靠读取方法不报错就认为协议有效。

参考答案

一个 16 位整数需要两个字节。数值 0x1234 可以把高位字节 0x12 放前面，也可以把低位字节 0x34 放前面；协议双方如果使用不同顺序，就会把同一组字节读成不同数字。

高位字节先出现叫大端，低位字节先出现叫小端。DataView 可以显式决定每次多字节读写使用哪一种顺序，而多字节 TypedArray 通常采用平台字节序，更适合已明确本地数据表示的同类型数组。

同样两个字节，读法不同结果就不同

JavaScript
const buffer = new ArrayBuffer(2);
const view = new DataView(buffer);
view.setUint16(0, 0x1234); // 未传 littleEndian，按大端写入

console.log(new Uint8Array(buffer).join(',')); // 18,52
console.log(view.getUint16(0)); // 4660，也就是 0x1234
console.log(view.getUint16(0, true)); // 13330，也就是 0x3412

0x12 的十进制值是 18，0x34 是 52，所以第一行能直接看见缓冲中两个字节的排列。getUint16 默认按大端解释；传入 true 表示按小端解释。false 也明确表示大端。

实际协议代码通常建议显式写出这个布尔参数，或用有意义的常量说明协议顺序，避免维护者误以为省略参数就是“自动使用当前机器的顺序”。单字节读写没有字节先后问题，不需要相同的字节序参数。

偏移按字节计算，不要求字段天然对齐

DataView 的 getUint16(offset)、getUint32(offset) 等方法，都以视图起点为参照按字节定位。一个 32 位字段可以从字节 3 开始，不需要像相应 TypedArray 构造偏移那样天然满足元素对齐。

这适合混合字段的二进制消息：例如先放 1 字节类型，再放 2 字节长度，再放 4 字节序号。各字段宽度和起点由协议决定，不应随意用一个 Uint32Array 把整包数据都当成同一种数值读。

一个带长度检查的消息解析例子

以下自定义示例协议只接受类型 1，头部为 7 字节，长度与序号都采用大端，输入必须恰好包含一条完整消息：

JavaScript
function parsePacket(bytes) {
  if (!(bytes instanceof Uint8Array)) {
    throw new TypeError('输入必须是 Uint8Array');
  }
  if (bytes.byteLength < 7) {
    throw new RangeError('消息不足以包含完整头部');
  }

  const view = new DataView(bytes.buffer, bytes.byteOffset, bytes.byteLength);
  const type = view.getUint8(0);
  const payloadLength = view.getUint16(1, false);
  const sequence = view.getUint32(3, false);

  if (type !== 1) throw new RangeError('不支持的消息类型');
  if (bytes.byteLength !== 7 + payloadLength) {
    throw new RangeError('消息长度与头部声明不一致');
  }

  return { type, sequence, payload: bytes.subarray(7) };
}

const storage = new Uint8Array(12);
storage.set([1, 0, 3, 0, 0, 0, 9, 65, 66, 67], 2);
const packet = parsePacket(storage.subarray(2));
console.log(packet.type); // 1
console.log(packet.sequence); // 9
console.log(packet.payload.join(',')); // 65,66,67

故意把消息放在 storage 的第 2 字节开始，是为了体现视图范围。若只写 new DataView(bytes.buffer)，就会从底层缓冲第 0 字节开始读，把前面的两个填充字节误当成消息头。

传入 byteOffset 和 byteLength，才能让 DataView 与当前 Uint8Array 看到同一段数据。真实 Node Buffer 或其他子视图也可能只是大缓冲的一部分，不能认为 buffer 属性一定只包含当前消息。

payload 使用 subarray 返回共享视图，没有再次复制字节。后续修改 storage 的对应区域会影响 payload；如果调用方需要独立保存，应明确改为 slice 等复制方式。

这个示例没有实现跨网络分块的缓冲拼接。一次网络读取可能只包含半个头部，也可能包含多条消息，需要先按协议分帧，再交给接受完整消息的解析函数。

数值类型与字节序是两个独立选择

JavaScript
const view = new DataView(new ArrayBuffer(2));
view.setInt16(0, -1, false);
console.log(view.getInt16(0, false)); // -1
console.log(view.getUint16(0, false)); // 65535

这两次使用相同字节序，但一个按有符号整数解释，另一个按无符号整数解释，所以得到不同结果。浮点字段则应使用 getFloat32、getFloat64 等相应方法，不能因为字段占 4 字节就一律读成 Uint32。

64 位整数可使用相应的 BigInt 读写方法，结果类型也是 BigInt。若再转成 Number，仍需要检查安全整数范围；DataView 正确读出了所有位，不代表之后的数值转换不会丢失精度。

方法边界检查不等于完整协议验证

读取超出当前可访问视图范围会抛 RangeError 等相应错误，缓冲被转移后失效或调整大小也会影响读取。但即使每个 get 都成功，数据仍可能存在不支持的版本、越界的业务值、错误校验和或不一致的字段关系。

写入时也不能把 DataView 当成自动业务校验器：窄整数写入有相应的数值转换规则，超出希望范围的输入未必按业务意图拒绝。应先验证类型与范围，再按协议编码。

最后，DataView 只负责按格式解释字节。它不自动解码 UTF-8 文本、不验证压缩格式，也不提供多线程共享内存上的原子一致性。文本应使用合适的解码器，跨线程同步则需要另外的共享内存与原子操作设计。
