实时协同编辑应该怎样设计状态和冲突解决？

从共享文档和在线光标场景区分传输、操作、权威状态与临时 presence，比较版本检查、OT 和 CRDT，并说明离线、权限、顺序与资源成本。

参考答案

简答

  • 协同编辑要分清四层：传输（WebSocket 等）、操作（插入、删除）、文档状态和临时状态（光标、在线成员）。
  • 冲突解决有三种思路：乐观锁版本检查（冲突时拒绝并让用户合并）、OT（服务端变换并发操作）和 CRDT（数据结构保证各端最终一致）。
  • 本地编辑立即生效再同步给他人，网络延迟不能影响输入体验。
  • 光标、选区等临时状态不需要持久化，丢失可以重新同步，不应和文档内容走同一套冲突解决。
  • 权限仍由服务端校验每个操作，断线重连后要能补齐缺失的操作。

三种冲突处理方式

方式原理适用场景
版本检查提交时带上基础版本号，不一致则拒绝表单、配置这类低频编辑
OT服务端按顺序接收操作，变换并发操作的位置再广播Google Docs 等中心化文本编辑
CRDT每个字符有唯一 ID 和顺序信息，任意顺序合并都得到相同结果去中心化、离线优先、点对点

并发插入示例：文档是 ab，A 在位置 1 插入 x，B 同时在位置 2 插入 y。直接按位置应用时，A 端先得到 axb，再应用"位置 2 插入 y"得到 axyb；B 端先得到 aby，再应用"位置 1 插入 x"得到 axby。两端结果不一致。OT 在应用对方操作前把位置 2 调整为 3；CRDT 用元素 ID 而不是数字位置定位插入点。

用 CRDT 库实现

JavaScript
import * as Y from 'yjs';
import { WebsocketProvider } from 'y-websocket';

const doc = new Y.Doc();
const provider = new WebsocketProvider('wss://collab.example.com', 'doc-123', doc);
const text = doc.getText('content');

text.observe(() => render(text.toString()));
text.insert(0, '你好');

provider.awareness.setLocalStateField('cursor', { index: 2 });
  • Y.Doc 维护本地副本，修改立即生效，并把增量更新发给服务器和其他客户端。
  • awareness 单独传输光标和在线状态，超时未更新的成员自动移除。
  • 自己实现 OT 或 CRDT 的正确性很难保证，通常使用 Yjs、Automerge 等成熟库。

离线与重连

  • CRDT 可以在离线时继续编辑，重连后交换缺失的更新自动合并。
  • 本地把未确认的更新存入 IndexedDB，防止页面关闭后丢失。
  • 长时间离线后合并结果可能在语义上不合理（两人改写了同一段），需要提供历史版本和恢复能力。

服务端的职责

  • 鉴权：连接时验证用户是否能访问该文档，每个更新也要检查是否有写权限，只读用户的更新直接拒绝。
  • 持久化：定期保存文档快照，并保留更新日志用于恢复。
  • 资源：CRDT 会保留删除的元信息，文档体积随编辑历史增长，需要定期压缩或做垃圾回收。

常见追问

  • 用 WebSocket 还是 WebRTC？WebSocket 经过服务器，便于鉴权和持久化；WebRTC 点对点延迟低，但仍需要信令服务器，权限控制更难。
  • 撤销怎么处理？协同场景下只撤销自己的操作，Yjs 的 UndoManager 按来源记录操作，不会撤销别人的修改。
