实时协同编辑应该怎样设计状态和冲突解决？

实时协同要分清传输、操作、权威状态和临时的 presence（光标、在线成员）。冲突解决可以用版本检查、OT 或 CRDT，还要处理离线、权限、操作顺序和资源成本。

参考答案

简答

实时协同编辑，就是几个人同时改同一份文档，每个人都能马上看到别人的修改。设计时要先分清四层：传输层，比如 WebSocket；操作，比如插入、删除；文档状态；还有光标、在线成员这类临时状态。

冲突怎么解决，有三种思路。第一种是版本检查，提交时带上版本号，冲突了就拒绝，让用户自己合并。第二种是 OT，服务端按顺序接收操作，把并发的操作调整位置后再广播。第三种是 CRDT，用特殊的数据结构，保证各端不管按什么顺序合并，最后都一致。

体验上，本地编辑要立刻生效，再同步给别人，不能让网络延迟影响打字。光标、选区这些临时状态不用持久化，丢了重新同步就行，不要和文档内容走同一套冲突解决。

还要注意，权限仍然要由服务端校验每一个操作，断线重连以后也要能把漏掉的操作补齐。

并发编辑为什么会冲突

看一个最简单的例子。文档内容是 ab，A 在位置 1 插入 x，B 同时在位置 2 插入 y。

如果双方直接按位置应用对方的操作，A 这边先得到 axb，再应用“位置 2 插入 y”，得到 axyb。B 那边先得到 aby，再应用“位置 1 插入 x”，得到 axby。两边的结果不一样了。

问题出在位置上。A 插入 x 以后，B 原来说的“位置 2”在 A 这边已经变成了位置 3。

OT 的做法是在应用对方操作之前，把位置 2 调整成 3。CRDT 的做法是不用数字位置，而是给每个字符一个唯一 ID，插入时说“插在某个 ID 后面”，这样无论先后，定位都不会错。

三种方式怎么选

方式原理适用场景
版本检查提交时带上基础版本号，不一致则拒绝表单、配置这类低频编辑
OT服务端按顺序接收操作，变换并发操作的位置再广播Google Docs 等中心化文本编辑
CRDT每个字符有唯一 ID 和顺序信息，任意顺序合并都得到相同结果去中心化、离线优先、点对点

用现成的 CRDT 库

自己实现 OT 或 CRDT，正确性很难保证，一般直接用 Yjs、Automerge 这类成熟的库。下面是 Yjs 的用法：

JavaScript
import * as Y from 'yjs';
import { WebsocketProvider } from 'y-websocket';

const doc = new Y.Doc();
const provider = new WebsocketProvider('wss://collab.example.com', 'doc-123', doc);
const text = doc.getText('content');

text.observe(() => render(text.toString()));
text.insert(0, '你好');

provider.awareness.setLocalStateField('cursor', { index: 2 });

Y.Doc 在本地维护一份文档副本。text.insert 的修改立刻生效，同时把增量更新发给服务器和其他客户端。别人的修改到了，observe 回调触发，重新渲染。

光标用的是 awareness，它和文档内容分开传输。成员长时间没有更新，就会被自动移除。这正是前面说的：临时状态和文档内容分开处理。

离线和重连怎么办

CRDT 的一个好处是离线时可以继续编辑，重连以后交换彼此缺的更新，自动合并。

本地还没被确认的更新，要存进 IndexedDB，防止页面关掉以后丢失。

不过要注意，长时间离线后自动合并的结果，在数据上是一致的，语义上却可能不合理，比如两个人改写了同一段话。所以还要提供历史版本和恢复能力。

服务端负责什么

鉴权方面，连接时验证用户能不能访问这份文档，每个更新也要检查有没有写权限，只读用户发来的更新直接拒绝。

持久化方面，定期保存文档快照，同时保留更新日志，用来恢复。

资源方面，CRDT 会保留已删除内容的元信息，文档体积会随着编辑历史一直增长，需要定期压缩或做垃圾回收。

常见追问

用 WebSocket 还是 WebRTC？

WebSocket 经过服务器，方便鉴权和持久化。WebRTC 是点对点的，延迟低，但仍然需要信令服务器来建立连接，权限也更难控制。

撤销怎么处理？

协同场景下，撤销只撤销自己的操作。Yjs 的 UndoManager 会按来源记录操作，不会把别人的修改撤掉。
