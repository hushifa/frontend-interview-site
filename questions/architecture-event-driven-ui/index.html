事件驱动 UI 怎样避免状态互相覆盖？

区分命令、事件与状态所有者，用可取消的最新搜索控制器解释请求身份和过期结果，并说明重复事件、DOM 事件及隐式总线的边界。

参考答案

把通信改成“发送事件”并不会自动避免覆盖。若多个监听器仍然随意修改同一份状态，变化来源反而可能更难追踪。

先分清三个概念：命令表达想做什么，例如搜索某个词；事件表达发生了什么，例如某次搜索已完成；状态表达当前应展示什么。系统还需要一个明确的状态所有者，决定哪些事件能被接受。

最常见的竞态来自完成顺序

用户先搜索“React”，随后改成“Vue”。第二次请求先返回，页面显示 Vue；第一次较慢，之后才返回，又把结果改成 React。

两个请求都可能成功，问题不在网络错误，而在于旧请求的结果已经不适合当前意图。每次发起时分配请求身份，并在提交状态前核对它，可以把“返回了数据”与“允许更新界面”区分开。

取消旧请求有助于节省资源，但不能只依赖取消：某些数据源不支持信号，或者结果已经到达、仍在等待处理，仍需要过期结果检查。

一个只接受最新搜索结果的控制器

load 是应用提供的数据加载函数，接收关键词与 AbortSignal；dispatch 接收下列内部事件，再交给状态存储或 reducer。它不是这里隐含调用的某个外部库 API。

JavaScript
function createSearchController(load, dispatch) {
  if (typeof load !== 'function' || typeof dispatch !== 'function') {
    throw new TypeError('加载和事件接收器必须是函数');
  }
  let sequence = 0;
  let active = null;
  let disposed = false;

  return {
    async search(keyword) {
      if (disposed) throw new Error('搜索控制器已销毁');
      active?.controller.abort();

      const requestId = ++sequence;
      const controller = new AbortController();
      active = { requestId, controller };
      const isCurrent = () => !disposed && !controller.signal.aborted && requestId === sequence;
      dispatch({ type: 'start', requestId, keyword });

      let data;
      try {
        controller.signal.throwIfAborted();
        data = await load(keyword, controller.signal);
      } catch (error) {
        if (isCurrent()) {
          dispatch({ type: 'fail', requestId, message: String(error?.message ?? error) });
        }
        return;
      } finally {
        if (active?.requestId === requestId) active = null;
      }

      if (isCurrent()) dispatch({ type: 'succeed', requestId, data });
    },
    cancel() {
      if (!active || disposed) return;
      const { requestId, controller } = active;
      sequence += 1;
      active = null;
      controller.abort();
      dispatch({ type: 'cancel', requestId });
    },
    dispose() {
      disposed = true;
      sequence += 1;
      active?.controller.abort();
      active = null;
    },
  };
}

新搜索会请求取消旧操作，但即使 load 忽略信号、旧结果仍返回，也不会发出可更新当前界面的 succeed。旧请求的失败也不会把新页面变成错误状态。

finally 只清理属于当前实例的活动引用，不会由旧请求无条件清空新请求的状态。cancel 用于用户主动取消并通知状态层；dispose 用于所属组件结束，不再向已销毁界面发送更新。

load 仍要负责检查 HTTP 状态、解析与验证数据。这里不会把 fetch 的 404 自动转换成失败，也不会回滚服务端操作。调用者还应处理自己的 dispatch 或其他编程错误造成的拒绝。

事件身份和业务版本不是同一件事

示例中的 requestId 是这个控制器内部的请求身份，用于判断哪个搜索更新了当前意图。它不是跨标签、跨设备的全局版本号，也不证明数据库中的记录比较新。

订单、草稿等实体的同步可能需要实体 ID、服务端版本、操作 ID 和协议版本。时间戳可以帮助日志分析，却不能独自保证所有设备上的更新顺序。

收到重复的“需要刷新列表”通常可以通过合并刷新安全处理；重复的“执行扣款”则不能只靠前端忽略第二条消息保证安全。应把通知事实与发起副作用的命令区分开，并由相应业务层实现幂等。

不同事件机制的执行语义也不同

DOM 的 dispatchEvent 会同步调用相应监听器，不是自动把它们放进异步队列。一个很重的监听器仍会阻塞调用过程；async 监听器返回的 Promise 也不会被 dispatchEvent 自动等待。

它的布尔返回值主要反映可取消事件是否被取消，不代表业务任务成功。监听器里抛出的异常也不按普通直接函数调用那样传播回 dispatchEvent 的调用者，所以不能把外层 try/catch 当成所有监听器的错误汇总。

跨 Web Component 边界的 CustomEvent 还需要考虑 bubbles、composed、detail 的结构与监听清理。它适合明确的 DOM 通信边界，但不是一种天然可靠、持久、有顺序保证的业务消息系统。

让状态写入路径保持可追踪

组件间简单的父子通信优先使用清楚的参数与回调；跨页面共享数据可以由明确的存储层负责。事件机制有价值时，应说明谁产生事件、谁拥有状态、谁执行副作用、谁负责错误与取消。

不要让任何模块都能监听一个模糊的 change 事件，再各自修改全局对象。可以使用有语义的事件类型、集中的状态转换、必要的操作关联信息和少量边界日志，让一次用户动作的影响能够被解释。

事件驱动不是消除依赖，而是把依赖放到协议和订阅关系中。协议越隐蔽，越需要治理；对于简单流程，直接调用一个明确的函数可能更容易维护。
