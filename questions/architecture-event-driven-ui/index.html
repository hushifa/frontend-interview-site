事件驱动 UI 怎样避免状态互相覆盖？

设计事件、命令和状态更新边界，处理异步完成顺序、重复事件和过期响应。

参考答案

事件、命令和状态解决的是三件不同的事。事件描述已经发生的事实，例如 cart.itemAdded；命令描述调用方希望系统做什么，例如 cart.addItem；状态描述当前结果，例如购物车里有哪些商品。把三者都写成“字符串 + 任意 payload”，调用方就很难知道谁会处理、处理几次，以及处理结果由谁负责。

异步流程最容易出现过期响应覆盖新状态。比如用户连续输入两个搜索词，第二次请求可能先返回；如果只在回调里直接写入结果，第一次请求随后返回时就会把页面改回旧内容。可以给每次任务分配请求 ID，只有仍属于当前查询的响应才能提交：

JavaScript
let activeRequest = 0;

async function search(keyword) {
  const requestId = ++activeRequest;
  const result = await fetchResults(keyword);
  if (requestId !== activeRequest) return;
  renderResults(result);
}

事件处理器还要考虑重复投递、取消和失败重试。能安全重复执行的操作应设计成幂等；不能重复的写操作要由服务端提供幂等键或状态查询。事件对象最好带上实体 ID、发生时间或版本，日志中也要能追踪一次操作经过了哪些模块。

跨组件通信优先使用明确的 props、状态存储或路由契约。CustomEvent 适合 Web Components 或明确的 DOM 边界，但把它当成整个应用的隐形总线，会让依赖关系、测试和错误定位越来越困难。架构选择还要考虑团队边界、回滚、监控和迁移成本。
