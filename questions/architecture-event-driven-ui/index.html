事件驱动 UI 怎样避免状态互相覆盖？

改成发事件并不能自动避免覆盖，要区分命令、事件与状态所有者。用可取消的最新搜索控制器给每次请求一个身份，丢弃过期结果，并弄清重复事件、DOM 事件和隐式总线的边界。

参考答案

简答

把代码改成“发事件、收事件”，并不会自动解决状态互相覆盖。如果好几个监听器都能随手改同一份状态，问题反而更难查。

关键是分清三样东西：命令是“我想做什么”，事件是“已经发生了什么”，状态是“现在界面上显示什么”。每份状态只有一个所有者负责更新，别人只能发事件给它。

最常见的覆盖是竞态：旧请求比新请求晚返回，把新结果盖掉了。解决办法是给每次请求一个身份，写入结果前先核对它还是不是最新的那次。取消旧请求能省资源，但过期检查不能省，因为有的数据源根本不理会取消。

还要注意，DOM 的 dispatchEvent 是同步调用监听器的，不会等异步监听器跑完，它也不是一个可靠的业务消息系统。

旧结果怎么会盖掉新结果

用户先搜“React”，紧接着改成“Vue”。Vue 的请求先返回，页面显示 Vue；React 的请求后返回，又把页面改回了 React。

两个请求都成功了，代码也没报错。问题在于，React 的结果返回时，已经不是用户想看的东西了。

只接受最新结果的控制器

下面这个控制器负责发起搜索。load 是应用提供的加载函数，接收关键词和 AbortSignal；dispatch 接收事件，交给状态的所有者，比如一个 reducer。阅读时重点看 isCurrent 在哪里被检查。

JavaScript
function createSearchController(load, dispatch) {
  if (typeof load !== 'function' || typeof dispatch !== 'function') {
    throw new TypeError('加载和事件接收器必须是函数');
  }
  let sequence = 0;
  let active = null;
  let disposed = false;

  return {
    async search(keyword) {
      if (disposed) throw new Error('搜索控制器已销毁');
      active?.controller.abort();

      const requestId = ++sequence;
      const controller = new AbortController();
      active = { requestId, controller };
      const isCurrent = () => !disposed && !controller.signal.aborted && requestId === sequence;
      dispatch({ type: 'start', requestId, keyword });

      let data;
      try {
        controller.signal.throwIfAborted();
        data = await load(keyword, controller.signal);
      } catch (error) {
        if (isCurrent()) {
          dispatch({ type: 'fail', requestId, message: String(error?.message ?? error) });
        }
        return;
      } finally {
        if (active?.requestId === requestId) active = null;
      }

      if (isCurrent()) dispatch({ type: 'succeed', requestId, data });
    },
    cancel() {
      if (!active || disposed) return;
      const { requestId, controller } = active;
      sequence += 1;
      active = null;
      controller.abort();
      dispatch({ type: 'cancel', requestId });
    },
    dispose() {
      disposed = true;
      sequence += 1;
      active?.controller.abort();
      active = null;
    },
  };
}

先看最关心的情况：新搜索开始时会取消旧请求。可如果 load 不理会信号，旧结果照样返回了呢？这时 isCurrent() 会发现 requestId 已经不是最新的，直接不派发，界面不受影响。同样，旧请求失败了，也不会把新页面变成错误状态。

finally 里只在 active 还属于自己时才清空它。因为新请求可能已经把 active 换成了自己的，旧请求不能误清。

cancel 和 dispose 用途不同。cancel 是用户主动取消，会通知状态层回到取消后的状态；dispose 用在组件卸载时，之后不再发送任何事件，再调用 search 会直接报错。

状态层可以配合《怎样避免加载、成功和失败状态互相矛盾？》里的 reduceRequest，它同样按 requestId 拒绝过期事件，相当于两边各守一道。

请求身份不是业务版本

requestId 只在这个控制器内部有意义，用来判断哪次搜索代表用户当前的意图。如果要跨标签页、跨设备同步订单或草稿，就需要实体 ID、服务端版本号这类东西，光靠时间戳没法保证顺序。

重复事件也要分情况看。重复收到“刷新列表”，合并成一次处理就行。重复收到“执行扣款”，就不能只靠前端忽略第二条，必须由服务端用幂等键保证同一笔只扣一次。

DOM 事件能当消息总线吗

dispatchEvent 的行为和很多人想的不一样，有几点要记住。

它是同步的，会依次调用所有监听器，监听器里做了重活，调用方就会被卡住。如果监听器是 async 函数，它返回的 Promise 不会被等待。dispatchEvent 的返回值只表示这个可取消的事件有没有被 preventDefault()，不代表业务成功了。监听器抛出的异常会被报告到全局错误处理，不会传回给调用 dispatchEvent 的地方。

所以它适合通知“发生了什么”，不适合当可靠的业务消息系统。跨 Web Component 通信用 CustomEvent 时，还要考虑 bubbles、composed 和 detail 的结构。

怎样让状态写入可追踪

简单的父子通信，优先用参数和回调。确实需要事件时，要说清楚谁产生事件、谁拥有状态、谁执行副作用。

最要避免的是一个含义模糊的全局 change 事件，被到处监听、到处修改状态。出了问题，你根本不知道是谁改的。

常见追问

为什么不直接在 then 里判断输入框的当前值？

这可以当作简化做法。但如果两次请求关键词相同，比如用户点了刷新，就区分不出哪次是最新的。用请求编号更可靠。

用 RxJS 的 switchMap 能解决吗？

可以。它在新值到来时会取消订阅旧的内部 Observable，本质上也是“只保留最新的请求”。
