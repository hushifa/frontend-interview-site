事件驱动 UI 怎样避免状态互相覆盖？

区分命令、事件与状态所有者，用可取消的最新搜索控制器解释请求身份和过期结果，并说明重复事件、DOM 事件及隐式总线的边界。

参考答案

简答

  • 改成"发送事件"不会自动避免状态覆盖；多个监听器随意修改同一份状态，问题只会更难追踪。
  • 区分命令（想做什么）、事件（发生了什么）和状态（当前展示什么），每份状态只有一个所有者负责更新。
  • 最常见的竞态是旧请求晚返回覆盖新结果，要给每次请求分配身份，提交结果前核对是否仍是最新请求。
  • 取消旧请求能节省资源，但仍要做过期检查，因为有的数据源不响应取消。
  • DOM 的 dispatchEvent 同步调用监听器，不等待异步监听器，也不是可靠的业务消息系统。

竞态示例

用户先搜"React"，紧接着改成"Vue"。Vue 的请求先返回，页面显示 Vue；React 的请求后返回，又把结果改回 React。两个请求都成功，问题在于旧结果已经不符合用户当前的意图。

只接受最新结果的控制器

load 是应用提供的加载函数，接收关键词和 AbortSignal；dispatch 接收事件并交给状态所有者（如 reducer）。

JavaScript
function createSearchController(load, dispatch) {
  if (typeof load !== 'function' || typeof dispatch !== 'function') {
    throw new TypeError('加载和事件接收器必须是函数');
  }
  let sequence = 0;
  let active = null;
  let disposed = false;

  return {
    async search(keyword) {
      if (disposed) throw new Error('搜索控制器已销毁');
      active?.controller.abort();

      const requestId = ++sequence;
      const controller = new AbortController();
      active = { requestId, controller };
      const isCurrent = () => !disposed && !controller.signal.aborted && requestId === sequence;
      dispatch({ type: 'start', requestId, keyword });

      let data;
      try {
        controller.signal.throwIfAborted();
        data = await load(keyword, controller.signal);
      } catch (error) {
        if (isCurrent()) {
          dispatch({ type: 'fail', requestId, message: String(error?.message ?? error) });
        }
        return;
      } finally {
        if (active?.requestId === requestId) active = null;
      }

      if (isCurrent()) dispatch({ type: 'succeed', requestId, data });
    },
    cancel() {
      if (!active || disposed) return;
      const { requestId, controller } = active;
      sequence += 1;
      active = null;
      controller.abort();
      dispatch({ type: 'cancel', requestId });
    },
    dispose() {
      disposed = true;
      sequence += 1;
      active?.controller.abort();
      active = null;
    },
  };
}
  • 新搜索会取消旧请求；即使 load 忽略信号、旧结果照样返回，isCurrent() 也会阻止它更新界面。
  • 旧请求失败不会把新页面变成错误状态。
  • finally 只清理属于自己的 active，不会误清新请求。
  • cancel 用于用户主动取消并通知状态层；dispose 用于组件卸载，之后不再发送任何事件。
  • 状态层可以配合《怎样避免加载、成功和失败状态互相矛盾？》中的 reduceRequest，它同样按 requestId 拒绝过期事件。

请求身份不是业务版本

requestId 只在这个控制器内部有意义，用来判断哪次搜索代表当前意图。跨标签页、跨设备同步订单或草稿时，需要实体 ID、服务端版本号等，时间戳不能独自保证顺序。

重复收到"刷新列表"可以合并处理；重复收到"执行扣款"不能只靠前端忽略第二条，必须由服务端通过幂等键保证。

DOM 事件的语义

  • dispatchEvent 同步依次调用监听器，重的监听器会阻塞调用方。
  • async 监听器返回的 Promise 不会被等待。
  • 返回值只表示可取消事件是否被 preventDefault()，不代表业务成功。
  • 监听器抛出的异常会被报告到全局错误处理，不会传回 dispatchEvent 的调用方。

跨 Web Component 通信时，CustomEvent 还要考虑 bubbles、composed 和 detail 的结构。

让状态写入可追踪

简单的父子通信优先用参数和回调；需要事件时，明确谁产生事件、谁拥有状态、谁执行副作用。避免一个模糊的全局 change 事件被到处监听、到处修改。

常见追问

  • 为什么不直接在 then 里判断输入框当前值？可以作为简化做法，但关键词相同的两次请求（例如刷新）就无法区分，请求编号更可靠。
  • 用 RxJS 的 switchMap 能解决吗？可以，它在新值到来时取消订阅旧的内部 Observable，本质也是"只保留最新请求"。
