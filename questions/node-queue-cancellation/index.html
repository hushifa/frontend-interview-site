消息队列任务怎样设计取消、超时、确认和重试？

从导出、转码和通知等后台任务出发，区分请求取消、任务取消、消息确认和业务回滚，说明 AbortSignal、租约、幂等键、重试和优雅排空如何协作。

参考答案

用户点击“导出报表”后，前端可能在几秒内关闭页面、修改筛选条件或点击取消。若服务端已经把任务放进持久化队列，简单地把 HTTP 连接断开并不能让任务自动消失；消费者可能已经取到消息，数据库写入也可能已经发生。要把这条链路设计可靠，首先要把几个容易混淆的概念分开。

概念表示什么能否自动撤销已经发生的副作用
请求取消调用方不再等待这次 HTTP 响应不能保证服务端停止任务
执行取消当前处理函数收到信号并主动停止只能影响仍支持协作式取消的工作
消息确认消费者告诉队列这条消息已处理或已接管不等于数据库事务自动提交或回滚
业务撤销领域状态明确记录“不要再继续”需要任务代码在关键阶段检查并遵守
回滚撤销同一事务中的数据库变更不能撤销已经发送的邮件、外部 API 写入或文件上传

HTTP 断开时不要直接删除任务

提交后台任务的接口通常只负责校验输入、保存任务记录和把消息放入可靠队列，然后返回任务 ID。客户端断开时，可以把“客户端不再等待”记录到日志或取消意图中，但是否真的取消要由任务类型决定：

JavaScript
import { randomUUID } from 'node:crypto';

export async function createExport(request, response, repository, queue) {
  const taskId = randomUUID();
  const input = await readAndValidateJson(request);

  await repository.insertTask({
    id: taskId,
    status: 'queued',
    input,
    requestedAt: new Date(),
  });

  await queue.publish({
    type: 'export.requested',
    taskId,
    schemaVersion: 1,
  });

  response.writeHead(202, { 'content-type': 'application/json' });
  response.end(JSON.stringify({ taskId, status: 'queued' }));
}

202 Accepted 表示服务端接受了异步处理请求，不表示报表已经生成。消息发布和任务记录必须有明确的一致性方案：如果先写数据库后发布消息，发布失败会留下“排队中但无人处理”的任务；如果先发布再写数据库，消费者可能先查不到任务。生产实现可以使用事务性 outbox、队列与数据库的原子能力，或由可靠的补偿任务扫描异常状态，不能只依赖两个独立的 await。

AbortSignal 需要贯穿同一执行链

如果任务只对当前请求有意义，AbortSignal 可以传给仍在等待的下游操作：

JavaScript
async function loadReportData(task, signal) {
  signal.throwIfAborted();

  const response = await fetch(task.dataUrl, {
    signal,
    headers: { accept: 'application/json' },
  });
  if (!response.ok) {
    throw new Error(`下游返回 HTTP ${response.status}`);
  }

  const data = await response.json();
  signal.throwIfAborted();
  return data;
}

只在最外层创建 controller、却不把 signal 传给 fetch、数据库驱动、文件流或自定义循环，实际上没有完成取消。AbortSignal 也不会强行中断任意同步 JavaScript；CPU 密集循环需要在可接受的检查点主动检查信号，外部库不支持取消时只能等待、隔离到可终止的 Worker，或让任务继续完成后丢弃结果。

取消发生在 fetch 已经把请求发送出去之后，也不能保证远端没有处理请求。对于写入、扣款和创建资源，客户端取消只能停止等待，不能被解释成业务撤销。需要撤销时应设计独立的取消命令和领域状态，例如“生成任务取消请求”，由消费者在安全边界检查后决定是否停止。

消费消息时先建立租约，再决定确认时机

队列通常采用至少一次投递：消费者处理过程中崩溃，消息可能重新出现。一个通用的消费者状态可以是 queued → running → succeeded/failed/canceled，并为运行中的任务设置租约或可见性超时：

JavaScript
async function consume(message, repository, runExport, signal) {
  const { taskId } = parseMessage(message);
  const task = await repository.claimTask(taskId, {
    leaseMs: 30_000,
  });

  if (!task || task.status === 'succeeded' || task.status === 'canceled') {
    return { acknowledge: true };
  }

  try {
    await runExport(task, signal);
    await repository.markSucceeded(taskId, { finishedAt: new Date() });
    return { acknowledge: true };
  } catch (error) {
    if (signal.aborted || error?.name === 'AbortError') {
      await repository.markCanceled(taskId, { reason: signal.reason });
      return { acknowledge: true };
    }

    await repository.recordAttemptFailure(taskId, summarize(error));
    return { acknowledge: false };
  }
}

示例中的 acknowledge: false 代表交给队列的重投递策略；不同队列的 API 和语义不同，不能把这个对象直接当成某个厂商 SDK 的可运行代码。确认太早会在进程崩溃后丢任务，确认太晚则会使消息超时重复投递。消费者必须能承受同一任务同时被两个实例短暂处理，租约续期、版本条件更新和幂等状态转换要一起设计。

claimTask 不能只是“先查询再更新”两步无条件操作。应使用数据库事务、条件更新或锁，让只有一个消费者能把同一版本从 queued 改为 running。租约过期后的接管也要检查版本和持有者，旧消费者恢复后不能继续覆盖新消费者的结果。

幂等是重试的前提

网络超时、进程崩溃和确认响应丢失都会造成“业务可能成功，但消费者不知道”的状态。此时重新投递是正常的，不能简单把重试次数当成重复执行的安全保证。任务应使用稳定的操作 ID 或幂等键：

JavaScript
async function saveExportResult(repository, taskId, artifact) {
  return repository.transaction(async (tx) => {
    const task = await tx.getTaskForUpdate(taskId);
    if (task.status === 'succeeded') return task.result;
    if (task.status === 'canceled') throw new Error('任务已取消');

    await tx.insertArtifactIfAbsent({
      idempotencyKey: `export:${taskId}`,
      taskId,
      location: artifact.location,
    });
    await tx.markSucceeded(taskId, { result: artifact.location });
    return artifact.location;
  });
}

这个事务可以防止同一个任务重复登记结果，但它不能撤销已经发出的邮件、第三方支付请求或对象存储上传。外部副作用应使用幂等键、可查询状态、outbox 或补偿流程。生成文件时可以先写临时对象，数据库确认后再以原子命名或版本标记发布，避免用户看到半成品。

取消命令必须有版本和权限

取消接口不应只接受一个任务 ID 就把任意任务标成取消。服务端要验证当前用户、租户、任务版本和可取消状态；已经成功或进入不可逆外部副作用阶段的任务，可能只能标记“取消请求已收到”，而不能承诺完全撤销：

JavaScript
async function requestCancel(user, taskId, repository, queue) {
  const task = await repository.requestCancelIfAllowed({
    taskId,
    ownerId: user.id,
    allowedStatuses: ['queued', 'running'],
  });

  if (!task) {
    return { status: 'unchanged' };
  }

  await queue.publish({
    type: 'task.cancel-requested',
    taskId,
    taskVersion: task.version,
  });
  return { status: 'cancel-requested' };
}

消费者处理取消消息时要比较版本，不能让旧的取消事件覆盖后来重新提交的新任务。取消状态和执行状态最好由同一状态机约束，避免出现数据库显示 canceled、但消费者仍发布成功结果的竞态。即使取消命令返回成功，响应也应说明是“已请求取消”还是“已确认未执行”，不要模糊地承诺副作用已经消失。

超时、重试和死信要按错误类型区分

超时是一个截止时间，不等于任务失败原因。可以把错误分为：

  • 可暂时恢复的网络错误、限流和服务端 5xx：使用有上限的指数退避和随机抖动；
  • 参数错误、权限拒绝和资源不存在：通常不应无限重试，应尽快标记失败并通知用户；
  • 取消或过期任务：确认消息、停止后续工作，不要把用户主动取消记成系统故障；
  • 代码 bug、数据损坏和未知异常：记录脱敏诊断，进入死信或人工处理队列。

每次重试都要增加尝试次数、下次执行时间和原因，设置任务总截止时间。只设置“最多重试 3 次”而没有全局时间、队列容量和死信处理，仍可能在高峰时造成重试风暴。错误日志要避免输出令牌、完整任务输入和个人数据。

优雅退出要停止接新消息并排空正在处理的任务

收到 SIGTERM 后，消费者通常应先停止拉取新消息，再给当前任务一个有限时间完成或协作取消；不能立即确认所有消息，也不能无限等待一个不支持取消的下游：

JavaScript
let accepting = true;
const running = new Set();

async function onMessage(message) {
  if (!accepting) return requeue(message);

  const controller = new AbortController();
  const job = consume(message, repository, runExport, controller.signal)
    .finally(() => running.delete(job));
  running.add(job);
  return job;
}

async function shutdown() {
  accepting = false;
  await stopConsuming();

  const deadline = AbortSignal.timeout(10_000);
  await Promise.race([
    Promise.allSettled([...running]),
    new Promise((resolve) => deadline.addEventListener('abort', resolve, { once: true })),
  ]);
  await closeDatabaseAndQueue();
}

示例只是生命周期示意，真实实现还要保存每个 controller，截止时向仍在运行的任务发出协作取消，并让队列根据确认结果重新投递未完成消息。Promise.race 返回后不代表另一组任务自动停止；关闭数据库前必须明确它们是完成、取消、重新入队还是失败。平台的 termination grace period、readiness 摘除延迟和消费者租约时间也要一起配置。

可靠的后台任务系统不追求“取消按钮一按，所有代码立刻消失”。它要让用户看到真实状态，让仍可取消的工作尽快停止，让已经发生的副作用可查询、可重试或可补偿，并用幂等和版本条件承受重复投递。AbortSignal 是执行层的协作信号，队列确认是投递层协议，数据库事务和业务状态机才是结果可信度的基础。
