消息队列任务怎样设计取消、超时、确认和重试？

以前端触发的报表导出为例，说明异步任务的提交与查询接口、至少一次投递下的幂等处理、处理完成后再确认消息、用持久化状态实现取消、有上限的退避重试和死信队列，以及任务记录与消息发布之间的一致性。

参考答案

简答

  • 提交接口只校验输入、写任务记录、投递消息，然后返回 202 和任务 ID；前端轮询或订阅任务状态，HTTP 连接断开不会停止后台任务。
  • 主流队列提供至少一次投递，同一条消息可能被处理多次，消费者要用任务 ID 做幂等，副作用写入前检查是否已完成。
  • 消息在业务处理完成后才确认；消费者崩溃或超时未确认时，队列会重新投递。
  • 取消是写进数据库的任务状态，消费者在每个阶段开始前检查；AbortSignal 只能停止当前进程里还在等待的操作，撤销不了已经发出的邮件或外部写入。
  • 可重试的错误按退避重试并设次数上限，超过上限或不可重试的错误进入死信队列，等人工处理。

提交与查询

JavaScript
export async function createExport(input, { db, outbox }) {
  const taskId = crypto.randomUUID();
  await db.transaction(async (tx) => {
    await tx.insert('tasks', { id: taskId, status: 'queued', input });
    // 与任务记录在同一个事务里写入待发送消息，由后台进程投递到队列。
    await outbox.add(tx, { type: 'export.requested', taskId });
  });
  return { status: 202, body: { taskId, status: 'queued' } };
}

如果先写数据库再单独发布消息，发布失败会留下"排队中但没人处理"的任务；先发布再写数据库，消费者可能查不到记录。事务性 outbox 把消息先写进同一个数据库事务，再由独立进程可靠地投递，避免两者不一致。

前端拿到任务 ID 后查询 GET /exports/:id，显示 queued、running、succeeded、failed、cancelled 等状态。

消费者

JavaScript
async function handleExport(message, { db, storage, signal }) {
  const task = await db.find('tasks', message.taskId);
  if (!task || ['succeeded', 'cancelled'].includes(task.status)) return 'ack';
  if (task.status === 'cancel_requested') {
    await db.update('tasks', task.id, { status: 'cancelled' });
    return 'ack';
  }

  // 条件更新：只在状态仍是 queued 或 running（崩溃后重新投递）时写入，
  // 不会覆盖期间并发写入的 cancel_requested；没写成就按新状态重新判断。
  const claimed = await db.updateWhere(
    'tasks',
    { id: task.id, status: ['queued', 'running'] },
    { status: 'running' },
  );
  if (!claimed) return handleExport(message, { db, storage, signal });

  const rows = await loadRows(task.input, signal);
  if ((await db.find('tasks', task.id)).status === 'cancel_requested') {
    await db.update('tasks', task.id, { status: 'cancelled' });
    return 'ack';
  }

  // 以任务 ID 作为对象名，重复执行只会覆盖同一个文件。
  await storage.put(`exports/${task.id}.csv`, toCsv(rows));
  await db.update('tasks', task.id, { status: 'succeeded' });
  return 'ack';
}

要点：

  • 幂等：开头检查任务是否已完成；输出文件用任务 ID 命名，重复处理不会产生两份结果。发邮件这类不可覆盖的副作用，要先记录"已发送"再确认消息，或者让下游接口接受幂等键。
  • 确认时机：函数返回 ack 后才确认消息。处理到一半进程崩溃，消息会重新投递，从头再做一遍。
  • 取消检查点：开始前和耗时阶段之间都检查任务状态，写入 running 用条件更新，避免把已请求的取消覆盖掉。用户点击取消只是把状态改成 cancel_requested，消费者在下一个检查点停下来。
  • 超时：队列的确认超时（或可见性超时）要大于正常的处理时间，否则消息会在处理中途被投递给另一个消费者。耗时长的任务需要定期延长租约。

重试与死信

错误类型处理
下游 503、网络超时指数退避加随机抖动后重试，例如最多 5 次
输入不合法、数据不存在不重试，任务标记为 failed，确认消息
超过重试上限进入死信队列，告警后人工排查

重试次数记录在消息头或任务记录里，不能依赖消费者进程的内存，因为每次重试可能由不同的进程处理。

优雅关闭

消费者进程收到 SIGTERM 时，先停止拉取新消息，等已取出的消息处理完并确认，再关闭连接。超过截止时间仍未完成的消息不确认，交给队列重新投递，靠幂等保证结果正确。HTTP 服务的关闭流程见《Node.js 服务如何实现优雅退出？》。

常见追问

  • 能做到恰好一次吗？ 投递层面通常做不到。实际做法是"至少一次投递加幂等处理"，让多次处理的结果和一次相同。
  • 前端怎样得知任务完成？ 轮询状态接口最简单；需要即时性时用 SSE 或 WebSocket 推送，推送只是通知，最终状态以查询接口为准。
