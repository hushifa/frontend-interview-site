前端怎样测试定时器、重试和超时，避免 Fake Timers 造成假通过？

vi.useFakeTimers 替换 setTimeout、Date 等时间 API，用 advanceTimersByTimeAsync 推进时间。推进时间要用异步版本，让 Promise 回调有机会执行；测试结束后恢复真实计时器。

参考答案

简答

测重试、超时这类逻辑时，不可能真的等几秒钟，所以要用假时钟。vi.useFakeTimers() 会把 setTimeout、setInterval、setImmediate、Date 等换成假的，时间由测试手动往前拨；默认不替换 process.nextTick 和 queueMicrotask。

最容易踩的坑是同步推进。vi.advanceTimersByTime() 只会触发到期的定时器，可是定时器回调里如果有 await，后面的代码排在微任务里，还没来得及跑时间就推完了。所以要用 advanceTimersByTimeAsync()，让 Promise 回调跟着一起执行。

还有两个相关的 API。vi.runAllTimersAsync() 会一直执行到没有定时器为止，遇到无限轮询会在循环上限（默认 10000 次）后抛错，所以轮询逻辑应该按时间推进。vi.setSystemTime() 只改当前时间，不触发定时器，适合测“过期”“今天”这类逻辑。

最后，每个测试结束后要调用 vi.useRealTimers()，不然后面的测试会继承这个假时钟。

怎样测一个带退避的重试函数

下面的函数失败后会等一段时间再试，每次等待时间翻倍，第一次等 1000ms，第二次等 2000ms：

TypeScript
async function fetchWithRetry(load: () => Promise<string>, retries = 2, delay = 1000) {
  for (let attempt = 0; ; attempt++) {
    try {
      return await load();
    } catch (error) {
      if (attempt >= retries) throw error;
      await new Promise((resolve) => setTimeout(resolve, delay * 2 ** attempt));
    }
  }
}

测试让 load 前两次失败、第三次成功，然后一点点拨时间，检查每个时刻调用了几次：

TypeScript
import { afterEach, beforeEach, expect, test, vi } from 'vitest';

beforeEach(() => vi.useFakeTimers());
afterEach(() => vi.useRealTimers());

test('失败两次后在第三次成功', async () => {
  const load = vi.fn()
    .mockRejectedValueOnce(new Error('a'))
    .mockRejectedValueOnce(new Error('b'))
    .mockResolvedValue('ok');

  const result = fetchWithRetry(load);

  await vi.advanceTimersByTimeAsync(999);
  expect(load).toHaveBeenCalledTimes(1);

  await vi.advanceTimersByTimeAsync(1);
  expect(load).toHaveBeenCalledTimes(2);

  await vi.advanceTimersByTimeAsync(2000);
  await expect(result).resolves.toBe('ok');
  expect(load).toHaveBeenCalledTimes(3);
});

拨到 999ms 时还只调用了 1 次，再拨 1ms 正好到 1000ms，第二次调用发生。这样连等待时间是不是刚好 1000ms 都验证到了。

如果把 advanceTimersByTimeAsync 换成同步的 advanceTimersByTime，调用次数就会对不上。原因是 load 被拒绝以后，进入 catch、再创建新的 setTimeout，这些都要等微任务执行；同步推进不会让出执行权，时间已经推完了，新的定时器才刚刚创建。

测试重试全部失败时要注意什么

TypeScript
test('重试用尽后抛出最后一次错误', async () => {
  const load = vi.fn().mockRejectedValue(new Error('down'));
  const result = fetchWithRetry(load);
  const assertion = expect(result).rejects.toThrow('down');

  await vi.advanceTimersByTimeAsync(3000);
  await assertion;
});

这里先创建断言，再推进时间。顺序反过来会怎样？Promise 会在推进时间的过程中被拒绝，而那时还没有任何地方处理这个拒绝，就会报出未处理的拒绝。先写好断言，相当于提前挂上了处理器。

假时钟管不到什么

真实的网络请求、文件读写不受假时钟控制。如果测试还在等真实的 I/O，推进时间没有意义。浏览器的 requestAnimationFrame、动画时间线，在 jsdom 里通常要另外模拟。Playwright 的端到端测试里用 page.clock 控制页面时间，原理类似。

还要分清它证明了什么。假时钟证明的是“时间相关的逻辑写对了”，不能证明真实环境下超时设得合不合理，那要靠集成测试或线上监控。

常见追问

什么时候不用假时钟？

等待时间只有几十毫秒，或者逻辑依赖真实的事件循环，比如流式读取，这时直接用真实时间加 vi.waitFor 更简单。
