前端怎样测试定时器、重试和超时，避免 Fake Timers 造成假通过？

vi.useFakeTimers 替换 setTimeout、Date 等时间 API，用 advanceTimersByTimeAsync 推进时间；推进时间要用异步版本，让 Promise 回调有机会执行，测试结束后恢复真实计时器。

参考答案

简答

  • vi.useFakeTimers() 替换 setTimeout、setInterval、setImmediate、Date 等，默认不替换 process.nextTick 和 queueMicrotask。
  • 同步的 vi.advanceTimersByTime() 只触发到期的定时器；定时器回调里有 await 时，后续代码排在微任务里，要用 advanceTimersByTimeAsync() 才能一起推进。
  • vi.runAllTimersAsync() 一直执行直到没有定时器，无限轮询会在循环上限（默认 10000 次）后抛错，所以轮询测试应按时间推进。
  • vi.setSystemTime() 只修改当前时间，不触发定时器，适合测试“过期”“今天”这类逻辑。
  • 每个测试结束后调用 vi.useRealTimers()，否则后续测试会继承假时钟。

测试重试

TypeScript
async function fetchWithRetry(load: () => Promise<string>, retries = 2, delay = 1000) {
  for (let attempt = 0; ; attempt++) {
    try {
      return await load();
    } catch (error) {
      if (attempt >= retries) throw error;
      await new Promise((resolve) => setTimeout(resolve, delay * 2 ** attempt));
    }
  }
}
TypeScript
import { afterEach, beforeEach, expect, test, vi } from 'vitest';

beforeEach(() => vi.useFakeTimers());
afterEach(() => vi.useRealTimers());

test('失败两次后在第三次成功', async () => {
  const load = vi.fn()
    .mockRejectedValueOnce(new Error('a'))
    .mockRejectedValueOnce(new Error('b'))
    .mockResolvedValue('ok');

  const result = fetchWithRetry(load);

  await vi.advanceTimersByTimeAsync(999);
  expect(load).toHaveBeenCalledTimes(1);

  await vi.advanceTimersByTimeAsync(1);
  expect(load).toHaveBeenCalledTimes(2);

  await vi.advanceTimersByTimeAsync(2000);
  await expect(result).resolves.toBe('ok');
  expect(load).toHaveBeenCalledTimes(3);
});

如果把 advanceTimersByTimeAsync 换成同步的 advanceTimersByTime，load 被拒绝后的 catch 和新的 setTimeout 还没来得及执行，时间就已经推进完了，调用次数对不上。

测试全部失败

TypeScript
test('重试用尽后抛出最后一次错误', async () => {
  const load = vi.fn().mockRejectedValue(new Error('down'));
  const result = fetchWithRetry(load);
  const assertion = expect(result).rejects.toThrow('down');

  await vi.advanceTimersByTimeAsync(3000);
  await assertion;
});

先创建断言再推进时间。否则 Promise 在推进过程中被拒绝，而此时还没有任何处理器，会报出未处理的拒绝。

假时钟的边界

  • 真实的网络请求、文件读写不受假时钟控制，测试里还在等真实 I/O 时，推进时间没有意义。
  • 浏览器的 requestAnimationFrame、动画时间线在 jsdom 中通常需要单独模拟。
  • Playwright 端到端测试用 page.clock 控制页面里的时间，原理类似。
  • 假时钟证明的是“时间逻辑正确”，不能证明真实环境下的超时配置合理，后者需要集成测试或监控。

常见追问

  • 什么时候不用假时钟？等待时间只有几十毫秒、逻辑依赖真实事件循环（例如流式读取）时，用真实时间加 vi.waitFor 更简单。
