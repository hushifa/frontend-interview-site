Electron 应用要做哪些安全配置？nodeIntegration、contextIsolation、sandbox 和 CSP 分别防什么？

Electron 的渲染进程一旦出现 XSS，危害取决于它能拿到多少权限。保持 nodeIntegration 关闭、contextIsolation 和 sandbox 开启，用 CSP 限制脚本来源，用 will-navigate 和 setWindowOpenHandler 管住导航和新窗口，再用自定义协议、权限处理器和 Fuses 收紧其余入口。

参考答案

简答

在普通浏览器里，XSS 最多偷 Cookie、改页面；在 Electron 里，如果渲染进程能直接用 Node.js，同一个 XSS 就能在用户电脑上执行命令。所以安全配置的目标，是让渲染进程即使被攻破，也只有普通网页那点权限。

第一层是 webPreferences 的三个默认值不要改：nodeIntegration: false（5.0 起默认）让页面用不了 Node API；contextIsolation: true（12.0 起默认）让 preload 和页面分开运行，页面改不了 preload 里的对象；sandbox: true（20.0 起默认）用 Chromium 沙箱限制渲染进程。

第二层是限制页面能加载和跳转到哪里：用 CSP 限制脚本来源，用 will-navigate 阻止主窗口跳到外部页面，用 setWindowOpenHandler 拒绝新窗口，只把校验过的地址交给系统浏览器。

还要注意几处容易漏的地方：本地页面用自定义协议代替 file://，给会加载远程内容的 session 设置权限请求处理器，打包时用 Fuses 关掉 runAsNode 这类不需要的能力，并及时升级 Electron。

为什么要把渲染进程当成不可信的

渲染进程显示的内容，可能包含第三方脚本、用户写的富文本，或者加载了远程页面。只要出现一处 XSS，攻击者就能使用渲染进程里的所有能力。所以每项配置都在回答同一个问题：页面被注入脚本以后，它能做什么。

页面确实需要文件读写这类能力时，正确的做法是由 preload 暴露几个具体的函数，经 IPC 交给主进程执行，主进程再校验发送方和参数。接口怎样写、怎样校验，见《Electron 的 IPC 和 contextBridge 怎样设计？》。这里只讲窗口和应用层面的配置。

webPreferences 里的三个开关

JavaScript
const win = new BrowserWindow({
  webPreferences: {
    preload: path.join(__dirname, 'preload.js'),
    // 下面三项都是当前默认值，写出来是为了防止被改掉
    nodeIntegration: false,
    contextIsolation: true,
    sandbox: true,
  },
});

nodeIntegration 打开以后，页面脚本能直接 require('child_process')。官方要求任何加载远程内容的渲染进程都不能打开它。沙箱文档还说明，设置 nodeIntegration: true 会让这个渲染进程不再运行在沙箱里。

contextIsolation 让 preload 脚本和 Electron 的内部逻辑跑在独立的 JavaScript 上下文里。为什么关了 Node 集成还要它？因为如果两边共用一个上下文，页面可以改写 JSON.parse 这类全局对象，进而影响 preload 里的代码。官方还提醒，关掉上下文隔离会同时关掉沙箱，不管 sandbox 写的是什么。

sandbox 开启后，preload 里的 require 只能加载 electron 模块的一部分，比如 contextBridge、ipcRenderer，Node 内置模块和 Buffer 这类全局对象都用不了。所以文件读写只能放到主进程。

webSecurity 默认开启，不要在生产环境关掉。关掉它会去掉同源策略，还会把 allowRunningInsecureContent 一起打开，让 HTTPS 页面加载 HTTP 脚本。

用 CSP 限制脚本从哪里来

CSP（内容安全策略）告诉浏览器，页面只能从哪些地方加载脚本和其他资源。即使攻击者注入了一段 <script src="https://evil.example/x.js">，浏览器也会拒绝加载。

官方推荐通过 HTTP 响应头下发 CSP，在 Electron 里可以用 session.defaultSession.webRequest.onHeadersReceived 给响应加上这个头。用 file:// 加载的页面没有响应头，只能写在页面的 meta 标签里：

HTML
<meta http-equiv="Content-Security-Policy" content="default-src 'none'" />

规则要尽量严格。官方示例是 script-src 'self' https://apis.example.com，只允许本地和一个明确的接口域名，而不是 *。

管住导航和新窗口

主窗口被导航到外部页面以后，一个不受你控制的页面就运行在这个窗口里，还能用上这个窗口的 preload 暴露的接口。官方把导航列为常见的攻击途径。所以要在 web-contents-created 里统一给所有 webContents 加上限制：

JavaScript
app.on('web-contents-created', (_event, contents) => {
  contents.on('will-navigate', (event, navigationUrl) => {
    if (new URL(navigationUrl).origin !== 'app://bundle') {
      event.preventDefault();
    }
  });

  contents.setWindowOpenHandler(({ url }) => {
    const { protocol, hostname } = new URL(url);
    if (protocol === 'https:' && hostname === 'docs.example.com') {
      setImmediate(() => shell.openExternal(url));
    }
    return { action: 'deny' };
  });
});

为什么比较 origin，不用 startsWith('https://example.com')？因为 https://example.com.attacker.com 也以这个字符串开头。官方建议用 URL 解析器拆出 origin 再比较。

新窗口一律拒绝，只有明确允许的地址交给系统浏览器打开。这么严是因为 shell.openExternal 遇到不受信任的地址可能被利用来执行任意命令，官方要求不要把用户能控制的数据传给它。

示例里的 app://bundle 假设应用用自定义协议加载本地页面，实际使用时要和你的加载方式一致。

其他容易漏的入口

本地页面尽量不用 file:// 加载。官方说明，file:// 页面在 Electron 里有额外的权限，能读取电脑上的任意文件，一处 XSS 就可能泄露本地文件。改用 protocol.handle 注册自定义协议，只提供指定的一组文件。

Electron 默认会自动同意页面的权限请求，比如通知、摄像头。加载远程内容的 session 要用 ses.setPermissionRequestHandler() 自己判断，只批准确实需要的权限。

远程资源只通过 HTTPS、WSS 这类加密协议加载。experimentalFeatures 和 enableBlinkFeatures 默认关闭，官方要求不要凭猜测打开。

runAsNode、nodeCliInspect 这类 Fuse 允许通过环境变量或命令行参数改变应用行为，别的程序可以借此用你的应用的权限执行命令。打包时用 @electron/fuses 关掉不需要的。

最后，及时升级 Electron。它内置的 Chromium 会持续修复安全漏洞，官方建议每次升一个大版本。

常见追问

打开 nodeIntegration 有多危险？

页面脚本可以直接使用 Node.js API，这个渲染进程也不再运行在沙箱里。渲染进程里任何一个 XSS 都能读写文件、执行系统命令。

已经关了 nodeIntegration，为什么还要 contextIsolation？

因为没有上下文隔离时，页面和 preload 共用全局对象。页面可以改写 JSON.parse 这类内置方法，让 preload 里的代码按攻击者的意思执行。关掉上下文隔离还会让沙箱失效。

preload 里能用 Node API 吗？

开启沙箱后不能。preload 的 require 只能加载 electron 模块的一部分，Node 内置模块都不可用，文件读写这类操作应该放到主进程。
