Electron 应用的主进程、渲染进程和 IPC 有哪些安全边界？

Electron 主进程有系统权限，渲染进程只应有普通网页的权限。要靠 preload、contextIsolation、沙箱和 IPC 校验守住两者的边界，谨慎处理远程内容和外部链接，不能把桌面应用当成普通浏览器页面。

参考答案

简答

Electron 应用里有两种权限差别很大的进程。主进程运行 Node.js，能读写文件、执行命令；渲染进程显示网页，应该只有普通网页那点权限。安全的关键，就是不让渲染进程拿到主进程的能力。

页面需要特权操作时，由 preload 脚本用 contextBridge 暴露几个明确的函数，再经 IPC 交给主进程执行。默认的安全设置要保持住：nodeIntegration: false（5.0 起默认）、contextIsolation: true（12.0 起默认）、sandbox: true（20.0 起默认）。

主进程要把渲染进程当成不可信的，校验每条 IPC 消息的发送方（senderFrame 的 origin）和参数。

另外要管住新窗口和外部链接：用 setWindowOpenHandler 拦截新窗口，交给系统浏览器打开之前先校验协议和地址；打包时用 Fuses 关掉 runAsNode 等不需要的能力。

为什么要把渲染进程当成不可信的

渲染进程显示的内容，可能包含第三方脚本、用户写的富文本，或者加载了远程页面。只要出现一处 XSS，攻击者就能使用渲染进程里的所有能力。

在普通浏览器里，XSS 最多偷 Cookie、改页面。可在 Electron 里，如果渲染进程能直接 require('child_process')，同样一个 XSS 就变成了在用户电脑上执行任意命令。所以渲染进程的能力越小越好。

preload 只暴露最小能力

JavaScript
// preload.js
const { contextBridge, ipcRenderer } = require('electron');

contextBridge.exposeInMainWorld('api', {
  saveNote: (id, text) => ipcRenderer.invoke('note:save', { id, text }),
});

页面只能调用 window.api.saveNote，别的什么都做不了。如果暴露的是 ipcRenderer 本身，或者一个通用的 invoke(channel, ...args)，页面就能调用任意通道，等于没设防。

contextIsolation 让 preload 和页面运行在不同的 JavaScript 上下文里，页面没法篡改 preload 里的对象。

主进程怎样校验发送方和参数

preload 限制了页面能调什么，但主进程不能因此就相信收到的消息。下面的 handler 先查发送方，再查参数：

JavaScript
// main.js
const { ipcMain, app } = require('electron');
const path = require('node:path');
const fs = require('node:fs');

const ALLOWED_ORIGINS = new Set(['app://bundle']);

function isTrustedSender(event) {
  const frame = event.senderFrame;
  return frame !== null && ALLOWED_ORIGINS.has(frame.origin);
}

ipcMain.handle('note:save', async (event, payload) => {
  if (!isTrustedSender(event)) throw new Error('拒绝来自未知页面的请求');

  const { id, text } = payload ?? {};
  if (typeof id !== 'string' || !/^[a-z0-9-]{1,64}$/.test(id)) throw new Error('非法 ID');
  if (typeof text !== 'string' || text.length > 100_000) throw new Error('非法内容');

  const file = path.join(app.getPath('userData'), 'notes', `${id}.md`);
  await fs.promises.writeFile(file, text, 'utf8');
});

为什么要查发送方？因为 iframe 和子窗口也能发 IPC，消息不一定来自你自己的页面。官方示例比较的是 origin 而不是 URL，因为 about:blank、blob: 这类地址看不出实际是谁在控制。frame 已经销毁时，senderFrame 是 null，也要拒绝。

ID 用白名单格式校验，是为了防止 ../../ 这样的路径穿越，把文件写到任意位置。

示例里的 app://bundle 假设应用用自定义协议加载本地页面，实际使用时要和你的加载方式一致。

新窗口和外部链接怎么处理

JavaScript
win.webContents.setWindowOpenHandler(({ url }) => {
  const { protocol, hostname } = new URL(url);
  if (protocol === 'https:' && hostname === 'docs.example.com') {
    setImmediate(() => shell.openExternal(url));
  }
  return { action: 'deny' };
});

所有新窗口一律拒绝，只有明确允许的地址交给系统浏览器打开。为什么要这么严？因为 shell.openExternal 遇到不受信任的地址，比如 file: 或者自定义协议，可能被利用来执行命令。

同样要监听 will-navigate，阻止主窗口被导航到外部页面。

其他还要注意什么

尽量不加载远程内容。必须加载时，放在独立的 BrowserWindow 或 WebContentsView 里，不给它 preload 能力。

给本地页面设置 CSP，限制脚本从哪里加载。

打包时用 @electron/fuses 关闭 runAsNode、nodeCliInspect 等能力，防止应用被当成 Node.js 解释器去执行任意脚本。

及时升级 Electron，它内置的 Chromium 会持续修复安全漏洞。

常见追问

打开 nodeIntegration 有多危险？

它会让这个渲染进程不再运行在沙箱里，页面脚本可以直接使用 Node.js API，渲染进程里任何一个 XSS 都能执行系统命令。

preload 里能用 Node API 吗？

开启沙箱后，preload 只能使用一部分 Electron 和 Node 模块，文件读写这类操作应该放到主进程。
