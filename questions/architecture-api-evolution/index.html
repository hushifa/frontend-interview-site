前端 API 如何演进，才能兼容旧客户端并安全迁移？

前端发布后旧页面和旧 App 会长期存在，API 要同时服务新旧客户端。字段增删、错误格式、分页都要按兼容方式演进，配合版本、弃用通知、缓存处理和灰度发布分阶段迁移。

参考答案

简答

前端发布了新版本，用户浏览器里开着的旧页面、手机上没升级的旧 App 还会存在很久。所以 API 不能只照顾最新的前端，必须同时服务新旧客户端。

改动分两类。新增可选字段、新增接口、新增枚举值，一般是兼容的，前提是客户端能忽略不认识的值。删除或重命名字段、改字段类型或含义、新增必填参数，就是不兼容的，要走新版本或分阶段迁移。

迁移的顺序是：先加新的，再双写或双读，然后迁移客户端，确认没人用旧的了再删。

废弃要提前通知。可以用 Deprecation、Sunset 响应头加文档告诉调用方，同时用日志统计旧接口还有多少调用量。

客户端为什么也要容错

服务端加了一个新的订单状态，旧客户端不认识它，会怎么样？看下面这段：

JavaScript
const STATUS_TEXT = { paid: '已支付', pending: '待支付' };

function statusText(order) {
  return STATUS_TEXT[order.status] ?? '处理中'; // 未知状态不崩溃
}

console.log(statusText({ status: 'paid' })); // 已支付
console.log(statusText({ status: 'refunding' })); // 处理中

refunding 是后来新增的状态，映射表里没有，查出来是 undefined，于是走 ?? 后面的默认文案。如果这里写成没查到就抛错，或者直接拿 undefined 去渲染，旧版本就可能白屏。

服务端加了新状态、客户端没有兜底，是“兼容改动把旧版本搞崩”最常见的原因。所以客户端要做到三点：忽略不认识的字段，不要用严格校验拒绝多余属性；未知的枚举值走默认分支；只依赖文档承诺的字段，不依赖字段顺序或文档没写的行为。

不兼容的改动怎样分阶段迁移

举个例子，要把 name 拆成 firstName 和 lastName。

  1. 服务端同时返回 name 和两个新字段，写接口两种格式都接受。
  2. 发布新版前端，读写都改用新字段。
  3. 观察日志，等到还在发送或依赖 name 的客户端比例足够低。
  4. 返回 Deprecation 头并发文档通知，到了约定时间再删掉 name。

第 3 步在移动端可能要等好几个月，因为没法强制所有用户升级 App，有时要配合最低版本强制更新。

要不要加版本号

方式适用场景
不加版本，只做兼容改动大部分日常演进
URL 版本（/v2/orders）大范围不兼容改动，新旧并存
请求头或媒体类型版本同一资源多种表示，路径保持稳定
能力协商（客户端声明支持的功能）客户端版本差异大，按能力返回不同数据

版本越多，要维护和测试的组合就越多。所以优先靠兼容改动解决问题，尽量不开新版本。

错误格式和分页也要考虑演进

错误响应用统一的结构，比如 RFC 9457 定义的 Problem Details，包含 type、title、status、detail 这几个字段。这样以后新增错误类型，旧客户端不认识 type，也能按 status 兜底处理。

分页从偏移量改成游标时，旧参数要保留一段时间。游标对客户端来说应该是一个看不懂内容的字符串，客户端只负责原样传回去。这样服务端以后换实现，客户端不受影响。

缓存和灰度发布

响应结构变了以后，CDN 或浏览器里缓存的旧响应可能和新前端混在一起用。要么在 URL 或请求头里区分版本，要么让新前端也能处理旧格式的响应。

发布顺序上，服务端先发兼容版本，再灰度发布前端。前端要回滚时，服务端必须仍然支持旧前端的请求，否则回滚本身就会出问题。

怎样通知调用方接口要废弃

RFC 9745 定义了 Deprecation 响应头，RFC 8594 定义了 Sunset 响应头，可以再配合 Link 头指向迁移文档。前端或 SDK 在开发环境读到这些头，就打印警告提醒开发者。

常见追问

GraphQL 怎样演进？

通常不做版本。需要变化时新增字段，用 @deprecated 标注旧字段，再通过查询日志确认没人用了才删除。

前后端同时发布，能避免这些问题吗？

不能。用户浏览器里已经打开的旧页面、CDN 里的缓存，都还会存在一段时间，新旧版本总会同时在线。
