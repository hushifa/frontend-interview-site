前端 API 如何演进，才能兼容旧客户端并安全迁移？

从字段增删、错误格式、分页和能力协商出发，设计前端 API 的兼容演进策略，说明版本、弃用、缓存和灰度发布边界。

参考答案

简答

  • 前端发布后，旧版本页面和移动端 App 会长期存在，API 必须同时服务新旧客户端。
  • 兼容的改动：新增可选字段、新增接口、新增枚举值（前提是客户端能忽略未知值）。
  • 不兼容的改动：删除或重命名字段、改变字段类型或含义、新增必填参数，需要新版本或分阶段迁移。
  • 迁移按"先加新、双写或双读、迁移客户端、确认无人使用后再删旧"的顺序进行。
  • 用 Deprecation、Sunset 响应头和文档提前通知废弃，并通过日志统计旧接口的调用量。

客户端也要容错

JavaScript
const STATUS_TEXT = { paid: '已支付', pending: '待支付' };

function statusText(order) {
  return STATUS_TEXT[order.status] ?? '处理中'; // 未知状态不崩溃
}
  • 忽略不认识的字段，不要用严格模式拒绝多余属性。
  • 未知的枚举值走默认分支，而不是抛错或白屏。
  • 只依赖文档承诺的字段，不依赖字段顺序或未文档化的行为。

服务端加了新状态而客户端没有兜底，是最常见的"兼容改动导致旧版本崩溃"。

分阶段迁移示例

把 name 拆成 firstName 和 lastName：

  1. 服务端同时返回 name 和两个新字段，写接口同时接受两种格式。
  2. 发布新版前端，读写都改用新字段。
  3. 观察日志，直到仍在发送或依赖 name 的客户端比例足够低。
  4. 返回 Deprecation 头和文档通知，到达约定时间后删除 name。

移动端 App 无法强制所有用户升级，第 3 步可能需要几个月，或者配合最低版本强制更新。

版本策略

方式适用场景
不加版本，只做兼容改动大部分日常演进
URL 版本（/v2/orders）大范围不兼容改动，新旧并存
请求头或媒体类型版本同一资源多种表示，路径保持稳定
能力协商（客户端声明支持的功能）客户端版本差异大，按能力返回不同数据

版本越多，维护和测试成本越高，所以优先通过兼容改动避免新版本。

错误格式和分页

  • 错误响应使用统一结构，例如 RFC 9457 定义的 Problem Details（type、title、status、detail），新增错误类型时客户端可以按 status 兜底处理。
  • 分页从偏移量改成游标时，旧参数保留一段时间；游标对客户端应是不透明字符串，便于服务端以后修改实现。

缓存与灰度

  • 响应结构变化后，CDN 或浏览器中缓存的旧响应可能和新前端混用，要么在 URL 或请求头中区分版本，要么让新前端兼容旧响应。
  • 服务端先发布兼容版本，再灰度发布前端；回滚前端时，服务端必须仍支持旧前端的请求。

废弃通知

RFC 9745 定义了 Deprecation 响应头，RFC 8594 定义了 Sunset 响应头，可以配合 Link 头指向迁移文档。前端或 SDK 在开发环境中读取这些头并打印警告。

常见追问

  • GraphQL 怎样演进？通常不做版本，新增字段，用 @deprecated 标注旧字段，并通过查询日志确认无人使用后删除。
  • 前后端同时发布能避免这些问题吗？不能，用户浏览器中打开的旧页面和 CDN 缓存仍会持续一段时间。
