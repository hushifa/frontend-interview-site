什么是 XS-Leaks？前端如何减少跨站状态被推断？

XS-Leaks 不读取跨站响应内容，而是利用浏览器可观察的差异（加载成功或失败、耗时、iframe 数量、窗口导航）推断用户在目标站点的状态，例如是否登录、搜索是否有结果。防护靠 SameSite Cookie、COOP、frame-ancestors、CORP 和基于 Fetch Metadata 的资源隔离策略。

参考答案

简答

  • 攻击者页面向目标站点发请求或嵌入页面，观察结果差异，从而推断跨站状态。同源策略阻止读内容，但不阻止这些副作用被观察。
  • 常见信号：<img>、<script> 的 onload 与 onerror，请求耗时，window.length（iframe 数量），弹窗是否发生了跳转，缓存是否命中。
  • 前提通常是请求带上了用户的 Cookie，所以 SameSite=Lax 或 Strict 是第一道防线。
  • Cross-Origin-Opener-Policy: same-origin 切断攻击者通过 window.open 拿到的窗口引用；frame-ancestors 阻止被嵌入；Cross-Origin-Resource-Policy 阻止资源被跨站加载。
  • 服务端检查 Sec-Fetch-Site 等 Fetch Metadata 请求头，拒绝来自跨站的非导航请求。

一个例子

JavaScript
// 攻击者页面
const img = new Image();
img.onload = () => report('已登录');   // 登录后返回头像
img.onerror = () => report('未登录');  // 未登录时 302 到登录页（HTML，不是图片）
img.src = 'https://target.example/api/me/avatar';

攻击者看不到头像，但从加载成功还是失败知道了登录状态。同理，搜索接口在"有结果"和"无结果"时返回不同状态码，就能逐字符探测私密数据。

防护

http
Set-Cookie: __Host-session=...; Secure; HttpOnly; SameSite=Lax; Path=/
Cross-Origin-Opener-Policy: same-origin
Content-Security-Policy: frame-ancestors 'self'
Cross-Origin-Resource-Policy: same-origin

资源隔离策略（服务端中间件示意）：

JavaScript
function isolationPolicy(req, res, next) {
  const site = req.headers['sec-fetch-site'];
  if (!site || site === 'same-origin' || site === 'same-site' || site === 'none') return next();
  // 允许跨站的顶层页面导航，例如用户点击外部链接进入
  if (req.headers['sec-fetch-mode'] === 'navigate' && req.method === 'GET') return next();
  res.status(403).end();
}

缺少 Fetch Metadata 头的旧浏览器直接放行，因此它是增强措施，不替代鉴权和 CSRF 防护。

让响应难以区分

  • 敏感接口在有权限和无权限时返回相同的状态码和结构，避免"存在与否"本身泄露信息。
  • 私有响应不要进入共享缓存，缓存命中与否也可能成为信号。
  • 不必给所有响应填充到相同大小或人为加延迟，代价高且难以完全消除差异，优先阻止请求带上凭据和阻止被嵌入。

常见追问

  • 和 CORS 有什么关系？CORS 决定脚本能否读取响应内容；XS-Leaks 根本不读内容，所以 CORS 配置再严格也防不住。
  • 跨源隔离（COOP 加 COEP）有什么帮助？COOP 本身就能阻断窗口引用类的探测，两者合用还会限制跨源资源的嵌入；配置细节见《crossOriginIsolated 为 true 需要哪些条件？》。
