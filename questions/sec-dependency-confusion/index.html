前端项目如何防范依赖混淆攻击？

依赖混淆是攻击者在公共 npm 上发一个和你内部包同名的包，让安装器装错。防法是内部包统一用组织作用域并指向私有仓库、私有代理不回退到公共仓库、提前占住作用域名，再按锁文件安装。

参考答案

简答

假设公司内部有个包叫 acme-utils，只发在私有仓库里。攻击者在公共 npm 上也发一个 acme-utils，版本号写得很高。如果私有仓库代理在找不到包或者版本更低时回退到公共仓库，安装器就会把攻击者的包装进来。这就是依赖混淆。

防护的核心是让内部包的名字只能从一个地方来。内部包统一用作用域，比如 @acme/utils，在 .npmrc 里写 @acme:registry=...，npm 对这个作用域只查私有仓库。同时在公共 npm 上把 @acme 这个组织名注册下来，防止别人抢注。

安装环节也要收紧。CI 用 npm ci 按锁文件安装，审查锁文件里的 resolved 地址是不是都来自允许的仓库。

要注意，恶意包通常在 preinstall、postinstall 这类安装脚本里动手，所以 CI 里还要限制网络和密钥，让它就算执行了也拿不走东西。

作用域映射怎么配

ini
# 项目 .npmrc
@acme:registry=https://npm.internal.example/
ini
# 用户或 CI 的 .npmrc，令牌按主机绑定，不要提交到仓库
//npm.internal.example/:_authToken=${NPM_INTERNAL_TOKEN}

第一段告诉 npm，凡是 @acme/ 开头的包都去内部仓库找。第二段把访问令牌绑定到具体的仓库主机，这样令牌不会被发给错误的仓库。

可是光配 .npmrc 还不够。很多公司用 Verdaccio、Nexus、Artifactory 这类私有仓库代理，它们本身也会向公共上游转发请求。如果代理没配置成“内部作用域不向上游代理”，npm 虽然只问了内部仓库，内部仓库却替它去公共 npm 拿了，作用域映射就挡不住。

锁文件里要查什么

锁文件记录了每个包的版本、下载地址和 integrity 哈希。下面的脚本列出锁文件中所有不是来自允许仓库的包：

bash
# 列出锁文件中所有不是来自允许仓库的包
node -e "
const lock = require('./package-lock.json');
for (const [path, info] of Object.entries(lock.packages ?? {})) {
  if (info.resolved && !/^https:\/\/(registry\.npmjs\.org|npm\.internal\.example)\//.test(info.resolved)) {
    console.log(path, info.resolved);
  }
}"

有了锁文件为什么还要查？因为锁文件只保证“按它写的装”。如果某次提交引入的新锁文件里本来就记了一个错误的来源，它会忠实地照着装。所以依赖变更要经过审查。

安装脚本怎么处理

npm ci --ignore-scripts 可以阻止安装脚本执行。可是需要编译原生模块的依赖会因此失败，所以要评估后对必要的包单独处理。

另外两件事是限制脚本执行后的危害。拉取外部贡献的流水线不注入发布令牌和云密钥。构建机只开放到包仓库和必要服务的网络出口，恶意脚本就算跑起来了，也很难把数据传出去。

老项目怎么迁移

已经有一批无作用域的内部包时，不要直接改名发布。先在私有仓库里用新的作用域名发布相同的代码，再逐个项目替换依赖。同时在公共 npm 上把旧的包名占住，或者确认它已经被保护起来。

常见追问

npm audit 能发现依赖混淆吗？

通常不能。npm audit 依据的是已知漏洞公告，攻击者新发布的恶意包还没有公告。

它和其他供应链攻击是什么关系？

依赖混淆是供应链攻击的一种。更全面的治理，比如仿冒包、维护者账号被盗，见《前端依赖供应链风险应该怎样防范？》。
