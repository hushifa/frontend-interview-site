Resource Timing 为什么有些跨源字段是零？

PerformanceResourceTiming 记录资源请求阶段和传输大小，但跨源细节受 Timing-Allow-Origin 保护。字段为零可能是缓存、连接复用、隐私限制或信息缺失，不能直接下结论。

参考答案

能加载不等于能读取网络细节

页面可以显示跨源图片、执行跨源脚本，但如果脚本能随意读取对方的 DNS、连接和响应时间，就可能推断其他站点的缓存状态和用户访问情况。因此浏览器会隐藏部分跨源 Resource Timing 字段。

一个条目可能仍有 name、startTime 和 duration，但 DNS、连接、请求开始和首字节时间为 0。这不一定表示请求没有经历这些阶段，也可能是跨源细节没有获得授权。

TAO 和 CORS 解决不同问题

资源服务器可以返回：

http
Timing-Allow-Origin: https://app.example.com

它控制页面能否读取受保护的性能细节。Access-Control-Allow-Origin 则主要控制跨源响应内容能否被脚本读取。图片不需要 CORS 也可能显示，但仍没有完整 Timing；fetch 通过了 CORS，也不代表所有计时字段自动开放。

跨源重定向链还可能影响可见字段，不能只检查最终文件的一个响应头就断定整个请求都可测。是否使用 * 要结合资源是否公开、是否涉及敏感路径和监控需求决定。

大小字段不代表同一种成本

字段含义
transferSize这次获取的响应头和编码后响应体传输量
encodedBodySize编码后的响应体大小，例如压缩后的体积
decodedBodySize解码后的响应体大小

decodedBodySize 不是脚本执行后的堆内存，也不是图片解码后的像素内存。几十 KB 的脚本可能在执行时创建大量对象；这些成本要通过其他工具和指标观察。

transferSize === 0 可能是缓存或连接复用的线索，但跨源字段不可见也会得到 0。304 重验证仍可能有网络流量，Service Worker 和缓存策略也会改变解释，不能写成“0 就是命中缓存”。

观察器应尽早建立并限制上报

JavaScript
function observeResources(onResource) {
  if (
    typeof PerformanceObserver === 'undefined' ||
    !PerformanceObserver.supportedEntryTypes?.includes('resource')
  ) return () => {};

  const observer = new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
      onResource({
        initiatorType: entry.initiatorType,
        duration: entry.duration,
        transferSize: entry.transferSize,
        encodedBodySize: entry.encodedBodySize,
        decodedBodySize: entry.decodedBodySize,
      });
    }
  });

  observer.observe({ type: 'resource', buffered: true });
  return () => observer.disconnect();
}

getEntriesByType() 只返回读取时已经存在的条目；用户之后点击触发的请求要用 Observer 监听。性能缓冲区不是无限的，长页面应尽早订阅并处理 buffer 满的情况。回调里只做轻量入队，后续批量、采样上报，不要同步序列化大量记录。

请求完成不等于功能完成

脚本下载结束后还要解析、编译和执行；图片下载结束后还要解码、布局和绘制；fetch 完成后还要解析 JSON、更新状态和渲染。用户第一次展开等待两秒，而答案资源只下载了 100ms，瓶颈可能在后续模块、主线程或渲染，而不是网络。

反过来，一条慢资源也未必影响用户。如果它在后台预取或低频页面中加载，优化优先级可能低于一个较小但阻塞首个操作的脚本。应把资源记录和用户任务、LCP、INP 或业务 mark 对齐。

生产采集要处理隐私和缺失

资源 URL 可能带查询参数、令牌、租户或用户标识。上报前应使用白名单、去除查询串或脱敏，不能把所有完整 URL 发送到监控平台。还要区分真实为零、缓存、连接复用、跨源不可见和记录丢失。

Resource Timing 提供的是线索，不是自动原因分析。要得出可信结论，需要结合响应头、缓存路径、浏览器网络面板、构建版本和页面实际交互一起验证。
