前端契约测试应该验证什么？

契约测试检查前端依赖的接口形状和行为是否与后端一致，包括字段、类型、状态码和错误格式；消费者驱动的契约（如 Pact）只记录前端真正用到的部分，后端在发布前验证不破坏它。

参考答案

简答

  • 前端单元测试里的 mock 是手写的，接口改了测试照样通过；契约测试用来发现这种前后端不一致。
  • 以 OpenAPI 为准时：从规范生成 TypeScript 类型和模拟数据，后端在 CI 中验证实现符合规范。
  • 消费者驱动契约（Pact）：前端测试记录“我发这个请求，期望收到这些字段”，生成契约文件，后端用它回放验证。
  • 契约要包括错误情况：401、403、404、422 的状态码和错误体格式，前端的错误处理依赖它们。
  • 删除或改类型是破坏性变更；请求字段从可选改成必填、响应字段从必填改成可选，也会破坏旧消费者。

用 OpenAPI 生成类型

bash
npx openapi-typescript ./openapi.yaml -o src/api/schema.d.ts
TypeScript
import type { paths } from './schema';

type Order =
  paths['/orders/{id}']['get']['responses']['200']['content']['application/json'];

规范一改，类型检查就会报出前端依赖了不存在的字段。类型只在编译期起作用，运行时收到的数据仍可能不符合，关键接口可以用 Zod 等库在边界处校验。

消费者驱动契约

TypeScript
await provider
  .given('订单 42 存在')
  .uponReceiving('获取订单详情')
  .withRequest({ method: 'GET', path: '/orders/42' })
  .willRespondWith({
    status: 200,
    body: { id: 42, total: like(99.5), status: regex(/paid|pending/, 'paid') },
  })
  .executeTest(async (mock) => {
    const order = await getOrder(mock.url, 42);
    expect(order.status).toBe('paid');
  });

like 只要求类型一致，regex 约束取值范围。契约里只出现前端使用的字段，后端新增字段不会导致失败，删除 total 才会。

三种测试分别证明什么

测试证明不能证明
前端 mock 测试前端按假设的数据正确工作假设是否正确
契约测试前后端对接口形状达成一致业务逻辑是否正确
端到端测试整条链路在某个环境下可用能覆盖的组合很少

发布流程

  • 后端发布前运行所有消费者的契约验证，失败就不能部署。
  • 破坏性变更要先新增字段或新版本接口，等所有消费者迁移后再删除旧的。
  • 方向要分开看：请求字段改成必填，没传它的旧客户端会被拒绝；响应字段改成可选，依赖它一定存在的旧客户端会出错。响应里新增字段、请求里新增可选字段通常兼容。
  • 移动端等无法强制升级的客户端，要保留旧契约更长时间。

常见追问

  • 有 TypeScript 全栈（如 tRPC）还需要契约测试吗？前后端在同一仓库同时部署时，类型共享已经能发现大部分不一致；独立部署、有多个客户端或第三方消费者时，契约测试仍然有价值。
