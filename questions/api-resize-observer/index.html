ResizeObserver 为什么可能出现循环通知错误？

ResizeObserver 观察元素盒尺寸的变化，适合组件尺寸由容器而非单纯窗口大小决定的场景。观察目标的内容盒、边框盒等需要按 API 选项和支持情况明确区分。

参考答案

简答

  • ResizeObserver 观察元素盒的尺寸变化，适合尺寸由容器决定的组件。
  • 要明确观察 content-box、border-box 等哪种盒。
  • 回调中改变被观察元素的尺寸可能引发循环，浏览器会报错跳过，但不会替你修复。
  • 修复应改变依赖关系或让尺寸收敛，requestAnimationFrame 只改变执行时机。

一个图表容器变窄，可能是侧栏展开了，并不是 window 发生 resize。ResizeObserver 让组件直接观察自身或容器的盒尺寸，因此更适合容器驱动的布局与绘制。

循环问题出现在“读取尺寸后又改变导致该尺寸的布局”。如果回调把目标宽度每次加 10 像素，目标会再次变大，下一轮又加 10，形成没有终点的反馈。

先确定观察哪种盒

content-box 对应内容盒，border-box 包含内容、padding 和 border；device-pixel-content-box 提供设备像素相关的内容尺寸，但支持情况需要单独核对。

entry.contentBoxSize、borderBoxSize 等使用 inlineSize 与 blockSize，它们是逻辑方向尺寸，不应永久理解为物理 width 与 height。多片段布局也可能涉及多个 size 记录，不能在复杂排版中无条件只取第一个。

contentRect 是常用的兼容读取方式，主要反映内容区域。若观察 border-box 却用 contentRect.width 与边框尺寸比较，会因为两者语义不同产生误判。

一个只报告尺寸变化的观察器

下面使用内容盒，并用 contentRect 读取物理宽高，适合这里的普通组件场景：

JavaScript
function watchSize(element, onSize) {
  if (typeof ResizeObserver === 'undefined') return () => {};
  let previousWidth;
  let previousHeight;
  const observer = new ResizeObserver((entries) => {
    for (const entry of entries) {
      const { width, height } = entry.contentRect;
      if (width === previousWidth && height === previousHeight) continue;
      previousWidth = width;
      previousHeight = height;
      onSize({ width, height });
    }
  });
  observer.observe(element);
  return () => observer.disconnect();
}

保存上次值减少重复业务更新，但不保证调用方不会制造循环。如果 onSize 每次把该元素宽度设成 width + 10，下一次宽度确实不同，去重仍然挡不住。

回调通常会在初次观察获得尺寸后通知，但隐藏、零尺寸和渲染状态会影响实际交付时机，不要把 observe 当成同步读取函数。

浏览器避免锁死，不代表替你修复循环

ResizeObserver 通知与绘制前的布局流程相关。回调触发布局后，浏览器可能继续发现尺寸变化，并按规则把部分通知推迟，报告类似“loop completed with undelivered notifications”的错误。

这表示当前处理没有把所有通知在本轮交付，并不自动证明观察器 API 有 bug。某次有限的调整可能最终稳定；如果每帧重复报错，就应检查反馈链。

一个复杂例子是：宽度小于阈值时添加 class，class 改变 padding 后宽度又跨过阈值，于是移除 class，再次回到原宽度。两个状态来回跳，不一定表现为单调增大，却同样不收敛。

修复应改变依赖关系或让它收敛

优先使用 CSS 媒体或容器查询表达纯样式适配，避免用 JavaScript 反复测量再设置。必须测量时，可观察稳定的外层容器，把结果用于不会反过来改变容器尺寸的内部绘制。

例如 Canvas 需要同步内部位图尺寸时，应先用 CSS 明确展示尺寸，避免设置 width/height 属性又改变布局尺寸。还应比较目标位图尺寸，没变化就不重设，因为重设会清空画布与绘制状态。

对于断点切换，可以采用稳定条件或适当滞回，避免临界值抖动。不能只用任意四舍五入掩盖真正的尺寸依赖错误。

requestAnimationFrame 只改变时机

把写操作推迟到 requestAnimationFrame 可能打断同一轮反馈，但如果逻辑仍然每次增加宽度，就会变成跨帧无限增长。它可以帮助调度，不会证明算法收敛。

若使用待执行动画帧，组件销毁时除了 disconnect，还要取消尚未执行的帧回调，避免在卸载后继续写 DOM。多个目标可以共享观察器，但尺寸缓存应按目标分别管理。

排查时记录是哪一个元素、读取了哪种盒、回调写了什么属性，以及该写入怎样影响下一次测量。只有把这条反馈链画清楚，才能修复循环，而不是在控制台过滤掉错误消息。
