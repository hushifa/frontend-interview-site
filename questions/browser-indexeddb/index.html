IndexedDB 为什么比 localStorage 更适合大型离线数据？

IndexedDB 是异步的事务型数据库，能存结构化对象和二进制、建索引、按范围查询，容量远大于 localStorage；代价是 API 偏底层，需要处理版本升级和事务生命周期。

参考答案

简答

  • IndexedDB 是异步 API，读写不会阻塞主线程；localStorage 是同步的，数据大时会卡住页面。
  • 它能直接存对象、Blob、ArrayBuffer，不需要序列化成字符串。
  • 支持索引和按范围查询，所有读写都在事务里，失败时整体回滚。
  • 容量由浏览器的存储配额决定，通常远大于 localStorage 的约 5MB。

核心概念

  • 数据库与版本：indexedDB.open(name, version)。版本号变大时触发 upgradeneeded，只能在这个事件里创建或修改对象仓库和索引。
  • 对象仓库（object store）：类似表，用 keyPath 或自增主键标识记录。
  • 索引：按某个字段查询，例如按 updatedAt 排序。
  • 事务：readonly 或 readwrite，作用于指定的对象仓库。

示例

JavaScript
function openDB() {
  return new Promise((resolve, reject) => {
    const request = indexedDB.open('notes', 2);
    request.onupgradeneeded = () => {
      const db = request.result;
      if (!db.objectStoreNames.contains('notes')) {
        const store = db.createObjectStore('notes', { keyPath: 'id' });
        store.createIndex('byUpdatedAt', 'updatedAt');
      }
    };
    request.onsuccess = () => {
      const db = request.result;
      // 其他标签页要升级版本时关闭旧连接，避免阻塞对方
      db.onversionchange = () => db.close();
      resolve(db);
    };
    request.onerror = () => reject(request.error);
    request.onblocked = () => reject(new Error('其他标签页仍在使用旧版本数据库'));
  });
}

async function saveNote(note) {
  const db = await openDB();
  return new Promise((resolve, reject) => {
    const tx = db.transaction('notes', 'readwrite');
    tx.objectStore('notes').put(note);
    tx.oncomplete = () => resolve();
    tx.onerror = () => reject(tx.error);
    tx.onabort = () => reject(tx.error ?? new Error('事务已中止'));
  });
}

实际项目一般用 idb 这类 Promise 封装，减少样板代码。

容易出错的地方

  • 事务自动提交：事务在没有待处理请求时会自动提交。在事务中间 await fetch() 之类的外部操作，事务会先提交，后续请求抛出 TransactionInactiveError。需要网络数据时先取回再开事务。
  • 版本升级被阻塞：其他标签页还打开着旧版本连接时，新版本的升级会触发 blocked。旧连接应监听 versionchange 并调用 db.close()。
  • 数据可能被清除：存储压力大时浏览器可能清理数据。重要数据可以调用 navigator.storage.persist() 申请持久化，并保留服务端备份。
  • 隐私模式：部分浏览器在隐私模式下容量很小或数据随窗口关闭清除。

常见追问

  • 什么时候还用 localStorage：少量、同步读取就能满足的配置，例如主题。
  • IndexedDB 能跨源共享吗：不能，它和 localStorage 一样按源隔离。
