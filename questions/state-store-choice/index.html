Zustand、Jotai 和 Redux Toolkit 应该怎样选择？

Zustand 用一个 hook 暴露整个 store，组件通过选择器订阅需要的部分，不需要 Provider；Jotai 把状态拆成原子，组件按原子订阅，派生原子自动追踪依赖；Redux Toolkit 要求通过 action 和纯 reducer 修改状态，约束最多，自带 DevTools、thunk 和开发期检查。服务端数据交给查询库，三者只管客户端状态。

参考答案

简答

Zustand 是一个集中的 store。create 返回一个 hook，组件用选择器读出自己要的字段，选择结果用 Object.is 比较，变了才重新渲染。它不需要 Provider，store 上的 getState、setState 在 React 外面也能调用。

Jotai 是把状态拆成一个个小原子。atom 只是一个定义，值实际保存在 store 里。派生原子的读函数里用 get 读别的原子，Jotai 会记下依赖，依赖变了自动重新计算。不用 Provider 时，所有组件共用一个默认 store。

Redux Toolkit 约束最多：状态只能通过 dispatch action 改变，reducer 是纯函数。configureStore 默认加上 thunk、连接 Redux DevTools，开发环境下还会检查有没有直接修改状态、有没有存进不可序列化的值。

怎么选，看状态的形状和团队要多少约束。业务状态集中、需要记录和回放每次操作，选 Redux Toolkit；状态零散、彼此之间有派生关系，Jotai 更顺手；想要一个样板代码少的集中 store，选 Zustand。要注意，服务端数据交给 TanStack Query 或 SWR，参见《为什么要用 TanStack Query 或 SWR 管理服务端状态？》。

Zustand 怎么用

JavaScript
import { create } from 'zustand';
import { useShallow } from 'zustand/react/shallow';

const useCartStore = create((set) => ({
  items: [],
  coupon: null,
  addItem: (item) => set((state) => ({ items: [...state.items, item] })),
  setCoupon: (coupon) => set({ coupon }), // 默认浅合并，其他字段保留
}));

// 只订阅 items 的长度，coupon 变化不会让它重新渲染
const count = useCartStore((state) => state.items.length);

// 选择器每次返回新对象时，要用 useShallow 按字段比较
const { items, addItem } = useCartStore(
  useShallow((state) => ({ items: state.items, addItem: state.addItem })),
);

set({ coupon }) 只传了一个字段，items 却不会丢，因为 set 默认把传入的对象浅合并进现有状态。

选择器决定了组件订阅什么。state.items.length 只在长度变化时才变，所以改 coupon 不会让这个组件重新渲染。

那为什么第二段要包一层 useShallow？因为选择器每次都返回一个新对象 { items, addItem }，按 Object.is 比较永远不相等。Zustand v5 用 Object.is 比较选择结果，这样写而不包 useShallow，可能导致 “Maximum update depth exceeded” 报错。useShallow 改成逐个字段比较，字段都没变就算没变。另一种办法是每个字段单独调用一次选择器。

Jotai 怎么用

JavaScript
import { atom, useAtom, useAtomValue } from 'jotai';

const priceAtom = atom(100);
const countAtom = atom(2);
// 派生原子：priceAtom 或 countAtom 变化时自动重新计算
const totalAtom = atom((get) => get(priceAtom) * get(countAtom));

function Total() {
  return useAtomValue(totalAtom);
}

totalAtom 的读函数里 get 了两个原子，Jotai 就记住它依赖这两个。任何一个变了，totalAtom 重新计算，用到它的 Total 组件也跟着更新。

原子要定义在模块顶层，或者用 useMemo 保持引用稳定。如果在渲染过程中直接创建原子，每次渲染都是一个新原子，useAtom 会陷入无限循环。

什么时候需要 Provider？想让不同的子树各有一份状态、需要注入初始值、或者想通过重新挂载把所有原子重置，这几种情况才需要。

Redux Toolkit 有什么不同

Redux Toolkit 的写法和 reducer 为什么要纯，见《Redux 的单向数据流为什么强调 reducer 的纯粹性？》。

它的样板代码比前两个多，换来的是统一的修改入口。每次变化都对应一个 action，可以在 DevTools 里一条条查看、回放，中间件也能统一处理日志、埋点和异步流程。

常见追问

SSR 时要注意什么？

模块级的 Zustand store 和 Jotai 的默认 store，会被同一个服务器进程里的所有请求共享。所以 SSR 时要为每个请求创建独立的 store，Jotai 可以给每个请求用一个独立的 Provider。

只用 React 自带的 useState 和 Context 行不行？

状态少、更新不频繁时可以。Context 的值一变，所有用到它的组件都会重新渲染，所以状态多、更新又频繁时，才需要这些库的细粒度订阅。

三者能混用吗？

可以。但同一份数据只应该有一个来源，否则就得在好几处之间同步。
