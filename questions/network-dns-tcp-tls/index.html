DNS、TCP 和 TLS 握手分别会给页面增加哪些等待？

新连接要依次经历 DNS 解析、TCP 握手和 TLS 握手，之后才能发 HTTP 请求。TLS 1.3 加 TCP 至少两个往返，HTTP/3 合并为一个。Navigation Timing 和 Resource Timing 的时间戳可以把每一段拆出来测量。

参考答案

简答

  • DNS：把域名解析为 IP。命中浏览器或系统缓存时几乎为 0，否则要问递归解析器，可能多出几十到上百毫秒。
  • TCP：三次握手，1 个往返。
  • TLS 1.3：再加 1 个往返（TLS 1.2 是 2 个）。HTTPS 新连接在发出请求前至少等待 2 个往返。
  • HTTP/3 的 QUIC 把传输和加密握手合并为 1 个往返，恢复连接时可以 0-RTT。
  • 连接复用、preconnect 和 CDN 就近接入都在减少这些等待。

用时间戳拆分

JavaScript
const [nav] = performance.getEntriesByType('navigation');

const dns = nav.domainLookupEnd - nav.domainLookupStart;
const tcp = nav.secureConnectionStart > 0
  ? nav.secureConnectionStart - nav.connectStart
  : nav.connectEnd - nav.connectStart;
const tls = nav.secureConnectionStart > 0 ? nav.connectEnd - nav.secureConnectionStart : 0;
const ttfb = nav.responseStart - nav.requestStart;

console.table({ dns, tcp, tls, ttfb, protocol: nav.nextHopProtocol });
  • connectEnd - connectStart 包含 TLS，所以 TCP 段要截到 secureConnectionStart。
  • 连接复用时 connectStart 和 connectEnd 相等，DNS 和连接耗时为 0。
  • HTTP/3 下传输和加密握手合在一起，按 TCP 和 TLS 分开解读没有意义。
  • 跨源资源没有 Timing-Allow-Origin 时，这些字段在 Resource Timing 里为 0。

往返时间才是关键

握手耗时约等于往返次数乘以 RTT。手机在 4G 下 RTT 可能是 50–100ms，跨洲访问可能超过 200ms，这时 2 个往返就要几百毫秒。所以减少往返（复用连接、HTTP/3、TLS 1.3）和缩短 RTT（CDN 边缘节点）比优化服务器 CPU 更有效。

前端能做什么

  • 减少首屏依赖的第三方域名数量，每个新域名都要一套握手。
  • 对关键第三方域名用 preconnect，可能用到的用 dns-prefetch，见《dns-prefetch、preconnect 和 preload 应该怎样选择？》。
  • 静态资源尽量和页面同域或走同一个 CDN 域名，便于 HTTP/2 连接复用。

常见追问

  • DNS 能在前端缓存吗？不能直接控制，由浏览器和操作系统按 TTL 缓存。
  • 为什么本地测不出差别？本地 RTT 很低且有缓存，要用真实用户数据或在 DevTools 中模拟慢网。
