编译目标、polyfill 和浏览器兼容性是什么关系？

用可选链与 toSorted 区分语法转换和运行时能力，说明 target、类型声明、polyfill、CSS 与安全上下文分别影响什么，以及怎样定义可验证的支持范围。

参考答案

简答

  • 编译目标（target）只决定语法怎样降级，例如把可选链改写成条件判断。
  • 新的内置 API（如 Array.prototype.toSorted）属于运行时能力，语法转换不会补上，需要 polyfill 或特性检测。
  • TypeScript 的 lib 只影响类型检查，不会给运行环境增加任何 API。
  • CSS 新特性、安全上下文要求和权限限制都不归 JavaScript 构建目标管。
  • 支持范围要写成可执行的浏览器列表，并在这些浏览器里实际测试。

语法和 API 是两类问题

JavaScript
const name = user?.profile?.name;
const sorted = list.toSorted((a, b) => a - b);

第一行是语法。把 target 设得足够低，构建工具会把 ?. 改写成旧浏览器能解析的代码。第二行是对内置方法的调用，语法很普通，旧浏览器能解析，但运行时找不到 toSorted 就会抛 TypeError。构建工具默认不会为它注入实现。

所以"降低 target 后旧浏览器还是报错"很常见：报错往往来自缺失的 API，而不是语法。

各项配置分别管什么

配置影响不影响
构建 target（Vite build.target、esbuild/Oxc 目标）语法降级和压缩方式内置 API 是否存在
TypeScript lib哪些 API 能通过类型检查产物和运行环境
polyfill（如 core-js）在运行时补齐缺失 API无法补齐的能力（如新的 CSS 布局、硬件 API）
Browserslist让支持它的工具共享同一份浏览器列表工具自身不读它时无效

Vite 的默认 build.target 是 'baseline-widely-available'：按每个大版本固定的日期，取当时 Baseline 广泛可用的浏览器版本，Vite 8 对应 Chrome 111、Firefox 114、Safari 16.4。需要更旧的浏览器时，官方提供 @vitejs/plugin-legacy，它会额外生成旧浏览器产物并按需注入 polyfill。

polyfill 的取舍

全量引入 polyfill 会让所有用户为少数旧浏览器承担体积。常见做法：

  • 按目标浏览器和实际用到的 API 按需注入。
  • 对可选增强功能用特性检测，缺失时走降级路径，而不是补一个不完整的实现。
  • 有些能力没法 polyfill，例如 Service Worker、WebGPU、新的 CSS 选择器，只能检测后降级。

CSS 和环境限制

CSS 新语法由 PostCSS、Lightning CSS 等单独处理，可以加前缀或降级部分写法，但 :has()、容器查询这类能力在不支持的浏览器里补不出来，要用 @supports 提供回退。

剪贴板、Service Worker、Web Crypto 的 subtle 等 API 要求安全上下文（HTTPS 或 localhost）。开发时在 localhost 正常，部署到 HTTP 内网地址就失效，这和构建目标无关。

怎样定义支持范围

把"支持主流浏览器"改成可检查的列表，例如"最近两个大版本的 Chrome、Edge、Firefox、Safari，以及 iOS Safari 16.4+"，写进 Browserslist 或构建配置。然后：

  1. 构建配置和 polyfill 策略都从这份列表推导。
  2. CI 里至少在列表的最低版本上跑一遍关键流程。
  3. 对列表外的浏览器给出明确的降级体验或提示。

常见追问

  • 为什么类型检查通过，线上却报 xxx is not a function？因为 lib 声明了 API，但目标浏览器没有实现。
  • 可以只靠 target 解决兼容吗？不行，target 只处理语法。
