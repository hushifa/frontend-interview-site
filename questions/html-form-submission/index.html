表单的 name、value、label 与提交行为如何协作？

label 建立控件名称与交互关联，name 决定提交字段名，value 提供当前提交值。原生表单按控件状态收集条目，同名多值、disabled、readonly 和提交按钮都需要按各自规则处理。

参考答案

表单的“看得到”“可以编辑”和“会被提交”是三件不同的事。输入框里显示了邮箱，不代表浏览器一定会把它提交；控件被设为只读，也不代表它会从提交数据里消失。

label 负责说明控件是什么，id 可以用于关联这个说明，name 才是提交的数据字段名。它们可以相同，但职责不能混淆。只写 id="email" 而没有 name，浏览器通常不会把这个文本框当成 email 字段收集。

从一个完整的表单看数据来源

HTML
<form id="subscription" action="/subscribe" method="post">
  <label for="reader-email">邮箱</label>
  <input
    id="reader-email"
    name="email"
    type="email"
    value="reader@example.com"
    required
  />

  <fieldset>
    <legend>感兴趣的专题</legend>
    <label><input type="checkbox" name="topic" value="html" checked /> HTML</label>
    <label><input type="checkbox" name="topic" value="css" checked /> CSS</label>
    <label><input type="checkbox" name="topic" value="react" /> React</label>
  </fieldset>

  <label for="plan">订阅方案</label>
  <input id="plan" name="plan" value="basic" readonly />

  <label for="invite">邀请码（暂不可用）</label>
  <input id="invite" name="invite" value="WELCOME" disabled />

  <button type="submit" name="intent" value="subscribe">订阅</button>
  <button type="button">查看说明</button>
</form>

for="reader-email" 与控件的 id 关联，点击“邮箱”标签可以把焦点交给控件，辅助技术也能获得名称。复选框则直接放在 label 中，属于隐式关联。同一文档中的 id 应保持唯一。

邮箱提交值来自控件的当前值。HTML 的 value 属性提供初始值，但用户编辑后的提交内容不是简单重新读取那段 HTML 属性文本。

两个选中的复选框使用相同的 name，产生两个 topic 条目：html 和 css。未选中的 React 不产生 topic 条目，也不会自动提交 false。如果复选框没有明确的 value，选中时常见的默认提交值是字符串 on，所以业务选项通常应写清具体值。

readonly 和 disabled 为什么会得到不同数据

只读文本框仍然可以参与提交，示例会收集 plan=basic。被禁用的邀请码字段不参与收集，虽然它仍然显示 WELCOME。禁用控件通常也不进入正常键盘焦点顺序；readonly 则允许用户聚焦、查看或复制适用控件的内容。

readonly 不是所有控件都支持的通用“锁定”开关，例如不能靠给 select 加 readonly 获得与文本框相同的行为。disabled 的 fieldset 也会影响其控件后代，并有第一个 legend 中控件等规则例外，应按 HTML 表单规则处理。

用 CSS 隐藏一个具名、未禁用的普通控件，并不等于把它排除出提交。反过来，不在 form 标签内部的控件，也可以通过 form="subscription" 关联表单并参与收集。因此实际收集依据是表单关联和控件规则，而不只是“找所有可见的 input 后代”。

用 FormData 保留浏览器的收集规则

下面代码应在上面的 DOM 已就绪后执行。它阻止演示表单导航，只展示本次收集到的数据，不实际发送请求：

JavaScript
const form = document.querySelector('#subscription');

form.addEventListener('submit', event => {
  event.preventDefault();
  const data = new FormData(form, event.submitter);

  console.log(data.get('email'));  // reader@example.com（未编辑时）
  console.log(data.getAll('topic')); // ['html', 'css']（保持默认选择时）
  console.log(data.get('plan'));   // basic
  console.log(data.has('invite')); // false
  console.log(data.get('intent')); // subscribe（点击订阅按钮时）
});

FormData 保留同名多值。get('topic') 只取第一个，getAll('topic') 才能取得所有选择。直接 Object.fromEntries(data) 会让同名键被后面的值覆盖，不适合无条件转换有复选框组、多选下拉或多文件字段的表单。

event.submitter 表示触发本次提交的按钮，可能是 null。把它传给 FormData，才能按规则包含该按钮的 name/value。单独 new FormData(form) 并不知道用户是点了“保存草稿”还是“正式发布”，不会自动选择一个提交按钮来收集。

构造 FormData 本身不会执行约束校验，也不会自动发送网络请求。它只是按当时的控件状态构造数据，因此如果要防重复点击，通常应先收集数据，再禁用相关按钮或字段；先禁用再收集，可能把需要的数据排除掉。

提交按钮、Enter 和脚本提交的区别

form 内没有明确指定类型的普通 button 通常会成为提交按钮，所以“查看说明”“添加一行”这类普通操作应显式写 type="button"。监听 form 的 submit 事件，比只监听某个按钮的 click 更合适，因为键盘 Enter 等途径也可能触发表单提交。

用户激活提交按钮时，浏览器会按表单设置执行约束校验。存在 required、type=email 等不满足的字段时，通常先提示错误，表单不会进入正常 submit 事件流程；novalidate 等设置可以改变这个过程。

需要脚本模拟用户提交时，优先考虑 form.requestSubmit(button)，它经过相应校验和 submit 事件，也能使用指定按钮的提交参数。form.submit() 则直接提交，不触发 submit 事件，也不执行同样的交互式约束校验，不能把两者视为同义方法。

避免把控件命名为 submit，因为具名控件可能遮住表单对象的同名方法，让 form.submit() 变成“不是函数”。

真正发送时，还要决定编码与结果处理

原生 GET 通常把表单条目放入 URL 查询部分，适合可分享的搜索条件；POST 把数据放在请求体中，但 POST 本身不等于加密，传输保护仍需要 HTTPS。上传文件的原生表单通常需要 enctype="multipart/form-data"。

若使用 fetch 并把 FormData 作为 body，通常不要手动设置 Content-Type: multipart/form-data。浏览器需要生成对应的 boundary 并放进请求头，手写一个缺少 boundary 的头会导致服务端无法正确解析。

收集和前端校验只是提交的前半段。实际业务还需要处理网络失败、服务端字段错误、重复提交和成功后的界面状态。readonly、hidden 和前端校验都不能防止请求被修改，服务端仍必须验证权限与字段内容。
