为什么不断追加微任务会阻塞页面响应？

浏览器每跑完一个任务，都要把微任务队列清空才继续，清空时新加的微任务也算在内。微任务不停地生出新微任务，渲染和点击处理就永远轮不到。

参考答案

简答

浏览器每执行完一个任务，就会把微任务队列一口气清空，这一步叫微任务检查点。

关键在于，清空过程中新加进来的微任务也在这一轮执行，不会留到下一轮。所以如果一个微任务又产生新的微任务，新的再产生新的，这一轮就永远结束不了。

事件循环卡在这一步，没法去渲染页面，也没法处理下一个任务，比如用户的点击。页面看起来就卡死了，效果和写了个死循环一样。

要真正让出主线程，得用任务级的调度，比如 setTimeout、MessageChannel 或者 scheduler.yield()。

先看现象

下面这段会让页面卡死：

JavaScript
function loop() {
  Promise.resolve().then(loop);
}
loop();

把 Promise 换成 setTimeout，页面就不会卡死，只是会一直占着 CPU：

JavaScript
function loop() {
  setTimeout(loop, 0);
}
loop();

两段代码都是“无限循环”，为什么一个卡死、一个不卡？

原因：微任务要清空才算完

第一段里，每个 then 回调都是微任务，它在执行时又加了一个新微任务。按规则，新加的也要在这一轮清掉，于是这一轮永远清不完，浏览器一直到不了渲染那一步。

第二段里，每个回调都是一个新任务。任务和任务之间，浏览器有机会去处理输入、渲染页面，所以页面还能响应。

可以在 Node 里验证这一点。下面让微任务链跑 10 万次，再看定时器什么时候执行：

JavaScript
let count = 0;
setTimeout(() => console.log('定时器执行时，微任务已跑了', count, '次'), 0);
function loop() {
  count += 1;
  if (count < 100000) Promise.resolve().then(loop);
}
loop();
// 定时器执行时，微任务已跑了 100000 次

定时器明明是 0 毫秒，可它要等 10 万个微任务全部跑完才轮到。换成浏览器，渲染和点击处理也是在后面等着的。

实际开发中哪些写法会踩到

最隐蔽的是用 await 循环处理大数组。每一步都 await 一个已经完成的 Promise，看起来“异步”了，其实整个循环还是在同一次微任务检查点里跑完的，没有让出主线程。

另外两种情况是没有终止条件的递归 Promise 链，以及在 MutationObserver 回调里修改被观察的 DOM，又触发新的回调。

改法：用任务把工作切开

大量数据要分片处理时，每处理一批就用 setTimeout 让出一次：

JavaScript
async function processInChunks(items, handle) {
  for (let i = 0; i < items.length; i++) {
    handle(items[i]);
    if (i % 500 === 499) {
      await new Promise((resolve) => setTimeout(resolve, 0));
    }
  }
}

每 500 项 await 一个定时器。后面的代码要等定时器这个任务来恢复，中间浏览器就能渲染、响应点击。

常见追问

为什么 await Promise.resolve() 不能让出主线程？

因为 await 后面的代码是在微任务里恢复的，还在同一个微任务检查点里，不会经过渲染。要让出，得等一个任务，比如 setTimeout。

那微任务适合做什么？

适合在当前任务结束前、渲染前做的收尾工作，比如把几次状态更新合并成一次。它的特点是“马上做、不让出”，所以不适合做大量计算。
