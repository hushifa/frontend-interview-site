前端依赖供应链风险应该怎样防范？

依赖的代码会在安装、构建和运行时执行，坏包可能是仿冒的、维护者账号被盗后发的，或者和内部包同名。防范要从选包、锁版本、限制安装脚本、隔离 CI 密钥一直做到保护自己的发布流程。

参考答案

简答

执行 npm install 时，你装进来的不只是自己选的那几个包，还有它们层层依赖的几百个包。这些代码会在安装、构建和运行时执行，其中任何一个有问题，都能读你的环境变量、改你的构建产物。这就是供应链风险。

防范从选包开始。核对包名和官方仓库地址，警惕 reacct 这种拼写相似的仿冒包；看维护是否活跃，不要为一个小函数引入一个依赖。然后是锁定，提交锁文件，CI 用 npm ci 严格按锁文件安装，版本变化只能通过审查过的提交进来。

执行环节要隔离。安装脚本能在开发机和 CI 上跑任意代码，要评估用 --ignore-scripts；处理外部贡献的 CI 任务不接触发布令牌和云密钥。自己发包时，npm 账号开启双因素认证，从 CI 带来源证明发布，限制发布权限。

要注意，npm audit 只覆盖已经公开的漏洞，零告警不代表没有风险。

有哪些攻击方式

类型例子主要防护
仿冒包reacct、lodahs核对包名，安装前检查
账号被盗或维护者作恶热门包的新版本里加了窃取代码锁文件、延迟升级、审查变更
依赖混淆公共仓库出现与内部包同名的包作用域映射，见《前端项目如何防范依赖混淆攻击？》
构建插件恶意 Vite、Babel 插件改写产物只用可信插件，审查构建配置
CDN 被篡改第三方托管的脚本被替换自托管或使用 SRI

最难防的是第二种。包是真的，作者也是真的，只是某个新版本被动了手脚。所以单靠“选对包”不够，还要控制新版本什么时候、怎样进来。

日常怎么做

bash
# CI 中按锁文件安装，不执行安装脚本
npm ci --ignore-scripts

# 查看某个包在安装时会执行什么
npm view some-package scripts

从第三方 CDN 加载脚本时，用 SRI 校验内容：

HTML
<!-- 从第三方 CDN 加载时用 SRI 校验内容 -->
<script
  src="https://cdn.example/lib@1.2.3/lib.min.js"
  integrity="sha384-..."
  crossorigin="anonymous"
></script>

integrity 里是文件内容的哈希。CDN 上的文件被换掉了，哈希对不上，浏览器就拒绝执行。

升级依赖也要讲究。Dependabot、Renovate 这类工具开的提交要经过审查，还可以设置成新版本发布若干天后再升级。为什么要等？因为不少恶意版本会在发布后不久被社区发现并下架，等一段时间能降低装到它的概率，但不能保证。

还有两件容易忽略的事。CI 里的 shell 命令不要直接拼接 PR 标题、分支名这类不可信输入，否则别人起个特殊的分支名就能注入命令。另外定期清理不用的依赖，依赖越少，攻击面越小。

自己发布包时

开启双因素认证，使用细粒度、有过期时间的访问令牌。从 CI 发布并生成来源证明，也就是 npm publish --provenance，使用者就能验证这个包是从哪个仓库、哪个工作流构建出来的。用 files 字段或 .npmignore 控制发布内容，避免把 .env 这类文件一起发出去。

常见追问

devDependencies 也有风险吗？

有。它们不会进生产代码，可是会在开发机和 CI 上执行，能读环境变量，也能修改构建产物。

有了锁文件就万无一失了吗？

不是。锁文件只防止“同一个版本号的内容被替换”和意外升级。如果审查通过的新版本本身就有问题，锁文件也会忠实地把它锁住。
