前端依赖供应链风险应该怎样防范？

依赖代码会在安装、构建和运行时执行，风险包括恶意包、维护者账号被盗后发布的恶意版本、拼写相似的仿冒包和依赖混淆。防范要覆盖选包、锁定版本、限制安装脚本、隔离 CI 密钥、审查升级和保护自己的发布流程。

参考答案

简答

  • 选包：核对包名和官方仓库地址，警惕拼写相似的仿冒包；关注维护活跃度和下载量，不引入只为一个小函数的依赖。
  • 锁定：提交锁文件，CI 用 npm ci 严格按锁文件安装，版本变化只能通过审查过的提交进入。
  • 执行与隔离：安装脚本可以在开发机和 CI 上运行任意代码，评估 --ignore-scripts；处理外部贡献的 CI 任务不接触发布令牌和云密钥。
  • 发布：自己的 npm 账号开启双因素认证，用带来源证明的方式从 CI 发布，限制发布权限。
  • npm audit 只覆盖已公开的漏洞，零告警不代表没有风险。

攻击类型

类型例子主要防护
仿冒包reacct、lodahs核对包名，安装前检查
账号被盗或维护者作恶热门包的新版本里加了窃取代码锁文件、延迟升级、审查变更
依赖混淆公共仓库出现与内部包同名的包作用域映射，见《前端项目如何防范依赖混淆攻击？》
构建插件恶意 Vite、Babel 插件改写产物只用可信插件，审查构建配置
CDN 被篡改第三方托管的脚本被替换自托管或使用 SRI

实践

bash
# CI 中按锁文件安装，不执行安装脚本
npm ci --ignore-scripts

# 查看某个包在安装时会执行什么
npm view some-package scripts
HTML
<!-- 从第三方 CDN 加载时用 SRI 校验内容 -->
<script
  src="https://cdn.example/lib@1.2.3/lib.min.js"
  integrity="sha384-..."
  crossorigin="anonymous"
></script>
  • 依赖升级工具（如 Dependabot、Renovate）的提交要经过审查，可以设置新版本发布若干天后再升级，给社区发现恶意版本留时间。
  • 把 CI 中的 shell 命令和不可信输入（PR 标题、分支名）隔离，不直接拼接进命令。
  • 定期清理不再使用的依赖，依赖越少攻击面越小。

自己发布包时

  • 开启双因素认证，使用细粒度、有过期时间的访问令牌。
  • 从 CI 发布并生成来源证明（npm publish --provenance），让使用者能验证包是从哪个仓库和工作流构建的。
  • 用 files 字段或 .npmignore 控制发布内容，避免把 .env 等文件发布出去。

常见追问

  • devDependencies 也有风险吗？有。它们在开发机和 CI 上执行，可以读取环境变量，也能修改构建产物。
  • 锁文件能防住一切吗？它只防止"同一版本号的内容被替换"以及意外升级；审查通过的新版本本身有问题，锁文件也会忠实地锁住它。
