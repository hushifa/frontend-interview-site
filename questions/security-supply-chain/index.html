前端依赖供应链风险应该怎样防范？

从依赖选择、锁文件、安装脚本、更新审查和发布权限说明前端项目的供应链安全边界。

参考答案

前端依赖不只是一些最终运行在浏览器里的函数。安装器、构建插件、测试工具和发布脚本都可能在开发机或 CI 上执行代码，接触源文件、环境变量和发布凭据。即使某个包只在 devDependencies 中，它也可能在打包时把恶意代码写进最终产物。

因此供应链安全要覆盖“选包、安装、构建、发布、运行”整条链，不能只看页面里有没有明显危险代码。

先确认安装的是正确的包

复制安装命令前应核对官方文档、包名和仓库，避免名称拼写相近的仿冒包。下载量和星数可以提供背景信息，但不能证明某个版本安全；维护者账号可能被接管，可信项目也可能引入有问题的传递依赖。

内部包还应使用明确的命名与 registry 配置，避免本应从内部源获取的依赖被同名公共包替代。评估新依赖时，看它承担的具体功能、维护情况、许可证、依赖数量和安装行为，而不是为了一个很小的功能引入庞大的不透明依赖树。

锁文件固定结果，但不会审查结果

package.json 中的版本范围说明允许哪些版本，锁文件记录这次解析到的具体依赖树和完整性信息。提交锁文件后，CI 可以使用：

sh
npm ci

npm ci 要求锁文件与 package.json 一致，不一致时失败，而不是悄悄更新依赖；它会清理已有 node_modules 后按锁文件安装。运行时、平台和安装配置仍会影响结果，所以“有锁文件”不等于不同机器上的全部行为完全相同。

integrity 可以检查下载内容是否与记录的摘要一致，但如果记录的本来就是恶意版本，摘要一致并不能把它变安全。更新时还要审查锁文件差异，留意新增依赖、下载来源变化和意外的大范围升级。

安装脚本与构建脚本都有执行权限

依赖的生命周期脚本可能下载二进制、编译原生模块，也可能读取环境并发起网络请求。对于不需要自动安装脚本的检查流程，可以评估：

sh
npm ci --ignore-scripts

这会影响正常依赖的准备工作，例如某些构建工具需要安装脚本获取平台二进制。因此不能全局禁用后不验证，也不能遇到构建失败就无条件对所有包重新开放。

ignore-scripts 不是进程沙箱，也不意味着之后执行 npm run build 没有风险。显式运行的脚本仍会执行，插件在构建时也可以运行任意 Node.js 代码。真正的隔离需要受限的构建环境、最小凭据和明确的网络及文件访问边界。

CI 不应把发布权限交给任意输入

普通检查任务不需要生产部署密钥。外部贡献的代码、PR 标题或分支名称都应视为不可信输入，尤其不能直接拼接进 shell。不要在能访问敏感令牌的任务里检出并运行未经信任的 PR 代码。

第三方工作流组件也是依赖。对敏感任务可固定到经过审查的提交引用，并制定升级流程；固定版本只减少静默变化，不证明固定的那份代码安全。发布使用最小权限和尽可能短期的凭证，对关键账号启用强认证，并控制谁能修改发布工作流。

前端公开包里的环境变量最终可能被直接替换进 JavaScript。变量名带有“环境”并不会使它保密，私钥、服务端 API 密钥和永久存储凭据都不应进入浏览器产物。

审计告警需要结合实际使用判断

npm audit 主要根据已知漏洞信息检查依赖，不是完整恶意代码扫描。零告警不能证明没有新漏洞或供应链攻击；有告警则应核对版本、调用路径、运行环境和可利用条件，再决定升级、替换或临时缓解。

不要只为了让数字归零就强制升级到不兼容版本。更新后应运行功能测试和构建，并检查关键产物差异。发布来源证明和签名有助于追溯产物由谁、在什么流程中生成，但也不保证源码业务逻辑没有恶意行为。

若发现可疑版本，先停止传播并确定影响范围，再回退到确认过的依赖和构建环境，检查是否泄露凭据并按需轮换。只删除 node_modules 再安装同一可疑锁文件，通常不会解决问题。

可靠的治理是可重复的流程：依赖变更有人审查、更新有测试、构建权限受限、产物能追溯、异常能撤回。它比单独复制一条安全命令更重要。
