React 流式 SSR 解决什么问题？

流式 SSR 先把 Suspense 边界以外的页面外壳发送给浏览器，慢的部分先显示 fallback，数据就绪后再以 HTML 片段和内联脚本补上。用户能更早看到内容，客户端也能按区域逐步 hydration。React 19.2 在此基础上新增了 resume 系列 API，用于部分预渲染。

参考答案

简答

传统 SSR 要等整页的数据都准备好，才能把 HTML 发出去。页面上只要有一个接口慢，整页都得等它，最慢的请求决定了首字节时间。

流式 SSR 就是边渲染边发。它以 <Suspense> 为边界，边界外面的页面外壳先发给浏览器，边界里面先显示 fallback；里面的内容准备好了，再接着往同一个响应里补，替换掉 fallback。Node 里用 renderToPipeableStream，Deno、边缘运行时这类 Web Streams 环境用 renderToReadableStream。

要注意状态码。响应一旦开始发送，状态码就改不了了，所以要在 onShellReady 或 onShellError 里设好。如果是 Suspense 边界里面出错，React 会发送 fallback，再在客户端重试渲染这一块。

React 19.2 又加了 resume、resumeToPipeableStream 等 API。prerender 现在能返回一个 postponed 状态，构建时先把静态部分预渲染好，请求时再从中断的地方接着渲染动态部分。

先看页面怎么划边界

JSX
function App() {
  return (
    <html>
      <body>
        <Header />
        <Suspense fallback={<p>评论加载中…</p>}>
          <Comments />
        </Suspense>
      </body>
    </html>
  );
}

Header 在边界外面，属于外壳，会先发出去。Comments 在边界里面，数据没好之前，浏览器先看到“评论加载中…”。

服务端怎么写

JavaScript
import { renderToPipeableStream } from 'react-dom/server';

app.get('*', (req, res) => {
  let didError = false;
  const { pipe, abort } = renderToPipeableStream(<App />, {
    bootstrapScripts: ['/main.js'],
    onShellReady() {
      res.statusCode = didError ? 500 : 200;
      res.setHeader('Content-Type', 'text/html');
      pipe(res);
    },
    onShellError() {
      res.statusCode = 500;
      res.send('<h1>出错了</h1>');
    },
    onError(err) {
      didError = true;
      console.error(err);
    },
  });
  setTimeout(() => abort(), 10_000);
});

这几个回调分别在不同时刻触发：

  • onShellReady：外壳渲染完成，可以开始发送了，所以状态码在这里设，然后 pipe 出去。
  • onShellError：外壳渲染失败。这时还一个字节都没发，所以还能换成一个备用页面。
  • onAllReady：全部内容都完成了。适合给爬虫或者静态生成用，但这时就没有渐进显示的效果了。
  • abort()：超时后不再等，把剩下边界的 fallback 发出去，由客户端接着渲染。

浏览器收到了什么

“补上内容”具体是怎么做到的？浏览器收到的东西分几批：

  1. 先是外壳 HTML，Comments 的位置是 fallback。
  2. 评论数据好了以后，同一个响应里追加一段隐藏的 HTML，再加一小段内联脚本，脚本把这段 HTML 挪到 fallback 的位置。
  3. 客户端 JS 加载后，React 可以先 hydration 已经到了的部分。用户如果点了某个还没 hydration 的区域，React 会优先处理那一块。

边界放在哪里，影响状态码

因为外壳一发出去状态码就定了，所以凡是决定 404 或者重定向的数据，都要放在外壳里加载，不能放进 Suspense。比如“这篇文章存不存在”，要在外壳阶段就查清楚。评论、推荐这种不影响状态码的内容，才放进 Suspense。

另外，React 19.2 起，服务端渲染出来的 Suspense 边界会被短暂地攒一批再显示，和客户端的行为保持一致。

部分预渲染是怎么回事

JavaScript
import { prerender } from 'react-dom/static';
import { resume } from 'react-dom/server';

// 构建时
const { prelude, postponed } = await prerender(<App />, { signal });
// 请求时
const stream = await resume(<App />, postponed);

构建时得到的 prelude 是静态 HTML，可以缓存到 CDN。postponed 记下了哪些部分要等到请求时才能完成。请求来了，resume 从这里接着渲染。Next.js 的 Cache Components 就基于这种模式，详见《Next.js App Router 中的几层缓存怎样区分？》。

React 19.2 也让 Web Streams 版本的 API 能在 Node 里用了。不过官方仍然推荐 Node 里用 Node Streams 版本，因为速度更快，而且支持压缩。

常见追问

流式输出对 SEO 有影响吗？

主流爬虫能处理流式 HTML。如果一定要保证爬虫拿到完整内容，可以对爬虫改用 onAllReady，等全部完成再发。

中间的代理会不会把响应攒起来？

会有这种情况。某些代理或压缩配置会等完整响应到了再转发，流式就失效了。所以部署时要确认流式输出真的生效了。
