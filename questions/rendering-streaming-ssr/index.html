React 流式 SSR 解决什么问题？

解释 renderToPipeableStream 的壳、Shell、Suspense 和错误处理边界，区分流式输出与客户端 hydration。

参考答案

流式 SSR 可以先发送已经准备好的 HTML 壳，再随着数据或组件准备完成继续输出内容，从而缩短首字节到可见内容的等待。Suspense 边界帮助服务器和客户端表达哪些部分可以稍后补齐。

在“React 流式 SSR 解决什么问题？”这个问题中，先比较服务端 HTML 与客户端首次输入，再检查时间、语言、随机数、权限和序列化差异；初始输出确定后再补浏览器状态。这里的 SSR、流式渲染、Suspense 不是孤立的 API 名称，而是会共同影响输入、过程和最终结果。

SSR 和客户端渲染问题要比较服务端 HTML、客户端首次渲染输入以及接管后的更新。时间、随机数、语言、时区、认证状态和浏览器专属对象都可能让两端得到不同结果。

流式输出不是“服务端生成后就能交互”。浏览器仍需要加载脚本并完成 hydration，事件才能接管；服务端和客户端的初始内容必须一致，否则会出现 hydration mismatch。错误处理要区分 Shell 发送前后，因为响应状态码和已经发送的字节无法同样处理。

生产实现还要处理请求取消、客户端断开、缓存、数据权限和代理是否支持长连接。不要把流式 SSR 当成所有页面的默认优化，先测量真实首屏和交互指标。

修复时优先让初始输出确定，再在客户端阶段补充只属于浏览器的状态。不要用关闭 SSR 或一味抑制警告掩盖局部不一致；还要验证刷新、直达链接和错误页面。

实际排查渲染问题时，先把服务端输出保存下来，再比较客户端第一次渲染的输入。不要直接把差异修成“客户端专属”，先确认差异是否来自时间、语言、权限或数据序列化。
