AI 前端应用为什么需要评测和可观测性？

接口返回 200 不代表答案正确。评测用固定样本和明确标准衡量质量；可观测性按阶段记录耗时、版本和用量，解释每次请求经历了什么。两者都要记录模型和提示词版本，日志默认脱敏。

参考答案

简答

  • 模型可以流畅地答错，工具可以返回 200 却改错了资源；用户主动停止也不一定是失败。所以不能只看成功率。
  • 评测回答"结果好不好"：先把目标写成可判断的标准，再用固定样本比较不同模型、提示词和检索策略。
  • 可观测性回答"这次请求经历了什么"：按阶段记录耗时、模型版本、token 用量和错误类型，用 trace ID 串起前后端。
  • 点赞和停留时间只是代理信号，关键样本要人工按评分标准复核。
  • 日志默认只存阶段、版本、用量和错误分类，需要原文时单独授权并设置保留期限。

评测标准举例

任务可判断的标准
文档问答结论是否被引用片段支持，关键断言是否都有引用
信息提取是否通过 Schema，字段值是否与原文一致
工具任务参数和目标资源是否正确，失败后是否正确恢复

样本要包含正常任务，也要包含没有答案、资料冲突、权限不足、恶意输入、超长输入。样本、判定规则、模型版本和提示词版本一起保存，否则换了标准后新旧分数无法比较。

前端该记录的阶段

text
提交 → 服务端开始 → 检索完成 → 首个可见内容 → 等待审批 → 工具完成 → 结束
  • 首个网络字节可能只是元数据，"首个可见内容"才是用户真正等到的时间。
  • 浏览器内耗时用 performance.now() 计算，不要拿浏览器时钟和服务端时钟直接相减。
  • 错误分开归类：模型拒答、用户取消、网络中断、工具失败、结果未知。

OpenTelemetry 的生成式 AI 语义约定定义了模型名、token 用量等通用属性名，用它可以让不同服务的数据放在一起分析。

从指标到修复

  • 引用覆盖率下降：检查召回、分段和引用映射。
  • 首个内容变慢：拆分排队、检索、模型首 token 和前端渲染的耗时。
  • 工具重复执行：检查幂等键和恢复流程。

修复后先跑固定评测，再分组观察线上数据。版本对比时按任务类型、设备和地区分组，避免把流量结构变化误判为版本问题。

常见追问

  • P95 能按天求平均得到周 P95 吗？ 不能。分位数要用整周的原始数据或直方图重新计算。
  • 用户删除数据后，评测样本怎么办？ 评测集和调试样本也要能撤回和替换，与用户数据的删除流程关联。
