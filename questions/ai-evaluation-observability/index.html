AI 前端应用为什么需要评测和可观测性？

AI 接口返回成功不代表答案正确。评测定义质量标准，可观测性解释请求经历的阶段、成本和失败原因，两者需要用同一套版本和样本口径连接起来。

参考答案

200 响应不能证明任务完成

模型可以流畅地答错，引用可以指向不支持结论的文档，工具也可能返回 200 但修改了错误资源。相反，用户主动停止长答案不一定是失败，可能已经得到了所需内容。

评测回答“结果是否达到目标”，可观测性回答“这次运行经过了哪些阶段，为什么会这样”。把它们都压成一个成功率，无法判断是质量、延迟、权限还是网络出了问题。

先把目标写成可判断的标准

文档问答可以评估结论是否被来源支持、引用是否覆盖关键断言；结构化提取可以检查 Schema、字段事实和缺失值；工具任务还要检查参数、目标资源、授权和失败恢复。

评测集应包含正常任务、无答案、冲突资料、权限不足、恶意内容、长输入和边界格式。高风险动作应有独立门槛，不能让大量简单摘要的高分掩盖一次越权写入。

固定且脱敏的样本便于比较模型、提示词和检索策略；线上抽样可以发现测试集之外的新问题。样本、判定规则、模型版本和提示版本都要保存，否则换了标准后，旧分数就无法比较。

指标要能解释用户等待

一次 AI 运行至少可以记录提交、服务端开始、检索完成、首个有用内容、等待审批、工具完成和最终结束。首个网络字节可能只是元数据，不等于用户看到了有用文本；语音还要区分首个音频数据和真正开始播放。

事件应使用 trace ID 和 run ID 关联，页面内耗时用 performance.now() 等单调时钟计算，不能直接把浏览器时间和服务端时间相减。工具失败、模型拒答、用户取消、网络中断和结果未知要有不同错误分类。

线上反馈不是天然真值

点赞、停留时间和重新提问都是代理信号。用户可能因为答案看起来流畅而点赞，也可能因为放弃而没有反馈。关键样本应由人工依据明确 rubric 复核，并保留正常任务与失败任务的比例。

发布新模型或提示词时，可以保留一部分对照流量，按任务类型、模型版本、设备和地区分组比较。分位数要结合样本量和时间窗口，不能把每天的 P95 简单求平均成整周 P95，也不能把流量结构变化误认为版本回归。

指标异常要能落到修复动作

引用覆盖率下降，先检查召回、分段和引用映射；首内容延迟上升，拆分排队、检索、模型首 Token 和前端渲染；工具重复执行，检查幂等、审批绑定和恢复协议。每个指标都应有阈值、负责人和处置动作。

修复后先运行固定评测，再观察线上分组数据、成本和错误率。一个测试集上的改善只能证明那个范围内的变化，不能宣称模型从此可靠。

可诊断不等于保存所有原文

提示词、附件、答案、URL 和工具结果可能包含个人或商业秘密。默认日志应保存阶段、版本、用量、错误分类和必要的脱敏标识，而不是完整会话。确实需要原文分析时，要有访问控制、保留期限、删除机制和受控抽样。

外链、文件名、错误堆栈和自定义 Header 也可能间接泄露内容。评测集本身要能撤回和替换，用户删除数据后，关联的调试样本和缓存也应有清理路径。
