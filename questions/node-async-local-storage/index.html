AsyncLocalStorage 如何在 Node.js 请求链路中传递上下文？

AsyncLocalStorage 在一次异步调用链里保存上下文，让深层的日志代码读到当前请求的 ID，并发请求之间互不干扰。原生 Promise、定时器和大多数核心 API 会自动传播上下文，EventEmitter 监听器、回调式库和 Worker 需要显式绑定或传递。

参考答案

简答

  • storage.run(store, fn) 让 fn 及其中启动的异步操作通过 getStore() 读到同一个 store，常用于请求 ID、trace 信息和日志关联。
  • 每次 run 有独立的 store，两个请求交错执行 await 也不会串用；在 run 之外调用 getStore() 返回 undefined。
  • 原生 Promise、定时器和大多数核心 API 会自动传播上下文。EventEmitter 监听器在触发 emit 的上下文中运行，需要 AsyncResource.bind 绑定；回调式第三方库可能丢失上下文。
  • Worker 线程不继承主线程的 store，需要在消息里显式传递请求 ID。
  • Node.js 24.0.0 起默认由 AsyncContextFrame 实现，可用 --no-async-context-frame 切回基于 async_hooks 的旧实现。

请求入口建立上下文

JavaScript
import { AsyncLocalStorage } from 'node:async_hooks';

const storage = new AsyncLocalStorage();

function log(message) {
  console.log(`${storage.getStore()?.requestId ?? '-'} ${message}`);
}

function handle(requestId, ms) {
  return storage.run({ requestId }, async () => {
    log('开始');
    await new Promise((resolve) => setTimeout(resolve, ms));
    log('完成');
  });
}

await Promise.all([handle('A', 30), handle('B', 5)]);
log('外部');

Node.js 22 实测输出：

text
A 开始
B 开始
B 完成
A 完成
- 外部

B 先完成，但两个请求的日志各自带着正确的 ID。真实服务里在 HTTP 处理函数的入口调用 run，请求 ID 由服务端生成，或者在校验格式后采用上游传来的值。

上下文丢失的场景

JavaScript
import { AsyncResource } from 'node:async_hooks';
import { EventEmitter } from 'node:events';

const emitter = new EventEmitter();
storage.run({ requestId: 'C' }, () => {
  emitter.on('x', () => log('普通监听'));
  emitter.on('x', AsyncResource.bind(() => log('绑定后的监听')));
});
storage.run({ requestId: 'D' }, () => emitter.emit('x'));
// D 普通监听
// C 绑定后的监听

普通监听器读到的是触发 emit 时的上下文 D，绑定后的监听器保留了注册时的上下文 C。其他常见情况：

场景处理方式
回调式 API用 util.promisify 转成 Promise，或用 AsyncResource 包装回调
自定义连接池、任务队列入队时用 AsyncResource.bind 绑定回调
Worker Threads在消息里传递请求 ID，Worker 内部重新 run
跨服务用 W3C Trace Context（traceparent 请求头）传递，进程内上下文不会跨网络

调试时，如果某条日志的 ID 变成 undefined，通常是它之前最近执行的那个回调丢失了上下文。

使用建议

  • 优先用 run()。enterWith() 仍是实验性 API，它会改变当前整段同步执行的上下文，容易让后续代码意外继承。
  • store 只放请求 ID、租户 ID 这类小而稳定的标识，可以用 Object.freeze 防止被下游改写。
  • 上下文用于日志关联，不用于授权判断；用户身份要从认证后的会话中取得。
  • store 中的数据会被复制到每条日志，不要放 Cookie、令牌和用户输入。

常见追问

  • 为什么不用模块级变量保存当前请求？ 并发请求会互相覆盖，第一个 await 之后读到的可能已经是另一个请求的值。
  • AsyncContextFrame 改变了什么？ 上下文改为随 V8 的 Promise 续体传播，不再依赖 async_hooks，开销更低，API 不变。官方说明两种实现的上下文流向在少数情况下可能不同，升级时要回归测试日志关联。
  • 和 diagnostics_channel 怎么配合？ 订阅者在收到诊断事件时调用 getStore() 给事件打上请求 ID，见《Node.js 的 diagnostics_channel 适合解决什么问题？》。
