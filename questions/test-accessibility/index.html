自动化无障碍检查为什么不能替代人工体验？

工具可以发现部分可访问名称、属性、颜色对比等问题。例如 Playwright 可结合 axe 检查当前页面状态。但规则通过并不说明操作流程对所有辅助技术都可理解，也不能自动判断所有文本描述是否准确。

参考答案

自动化工具可以发现很多可规则化的问题，例如表单缺少名称、部分 ARIA 使用错误和某些颜色对比不足。但它很难判断“这段说明是否能让用户理解”“错误后应该把焦点放在哪里”以及实际读屏操作是否顺畅。

所以扫描通过的准确含义是：在当前页面状态、当前工具规则与配置下，没有发现所报告的违规。它不是完整无障碍体验或合规性的证明。

页面状态决定扫描看到了什么

首页初始状态没有弹窗，不代表弹窗打开后也没有问题。表单错误、折叠菜单、加载结果和禁用状态都可能形成新的可访问性风险。

下面是假设有“编辑资料”弹窗的 Playwright 用例，需要安装 @axe-core/playwright 并配置实际测试站点：

TypeScript
import { expect, test } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('编辑弹窗打开后没有自动检测到的违规', async ({ page }) => {
  await page.goto('/profile');
  await page.getByRole('button', { name: '编辑资料' }).click();
  await expect(page.getByRole('dialog', { name: '编辑资料' })).toBeVisible();

  const result = await new AxeBuilder({ page }).analyze();
  expect(result.violations).toEqual([]);
});

测试先进入目标状态再扫描。若只限定扫描某个组件，会减少无关噪声，但可能漏掉整个文档层面的结构问题，所以局部与整页检查应有明确分工。

工具结果里需要人工复核的项目也不应被忽略。为了清零而禁用规则或排除复杂区域，只会缩小检测范围，不会让用户更容易使用。

键盘测试要验证完整操作路径

不使用鼠标完成打开弹窗、移动焦点、提交、处理错误和关闭。检查焦点是否可见，是否进入合理控件，是否被挡在视口外，关闭后是否返回合理位置。

弹窗通常还需要限制背景交互，防止 Tab 跑到不可见的背景按钮；但非模态弹层与模态弹窗并不采用完全相同规则。应按组件模式验证，而不是所有浮层都强行套一个焦点陷阱。

自动化可以模拟键盘并检查 document.activeElement，但这仍不能完整替代实际辅助技术体验。焦点放对了，不代表用户听到的名称、状态和操作说明也正确。

名称存在不代表名称准确

图片有 alt 属性，工具可能不再报告“缺少替代文本”，但 alt="图片" 对理解订单状态帮助很小。反过来，纯装饰图可能应该使用空替代文本，避免给用户增加噪声。

类似地，多个按钮都叫“点击这里”、错误提示只写“失败”，可能满足某些结构规则却难以完成任务。需要结合上下文判断说明是否清楚、内容是否重复、动态结果是否在合适时机播报。

真实体验还包括缩放和视觉设置

检查文本放大与页面缩放后是否丢失内容，窄视口下能否访问关键操作，高对比或强制颜色模式下控件是否仍可辨认。截图看着正常，不代表键盘焦点或状态变化对用户清晰。

对动态通知，确认读屏能适时感知而不会反复打断；对复杂表格和组合控件，确认角色、层级和操作方式符合用户预期。不同浏览器与辅助技术组合可能存在差异，应覆盖目标用户常用组合。

有效做法是把自动扫描放进日常回归，用键盘和人工辅助技术检查验证关键流程，并持续吸收真实用户反馈。自动化擅长快速拦住重复出现的基础错误，人工判断负责它看不到的语义和体验。
