时间戳、时区和只有日期的业务值应该怎样区分？

时间戳是一个确定的瞬间，时区决定它显示成哪个当地时间；生日这类只有日期的值不该转成 Date；未来的当地时间日程要保存本地时间加 IANA 时区。夏令时让“加一天”和“加 24 小时”结果不同，Temporal 为这三种语义提供了不同类型。

参考答案

简答

业务里的时间其实有三种，要分开存。已经发生的事件，比如订单创建时间，存时间戳；只有日期的值，比如生日，存 YYYY-MM-DD 字符串；未来的当地时间，比如每周一上午九点开会，存本地时间加 IANA 时区。

为什么要分？因为 Date 内部只是一个毫秒数，它不记得时区。同一个瞬间，在上海是 1 月 1 日 08:00，在纽约是 12 月 31 日 19:00。把生日转成 Date 也会出问题：new Date('2026-01-01') 按 UTC 解析，new Date('2026-01-01T00:00') 按本地时间解析，在西半球显示出来就成了前一天。

时区也有讲究。+08:00 是固定偏移，America/New_York 是带夏令时和历史规则的时区，二者不能互换。

要特别注意夏令时。切换那天，“加一天”可能只有 23 小时。Temporal 用 Instant、PlainDate、ZonedDateTime 分别表达这几种语义，它已进入 TC39 第 4 阶段。

同一个瞬间，显示成不同的时间

下面把同一个 UTC 时刻，分别按上海和纽约显示。

JavaScript
const instant = new Date('2026-01-01T00:00:00Z');

for (const timeZone of ['Asia/Shanghai', 'America/New_York']) {
  const text = new Intl.DateTimeFormat('en-GB', {
    timeZone,
    dateStyle: 'short',
    timeStyle: 'short',
  }).format(instant);
  console.log(timeZone, text);
}
// Asia/Shanghai 01/01/2026, 08:00
// America/New_York 31/12/2025, 19:00

instant 只有一个，变的只是显示用的时区。上海已经是新年早上，纽约还是前一天晚上，连年份都不一样。所以时间戳本身没有“几点”，“几点”是时区算出来的。

接口里还要写清楚时间戳的单位是秒还是毫秒。两者混用不会报错，只会得到一个合法但错误的日期，更难发现。

生日为什么不能转成 Date

先看一个只有日期的字符串被解析成什么。

JavaScript
new Date('2026-01-01').toISOString(); // '2026-01-01T00:00:00.000Z'，按 UTC 午夜解析

它被当成了 UTC 的午夜。纽约比 UTC 晚，这个时刻在纽约还是 12 月 31 日晚上，所以用户在西半球看到的生日就早了一天。

生日、账单日这种值本来就没有时区，直接存经过校验的 '1995-06-10' 字符串。显示时按年、月、日拆开格式化，不经过时区换算。校验时还要检查日期是否真实存在，比如 2 月 30 日不合法，不能指望 Date 自动进位成 3 月 2 日。

加一天和加 24 小时为什么不一样

2026 年 3 月 8 日，纽约进入夏令时，凌晨 2 点直接跳到 3 点，这一天只有 23 小时。

JavaScript
process.env.TZ = 'America/New_York'; // 在 Node 中设置，Windows 上命令行 TZ= 前缀可能不生效
const start = new Date(2026, 2, 7, 12); // 3 月 7 日中午

const nextDay = new Date(start);
nextDay.setDate(nextDay.getDate() + 1);
const plus24h = new Date(start.getTime() + 24 * 3600 * 1000);

nextDay.getHours(); // 12
plus24h.getHours(); // 13
(nextDay - start) / 3600000; // 23

setDate 加的是日历上的一天，所以第二天还是中午 12 点，但实际只过了 23 小时。直接加 24 小时的毫秒数，时钟就跑到了下午 1 点。两种都没错，只是语义不同：订闹钟要前者，算时长要后者。

秋季切换时反过来，同一个当地时间会出现两次。排班和预约系统要提前定好规则：碰到不存在的时间是报错还是顺延，碰到重复的时间选哪一个。

Temporal 怎样表达这些语义

Temporal 给每种语义一个独立的类型，不用再拿 Date 硬凑。

JavaScript
// 需要支持 Temporal 的运行时或 polyfill
const birthday = Temporal.PlainDate.from('1995-06-10'); // 没有时区
const meeting = Temporal.ZonedDateTime.from('2026-03-09T09:00[America/New_York]');
meeting.add({ days: 1 }); // 按日历加一天，仍是当地 09:00
meeting.add({ hours: 24 }); // 按时长加 24 小时

PlainDate 没有时区，正好对应生日。ZonedDateTime 带着 IANA 时区，加一天还是加 24 小时，写法上就区分开了。

Node 22 还没有内置 Temporal，用之前要做能力检测。

接口怎样约定

事件时间用带 Z 或偏移的 ISO 字符串，或者毫秒时间戳。纯日期用 YYYY-MM-DD。未来日程用本地日期时间加 IANA 时区，重复的日程另外存重复规则。不要传 01/02/2026 这种要猜地区才知道是 1 月 2 日还是 2 月 1 日的格式。

测试要覆盖跨日显示、夏令时前后、服务端和浏览器时区不同，以及无效日期。

常见追问

只存 UTC 时间戳不行吗？

过去的事件可以。未来的当地时间不行，因为时区规则可能被政府修改。如果只存了 UTC，规则一改，会议的当地时间就漂移了。

怎样显示时区名称？

用 Intl.DateTimeFormat 的 timeZoneName: 'short'，会输出 EDT 这样的缩写。
