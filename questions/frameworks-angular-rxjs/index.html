Angular 中 Observable 和 Signals 怎样协作？

Observable 适合描述随时间产生值、错误和完成的异步流，Signal 适合同步读取当前状态。Angular 可以互转，但转换会建立订阅，仍需明确生命周期、初始值、取消和错误模型。

参考答案

先按职责选择抽象

搜索框输入的防抖、去重、切换请求和错误恢复是时间流问题，RxJS 的操作符更适合；模板需要随时读取“当前搜索结果”和“当前加载状态”时，Signal 更自然。把所有 Observable 都改成 Signal，会丢掉取消、完成和多值流的语义；把所有状态都留在 Observable，又可能让模板读取变复杂。

一个常见边界是：RxJS 组织异步过程，Signal 暴露当前 UI 状态，computed 推导同步显示值，副作用由明确的生命周期管理。

toSignal 创建时就订阅

TypeScript
const results = toSignal(searchResults$, {
  initialValue: [],
});

toSignal 不是等模板第一次读取才订阅。创建时可能立即触发冷 Observable 的 HTTP 请求，所以应在稳定的组件或服务生命周期中创建一次并复用，不能在模板函数或每次变更检测中反复调用。

Observable 可能尚未发出值，因此要提供 initialValue、接受 undefined，或仅对订阅时同步发出的源使用 requireSync。requireSync 不会让异步 HTTP 变成同步请求，普通网络请求强行使用会抛错。

Signal 读取到源错误时可能抛出，源完成后通常保留最后一个值，不会自动变成“已完成”。如果界面需要加载、成功、失败和完成，应先在流中建立明确的状态模型：

TypeScript
const viewState$ = results$.pipe(
  map((data) => ({ kind: 'ready' as const, data })),
  startWith({ kind: 'loading' as const }),
  catchError((error) => of({ kind: 'error' as const, error })),
);
const viewState = toSignal(viewState$, { initialValue: { kind: 'loading' } });

生命周期决定订阅是否泄漏

在组件或注入上下文中创建的 toSignal 通常会随上下文销毁而退订。手动提供 injector 或使用 manualCleanup 会改变默认清理行为，只有源会自然完成或应用明确掌控结束时才适合。一个永不完成的流如果无人负责清理，会一直保留订阅。

仍需要直接 subscribe 时，可考虑 takeUntilDestroyed 等工具；不必为了每个订阅都先创建 Signal。toSignal 的价值是把当前值暴露给模板，不是替代所有流订阅。

toObservable 不是事件日志

Signal 表达当前状态，连续同步写入可能在稳定后只让 Observable 订阅者看到最后结果。若业务必须记录每次按键、拖动或操作，应使用显式事件流或日志，而不能从最终 Signal 值反推历史。

首次发射和后续调度要按 Angular 版本的互操作规则理解，不能把它等同于 Subject.next 的同步行为。状态同步和事件记录是两个不同需求。

RxJS 仍然决定取消和错误传播

搜索请求常见写法是 switchMap：新输入到来时取消旧订阅，但底层 fetch 是否真正中止取决于实现；即使客户端取消，也不代表服务端已经回滚写操作。catchError 放在内部请求流可以让外层输入继续工作，放在外层则可能让整个搜索流结束。

多个组件订阅同一个冷 Observable 可能发起重复请求。共享和缓存要根据刷新、引用计数、错误重试和数据过期语义决定；转换成 Signal 不会自动把它变成全局共享缓存。

实践中要明确每条边界：Observable 管理异步时间和取消，Signal 提供当前状态，computed 做纯同步派生，工具和网络副作用有明确的创建与清理位置。这样互操作才是在减少复杂度，而不是把同一状态在两种抽象之间来回搬运。
