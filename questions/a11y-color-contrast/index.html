无障碍色彩对比和状态表达应该怎样设计？

区分普通文本、大文本、图形和控件边界的对比要求，说明颜色不能承担唯一信息、焦点与错误状态如何表达，以及强制颜色模式下的降级。

参考答案

把错误文字改成红色、把“已完成”改成绿色，看起来很直观，但色觉差异、低亮度屏幕、强制颜色模式和环境光都会让一部分用户无法仅靠颜色区分状态。无障碍的目标不是让所有颜色都变成黑白，而是让信息在颜色改变或不可见时仍然可理解。

对比度不是只看两个十六进制颜色

WCAG 2.2 的 1.4.3（AA）要求普通文本通常至少 4.5:1，大文本至少 3:1。大文本的定义包含至少 18pt 的普通字体或至少 14pt 的粗体，按 96dpi 换算约为 24 CSS px 和 18.67 CSS px，不能仅因为设计稿把它叫“标题”就采用较低阈值。非文本内容另有适用条件，不能把普通文字规则直接套用所有图形。

对比度计算基于相对亮度，不是简单比较 RGB 三个数字的差值。文字还可能叠在渐变、图片、半透明层或动态背景上，不能只用设计稿中的单一背景色判断。

CSS
:root {
  --text: #172033;
  --surface: #ffffff;
  --danger: #b42318;
  --focus: #005fcc;
}

body {
  color: var(--text);
  background: var(--surface);
}

.error-message {
  color: var(--danger);
}

button:focus-visible,
input:focus-visible {
  outline: 3px solid var(--focus);
  outline-offset: 2px;
}

工具可以帮助检查候选颜色，但不能代替真实页面检查。字体抗锯齿、文字大小、背景图片和透明度都会影响实际可读性；一个颜色对比工具通过，不代表所有状态和主题都通过。

一个可运行的对比度计算示例

以下只接受 #RRGGBB 格式的不透明 sRGB 颜色，不解析透明度、渐变或 CSS Color 4 色域。先把 sRGB 分量线性化，再按相对亮度权重计算，最后用较亮与较暗的亮度求比值：

JavaScript
function luminance(hex) {
  if (typeof hex !== 'string' || !/^#[0-9a-f]{6}$/i.test(hex)) {
    throw new TypeError('只接受不透明的 #RRGGBB 颜色');
  }
  const channels = [1, 3, 5].map((start) => {
    const value = parseInt(hex.slice(start, start + 2), 16) / 255;
    return value <= 0.04045 ? value / 12.92 : ((value + 0.055) / 1.055) ** 2.4;
  });
  return 0.2126 * channels[0] + 0.7152 * channels[1] + 0.0722 * channels[2];
}

function contrastRatio(first, second) {
  const a = luminance(first);
  const b = luminance(second);
  return (Math.max(a, b) + 0.05) / (Math.min(a, b) + 0.05);
}

console.log(contrastRatio('#000000', '#ffffff')); // 21
console.log(contrastRatio('#ffffff', '#ffffff')); // 1
console.log(contrastRatio('#b42318', '#ffffff') >= 4.5); // true

展示时可以保留两位小数，是否达标则应使用未舍入的结果。半透明前景需要先按实际背景合成，图片背景需要考虑文字覆盖区域的变化；这个函数没有这些能力。它也不能判断字号、字重、例外条件或实际阅读体验，只计算两个已知颜色的比值。

颜色不能是唯一的信息通道

下面的提示同时使用图标、文字和语义属性，而不是只依赖红色边框：

HTML
<label for="email">邮箱</label>
<input
  id="email"
  type="email"
  aria-invalid="true"
  aria-describedby="email-error"
  value="wrong"
  class="field field--error"
>
<p id="email-error" class="error-message">
  <span aria-hidden="true">!</span>
  请输入有效的邮箱地址。
</p>

aria-invalid 表达字段状态，错误文字说明如何修复，图标只是辅助提示。CSS 可以再加边框或背景，但即使用户看不出红色，也应能通过文字、结构和读屏信息理解问题。

图表同样不能只用红绿区分两条线。可以加入不同线型、点形、直接标注和可访问数据表；地图热力图要考虑色盲用户、灰度显示和极端值，不要把彩虹渐变当成默认科学可视化方案。

文本、图标和控件边界要分别判断

禁用状态、占位文本和辅助说明经常被设计成低对比度，但“次要”或“不重要”不是任意降低文本对比度的理由。不可用控件中的文字、纯装饰等在标准中有特定例外；仍用于传达信息的帮助文字和 placeholder 通常要满足相应对比要求。placeholder 也不应承担字段名称或唯一提示。比例是阈值，不应将低于要求的结果四舍五入后判为通过。

图标按钮需要可访问名称，图标本身的颜色不应是唯一状态。选中、未选中、连接中和错误可以同时使用文字、形状、边框、aria-pressed、aria-selected 或状态区域表达。装饰图标则应避免重复朗读。

焦点指示器是控件可用性的必要部分。不要用 outline: none 后只留下颜色很接近背景的阴影；焦点应在相邻状态和不同主题中都清楚可见，并且不能被 overflow: hidden 裁掉。键盘用户需要知道当前操作位置，而不只是看到页面颜色改变。

主题、图片和透明度会改变实际结果

深色主题不能只把背景改黑，却保留一套在白底上设计的灰色文字。每个主题都要检查正文、次要文字、链接、边框、图标、焦点和错误状态。用户放大字体后，换行和控件尺寸也可能改变，不能只在默认字号下验收。

文字叠在图片或渐变上时，应增加稳定的背景层、文字阴影或单独的内容区域。阴影不能当作提高对比度的唯一修复；背景变化后它可能仍然不够清晰。半透明文字和半透明背景要按照合成后的实际颜色评估，不能只拿 CSS 源值送进工具。

还要考虑 prefers-contrast、forced-colors: active 和高对比系统设置。强制颜色模式可能替换背景、边框和文字颜色，依赖背景图或纯色装饰来表达状态的设计会失效：

CSS
@media (forced-colors: active) {
  .status-dot {
    border: 1px solid CanvasText;
    background: Canvas;
  }

  .status-dot[data-state="error"] {
    border-color: Mark;
    border-style: double;
    border-width: 3px;
  }
}

这个样式使用系统颜色并保留默认的强制颜色调整，同时用边框形态辅助区分。状态点旁仍应有“错误”等文字，不依赖系统颜色恰好不同来表达唯一信息。forced-color-adjust: none 会退出部分自动颜色调整，只有确实需要保留特殊图形且验证过系统配色时才局部使用，不能把它当成恢复原设计的默认开关。

自动检查和人工检查各自能证明什么

自动化工具可以发现部分文本对比度、缺少焦点样式或颜色规则问题，但无法判断文案是否清楚、图表是否可理解、焦点是否被遮挡，也不能覆盖所有浏览器和系统颜色模式。截图测试同样可能在默认主题下通过，却在高对比模式下完全失效。

验收至少包括：

  • 普通文本、链接、错误、禁用、悬停、聚焦和选中状态；
  • 浅色、深色、系统高对比和强制颜色模式；
  • 灰度显示、低亮度屏幕、文字放大和窄视口；
  • 不看颜色时能否通过文字、形状、位置或语义理解状态；
  • 键盘焦点是否清晰，读屏用户是否能获得同样的状态信息。

对比度只是可访问性的一部分。一个颜色数字满足最低比例，不代表页面的层级、焦点、文案和操作路径已经可用；把视觉检查、自动规则和真实用户流程结合起来，才能知道设计是否真的帮助用户完成任务。
