File System Access API 的权限和文件句柄怎样管理？

理解用户选择文件、读写句柄、权限重新确认和浏览器兼容性，避免把本地文件当成普通 URL。

参考答案

普通文件选择得到 File，主要用于读取所选数据；File System Access 的选择器可以返回文件或目录句柄，让应用在授权范围内再次访问，甚至写回用户选择的位置。

句柄代表一种受权限控制的访问能力，不是网页拿到了整块磁盘，也不是一个可以自由拼接路径的普通字符串。

用户选择与权限范围是入口

showOpenFilePicker、showSaveFilePicker 等能力需要支持它们的浏览器、安全上下文及相应用户激活。应从打开或保存按钮触发，并处理用户取消，而不是页面加载后自动扫描文件。

文件句柄可以通过 getFile 得到可读取的 File。保存到外部文件通常还需要 readwrite 权限，已有读取权限不等于写入权限。

句柄的 queryPermission/requestPermission 与 Permissions.query 不是同一个调用接口。重新打开页面后，即使保存过句柄，也可能需要重新确认权限；不应把曾经授权作为永久事实。

一次完整保存要等待 close

下面的函数从用户“另存为”操作中调用，text 已经准备好：

JavaScript
async function saveTextFile(text) {
  if (!window.showSaveFilePicker) {
    return { saved: false, reason: 'unsupported' };
  }

  let handle;
  try {
    handle = await window.showSaveFilePicker({
      suggestedName: 'notes.txt',
      types: [{ description: '文本文件', accept: { 'text/plain': ['.txt'] } }],
    });
  } catch (error) {
    if (error?.name === 'AbortError') return { saved: false, reason: 'cancelled' };
    throw error;
  }

  const writable = await handle.createWritable();
  try {
    await writable.write(text);
    await writable.close();
    return { saved: true, handle };
  } catch (error) {
    try {
      await writable.abort();
    } catch {
      // 流可能已经失败或关闭，保留原始保存错误。
    }
    throw error;
  }
}

write 完成不代表全部保存已经提交；应等待 close 成功再提示“已保存”。这种写入通常通过临时内容再替换目标实现，但应用仍需处理 close 失败，不能承诺任意系统崩溃场景下都绝对不会丢数据。

示例把选择器取消当作正常结果，其他权限、空间或 I/O 错误交给调用方显示。没有开启 keepExistingData 的写入通常从空内容开始，适合完整替换；局部编辑必须明确保留、seek 和 truncate 的语义，避免把原文件尾部处理错。

文件可能在应用之外改变

其他程序、浏览器标签页或用户都可能修改、移动、删除文件。之前拿到的 File 不一定永远能继续读取；需要时重新 getFile，并对读写错误给出恢复路径。

并发编辑不能只靠保存按钮解决。可记录上次读取时的元信息或内容版本，在保存前提示外部变化；严格冲突检测还应根据实际平台能力设计，不能把时间戳比较当成完美事务锁。

保存成功也不要自动丢弃所有内存草稿，尤其在需要撤销或错误恢复的编辑器中。文件写入与编辑历史是不同层次的状态。

保存句柄不代表保存了权限

支持的环境中可通过 IndexedDB 等结构化克隆机制保存句柄，便于下次继续选择记录。JSON.stringify 不是序列化文件能力的通用方法。

恢复后仍要查询权限并在适当用户操作时请求，处理授权拒绝、句柄无效和文件不存在。界面可以显示最近文件，但不能在用户不知情时把它们全部读取或写入。

OPFS 与用户文件选择器要区分

Origin Private File System 是来源私有的存储空间，用户通常不会像普通文档目录那样直接看到它。它适合应用内部数据和缓存，但受配额、清理及来源隔离约束。

拥有 OPFS 不等于支持系统文件选择器，也不等于可以写入用户 Documents 目录。同步访问句柄等能力还有执行环境限制，应按具体 API 使用，不要把整个 File System API 当成一个支持度完全相同的功能。

不支持外部句柄时，可退回 input type="file" 读取与下载副本保存，但这通常不是对原文件直接覆盖。降级界面应说明差异，让用户知道保存在哪里，而不是仍显示同一套误导性的“已覆盖原文件”。
