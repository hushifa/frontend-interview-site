AI 结构化输出为什么仍需要 Schema 校验？

合法 JSON 不代表字段类型、范围和业务含义正确。服务商的结构化输出模式能提高符合率，应用仍要做 JSON 解析、运行时 Schema 校验和业务核验；流式的部分对象只能预览。

参考答案

简答

  • {"quantity":"很多"} 是合法 JSON，但数量不是整数；{"productId":"不存在"} 结构对，商品却不存在。
  • TypeScript 的 as Order 只影响编译期，运行时不做任何检查。外部数据要经过 Zod、Valibot 这类运行时校验。
  • 服务商的结构化输出模式是第一道防线，应用的 Schema 校验和业务核验（商品是否存在、库存、权限）是第二道。
  • 价格、用户角色、approved 这类字段不能由模型提供，要从可信服务重新获取。
  • 流式输出的部分对象只用于预览，完成并通过校验后才能执行；校验失败时的重试要有次数上限。

运行时校验示例

TypeScript
import { z } from 'zod';

const DraftSchema = z.strictObject({
  productId: z.string().regex(/^[A-Za-z0-9_-]{1,64}$/),
  quantity: z.number().int().min(1).max(100),
});

type ParseResult =
  | { ok: true; data: z.infer<typeof DraftSchema> }
  | { ok: false; reason: 'invalid-json' | 'invalid-schema' };

function parseDraft(text: string): ParseResult {
  let value: unknown;
  try {
    value = JSON.parse(text);
  } catch {
    return { ok: false, reason: 'invalid-json' };
  }
  const result = DraftSchema.safeParse(value);
  return result.success
    ? { ok: true, data: result.data }
    : { ok: false, reason: 'invalid-schema' };
}

z.strictObject 遇到未知字段直接拒绝，防止模型塞进 isAdmin: true 之类的字段被后续代码误用。也可以选择剥离未知字段，但要明确选择，不要依赖库的默认行为。

两道防线各管什么

服务商结构化输出应用校验
作用让模型尽量按 JSON Schema 生成拒绝不符合契约的数据
能检查类型、必填字段、枚举加上自定义规则和跨字段关系
不能检查商品是否存在、库存、权限商品是否存在、库存、权限（需要业务层）

服务商支持的 JSON Schema 通常只是一个子集，复杂规则要在应用里补。

流式对象

AI SDK 的 streamObject 等接口会在生成中途返回部分对象，例如只有 productId、还没有 quantity。可以展示成草稿，但保存、下单、调用工具要等最终对象通过校验。

生成被停止或断线时，不要给缺失字段补默认值，例如把数量默认成 1，这可能造成用户没确认过的订单。应标记为不完整，让用户重新生成或手动填写。

失败处理

  • 校验失败后可以把错误信息交给模型重试一次或两次，超过上限就交给用户处理。
  • 不要用正则从解释文本里截取第一对大括号，也不要用 eval 解析"像对象的字符串"。

常见追问

  • 服务商保证 100% 符合 Schema，还需要校验吗？ 需要。输出可能被截断，Schema 也表达不了业务规则，而且服务商、模型版本随时可能更换。
  • 校验应放在前端还是后端？ 两边都做。前端校验用于即时提示，后端校验才是安全边界。
