AI 结构化输出为什么仍需要 Schema 校验？

是合法的 JSON，不代表字段类型、取值范围和业务含义都对。服务商的结构化输出模式能让模型更守规矩，应用自己还要做 JSON 解析、运行时校验和业务检查；流式输出的半成品对象只能拿来预览。

参考答案

简答

因为合法的 JSON 不等于正确的数据。比如 {"quantity":"很多"} 能解析，但数量不是整数；{"productId":"不存在"} 格式没问题，商品却根本没有。

TypeScript 的 as Order 帮不上忙，它只在编译时起作用，运行时什么都不检查。外部来的数据要用 Zod、Valibot 这类库在运行时校验。

服务商的结构化输出模式是第一道防线，能让模型尽量按格式生成；应用自己的 Schema 校验和业务检查是第二道，比如商品存不存在、库存够不够、用户有没有权限。价格、用户角色、approved 这类字段，根本不能让模型提供，要从可信的服务重新取。

流式输出时，中途拿到的半个对象只能用来预览，要等完整生成并通过校验才能执行。校验失败可以让模型重试，但次数要有上限。

运行时校验怎么写

下面用 Zod 定义一个下单草稿的格式，然后分两步检查：先看是不是合法 JSON，再看符不符合格式。

TypeScript
import { z } from 'zod';

const DraftSchema = z.strictObject({
  productId: z.string().regex(/^[A-Za-z0-9_-]{1,64}$/),
  quantity: z.number().int().min(1).max(100),
});

type ParseResult =
  | { ok: true; data: z.infer<typeof DraftSchema> }
  | { ok: false; reason: 'invalid-json' | 'invalid-schema' };

function parseDraft(text: string): ParseResult {
  let value: unknown;
  try {
    value = JSON.parse(text);
  } catch {
    return { ok: false, reason: 'invalid-json' };
  }
  const result = DraftSchema.safeParse(value);
  return result.success
    ? { ok: true, data: result.data }
    : { ok: false, reason: 'invalid-schema' };
}

两种失败原因分开返回，是因为处理方式可能不同：JSON 坏了多半是输出被截断，格式不对则是模型理解错了，重试时给它的提示也不一样。

为什么用 z.strictObject？它碰到没定义的字段会直接拒绝。如果模型多塞了一个 isAdmin: true，后面的代码又恰好用了展开运算符把整个对象传下去，这个字段就可能被误用。你也可以选择把多余字段剥掉，但这是要明确做的选择，不要依赖库的默认行为。

两道防线分别管什么

服务商结构化输出应用校验
作用让模型尽量按 JSON Schema 生成拒绝不符合契约的数据
能检查类型、必填字段、枚举加上自定义规则和跨字段关系
不能检查商品是否存在、库存、权限商品是否存在、库存、权限（需要业务层）

还要知道，服务商支持的 JSON Schema 通常只是完整规范的一部分，复杂一点的规则，要在应用里自己补上。

流式输出的半成品对象怎么办

AI SDK 的 streamObject 这类接口，会在生成过程中不断返回部分对象，比如已经有 productId、还没有 quantity。这个可以显示成草稿给用户看，但保存、下单、调用工具，都要等最终对象通过校验。

如果生成被停止了，或者断线了，缺的字段不要自己补默认值。比如把数量默认成 1，看起来很贴心，结果可能是一张用户从没确认过的订单。正确做法是标成“不完整”，让用户重新生成或者手动填。

校验失败以后

可以把错误信息交给模型，让它重试一两次，超过上限就交给用户处理。

不要用正则从模型的解释文字里截第一对大括号，也不要用 eval 去解析“看起来像对象的字符串”。前者很容易截错，后者等于执行模型写的代码。

常见追问

服务商保证 100% 符合 Schema，还需要校验吗？

需要。输出可能被截断，Schema 也表达不了业务规则，而且服务商和模型版本随时可能换。

校验应该放在前端还是后端？

两边都做。前端校验是为了及时给用户提示，后端校验才是安全边界，因为前端的代码用户可以改。
