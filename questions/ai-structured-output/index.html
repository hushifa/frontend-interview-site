AI 结构化输出为什么仍需要 Schema 校验？

“返回 JSON”只描述格式愿望，不能证明输出完整、字段符合运行时契约或数据允许执行。结构化输出仍需解析、Schema 校验、业务核验和安全展示。

参考答案

JSON 合法不等于应用可以使用

{"quantity":"很多"} 是合法 JSON，但数量不是应用需要的整数；{"productId":"不存在","quantity":2} 结构正确，却不能直接创建订单。模型还可能输出截断对象、缺失字段、未知字段或夹带解释文本。

TypeScript 的 as Order 只改变编译器的看法，不会在运行时检查数据。结构化输出模式能提高符合度，但仍可能受模型能力、Schema 子集、网络截断和业务语义影响。

让所有外部数据经过运行时入口

TypeScript
import { z } from 'zod';

const DraftSchema = z.strictObject({
  productId: z.string().regex(/^[A-Za-z0-9_-]{1,64}$/),
  quantity: z.number().int().min(1).max(100),
});

function parseDraft(text: string) {
  let value: unknown;
  try {
    value = JSON.parse(text);
  } catch {
    return { ok: false, reason: 'invalid-json' as const };
  }

  const result = DraftSchema.safeParse(value);
  if (!result.success) return { ok: false, reason: 'invalid-schema' as const };
  return { ok: true, data: result.data };
}

Schema 约束了类型、范围和字段集合，但 productId 格式正确不代表商品存在，数量合法也不代表库存足够。价格、用户身份、角色、权限和 approved 字段不能由模型提供，必须从可信服务和当前会话重新取得。

未知字段是协议选择：可以严格拒绝、明确剥离或保留到另一个扩展字段，但不能让库默认行为悄悄把 role、isAdmin 或 approved 变成可信控制值。

生成约束和应用校验是两道防线

服务商或 SDK 的结构化输出可以帮助模型更接近 Schema，生成完成时也可能提供验证结果。要确认读取的是最终已验证对象，还是流式预览中的部分对象。模型支持的 JSON Schema 子集可能不支持自定义 refinement、跨字段关系和所有业务规则。

因此应用和执行端仍要检查事实、资源归属、版本、权限和状态。Schema 合法的日期可能已过期，合法的引用可能属于另一个租户，合法的金额可能与当前价格不一致。

流式对象只能展示，不能提前执行

中途可能只有 productId，嵌套对象也可能尚未闭合。界面可以把部分字段作为草案预览，但不能因为当前看起来合理就保存、下单或调用有副作用工具。只有协议确认正常完成、获得最终对象并通过校验后，才能进入下一阶段。

用户停止、超时和断线后，不能给缺失字段补默认值来伪装完整结果。前端应标记为不完整，允许重新生成或让用户手动修正。

修复和重试必须有上限

格式错误可以重新生成、提示用户修改或放弃，但修复次数、总时长和费用必须有限。模型与校验器无限互相纠错，会把一次简单失败变成不可控循环。

不要用正则从解释文本中截第一对大括号，也不要用 eval 解析“像 JavaScript 的对象”。去掉代码围栏等兼容步骤也要有明确协议和失败路径，不能默默吞掉真正的格式错误。

高风险数据缺失时不能填入会改变业务的默认值。数量缺失默认 1 可能导致用户未确认的订单，更安全的流程是回到草案或人工确认。

测试要覆盖非法 JSON、截断、类型错误、边界数值、未知字段、结构合法但业务拒绝、权限变化和重复执行。结构整齐只是输入契约的一部分，安全可用还需要可信数据和业务校验。
