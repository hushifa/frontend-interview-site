dns-prefetch、preconnect 和 preload 应该怎样选择？

dns-prefetch 只提前解析域名，preconnect 提前完成 DNS、TCP 和 TLS，preload 提前下载当前页面一定会用到的具体资源。提示越重成本越高，只用于确定的、关键的少数资源。

参考答案

简答

  • dns-prefetch：只做 DNS 解析，成本最低，适合可能用到的第三方域名。
  • preconnect：完成 DNS、TCP、TLS 握手，适合马上就会请求、且只有少数几个的关键域名。连接没有被使用时，浏览器会在一段时间后关闭它，时长取决于浏览器，用不到就白白浪费。
  • preload：下载指定资源并放入缓存，但不执行脚本、不应用样式。适合浏览器发现得晚的关键资源，如 CSS 里引用的字体、JS 才插入的首屏图片。
  • preload 必须写对 as；字体等以 CORS 模式请求的资源还要加 crossorigin，否则缓存匹配失败，资源会下载两次。

写法

HTML
<link rel="preconnect" href="https://fonts.example" crossorigin />
<link rel="dns-prefetch" href="https://analytics.example" />

<link rel="preload" href="/fonts/inter.woff2" as="font" type="font/woff2" crossorigin />
<link rel="preload" as="image" href="/hero.avif" fetchpriority="high" />
<link rel="modulepreload" href="/assets/app.js" />
  • preconnect 的 crossorigin 要和后续请求一致：字体用 CORS 模式请求，就需要带 crossorigin 的连接。
  • type 让浏览器在不支持该格式时跳过下载。
  • modulepreload 用于 ES 模块，会下载并解析模块，比 preload as="script" 更合适。
  • 响应式图片可以用 imagesrcset 和 imagesizes 预加载正确尺寸，取值必须和 <img> 的 srcset、sizes 完全一致，否则浏览器会按两套规则各选一张，下载两次。
  • preload 不能像 <picture> 那样按格式回退。同时 preload AVIF 和 WebP，支持两者的浏览器会两张都下载；只 preload 目标浏览器一定会用到的那一种，或在 <link> 上用 type 让不支持的浏览器跳过。

怎么判断该不该用

  • 资源在 HTML 里本来就能被扫描到（普通 <img>、<script>），通常不需要 preload，浏览器的预加载扫描器已经会提前发现。
  • preload 的资源会和其他资源竞争带宽，预加载太多会推迟真正关键的资源。
  • preload 后约 3 秒内没被使用，Chrome 控制台会警告，说明资源没用上或 as、crossorigin 不匹配。
  • 想提高某个已发现资源的优先级，用 fetchpriority，见《fetchpriority 能解决资源加载优先级问题吗？》。
  • 下一个页面才用到的资源用 prefetch，以低优先级下载；预取整个下一页可以用 Speculation Rules。

也可以用响应头

http
Link: </fonts/inter.woff2>; rel=preload; as=font; type="font/woff2"; crossorigin

配合 103 Early Hints，服务器可以在生成 HTML 前就发出这些提示，见《HTTP 103 Early Hints 适合怎样的加载优化？》。

常见追问

  • 为什么首屏图片用了 loading="lazy" 还 preload？两者矛盾，首屏图片不要懒加载。
  • 怎么验证效果？看 DevTools 瀑布图中资源的开始时间是否提前，以及 LCP 是否改善。
