dns-prefetch、preconnect 和 preload 应该怎样选择？

dns-prefetch 只提前查域名，preconnect 提前把连接建好，preload 提前下载当前页面一定会用的某个文件。越往后越重、越费资源，只给少数确定关键的资源用。

参考答案

简答

这三个都是告诉浏览器“提前做点准备”，区别是准备到哪一步。

dns-prefetch 只提前把域名解析成 IP，成本最低，适合可能会用到的第三方域名。preconnect 更进一步，把 DNS、TCP、TLS 握手都做完，适合马上就要请求、而且只有少数几个的关键域名。连接建好了却没人用，浏览器过一阵会关掉它，具体多久看浏览器，等于白建。

preload 是直接把某个文件下载下来放进缓存，但不执行脚本、不应用样式。它适合浏览器发现得晚的关键资源，比如 CSS 里引用的字体、JS 才插进页面的首屏图片。

用 preload 要注意两点：as 必须写对；字体这类以 CORS 模式请求的资源还要加 crossorigin。不然缓存对不上，同一个文件会下载两次。

怎么写

HTML
<link rel="preconnect" href="https://fonts.example" crossorigin />
<link rel="dns-prefetch" href="https://analytics.example" />

<link rel="preload" href="/fonts/inter.woff2" as="font" type="font/woff2" crossorigin />
<link rel="preload" as="image" href="/hero.avif" fetchpriority="high" />
<link rel="modulepreload" href="/assets/app.js" />

先看第一行为什么带 crossorigin。浏览器会把 CORS 模式和普通模式的连接分开用。字体是用 CORS 模式请求的，所以提前建的连接也要带 crossorigin，不然建好的连接字体用不上。

字体那行的 type 是给浏览器一个机会：不支持这个格式，就直接跳过，不下载。

最后一行的 modulepreload 是专门给 ES 模块用的，它会下载并解析模块，比 preload as="script" 更合适。

响应式图片和多格式容易下载两次

响应式图片可以用 imagesrcset 和 imagesizes 预加载正确尺寸的那张。但这两个值必须和 <img> 上的 srcset、sizes 完全一致。不一致的话，浏览器会按两套规则各挑一张，结果下载两次。

格式也一样。preload 不能像 <picture> 那样按格式回退。你同时 preload 了 AVIF 和 WebP，两种都支持的浏览器就会两张都下。所以只 preload 目标浏览器一定会用的那一种，或者在 <link> 上写 type，让不支持的浏览器跳过。

怎么判断该不该用

资源如果本来就写在 HTML 里，比如普通的 <img>、<script>，一般不用 preload。浏览器有个预加载扫描器，会提前扫 HTML 发现它们。

preload 也不是越多越好。预加载的资源会和其他资源抢带宽，预加载太多，真正关键的反而被推后。

预加载了却没用上，Chrome 会在大约 3 秒后在控制台警告。看到警告，要么是资源确实没用，要么是 as、crossorigin 写得不匹配。

另外两个相关的工具：想提高某个已经被发现的资源的优先级，用 fetchpriority，见《fetchpriority 能解决资源加载优先级问题吗？》；下一个页面才用的资源用 prefetch，它以低优先级下载，预取整个下一页可以用 Speculation Rules。

也可以写在响应头里

http
Link: </fonts/inter.woff2>; rel=preload; as=font; type="font/woff2"; crossorigin

配合 103 Early Hints，服务器可以在 HTML 还没生成时就先把这些提示发出去，见《HTTP 103 Early Hints 适合怎样的加载优化？》。

常见追问

首屏图片加了 loading="lazy"，又 preload 了？

这两个是矛盾的，一个说晚点加载，一个说赶紧加载。首屏图片不要懒加载。

怎么验证有没有效果？

看 DevTools 瀑布图里资源开始下载的时间有没有提前，再看 LCP 有没有改善。
