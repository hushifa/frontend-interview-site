dns-prefetch 和 preconnect 分别把连接的哪几步提前了？

请求一个新的跨域源要先查 DNS、建 TCP 连接，HTTPS 还要做 TLS 握手。dns-prefetch 只提前做 DNS 查询；preconnect 把 DNS 和 TCP 都做完，HTTPS 源连 TLS 握手也做完。两者都只对跨域源有用，preconnect 只留给最关键的几个源，字体这类匿名 CORS 请求要加 crossorigin。

参考答案

简答

页面要从 https://fonts.example 加载字体。浏览器第一次向这个源发请求前，要先把域名解析成 IP，再建立 TCP 连接，因为是 HTTPS，还要做 TLS 握手。这几步每一步都要等网络往返，做完了才能真正发出请求。

dns-prefetch 只把第一步 DNS 查询提前。preconnect 把握手提前做完，MDN 的说法是：HTTP 源提前做 DNS 加 TCP，HTTPS 源提前做 DNS、TCP 加 TLS。等页面真的请求这个源时，连接已经在那里了。

两者都只对跨域的源有用。自己站点的域名在浏览器看到提示时已经解析过了，连接也已经开着，再写一遍没有收益。

preconnect 做得多，代价也大。MDN 提醒，给很多第三方域名都写 preconnect 会适得其反，它只适合最关键的几个连接，其余的用 dns-prefetch 省下 DNS 查询时间就够了。字体这类以匿名模式加载的资源，preconnect 要加 crossorigin，否则浏览器只做 DNS 查询。

一次跨域请求前要做哪些事

以 HTTPS 为例，浏览器访问一个从没连过的源，顺序是：DNS 解析拿到 IP；TCP 三次握手建立连接；TLS 握手协商加密参数；最后才发出 HTTP 请求。前三步和要下载什么文件无关，只和“连到哪个源”有关，所以可以在知道具体文件之前就提前做。

MDN 解释 dns-prefetch 时提到，DNS 缓存能减少延迟，但 DNS 解析仍可能给请求增加明显的延迟，页面连接的第三方越多，这部分影响越大。TCP 和 TLS 握手同样要等往返，各阶段的耗时见《DNS、TCP 和 TLS 握手分别会给页面增加哪些等待？》。

怎么写

HTML
<!-- 关键源：把连接建好，字体是匿名 CORS 请求，要加 crossorigin -->
<link rel="preconnect" href="https://fonts.example" crossorigin />
<!-- 同一个源也写 dns-prefetch，不支持 preconnect 的浏览器可以退回 -->
<link rel="dns-prefetch" href="https://fonts.example" />
<!-- 次要的第三方：只提前查 DNS -->
<link rel="dns-prefetch" href="https://analytics.example" />

为什么同一个源两个都写？MDN 的解释是，dns-prefetch 的支持比 preconnect 更好，不支持 preconnect 的浏览器还能退回到 dns-prefetch，拿到一部分收益。

字体那行的 crossorigin 容易漏。MDN 说明，字体等资源以匿名模式加载，这时 preconnect 要设置 crossorigin；不写的话，浏览器只会做 DNS 查询，提前建好的连接用不上。

怎样决定给哪些源用

先列出首屏会访问的跨域源，比如字体、图片 CDN、接口域名、统计脚本。马上就要请求、又在关键路径上的一两个源用 preconnect；可能会用到、或者不那么急的，用 dns-prefetch。MDN 对 preconnect 的说法是“只用于最关键的连接”，没有给出具体数量，要用实际页面的瀑布图验证。

这两个提示也可以写在响应头里，浏览器收到响应头就能开始准备，不用等 HTML 解析到 <head>：

http
Link: <https://fonts.example>; rel=preconnect
Link: <https://fonts.example>; rel=dns-prefetch

连接准备好以后，具体文件怎样提前下载、以什么优先级下载，是 preload、modulepreload 和 prefetch 的事，见《preload、modulepreload 和 prefetch 怎样安排资源的加载优先级？》。

常见追问

给自己的域名写 preconnect 有用吗？

没有用。MDN 说明 preconnect 对同源请求没有收益，因为连接已经开着；dns-prefetch 也一样，浏览器看到提示时自己域名的 IP 已经解析过了。

怎么验证 preconnect 生效了？

在 DevTools 网络面板里看这个源的第一个真实请求的耗时分解。提示生效时，DNS、建连和 TLS 这几段已经在请求之前完成，不再出现在这个请求的等待里；如果字体请求仍然重新建连接，先检查 preconnect 是否漏了 crossorigin。
