页面关闭时怎样可靠上报？sendBeacon 和 keepalive 怎么选？

在 visibilitychange 变成 hidden 时上报，不要依赖 unload/beforeunload；sendBeacon 只能发 POST，只返回是否入队；fetch keepalive 可以自定义请求、读响应；fetchLater 由浏览器在页面离开或超时时代发，目前只有 Chromium 支持。

参考答案

简答

页面关闭时上报，最大的问题是抓不准时机。unload 和 beforeunload 在移动端经常不触发，unload 还会让页面进不了 bfcache。所以上报时机要选 visibilitychange，在 visibilityState 变成 hidden 时发。

发送方式常用两种。sendBeacon 只能发 POST，只告诉你有没有放进发送队列；fetch 加 keepalive 可以自定义请求，也能读响应。两者共用 64 KiB 的配额，一个超额了换另一个也会失败，所以要平时分批发，控制单次体积。

还有一个新的 fetchLater，是先把请求登记给浏览器，页面离开或者到了 activateAfter 设定的时间，浏览器替你发出去，适合“先登记、最后再发”的数据。但它还是实验性 API，目前只有 Chromium 系浏览器支持，要做特性检测和降级。

为什么要在 visibilitychange 里上报

先看推荐的写法：

JavaScript
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') flush();
});

为什么不用 unload？设想用户先切到别的应用，过了一会儿在任务管理器里把浏览器划掉。这时 unload 根本没有机会执行，而 visibilitychange 在切走的那一刻就已经触发了。

可是 hidden 不一定代表用户离开了，他可能还会切回来。所以 flush 只发当前缓冲区里的数据，之后的数据继续攒着，下次隐藏再发。

那 pagehide 呢？它和 bfcache 兼容，但可靠性问题和 unload 差不多，MDN 推荐优先用 visibilitychange。bfcache 的细节见《bfcache 与 HTTP 缓存有什么区别？》。

sendBeacon、keepalive、fetchLater 怎么选

三种方式对比如下：

方式方法读响应体积限制兼容性
sendBeacon仅 POST否与 keepalive 共享 64 KiB广泛支持
fetch + keepalive任意可以与 sendBeacon 共享 64 KiB广泛支持
fetchLater任意否有配额，超出抛 QuotaExceededError仅 Chromium

很多人会想：sendBeacon 返回 false，那就换 keepalive 再试一次。可是 false 多半意味着配额满了，而两者共用同一份配额，换了也一样失败。

所以可靠的做法是平时按数量或时间分批发送，离开时只剩一小块数据要发。keepalive 只用作不支持 sendBeacon 的环境下的回退。返回值、Content-Type 和预检请求的细节见《sendBeacon 返回 true 就代表上报成功了吗？页面离开时怎样发送统计？》。

fetchLater 怎么用

fetchLater 的思路不一样：不用抓离开的时机，先把请求登记好，由浏览器决定什么时候发。

JavaScript
let controller;
function schedule(data) {
  if (!('fetchLater' in window)) return; // 降级到 visibilitychange + sendBeacon
  controller?.abort(); // 数据更新时取消旧请求再重新登记
  controller = new AbortController();
  try {
    fetchLater('/collect', {
      method: 'POST',
      body: JSON.stringify(data),
      signal: controller.signal,
      activateAfter: 60_000,
    });
  } catch (error) {
    if (error.name !== 'QuotaExceededError') throw error;
  }
}

为什么每次登记前都要 abort 旧的？因为数据一直在更新，旧的请求已经过时了，取消它再登记新的，最后发出去的就是最新数据，也不会重复。

它的价值在于：页面被销毁或者进入 bfcache 时，浏览器会发出已登记的请求，不依赖离开事件有没有触发。activateAfter: 60_000 表示就算页面一直没关，60 秒后也会发。

它也有限制：只接受 HTTPS 这类可信 URL，请求体不能是流，响应会被丢弃，还受 CSP 的 connect-src 约束。

常见追问

为什么不在 beforeunload 里用同步 XHR？

同步请求会卡住页面离开，体验很差。而且 Chrome 等浏览器已经禁止在页面卸载期间发送同步 XHR，可靠性也没有保证。

数据会不会重复上报？

会。hidden 可能触发很多次，所以每条事件带一个 ID 去重，服务端也要能处理重复数据。

上报接口要带 Cookie 吗？

尽量不带，改用 URL 参数或者请求体里的匿名 ID。这样可以避开跨站 Cookie 带来的各种限制。
