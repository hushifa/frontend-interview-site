真实用户监测与实验室性能测试为什么要结合？

实验室测试用于控制变量和定位原因，RUM 用于观察真实设备、网络和交互的体验分布；两者回答不同问题，不能相互替代。

参考答案

简答

  • 实验室测试适合定位原因，RUM 反映真实用户的分布。
  • RUM 要先定义每条数据的含义，SPA 路由要单独测量。
  • 用 p75、p95 和样本量判断体验，不看平均数。
  • 上报要采样、批量、脱敏，并用 sendBeacon 等不阻塞的方式发送。

两种测试看到的是不同世界

实验室测试固定设备、CPU、网络、缓存、数据和操作步骤，适合回答“这次改动为什么变慢”。真实用户监测则收集真实访问，能看到低端手机、弱网、不同地区和真实交互路径，回答“谁在什么场景下受影响”。

开发机热缓存的结果不能代表线上长尾，实验室的严格限速也不一定代表大多数用户。两者结果不同并不意味着某一方错误，而是样本和问题不同。

实验室先把原因测出来

固定视口、设备、网络、缓存和数据量，记录资源瀑布、长任务、布局偏移和交互处理。只改变一个关键实现，重复运行并比较分布，而不是只取一次最好成绩。

场景必须完成真实操作。只打开首页无法说明用户首次展开答案、切换筛选或打开编辑器时的等待。实验室的 TBT 能提示主线程阻塞，但不能直接当作线上 INP。

RUM 要先定义一条数据的含义

线上可以采集 LCP、INP、CLS、导航信息和业务阶段耗时，但每个指标都有生命周期。SPA 只发生一次文档导航时，首页 LCP 和后续路由切换不是同一件事，应分别记录。

业务指标要明确开始和结束，例如用户点击筛选到结果可交互；用户取消、请求失败和页面离开要有不同状态。首个网络字节也不一定是首个有用内容，语音还要区分首个音频数据和真正开始播放。

页面内耗时用 performance.now() 等单调时钟计算，跨服务使用 trace ID 关联，不要直接拿浏览器和服务端墙上时间相减。指标实现应处理页面隐藏、恢复和多次候选更新，不能随便取一次 PerformanceObserver 回调就当最终值。

用分布而不是平均数判断体验

应按页面、设备、版本和任务类型观察 p50、p75、p95 及样本量。平均值会掩盖少数用户的长尾；样本很少时 p95 又可能不稳定。每天的 p75 不能简单求平均当成整周 p75，分位数需要原始样本或合并统计结构。

发布后总体变慢可能是代码变慢，也可能是更多低端设备进入流量，或者采样和指标库发生变化。分批发布、对照组和可比人群分组比单纯比较两个总数更接近因果判断。

上报本身不能破坏性能和隐私

限制采样率、字段和队列大小，批量发送；页面隐藏时可尽力使用 sendBeacon，不要为保证上报在离开页面时执行阻塞操作。区分真实零值、没有产生指标、API 不支持和上报失败，缺失数据不能填成零。

默认不要采集完整 URL 查询串、输入内容、令牌、附件名或响应正文。日志和报表至少要有应用版本、页面类型、设备类别、样本量和覆盖率，并设置访问控制与保留期限。

从发现到修复要形成闭环

RUM 发现移动端列表页 INP 变差后，在实验室复现并查看长任务；发现详情展开慢后，拆分数据请求、渲染和图片解码。修复后先用固定场景确认原因，再通过分批发布观察线上分布，同时检查错误率、功能完成率和成本是否变差。

RUM 告诉你优先修什么，实验室轨迹帮助你知道改哪里。只有两者口径一致，性能结论才有可信度。
