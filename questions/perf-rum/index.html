真实用户监测与实验室性能测试为什么要结合？

实验室测试（Lighthouse、WebPageTest、DevTools）条件固定，适合复现、找原因和发布前拦截退化；RUM 采集真实用户在各种设备、网络和交互下的数据，反映体验分布。INP 这类交互指标只能靠 RUM 拿到真实值，两者回答不同问题，不能互相替代。

参考答案

简答

实验室测试就是用 Lighthouse、WebPageTest、DevTools 这些工具，在固定的设备和网络下跑页面。条件可控、结果能重复，还有完整的瀑布图和调用栈，适合找原因，也适合放进 CI 里拦截退化。缺点是设备、网络、缓存状态和用户行为都是假设的。

真实用户监测，简称 RUM，是在用户浏览器里采集数据。它覆盖低端手机、弱网和真实的交互，能发现实验室想不到的问题。可它只有指标和有限的归因，很难直接看出原因。

所以两者回答的是不同的问题：RUM 告诉你谁慢、有多普遍，实验室告诉你为什么慢。Core Web Vitals 按真实用户的 75 分位评估，Chrome 的 CrUX 数据集就是 RUM 数据。

要注意，实验室工具不会模拟用户点击，测不到真实的 INP，一般用总阻塞时间 TBT 作为参考。看数据时也要看 p75、p95 和样本量，不要看平均值。

两者各自擅长什么

把两者放在一起比较：

实验室RUM
回答的问题为什么慢谁慢、多慢、多普遍
条件固定真实且多样
详细程度瀑布图、调用栈、截图指标加有限的归因
时机开发、CI、发布前发布后持续
交互指标只有模拟值真实 INP

为什么不能只要一个？只有实验室，你测的是自己假设的场景，真实用户的低端手机和弱网你看不到。只有 RUM，你知道某个版本变慢了，却没有调用栈和瀑布图告诉你为什么。

怎样采集 RUM

下面用 web-vitals 采集几个核心指标，先放进队列，页面隐藏时一次发出去：

JavaScript
import { onCLS, onINP, onLCP, onTTFB } from 'web-vitals';

const queue = [];

function report(metric) {
  queue.push({
    name: metric.name,
    value: Math.round(metric.name === 'CLS' ? metric.value * 1000 : metric.value),
    rating: metric.rating,
    page: location.pathname,
    version: __APP_VERSION__, // 构建时注入的版本号
  });
}

onLCP(report);
onINP(report);
onCLS(report);
onTTFB(report);

addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden' && queue.length > 0) {
    navigator.sendBeacon('/rum', JSON.stringify(queue.splice(0)));
  }
});

为什么 CLS 要乘 1000？因为 CLS 是 0.1 这种小数，直接 Math.round 就变成 0 了，乘 1000 再取整能保留精度，服务端再除回去。

为什么在页面隐藏时发？因为 INP 和 CLS 要到最后才有最终值，而且 sendBeacon 不会阻塞页面卸载。

带上版本号和页面路由，才能按维度拆开看，设备类型也最好一起带上。另外要按比例采样，不要上报用户输入、完整 URL 查询参数这类个人信息。

还有一点，SPA 切换路由不会产生新的导航，所以“路由切换完成”要自己定义、自己测。

两者怎样配合

一个典型的流程是这样的：

  1. RUM 发现某个版本以后，低端设备的 LCP 变差了。
  2. 实验室按低端设备的条件复现，用瀑布图找到原因。
  3. 修复后先在实验室验证，再看 RUM 有没有恢复。
  4. 把这个场景加进 CI 的实验室检查，防止再次退化。

常见追问

Lighthouse 分数很高，CrUX 数据却很差，为什么？

Lighthouse 只测一次，用的是固定的模拟条件。真实用户的设备更慢、网络更差，还会有交互，所以两边差得远是正常的，应以真实用户数据为准。

样本量多少才可信？

没有固定数字。分组以后样本太少，分位数会波动得很厉害，所以展示分位数时要同时展示样本量。
