Cache-Status 响应头能帮助诊断哪些缓存问题？

Cache-Status 让链路上每一层缓存都在响应里留一条记录，说明有没有命中、为什么去找上游、有没有存下来。它是 RFC 9211 定义的标准头，排查 CDN 多层缓存比 Age 或 X-Cache 清楚。

参考答案

简答

一个请求可能经过好几层缓存，比如 CDN 边缘节点、回源用的中间层。Cache-Status 让每一层都在响应上追加一条记录，顺序是从离源站最近的那层，到离用户最近的那层。

每条记录说明这一层做了什么。hit 表示直接用缓存回答了；fwd 表示转给了上游，并写明原因，比如 uri-miss 是没有副本，stale 是副本过期，vary-miss 是 Vary 对不上，bypass 是配置要求绕过。

还有几个参数常用：fwd-status 是上游回的状态码，ttl 是还剩多少新鲜时间，stored 表示这次响应有没有存下来，key 能显示缓存键。

要注意，它只是诊断信息，不保证每层都写。真正决定缓存行为的是 Cache-Control，而 Age 只说明副本在缓存里待了多久。

读懂一个例子

http
Cache-Status: OriginShield; fwd=stale; fwd-status=304; stored, EdgePOP; hit; ttl=120

逗号分开的是两层缓存，靠前的离源站近。OriginShield 这一层发现副本过期了，就去源站验证，源站回了 304，这一层把副本更新后存了下来。EdgePOP 是离用户最近的边缘节点，它直接命中，副本还有 120 秒新鲜期。

只看 Age，你只知道副本存了多久，看不出是哪一层命中的、为什么回了源。

能用它排查哪些问题

现象关注的参数
发版后用户仍拿到旧内容哪一层是 hit、ttl 还剩多少
命中率低fwd=uri-miss 是否频繁，key 是否包含了不该有的查询参数或头
不同语言内容串了fwd=vary-miss 是否出现，Vary 是否设置
本应缓存却没缓存stored 缺失，结合 detail 找原因

比如命中率低，常见原因是缓存键里混进了追踪参数，每个用户的 URL 都不一样。这时看 key，就能直接看出来。

用的时候有哪些限制

首先，得 CDN 或代理实现了这个头才有。很多厂商目前还只提供自己的私有头。

其次，key 和 detail 可能暴露内部结构。生产环境可以只对带调试标记的请求返回，或者在边缘节点把它去掉。

最后，浏览器自己的缓存不会写 Cache-Status。浏览器有没有命中，要看 DevTools 的 Size 列，显示 memory cache 或 disk cache 就是命中了。

常见追问

和 Age 有什么区别？

Age 只说明副本存在多久，不说明是哪一层命中、为什么转发。

和 Server-Timing 有什么区别？

Server-Timing 报告服务端各环节的耗时，前端可以通过 Resource Timing 读到。Cache-Status 报告的是缓存做了什么决定。
