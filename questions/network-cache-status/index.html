Cache-Status 响应头能帮助诊断哪些缓存问题？

按 RFC 9211 解读命中、转发、重新验证和多层缓存记录，说明 Cache-Status 与 Age、Cache-Control 的区别，以及诊断信息的时效和可见性限制。

参考答案

简答

  • Cache-Status 是缓存层报告自己如何处理请求的可选诊断头，没有它不代表没有缓存。
  • hit 表示该层直接满足请求，ttl 是该层计算的剩余新鲜时间，不是浏览器的缓存期限。
  • fwd 的原因（uri-miss、vary-miss、stale、bypass 等）比单纯的 MISS 更能指出排查方向。
  • fwd-status 是下一跳返回的状态，浏览器收到 200 时上游可能只返回了 304。
  • 跨源脚本读取它需要 Expose-Headers，解析要用 Structured Fields 解析器。

一个请求最终返回 200，不足以说明它是否真的访问了源站。可能是 CDN 直接返回缓存，也可能是 CDN 向源站重新验证后，把原有正文返回给浏览器。Cache-Status 让参与处理的缓存层描述自己做了什么，帮助把这些情况区分开。

它是可选的诊断响应头，不是浏览器必定自动添加的信息。没有这个头，不能断言没有缓存；出现这个头，也不能认为它已经描述了整条链路上所有缓存。

从一条简单的命中记录读起

http
Cache-Status: EdgeCache; hit; ttl=120

EdgeCache 是报告该信息的缓存标识。hit 表示它用缓存中的响应满足请求，没有为这次处理向上游转发；ttl=120 表示这层缓存报告时计算出的剩余新鲜时间约为 120 秒。

这里的 ttl 不是“浏览器一定还能缓存 120 秒”，也不是资源自创建以来的年龄。不同缓存可能采用自己的策略和计算，客户端仍应依据适用的 HTTP 缓存规则决定如何使用响应。

hit 也不一定意味着内容新鲜。某些允许使用过期响应的情况可以报告：

http
Cache-Status: EdgeCache; hit; ttl=-30

它表示这次由缓存满足，但按照该缓存的计算，响应已过期 30 秒。是否允许这样返回，还要结合 stale 相关策略、请求要求和服务端可用性判断。

没命中时，fwd 比一个 MISS 更有用

http
Cache-Status: EdgeCache; fwd=uri-miss; stored

这表示该层没有找到匹配请求 URI 的响应，所以向上游转发，并把获得的响应存了下来。stored 说明这次发生了存储，不保证下一次一定命中：缓存还可能过期、被淘汰，或者下一次请求选中了不同变体。

常见 fwd 原因包括：

值这层缓存报告的原因
uri-miss没有匹配请求 URI 的缓存响应
vary-miss地址匹配，但请求头与已有 Vary 变体不匹配
stale找到了响应，但已过期，需要向上游处理
bypass配置要求绕过此缓存
request有新鲜响应，但本次请求的要求不允许直接使用
method请求方法的语义要求转发
partial只有部分内容，无法满足本次范围或完整内容请求

例如看到 vary-miss，应该检查语言、编码等请求头和缓存变体规则，而不是只检查资源是否过期。看到 bypass，则应检查 CDN 路由和缓存配置，不要把它解释成缓存服务器坏了。

同一个列表成员中的 hit 与 fwd 应互斥：这层处理要么直接由缓存满足，要么需要向上游转发。不要为了让监控“看起来命中”而在一次同步重新验证后同时标两者。

浏览器收到 200，上游却可能只返回了 304

http
HTTP/1.1 200 OK
Cache-Status: EdgeCache; fwd=stale; fwd-status=304

这个例子表示缓存里有旧响应，但需要向上游确认；上游返回 304，缓存因此可以更新相应元信息并继续使用原正文，最终向客户端提供完整响应。

fwd-status=304 是下一跳对转发请求返回的状态码，不必等于浏览器最终收到的状态码。由于确实发生了上游验证，这个处理不按 RFC 9211 定义算作直接 hit。诊断时如果只看浏览器的 200，就会漏掉这一段等待。

同样，上游的下一跳可能是另一层缓存，不一定就是应用源站。

多层缓存的记录要从来源和时间一起理解

http
Cache-Status: OriginCache; hit; ttl=900, EdgeCache; hit; ttl=120

列表通常从靠近源站的缓存排到靠近用户的缓存。这个例子中 EdgeCache 更靠近用户。

但它不能简单读成“这次请求先访问了 OriginCache，再访问了 EdgeCache”。当 EdgeCache 直接命中时，请求没有继续发到上游；响应里保留的 OriginCache 信息可能来自更早获取并保存该响应的那次请求。

因此多层记录可以帮助理解响应经过了什么处理，却不总是一次请求的实时完整调用链。尤其不能把每一层 ttl 相加，或者把多条 hit 当成当前同时访问所有层的证据。

它与其他缓存相关信息各有职责

  • Cache-Control 提供缓存行为指令，例如能否存储、何时需要验证。
  • Vary 描述哪些请求头影响缓存变体的匹配。
  • ETag 等验证器帮助判断表示是否变化。
  • Age 表达响应的估计年龄，和“还剩多久新鲜”不同。
  • Cache-Status 报告某一缓存层如何处理请求，是解释和诊断信息。

因此手动在响应里写 Cache-Status: MyCache; hit 不会凭空创建缓存，也不能证明实现真的命中。必须让实际缓存组件按真实处理结果生成它。

开发者工具里的 from memory cache、from disk cache 和 from ServiceWorker 也来自不同观察角度。若浏览器根本没有发送网络请求，看到的服务器诊断头可能只是以前响应保留下来的内容，不是 CDN 刚刚生成的新记录。

在代码中读这个头时要注意什么

同源响应可以通过 response.headers.get('Cache-Status') 读取；跨源脚本通常需要服务端用 Access-Control-Expose-Headers 暴露该字段。开发者工具能看到它，不代表跨源 JavaScript 也能读取。

它使用 HTTP Structured Fields 的列表和参数语法，缓存名称可能是带引号的字符串，参数也有不同类型。正式做诊断面板时应使用成熟的结构化字段解析器，不要仅靠逗号和分号切割所有内容。厂商自己的 X-Cache 等字段也可能有完全不同的约定，不能直接按同一套语义解析。

key、detail 等可选参数可能透露内部缓存键、节点或规则。公开程度应按需要控制，敏感详情可以仅对授权诊断请求返回。

真正排查问题时，把当前请求头、最终响应状态、Cache-Status、Age、Vary 和服务端日志对齐到同一次请求。它能缩小原因范围，但不能替代对实际缓存策略和内容正确性的检查。
