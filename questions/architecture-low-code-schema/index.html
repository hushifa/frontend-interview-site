低代码和 Schema 驱动 UI 怎样保持可维护与安全？

Schema 驱动 UI 用 JSON 描述页面，渲染器只用注册过的组件，逻辑用声明式条件或注册函数名表达，不在配置里执行任意 JavaScript。Schema 要带版本做数据迁移，配置校验也不能当成权限控制。

参考答案

简答

Schema 驱动 UI，就是用一份 JSON 描述页面或表单长什么样，渲染器读这份描述，把组件创建出来。它适合结构差不多、数量又多的后台页面和表单。

安全上最重要的一条是：配置里只能写组件名和参数，不能写代码。渲染器只认预先注册好的组件白名单。显隐、校验、联动这些逻辑，用受限的声明式条件，或者引用注册好的函数名来表示，不要用 eval、new Function 去执行配置里的字符串。

可维护上，Schema 要带版本号。配置会在数据库里存很久，渲染器升级时要提供迁移函数，把旧配置自动转成新格式。

还要注意，前端按配置做的校验只是为了体验。权限和数据是否合法，必须由服务端校验。

一份表单 Schema 长什么样

下面这份配置描述了两个字段，“企业名称”只在类型选了“企业”时显示：

json
{
  "version": 2,
  "fields": [
    { "name": "type", "component": "Select", "label": "类型",
      "options": [{ "value": "person", "label": "个人" }, { "value": "company", "label": "企业" }] },
    { "name": "companyName", "component": "Input", "label": "企业名称",
      "visibleWhen": { "field": "type", "equals": "company" },
      "rules": [{ "required": true }] }
  ]
}

注意 visibleWhen 是一个对象，不是一段代码。渲染器读到它，自己去判断要不要显示。

渲染器怎样只用注册过的组件

JavaScript
const registry = { Input, Select, DatePicker };

function renderField(field) {
  const Component = registry[field.component];
  if (!Component) return <UnknownField name={field.name} />;
  return <Component {...pickAllowedProps(field)} />;
}

配置里写的组件名，只有在注册表里查得到才会渲染。查不到就显示一个占位，而不是整个页面崩掉。

传给组件的参数也要过一遍白名单，也就是 pickAllowedProps。为什么？因为如果把配置原样展开传进去，能编辑配置的人就可以塞进 dangerouslySetInnerHTML 或者事件处理器。

逻辑怎样写进配置

大部分显隐和联动，用上面 visibleWhen 这种声明式条件就能覆盖。它还有个好处：渲染器不用运行就能分析出字段之间谁依赖谁。

更复杂的逻辑，先在代码里注册成命名函数，配置里只写函数名：

json
{ "rules": [{ "validator": "isValidTaxId" }] }

如果确实需要让用户自己写表达式，就用一个只支持有限运算符的表达式解析器，而不是执行 JavaScript。允许配置执行任意代码，等于把 XSS 的能力交给了每一个能编辑配置的人。

旧配置怎样升级

JavaScript
const migrations = {
  1: (schema) => ({ ...schema, version: 2, fields: schema.items }),
};

function migrate(schema) {
  let current = schema;
  while (migrations[current.version]) current = migrations[current.version](current);
  return current;
}

每个版本对应一个迁移函数，把配置升到下一版。migrate 一级一级往上升，直到没有更新的迁移为止。

为什么要这样做？因为配置长期存在数据库里，渲染器哪天改了字段名或结构，旧配置不能就这么坏掉，必须能自动升级。这些迁移函数也要写测试。

安全边界在哪里

表单配置里的 required、maxLength 只影响前端体验。服务端要用同一份规则独立校验提交的数据，比如从 Schema 生成 JSON Schema 来校验。

字段隐藏了，不等于用户没有权限。敏感字段要由服务端根据权限决定返不返回、接不接受。

能编辑配置的人本身也要有权限控制，修改要留审计记录。

什么时候不适合用

交互复杂、定制化强的页面，硬用配置去描述，往往比直接写代码更难维护。常见的折中是让 Schema 覆盖标准的部分，同时允许嵌入注册好的自定义组件。

常见追问

这和 JSON Schema 是什么关系？

JSON Schema 描述的是数据结构和校验规则；UI Schema 描述的是怎么展示。两者经常配合使用。

配置出问题了怎么调试？

渲染器在开发模式下先校验 Schema，出错时给出具体到字段路径的错误信息。
