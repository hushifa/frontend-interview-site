低代码和 Schema 驱动 UI 怎样保持可维护与安全？

用表单和页面配置说明 Schema、组件注册、数据绑定和版本迁移的边界，避免把任意 JavaScript 放进配置或把配置校验当成权限控制。

参考答案

简答

  • Schema 驱动 UI 用 JSON 描述页面或表单，渲染器根据描述创建组件，适合结构相似、数量多的后台页面和表单。
  • 渲染器只能使用预先注册的组件白名单，配置里只写组件名和参数，不能写任意代码。
  • 逻辑（显隐、校验、联动）用受限的声明式表达式或注册好的函数名表示，不用 eval 或 new Function 执行配置中的字符串。
  • Schema 要带版本号，渲染器升级时提供迁移函数，把旧配置转换成新格式。
  • 前端校验只是体验，权限和数据合法性必须由服务端校验。

一个表单 Schema

json
{
  "version": 2,
  "fields": [
    { "name": "type", "component": "Select", "label": "类型",
      "options": [{ "value": "person", "label": "个人" }, { "value": "company", "label": "企业" }] },
    { "name": "companyName", "component": "Input", "label": "企业名称",
      "visibleWhen": { "field": "type", "equals": "company" },
      "rules": [{ "required": true }] }
  ]
}

组件注册

JavaScript
const registry = { Input, Select, DatePicker };

function renderField(field) {
  const Component = registry[field.component];
  if (!Component) return <UnknownField name={field.name} />;
  return <Component {...pickAllowedProps(field)} />;
}
  • 只渲染注册表中存在的组件，未知组件显示占位而不是崩溃。
  • 只把允许的参数传给组件，防止配置注入 dangerouslySetInnerHTML 或事件处理器。

逻辑表达

声明式条件（如上例的 visibleWhen）覆盖大多数显隐和联动场景，渲染器可以静态分析字段之间的依赖。

复杂逻辑可以注册为命名函数，配置中只引用函数名：

json
{ "rules": [{ "validator": "isValidTaxId" }] }

需要用户编写表达式时，使用只支持有限运算符的表达式解析器，而不是执行 JavaScript。配置执行任意代码相当于把 XSS 能力交给了能编辑配置的人。

版本迁移

JavaScript
const migrations = {
  1: (schema) => ({ ...schema, version: 2, fields: schema.items }),
};

function migrate(schema) {
  let current = schema;
  while (migrations[current.version]) current = migrations[current.version](current);
  return current;
}

配置会长期存储在数据库中，渲染器改动字段名或结构时，旧配置必须能被自动升级。迁移函数要有测试。

安全边界

  • 表单配置里的 required、maxLength 只影响前端体验，服务端要用同一份规则（例如从 Schema 生成 JSON Schema）独立校验提交数据。
  • 字段是否隐藏不等于用户有没有权限，敏感字段要由服务端根据权限决定是否返回和接受。
  • 能编辑配置的人员本身要有权限控制和审计记录。

什么时候不适合

交互复杂、定制化强的页面用配置描述会比代码更难维护。常见做法是让 Schema 覆盖标准部分，同时允许嵌入注册好的自定义组件。

常见追问

  • 和 JSON Schema 是什么关系？JSON Schema 描述数据结构和校验规则；UI Schema 描述怎样展示，两者常配合使用。
  • 怎样调试配置问题？渲染器在开发模式下校验 Schema 并给出具体字段路径的错误信息。
