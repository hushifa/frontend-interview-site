媒体查询和容器查询分别适合什么场景？

媒体查询依据视口、设备能力或用户偏好，容器尺寸查询依据祖先容器的可用空间。前者适合页面级适配，后者让同一个组件在不同位置独立调整布局。

参考答案

假设一张课程卡片会同时出现在首页主栏和右侧推荐栏。电脑屏幕很宽，但右侧推荐栏仍然很窄。如果只写 @media (min-width: 60rem)，两处卡片都会采用“大屏布局”，推荐栏中的图片和文字就可能挤在一起。

媒体查询知道页面所处的环境，容器查询知道组件获得了多少空间。 选择哪一种，要看影响设计的因素来自哪里。

页面环境交给媒体查询

CSS
.page {
  display: grid;
  gap: 2rem;
}

@media (min-width: 60rem) {
  .page {
    grid-template-columns: minmax(0, 1fr) 18rem;
  }
}

这段规则表示：视口达到一定宽度，页面才分成主栏和侧栏。对于屏幕媒体，width 查询的是视口宽度，并不是显示器的物理宽度。

媒体查询也不只管宽度。打印用 @media print，减少动画可查询 prefers-reduced-motion，深色偏好可查询 prefers-color-scheme。这些都不是某个卡片容器的尺寸，仍然应使用媒体查询。

组件内部根据容器改变排版

下面的卡片默认上下排列；外层容器足够宽时，图片和正文才左右排列。

HTML
<div class="course-slot">
  <article class="course-card">
    <img class="course-cover" src="/images/course.webp" alt="" />
    <div class="course-body">
      <h2>浏览器渲染原理</h2>
      <p>从 HTML 解析到布局与绘制，理解页面如何显示出来。</p>
    </div>
  </article>
</div>
CSS
.course-slot {
  container-type: inline-size;
  container-name: course;
}

.course-card {
  display: grid;
  gap: 1rem;
}

.course-cover {
  display: block;
  width: 100%;
  height: auto;
}

.course-body {
  min-width: 0;
  overflow-wrap: anywhere;
}

@container course (min-width: 32rem) {
  .course-card {
    grid-template-columns: 10rem minmax(0, 1fr);
  }
}

这里的 32rem 判断的是名为 course 的查询容器宽度，不是整个视口。主栏和侧栏各放一份这段结构，就能在同一个屏幕上出现不同的卡片排版。图片路径需要换成项目实际提供的文件，图片本身不影响查询机制。

container-type: inline-size 建立行内轴尺寸查询容器。在通常的横排文本中，行内轴对应水平方向。container-name 只给容器命名，单独写名字不能建立尺寸查询所需的包含关系。也可以把两行合成 container: course / inline-size。

不写容器名时，浏览器会为目标元素寻找最近的、支持所查询尺寸特征的祖先容器。命名可以避免组件嵌套后误用内层容器；但名字不是全局 ID，多个区域可以使用同一个容器名。

为什么需要额外的外层容器

查询的尺寸来自祖先，规则影响里面的元素。如果让一张卡片因为“自己很宽”而变窄，又因为“自己变窄”而变宽，就会产生循环依赖。尺寸包含会限制后代内容对容器相应内在尺寸的影响，让浏览器能够确定布局。

因此应让 .course-slot 从页面的 Grid、Flex 或正常流获得宽度，再让内部卡片适配它。不要为了查高度随手改成 container-type: size：这会引入两个轴的尺寸包含，如果容器原本完全依靠内容撑高，又没有其他尺寸安排，可能得到意外的高度。

实现时保留可用的基础单列布局。旧环境忽略容器查询时，用户仍然能阅读内容；支持查询的环境再增强布局。媒体查询与容器查询可以同时生效，前者决定页面怎么分配区域，后者决定组件如何利用分到的空间。
