Testing Library 查询方式为什么优先按用户可见语义？

从 getByRole、getByLabelText 和 getByTestId 的优先级理解稳定组件测试，避免把实现细节写进断言。

参考答案

查询方式决定测试通过什么线索找到界面元素。使用 .form > div:nth-child(2) > button，测试依赖的是当前 DOM 排列；使用“名为保存的按钮”，依赖的是用户可以识别的控件语义。

Testing Library 推荐优先按角色、可访问名称和标签查询，是为了让测试与实际使用方式接近，同时减少无关重构引起的失败。

角色和名称分别说明“是什么”与“叫什么”

HTML
<label for="nickname">昵称</label>
<input id="nickname" type="text" />
<button type="submit">保存</button>

对应查询可以是：

JavaScript
const nickname = screen.getByRole('textbox', { name: '昵称' });
const save = screen.getByRole('button', { name: '保存' });

input 通过关联 label 得到可访问名称，button 通常从自身文字得到名称。名称还可能由 aria-label、aria-labelledby 等方式提供，不只是元素的 textContent。

若查询失败，先检查实际语义是否符合预期。不要为了测试加一个随意 role 来覆盖原生语义。不同 input 类型的角色也不同，例如 type="search" 通常是 searchbox；密码输入没有隐式角色，按标签查询往往更合适。

getBy、queryBy、findBy 的差别是时机与数量

查询没找到找到多个是否自动等待
getBy…抛错抛错否
queryBy…返回 null抛错否
findBy…超时后拒绝 Promise无法在等待期内唯一匹配则拒绝是

getBy 适合当前应存在的元素；queryBy 适合检查缺失；findBy 适合等待异步出现。AllBy 版本用于多个结果，其中 queryAllBy 没找到时返回空数组，getAllBy 则会抛错。

要断言错误提示不存在，不能先 getByRole('alert') 再断言为空，因为查询已经先抛错。可以使用 queryByRole 并检查 null。若提示应该在异步操作后消失，则需 waitFor 或 waitForElementToBeRemoved，不能用一次同步查询赌状态已经更新。

多个相似控件时缩小范围

JavaScript
const dialog = screen.getByRole('dialog', { name: '编辑资料' });
const save = within(dialog).getByRole('button', { name: '保存' });

这里需要从 Testing Library 导入 within。限定到对话框比拿全页面所有“保存”按钮的第一个更清晰，也避免页面新增其他表单后误点。

screen 的查询通常绑定到 document.body；within 将查询限制在指定节点。测试里若存在多个渲染根或 portal，应确认查询范围与目标内容所在位置一致。

可访问树中的存在，不等于肉眼一定可见

getByRole 默认排除许多不在可访问树中的元素，但它并不是浏览器视觉判断器。例如某些元素可能在语义上可查询，却因透明度或其他样式无法被用户看到。

因此找到元素之后，仍应根据目标添加可见、启用、选中等断言。使用 hidden: true 可以查询被排除的元素，但不应为了让失败用例通过就普遍打开；用户要操作的元素是否被隐藏，本来可能就是缺陷。

文本与 test id 也有合理用途

普通说明文字适合 getByText，输入值可以用相关查询或值断言。对没有合适语义入口的画布容器、测试专用锚点，可以使用 data-testid；稳定 test id 通常优于依赖样式类名。

但 test id 无法证明控件有名称、角色或正确标签。若所有按钮都只能靠 test id 找到，应该检查是否遗漏可访问性设计，而不是把查询优先级当成无关紧要的风格偏好。

文本匹配也应控制精度：过宽的正则可能同时匹配多个元素，过度绑定整段动态文案又可能让无关翻译调整触发失败。选取真正属于契约的名称和范围，而不是为了少写代码放松条件。

这些示例说明查询规则，不代表一次语义查询就完成无障碍验收。真实键盘顺序、焦点管理、排版和屏幕阅读器行为仍需相应测试。
