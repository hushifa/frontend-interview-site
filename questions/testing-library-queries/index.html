Testing Library 查询方式为什么优先按用户可见语义？

按角色和可访问名称查询（getByRole）和用户、读屏软件找元素的方式一致，组件内部结构变了测试也不会失败，查不到时还顺带暴露了无障碍问题。按类名或 test id 查询只作为最后手段。

参考答案

简答

用户找一个按钮，看的是“这是个按钮，上面写着保存”，读屏软件也是按“角色加名称”来读的。Testing Library 推荐用同样的方式找元素，优先级是 getByRole → getByLabelText → getByPlaceholderText → getByText → getByDisplayValue → getByAltText、getByTitle → getByTestId。

这样做有两个好处。一是 getByRole('button', { name: '保存' }) 同时检查了角色和名称，如果有人用 div 做按钮，测试就找不到它，等于顺带发现了无障碍问题。二是选择器离实现细节越远，重构时越不容易误报；按类名、DOM 层级找，结构一调整就挂。

查询还分三类：getBy* 找不到或找到多个时立刻抛错；queryBy* 找不到返回 null，用来断言“不存在”；findBy* 返回 Promise，等元素出现，默认等 1000ms。

要注意，有些角色的名称不能从内容算出来，比如 listitem，按名称查会得到空名称，这时改用 getByText 或者 within(list)。

先看一个例子

下面的测试找输入框、按钮和列表，用的都是用户能看到的标签和名称：

TSX
import { render, screen, within } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

test('添加任务后出现在列表中', async () => {
  const user = userEvent.setup();
  render(<TodoApp />);

  await user.type(screen.getByLabelText('新任务'), '写周报');
  await user.click(screen.getByRole('button', { name: '添加' }));

  const list = screen.getByRole('list', { name: '待办' });
  expect(within(list).getByText('写周报')).toBeInTheDocument();
  expect(screen.queryByText('暂无任务')).not.toBeInTheDocument();
});

这段测试不知道组件里用了什么类名、套了几层 div。只要界面上还是“新任务”输入框、“添加”按钮和“待办”列表，组件内部怎么重构，测试都不用改。

最后一行用的是 queryByText，因为要断言的是“暂无任务”已经不在了。如果用 getByText，找不到时会直接抛错，测试就没法表达“不存在”这个意思。

get、query、find 三类查询怎么选

找不到找到多个异步
getBy抛错抛错否
queryBynull抛错否
findBy超时后 rejectreject是
*AllBy同上返回数组

简单记：元素应该已经在，用 getBy；要断言它不在，用 queryBy；要等它出现，用 findBy。要找多个元素时，换成对应的 getAllBy、queryAllBy、findAllBy。

常见的用错方式

一种是用 queryBy 去断言元素存在。找不到时它只返回 null，报错信息远不如 getBy 清楚。

另一种是在 waitFor 里放 getBy，外面又套一个 findBy，等了两遍。findBy 本身就是 getBy 加 waitFor，直接用它就够了。

还有直接用 container.querySelector。这样绕开了 Testing Library 的语义查询，也拿不到它详细的错误提示。

什么时候才用 test id

只有两种情况：文本经常变化，比如多语言、A/B 测试；或者元素确实没有可访问的角色和名称，比如图表用的 Canvas。这时才给元素加 data-testid，用 getByTestId 去找。

常见追问

不知道该用哪个查询时怎么办？

看报错信息。查询失败时，Testing Library 会把页面上所有可访问的角色列出来。也可以调用 screen.logTestingPlaygroundURL()，在浏览器里点选元素，它会生成推荐的查询写法。
