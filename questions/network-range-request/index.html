HTTP Range 请求适合什么场景？

通过字节范围和断点续传说明 206、200、416 的不同处理，解释 If-Range 如何防止文件版本混拼，并给出校验单个分片的 fetch 示例。

参考答案

简答

  • Range 请求按字节区间获取部分内容，适合断点续传和媒体拖动。
  • 区间按字节计算，结束位置包含在内；成功返回 206 和 Content-Range。
  • 续传前用 If-Range 加 ETag 确认还是同一个文件，否则会拼出错误内容。
  • 416 表示范围无法满足，不一定代表下载完成；跨源和内容编码要单独处理。

下载一个 100 MB 的文件，传到 60 MB 时网络断开。如果重新下载整个文件，之前的流量和等待就浪费了。Range 请求允许客户端指定“我只需要这个资源的某一部分”，是断点续传、视频拖动播放位置和按需读取大型文件的基础能力之一。

但 Range 只描述要读取的范围，不会替应用保存已下载数据、记录文件版本或完成分片合并。完整的下载器仍需要设计这些逻辑。

范围是字节位置，结束位置也包含在内

例如请求前 1024 个字节：

http
GET /files/report.zip HTTP/1.1
Host: example.com
Range: bytes=0-1023

0-1023 包含两个端点，所以长度是 1023 - 0 + 1 = 1024。常见写法还有：

Range 值含义
bytes=1024-2047从位置 1024 到 2047，共 1024 字节
bytes=1024-从位置 1024 直到结尾
bytes=-500最后 500 字节；文件不足 500 字节时取整个文件
bytes=0-99,200-299请求两个范围，响应可能是 multipart/byteranges

这里数的是字节，不是 JavaScript 字符串的字符数。汉字、emoji 等在 UTF-8 下可能占多个字节，不能把 text.length 直接当成下载偏移量，也不要把任意字节片段分别解码成字符串后再拼接。

服务器支持本次单范围请求时，典型响应如下：

http
HTTP/1.1 206 Partial Content
Content-Type: application/zip
Content-Range: bytes 0-1023/104857600
Content-Length: 1024
ETag: "report-v7"

...1024 字节的正文...

Content-Range 说明本次正文来自完整表示的哪个区间，斜杠后是完整长度。Content-Length 若存在，在这里表示本次分片的正文长度，不是完整文件大小。多范围响应则会在各个 MIME 分段中分别携带范围信息，不能拿一个普通 ArrayBuffer 就假装它已经是按顺序拼好的文件。

续传先确认：还是原来的那个文件吗

只记录“已经下载 60 MB”还不够。假设服务器把同一个 URL 下的文件从 v7 更新成 v8，客户端继续请求第 60 MB 后面的内容，就可能拼出“前半段 v7、后半段 v8”的损坏文件。

可以保存服务器提供的强 ETag，在续传时一起发送：

http
Range: bytes=62914560-
If-Range: "report-v7"

意思是：“如果仍是这个版本，给我剩下的部分；如果版本已经变化，就把当前完整文件给我。”

  • 验证器匹配且范围被接受时，服务器可以返回 206，客户端校验后继续保存。
  • 验证器不匹配时，服务器忽略 Range，通常返回完整的 200 响应。客户端必须重新开始，不能把它接在旧文件尾部。
  • 服务器不支持或忽略 Range 时，也可能返回 200。客户端必须具备这种处理分支，不能只看 response.ok，因为 200 和 206 都属于成功状态。

If-Range 不能使用 W/"..." 这样的弱 ETag。它也可以使用符合强验证器要求的日期，但不能把任意 Last-Modified 值都当成可靠的字节版本证明。涉及拼接时优先使用服务端明确提供的强 ETag，并保持请求选择的是同一份表示。

Accept-Ranges: bytes 是服务端支持范围请求的提示，不是之后每次都返回 206 的承诺。按照 HTTP 规范，即使先前没有收到这个头，客户端也可以尝试 Range；是否能使用返回的分片，最终要检查当前响应。具体规则见 RFC 9110 的 Accept-Ranges 定义。

416 不一定代表“文件下载完成”

如果文件总共只有 1000 字节，却请求 bytes=1500-，没有可满足的范围，服务器可能返回：

http
HTTP/1.1 416 Range Not Satisfiable
Content-Range: bytes */1000

*/1000 提示当前表示的总大小。原因可能是偏移计算错误、文件变短，或者本地已经有全部数据。客户端要结合保存的版本、长度和完整性信息判断，不能收到 416 就直接宣布下载成功。服务器也可能拒绝不合理的多范围请求，因此 416 不只对应一种业务原因。

在 fetch 中校验一个小分片

下面是用于教学的单范围读取函数：每次最多请求 1 MiB，要求服务器返回已知总长度、没有内容编码的二进制表示。它不实现并发调度、持久化和最终文件合并；这种明确的限制可以让分片校验过程更容易看懂。

JavaScript
async function readRange(url, start, end, etag, signal) {
  if (
    !Number.isSafeInteger(start) ||
    !Number.isSafeInteger(end) ||
    start < 0 ||
    end < start ||
    end - start + 1 > 1024 * 1024
  ) {
    throw new RangeError('范围必须有效，且单次不能超过 1 MiB');
  }
  if (typeof etag !== 'string' || !/^"[^"\r\n]*"$/.test(etag)) {
    throw new TypeError('请传入此前响应中的强 ETag');
  }

  const response = await fetch(url, {
    headers: { Range: `bytes=${start}-${end}`, 'If-Range': etag },
    signal,
  });

  if (response.status === 200) {
    // 由调用方决定重新下载或取消，绝不能把完整正文追加到旧分片后。
    return { kind: 'full', response };
  }

  async function fail(message) {
    await response.body?.cancel();
    throw new Error(message);
  }

  if (response.status === 416) {
    return fail(`范围不可满足：${response.headers.get('Content-Range') ?? '总长度未知'}`);
  }
  if (response.status !== 206) {
    return fail(`读取分片失败：HTTP ${response.status}`);
  }
  if (response.headers.get('Content-Encoding')) {
    return fail('此示例只支持没有内容编码的二进制表示');
  }

  const match = /^bytes (\d+)-(\d+)\/(\d+)$/.exec(
    response.headers.get('Content-Range') ?? '',
  );
  if (!match) return fail('缺少可识别的单范围 Content-Range');

  const [actualStart, actualEnd, total] = match.slice(1).map(Number);
  if (
    ![actualStart, actualEnd, total].every(Number.isSafeInteger) ||
    actualStart !== start ||
    actualEnd < actualStart ||
    actualEnd >= total ||
    actualEnd !== Math.min(end, total - 1)
  ) {
    return fail('服务器返回的范围与请求不一致');
  }

  const returnedEtag = response.headers.get('ETag');
  if (returnedEtag !== null && returnedEtag !== etag) {
    return fail('分片所属文件版本发生了变化');
  }

  const bytes = new Uint8Array(await response.arrayBuffer());
  if (bytes.byteLength !== actualEnd - actualStart + 1) {
    throw new Error('实际分片长度与 Content-Range 不一致');
  }
  return { kind: 'partial', bytes, start: actualStart, end: actualEnd, total };
}

返回 kind: 'partial' 后才可以按照偏移保存字节，保存成功后再更新续传进度。返回 kind: 'full' 时，调用方可以把这个响应作为新版本从头保存；如果不准备继续，应该取消它的响应体，避免无用传输。读取响应体本身也可能因断网或取消而失败，调用方需要捕获整个函数的拒绝。

这里允许服务器把结束位置截到文件末尾，例如文件长 1000 字节，请求 900-1199，有效响应可以是 900-999/1000。但任意错误偏移、混入其他版本或长度不符的正文都不能进入本地拼接结果。

示例用 arrayBuffer() 便于展示小分片的检查。实际大文件下载应根据环境采用流式写入或合适的持久化方案；不要把数 GB 文件的全部分片一直留在内存里。对不可信端点还应在读取过程中限制字节数，而不是只在完整读入后检查长度。

浏览器里还要考虑跨域和压缩

满足 CORS 安全列表格式的单个字节范围 Range 可以免于预检，但这里还发送了 If-Range，跨源调用通常需要预检，并由服务端允许相应请求头。要让脚本读取 Content-Range、ETag 和 Content-Encoding，服务端还需要通过 Access-Control-Expose-Headers 暴露它们，否则代码无法可靠判断响应。身份验证和资源权限也照常生效。

Range 针对的是选定表示的字节序列。内容编码、浏览器自动解压和 CDN 转换会让“响应里的字节位置”与“脚本最终得到的字节”产生混淆，所以示例要求下载端点提供稳定且未做内容编码的表示。不要试图在浏览器脚本里随意设置 Accept-Encoding 来修复它，该请求头由浏览器控制。

Range 与 HTTP/1.1 的 Transfer-Encoding: chunked 也不是一回事：前者是请求资源的某个区间，后者是传输响应体时的一种分帧方式。一次普通的全量下载也可以边传边读，却不一定支持中断后从指定偏移重新获取。
