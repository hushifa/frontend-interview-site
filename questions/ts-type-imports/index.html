import type 和 verbatimModuleSyntax 如何影响模块输出？

import type 表达纯类型依赖，verbatimModuleSyntax 让类型修饰符直接决定相关导入导出的保留方式。整条类型导入与普通导入中的 type 成员并不完全相同，模块副作用和运行时解析仍需显式设计。

参考答案

一个 TypeScript 模块可能同时导出接口和真实函数。接口只参与类型检查，函数则可能需要在运行时加载。import type 用语法明确说明“这份依赖只用来解释类型”，避免把是否保留导入完全交给后续使用情况推断。

这不仅影响输出大小，也可能影响模块顶层副作用是否执行。因此类型依赖与初始化依赖应分别表达。

先准备一个同时有类型和运行时代码的模块

以下文件使用 ESM，并在编译时启用 verbatimModuleSyntax：

TypeScript
// model.ts
export interface User {
  name: string;
}
export const version = '1.0';
console.log('model 已执行');
TypeScript
// type-only.ts
import type { User } from './model.js';

const user: User = { name: 'Lin' };
console.log(user.name); // Lin

整条 import type 会被擦除。若没有其他路径加载 model，运行 type-only 的编译产物不会执行 model 的那条日志。类型检查时仍然需要找到它的声明信息，但这不是运行时模块求值。

ESM 输出中可能保留 export {} 来维持当前文件的模块身份，这也不等于重新加载 model。

普通 import 中的 type 成员可能留下空导入

TypeScript
// inline-type.ts
import { type User } from './model.js';

const user: User = { name: 'Lin' };
console.log(user.name);

在 verbatimModuleSyntax 规则下，类型成员被移除，但普通 import 语句可以保留为 import {} from './model.js'。这个空导入仍然会加载并求值模块，所以运行时先输出“model 已执行”，再输出 Lin。

因此 import type { User } 与 import { type User } 在只导入类型成员时，不能一概认为输出完全一样。如果目标明确是纯类型依赖，整条 import type 更直接；如果有必要执行模块，则应显式表达那个目的。

TypeScript
// mixed.ts
import { version, type User } from './model.js';

const user: User = { name: 'Lin' };
console.log(`${version}:${user.name}`); // 1.0:Lin

这时输出会保留 version 的运行时导入，移除 User 的类型部分。模块执行日志仍然发生，是因为确实存在值依赖。

初始化副作用不要寄托在类型导入上

某个模块可能负责注册插件、安装补丁或初始化全局能力。如果这些行为是必要依赖，应使用明确的副作用导入，例如 import './register.js'，而不是期待某个接口引用碰巧保留导入。

类型导入被移除后，编译器也不允许把它直接当作运行时值使用。类同时有类型和构造器两种含义，若用 import type 导入类名，可以用来标注实例类型，却不能据此 new 一个实例。需要构造器、instanceof 或静态方法时，应导入实际值。

导出也有类似区别：export type 明确只暴露类型，普通值导出则需要对应运行时实体。只看名字是否大写，不能准确区分这两种用途。

verbatimModuleSyntax 让模块格式错误更早暴露

该选项保留未标记为类型的相应模块语法，而不是在不匹配的模块环境中悄悄把 ESM import/export 改写成 CommonJS require。

例如在按 CommonJS 解释的文件里编写不适合该设置的 ESM 值语法，会得到诊断。应统一 package.json 的 type、文件扩展名、module 与 moduleResolution，不能为了消除错误就随意关闭规则。

确实面向 CommonJS 的代码，可以采用符合 TypeScript 与宿主约定的 CommonJS 表达方式或调整模块输出策略。正确配置的目标是让源码意图与运行时格式一致，不是让所有语法在任何文件里都被强行接受。

类型检查器、转换器和打包器分别承担不同工作

Vite、Babel、SWC 等链路可能按文件转换 TypeScript，而不进行完整跨文件类型检查。显式类型导入能减少它们判断导入性质的歧义，但不能因此省略独立的类型检查。

该选项也不是 tree shaking 的替代。TypeScript 保留一个值导入后，打包器还可能根据实际使用和副作用规则进一步优化；如果副作用声明不准确，最终结果仍可能偏离意图。

同样，编译器能找到模块类型，不代表浏览器能解析某个裸包名或路径别名。类型导入消失后不需要运行时解析，但真正保留下来的导入必须有可用的运行时目标。

验证时要同时看输出和执行顺序

可以编译上面的三个入口，检查 JavaScript 中是否仍有指向 model 的 import，再分别运行入口观察日志。只看 TypeScript 文件中“这个名字只用于类型”，不足以判断最终是否执行了依赖模块。

升级编译器或调整 verbatimModuleSyntax 时，应重点检查纯类型导入、混合导入、副作用入口与模块格式。把这些意图写清楚，通常比依赖历史导入擦除选项和偶然的转换行为更容易维护。
