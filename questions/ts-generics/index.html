泛型解决了什么问题？如何约束泛型？

泛型就是把类型也当成参数，调用时再确定，这样“传进什么类型就返回什么类型”的关系不会丢。extends 用来限制这个类型参数至少要有哪些结构。

参考答案

简答

泛型就是把类型也当成参数。写函数时先用 T 占个位，调用的时候再确定 T 是什么，一般由编译器自动推断。这样“传进字符串数组就返回字符串数组”这种关系能保留下来；要是用 any，这层关系就没了。

约束用 extends。T extends { length: number } 表示 T 至少要有 length，函数里就能放心用它。K extends keyof T 让 key 只能是 T 的键，再返回 T[K]，就能拿到这个键对应的精确类型。

泛型还有几个常用能力。<T = string> 给类型参数设默认值；<const T>（5.0）让推断保留字面量；NoInfer<T>（5.4）让某个参数只做检查、不参与推断。

要注意，满足约束的对象不一定就是调用方选的那个 T，不能随手构造一个返回。泛型也不做运行时检查。另外，只出现一次的类型参数通常没意义，直接写 unknown 更清楚。

泛型保留了什么关系

TypeScript
function identity<T>(value: T): T {
  return value;
}
const result = identity(['HTML', 'CSS']); // string[]

调用时没写 <string[]>，编译器根据参数推断出 T 是 string[]，返回值也就是 string[]。如果把参数和返回值都写成 any，result 就是 any，后面写错了也没人提醒。

用 extends 加约束

如果函数里要用 length，就得告诉编译器 T 一定有这个属性：

TypeScript
function longer<T extends { length: number }>(first: T, second: T): T {
  return first.length >= second.length ? first : second;
}
longer('HTML', 'TypeScript'); // 'HTML' | 'TypeScript'
longer([1], [1, 2]);          // number[]

字符串和数组都有 length，所以都能传。返回类型仍是调用时推断出的 T，传字符串字面量得到字面量联合，传数组得到 number[]。

可是约束只说了“至少有什么”，不代表随便一个有 length 的对象都能当 T：

TypeScript
function ensureLength<T extends { length: number }>(value: T, minimum: number): T {
  if (value.length >= minimum) return value;
  // @ts-expect-error 仅有 length 的对象不一定是调用方选择的 T
  return { length: minimum };
}

为什么这里报错？因为调用方可能把 T 定成 string，而 { length: 5 } 不是字符串。函数承诺返回 T，就只能返回真的属于 T 的值。

keyof 配合索引访问

TypeScript
function getProperty<T, K extends keyof T>(object: T, key: K): T[K] {
  return object[key];
}
const user = { name: 'Lin', age: 24 };
const age = getProperty(user, 'age'); // number
// @ts-expect-error missing 不是 user 的键
getProperty(user, 'missing');

keyof T 是 T 所有键组成的联合，这里是 'name' | 'age'。K 被限制在这个范围里，传错键名直接报错。T[K] 叫索引访问类型，意思是“T 里键 K 对应的类型”，所以传 'age' 得到的是 number，而不是笼统的 string | number。

默认值、const 和 NoInfer

TypeScript
type ApiResponse<T = unknown> = { data: T; status: number };
const raw: ApiResponse = { data: null, status: 200 }; // T 为 unknown

function routes<const T extends readonly string[]>(paths: T): T {
  return paths;
}
const r = routes(['/a', '/b']); // readonly ['/a', '/b']

function createState<T extends string>(states: T[], initial: NoInfer<T>) {
  return initial;
}
// @ts-expect-error 'c' 不在 states 推断出的 'a' | 'b' 中
createState(['a', 'b'], 'c');

ApiResponse 不写类型实参时，T 就用默认的 unknown。routes 的 const T 让编译器像加了 as const 一样推断，得到只读元组 readonly ['/a', '/b']，而不是 string[]。

NoInfer 解决的是另一个问题。没有它的话，'c' 也会参与推断，T 变成 'a' | 'b' | 'c'，错误就被藏起来了。加上 NoInfer 以后，T 只从 states 推断，initial 只负责被检查。

泛型管不到的地方

泛型不做运行时检查。fetchJson<User>(url) 里如果只是 as T，这个 User 只是调用方的期望，接口真返回什么它不知道。更好的写法是接收一个解析函数 (input: unknown) => T，让它去真正校验。

还有两个小习惯。读取数组第一项的函数，返回类型应该是 T | undefined，因为数组可能是空的。一个类型参数只出现一次，比如 <T>(x: T): void，它没有连接任何关系，直接写 unknown 更清楚。

常见追问

泛型约束和函数重载怎么选？

输入和输出有统一的关系，用泛型；几种固定的调用方式各自返回不同类型，用重载，见《函数重载、联合参数与泛型怎样选择？函数类型何时可赋值？》。

为什么在 TSX 里写 <T>(x: T) => x 会报错？

因为 <T> 会被当成 JSX 标签。写成 <T,> 或 <T extends unknown> 就能区分开。
