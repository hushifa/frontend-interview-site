前端路由除切换组件外还需要管理什么？

从可恢复的 URL 出发解释参数、数据、历史、错误和焦点管理，并说明路由模式与深链接部署的关系，避免把路由当成组件切换器。

参考答案

简答

前端路由的核心是让 URL 成为界面状态的可恢复来源：路径和查询参数决定页面与筛选条件，支持刷新、分享和前进后退。hash 模式不需要服务器配置；history 模式地址更干净，但服务器要把所有路径回退到应用入口。导航时还要处理数据加载与取消、错误和 404、标题与焦点管理、滚动位置恢复。

用户打开一个筛选后的题库地址，刷新后仍应看到相同条件；按后退应回到前一个筛选；把链接发给别人，对方也能理解当前页面。这些都不是简单地“把组件 A 换成 B”就能完成的。

路由负责把地址、历史记录、数据加载和界面状态协调起来。它既是导航机制，也是一份关于页面能否直接访问、分享和恢复的契约。

哪些状态应该进入 URL

页面身份通常放在路径中，例如某篇文章的 ID；可分享的搜索、分类和页码常放在查询参数中；片段标识可以表达文档内的位置。

输入框焦点、弹窗里的未提交输入和临时拖拽位置通常不需要进入 URL。是否保存某个状态，要看用户是否希望刷新、回退或分享时恢复它，而不是所有状态都写进去。

一旦 URL 是某项状态的事实来源，就要避免另一个 store 长期保存互不关联的副本。搜索输入可以有临时草稿，但提交后应明确怎样转成规范 URL。

路由参数同样需要解析和校验

查询参数都是外部输入。页码可能是负数、小数或超大数，分类可能不存在，重复参数也需要约定怎样处理。

下面演示一个题库查询的读取规则：

JavaScript
function parseQuestionUrl(address) {
  const url = new URL(address);
  const params = url.searchParams;
  const allowedCategories = new Set(['all', 'javascript', 'css']);
  const requestedCategory = params.get('category') ?? 'all';
  const pageText = params.get('page') ?? '1';
  const pageNumber = /^\d+$/.test(pageText) ? Number(pageText) : NaN;

  return {
    keyword: (params.get('q') ?? '').trim(),
    category: allowedCategories.has(requestedCategory) ? requestedCategory : 'all',
    page: Number.isSafeInteger(pageNumber) && pageNumber > 0 ? pageNumber : 1,
  };
}

这里要求传入完整 URL，使用第一项同名查询参数，非法分类与页码回到默认值。实际页码是否超过结果总页数，还需要数据层判断；不是解析成正整数就一定有那一页。

构造 URL 时应使用 URL、URLSearchParams 或框架提供的接口，正确处理中文、空格和 + 等字符。字符串拼接容易把值中的特殊字符变成新的参数结构。

push 与 replace 影响用户的后退体验

push 创建新的历史位置，replace 更新当前位置。用户明确进入一个新页面通常值得保留历史；输入时每个字符都 push，则可能让后退需要按几十次。可以按产品约定在编辑中 replace，提交或关键筛选变化时 push。

使用原生 History API 时，pushState/replaceState 不会因此自动触发一次 popstate，也不会自动让组件重新渲染。路由库会组织状态同步，自己实现时必须处理这些不同入口。

后退不等于重新执行一次普通点击。它可能恢复历史状态、滚动位置或 bfcache 页面，加载与失效策略也应覆盖这种情况。

数据加载与导航应属于同一次操作

新页面可能需要数据、权限检查或代码分包。用户快速连续导航时，旧请求不应在新页面上提交结果；导航取消与请求取消需要关联，仍不支持取消的数据源也要检查结果是否过期。

还要区分首次加载、后台刷新、参数变化和表单提交后的重新验证。loading 不应永远覆盖已有可用内容，错误也应落到合适的路由边界，而不是任何子区域失败就让整站白屏。

React Router 的 Declarative、Data 和 Framework 模式提供不同程度的组织能力。Data 模式增加 loader/action、等待与错误等数据路由能力，Framework 模式进一步结合构建插件和路由模块；不能把某种模式的 API 直接复制到另一种用法中。具体选择取决于愿意让框架管理多少内容，也要核对项目版本。

守卫与深链接

前端守卫只控制界面导航，接口必须由服务端重新鉴权，详见路由并发与权限一题。History 路由的地址在直接打开和刷新时也要由托管服务返回正确入口，回退规则与 404 处理见 SEO 与部署一题；hash 路由不依赖服务端配置，代价是地址可读性和 SEO 较差。

导航完成还需要让用户知道发生了什么

更新标题，提供适当的主内容焦点或导航通知，并处理滚动恢复。进入新页面通常不应停留在上一页底部；后退又可能需要恢复之前的位置，不能每次都无条件滚到顶部。

保留普通链接的语义也很重要：新标签打开、复制地址、浏览器前后退和键盘操作都属于导航体验。复杂路由器可以帮助组织这些能力，但仍需要应用明确地址、数据与交互之间的规则。
