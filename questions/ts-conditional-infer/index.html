条件类型、infer 和分布式条件类型如何理解？

条件类型根据类型可赋值关系选择结果，infer 在匹配结构中提取组成部分。裸类型参数会对联合成员分别计算，元组包装则可改为整体判断；never、any 和重载需要单独理解。

参考答案

简答

  • 条件类型 T extends U ? X : Y 按类型关系选择结果。
  • infer 在条件类型中声明待推断的类型变量，例如提取函数返回值或 Promise 内部类型。
  • 裸类型参数遇到联合类型时会分布到每个成员上分别计算。
  • 用 [T] extends [U] 包裹可以关闭分布行为。

条件类型写成 T extends U ? X : Y，意思是根据 T 能否满足 U 的类型关系，选择 X 或 Y。这里的 extends 不是运行时的 instanceof，也不会在 JavaScript 中生成一个 if。

它适合表达“如果输入类型具有某种结构，就提取其中一部分，否则给出另一个类型”，避免为每种具体类型手工重复声明。

先看一个读取消息类型的条件

TypeScript
type MessageOf<T> = T extends { message: unknown } ? T['message'] : never;

type TextMessage = MessageOf<{ message: string }>;
type NoMessage = MessageOf<{ id: number }>;

const message: TextMessage = '加载失败';

// @ts-expect-error TextMessage 是 string，不接受 number
const wrongMessage: TextMessage = 123;

当 T 有 message 成员时，结果是该成员的类型。没有成员时，这份工具选择 never，表示没有可提取的消息类型；也可以按接口需要设计成其他回退，但要把语义说明白。

条件类型是在处理类型，不会从一个真实对象里取出 message 值。运行时代码如果要安全访问未知输入，仍然需要检查。

infer 在正在匹配的结构中命名一部分类型

TypeScript
type ElementOf<T> = T extends readonly (infer Item)[] ? Item : never;

type Numbers = ElementOf<number[]>; // number
type TupleValues = ElementOf<readonly ['ok', 1]>; // 'ok' | 1

type FunctionResult<T> =
  T extends (...args: infer Parameters) => infer Result ? Result : never;
type NameResult = FunctionResult<(id: number) => string>; // string

Item 是在数组结构匹配成功时推导出的元素类型，不是外部额外传进来的参数。readonly 写在匹配结构里，让普通数组和只读数组都能参与；如果只匹配可变数组，某些只读元组就不符合条件。

函数例子中，infer 同时匹配参数列表与返回部分，这里最终只使用 Result。实际业务可优先使用已有的 ReturnType、Parameters、Awaited 等工具，不必为了展示 infer 再维护一套语义相同的复杂实现。

infer 不是运行时反射，也不会读取一个函数执行后到底返回了什么。它根据已有静态签名推导；签名不准确时，推导结果不会自动变成真实数据的证明。

裸类型参数会把联合拆开计算

TypeScript
type ToArray<T> = T extends unknown ? T[] : never;
type Separated = ToArray<string | number>; // string[] | number[]

const onlyText: Separated = ['HTML'];
const onlyNumbers: Separated = [1, 2];

// @ts-expect-error 结果要求是其中一种数组，不是任意混合数组
const mixed: Separated = ['HTML', 1];

因为条件左侧直接是类型参数 T，传入 string | number 时会分别计算：先得到 string[]，再得到 number[]，最后把两者联合起来。

这与 (string | number)[] 不同。前者表示数组整体属于字符串数组或数字数组之一，后者允许同一个数组里混合两种值。理解这一步，很多看似古怪的条件类型结果就能展开推导。

“只要类型里出现联合就一定分发”是不准确的。关键在于条件检查位置是否是符合分发规则的裸类型参数。

用元组包装，改为判断整个联合

TypeScript
type ToArrayTogether<T> = [T] extends [unknown] ? T[] : never;
type Together = ToArrayTogether<string | number>; // (string | number)[]

const accepted: Together = ['HTML', 1];

方括号在这里形成一元素元组类型，使条件检查的左侧不再直接是裸 T。因此整个 string | number 一起通过判断，然后放进同一个数组元素类型中。

常见的 [T] extends [U] 写法不是特殊的括号装饰，而是通过包装类型改变了分发条件。是否应该阻止分发，要根据工具是在逐成员处理，还是在判断整体关系。

never 为什么经常让结果消失

TypeScript
type IsNeverDistributed<T> = T extends never ? true : false;
type IsNever<T> = [T] extends [never] ? true : false;

type Lost = IsNeverDistributed<never>; // never
type Found = IsNever<never>; // true

never 可以理解为没有成员的联合。分布式条件面对它时，没有任何成员可计算，因此结果仍是 never，并不会像普通直觉中的 if 一样得到 true。

元组包装后变成整体判断，才能表达“这个类型是否就是 never”。在 Exclude、Extract 一类按成员筛选的工具里，never 与其他类型联合时消失，恰好可以表示被排除的成员；它不是计算过程出了随机错误。

any、重载与递归需要额外谨慎

any 在许多条件类型中会使判断结果包含两侧分支，或者继续传播成更宽泛结果，具体取决于表达式。不能把它当作一个稳定的普通联合成员分析，也不应为了让类型运算通过就随便加入 any。

对重载函数进行返回类型推导，通常依据最后一个相关调用签名，而不是像实际调用表达式一样自动为某组参数挑选重载。例如 ReturnType 不会因为调用者心里想的是某个入参，就只得到那个重载的返回值。

递归条件类型可以展开嵌套结构，但也会增加实例化深度、联合规模和编译成本。内置工具已经覆盖的场景应优先复用；必须自定义时，用普通类型、联合、never、any、只读结构和实际重载分别验证。

好的类型工具应让调用方少写重复关系，同时保留可理解的错误信息。如果一个简单数据结构需要很长的递归条件和多层断言才能使用，通常值得先检查业务模型是否可以简化。
