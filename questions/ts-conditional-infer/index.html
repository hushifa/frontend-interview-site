条件类型、infer 和分布式条件类型如何理解？

条件类型就是类型层面的三元表达式 T extends U ? X : Y，infer 用来从匹配的结构里“抠出”一部分类型。传入联合类型时，它会对每个成员分别计算再合并，这叫分布式条件类型。

参考答案

简答

条件类型可以理解成类型版的三元表达式：T extends U ? X : Y，T 能赋值给 U 就得到 X，否则得到 Y。这里的 extends 意思是“能不能赋值过去”，跟类的继承没关系。

infer 是在匹配的时候顺便声明一个待推断的类型变量。比如 T extends Promise<infer V> ? V : T，匹配成功时 V 就是 Promise 里面包着的类型。内置的 ReturnType、Parameters、Awaited 都是这么写出来的。

如果条件左边直接是类型参数 T，传进来 A | B 这样的联合，它会把 A 和 B 分开各算一遍，再把结果合起来，这叫分布式条件类型。Exclude、Extract、NonNullable 就是靠这个特性实现的。

要注意两点。不想分开算，就把两边包成元组，写 [T] extends [U]。另外 never 会被当成空的联合，分布式计算的结果还是 never，所以判断是不是 never 要写 [T] extends [never]。

条件类型怎么读

先看最基本的写法。下面的 MessageOf 判断传进来的类型有没有 message 属性，有就把它的类型取出来。

TypeScript
type MessageOf<T> = T extends { message: unknown } ? T['message'] : never;
type A = MessageOf<{ message: string }>; // string
type B = MessageOf<{ id: number }>;      // never

{ message: string } 能赋值给 { message: unknown }，所以走问号后面的分支，得到 string。{ id: number } 没有 message，赋值不过去，走冒号后面的分支，得到 never。读条件类型时，把 extends 换成“能不能赋值给”去念，就不容易和继承搞混。

infer 怎样把一部分类型抠出来

很多时候我们不只想知道“是不是数组”，还想知道“数组里装的是什么”。infer 就是干这个的：在要匹配的结构里留一个空位，起个名字，匹配成功后这个名字就代表填进空位的类型。

TypeScript
type ElementOf<T> = T extends readonly (infer Item)[] ? Item : never;
type C = ElementOf<number[]>;              // number
type D = ElementOf<readonly ['ok', 1]>;    // 'ok' | 1

type MyReturnType<T> = T extends (...args: any[]) => infer R ? R : never;
type E = MyReturnType<(id: number) => string>; // string

type UnwrapPromise<T> = T extends Promise<infer V> ? UnwrapPromise<V> : T;
type F = UnwrapPromise<Promise<Promise<number>>>; // number

ElementOf 在数组元素的位置放了 infer Item，所以 number[] 匹配后 Item 就是 number。MyReturnType 把空位放在返回值上，取出的就是返回类型，这基本就是内置 ReturnType 的写法。UnwrapPromise 还调用了自己，一层层剥开嵌套的 Promise，直到不再是 Promise 为止。

infer 后面还能加约束，比如 T extends [infer H extends string, ...unknown[]] ? H : never，只有第一个元素是字符串时才匹配。另外，对有重载的函数用 ReturnType，取到的是最后一个重载签名的返回类型。

传入联合类型时为什么会“分开算”

看下面两个几乎一样的类型，只差在 T 外面有没有包一层方括号，结果却不一样。

TypeScript
type ToArray<T> = T extends unknown ? T[] : never;
type G = ToArray<string | number>; // string[] | number[]

type ToArrayTogether<T> = [T] extends [unknown] ? T[] : never;
type H = ToArrayTogether<string | number>; // (string | number)[]

type MyExclude<T, U> = T extends U ? never : T;
type I = MyExclude<'a' | 'b' | 'c', 'a'>; // 'b' | 'c'

ToArray 的条件左边直接是 T，TypeScript 会把 string | number 拆开，分别算出 string[] 和 number[]，再合成联合，这就是分布式条件类型。ToArrayTogether 把 T 包进了元组，左边不再是“光秃秃的类型参数”，所以联合被当成一个整体，得到的是 (string | number)[]。

MyExclude 正好利用了分开算：'a' 能赋给 'a'，结果是 never；'b'、'c' 赋不过去，保留下来。联合里的 never 会自动消失，最后剩下 'b' | 'c'。

记住触发条件：只有条件左边直接是被传入的类型参数时才会分布，写成 T[] extends ... 或 [T] extends ... 都不会。

为什么判断 never 要包一层

TypeScript
type IsNeverWrong<T> = T extends never ? true : false;
type IsNever<T> = [T] extends [never] ? true : false;
type J = IsNeverWrong<never>; // never
type K = IsNever<never>;      // true

按直觉，IsNeverWrong<never> 应该是 true，结果却是 never。原因是 never 在分布式计算里被当作一个成员都没有的联合，没有成员可算，结果就是空的，也就是 never。包成 [T] 关掉分布以后，[never] 能赋给 [never]，才得到 true。

any 也有特殊行为：它作为被检查的类型时，两个分支都会取，any extends string ? 1 : 2 得到 1 | 2。

什么时候不该写复杂的条件类型

递归条件类型能处理嵌套结构，比如写一个深层的 Readonly。可是它会拖慢类型检查，报错信息也很难读。内置工具类型够用时优先用内置的；业务代码里，一个简单的重载或联合类型往往比一段类型体操更好维护。

常见追问

怎样把联合类型转成交叉类型？

利用函数参数位置的推断。先把每个成员变成以它为参数的函数，再从这些函数的参数位置推断，结果就是交叉：(U extends any ? (x: U) => void : never) extends (x: infer I) => void ? I : never。这是因为参数位置是逆变的，多个候选会被合成交叉而不是联合。

模板字面量类型里能用 infer 吗？

能。比如 T extends `${infer Head}/${infer Rest}` ? Head : T，可以把 'a/b/c' 这样的路径拆出第一段 'a'，配合递归就能把整条路径拆开。
