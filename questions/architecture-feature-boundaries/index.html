前端大型项目怎样划分功能边界？

围绕一起变化的业务能力组织模块，明确公开接口、依赖方向和状态归属，并用订单功能说明如何逐步拆分而不制造新的耦合。

参考答案

简答

  • 按业务能力（订单、商品、账户）组织代码，比按技术类型（components、hooks、utils）更容易让一次需求只改一个目录。
  • 每个功能模块只通过一个公开入口（如 index.ts）对外暴露，其他模块不能深层导入它的内部文件。
  • 依赖方向单向：页面依赖功能模块，功能模块依赖共享层，共享层不依赖任何业务模块。
  • 每份状态只归一个模块所有，其他模块通过它的公开接口读取或触发变更。
  • 用 ESLint 规则或依赖检查工具强制这些约束，并按需求逐步迁移，而不是一次性重构。

按技术类型组织的问题

代码
src/
  components/OrderList.tsx
  hooks/useOrders.ts
  api/orders.ts
  store/orderSlice.ts

改一个订单需求要在四个目录间跳转，删除订单功能时也很难确认哪些文件可以一起删。

按功能组织

代码
src/
  app/            路由、全局布局、组装各功能
  features/
    orders/
      index.ts    公开入口
      api.ts
      OrderList.tsx
      useOrders.ts
    cart/
  shared/         与业务无关的 UI 组件、工具函数、请求封装
TypeScript
// features/orders/index.ts
export { OrderList } from './OrderList';
export { useOrderSummary } from './useOrders';
export type { OrderSummary } from './types';

其他模块只能 import { OrderList } from '@/features/orders'，api.ts 和内部组件可以自由修改而不影响外部。

依赖方向

代码
app → features → shared
  • shared 不导入任何 features。
  • 功能之间尽量不直接依赖。确实需要时（例如购物车需要显示商品信息），只依赖对方的公开入口，并避免循环依赖。
  • 跨功能的组合放到 app 层或页面中完成：页面同时引入订单和购物车组件，并在两者之间传递数据。

状态归属

订单列表的数据只由 orders 模块获取和缓存。购物车下单后需要刷新订单列表时，调用 orders 暴露的刷新方法或触发查询失效，而不是直接修改订单的 store。这样排查订单数据问题时只需要看一个模块。

强制约束

  • ESLint 的 no-restricted-imports 禁止导入 features/*/ 下的内部路径。
  • dependency-cruiser 等工具检查依赖方向和循环依赖，放进 CI。
  • monorepo 中可以把功能拆成独立包，用 exports 字段在包级别限制入口。

逐步迁移

  1. 新功能按新结构编写。
  2. 修改旧功能时顺手把它迁移到 features/ 下。
  3. 先建立公开入口，再逐步收紧导入规则。

一次性大规模搬迁会产生大量冲突，也很难评审。

常见追问

  • 共享组件放哪里？与业务无关的按钮、表格放 shared；只在两个功能间共享且带业务含义的组件，优先考虑放在其中一方并通过公开入口导出。
  • 这和微前端有什么关系？功能边界是代码组织层面；微前端还涉及独立部署和运行时集成，见《微前端适合解决什么组织和部署问题？》。
