前端大型项目怎样划分功能边界？

围绕一起变化的业务能力组织模块，明确公开接口、依赖方向和状态归属，并用订单功能说明如何逐步拆分而不制造新的耦合。

参考答案

判断模块边界，可以先问：修改一个业务需求时，通常要一起改哪些代码？如果修改订单取消规则，总要穿过全局 components、utils、services、store 中很多互不关联的文件，就值得把属于订单能力的部分组织到一起。

按文件类型分目录并没有天然错误，小项目也不必立即拆成几十个包。问题是随着规模增长，目录是否还能表达职责、状态由谁拥有，以及改动会影响哪里。

先划业务能力，再安排内部文件

订单功能可以拥有订单列表、详情、取消流程、状态转换和数据访问；账户功能负责登录会话与账户信息。模块内部仍可按 UI、模型、接口分层：

text
src/
  app/                 应用入口、路由与跨功能组合
  features/
    orders/
      ui/              订单界面
      model/           状态与业务规则
      api/             请求和响应转换
      public.ts        对外入口
    account/
      ...
  shared/
    ui/                不含订单等业务知识的基础组件
    lib/               通用底层能力

这是一种组织例子，不是所有项目必须遵守的模板。关键是外部通过明确入口使用 orders，而不是任意导入它内部的 store、私有组件和接口实现。

公开入口可以暴露页面入口、业务操作或只读查询，但不必把目录中所有文件重新导出。否则只是把深层依赖换了个路径，内部仍无法自由调整。

状态应该有明确的主人

“放进全局 store 最方便”往往让所有模块都有机会修改所有数据。更好的做法是先按生命周期和用途判断：

状态常见归属
输入框焦点、局部展开状态当前组件或局部交互
可分享的筛选、页码URL 与路由规则
服务端订单数据统一的请求缓存或订单数据层
尚未提交的表单草稿编辑流程，必要时持久化
登录会话的客户端视图账户能力或应用级会话层

这些位置也不是互相独立的五份事实。例如筛选条件已由 URL 表示，就不要再维护一个可能与 URL 不同的全局副本；请求缓存与表单草稿则要区分，避免刷新接口把用户未保存的输入覆盖掉。

状态所有者应定义怎样修改。外部需要取消订单时，调用相应操作并处理结果，比直接把另一个模块的 status 字段改成 canceled 更清楚。

跨模块协作不等于禁止所有依赖

订单可能确实需要当前账户信息，这种业务关系不会因为目录拆开就消失。可以依赖账户模块稳定的公开接口，或由应用层把用户标识、权限信息等必要输入传进去。

需要同时协调多个功能的流程，可以由应用层或明确的业务协调层组织，避免订单调用账户私有实现、账户又反过来调用订单，最后形成循环。

shared 应尽量依赖更基础的能力，而不反向知道具体订单页面。一个名叫通用弹窗的组件如果内部写满“订单”“发票”“退款”的分支，就已经承担业务职责，不能仅靠放进 shared 变成基础组件。

重复代码不一定马上值得共享

两个功能的代码现在看起来相似，可能只是碰巧具有相同外观。例如订单状态和审核状态都显示一个彩色标签，但状态来源、权限与转换规则不同。

可以共享稳定的标签视觉组件，同时保留各自的业务映射。若为了去重提取一个带十几个布尔参数的“万能状态组件”，以后两个业务分别演化时，反而更难维护。

值得共享的通常是语义和变化原因都相近的部分，而不只是几行代码长得一样。共享模块还会产生升级影响面，应有明确维护者。

目录本身不能阻止依赖穿透

公开入口、包 exports、路径约定和 lint/import 规则可以帮助约束允许的依赖方向；循环依赖检查、类型检查和模块测试可以尽早发现问题。

但 TypeScript 路径别名不会自动创建安全边界，前端模块私有也不能替代服务端权限验证。这里讨论的是代码组织与维护约束，不是把浏览器里的业务代码变成秘密。

模块独立测试也不自动意味着可以独立发布。如果最终仍一起构建、部署和运行，发布边界可能仍是整个应用；是否拆成独立包或微前端，应另行评估。

迁移可以从一个真实改动开始

选择一个边界比较清楚、近期需要修改的功能，整理它的数据入口和状态所有权，先建立对外契约，再逐步把内部实现移过去。旧调用可以通过临时适配层迁移，避免一次移动所有文件却没有改善依赖关系。

效果可以从具体变化判断：一个需求是否更少跨目录修改，测试能否只准备相关依赖，其他模块是否无需知道内部字段，循环依赖和跨模块条件分支是否减少。

划分不是越细越好。大量只有一个转发函数的小包、无意义的接口层和复杂构建链，也会增加理解成本。边界应帮助团队解释和修改业务，而不是只让目录看起来像某种架构图。
