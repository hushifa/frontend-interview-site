前端大型项目怎样划分功能边界？

按一起变化的业务能力组织模块，每个模块只通过公开接口对外，依赖方向单向，每份状态只归一个模块。用订单功能说明怎样逐步拆分，而不是制造新的耦合。

参考答案

简答

划分功能边界，最实用的标准是“哪些代码会一起改”。按业务能力组织，比如订单、商品、账户各一个目录，比按 components、hooks、utils 这种技术类型组织，更容易做到一次需求只改一个目录。

每个功能模块只留一个公开入口，比如 index.ts，别的模块只能从这里导入，不能深入到它内部的文件。依赖方向也是单向的：页面依赖功能模块，功能模块依赖共享层，共享层不依赖任何业务模块。

状态也要有归属。每份状态只归一个模块所有，其他模块想读或想改，都走它的公开接口。

这些约定光靠自觉守不住，要用 ESLint 规则或依赖检查工具强制。迁移也要按需求一点点做，不要一次性大重构。

按技术类型组织有什么问题

很多项目一开始是这样分目录的：

代码
src/
  components/OrderList.tsx
  hooks/useOrders.ts
  api/orders.ts
  store/orderSlice.ts

看着整齐，可改一个订单需求，要在四个目录之间来回跳。哪天要删掉订单功能，也很难确认哪些文件能一起删。因为同一个功能的代码被拆散了。

按功能组织是什么样

换成按功能分：

代码
src/
  app/            路由、全局布局、组装各功能
  features/
    orders/
      index.ts    公开入口
      api.ts
      OrderList.tsx
      useOrders.ts
    cart/
  shared/         与业务无关的 UI 组件、工具函数、请求封装

订单相关的东西都在 features/orders/ 里。它对外只通过 index.ts 暴露：

TypeScript
// features/orders/index.ts
export { OrderList } from './OrderList';
export { useOrderSummary } from './useOrders';
export type { OrderSummary } from './types';

别的模块只能写 import { OrderList } from '@/features/orders'。这样 api.ts 和内部组件怎么改都行，只要入口导出的东西不变，外面就不受影响。

依赖方向为什么要单向

依赖只能这样走：

代码
app → features → shared

shared 不能导入任何 features，否则共享层就带上了业务，谁都离不开它。

功能之间尽量不直接依赖。确实需要的时候，比如购物车要显示商品信息，也只依赖对方的公开入口，并且避免循环依赖。

需要把几个功能组合起来时，放到 app 层或页面里做。页面同时引入订单和购物车的组件，在两者之间传数据，这样订单和购物车彼此都不用认识对方。

状态归谁管

订单列表的数据，只由 orders 模块负责获取和缓存。

购物车下单以后，订单列表需要刷新。这时购物车不应该直接去改订单的 store，而是调用 orders 暴露的刷新方法，或者让对应的查询缓存失效。这样以后订单数据出了问题，只用看一个模块。

怎样强制执行这些约定

ESLint 的 no-restricted-imports 规则可以禁止导入 features/*/ 下面的内部路径。dependency-cruiser 这类工具可以检查依赖方向和循环依赖，放进 CI 里，违规的代码合不进去。如果是 monorepo，还可以把功能拆成独立的包，用 package.json 的 exports 字段在包这一级限制入口。

旧项目怎样逐步迁移

  1. 新功能按新结构写。
  2. 修改旧功能时，顺手把它迁到 features/ 下面。
  3. 先建立公开入口，再逐步收紧导入规则。

为什么不一次性搬完？因为大规模搬迁会和别人的代码产生大量冲突，评审也几乎没法做。

常见追问

共享组件该放哪里？

跟业务无关的按钮、表格放 shared。只在两个功能之间共享、而且带业务含义的组件，优先放在其中一方，通过它的公开入口导出。

这和微前端有什么关系？

功能边界是代码组织层面的事。微前端还涉及独立部署和运行时集成，见《微前端适合解决什么组织和部署问题？》。
