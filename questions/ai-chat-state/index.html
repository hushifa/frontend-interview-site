AI 聊天界面为什么不能只有 loading 一个状态？

等待服务端开始响应、正在接收内容、生成完成和请求失败，对用户意味着不同的事情。AI SDK 当前 useChat 的 status 区分 submitted、streaming、ready 和 error，可据此控制等待提示、停止按钮…

参考答案

AI 聊天界面不能只用一个 loading 布尔值。提交后可能还没有收到服务端响应，随后进入持续接收流，之后生成完成，也可能在中途取消或失败；这些状态决定了输入框、停止按钮、重试按钮和滚动行为是否应该可用。AI SDK 的 submitted、streaming、ready 和 error 只是状态分类，具体文案和交互仍要由产品决定。

消息也不应永远建模成一条字符串。一条回答可能同时包含文本、图片、引用、工具调用和工具结果，这些部分需要稳定的消息 ID 和 part ID，才能在流式更新、刷新恢复和重试时正确合并。只用数组最后一项或不断覆盖最后一段文字，很容易把两次请求的内容串在一起。

TypeScript
type ChatStatus = 'submitted' | 'streaming' | 'ready' | 'error';

type MessagePart =
  | { type: 'text'; text: string }
  | { type: 'tool-call'; id: string; name: string; status: 'waiting' | 'done' | 'error' };

中断和重试要有可解释的结果：用户主动停止后，已经收到的文本是否保留；网络失败后，重试是继续当前消息还是新建一次请求；工具已经执行一半时，界面如何提示。用户向上阅读历史消息时也不应被每个 token 强行滚回底部，屏幕阅读器则需要避免逐 token 高频播报。

模型输出、检索内容和工具结果仍是不可信输入。前端可以负责流式展示、状态反馈和用户确认，但密钥、权限和不可逆工具执行必须在受控边界。刷新、断网和多标签页场景都要能说明哪些内容已经保存，哪些任务仍在运行。
