视觉回归测试如何减少无意义的截图差异？

截图测试拿页面和基线图片逐像素比较。要稳定，就得固定浏览器和系统环境、等字体和数据就绪、遮住动态内容，再用 threshold、maxDiffPixels 等容差把抗锯齿噪声和真实变化分开。

参考答案

简答

视觉回归测试就是给页面拍一张标准照，叫基线，以后每次运行都重新截图，和基线逐像素比较。Playwright 里写 await expect(page).toHaveScreenshot()，第一次运行没有基线，测试会失败并把当前截图存成基线，人工确认后再提交。

截图最怕的是无意义的差异。不同系统、浏览器版本、字体和显卡渲染出来都不一样，所以基线文件名里带着浏览器和平台，比如 landing-chromium-linux.png，而且应该在固定的 CI 环境里生成和比较，比如官方 Docker 镜像。

页面上的动态内容也要处理。截图默认会禁用动画、隐藏光标；时间、随机数据、广告这类东西，用 mask 遮住，或者先把数据固定下来。剩下的细微噪声再交给容差：threshold 管单个像素的颜色差多少算一样，默认 0.2；maxDiffPixels 和 maxDiffPixelRatio 管允许多少像素不同。

界面是有意改的，就用 npx playwright test --update-snapshots 更新基线，并且在代码评审里看一眼新图。

一个稳定的截图测试长什么样

下面这个测试在截图前先固定了时间和接口数据，又遮住了在线客服窗口：

TypeScript
import { test, expect } from '@playwright/test';

test('价格页', async ({ page }) => {
  await page.clock.setFixedTime(new Date('2026-01-01T10:00:00'));
  await page.route('**/api/plans', (route) =>
    route.fulfill({ path: 'fixtures/plans.json' }),
  );
  await page.goto('/pricing');
  await expect(page.getByRole('heading', { name: '选择套餐' })).toBeVisible();

  await expect(page).toHaveScreenshot('pricing.png', {
    fullPage: true,
    mask: [page.getByTestId('live-chat')],
    maxDiffPixelRatio: 0.01,
  });
});

页面上显示的时间每次运行都不同，接口返回的价格也可能变，不处理的话每次截图都会有差异。所以先用 page.clock 把时间固定，用 page.route 返回固定的数据，再等标题出现，确认页面已经渲染好。

截图本身也有一层保护。toHaveScreenshot 会等页面连续两次截图一致后才去比较，这样就不容易截到渲染一半的样子。

三个容差怎样选

选项含义适合
threshold单个像素的颜色差异容忍度，0 最严格，1 最宽松抗锯齿、渐变的细微色差
maxDiffPixels允许不同的像素个数小组件，少量像素噪声
maxDiffPixelRatio允许不同的像素比例（0–1）整页截图，尺寸不固定

容差不是越大越好。设得太宽，按钮少了 1px 边框这种真实问题也会被放过去。正确的顺序是先通过固定环境和数据把噪声消掉，最后再用尽量小的容差兜底。全局默认值可以写在 playwright.config.ts 的 expect.toHaveScreenshot 里。

还有哪些地方会让截图不稳定

字体是一个大来源，系统字体在不同机器上不一样，所以用本地托管的 Web 字体。时间用 page.clock 固定，数据用 page.route 返回固定响应。视口大小要固定，必要时用 stylePath 注入只在截图时生效的样式，把滚动条或 iframe 隐藏掉。页面里有图片的话，等图片加载完再截图。

组件也能单独截图

整页截图能看到整体布局，组件截图更快，失败时也更容易看出是哪里坏了：

TypeScript
await expect(page.getByRole('dialog')).toHaveScreenshot('confirm-dialog.png');

如果用 Storybook 管理组件状态，每个 story 固定了一组 props 和数据，本身就相当于一个视觉用例。Storybook 官方的像素比较依赖 Chromatic 云服务；不用云服务的话，可以让 Playwright 逐个打开 story 的独立 iframe 页面截图：

TypeScript
import { expect, test } from '@playwright/test';

const stories = ['datepicker--closed', 'datepicker--open', 'datepicker--invalid'];

for (const id of stories) {
  test(`视觉：${id}`, async ({ page }) => {
    await page.goto(`/iframe.html?id=${id}&viewMode=story`);
    await expect(page.locator('#storybook-root')).toHaveScreenshot(`${id}.png`);
  });
}

story ID 是 Storybook 按标题和导出名生成的，以实际构建出来的 index.json 为准。直接从这个文件读列表，新增状态后也不会忘记登记。状态不用穷举，按风险挑：关闭、展开、错误、禁用、长文案、窄容器，这几种比所有组合都截一遍更有价值。

基线图片怎样管理

基线是绑定运行环境的。它要在 CI 用的同一个容器镜像里生成，开发者本机生成的图和 CI 不一致，提交上去只会让 CI 失败。

浏览器或字体升级时，会出现一大批合理的差异。这种基线更新要单独提交一次，不要和业务改动混在一起。平时更新基线，也只更新本次明确改过的组件状态，不要顺手把其他失败一起接受了；提交说明里写清改了哪些状态、主题和视口。

第一次生成的基线同样要人工确认，因为工具只是记下当前长什么样，不知道设计对不对。组件或状态删掉时，旧基线也一起删掉。

常见追问

截图测试失败了，怎么看？

打开 HTML 报告，里面会把期望图、实际图和差异图并排放着。先判断这是有意的修改、环境噪声，还是真的回归了，再决定是更新基线还是去修代码。
