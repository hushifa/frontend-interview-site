怎样实现一个 Node.js Worker Threads 任务池？

任务池预先创建固定数量的 Worker，用空闲列表、等待队列和按 ID 记录的在途任务三个结构分发任务，结果按 ID 回到调用方。生产环境还要处理 Worker 崩溃后补位、排队上限、任务超时和优雅关闭，池子大小一般不超过 CPU 核数。

参考答案

简答

Node.js 文档建议 CPU 密集任务用 Worker 池来跑，因为每个 Worker 都要初始化独立的 V8 实例和事件循环，每来一个任务就新建一个，创建的开销可能超过它带来的收益，并发一高线程数和内存也控制不住。为什么需要 Worker、线程之间怎样传数据，见《Node.js Worker Threads 适合解决什么问题？》。

任务池的做法是提前建好固定数量的 Worker，通常不超过 os.availableParallelism()。有任务来了，交给空闲的 Worker；没有空闲的，就先进队列排着。

每个任务带一个 ID，结果回来时按 ID 找到对应的调用方。某个 Worker 崩溃了，就让它手上的任务失败，再补一个新 Worker。

放到生产环境还要补几样：排队上限、任务超时，以及关闭时先等在途任务完成再终止 Worker。

一个能跑的最小任务池

下面的池子开 2 个 Worker，计算几个斐波那契数。重点看 #idle、#queue、#pending 这三个结构怎么配合：

JavaScript
import { Worker } from 'node:worker_threads';
import { availableParallelism } from 'node:os';

const workerSource = `
const { parentPort } = require('node:worker_threads');
parentPort.on('message', ({ id, n }) => {
  let a = 0n, b = 1n;
  for (let i = 0; i < n; i++) [a, b] = [b, a + b];
  parentPort.postMessage({ id, value: a.toString() });
});
`;

class WorkerPool {
  #idle = [];
  #queue = [];
  #pending = new Map();
  #nextId = 0;

  constructor(size) {
    for (let i = 0; i < size; i++) this.#spawn();
  }

  #spawn() {
    const worker = new Worker(workerSource, { eval: true });
    worker.on('message', ({ id, value }) => {
      this.#pending.get(id).resolve(value);
      this.#pending.delete(id);
      this.#release(worker);
    });
    worker.on('error', (error) => {
      // 崩溃的 Worker 上正在执行的任务失败，再补一个新 Worker。
      for (const [id, task] of this.#pending) {
        if (task.worker === worker) {
          task.reject(error);
          this.#pending.delete(id);
        }
      }
      this.#spawn();
    });
    this.#release(worker);
  }

  #release(worker) {
    const next = this.#queue.shift();
    if (next) this.#dispatch(worker, next);
    else this.#idle.push(worker);
  }

  #dispatch(worker, task) {
    this.#pending.set(task.id, { ...task, worker });
    worker.postMessage({ id: task.id, n: task.n });
  }

  run(n) {
    return new Promise((resolve, reject) => {
      const task = { id: this.#nextId++, n, resolve, reject };
      const worker = this.#idle.pop();
      if (worker) this.#dispatch(worker, task);
      else this.#queue.push(task);
    });
  }

  async close() {
    await Promise.all(this.#idle.map((worker) => worker.terminate()));
  }
}

const pool = new WorkerPool(Math.min(2, availableParallelism()));
const results = await Promise.all([10, 20, 30, 90].map((n) => pool.run(n)));
console.log(results); // [ '55', '6765', '832040', '2880067194370816120' ]
await pool.close();

#idle 放空闲的 Worker，#queue 放还没分到 Worker 的任务，#pending 按 ID 记着已经派出去、还没回来的任务。run 被调用时，有空闲 Worker 就直接派发，没有就排队。一个 Worker 算完发回消息，#release 先看队列里有没有等着的任务，有就接着干，没有才回到空闲列表。

四个任务同时提交，池子只有 2 个 Worker，所以后两个任务先排队，等前面的算完才被派出去。结果仍然按提交顺序排列，因为每个 Promise 只认自己的 ID，Promise.all 也按数组顺序返回。

示例为了能单独运行，用 eval: true 内联了 Worker 代码，实际项目应该放在独立文件里。close() 只终止空闲的 Worker，调用前要确保所有任务都已经完成。

放到生产环境还要补什么

问题处理方式
队列无限增长设置排队上限，超过时直接拒绝，例如返回 503，让上游重试或降级
单个任务卡死给任务设超时；超时后终止对应 Worker 并补一个新的
优雅关闭停止接收新任务，等待队列和在途任务完成，再调用 terminate()
大块二进制数据用 transferList 转移 ArrayBuffer，避免复制

池子开多大合适

一般按 CPU 核数来定。Worker 数超过核数，线程之间只是互相抢 CPU，总吞吐并不会提高。如果同一台机器上还跑着多个 Node.js 进程，每个进程的池都要相应缩小。

成熟的实现可以直接用 Piscina 这类库，上面这些问题它都处理了。

常见追问

为什么不用 cluster 代替？

cluster 复制整个服务进程来分担请求，适合扩展 I/O 吞吐；任务池是把单个请求里的重计算移出主线程。两者解决的问题不同。
