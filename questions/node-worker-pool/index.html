Node.js 为什么要用 Worker Threads 任务池，而不是每次请求都创建 Worker？

每个 Worker 都要启动新的 V8 实例，频繁创建会消耗时间和内存，并发高时还可能耗尽资源。任务池预先创建固定数量的 Worker，用队列分发任务，并处理 Worker 崩溃、排队上限和关闭流程。

参考答案

简答

  • 创建 Worker 要初始化独立的 V8 实例和事件循环，按请求创建会让启动成本叠加到每个请求上，并发高时线程数和内存不受控。
  • 任务池预先创建固定数量的 Worker（通常不超过 os.availableParallelism()），空闲时直接派发任务，没有空闲时进入队列。
  • 每个任务用 ID 对应结果；某个 Worker 崩溃时，让它正在执行的任务失败，并补一个新 Worker。
  • 生产环境还需要排队上限和超时，并在关闭时等待在途任务完成后再终止 Worker。

最小实现

JavaScript
import { Worker } from 'node:worker_threads';
import { availableParallelism } from 'node:os';

const workerSource = `
const { parentPort } = require('node:worker_threads');
parentPort.on('message', ({ id, n }) => {
  let a = 0n, b = 1n;
  for (let i = 0; i < n; i++) [a, b] = [b, a + b];
  parentPort.postMessage({ id, value: a.toString() });
});
`;

class WorkerPool {
  #idle = [];
  #queue = [];
  #pending = new Map();
  #nextId = 0;

  constructor(size) {
    for (let i = 0; i < size; i++) this.#spawn();
  }

  #spawn() {
    const worker = new Worker(workerSource, { eval: true });
    worker.on('message', ({ id, value }) => {
      this.#pending.get(id).resolve(value);
      this.#pending.delete(id);
      this.#release(worker);
    });
    worker.on('error', (error) => {
      // 崩溃的 Worker 上正在执行的任务失败，再补一个新 Worker。
      for (const [id, task] of this.#pending) {
        if (task.worker === worker) {
          task.reject(error);
          this.#pending.delete(id);
        }
      }
      this.#spawn();
    });
    this.#release(worker);
  }

  #release(worker) {
    const next = this.#queue.shift();
    if (next) this.#dispatch(worker, next);
    else this.#idle.push(worker);
  }

  #dispatch(worker, task) {
    this.#pending.set(task.id, { ...task, worker });
    worker.postMessage({ id: task.id, n: task.n });
  }

  run(n) {
    return new Promise((resolve, reject) => {
      const task = { id: this.#nextId++, n, resolve, reject };
      const worker = this.#idle.pop();
      if (worker) this.#dispatch(worker, task);
      else this.#queue.push(task);
    });
  }

  async close() {
    await Promise.all(this.#idle.map((worker) => worker.terminate()));
  }
}

const pool = new WorkerPool(Math.min(2, availableParallelism()));
const results = await Promise.all([10, 20, 30, 90].map((n) => pool.run(n)));
console.log(results); // [ '55', '6765', '832040', '2880067194370816120' ]
await pool.close();

示例为了能单独运行，用 eval: true 内联了 Worker 代码，实际项目应放在独立文件里。close() 只终止空闲 Worker，调用前要确保所有任务已经完成。

生产环境要补的部分

问题处理方式
队列无限增长设置排队上限，超过时直接拒绝，例如返回 503，让上游重试或降级
单个任务卡死给任务设超时；超时后终止对应 Worker 并补一个新的
优雅关闭停止接收新任务，等待队列和在途任务完成，再调用 terminate()
请求上下文AsyncLocalStorage 的 store 不会跨线程，需要在消息里带上请求 ID
大块二进制数据用 transferList 转移 ArrayBuffer，避免复制

池的大小一般按 CPU 核数设置。Worker 数超过核数时，线程之间互相抢占，总吞吐不会提高。如果同一台机器上还运行着多个 Node.js 进程，每个进程的池应相应缩小。

成熟的实现可以直接用 Piscina 这类库，它处理了上面这些问题。

常见追问

  • 为什么不用 cluster 代替？ cluster 复制整个服务进程来分担请求，适合扩展 I/O 吞吐；任务池把单个请求里的重计算移出主线程，两者解决的问题不同。
  • Worker 线程和 libuv 线程池是一回事吗？ 不是。libuv 线程池（默认 4 个线程）执行 fs、dns.lookup、部分 crypto 和 zlib 操作，不运行 JavaScript；Worker Threads 运行 JavaScript。
