WebRTC 为什么需要信令、STUN 和 TURN？

建立实时连接需要交换会话信息与候选连接信息，应用通常通过独立信令通道完成交换；WebRTC 并不规定必须使用某一种业务信令协议。ICE 组织连接候选和连通性检查。

参考答案

两台浏览器想通话，首先要知道对方是谁、能接收哪些媒体、有哪些可能连通的网络地址。WebRTC 提供实时媒体与数据通道能力，但不会替应用定义账号、房间和邀请流程，也不规定必须用哪一种信令协议。

可以把建立连接理解成两部分：信令负责交换协商信息，ICE 负责寻找并检查可用网络路径。STUN 和 TURN 是路径建立过程中可能使用的工具。

信令传递描述，不等于传输媒体

应用常通过 WebSocket、HTTP 或其他通道交换 offer、answer 和 ICE candidates。SDP 描述媒体与连接协商所需信息；它不是摄像头视频本身。

一方设置本地描述并发送给对方，对方设置远端描述后生成回应，双方还要处理候选信息的持续交换。候选可能在远端描述准备好之前到达，需要合理排队，不能一收到就无条件调用 addIceCandidate。

双方同时发起协商、增加轨道或网络变化时，状态还会更复杂。生产应用应采用成熟的协商模式，例如处理冲突的 perfect negotiation 思路，而不是只按“呼叫一次成功”的最短路径实现。

信令服务也必须鉴权，确认谁有权加入哪个房间。媒体 API 获准访问麦克风，不等于该用户有权加入任意会议。

ICE 选择能实际通信的候选对

浏览器可能收集本地接口候选、通过 STUN 获得的服务器反射候选，以及 TURN 中继候选。ICE 通过连通性检查找到可用候选对，并维护连接状态。

STUN 帮助了解客户端在外部网络看来使用的映射地址，不会替你永久打开所有 NAT 和防火墙。两端知道地址也不一定能直连，企业网络、网络转换规则和 UDP 限制都可能阻碍路径。

因此只在同一 Wi-Fi 下测试成功，不足以证明真实用户跨网通话可靠。

TURN 在需要时提供中继路径

TURN 服务可以分配中继地址，把流量经服务器转发，帮助无法直接互通的两端连接。生产系统常需要可用的 TURN 服务，而不是只配置一个公共 STUN 地址就结束。

中继会带来带宽与部署成本，需要身份凭据、容量和地域规划。还要测试在限制网络中可用的传输方式，不能假设所有用户都允许相同端口和协议。

TURN 负责转发，不自动成为懂业务媒体的会议服务器。WebRTC 传输加密与多方会议中的端到端加密概念也不同，不能因为用了 WebRTC 就宣称任何服务器都不可能访问媒体内容。

多人会议不一定是所有人两两互连

若 N 个用户使用全网状连接，每个用户可能需要向很多其他用户发送媒体，上传和编码成本随人数增加。实际会议常采用 SFU 转发媒体，或根据场景使用混流等架构。

此时浏览器的 peer 可能是媒体服务器，WebRTC 仍然适用。“PeerConnection”不保证对端一定是另一个浏览器，也不保证连接永远绕过服务器。

DataChannel 用于数据传输，不要求先获得摄像头；它与媒体轨道有不同使用方式。可靠性、顺序和消息大小等还要按业务及通道配置处理。

连接成功之后仍有生命周期

监听连接与 ICE 状态，区分暂时 disconnected 与确实 failed，不要一有短暂波动就重建全部会话。网络切换后可能需要 ICE restart 或重新协商，但恢复不能绕过房间权限与业务状态检查。

结束通话时关闭 PeerConnection、清理信令监听和计时器，并停止自己不再需要的本地 MediaStreamTrack。关闭连接不等于所有摄像头来源自动停止，也不代表页面里的 video.srcObject 已清空。

诊断可以结合 getStats 查看候选路径、丢包和往返等信息，但不要随意记录用户网络地址与媒体内容。验收应包含不同网络、TURN 路径、拒绝权限、设备切换和重连；一条本地回环连接只能证明很有限的环节。
