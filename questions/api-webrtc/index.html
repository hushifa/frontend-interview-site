WebRTC 为什么需要信令、STUN 和 TURN？

WebRTC 只负责点对点传输，双方交换 SDP 和 ICE 候选需要自己实现信令通道；STUN 帮设备发现自己的公网地址，TURN 在无法直连时中转流量。

参考答案

简答

  • 信令：建立连接前，双方要交换 SDP（媒体能力和编码参数）和 ICE 候选（可用的网络地址）。WebRTC 不规定信令方式，一般用 WebSocket 或 HTTP 实现。
  • STUN：设备通常在 NAT 后面，只知道自己的内网地址。STUN 服务器告诉它"你在公网上看起来是哪个 IP 和端口"，用于打洞直连。
  • TURN：对称型 NAT 或严格防火墙下无法直连时，TURN 服务器中转所有媒体数据。成本高，但保证能连上。
  • ICE：收集所有候选地址（本地、STUN 得到的、TURN 中继），逐对尝试连通，选出最好的一条路径。

连接流程

  1. A 创建 RTCPeerConnection，添加音视频轨道，生成 offer 并设为本地描述。
  2. A 通过信令把 offer 发给 B。
  3. B 设为远端描述，生成 answer，通过信令发回 A。
  4. 双方在 icecandidate 事件中拿到候选，通过信令发给对方，对方调用 addIceCandidate。
  5. ICE 找到可用路径，connectionState 变为 connected，媒体开始传输。
JavaScript
const pc = new RTCPeerConnection({
  iceServers: [
    { urls: 'stun:stun.example.com:3478' },
    { urls: 'turn:turn.example.com:3478', username: 'user', credential: 'temp-token' },
  ],
});

pc.onicecandidate = ({ candidate }) => signaling.send({ candidate });
pc.ontrack = ({ streams }) => {
  remoteVideo.srcObject = streams[0];
};

双方同时发起协商时容易冲突，处理方法见《WebRTC 的 perfect negotiation 如何避免协商碰撞？》。

TURN 的部署要点

  • 生产环境一定要配置 TURN，否则一部分用户会连不上。
  • TURN 凭据要由服务端按用户签发并设置短有效期，不要把长期密码写在前端代码里。
  • 只有 UDP 被封时还可以用 turns:（TLS over TCP 443 端口）穿透。

常见追问

  • 多人会议也是点对点吗：人数少可以网状互连，人数多时通常用 SFU 服务器转发，每个人只上传一路。
  • 数据通道：pc.createDataChannel() 可以在同一连接上传任意数据，支持可靠和不可靠两种模式。
