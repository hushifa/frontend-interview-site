WebRTC 为什么需要信令、STUN 和 TURN？

WebRTC 负责实时媒体和数据通道，但应用仍需通过信令交换会话描述，借助 ICE、STUN 和 TURN 建立可用网络路径；这些组件解决的是不同问题。

参考答案

简答

  • WebRTC 负责实时媒体和数据通道，但应用要自己实现信令。
  • 信令交换的是 SDP 会话描述和 ICE 候选，不传输媒体本身。
  • ICE 借助 STUN 发现公网地址，打洞失败时通过 TURN 中继。
  • 多人会议通常需要媒体服务器；连接建立后仍要管理生命周期。

WebRTC 连接不是“创建对象就通了”

两台浏览器要传视频，至少要解决三件事：双方如何找到彼此并交换协商信息，网络上是否存在可达路径，连接建立后如何传输和恢复媒体。WebRTC 提供后两部分的大量能力，但不负责账号、房间、邀请和业务权限。

因此信令、ICE、STUN 和 TURN 不是同一个东西：信令负责传递信息，ICE 负责收集和检查候选路径，STUN 帮浏览器发现外部映射地址，TURN 在直连失败时中继流量。

信令交换的是描述，不是视频

应用可以用 WebSocket、HTTP 或其他自定义通道传递 offer、answer 和 ICE candidates。SDP 描述媒体能力、编码、方向和连接协商信息，不是摄像头视频本身。

典型流程是：

  1. 一方创建 RTCPeerConnection 和本地媒体轨道。
  2. 创建 offer，设置本地描述并通过信令发送。
  3. 对方设置远端描述，创建 answer，再发回。
  4. 双方持续交换 ICE candidates。
  5. 连接状态变化后开始播放或发送数据。

候选可能在远端描述设置前到达，因此信令层要暂存并按顺序处理：

JavaScript
const pendingCandidates = [];
let remoteDescriptionReady = false;

async function receiveCandidate(candidate) {
  if (!remoteDescriptionReady) {
    pendingCandidates.push(candidate);
    return;
  }
  await peer.addIceCandidate(candidate);
}

async function markRemoteReady(description) {
  await peer.setRemoteDescription(description);
  remoteDescriptionReady = true;
  for (const candidate of pendingCandidates.splice(0)) {
    await peer.addIceCandidate(candidate);
  }
}

真实应用还要处理双方同时发起协商、增加轨道、网络切换和冲突，通常采用 perfect negotiation 等成熟模式。信令服务必须做房间鉴权；允许浏览器访问麦克风不代表用户有权加入任意会议。

ICE 会寻找可用候选对

浏览器会收集不同类型的候选：本机网络接口地址、通过 STUN 得到的服务器反射地址，以及 TURN 分配的中继地址。ICE 对候选对进行连通性检查，选择一条可工作的路径。

STUN 只是帮助浏览器了解自己在外部网络看到的映射地址。它不能保证 NAT 会允许入站连接，也不能解决企业防火墙、UDP 限制和对称 NAT。只在同一个 Wi-Fi 下测试成功，不能证明跨运营商和公司网络可用。

TURN 是可靠性成本，不是可选装饰

直连失败时，TURN 服务器可以作为中继转发媒体和数据。生产系统通常需要鉴权的 TURN 服务，而不是只配置一个公共 STUN 地址。TURN 会消耗服务器带宽，需要规划凭据、地域、容量、计费和过期时间。

中继服务器负责传输，不自动理解房间、录制或业务协议。WebRTC 的传输加密也不等同于“服务器永远无法访问媒体”，尤其在 SFU、混流、录制等架构中，媒体可能在服务器侧被处理。安全声明必须结合实际拓扑和密钥设计。

多人会议通常需要媒体服务器

N 个浏览器两两建立连接时，每个用户的上传、编码和连接数量会迅速增加。多人会议常用 SFU 接收并转发各路媒体，或使用混流服务器生成一路视频。此时 RTCPeerConnection 的对端可能是媒体服务器，不一定是另一台浏览器。

RTCDataChannel 可以独立传输聊天、控制和协作数据，不要求先打开摄像头。可靠性、顺序、消息大小和拥塞策略要按业务选择，不能把媒体轨道的假设直接套到数据通道。

连接成功后仍要管理生命周期

监听 iceConnectionState、connectionState 和轨道事件，区分短暂 disconnected 与确定 failed。网络切换可能需要 ICE restart 或重新协商，不要一有抖动就销毁整个会话。重连仍要重新检查房间权限和会话有效期。

结束通话时关闭 PeerConnection、移除信令监听和计时器，并停止不再使用的 MediaStreamTrack：

JavaScript
function closeCall(stream, peer, cleanupSignal) {
  cleanupSignal();
  for (const track of stream?.getTracks() ?? []) track.stop();
  peer.close();
}

关闭连接不会自动停止所有摄像头来源，也不会自动清空 video.srcObject。诊断可以使用 getStats() 查看候选路径、丢包和往返时间，但日志要避免暴露不必要的网络地址和媒体内容。验收应覆盖权限拒绝、跨网、TURN、设备切换、后台恢复和重连。
