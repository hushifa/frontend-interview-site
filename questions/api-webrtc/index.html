WebRTC 为什么需要信令、STUN 和 TURN？

WebRTC 只管点对点传数据，双方先要交换媒体参数和网络地址，这条信令通道得自己做。STUN 帮设备查到自己的公网地址，TURN 在实在连不上时帮忙中转。

参考答案

简答

两个浏览器要视频通话，连上之前得先互相了解：支持什么编码，以及从哪个地址能找到对方。前者叫 SDP，后者叫 ICE 候选。WebRTC 不规定怎么交换这些信息，这条通道叫信令，要自己用 WebSocket 或 HTTP 实现。

难点在网络地址。设备通常在 NAT（路由器的地址转换）后面，只知道自己的内网地址。STUN 服务器的作用是告诉它“你在公网上看起来是哪个 IP 和端口”，双方拿着公网地址尝试打洞直连。

但对称型 NAT 或严格的防火墙下，打洞会失败。这时就要 TURN 服务器，把所有媒体数据中转过去。成本高，但保证能连上。

把这些串起来的是 ICE：它收集所有候选地址，包括本地的、STUN 得到的、TURN 中继的，一对一对试，选出最好的一条路。所以生产环境一定要配 TURN，否则总有一部分用户连不上。

一次连接是怎么建立的

整个过程分五步：

  1. A 创建 RTCPeerConnection，添加音视频轨道，生成 offer 并设为本地描述。
  2. A 通过信令把 offer 发给 B。
  3. B 把它设为远端描述，生成 answer，通过信令发回 A。
  4. 双方在 icecandidate 事件里拿到自己的候选地址，通过信令发给对方，对方调用 addIceCandidate。
  5. ICE 找到可用的路径，connectionState 变成 connected，媒体开始传输。

可以看到，第 2、3、4 步都要靠信令。WebRTC 自己只负责第 5 步以后的传输。

下面是创建连接时配置 STUN 和 TURN 的代码：

JavaScript
const pc = new RTCPeerConnection({
  iceServers: [
    { urls: 'stun:stun.example.com:3478' },
    { urls: 'turn:turn.example.com:3478', username: 'user', credential: 'temp-token' },
  ],
});

pc.onicecandidate = ({ candidate }) => signaling.send({ candidate });
pc.ontrack = ({ streams }) => {
  remoteVideo.srcObject = streams[0];
};

每发现一个候选地址，onicecandidate 就触发一次，通过信令发给对方。对方的音视频到达时触发 ontrack，把流交给 <video> 播放。

双方同时发起协商时容易冲突，处理方法见《WebRTC 的 perfect negotiation 如何避免协商碰撞？》。

部署 TURN 要注意什么

TURN 一定要配，否则处在严格网络里的用户就连不上。

TURN 会中转流量，谁都能用就会被白嫖带宽。所以凭据要由服务端按用户签发，设置很短的有效期，不要把长期密码写在前端代码里。

有些网络把 UDP 全封了，这时还可以用 turns:，也就是走 TCP 443 端口上的 TLS，这个端口和 HTTPS 相同，通常不会被防火墙拦截。

常见追问

多人会议也是点对点吗？

人少的时候可以网状互连，每个人和其他人各连一条。人多了上传带宽扛不住，通常用 SFU 服务器转发，每个人只上传一路，由服务器分发给其他人。

WebRTC 只能传音视频吗？

不是。用 pc.createDataChannel() 可以在同一条连接上传任意数据，还能选可靠或不可靠两种模式。
