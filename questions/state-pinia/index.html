Pinia 中 state、getter 和 action 应如何分工？

state 保存状态，getter 表达派生值，action 承担明确的业务操作，可以包含异步流程。store 需要唯一 ID，适合跨组件共享而具有共同生命周期的数据。

参考答案

state 保存状态，getter 表达派生值，action 承担明确的业务操作，可以包含异步流程。store 需要唯一 ID，适合跨组件共享而具有共同生命周期的数据。

在“Pinia 中 state、getter 和 action 应如何分工？”这个问题中，先判断数据属于组件、URL、全局状态还是服务端缓存，再设计刷新、回退、失效和并发恢复；一个数据只能有一个明确事实来源。这里的 Pinia、Store、状态管理 不是孤立的 API 名称，而是会共同影响输入、过程和最终结果。

先判断数据的生命周期和分享范围：只在一个组件使用的状态不必提升，跨页面共享的数据不一定适合放进全局 store，服务端缓存也不等同于客户端状态。明确归属后，再设计更新、失效、刷新和回退行为。

组件仍可拥有局部状态，不应把每个输入框是否展开都放进全局 store。直接解构 store 的响应式属性可能失去关联，按需要使用 storeToRefs；action 方法可以按其 API 约定解构使用。

服务端渲染要注意每个请求的状态隔离以及序列化边界。请求失败、取消和重复调用应在 action 或相应数据层明确处理。持久化插件也不意味着可以把访问令牌或全部敏感数据随意写入浏览器存储。

路由参数、表单草稿、请求缓存和权限状态需要不同的持久化策略。刷新、重复请求、离线恢复和用户退出时，要验证旧数据不会覆盖当前页面。

实际应用中，URL、缓存和全局状态经常同时保存相似数据。应明确哪一个是可恢复的事实来源，其他地方只保留临时视图或缓存；否则刷新、回退和并发请求很容易出现页面显示与真实状态不一致。
