using 和 await using 解决什么资源清理问题？

用 using 声明的资源，离开代码块时会自动调用它的释放方法，不用再手写 try/finally。await using 用于需要异步释放的资源。这个特性还比较新，部分浏览器不支持。

参考答案

简答

打开文件、拿到锁、建立连接以后，用完必须释放。以前要手写 try/finally 保证释放，现在可以用 using 声明：using x = resource，等这个代码块结束时，不管是正常结束、return 还是抛错，都会自动调用 x[Symbol.dispose]()。

释放是异步的资源，比如要等网络关闭的连接，用 await using，它会调用并等待 x[Symbol.asyncDispose]()。它只能用在 async 函数或模块顶层。

多个资源会按声明的相反顺序释放，后拿到的先释放。如果主逻辑抛错，释放时又抛错，最终会得到一个 SuppressedError，它的 error 是释放时的错误，suppressed 是被压住的主逻辑错误。资源数量不固定时，用 DisposableStack。

要注意兼容性。这个特性在 TC39 列为 2027 版，MDN 标注为非 Baseline，部分浏览器还不支持。它是新语法，不支持的引擎在解析阶段就报错。

资源按什么顺序释放

下面声明两个资源，注意释放的顺序和获取的顺序是反的。

JavaScript
function resource(name) {
  console.log(`获取${name}`);
  return {
    [Symbol.dispose]() {
      console.log(`释放${name}`);
    },
  };
}

function work() {
  using first = resource('A');
  using second = resource('B');
  console.log('执行工作');
}

work();
// 输出：获取A → 获取B → 执行工作 → 释放B → 释放A

work 结束时，先释放 B 再释放 A。这样安排是因为后拿到的资源可能依赖前面的，比如先建立连接再开事务，那就要先结束事务再关连接。

这段代码的效果，等于自己写两层嵌套的 try/finally。using 只认 Symbol.dispose 这个方法，资源上有一个叫 close 的普通方法，它也不会去调。值是 null 或 undefined 时会跳过，其他没有这个方法的值会直接抛 TypeError。

await using 里为什么有两个 await

JavaScript
async function work() {
  await using connection = await openConnection();
  return connection.query('select 1');
}

两个 await 管的是不同的事。右边的 await 是等待获取资源，也就是等 openConnection() 完成。左边的 await using 表示退出作用域时，要等待异步释放完成，才算真正离开。

释放也出错时，得到哪个错误

JavaScript
function fail() {
  using resource = {
    [Symbol.dispose]() {
      throw new Error('释放失败');
    },
  };
  throw new Error('工作失败');
}

try {
  fail();
} catch (error) {
  console.log(error.name); // SuppressedError
  console.log(error.error.message); // 释放失败
  console.log(error.suppressed.message); // 工作失败
}

主逻辑抛了“工作失败”，释放时又抛了“释放失败”。手写 try/finally 时，finally 里的错误会把原来的错误盖掉，原来的错误就丢了。

using 不会丢。它把两个错误包成一个 SuppressedError：error 是后发生的释放错误，suppressed 是被它压住的工作错误，两个都能拿到。另外，一个资源释放失败以后，剩下的资源仍然会继续释放。

资源数量不固定时怎么办

using 要求一个资源写一行声明。要打开一组数量不定的文件，就用 DisposableStack，它像一个容器，把资源一个个登记进去，最后一起释放。

JavaScript
function openAll(paths) {
  using stack = new DisposableStack();
  const files = paths.map((path) => stack.use(openFile(path)));
  const owned = stack.move(); // 全部成功，转移所有权给调用方
  return { files, [Symbol.dispose]: () => owned.dispose() };
}

如果中途某个 openFile 抛错，stack 离开作用域，已经打开的文件会被逆序关闭，不会漏掉。

如果全部成功，这些文件要交给调用方继续用，不能在这里关掉。stack.move() 把登记的资源转移到一个新的栈 owned 上，原来的 stack 变空，退出时就什么都不释放。调用方拿到返回值以后，再自己决定什么时候释放。

还有两个登记方法：stack.adopt(value, fn) 给没有实现释放协议的对象配一个释放函数，stack.defer(fn) 登记任意一个清理回调。

什么场景不适合用

using 的释放时机是跟着代码块走的，所以资源的生命周期必须和作用域一致。组件、订阅这类创建以后要长期存在的对象，不适合在创建它的函数里用 using，否则函数一返回它就被释放了。

如果代码块里有一个 await 永远不结束，作用域就不会结束，资源也不会释放，这时要配合 AbortSignal 去取消。进程被杀掉、页面被关闭时，清理代码也不保证会执行。

兼容性方面，因为是新语法，不支持的引擎在解析阶段就会报错，没法用 if 判断后降级。TypeScript 5.2 起可以把它编译成 try/finally，但运行时还需要 Symbol.dispose 和 DisposableStack 的 polyfill。

常见追问

和 try/finally 比好在哪里？

释放逻辑写在资源自己身上，调用方只要写 using，就不会忘记释放。多个资源也不用一层套一层地嵌套 try/finally，而且两个错误都能保留下来。

它和垃圾回收有关系吗？

没有关系。垃圾回收只管内存，而且什么时候回收不确定。using 是在确定的时间点释放文件句柄、锁这类外部资源。
