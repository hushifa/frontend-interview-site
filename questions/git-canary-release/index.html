前端怎样做灰度发布和金丝雀发布？出问题怎样回滚？

金丝雀发布先让一小部分用户用新版本，对比新旧版本的错误率和关键指标，没有退化再逐步放大比例。前端要让同一用户稳定命中同一版本，新旧两版的静态资源同时可用，接口对两版都兼容。回滚就是把流量切回旧版本，新版资源要保留到旧页面不再请求它们。

参考答案

简答

金丝雀发布就是新版本先只给一小部分用户用，观察指标没有变差，再一步步扩大范围，直到所有人都用上新版本。它也叫分阶段发布或增量发布，灰度发布说的也是这件事。

分给谁可以按随机比例，也可以按内部员工、地区或用户特征。前端分流有个特别的要求叫粘性：同一个用户在一次会话里要一直命中同一个版本，不能刷新一下就在新旧版本之间来回跳。

灰度期间新旧版本同时在线，所以两版 HTML 引用的静态资源都要能访问，后端接口和数据格式也要同时兼容两版。放不放量要看提前定好的标准：对比金丝雀组和对照组的错误率、接口失败率、性能指标和关键业务转化，明显变差就停。

回滚就是把流量切回旧版本。要注意，已经打开新页面的用户还会继续请求新版资源，所以切流时不能马上把新版资源删掉。

分流放在哪一层

方式做法注意点
入口分流CDN、网关或边缘函数按 Cookie 或比例返回不同版本的 index.html入口 HTML 不能被长时间缓存，否则切流不生效
功能开关同一份构建，运行时按开关决定是否启用新功能新旧代码同时打包，开关清理不及时会积累分支

入口分流是在用户拿到 HTML 之前就决定给哪个版本，适合整站升级，比如换框架、改构建配置。功能开关是同一份代码里包着新旧两套逻辑，运行时决定走哪一套，适合单个功能灰度，切换时不用重新发布。开关怎样稳定分桶、怎样清理，见《前端功能开关和灰度发布应该怎样设计？》。

新旧版本怎样同时在线

靠的是资源文件名里带内容哈希，比如 app.3f2a1c.js。内容不同，文件名就不同，两版资源可以放在同一个目录里互不覆盖。所以发布时是把新资源追加进去，而不是先清空目录再上传。

为什么旧资源不能马上删？因为旧版本的页面可能在用户浏览器里开着很久，它按需加载的分块指向的还是旧文件名。删旧资源前要等足够长的时间，或者在分块加载失败时提示用户刷新。资源路径和缓存怎样检查，见《静态托管发布时为什么要检查资源路径和缓存？》。

接口这边要注意顺序。先上线一个同时兼容新旧格式的后端，再灰度前端，等全部切换完，最后才移除旧格式的支持。顺序反过来，灰度期间还在用旧版前端的用户就会出错。

怎样观察指标、什么时候放量

放量通常分几个阶段，比如 1%、10%、50%、100%，每个阶段停一段时间，让指标攒够样本再判断。

要能比较，监控和错误上报就得带上版本号，不然分不清哪些错误来自金丝雀组、哪些来自对照组。

还要和 A/B 测试分开。金丝雀用来发现新版本有没有变差，按分钟到小时判断；A/B 测试用来验证产品假设，需要更长时间。两件事不要混在一起做。

出了问题怎样回滚

入口分流的话，把新版本的比例调回 0 就行，不用重新构建。功能开关灰度的话，把开关关掉。回滚之后还要确认入口、资源和关键交互都正常，完整流程见《静态网站发布失败时怎样安全回滚？》。

常见追问

纯静态托管没有网关，还能灰度吗？

托管平台不支持按请求分流时，只能在运行时用功能开关，或者把新版本发布到另一个地址，让部分用户去访问。

为什么用户刷新一下，版本就变了？

要么是分流没有粘性，要么是入口 HTML 被缓存了。要用 Cookie 这类标识把用户固定在一个分组里，同时让入口文件只做短缓存。

数据库迁移怎么办？

迁移要做到新旧两版代码都能正常运行。灰度阶段不能做那种只有新版本才能读的改动。
