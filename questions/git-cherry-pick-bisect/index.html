git cherry-pick 和 git bisect 分别解决什么问题？

cherry-pick 把指定提交引入的修改重新应用到当前分支，生成哈希不同的新提交，常用来把修复移植到发布分支。bisect 在一个已知正常、一个已知有问题的提交之间二分查找，定位第一个引入问题的提交，可以配合脚本用 bisect run 自动执行。

参考答案

简答

cherry-pick 解决的是“只要某一个提交”的问题。比如主干上修了一个 bug，线上维护的发布分支也要这个修复，但不能把主干其他改动带过去。git cherry-pick <提交> 会算出这个提交相对它父提交改了什么，把这份改动应用到当前分支，生成一个新提交，新提交的哈希和原来的不一样。加上 -x，提交说明末尾会多一行 (cherry picked from commit ...)，以后能查到修复来自哪里。

bisect 解决的是“哪个提交引入了问题”。你告诉它一个有问题的提交和一个正常的提交，它每次检出中间那个让你标记 good 或 bad，范围每次减半，大约 log2(N) 步就能找到第一个坏提交。

判断好坏能用命令完成时，用 git bisect run <命令> 让它自动跑。它看命令的退出码：0 是好，125 是跳过，1 到 127 之间的其他值是坏，128 及以上会中止整个 bisect。

结束后用 git bisect reset 回到原来的分支。

cherry-pick 怎样把修复移植到发布分支

bash
git switch release/1.2
git cherry-pick -x 71b8558

先切到发布分支，再把主干上的修复提交挑过来。遇到冲突时，解决完 git add，再 git cherry-pick --continue；不想要了就 git cherry-pick --abort。如果挑的是一个合并提交，要用 -m <父编号> 指定以哪个父提交为主线，不然 Git 不知道“改动”该相对哪一边算。

这样做以后，同一份修改在两个分支上各有一个提交。之后两个分支合并时，Git 通常能认出内容相同；可是如果其中一边又改了同一处，还是可能冲突。如果团队需要大量 cherry-pick，往往说明分支策略该调整了，参见《git merge 与 rebase 应该怎样选择？》。

bisect 怎样一步步找到坏提交

手动二分的流程是这样的：

bash
git bisect start HEAD v1.0   # 先坏后好
# Git 检出中间提交，测试后标记
git bisect good   # 或 git bisect bad
# 重复直到输出 "<哈希> is the first bad commit"
git bisect reset

git bisect start 后面先写坏的、再写好的。为什么能这么快？因为每标记一次，可疑范围就减掉一半。比如两个版本之间有 1000 个提交，大约 10 步就能找到。

能用命令判断好坏时，就交给 bisect run：

bash
git bisect start HEAD v1.0
git bisect run npm test
git bisect reset

这里有个容易出错的地方。如果测试命令在某些提交上根本跑不起来，比如依赖装不上，脚本应该返回 125，让 Git 跳过这个提交；不然它会被当成坏提交，结果就找错了。脚本因为被信号终止等原因返回 128 及以上时，Git 会报错停下，不会把当前提交标记为坏。

常见追问

bisect 之前要注意什么？

工作区要干净。测试脚本最好放在仓库外面，或者放在不受历史版本影响的位置，不然检出旧提交时，脚本可能根本不存在。

问题时有时无怎么办？

二分要求每一步判断都准确。偶发问题要先找到稳定复现的办法，或者在脚本里多跑几次再给结论。

cherry-pick 和 rebase 有什么关系？

rebase 可以看成把一串提交依次 cherry-pick 到新的基点上。
