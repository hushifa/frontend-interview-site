Node.js Worker Threads 适合解决什么问题？

区分 Worker Threads 与异步 I/O、子进程和集群，理解线程通信、数据传递和共享内存边界。

参考答案

Worker Threads 适合把 CPU 密集型 JavaScript 计算移出主线程，例如解析、压缩或特定算法。它不能让阻塞代码自动变成异步，也不是处理普通网络 I/O 的首选；Node 的异步 I/O 本身通常已经不需要额外线程来包装。

主线程和 Worker 通过消息通信，数据通常经过结构化克隆，也可以使用 transferable 对象转移所有权；SharedArrayBuffer 和 Atomics 提供共享内存能力，但会带来同步复杂度和数据竞争风险。创建 Worker 也有启动成本，应根据任务粒度和并发上限设计池，而不是每个请求都创建一个线程。

Worker 中的异常、退出、取消和资源释放都要显式处理。来自用户的任务仍需限制输入规模和执行时间，避免把 Worker 变成新的拒绝服务入口。

Node.js 代码比浏览器拥有更广的文件、网络和进程权限。处理请求时要限制请求体、并发、超时和连接生命周期，并对路径、命令参数、Header 和环境变量做输入校验。

CPU 密集任务、流式响应和上游重试会影响整个进程的资源。BFF 可以整理接口和会话，但不能替代业务服务的认证、授权、幂等和审计。

实际 BFF 中，客户端传来的参数和上游返回的数据都应重新校验。为每个上游调用设置超时、大小和并发边界，并在日志中隐藏令牌和个人数据，才能让服务在异常流量下保持可诊断。
