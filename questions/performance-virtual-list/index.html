虚拟列表怎样减少长列表的渲染成本？

虚拟列表只挂载视口附近的内容，但要同时解决高度估算、滚动锚点、焦点保留和浏览器查找等正确性问题。

参考答案

虚拟化真正解决的是什么

渲染一万行表格时，慢的不只是第一次创建 DOM。每一行都可能有图片、事件监听、布局计算和组件状态，滚动过程中浏览器还要维护这些节点。虚拟列表把数据和 DOM 分开：数据仍然有一万条，但只渲染视口附近的一小段。

为了让滚动条看起来仍然代表完整列表，虚拟列表会保留一个具有总高度的容器，再把当前窗口的行放在对应偏移处。用户看到的是几十个节点，滚动范围仍然像一万行。

固定高度时可以直接计算窗口

如果每行高度都固定，滚动位置到索引的计算比较简单：

JavaScript
function getWindow({ scrollTop, viewportHeight, rowHeight, total, overscan = 4 }) {
  const first = Math.floor(scrollTop / rowHeight);
  const start = Math.max(0, first - overscan);
  const count = Math.ceil(viewportHeight / rowHeight);
  const end = Math.min(total, first + count + overscan);

  return {
    start,
    end,
    offsetTop: start * rowHeight,
    totalHeight: total * rowHeight,
  };
}

渲染 [start, end) 的行，并把它们放在 offsetTop 位置。overscan 是视口外的缓冲区：太小会在快速滚动时出现空白，太大则增加渲染工作。它应根据设备性能、行复杂度和滚动速度调整。

真实代码还要节流滚动事件、处理容器尺寸变化，并在数据减少时把 scrollTop 限制在新的最大值内。只减少 DOM 数量，不处理这些边界，仍会出现跳动和错位。

动态高度会改变后续所有位置

行里有换行文本、图片或可展开答案时，不能再用 index * rowHeight。虚拟器通常先用估计高度计算位置，行挂载后通过 ResizeObserver 测量真实高度，再更新高度缓存和总高度。

如果第二行从 60px 变成 120px，第三行以及后面所有行的起点都会下移 60px。测量结果应批量处理，避免在一次滚动回调里不断读取和写入布局。图片应提前预留尺寸，字体加载和内容展开则要使对应缓存失效。

高度缓存要使用稳定数据 ID，而不是只按索引保存。排序、筛选和插入数据后，索引对应的对象已经变了，继续使用旧高度会造成错误位置。

滚动锚点决定用户会不会迷路

聊天记录向顶部插入历史消息时，用户通常希望原来看到的那条消息仍然保持在原位置。可以记录锚点行的稳定 ID 和它相对视口的距离，前方内容高度发生变化后，只补偿变化量。

但不能每次测量都强行设置 scrollTop。用户正在拖动滚动条、已经主动滚向其他位置或浏览器正在执行自身滚动锚定时，程序无条件修正会与用户争夺控制权。只有在用户仍接近锚点且变化来自内容测量时，才适合自动补偿。

虚拟化会影响焦点和无障碍

正在编辑的输入框可能因为离开窗口被卸载，焦点、光标和未保存状态都会丢失。可以把编辑状态提升到列表外，暂时保留活动行，或使用独立编辑面板。键盘移动到未挂载的行时，要先更新活动索引、滚动到目标，等待节点出现后再设置焦点。

列表、表格和网格应使用与交互相符的语义，并提供位置和总量信息。aria-activedescendant 引用的节点必须真实存在。只给容器加几个 ARIA 属性，不能解决节点根本没有挂载的问题。

什么时候不应该虚拟化

浏览器页面查找、复制和打印无法可靠访问没有挂载的行。长文阅读、需要全文搜索的文档、打印报表和搜索引擎抓取页面，分页、分段渲染或静态详情页可能更合适。

因此验收不能只看“DOM 从一万行变成几十行”。还要测试快速滚动、动态高度、顶部插入、筛选删除、滚动到指定项、键盘编辑、读屏器和移动端。虚拟化是性能与原生行为之间的取舍，不是所有长页面的默认方案。
