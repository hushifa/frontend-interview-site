微前端适合解决什么组织和部署问题？

微前端主要解决多个团队要独立开发、独立部署的组织问题。构建时集成、运行时集成与 iframe 各有取舍，要提前考虑契约、共享依赖、故障隔离、样式隔离和回滚的成本。

参考答案

简答

微前端主要解决的是组织问题，不是技术问题。一个产品由好几个团队负责不同的部分，每个团队都想按自己的节奏开发、部署和回滚，这时才需要微前端。

集成方式大致三类：构建时集成，也就是把子应用发成 npm 包；运行时集成，比如 Module Federation、import maps、qiankun；还有 iframe。只有运行时集成和 iframe 能真正独立部署。

代价是很多原本不用操心的事都要自己处理：共享依赖的版本、样式隔离、全局状态、一个子应用挂了别拖垮整页。子应用之间只能通过明确的契约通信，比如路由、事件和少量共享数据，不能互相访问内部实现。

所以要注意，如果团队不多、发布节奏也一致，一个模块划分得好的单体应用通常更简单。

什么时候值得用

第一种情况是产品由多个团队负责，每个团队需要独立发布。第二种是要渐进迁移旧系统，比如在旧的 AngularJS 应用里，一页一页换成 React。第三种是不同部分对技术栈确实有不同要求。

反过来，如果所有代码都是一个团队在维护，微前端带来的协调成本往往比收益大。按功能把模块分好就够了。

几种集成方式怎么比

方式独立部署隔离性主要成本
构建时（npm 包）否，主应用要重新构建无发布要串行协调
Module Federation是弱，共享同一个页面共享依赖版本协商
import maps + ES 模块是弱手动管理模块地址和共享依赖
qiankun / single-spa是JS 沙箱和样式隔离（不完全）框架自身复杂度
iframe是强通信、路由同步、弹窗和样式统一困难

构建时集成看起来最简单，但子应用一更新，主应用就得重新构建发布，团队之间还是绑在一起。iframe 隔离最彻底，可正因为隔得太开，通信、路由同步、弹窗盖住整页这些事都变难了。

Module Federation 怎么用

Module Federation 由 webpack 5 引入，它让一个应用在运行时加载另一个应用暴露出来的模块。Module Federation 2.0 又提供了 Rspack、Vite 等工具的插件。

子应用 orders 这样声明自己暴露什么：

JavaScript
// 子应用 orders 的配置
new ModuleFederationPlugin({
  name: 'orders',
  filename: 'remoteEntry.js',
  exposes: { './OrderPage': './src/OrderPage.tsx' },
  shared: { react: { singleton: true }, 'react-dom': { singleton: true } },
});

主应用像导入普通模块一样用它：

JavaScript
// 主应用
const OrderPage = React.lazy(() => import('orders/OrderPage'));

配置里的 singleton 很关键。它让 React 在页面上只加载一份。要是主应用和子应用各加载了一份 React，Hooks 就会报错。

用了以后必须处理哪些问题

共享依赖是第一个。版本不一致时，同一个库可能被加载好几份，体积变大，像 React 这种只能有一份的库还会直接出错。所以要约定共享库的版本范围和升级流程。

样式冲突是第二个。可以用 CSS Modules、命名前缀或 Shadow DOM 隔离，全局样式只由主应用提供。

故障隔离是第三个。子应用加载失败或运行报错时，主应用要用错误边界显示降级内容，不能让整页白屏。

契约和回滚是最后一个。路由前缀、跨应用的事件名、共享数据的格式，都要写成文档并做版本管理。每个子应用能独立回滚，前提是它和主应用之间的契约是向后兼容的。

常见追问

登录状态怎么共享？

由主应用负责登录，通过 Cookie 或共享的上下文把用户信息提供给子应用。子应用不要各自实现一套登录。

微前端会影响性能吗？

会。请求变多，还可能有重复代码。需要靠共享依赖和合理的预加载来弥补。
