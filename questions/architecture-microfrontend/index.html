微前端适合解决什么组织和部署问题？

从团队独立交付的需求判断微前端是否值得，比较构建集成、运行时集成与 iframe，并说明契约、依赖、故障、隔离和回滚成本。

参考答案

简答

  • 微前端主要解决组织、集成和发布问题，不是组件多就要采用的拆分技巧。
  • 先判断是否真的需要独立发布、独立承担质量和故障隔离。
  • 共享大量同步状态的业务拆开后仍难独立交付，模块化单体或 monorepo 可能就够了。
  • 按完整业务能力划分边界，集成方式决定实际承担的成本。

一个大型产品可能由订单、账户和报表等团队分别负责。如果每次修改报表都必须与整个应用一起协调构建、测试和发布，团队的交付节奏就会互相牵制。微前端尝试让业务区域拥有较独立的开发与交付边界，再组合成用户看到的完整产品。

它主要回答组织、集成和发布问题，不是“组件很多”就必须采用的代码拆分技巧。代码可以在一个应用中按业务模块组织，是否还要拆成独立运行或发布单元，需要额外收益来支撑。

先判断需要独立的是什么

可以具体看几个问题：不同团队是否真的需要不同发布频率，是否能分别承担线上质量，某个区域故障是否需要与其他区域隔离，以及当前协调成本是否主要来自统一发布。

如果业务之间共享大量同步状态、每次变更都必须一起改协议，即使拆成几个仓库，也可能仍然无法独立交付。反过来，边界清晰的模块化单体或 monorepo，也能解决很多代码归属和复用问题，不必立刻增加运行时远程加载。

边界通常应沿相对完整的业务能力划分，而不是把页面中的每个小按钮交给一个独立应用。过细的拆分会把本地函数调用变成大量跨应用协议。

集成方式决定你实际承担哪些成本

方式主要特点需要注意
构建时集成子模块以包等方式进入宿主构建运行模型较直接，但发布常仍需要更新宿主
运行时加载宿主按需加载独立产物或远程模块可以解耦发布，但多出网络失败、版本匹配和运行时契约
iframe使用独立文档集成文档与样式边界明确，路由、尺寸、焦点、认证与通信更复杂

这些方式不是只有优缺点的静态排名。选型应对应真实需求：需要独立部署、迁移旧技术、明确文档边界，还是隔离不可信内容。

运行在同一个 window 中的远程 JavaScript 通常共享大量页面能力，不因为叫子应用就获得安全隔离。iframe 的安全边界也取决于源与 sandbox 等配置；同源且具有广泛权限的 iframe，不能一概宣称与宿主完全隔离。

宿主与子应用要有可验证的契约

至少需要约定谁负责主导航和 URL、怎样挂载与卸载、如何传入会话上下文、哪些事件可以跨边界，以及发生错误时由谁展示恢复入口。

例如子应用卸载后，应释放自己的监听器、定时器、订阅和挂载节点，不能留下下一次进入时会重复执行的后台工作。路由也不应由多个子应用任意覆盖同一段全局历史状态。

认证上下文可以由宿主协调，但权限仍要由服务端验证。不要把“宿主告诉我当前用户有某权限”当成接口授权的全部依据，也不应把长期秘密通过任意全局变量广播。

跨应用事件需要明确结构和版本。让子应用直接读取另一个子应用的私有 store，通常会把发布依赖重新绑在一起。

共享依赖需要在体积与兼容之间取舍

每个子应用独立携带框架，可能重复下载；所有应用强制共用一份框架，又会把版本升级变成全局协调。某些库还依赖单一实例或兼容的运行时，多份 React 等依赖可能引发特定集成问题。

因此要明确哪些依赖由宿主提供、兼容范围是什么、谁验证升级，以及旧子应用还能支持多久。运行时加载工具可以协助实现共享，不会自动证明所有版本组合都兼容。

视觉一致性也可以通过设计 token 和稳定的基础组件契约推进，不必共享所有业务状态。CSS Modules、Shadow DOM 等能提供不同程度的样式封装，但不能被混同为任意脚本的安全隔离。

子应用加载失败时，产品仍需要可用状态

远程脚本可能超时、返回错误版本或初始化失败。宿主应区分加载中、可重试失败、运行错误和功能不可用，并尽量让无关区域继续工作。

组件错误边界不一定能捕获资源获取、模块引导和所有异步错误，初始化链路也要有独立处理。不要让一个远程模块的 Promise 永远挂起，整个页面就一直等待。

本地开发还需能复现宿主、子应用与后端的版本组合，日志应能关联具体发布版本。只有多个开发服务器都能启动，不代表线上混合版本已经被验证。

独立部署还必须有独立回退的条件

回滚不仅是把入口配置改回旧字符串，还要确保对应资源仍可提供、宿主契约兼容、后端协议没有单向破坏，以及已经打开的页面如何恢复。

可以根据部署方式重新发布对应版本或管理版本清单，但不能假定旧资源地址永远可用。宿主和子应用同时变更时，需要明确哪些组合允许上线，哪些变更必须分阶段兼容。

测试上既要有子应用自己的边界测试，也要有覆盖关键跨应用流程的集成测试。共享登录、路由和基础组件发生变化时，完全只测一个子应用通常不够。

最后应比较真实收益：团队是否更少相互等待、是否能在明确契约下发布与回滚、故障是否更容易定位。若这些收益不足以覆盖网络、治理和运维成本，维持清晰的模块化应用往往更合适。
