原型污染为什么常出现在动态属性赋值和深合并中？

属性名由外部输入决定时，写到 __proto__ 上就等于改了所有普通对象共享的原型。防法是拦掉危险的键、用没有原型的对象或 Map 存动态键，并且只按白名单取字段。

参考答案

简答

普通对象读不到自己的属性时，会去它的原型 Object.prototype 上找，而所有普通对象共用这一个原型。obj['__proto__'] 拿到的正是这个共享原型，如果再往上面赋值，所有对象就都“继承”了这个值，这就是原型污染。

它常出现在属性名由外部输入决定的地方。比如按路径设置值的工具函数、递归的深合并、把查询字符串解析成嵌套对象。攻击者只要让某个键是 __proto__，就能一路写到共享原型上。

后果是 if (user.isAdmin) 这类读继承属性的判断会被绕过，或者配置默认值被篡改，在 Node 里还可能进一步导致代码执行。

防御上，拒绝 __proto__、constructor、prototype 这几个键；动态键用 Object.create(null) 或 Map 存；更可靠的是按 schema 只取已知字段。要注意，JSON.parse 本身不会污染，危险发生在之后交给不安全的合并逻辑。

先看一个例子

下面直接用 __proto__ 作为键赋值，然后看一个全新的空对象能读到什么：

JavaScript
const record = {};
record['__proto__']['demoPermission'] = 'admin';
console.log(Object.hasOwn(record, 'demoPermission')); // false
console.log({}.demoPermission); // admin
delete Object.prototype.demoPermission;

record 自己身上并没有 demoPermission，可一个跟它毫无关系的 {} 却读到了 admin。原因是 record['__proto__'] 就是 Object.prototype，第二步赋值实际改的是所有对象共享的原型。最后一行把它删掉，是为了不影响后面的代码。

深合并是怎么被利用的

真实代码里很少有人直接写 obj['__proto__']，更常见的是一个通用的深合并函数：

JavaScript
function merge(target, source) {
  for (const key of Object.keys(source)) {
    if (typeof source[key] === 'object' && source[key] !== null) {
      target[key] ??= {};
      merge(target[key], source[key]);
    } else {
      target[key] = source[key];
    }
  }
  return target;
}

const input = JSON.parse('{"__proto__":{"preview":true}}');
console.log({}.preview); // undefined，JSON.parse 本身没有污染
merge({}, input);
console.log({}.preview); // true，合并时 target['__proto__'] 指向了 Object.prototype

先看第一个输出，JSON.parse 之后 {}.preview 还是 undefined。因为 JSON.parse 遇到 __proto__ 只会创建一个名字叫 __proto__ 的普通自身属性，不会改原型。

问题出在合并。Object.keys(input) 会列出 __proto__ 这个键，合并函数接着读 target['__proto__']。对普通对象来说，这个读取拿到的是 Object.prototype，它不是 null，??= 不会替换它，于是下一层递归就往 Object.prototype 上写了 preview: true。

怎么改

改法是遇到危险的键直接跳过，并且只在目标自己身上有对象时才往下递归：

JavaScript
const BLOCKED = new Set(['__proto__', 'constructor', 'prototype']);

function safeMerge(target, source) {
  for (const key of Object.keys(source)) {
    if (BLOCKED.has(key)) continue;
    const value = source[key];
    if (typeof value === 'object' && value !== null && !Array.isArray(value)) {
      // 目标缺少该键或是原始值时，换成新对象再递归
      if (!Object.hasOwn(target, key) || typeof target[key] !== 'object' || target[key] === null) {
        target[key] = {};
      }
      safeMerge(target[key], value);
    } else {
      target[key] = value;
    }
  }
  return target;
}

为什么 constructor 和 prototype 也要拦？因为 obj.constructor.prototype 同样指向 Object.prototype，攻击者可以绕一圈走这条路。

黑名单之外还有更根本的办法。存放动态键的字典用 Object.create(null) 或 Map，它们没有原型链可走，__proto__ 在里面只是一个普通的键。接口参数按 schema 校验后只取已知字段，比任何黑名单都可靠。权限判断用 Object.hasOwn 或显式的默认值，不依赖继承来的属性。

还可以用 Object.freeze(Object.prototype) 加固，让原型根本改不了。可是有些第三方库会修改内置原型，冻结后可能出问题，要充分测试。

常见追问

对象展开 { ...input } 安全吗？

展开本身不会改原型，它会把 __proto__ 当作普通的自身属性复制过来。可是危险的键还在新对象里，之后交给不安全的合并函数，照样会污染。

前端的原型污染危害有多大？

可以绕过前端的特性开关，或者改写模板库的配置引发 XSS。不过最终的权限判断应该在服务端做，前端的判断被绕过不应该直接造成越权。
