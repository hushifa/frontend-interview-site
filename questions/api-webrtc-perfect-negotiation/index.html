WebRTC 的 perfect negotiation 如何避免协商碰撞？

两端同时发起协商会撞车。perfect negotiation 给一端"礼貌"、一端"不礼貌"的角色：撞车时不礼貌的一方不理对方的 offer，礼貌的一方回滚自己的 offer 去应答。两端代码一样，只有 polite 不同。

参考答案

简答

视频通话里，A 打开屏幕共享，B 同时打开摄像头，两边都要重新协商，各自发出一个 offer，这就撞车了，术语叫协商碰撞（glare）。

perfect negotiation 的思路是事先定好谁让步。一端设 polite = true（礼貌方），另一端设 false（不礼貌方），比如先连上信令服务器的那端当礼貌方。撞车时，不礼貌方直接忽略收到的 offer；礼貌方照样 setRemoteDescription(offer)，浏览器会隐式回滚它自己的 offer，然后应答。

判断是否撞车，要用自己维护的 makingOffer 和 isSettingRemoteAnswerPending，不能只看 signalingState，因为它是异步变化的，会漏判。

还有一个细节：被忽略的 offer 还会带来一些 ICE 候选，addIceCandidate 报错时要忽略掉。两端代码完全一样，只有 polite 不同。

完整代码

下面是 MDN 推荐的写法，两端都跑这段代码。

JavaScript
// 两端代码相同，只有 polite 不同：一端为 true，另一端为 false。
const polite = isFirstToJoin;
let makingOffer = false;
let ignoreOffer = false;
let isSettingRemoteAnswerPending = false;

pc.onnegotiationneeded = async () => {
  try {
    makingOffer = true;
    await pc.setLocalDescription();
    signaler.send({ description: pc.localDescription });
  } catch (error) {
    console.error(error);
  } finally {
    makingOffer = false;
  }
};

pc.onicecandidate = ({ candidate }) => signaler.send({ candidate });

signaler.onmessage = async ({ data: { description, candidate } }) => {
  try {
    if (description) {
      const readyForOffer =
        !makingOffer && (pc.signalingState === 'stable' || isSettingRemoteAnswerPending);
      const offerCollision = description.type === 'offer' && !readyForOffer;

      ignoreOffer = !polite && offerCollision;
      if (ignoreOffer) return;

      isSettingRemoteAnswerPending = description.type === 'answer';
      await pc.setRemoteDescription(description);
      isSettingRemoteAnswerPending = false;

      if (description.type === 'offer') {
        await pc.setLocalDescription();
        signaler.send({ description: pc.localDescription });
      }
    } else if (candidate) {
      try {
        await pc.addIceCandidate(candidate);
      } catch (error) {
        if (!ignoreOffer) throw error;
      }
    }
  } catch (error) {
    console.error(error);
  }
};

核心就两行：offerCollision 判断收到的 offer 是不是撞车了，ignoreOffer = !polite && offerCollision 决定要不要忽略。礼貌方从来不忽略，所以会走到 setRemoteDescription，让浏览器回滚自己的 offer。

为什么要自己维护 makingOffer

setLocalDescription() 是异步的。从开始创建 offer 到真正发出去这段时间，signalingState 可能还是 stable。如果这时收到对方的 offer，只看状态会以为没撞车，可实际上自己的 offer 马上就要发出去了。所以要用 makingOffer 标记“我正在发 offer”。

isSettingRemoteAnswerPending 是干什么的

本端正在应用对方的 answer 时，状态还是 have-local-offer，看起来像是“我发了 offer 还没完成”。但其实协商马上就会回到 stable，这时收到对方的新 offer，并不是撞车，只要排在后面处理就行。这个标记就是为了不把这种情况误判成碰撞。

不传参数的 setLocalDescription 和隐式回滚

代码里 setLocalDescription() 没传参数。浏览器会根据当前状态自动创建 offer 或 answer，所以不用自己写 createOffer、createAnswer 和状态判断。

隐式回滚是指：礼貌方处于 have-local-offer 状态时，调用 setRemoteDescription(offer)，现代浏览器会自动把本地的 offer 撤回，不需要手动传 { type: 'rollback' }。

为什么两端代码一样

两端只有 polite 的值不同，其他逻辑完全相同。所以任何一端都可以随时添加或移除轨道、重启 ICE，negotiationneeded 会自动触发协商，撞车了就由角色决定谁让步，不用区分谁是“呼叫方”。

常见追问

为什么 addIceCandidate 报错时要忽略？

不礼貌方忽略了对方的 offer，但对方还会继续发这个 offer 对应的 ICE 候选。这些候选没有对应的远端描述，添加时会报错。这时 ignoreOffer 为 true，报错就忽略；否则才是真错误，要抛出去。

能不能只用 signalingState 判断碰撞？

不能。状态是异步变化的，创建 offer 的过程中它可能还是 stable，会漏判。所以要配合 makingOffer 和 isSettingRemoteAnswerPending 一起判断。
