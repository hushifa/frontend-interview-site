Electron 的 IPC 和 contextBridge 怎样设计？

渲染进程到主进程有单向与双向两种通信，主进程可以向指定窗口推送，渲染进程之间用 MessagePort 直接通信。preload 通过 contextBridge 只暴露窄接口，跨进程只传可序列化数据。

参考答案

简答

Electron 的页面跑在渲染进程里，打开文件、改窗口标题这些事要交给主进程做，两个进程之间传消息就叫 IPC。页面要等结果时，用 ipcRenderer.invoke 配合主进程的 ipcMain.handle，拿到一个 Promise；只通知不等结果，用 ipcRenderer.send 配合 ipcMain.on。

反过来，主进程推消息给页面，要指定是哪个窗口，调用它的 webContents.send，页面用 ipcRenderer.on 接收，这个方向没有对应的 invoke。两个渲染进程之间没有直接的通道，可以让主进程转发，或者由主进程分发一对 MessagePort，让它们直接通信。

这些能力不是直接给页面的，而是由 preload 脚本通过 contextBridge 暴露几个具体的业务函数。不要把 ipcRenderer 本身暴露出去；监听回调也要包一层，不能把 event 对象交给页面。

要注意，IPC 数据走结构化克隆，DOM 对象、BrowserWindow 这类由 C++ 支撑的对象传不过去。sendSync 会阻塞渲染进程，官方建议避免使用。

页面通知主进程，不需要结果

改窗口标题只是发个通知，用 send 和 on 就够了：

JavaScript
// preload.js
contextBridge.exposeInMainWorld('api', {
  setTitle: (title) => ipcRenderer.send('window:set-title', title),
});

// main.js
ipcMain.on('window:set-title', (event, title) => {
  BrowserWindow.fromWebContents(event.sender)?.setTitle(String(title));
});

主进程通过 event.sender 找到是哪个窗口发来的，再改它的标题。页面调用的是 window.api.setTitle，碰不到 ipcRenderer。

页面调用主进程，并等待结果

打开文件对话框要拿回用户选的路径，用 invoke 和 handle：

JavaScript
// preload.js
contextBridge.exposeInMainWorld('api', {
  openFile: () => ipcRenderer.invoke('dialog:open-file'),
});

// main.js
ipcMain.handle('dialog:open-file', async () => {
  const { canceled, filePaths } = await dialog.showOpenDialog({});
  return canceled ? null : filePaths[0];
});

invoke 从 Electron 7 开始提供，官方推荐尽量用它。handler 的返回值就是页面拿到的 Promise 结果。handler 里抛出的错误会被序列化，页面只能拿到 message，需要错误码的话，要在返回值里自己约定。

那以前是怎么做的？旧写法是 send 加 event.reply，需要另外注册一个监听器收回复，也没有内置机制把响应和请求对上号。sendSync 更不推荐，主进程回复之前，渲染进程会一直卡着。

主进程主动推消息给页面

比如用户点了菜单里的缩放，主进程要通知对应的窗口：

JavaScript
// main.js
win.webContents.send('menu:zoom', 1);

// preload.js
contextBridge.exposeInMainWorld('api', {
  onZoom: (callback) => {
    const listener = (_event, value) => callback(value);
    ipcRenderer.on('menu:zoom', listener);
    return () => ipcRenderer.removeListener('menu:zoom', listener);
  },
});

为什么不直接写 ipcRenderer.on('menu:zoom', callback)？因为回调的第一个参数是 event，通过 event.sender 能拿到 ipcRenderer，这等于把整个 IPC 能力交给了页面。包一层只把 value 传过去，就没有这个问题。

返回一个取消函数，是为了组件卸载时能移除监听。不然组件每挂载一次就多注册一个，既重复触发又泄漏内存。

两个窗口之间怎么直接通信

主进程用 MessageChannelMain 创建一对端口，通过 webContents.postMessage 分别发给两个窗口。之后两个窗口直接收发消息，不再经过主进程转发。utility 进程也可以用同样的方式和渲染进程直连。

接口应该怎么设计

通道名按业务来起，用 领域:动作 的形式，比如 note:save。这个前缀只是为了好读，Electron 不会据此做任何处理。

接口要窄。每个能力一个函数，参数固定，不要暴露 invoke(channel, ...args) 这种通用转发，否则页面可以调用任意通道。

通道名、参数和返回值类型最好集中放在一个共享的 TypeScript 文件里，主进程、preload 和页面共用，避免拼写对不上。

只传可序列化的数据。IPC 使用结构化克隆，Element、process.env、WebContents、BrowserWindow 等对象无法传递，函数也不能跨进程调用。传大文件时，优先传路径或者分块处理。

最后，主进程不能信任收到的任何输入，每个 handler 都要校验发送方和参数，具体做法见《Electron 应用的主进程、渲染进程和 IPC 有哪些安全边界？》。

常见追问

为什么不直接用 @electron/remote？

它让渲染进程同步调用主进程里的对象，既有性能问题，也扩大了渲染进程的权限，官方性能指南建议避免使用。

多个窗口同时调用同一个 handler，怎么区分？

handler 收到的 event.sender 和 event.senderFrame 标识了调用方，可以据此找到对应窗口，或者校验来源。进程职责划分见《Electron 的主进程、渲染进程、preload 和 utility 进程分别负责什么？》。
