前端插件系统怎样设计才能保持可维护？

插件系统要有一份稳定的插件契约，宿主通过 API 对象做能力注入，管好激活和停用的生命周期，契约带版本保证兼容，并做故障隔离。受信任插件可以同进程运行，不可信插件要放进 iframe/Worker。

参考答案

简答

插件系统的核心是一份稳定的契约：插件说明自己是谁、需要哪些能力、往哪些扩展点加东西。编辑器的状态栏、后台的菜单，都是这样的扩展点。

宿主不让插件直接碰自己的内部状态，而是把插件需要的能力打包成一个 API 对象传给它，这叫能力注入。插件能做什么，完全看这个对象里给了什么。

生命周期至少要有激活和停用两步。插件注册的监听器、定时器，停用时必须由宿主统一清理，不能指望插件自觉。契约还要带版本号，宿主按版本判断兼容不兼容，废弃的 API 先警告、再移除。

要注意安全边界。同进程运行的插件等于拥有整个页面的权限，只适合受信任的插件。不可信的第三方插件要放进 iframe 或 Worker 里隔离。

一个插件长什么样

下面是一个统计字数的插件，它在状态栏加一项，编辑器内容变了就更新字数：

JavaScript
export default {
  name: 'word-count',
  apiVersion: 1,
  activate(api) {
    const item = api.statusBar.add({ text: '0 字' });
    const off = api.editor.onChange((text) => {
      item.setText(`${text.length} 字`);
    });
    return () => {
      off();
      item.remove();
    };
  },
};

插件只用到了 api 里给它的两样东西：状态栏和编辑器的变化通知。它碰不到宿主的其他部分。activate 返回的函数是清理函数，停用插件时调用。

宿主要怎样实现

JavaScript
function loadPlugin(plugin, host) {
  if (plugin.apiVersion !== 1) throw new Error(`不支持的 API 版本：${plugin.apiVersion}`);

  const disposers = [];
  const api = {
    editor: {
      onChange(fn) {
        const off = host.editor.subscribe(safe(fn, plugin.name));
        disposers.push(off);
        return off;
      },
    },
    statusBar: {
      add(options) {
        const item = host.statusBar.create(options);
        disposers.push(() => item.remove());
        return item;
      },
    },
  };

  const cleanup = plugin.activate(api);
  return () => {
    cleanup?.();
    disposers.forEach((dispose) => dispose());
  };
}

function safe(fn, name) {
  return (...args) => {
    try {
      fn(...args);
    } catch (error) {
      console.error(`插件 ${name} 出错`, error);
    }
  };
}

你可能会问，插件不是已经返回了清理函数吗，宿主为什么还要自己记一份 disposers？因为插件可能忘了清理，也可能清理得不完整。宿主把插件通过 API 注册的每一样资源都记下来，停用时统一回收，就不会有漏掉的监听器一直挂着。

插件的回调都用 safe 包了一层错误捕获。这样一个插件出错，只会打一条日志，不会把编辑器和别的插件一起带崩。

API 对象也只暴露最小的能力，比如只读的文档内容和受控的修改方法。给得越少，插件能造成的破坏越小，宿主以后改内部实现也越自由。

插件多了怎样不拖慢启动

VS Code 这类成熟系统，让插件在清单文件里静态声明扩展点，比如命令、菜单、视图，以及什么时候激活。宿主不用加载插件代码，就能把菜单项显示出来，等用户第一次用到时才真正激活插件。这叫懒激活，插件一多，能明显缩短启动时间。

版本怎样保持兼容

宿主的 API 只增不改。需要改变行为时就新增一个 API，旧的标记废弃，在开发模式下打警告。

插件要声明自己兼容哪个范围的宿主版本，宿主遇到不兼容的插件就拒绝加载，并说明原因。宿主再提供一个 TypeScript 类型声明包，插件作者在编译时就能发现不兼容的用法。

不可信的插件怎样隔离

同进程运行的插件能访问 window、DOM 和 Cookie，等于拥有页面的全部权限。所以第三方插件应该放到隔离环境里运行。

一种是沙箱 iframe，带 sandbox 属性并且和宿主不同源。它可以渲染界面，通过 postMessage 和宿主通信。另一种是 Web Worker，它没有 DOM，适合纯计算或数据处理类的插件。

不管哪种，宿主都要在消息边界上校验来源和消息格式，只执行白名单里的操作。

常见追问

插件之间怎么通信？

通过宿主提供的事件或服务注册机制，插件之间不直接互相导入。

怎样避免插件拖慢宿主？

限制同步回调的执行时间，耗时的操作要求放进 Worker 或者异步执行，再提供性能统计，帮助定位是哪个插件慢。
