CSP 的 nonce、hash 与 Report-Only 如何使用？

CSP 用响应头告诉浏览器哪些脚本可以执行。nonce 是每次响应换一个的随机标记，hash 是固定脚本内容的指纹；新策略先用 Report-Only 只报告不拦截，确认没问题再强制执行。

参考答案

简答

CSP 是服务端通过响应头告诉浏览器“哪些脚本可以执行”。它是 XSS 的第二道防线：就算攻击者成功往页面里塞了一个 <script>，只要它没被策略授权，浏览器就不执行。

授权脚本常用两种办法。nonce 是服务端每次响应都随机生成一个值，同时写进响应头和合法的 <script nonce> 上，攻击者猜不到这个值。hash 是对固定的内联脚本内容算 SHA-256，适合静态站点。再加上 'strict-dynamic'，已授权的脚本动态加载的脚本也会被信任。

新策略不要直接上线。先用 Content-Security-Policy-Report-Only 下发，它只报告违规、不拦截，确认业务不受影响再改成强制执行。

要注意，nonce 必须每次响应都不同，不能写死在静态 HTML 里。另外 'unsafe-inline' 会让 CSP 对脚本注入几乎失效。

推荐的严格策略

http
Content-Security-Policy:
  script-src 'nonce-R4nd0m' 'strict-dynamic';
  object-src 'none';
  base-uri 'none'
HTML
<script nonce="R4nd0m" src="/assets/app.js"></script>

浏览器看到这个 <script> 上的 nonce 和响应头里的一致，才会执行它。攻击者注入的脚本拿不到这个值，所以跑不起来。

那么 nonce 为什么一定要每次响应都换？因为它的安全性全靠“攻击者猜不到”。所以要用密码学安全的随机数生成，不能写死在静态 HTML 里。也不能给拼进来的用户 HTML 统一补上 nonce，那等于把攻击脚本一起授权了。

另外两条指令是堵漏洞用的。object-src 'none' 禁用插件。base-uri 'none' 防止攻击者注入一个 <base> 标签，把页面上所有相对路径的脚本地址改到他的服务器上。

'strict-dynamic' 解决的是“授权脚本又加载了别的脚本”的问题。打包工具和第三方 SDK 经常动态创建 <script>，有了它，这些脚本自动继承信任。代价是此时 'self' 和主机白名单会被忽略，信任只从 nonce 或 hash 开始传递。

为什么不推荐只写域名白名单

script-src https://cdn.example 这种写法看起来很直观，但很容易被绕过。白名单里的域名上只要有一个 JSONP 接口或者一个旧版本的库，攻击者就能借它执行任意代码。所以更推荐 nonce 或 hash。

hash 怎么算

下面用 Node 算一段内联脚本的摘要，同时演示多一个换行会怎样：

JavaScript
import { createHash } from 'node:crypto';

const source = 'console.log("页面初始化");';
const digest = createHash('sha256').update(source, 'utf8').digest('base64');
console.log(`script-src 'sha256-${digest}'`);
// script-src 'sha256-wCEOeq5cgVDdzNa52AZZico2gWU77+6TJCQcYBtcW0Q='

const withNewline = createHash('sha256').update(`${source}\n`, 'utf8').digest('base64');
console.log(withNewline === digest); // false

只多了一个换行，摘要就完全变了。因为摘要针对的是 <script> 标签之间的确切内容，空格和换行都算在内。所以要按最终的构建产物计算，格式化工具改了一下缩进，策略就会失效。

迁移时常见的阻碍

老项目上 CSP，最常遇到的是内联事件属性，比如 onclick="..."。nonce 授权不了它，要改成 addEventListener。其次是 eval 和 new Function，它们需要 'unsafe-eval'，应该尽量把这类依赖去掉。

有人会想干脆加个 'unsafe-inline' 了事，可是这样 CSP 对脚本注入就几乎没用了。好在同时写了 nonce 或 hash 时，支持的浏览器会忽略 'unsafe-inline'，所以它可以作为旧浏览器的兼容项留着。第三方脚本再加载子脚本的情况，配合 'strict-dynamic' 处理。

上线前先用 Report-Only 观察，报告的配置和处理流程见《CSP Report-Only 和违规报告怎样用于安全治理？》。

常见追问

CSP 能放在 <meta> 里吗？

大部分指令可以。但 frame-ancestors、sandbox、报告相关的配置和 Report-Only 只能用响应头。

同时有多个 CSP 头时怎么生效？

每个都生效，资源必须同时满足所有策略。所以多加一个头只会更严格，不会放宽。

DOM 型 XSS 能怎么进一步约束？

可以用 Trusted Types 限制数据进入 innerHTML 这类危险入口，见《Trusted Types 会自动过滤所有危险 HTML 吗？》。
