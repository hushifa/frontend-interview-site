CSP 的 nonce、hash 与 Report-Only 如何使用？

CSP 用响应头告诉浏览器哪些脚本可以执行。nonce 是每次响应随机生成的标记，hash 是固定脚本内容的摘要，'strict-dynamic' 把信任传给已授权脚本加载的脚本；新策略先用 Report-Only 观察，再强制执行。

参考答案

简答

  • CSP 是 XSS 的第二道防线：即使攻击者注入了 <script>，没有被策略授权也不会执行。
  • nonce：服务端每次响应生成一个随机值，同时写进响应头和合法的 <script nonce>，攻击者猜不到。
  • hash：对固定内联脚本的内容算 SHA-256，适合静态站点。
  • 'strict-dynamic'：已授权的脚本动态创建的脚本也被信任，此时 'self' 和主机白名单会被忽略。
  • Content-Security-Policy-Report-Only 只报告不拦截，用于上线前验证，报告配置见《CSP Report-Only 和违规报告怎样用于安全治理？》。

推荐的严格策略

http
Content-Security-Policy:
  script-src 'nonce-R4nd0m' 'strict-dynamic';
  object-src 'none';
  base-uri 'none'
HTML
<script nonce="R4nd0m" src="/assets/app.js"></script>
  • nonce 用密码学安全的随机数生成，每次响应都不同。不能写死在静态 HTML 里，也不能给拼接进来的用户 HTML 统一补 nonce，那会连攻击脚本一起授权。
  • object-src 'none' 禁用插件，base-uri 'none' 防止注入 <base> 改写相对脚本地址。
  • 基于主机白名单的策略（script-src https://cdn.example）容易被白名单域名上的 JSONP 或旧版库绕过，更推荐 nonce 或 hash。

hash

JavaScript
import { createHash } from 'node:crypto';

const source = 'console.log("页面初始化");';
const digest = createHash('sha256').update(source, 'utf8').digest('base64');
console.log(`script-src 'sha256-${digest}'`);

摘要针对 <script> 标签之间的确切内容，空格或换行变化都会改变摘要，要按最终产物计算。

迁移时常见的阻碍

  • 内联事件属性（onclick="..."）不受 nonce 授权，改为 addEventListener。
  • eval、new Function 需要 'unsafe-eval'，应尽量移除这类依赖。
  • 'unsafe-inline' 会让 CSP 对脚本注入几乎失效；同时存在 nonce 或 hash 时，支持的浏览器会忽略 'unsafe-inline'。
  • 第三方脚本加载的子脚本：配合 'strict-dynamic' 处理。

常见追问

  • CSP 能放在 <meta> 里吗？大部分指令可以，但 frame-ancestors、sandbox、报告相关配置和 Report-Only 只能用响应头。
  • 多个 CSP 头怎么生效？都会生效，资源必须同时满足所有策略，结果只会更严格。
  • DOM 型 XSS 怎么进一步约束？见《Trusted Types 会自动过滤所有危险 HTML 吗？》。
