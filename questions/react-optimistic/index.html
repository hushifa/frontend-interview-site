useOptimistic 的临时状态怎样与真实结果收敛？

useOptimistic 在 Action 进行期间把临时更新叠加到当前确认值上，Action 结束后仍以传入的真实值为依据。成功要更新确认数据，失败要恢复并说明原因，临时显示不能代替服务端一致性。

参考答案

用户点击收藏后，可以先让按钮呈现正在收藏的样子，而不必等网络全部完成才给予反馈。但这时有两种状态：暂时希望达到的状态，以及已经确认成功的状态。

useOptimistic 让这两层关系更容易表达。它在 Action 期间提供临时视图，Action 结束后再根据传给 Hook 的确认值收敛；它并不替应用执行真正保存，也不会把临时结果自动变成持久数据。

用可失败的本地演示观察收敛过程

下面通过延迟模拟保存，没有服务器请求。勾选失败选项后，可以观察乐观状态如何回退。

JSX
import { useOptimistic, useState, useTransition } from 'react';

async function simulateSave(value, shouldFail) {
  await new Promise(resolve => setTimeout(resolve, 300));
  if (shouldFail) throw new Error('模拟保存失败，请重试。');
  return value;
}

export default function FavoriteDemo() {
  const [confirmed, setConfirmed] = useState(false);
  const [simulateFailure, setSimulateFailure] = useState(false);
  const [error, setError] = useState('');
  const [isPending, startTransition] = useTransition();
  const [optimistic, setOptimistic] = useOptimistic(confirmed, (_current, next) => next);

  function changeFavorite() {
    const next = !confirmed;
    startTransition(async () => {
      setError('');
      setOptimistic(next);
      try {
        const saved = await simulateSave(next, simulateFailure);
        startTransition(() => setConfirmed(saved));
      } catch (failure) {
        setError(failure instanceof Error ? failure.message : '保存失败');
      }
    });
  }

  return (
    <section>
      <label>
        <input type="checkbox" checked={simulateFailure} disabled={isPending}
          onChange={event => setSimulateFailure(event.target.checked)} />
        模拟失败
      </label>
      <button type="button" aria-pressed={optimistic} disabled={isPending} onClick={changeFavorite}>
        {isPending ? (optimistic ? '正在收藏' : '正在取消') : (optimistic ? '已收藏' : '收藏')}
      </button>
      <p>已确认状态：{confirmed ? '已收藏' : '未收藏'}</p>
      {error && <p role="alert">{error}</p>}
    </section>
  );
}

初始确认值为 false。点击后，乐观值先变成 true，按钮明确显示“正在收藏”，而确认值仍是 false。成功后更新 confirmed，Action 完成时临时层撤下，真实值已经是 true，所以界面不会跳回未收藏。

失败时没有写入新的确认值，Action 结束后展示回到原确认状态，并显示错误。这里只针对一次正在处理的切换禁用按钮，避免把并发冲突问题混进最小例子。

为什么必须更新真实数据

如果只调用 setOptimistic，却在成功后不更新 confirmed 或其他真实数据来源，那么 Action 完成后 Hook 仍会回到旧确认值。用户会看到“刚变成收藏，马上又恢复”，这不是 Hook 丢失了成功结果，而是应用从未提交那份结果。

确认数据可以来自本地 state，也可以来自框架刷新后的服务端数据或外部缓存。关键是明确谁拥有最终事实，以及结果何时进入那份数据来源。

示例在 await 之后再次使用 startTransition 标记确认状态更新，遵循当前 Transition 对异步边界后更新的要求。它不是再发一次保存请求，而是标记这次 React 状态更新。

reducer 合成临时状态时必须保持纯粹

useOptimistic 可以使用 reducer 根据当前基础状态与本次乐观载荷计算临时状态。本例只切换布尔值，所以直接返回 next；列表增加、删除或编辑则可能需要按 ID 合并。

reducer 不应发送请求、生成随机 ID、修改传入数组或写外部对象。基础值变化时，React 可能需要在新的基础上重新应用相应乐观更新，依赖旧闭包或产生副作用会让重算结果不可靠。

当前 API 也支持省略 reducer 的相应设置形式，但应按项目实际 React 版本使用。两种写法都不改变“临时层最终依赖基础值”的原则。

更新必须属于相应的 Action 生命周期

乐观更新应在 Action 或 Transition 中触发，而不是渲染期间或任意脱离上下文的回调里调用。React 需要知道这份临时更新关联的工作何时结束，才能正确收敛。

useOptimistic 本身不返回一个通用的 pending 状态。示例使用 useTransition 跟踪这次动作，表单场景也可以结合相应的 Action 和提交状态接口。

如果 Action 启动工作后立刻返回，却没有等待真正的异步过程，临时状态也可能过早结束。不要把一个长任务藏到没有返回的 Promise 里，再期待框架自动知道它尚未完成。

失败恢复不只是把一个数字改回去

消息列表中，失败后可能需要保留输入草稿、标明失败消息并提供重试，而不是静默删除一条刚显示的内容。收藏切换可以回到原值，但也应让用户知道没有保存成功。

临时记录通常需要稳定的客户端标识，以便与服务器返回的真实记录关联。否则成功刷新数据后，可能出现临时项与真实项同时存在、顺序错乱或重复追加。

如果允许多个动作同时进行，还需要判断基础值变化时怎样合并、旧响应是否还能覆盖新结果，以及重试是否会重复执行。useOptimistic 不自动提供幂等键、冲突解决或离线同步协议。

乐观界面不等于业务已经完成

适合快速反馈且失败可解释、可恢复的操作，可以考虑乐观更新。对于付款、权限改变或库存确认等场景，更应明确“处理中”与“已确认”，不能把尚未得到保证的结果直接当作最终事实。

即使界面回滚了，已经到达服务器的操作也不一定被撤销。网络超时、客户端取消和服务器成功之间可能存在不确定性，需要查询状态或依靠后端协议解决。

设计时先确定基础数据、临时载荷、成功提交、失败反馈四个环节。它们都清楚后，useOptimistic 才能改善反馈速度，而不会把一个不一致的数据流程藏在更快的动画后面。
