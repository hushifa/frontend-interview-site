iframe sandbox 的权限组合有什么风险？

只写 sandbox 不加值时限制最严，iframe 不能跑脚本、提交表单、弹窗或跳走整个页面，每加一个 allow-* 就放开一项。同源内容同时放开脚本和同源时，脚本能直接拆掉自己的沙箱。

参考答案

简答

sandbox 是 iframe 上的一个属性，用来限制里面的页面能做什么。只写 sandbox 不加值时最严格：里面的内容被当成一个谁都不认识的源，叫不透明源，而且不能运行脚本、提交表单、打开弹窗、跳转顶层页面，插件、自动播放这些也都禁止。

需要放开时，就往里加 allow-*，每加一个撤掉一项限制。常用的有 allow-scripts、allow-forms、allow-popups、allow-same-origin 和 allow-top-navigation-by-user-activation。

allow-same-origin 容易被误解。它只是让文档保留自己原本的源，不会让跨源内容变成和父页面同源。

最危险的组合是：iframe 的内容和父页面同源，又同时开了 allow-scripts 和 allow-same-origin。这时里面的脚本可以访问 parent.document，把 iframe 上的 sandbox 属性删掉再重新加载自己，沙箱就等于没有。所以展示用户提供的 HTML 时，要放在独立的源上，再配合 sandbox。

常见组合

HTML
<!-- 只展示静态内容 -->
<iframe sandbox src="/preview.html"></iframe>

<!-- 第三方小组件：可以运行脚本，但处于不透明源，读不到自己的 Cookie 和存储 -->
<iframe sandbox="allow-scripts" src="https://widget.example/embed"></iframe>

<!-- 第三方登录或支付：需要自己的源和用户点击触发的顶层跳转 -->
<iframe
  sandbox="allow-scripts allow-same-origin allow-forms allow-popups allow-top-navigation-by-user-activation"
  src="https://pay.example/checkout"
></iframe>

第三个例子同时开了脚本和同源，为什么不危险？因为 pay.example 和父页面本来就跨源。allow-same-origin 只是让它拿回自己的源，它照样受同源策略约束，访问不了父页面，也就拆不掉沙箱。危险只发生在内容和父页面同源的时候。

为什么 srcdoc 要特别小心

srcdoc 是直接把 HTML 字符串写在 iframe 属性里，它的内容默认和父页面同源。所以用 srcdoc 展示不可信的 HTML 时，绝对不要同时允许脚本和同源，否则就是上面说的那个最危险的组合。

其他需要注意的点

allow-top-navigation 允许 iframe 随时把整个页面跳走，用户什么都没点，页面就到了别的网站。所以优先用 allow-top-navigation-by-user-activation，只有用户点击后才允许跳转。

allow-popups 打开的新窗口默认继承沙箱限制，要再加 allow-popups-to-escape-sandbox 才会解除。

除了嵌入方写属性，服务端也可以用响应头 Content-Security-Policy: sandbox 给文档本身加沙箱。用户上传文件的下载域很适合这样做，不管文件被谁、用什么方式打开，限制都在。

和其他机制怎么分工

机制控制什么
sandbox嵌入方限制 iframe 内的能力
allow 属性 / Permissions Policyiframe 能否使用摄像头、地理位置等能力，见《Permissions Policy 怎样限制页面和 iframe 的设备能力？》

postMessage 校验父子窗口之间的消息信任

常见追问

沙箱里的脚本能用 localStorage 吗？

没有 allow-same-origin 时不能。这时它处于不透明源，访问存储会抛出异常。

被嵌入的页面怎么知道自己在沙箱里？

没有专门的 API 直接告诉它，只能做能力检测，比如试着访问存储，看会不会抛错。
