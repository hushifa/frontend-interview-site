iframe sandbox 的权限组合有什么风险？

空的 sandbox 属性施加全部限制：内容被当作唯一的不透明源，不能运行脚本、提交表单、打开弹窗或导航顶层页面；每加一个 allow-* 就撤掉一项限制。同源内容同时开 allow-scripts 和 allow-same-origin 时，脚本可以直接移除自己的沙箱。

参考答案

简答

  • sandbox 不写值就是最严格的：不透明源、禁止脚本、表单、弹窗、顶层导航、插件、自动播放等。
  • 常用允许项：allow-scripts、allow-forms、allow-popups、allow-same-origin、allow-top-navigation-by-user-activation。
  • allow-same-origin 只是保留文档原本的源，不会让跨源内容变成同源。
  • 内容与父页面同源时，allow-scripts 加 allow-same-origin 等于没有沙箱：脚本可以访问 parent.document，删掉 iframe 的 sandbox 属性再重新加载自己。
  • 展示用户提供的 HTML 时，放在独立的源（如 usercontent.example）上，再配合 sandbox。

常见组合

HTML
<!-- 只展示静态内容 -->
<iframe sandbox src="/preview.html"></iframe>

<!-- 第三方小组件：可以运行脚本，但处于不透明源，读不到自己的 Cookie 和存储 -->
<iframe sandbox="allow-scripts" src="https://widget.example/embed"></iframe>

<!-- 第三方登录或支付：需要自己的源和用户点击触发的顶层跳转 -->
<iframe
  sandbox="allow-scripts allow-same-origin allow-forms allow-popups allow-top-navigation-by-user-activation"
  src="https://pay.example/checkout"
></iframe>

第三方页面跨源，开 allow-same-origin 后它也只是拿回自己的源，仍然不能访问父页面。

需要注意的点

  • allow-top-navigation 允许 iframe 随时把整个页面跳走，优先用 allow-top-navigation-by-user-activation。
  • allow-popups 打开的新窗口默认继承沙箱；加 allow-popups-to-escape-sandbox 才会解除。
  • srcdoc 内容默认与父页面同源，展示不可信 HTML 时绝对不要同时允许脚本和同源。
  • 服务端也可以用响应头 Content-Security-Policy: sandbox 对文档本身施加沙箱，适合用户上传文件的下载域。

与其他机制的分工

机制控制什么
sandbox嵌入方限制 iframe 内的能力
allow 属性 / Permissions Policyiframe 能否使用摄像头、地理位置等能力，见《Permissions Policy 怎样限制页面和 iframe 的设备能力？》
frame-ancestors被嵌入方限制谁能嵌入自己
postMessage 校验父子窗口之间的消息信任

常见追问

  • 沙箱里的脚本能用 localStorage 吗？没有 allow-same-origin 时处于不透明源，访问存储会抛出异常。
  • 被嵌入方怎么知道自己在沙箱里？可以通过能力检测（如访问存储是否抛错）判断，没有专门的 API 直接告知。
