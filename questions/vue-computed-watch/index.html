computed、watch 和 watchEffect 应该如何选择？

computed 表达派生值，watch 对明确来源的变化执行副作用，watchEffect 自动收集同步读取的来源。它们的返回、缓存、触发与清理规则不同，应围绕数据是否需要单独保存和外部工作怎样结束来选择。

参考答案

总价由单价与数量决定，搜索请求由关键词变化触发，日志记录可能使用多个响应式来源。这些需求不应该都写成一个 watch，再把结果到处复制。

先判断要的是一个可以读取的派生值，还是某种外部副作用。前者通常适合 computed；后者再根据触发条件是否需要显式表达，选择 watch 或 watchEffect。

computed 让派生结果只有一份来源

JavaScript
import { computed, nextTick, reactive, ref, watch } from 'vue';

const price = ref(10);
const quantity = ref(2);
const total = computed(() => price.value * quantity.value);

console.log(total.value); // 20
console.log(total.value); // 20
quantity.value = 3;
console.log(total.value); // 30

computed 返回可读取的计算引用，并根据响应式依赖缓存。依赖没有变时，重复读取可以复用结果；依赖变化后，再按需要获得新的派生结果。

不必再用 watch 把 price、quantity 同步到另一个可随意修改的 total state，那样反而多出一份可能不一致的状态。getter 应只计算结果，不在里面发请求、修改别的响应式值或操作 DOM。

也不要把 async getter 得到的 Promise 当作自动请求管理。computed 不负责等待、loading、错误与取消。Date.now 等非响应式读取也不会自己让 computed 不断失效，必须有实际响应式来源发生变化。

watch 明确说明监听什么

JavaScript
const state = reactive({ count: 0 });
const changes = [];
const stop = watch(
  () => state.count,
  (next, previous) => changes.push(`${previous}->${next}`),
);

state.count = 1;
state.count = 2;
await nextTick();
console.log(changes.join(',')); // 0->2
stop();

watch 默认懒执行，先记录来源，再在相关变化后调用回调。默认调度可以合并同一轮变化，所以本例观察到旧值 0 与最后的新值 2，不是保证每次赋值都单独产生一个回调。

来源可以是 ref、响应式对象、getter 或多个来源组成的数组。watch(state.count, ...) 传进去的是一个当时的数字，不是可继续追踪的属性入口，因此通常应写 getter。

watch 只追踪明确给出的源，回调里额外读取其他响应式值，不会自动把它们全部变成触发条件。需要首次也执行时，可以使用 immediate，并处理首次没有普通旧值的情况。

watchEffect 适合依赖自然来自同步读取的副作用

watchEffect 会立即运行并自动记录同步执行中读取的响应式来源，相关来源变化后重新执行。它不提供与 watch 相同的新旧值参数，优势是不用在读取和依赖列表之间重复维护同一组来源。

async watchEffect 只收集第一次 await 之前的同步读取。等待后才读取的变量，不会因为出现在同一个函数文本中，就自动加入这一轮依赖。

需要精确控制请求由哪个 ID、关键词或配置触发时，watch 的显式源通常更清楚；小范围自动同步或调试观察则可以考虑 watchEffect。不要为了省一行源表达式而让触发关系变得难以预测。

请求副作用必须处理失效清理

以下组件假设项目提供 /api/search?q=...，返回包含字符串 label 的 JSON；接口本身需要由实际项目实现。

vue
<script setup>
import { ref, watch } from 'vue';

const query = ref('');
const result = ref('请输入关键词');
const loading = ref(false);

watch(query, async (value, _previous, onCleanup) => {
  const keyword = value.trim();
  if (!keyword) {
    result.value = '请输入关键词';
    loading.value = false;
    return;
  }

  const controller = new AbortController();
  let active = true;
  onCleanup(() => {
    active = false;
    controller.abort();
  });

  loading.value = true;
  result.value = '';
  try {
    const response = await fetch(`/api/search?q=${encodeURIComponent(keyword)}`, {
      signal: controller.signal,
    });
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    const data = await response.json();
    if (typeof data?.label !== 'string') throw new Error('返回数据不符合约定');
    if (active) result.value = data.label;
  } catch (error) {
    if (active) result.value = error instanceof Error ? error.message : '查询失败';
  } finally {
    if (active) loading.value = false;
  }
});
</script>

<template>
  <label>关键词<input v-model="query" /></label>
  <p role="status">{{ loading ? '查询中' : result }}</p>
</template>

关键词变化时，旧回调先被标记为失效并请求取消。即使某些后续工作不响应取消，active 检查也阻止旧结果和旧 finally 覆盖新查询的状态。

Vue 3.5 及以上还提供 onWatcherCleanup，但必须在相应同步执行阶段登记，不能等 await 之后再调用。示例使用回调参数 onCleanup，并同样选择在等待前登记，避免清理关系建立得太晚。

这里的注册方式不同于 React Effect：不是让 async 回调返回一个清理函数，而是通过 Vue 的清理入口登记。返回的 Promise 也不会自动把网络请求变成可取消资源。

深度监听不等于给你一份历史快照

直接 watch 响应式对象通常具有相应深度监听行为；watch 一个返回对象的 getter，默认更关注这个返回引用是否替换，需要时再开启 deep。

深层属性原地变化时，新值与旧值可能仍是同一个对象引用，不能把它们当成两份独立快照来计算差异。需要历史差异，应明确保存或生成相应数据，而不是期待 deep 自动深拷贝。

深度遍历可能有成本。Vue 3.5 起 deep 也可以指定最大遍历深度，但这只是进一步控制边界，不代表大结构从此可以无成本地随意深度监听。

选择回调时机与停止时机

默认侦听回调与组件更新存在调度顺序，读取所属组件的新 DOM 时，应考虑 flush:'post'、watchPostEffect 或在正确位置等待 nextTick。flush:'sync' 则同步触发、缺少相同的批处理优势，不宜不加分析地用于频繁变动的大数组。

setup 中同步创建的侦听通常会随组件卸载停止。异步创建或脱离组件生命周期的侦听，需要自己持有并调用停止函数，否则可能继续执行无用工作。

最后，computed 负责让派生数据可读，watch/watchEffect 负责在变化后做事。把这两个目的分开，通常比反复添加更多侦听器来同步同一事实更容易保证正确性。
