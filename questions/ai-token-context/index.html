为什么不能用字符串长度准确计算 Token 和费用？

Token 是模型分词器的计量单位，和字符数、字节数都不同，还随模型变化。前端只能估算；上下文限制和费用按目标模型的完整请求计算，以响应里的 usage 为准。

参考答案

简答

  • string.length 是 UTF-16 码元数，UTF-8 字节数是存储大小，Token 是模型分词器切出的单位，三者不一样。同一段文字换个模型，Token 数也会变。
  • 实际请求远比输入框长：系统提示、历史消息、工具定义、检索片段、图片都要计入。
  • 上下文窗口要给输出留出空间。截断历史时按整条消息删除，工具调用和它的结果要一起保留或一起删掉。
  • 准确计数用服务商的计数接口；费用以响应里的 usage 为准，输入、输出、缓存读写的单价各不相同。

一个预算分配示例

JavaScript
// count 应调用与目标模型一致的计数方式；前端只用于提前提示
function buildContext({ system, history, docs, limit, outputBudget, count }) {
  const fixed = count(system) + outputBudget;
  if (fixed >= limit) throw new Error('系统提示和输出预留已经超过上限');

  let remaining = limit - fixed;
  const recent = [];
  // 从最新消息往前取，整条保留
  for (let i = history.length - 1; i >= 0; i--) {
    const size = count(history[i]);
    if (size > remaining * 0.5) break; // 给检索内容留一半
    recent.unshift(history[i]);
    remaining -= size;
  }

  const selected = [];
  for (const doc of docs) {
    const size = count(doc);
    if (size > remaining) break;
    selected.push(doc);
    remaining -= size;
  }
  return { system, history: recent, docs: selected };
}

服务端发送前还要按完整请求重新计数并强制执行上限，不能依赖浏览器的估算。

历史太长时

  • 按消息删除，保留系统约束和最近几轮。
  • 工具调用和结果成对处理，否则模型 API 可能报错。
  • 用摘要压缩更早的历史时，保留用户的约束、关键决定、未完成事项和重要 ID。摘要会丢信息，需要精确数据的场景保留原文。
  • 检索内容过多时先去重、重排、限制单篇长度，塞进更多内容不一定让回答更准。

隐私

权限过滤和敏感字段脱敏要在检索和构造请求之前完成。被截断的内容已经经过处理链路，不能靠截断防止泄露。

常见追问

  • 接近上限时界面怎么提示？ 告诉用户会丢掉哪些历史或资料，而不是静默删除刚输入的内容，或者报一个笼统的网络错误。
  • 缓存命中的 Token 还算钱吗？ 算，只是读取单价更低，见"AI Prompt Caching 对前端请求设计有什么影响？"。
