为什么不能用字符串长度准确计算 Token 和费用？

Token 是模型分词器使用的单位，不等于字符数、字节数或单词数。不同模型及分词器可能对同一文本得到不同计数，不能把“一个中文字符等于一个 Token”写成通用规则。

参考答案

Token 是模型分词器处理输入的单位，不等于 JavaScript 字符串 length、UTF-8 字节数或自然语言单词数。一个常见词可能是一个 Token，也可能被拆开；中文、空格、代码、标点和特殊格式都会影响切分。

同一文本换模型或分词器版本，计数也可能不同。因此字符数适合做粗略 UI 提醒，不适合准确计算上下文容量或最终费用。

实际输入远不止输入框文字

一次请求可能包含系统指令、历史消息、工具定义、检索片段、附件和协议包装。用户只输入一句话，前端却发送几十轮历史与大量工具 schema，实际输入可能很大。

图片、音频等模态还有各自的计量规则，不能把文件字节数直接当 Token。某些服务端工具或模型内部处理也可能影响 usage 的分类，需要按提供方说明理解。

因此计数应针对即将发送给目标模型的完整结构，而不是只计算当前 textarea。

使用目标模型的计数能力

优先采用提供方的计数接口，或与目标模型匹配的 tokenizer。不要拿另一个模型的编码器结果当作权威数量，也不要在模型升级后继续沿用旧版本经验值。

例如 Claude 的 Token 计数接口接受模型与结构化消息等参数，文档也说明结果属于估计，实际请求的输入用量可能略有差异。是否支持工具、图片和其他请求特性，应按当前接口约束核对。

最终统计应结合响应 usage 与当时适用的计费规则。前端显示预估，受控执行端负责真实预算校验与限额，避免用户绕过浏览器限制后提交超大请求。

上下文容量和输出上限不是同一个数字

模型可能有总上下文限制、最大输入或输出限制，以及与特定模式相关的约束。不能把上下文窗口全部塞满输入，再期待仍能生成任意长度答案。

规划时为输出预留预算，并考虑工具结果或后续轮次可能增加的内容。某些模型还有额外用量类别，是否占窗口、如何计费，应按具体文档处理，不能通用地假定都是可见正文长度。

max_tokens 等参数通常约束输出的一部分或相应模型定义的输出预算，它不是“输入加输出的总费用上限”。字段含义和可取范围要与目标 API 对齐。

费用需要分类计算

输入、输出、缓存读取、缓存写入或其他服务能力可能采用不同价格。计费还可能受模型版本、服务层级、批处理或工具调用影响。

概念上可以把每类用量乘以对应单价再汇总，但不能把全部 Token 乘同一个固定价格。预估时也无法知道最终输出会有多长，应给出范围或预算，并在完成后记录实际用量。

不能从首字节延迟或请求次数推断费用，也不能因为缓存命中就认为输入完全免费。

截断上下文要保留任务结构

从字符串开头按字符删除可能切坏消息边界、丢失约束，或者把工具调用与结果拆散。更合适的方式是按消息、任务阶段和重要性筛选，保留必要指令与配对结构。

历史摘要可以减少体积，但也是一种有损转换，可能漏掉细节或改变事实。应保留必要来源与关键决策，并对压缩后能否完成任务进行验证。

如果检索内容占用过多，可以提高召回与重排质量，减少无关片段，而不是直接用更大窗口掩盖问题。上下文更长不保证答案更准确，成本与注意力分配也需要考虑。

前端可以显示剩余额度、附件大小和接近上限的提示，但应注明估算性质。真正发送前再次按完整请求核对，才能减少界面看似允许、服务端却因上下文超限失败的情况。
