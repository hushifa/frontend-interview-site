一个线上页面变慢后应该怎样完成性能诊断闭环？

先用 RUM 按页面、版本、设备拆分，确认哪些用户、哪个指标、从哪个版本开始变慢；再在实验室固定条件复现，用瀑布图分析 LCP、用 Performance 面板分析 INP；修复要对应找到的瓶颈，最后通过对照测试和分批发布验证真实用户数据是否改善。

参考答案

简答

  • 确认范围：看 75 分位而不是平均值，按页面、版本、设备、网络拆分，找出问题从哪次发布开始、影响哪类用户。
  • 复现：在实验室固定设备（或 CPU 降速）、网络、缓存状态和数据量，每次只改变一个因素，多次运行比较。
  • 定位：LCP 看瀑布图中最大内容在哪一段等待；INP 看最慢交互慢在输入延迟、处理还是呈现。
  • 修复：措施要对应瓶颈，图片压缩修不了主线程长任务，代码拆分修不了慢接口。
  • 验证：同场景对比修复前后，再小比例发布观察 RUM，同时看错误率和业务完成率。

案例：题库首页 INP 从 180ms 升到 420ms，LCP 也变差

1. 确认范围

RUM 显示问题集中在中低端 Android、新版本发布之后，INP 的慢交互主要是"输入搜索关键词"，LCP 元素是首屏的题目列表文本。

2. 复现

用 DevTools 开启 4 倍 CPU 降速和慢速 4G，加载与线上相同规模的题目数据，录制"冷启动首页"和"输入关键词"两个流程。

3. 定位 LCP

瀑布图显示列表数据在 JS 包下载、执行后才请求，新版本的 JS 包增大了 40%。列表依赖客户端渲染，形成"HTML → JS → 数据 → 渲染"的串行链路。

4. 定位 INP

Performance 面板里，每次按键触发对全部题目的同步过滤和全量重渲染，单次处理超过 300ms。web-vitals 的 attribution 数据也显示处理时间占大部分，见《INP 很高时，如何定位到底是哪一段交互变慢？》。

5. 修复

瓶颈措施
列表靠客户端渲染首屏列表改为预渲染进 HTML
JS 包变大分析产物，把新引入的大依赖改为按需加载
每次按键全量过滤预先建立搜索索引，输入防抖，结果区域用低优先级更新
全量重渲染虚拟列表，只渲染可见的行

6. 验证

同一实验室场景多次运行，对比中位数和 75 分位。灰度发布 10% 流量，按设备分组对比 RUM 的 INP、LCP，同时确认搜索成功率没有下降，再全量发布。

容易出错的地方

  • 只看平均值：少数严重慢的用户被淹没。
  • 看一次最好成绩：实验室结果有波动，要多次运行。
  • 修复与瓶颈不对应：给组件加 memo 但瓶颈其实是网络。
  • 只看技术指标：把结果推迟到点击后才显示，指标好看了，用户完成任务的时间却变长。
  • 流量结构变化：新增了大量高端设备用户，整体指标变好不代表代码变快。

常见追问

  • 怎样防止再次退化？在 CI 中加入性能预算，见《前端性能预算应该怎样制定和落地？》。
