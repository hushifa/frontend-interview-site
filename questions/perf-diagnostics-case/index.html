一个线上页面变慢后应该怎样完成性能诊断闭环？

先用 RUM 按页面、版本、设备拆分，找出谁变慢、哪个指标、从哪个版本开始；再在实验室固定条件复现，用瀑布图查 LCP、用 Performance 面板查 INP；按瓶颈修复，最后用对照测试和分批发布确认真实用户数据变好。

参考答案

简答

线上变慢了，第一步不是动手改代码，而是先搞清楚谁慢了。我会看真实用户监测，也就是 RUM 的数据，看 75 分位而不是平均值，按页面、版本、设备、网络拆开，找出问题从哪次发布开始、影响的是哪类用户。

然后在实验室里复现。固定设备或者 CPU 降速、网络、缓存状态和数据量，每次只改一个因素，多跑几次比较。复现出来以后再定位：LCP 慢就看瀑布图，最大的那块内容卡在哪一段等待；INP 慢就看最慢的那次交互，是输入延迟、处理时间还是呈现延迟。

修复要对准瓶颈。图片压缩修不了主线程长任务，代码拆分也修不了慢接口。

最后要验证。同一个实验室场景对比修复前后，再小比例发布观察 RUM，同时看错误率和业务完成率有没有变差，确认没问题再全量。

用一个案例走一遍

假设题库首页发版以后，RUM 显示 INP 从 180ms 升到 420ms，LCP 也变差了。下面按顺序走一遍。

先确认范围

RUM 拆开一看，问题集中在中低端 Android，时间点是新版本发布之后。慢的交互主要是“输入搜索关键词”，LCP 元素是首屏的题目列表文字。

这一步拿到的是“谁慢、哪里慢、什么时候开始”，还不知道为什么慢。

在实验室复现

用 DevTools 开 4 倍 CPU 降速和慢速 4G，加载和线上同样规模的题目数据，录两个流程：冷启动打开首页，以及输入关键词。

为什么要降速？因为开发用的电脑通常比用户的手机快得多，不降速可能根本看不到问题。

定位 LCP

瀑布图显示，列表数据要等 JS 包下载、执行完以后才去请求，而新版本的 JS 包大了 40%。列表靠客户端渲染，形成了“HTML → JS → 数据 → 渲染”一环套一环的串行链路，JS 包一变大，整条链都往后推。

定位 INP

Performance 面板里能看到，每按一次键，都会对全部题目做一次同步过滤，再把整个列表重新渲染，单次处理超过 300ms。web-vitals 的 attribution 数据也显示处理时间占了大头。具体怎么拆这三段，见《INP 很高时，如何定位到底是哪一段交互变慢？》。

对着瓶颈修复

每个措施都对应上面找到的一个原因：

瓶颈措施
列表靠客户端渲染首屏列表改为预渲染进 HTML
JS 包变大分析产物，把新引入的大依赖改为按需加载
每次按键全量过滤预先建立搜索索引，输入防抖，结果区域用低优先级更新
全量重渲染虚拟列表，只渲染可见的行

验证

同一个实验室场景多跑几次，对比中位数和 75 分位。然后灰度发布 10% 的流量，按设备分组对比 RUM 里的 INP 和 LCP，同时确认搜索成功率没有下降，再全量发布。

容易在哪里出错

最常见的是只看平均值。少数用户特别慢，平均一下就被淹没了，所以要看分位数。

第二个是只看一次最好成绩。实验室结果本身有波动，跑一次说明不了问题，要多跑几次。

第三个是修复和瓶颈对不上，比如瓶颈其实在网络，却去给组件加 memo，改完自然没效果。

第四个是只盯技术指标。比如把结果推迟到点击后才显示，指标好看了，用户完成任务反而更慢了。

还有一个是流量结构变了。如果新来了大量高端设备用户，整体指标变好也不代表代码变快了，所以要按设备分组对比。

常见追问

RUM 和实验室测试怎么配合？

RUM 回答“谁慢、有多普遍”，实验室回答“为什么慢”。一般是 RUM 发现问题，实验室复现定位，修完再回到 RUM 看是否恢复，详见《真实用户监测与实验室性能测试为什么要结合？》。

怎样防止以后再退化？

在 CI 里加性能预算，构建产物超出体积或者实验室指标超标就提示或拦截合并，详见《前端性能预算应该怎样制定和落地？》。
