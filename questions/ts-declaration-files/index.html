.d.ts 声明文件提供了什么，不能保证什么？

.d.ts 是写给编译器看的“说明书”，告诉它一段 JavaScript 有哪些导出、各是什么类型，本身不产生任何代码。说明书写得对不对由发布者负责，编译器不会去核对真实实现。

参考答案

简答

.d.ts 文件就是一份类型说明书。比如一个 JS 库导出了 formatCount 函数，.d.ts 里写一句 export declare function formatCount(value: number): string，编辑器就知道它要什么参数、返回什么。它只能写 declare、interface、type 这类声明，不能写实现，编译后也不生成代码。

它保证不了声明和真实代码一致。声明写错了，编译器会放过错误的调用，或者拒绝正确的调用，问题要到运行时才暴露。skipLibCheck 只是跳过检查声明文件本身，不会把写错的声明改对。

TypeScript 找声明的顺序是：相对路径导入就找同名 .d.ts；导入包时先看 exports 里的 types 条件，再看 types 字段；都没有就去找 @types/包名。

还要分清全局和模块。没有 import、export 的 .d.ts 是全局声明；有的话就是模块，想扩展全局要写 declare global。另外 declare module '*.svg' 只是告诉编译器导入 SVG 得到什么类型，真正处理文件的是构建工具。

给一个 JS 模块配说明书

下面是一个普通的 JS 函数，旁边配一份 .d.ts，再看 TS 代码怎么用它。

JavaScript
// format-count.js
export function formatCount(value) {
  if (!Number.isSafeInteger(value) || value < 0) {
    throw new RangeError('数量必须是非负安全整数');
  }
  return `${value} 项`;
}
TypeScript
// format-count.d.ts
/** 将非负安全整数格式化为数量文案。 */
export declare function formatCount(value: number): string;
TypeScript
// consumer.ts
import { formatCount } from './format-count.js';

const label = formatCount(3); // string
// @ts-expect-error 声明要求 number
formatCount('3');

consumer.ts 导入的是 JS 文件，可编译器知道 formatCount 只接受 number，因为它读的是旁边那份同名的 .d.ts。传字符串会报错，返回值被当成 string。声明上方的 JSDoc 注释也会显示在编辑器的悬停提示里。

可是 number 这个类型并不排除负数和小数，formatCount(-1) 照样能通过检查。所以真正的业务校验还得留在 JS 实现里，声明只能描述到类型这一层。

声明写了，运行时就一定有吗

不一定。声明只是承诺，编译器信它，但不会去验证。看一个全局变量的例子：

TypeScript
// env.d.ts，没有 import/export，属于全局
declare const APP_VERSION: string;

declare module '*.svg' {
  const url: string;
  export default url;
}

写了 declare const APP_VERSION 以后，代码里直接用 APP_VERSION 不会报错。可如果构建工具（比如 Vite 的 define）并没有把这个值注入进去，运行时就是 ReferenceError。*.svg 那段也一样，它只说明“导入 SVG 会得到一个字符串默认导出”，能不能真的导入，要看构建工具有没有配置处理 SVG。

声明从哪里来

用 TS 写的源码，打开 declaration 就能自动生成声明；只想要声明、不要 JS 输出时再加 emitDeclarationOnly。纯 JS 项目也可以生成，开启 allowJs、checkJs 和 declaration，TypeScript 会根据 JSDoc 推出类型。

TypeScript 5.5 加了 isolatedDeclarations。它要求导出的东西都写明类型，这样别的工具不用做完整的类型检查，也能逐个文件生成声明。

生成以后最好看一遍产物：有没有把内部类型暴露出去，有没有引用只在库自己的源码里才有的 paths 别名。别名在使用者那边是解析不到的。

声明为什么会和实际对不上

最常见的是版本不匹配，比如装了 @types/x@2，运行的却是 x@3，新版改过的 API 在类型里还是老样子。其次是模块格式不一致，比如 CommonJS 包的声明写成了 export default，使用者按默认导入写，运行时拿到的东西和类型说的不同，详见《TypeScript 库发布时怎样组织类型声明和入口？》。还有一种是声明里用了别的包的类型，而使用者没装那个包。

常见追问

第三方库的类型写错了怎么办？

先确认类型包和库的版本是不是对得上。确实是声明写错了，可以先在自己项目里用模块增补临时修正，同时给类型包提一个修复。

/// <reference types="node" /> 是做什么的？

它在声明文件里引入某个类型包的全局声明，比如 Node 的 process、Buffer。应用代码里更推荐在 tsconfig 的 types 里配置，集中管理。
