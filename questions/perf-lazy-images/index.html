懒加载为什么有时反而让首屏和首次交互变慢？

懒加载把非关键资源推迟到需要时，能减少首屏下载与执行成本，但它也把部分等待转移到第一次使用。若首屏关键图片或用户马上要用的组件被延后，体验可能反而变差。

参考答案

懒加载把非关键资源推迟到需要时，能减少首屏下载与执行成本，但它也把部分等待转移到第一次使用。若首屏关键图片或用户马上要用的组件被延后，体验可能反而变差。

应先区分关键资源与低频资源，再决定预加载、预取、立即加载或按需加载。对于静态内容，还可以在构建阶段提前处理，避免浏览器首次操作时再下载大型解析器。

评估时既看页面初次打开，也看首次展开、首次切换和弱网条件。压缩后的实际传输体积、请求瀑布和执行成本都值得测量，不能仅以“拆成了多个文件”证明优化有效。

loading="lazy" 是浏览器提示，不是精确的请求时间控制。可以结合 srcset、sizes、合适的压缩格式和尺寸占位减少传输与 CLS；接近视口的图片应留出足够提前量，避免滚动到空白区域。懒加载还要考虑打印、无 JavaScript 和错误占位。

性能优化先固定场景和指标，再判断瓶颈属于网络、脚本、布局、绘制、内存还是交互延迟。优化前后要使用相同设备、网络和数据量比较，不能只看开发机上的一次耗时。

每个优化都有成本：预加载会增加流量，缓存会增加失效复杂度，虚拟化会改变测量和无障碍行为。上线后还应观察真实用户数据，确认收益没有转移到另一个阶段。

实际优化时先记录基线，再只改一个变量。若首屏变快但首次展开、滚动或弱网体验变差，说明成本只是被推迟；最终要以用户完成任务的时间判断优化是否成立。
