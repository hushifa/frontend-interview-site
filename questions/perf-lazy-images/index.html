懒加载为什么有时反而让首屏和首次交互变慢？

懒加载只是推迟下载或执行，减少了当前关键路径的工作，却可能把等待转移到用户第一次使用时。应按访问概率、首屏重要性和资源成本决定。

参考答案

懒加载把成本推迟到什么时候

打开题库后，用户马上展开第一题。如果题解、Markdown 解析器和代码高亮库都在点击后才下载，首屏确实少了代码，但用户要在第一次展开时支付模块发现、下载、解析和渲染的全部等待。之后展开其他题很快，可能只是依赖已经进入缓存。

因此懒加载不是“越多越好”，而是把低概率、非关键资源从当前路径移开。首屏大图、首个交互需要的内容和用户几乎必然打开的模块，延后反而可能损害体验。

关键图片不要盲目 lazy

首屏主图可能是 LCP 元素，应让浏览器尽早发现并提供尺寸：

HTML
<img
  src="/images/hero.webp"
  width="1200"
  height="600"
  fetchpriority="high"
  alt="产品使用场景"
/>

下方相册、低频弹窗和编辑器更适合延后。fetchpriority 只是相对优先级提示，不会让网络变快；每张图都设为 high 只会让关键资源互相竞争。真正的选择依据是实际访问路径、LCP 和设备网络数据。

图片懒加载仍要稳定布局

HTML
<img
  src="/images/card-640.webp"
  srcset="/images/card-640.webp 640w, /images/card-1280.webp 1280w"
  sizes="(max-width: 700px) 100vw, 640px"
  width="1280"
  height="720"
  loading="lazy"
  alt="组件布局示例"
/>

width 和 height 让浏览器预留比例空间，减少图片到达时的 CLS。srcset 和 sizes 必须反映真实布局，否则可能下载过大的候选图。原生 loading="lazy" 的提前距离由浏览器决定，不是精确的“进入视口才加载”；自定义 IntersectionObserver 也应留提前量。

懒加载不能替代压缩、合适格式和响应式尺寸。推迟一张超大图片，只是把带宽和解码成本移到了后面。

避免把首次交互变成串行瀑布

如果点击后必须先下载组件、组件启动后才请求数据、数据返回后才加载高亮语言，用户会遇到多次串行等待。已知用户意图出现时，可以让模块和数据并行准备，或在聚焦入口、即将进入视口时预取。

预取也有预算。触控设备没有鼠标悬停，预取不能成为功能正常工作的必要前提；首屏一次性预取所有低频模块，又会挤占关键资源。小而高频的组件有时直接随首屏提供，比拆成懒块更快。

静态题解还可以在构建阶段完成 Markdown 解析和代码高亮，浏览器只加载展示结果。是否这样做，要比较构建产物、缓存复用和内容更新方式，而不是只看代码拆得更细。

加载失败和旧版本要有恢复路径

动态 import、图片和数据请求都可能失败。界面需要错误说明、重试和取消/忽略过期结果的策略。旧页面引用已经删除的异步 chunk 时，继续无限重试没有意义，应提示刷新并保护未保存输入。

自定义懒加载不能把真实地址全部藏在 data-* 后再假设脚本永远成功；脚本失败时仍应有合理的图片占位、alt 和错误状态。长页面快速滚动、打印和弱网也是验收场景。

评估时至少比较冷缓存首屏、首次展开、后续展开和弱网：看资源发现、下载、执行、渲染以及用户完成任务的等待。bundle 文件数量变多不是收益本身，只有真实关键路径变快才说明懒加载策略正确。
