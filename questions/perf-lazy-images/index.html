懒加载为什么有时反而让首屏和首次交互变慢？

懒加载只是把下载和执行往后挪，用户马上要用的东西就会在第一次用时多等一轮。首屏 LCP 图片加 loading="lazy" 会推迟请求；点击后才依次下载组件、数据和依赖，会形成串行瀑布。

参考答案

简答

懒加载就是先不加载，等用到的时候再加载。它没有减少总的工作量，只是把工作挪到了后面。挪给用户暂时用不到的东西是赚的，挪给用户马上要用的东西就会变慢。

最典型的是首屏图片。首屏大图如果加了 loading="lazy"，浏览器要等布局算出来、确认它在视口里才开始请求，LCP 就被推迟了。所以首屏图片不要懒加载，所有图片都写上宽高，懒加载的图片到了才不会把布局撑开。

代码懒加载也一样。如果点击以后才开始下载组件，组件跑起来再请求数据，数据回来再加载依赖，这几步是串行的，用户就要等好几轮。可以在用户表现出意图时，比如鼠标悬停、获得焦点，就提前开始下载。

还要注意，动态导入可能失败，特别是发布新版本后旧的分块被删掉了，所以要有错误提示和重试。

首屏图片为什么不能懒加载

浏览器解析 HTML 时，看到普通的 <img> 就会尽早发请求。可是加了 loading="lazy" 的图片，浏览器要先知道它会不会出现在视口里，这得等布局算出来以后才知道。所以首屏主图懒加载，请求反而比不加更晚。

下面是推荐的写法：首屏主图立即加载并提高优先级，首屏以下的图片懒加载，两种都写宽高。

HTML
<!-- 首屏主图：立即加载并提高优先级 -->
<img src="/hero.avif" width="1200" height="600" fetchpriority="high" alt="产品主图" />

<!-- 首屏以下：懒加载，预留尺寸 -->
<img
  src="/card-640.avif"
  srcset="/card-640.avif 640w, /card-1280.avif 1280w"
  sizes="(max-width: 700px) 100vw, 640px"
  width="1280"
  height="720"
  loading="lazy"
  alt="组件布局示例"
/>

为什么懒加载的图片也要写 width 和 height？因为图片还没下载时，浏览器不知道它多大，没法提前留出位置。等图片到了再撑开，下面的内容就会被推下去，这就是布局偏移，会计入 CLS。写了宽高或者 aspect-ratio，位置就提前留好了。

原生懒加载不会等图片真的进入视口才加载，而是接近视口时就提前开始，具体提前多少由浏览器决定。iframe 也支持 loading="lazy"，适合页面下方的视频和地图嵌入。

代码懒加载怎么避免多等一轮

下面这个编辑器按钮，等用户点击才下载编辑器代码。为了不让用户干等，在鼠标移上去或者按钮获得焦点时就开始下载：

JavaScript
const button = document.querySelector('#open-editor');
let editorModule;

// 用户表现出意图时开始下载，不必等到点击
const preload = () => (editorModule ??= import('./editor.js'));
button.addEventListener('pointerenter', preload, { once: true });
button.addEventListener('focus', preload, { once: true });

button.addEventListener('click', async () => {
  try {
    const { openEditor } = await preload();
    openEditor();
  } catch {
    editorModule = undefined;
    showError('加载失败，请刷新页面后重试');
  }
});

??= 保证 import() 只发起一次，悬停时开始的下载，点击时直接复用同一个 Promise。从悬停到点击通常有几百毫秒，这段时间正好用来下载。

失败时为什么要把 editorModule 设回 undefined？因为失败的 Promise 会被一直缓存，不清掉的话下次点击还是拿到同一个失败结果，永远没法重试。

还有一点，触屏设备没有悬停，所以预取只能是加速手段，不能当成功能能用的前提。点击时没有提前下载好，也必须能正常加载。

什么该懒加载，什么不该

判断标准是：这个东西是不是大多数用户一进来就要用。

适合不适合
首屏以下的图片、视频、地图首屏主图、Logo
低频的弹窗、编辑器、图表库几乎每个用户都会打开的模块
只在特定路由使用的代码很小的高频组件，拆分后请求开销大于收益

常见追问

怎么判断懒加载到底有没有收益？

对比两件事：冷缓存下首屏的 LCP，以及第一次使用这个功能时要等多久。只看拆出来的分块变多了，没有意义。

发布新版本后旧分块 404 了怎么办？

用户手里的旧页面还在引用旧的分块文件名，新版本部署后这些文件被删了，动态导入就会失败。可以把旧版本的静态资源保留一段时间，加载失败时提示用户刷新页面。
