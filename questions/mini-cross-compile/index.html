Taro 和 uni-app 如何把代码转换成小程序？编译时和运行时有什么区别？

编译时方案是构建阶段把代码翻译成小程序代码，运行时方案是在小程序里模拟一个浏览器环境。对比编译型转换与 Taro 3 的运行时架构（模拟 DOM、自定义渲染器、模板递归），以及 uni-app 的条件编译和逻辑层/视图层拆分。

简答

用 React 或 Vue 写代码，最后跑在小程序里，大体有两条路。一条是编译时方案：构建时把 JSX 这类源码直接翻译成小程序的 WXML、JS 和 WXSS。生成的代码接近手写，运行开销小，可是只能支持编译器看得懂的写法。

另一条是运行时方案，Taro 3 就是这样。它用 @tarojs/runtime 在逻辑层模拟一套精简的 DOM 和 BOM，让 React、Vue 直接跑起来。React 用基于 react-reconciler 的自定义渲染器去改这棵模拟 DOM 树，Taro 再把树序列化后 setData 出去，由预先生成、能互相引用的 <template> 把界面渲染出来。

uni-app 是在编译时把 Vue 单文件组件拆成逻辑层和视图层，再用 #ifdef 这类条件编译给不同平台保留不同代码。

运行时方案换来了更完整的框架能力，代价是多了运行时体积和数据传输。长列表这类场景，还是要注意 setData 的开销。

编译时方案是怎么做的

Taro 文档把这类框架叫做“编译型的小程序框架”，早期 Taro 通常也被归为这一类。它用 Babel 解析 JSX，把模板部分转成 WXML，把组件逻辑转成小程序的 Page、Component 调用。

这样生成的代码很接近手写的小程序。可是 JSX 里能写任意 JavaScript 表达式，编译器只能识别其中有限的写法。所以动态渲染、高阶组件这类用法会受限制，开发体验和完整的 React 有差距。

Taro 3 的运行时方案分几步

Taro 换了个思路：既然没法把所有写法都翻译过去，那就在小程序里造一个浏览器环境，让框架原样跑。按 Taro 文档的说明，可以概括成四步。

第一步，模拟浏览器环境。@tarojs/runtime 在逻辑层实现了精简的 DOM、BOM API、事件系统，以及 Web 框架和小程序框架之间的桥接层。

第二步，自定义渲染器。ReactDOM 体积大，又带着大量浏览器兼容代码。所以 Taro 借助 react-reconciler 写了自己的渲染器 @tarojs/react，把 React 的更新落到 Taro 的 DOM 树上。

第三步，模板递归。小程序的模板必须在构建时就定下来，不能运行时生成。可是 <template> 能引用别的 <template>，Taro 就利用这一点，让 DOM 树里每个节点对应渲染成一个 template。构建产物里的 base.xml，就是这些模板的集合。

第四步，setData 驱动。把 Taro DOM 树的序列化数据 setData 给视图层，模板一层层互相引用，最后渲染出界面。

因为 React、Vue 都只跟模拟 DOM 打交道，Taro 3 可以同时支持多个框架。代价是每次界面更新都要经过模拟 DOM 和 setData 两层，节点越多，序列化和渲染的成本越高。

uni-app 是怎么做的

uni-app 文档说明，除了 H5，uni-app 在各个平台都分成逻辑层和视图层。开发者虽然把 JS 和 CSS 写在同一个 .vue 文件里，编译时其实已经拆开了。逻辑层跑在独立的 JS 引擎里，所以不能用 window、document 这些浏览器 API。

平台之间的差异主要靠条件编译。意思是在代码里用特殊注释标明“这段只给某个平台”，打包时不相关的代码会被去掉：

vue
<template>
  <!-- #ifdef MP-WEIXIN -->
  <button open-type="share">分享</button>
  <!-- #endif -->
</template>

<script>
// #ifdef H5
console.log('只在 Web 端打包');
// #endif
</script>

#ifdef 表示只在指定平台保留，#ifndef 表示在指定平台以外保留，都以 #endif 结束。

这里有个坑：平台名写错了，#ifdef 里的代码不会生效，可是 #ifndef 里的代码反而会生效。所以反向条件更容易出问题。

除了代码块，static 目录下按平台命名的子目录，还能做到文件级的条件编译。

uni-app 的性能文档也提醒：数据变化会同步到视图层，如果页面不拆组件，一个小字段变了也可能导致整页数据同步。所以 data 里不要放视图用不到的变量。

常见追问

跨端框架里能用 document.querySelector 吗？

Taro 运行时提供的是逻辑层里的精简 DOM，拿不到渲染层真实的布局信息。要测量尺寸，得用小程序的 createSelectorQuery，或者框架封装好的 API。

运行时方案会让小程序变慢吗？

会增加运行时体积和初始化开销，一般业务影响有限。节点很多的长列表要用虚拟列表等手段。setData 的通用优化见《setData 为什么会慢？如何优化小程序的数据更新？》。
