多租户前端怎样设计，才能避免配置和数据串租户？

从租户上下文、权限、缓存、主题和路由出发，设计多租户前端的状态边界，说明哪些判断必须由服务端完成以及如何测试隔离。

参考答案

简答

  • 租户身份由服务端根据登录会话确定，前端传来的租户 ID 只能用于选择，不能作为授权依据。
  • 所有缓存（请求缓存、本地存储、Service Worker 缓存、CDN）的键都要包含租户，切换租户时清空上一个租户的数据。
  • 租户上下文放在 URL（子域名或路径前缀）中最清晰，刷新、分享链接和多标签页都能保持一致。
  • 主题、功能开关等租户配置在应用启动时加载，加载完成前不要渲染业务内容。
  • 用两个租户的测试账号做自动化测试，验证互相看不到对方的数据。

租户从哪里来

方式示例特点
子域名acme.app.com隔离 Cookie 和存储最彻底，需要通配证书
路径前缀app.com/t/acme/部署简单，同源共享存储，需要在键中区分
登录后选择同一 URL，账号属于多个租户URL 中看不出租户，分享链接容易出错

无论哪种方式，服务端每次请求都要校验"当前用户是否属于这个租户、是否有权访问这条记录"。前端隐藏菜单只影响展示。

缓存键包含租户

JavaScript
// TanStack Query 示例
useQuery({
  queryKey: ['tenant', tenantId, 'orders', filters],
  queryFn: () => api.getOrders(tenantId, filters),
});
JavaScript
function switchTenant(nextId) {
  queryClient.clear();
  sessionStorage.clear();
  location.assign(`/t/${nextId}/`); // 整页切换，丢弃内存中的旧状态
}
  • 本地存储的键加租户前缀：acme:draft:123。
  • Service Worker 缓存 API 响应时，缓存键或缓存名包含租户。
  • CDN 缓存接口响应时，响应要按租户或会话区分（如 Vary 或 Cache-Control: private），最安全的做法是租户数据不进共享缓存。

切换租户时的竞态

用户从 A 切到 B 时，A 的请求可能还在进行，返回后写入状态就会出现 A 的数据显示在 B 的页面里。整页跳转最简单可靠；在单页内切换时，要取消所有进行中的请求并让旧请求的结果失效。

租户配置

JavaScript
async function bootstrap() {
  const config = await fetch(`/api/tenants/${tenantId}/config`).then((r) => r.json());
  applyTheme(config.theme);   // 设置 CSS 自定义属性
  setFeatureFlags(config.features);
  renderApp();
}
  • 主题用 CSS 自定义属性实现，不为每个租户单独打包。
  • 租户自定义的文案、Logo 链接也是外部输入，要做转义和 URL 校验，不能直接插入 HTML。

测试隔离

  1. 准备两个租户、各自的测试账号和测试数据。
  2. 用 A 的账号访问 B 的资源 ID，期望服务端返回 403 或 404。
  3. 在同一浏览器中先后登录两个租户，检查页面、本地存储和缓存中没有残留。
  4. 对日志和错误上报也检查租户字段，确保排查时能区分。

常见追问

  • 不同租户需要不同功能版本怎么办？用租户级功能开关控制，同一份代码部署，避免为每个租户维护分支。
  • 白标域名怎么处理？服务端根据请求的 Host 映射到租户，前端从配置接口拿到结果，不要信任前端自己解析的域名。
