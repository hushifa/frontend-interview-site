AI 对话前端为什么不能直接内置服务商 API 密钥？

写进前端的东西用户都能看到，密钥被拿走就能拿你的账户随便调模型。长期密钥要放在自己的服务端；纯静态站点可以调用另外部署的接口，或者用服务端签发的短期受限令牌。

参考答案

简答

因为写进前端的东西，最后都会下载到用户的浏览器里。不管是放在 VITE_* 环境变量里，还是做了代码混淆、关掉了 Source Map，打开开发者工具都能找到。

别人拿到密钥，可以在自己的服务器上直接调模型 API，CORS 拦不住，费用全算在你的账户上。

正确做法是浏览器调用自己的服务端接口，服务端先认证用户、检查额度，再拿密钥去请求模型服务。纯静态站点也可以这样做，调用另外部署的云函数或后端就行。实时语音这类场景，可以由服务端给浏览器签发一个短期、限定用途的令牌。

要注意，服务端只做转发也不够。别人照样可以通过你的接口刷额度，所以服务端还要做登录校验、限流、限制输入大小，并且由服务端自己决定用哪个模型、开放哪些工具。

为什么藏不住

前端构建时，VITE_* 这类变量会被直接替换成字符串，打进 JavaScript 文件里。混淆只是让代码难读，字符串还在；关掉 Source Map 只是看不到源码，打包后的文件照样能看。就算代码里找不到，浏览器发请求时密钥也得带在请求头里，在网络面板里一眼就能看到。

那 CORS 能不能挡住？不能。CORS 是浏览器自己的限制，用来管“这个网页能不能读别的网站的响应”。别人拿着密钥用 curl 或者自己的服务器去调 API，根本不经过浏览器，CORS 不起作用。

各方分别负责什么

text
浏览器：收集输入、展示流式输出、停止和重试、展示工具确认
自己的服务端：认证用户、检查租户和额度、保存密钥、选择模型、执行工具
模型服务：处理请求、返回输出

模型名、系统提示、能用哪些工具、请求发到哪个地址，都由服务端决定，不接受客户端随便指定。不然用户改一下请求参数，就能换成最贵的模型，或者调用本不该开放的工具。

一条规则该放在前端还是服务端

可以问自己一句：如果用户改了前端代码，或者直接用 curl 发请求，这条规则还成立吗？如果不成立，它就必须放在服务端。费用、权限、长期密钥、不可逆操作的限制，都属于这一类。

前端也不是什么都不做。它可以提前提示“输入太长了”“额度快用完了”，让用户少走冤枉路。出错时展示用户能看懂的信息，比如“额度不足”“请求被拒绝”，附上一个内部错误 ID 方便排查，但不要把服务端堆栈或请求头展示出来。

用户自己填密钥怎么办

有的产品允许用户填写自己的服务商密钥。这时密钥是用户自己的，风险也要跟用户讲清楚：页面有 XSS、装了恶意浏览器扩展、用的是公共电脑，密钥都可能泄露。所以尽量只把它放在内存里，不写进 localStorage。

常见追问

服务端拿着密钥，提示词注入的问题就解决了吗？

没有。把密钥放在服务端，解决的是“谁在调用、谁来付钱”的问题。模型输出可能被注入的内容带偏，工具调用照样要单独校验，见《提示词注入与普通 XSS 有什么区别？》。

短期令牌和长期密钥有什么不同？

短期令牌是服务端按这个用户的权限临时签发的，有效期短、用途也受限，就算泄露了，影响也有限。长期密钥能调用账户下的全部能力，一旦泄露，要等你发现并作废它才会停止。
