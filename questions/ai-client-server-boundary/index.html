AI 对话前端为什么不能直接内置服务商 API 密钥？

浏览器收到的 JavaScript、请求参数和构建时注入的变量，都可以被用户检查。把服务商长期密钥写进 VITE 环境变量、打包文件或混淆字符串，不能让它保密；私有源码仓库也不改变已发布网页的可读取性。

参考答案

浏览器必须拿到页面代码才能运行它，用户也可以检查脚本、网络请求和运行时值。因此，长期服务商 API 密钥一旦发到浏览器，就不能再把它当作只有项目拥有者知道的秘密。

把密钥放进 VITE_ 环境变量、混淆字符串或私有源码仓库，只改变开发和展示方式，不改变已发布代码可被读取的事实。

构建时环境变量不等于服务端秘密

前端构建工具可能把指定环境变量替换进 JavaScript，最终所有访问者都能下载。源码仓库私有，只限制源码访问者，不限制公开网页的执行者。

浏览器向服务商发送 Authorization 头时，密钥也会出现在用户可检查的请求中。关闭 Source Map 或把代码压缩成一行，都无法建立保密边界。

CORS 也不能保护已经泄露的密钥。它约束浏览器跨源读取，不阻止攻击者在自己的脚本、服务器或命令行中使用拿到的凭证。

常见分工是浏览器负责交互，受控端负责权限

text
浏览器：收集输入、显示流、停止与重试、展示工具拟执行内容
受控服务：认证用户、检查额度、选择模型、保存长期凭据、授权工具
模型服务：处理请求并返回输出

浏览器调用项目自己的 API，受控服务使用长期凭据访问模型。这个受控端可以是独立服务、函数或现有平台，不要求一定采用某个全栈框架。

但仅仅加一层代理不够。没有认证、速率限制、输入与输出预算的代理，仍可能被别人滥用成免费模型接口。模型、工具和目标 URL 等参数也不能全部任由客户端决定。

服务端应独立校验租户、资源权限、附件访问和工具参数。隐藏按钮只能改善界面，不是防止直接调用接口的授权机制。

纯静态网站仍有可选方案

静态前端可以访问另行部署的受控 API；也可以采用适合设备的本地模型。纯静态部署限制的是站点自身不能执行任意服务端代码，不等于完全不能有 AI 功能。

如果产品允许用户自行提供其凭据，需要明确说明风险和存储方式，不能把项目长期密钥偷偷嵌进去。用户凭据也可能被 XSS、浏览器扩展或错误日志暴露，应尽量减少持久化与传播。

更适合浏览器直连的服务可能提供短期、受限的客户端凭据。它应由受控端按用户权限签发，限制有效期、用途或资源，并遵循提供方协议。短期凭据不是把普通长期密钥改个变量名。

输出与工具调用仍跨越信任边界

模型返回的工具名称与参数只是拟议操作，不能直接转换成拥有全部权限的数据库或系统调用。受控端应再次检查当前用户是否有权执行，以及参数是否与用户确认内容一致。

即使前端显示了确认弹窗，攻击者仍可绕过 UI 调用接口；授权记录应与具体任务、参数和有效期绑定。高风险副作用还要考虑幂等、审计与取消后的真实状态。

检索文本和模型输出也不能直接成为 HTML、SQL、脚本或路径。把秘密留在服务端，只解决凭据存放的一部分问题，不自动消除提示词注入和输出注入。

日志与缓存也是泄露路径

不要在前端报错信息中返回服务商密钥、完整内部提示词或敏感附件内容。服务端日志也应按必要范围记录，避免调试打印把用户输入和认证头全部复制到第三方平台。

流式响应错误应对用户可理解，同时保留内部可关联的错误 ID，而不是原样暴露堆栈与配置。缓存和持久化还要按租户及权限边界组织。

判断边界可以用一个简单问题：如果用户修改浏览器代码或直接构造请求，这条规则还会成立吗？凡是涉及费用、权限、长期秘密与不可逆执行的限制，都不能只依赖前端自觉遵守。
