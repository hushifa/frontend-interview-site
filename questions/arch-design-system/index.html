设计系统为什么不能只有一套视觉样式？

从按钮和表单的实际使用说明设计系统还需要交互、语义和组件契约，并解释 token、业务组件、文档测试及版本迁移各自的职责。

参考答案

两处按钮用了同样的颜色和圆角，却可能一个能用键盘操作，另一个只能点击；一个加载中会阻止重复提交，另一个会连续发出请求。它们看起来一致，行为却不一致，业务开发仍要反复解决同一类问题。

设计系统因此不仅管理视觉，还应让团队共享可预期的组件、交互和使用规则。它可以包含设计原则、token、组件、文档与治理，但范围应根据产品需要确定，不是文件越多越完整。

组件首先是一份行为契约

以按钮为例，除了大小和颜色，还要明确它是执行动作还是导航，如何提供名称，能否获得焦点，禁用与加载中有什么区别，以及是否默认提交表单。

原生 button 已经提供许多基础行为。给 div 添加 role=button 只是承诺它应该表现为按钮，并不会自动得到 Enter、空格、焦点和表单语义。组件外观统一，却丢掉原生能力，通常会把维护成本转移给每个使用者。

一个表单字段也不只是“输入框加红边”。它需要可见标签、帮助信息、错误关联、必填状态，以及明确的值更新方式。验证失败后用户能否找到原因并继续修改，是组件质量的一部分。

输入、状态和事件需要稳定定义

设计组件 API 时，可以围绕实际使用问题约定：

契约部分需要说清的问题
值的所有权受控还是内部维护？两种方式能否混用？
默认行为按钮 type、关闭方式、初始焦点是什么？
事件通知的是用户意图，还是状态已经改变？携带什么数据？
状态禁用、只读、加载、错误分别允许哪些操作？
组合标签、图标、错误信息和子组件怎样关联？
可扩展性哪些样式或行为可以覆盖，哪些约束必须保持？

例如 loading 不一定等于 disabled。某些流程需要阻止重复操作但保留焦点和状态说明；若组件只是把所有情况都映射成 disabled，可能无法满足任务需求。

参数也不能无限增加。出现多个互相矛盾的布尔值时，应考虑明确的变体或不同组件，而不是让调用者猜哪些组合才合法。

Token、基础组件和业务组合各管一层

设计 token 表达颜色、间距、字体等可复用决策。基础组件把这些决策落实为按钮、输入框、对话框等可操作的界面单元。业务组合再使用它们完成订单取消、账户设置或搜索筛选。

这几层可以协作，但不应互相吞并。主题变化不应该要求改写订单逻辑；基础 Button 也不应该知道某个订单状态是否允许退款。

业务中确实反复出现的组合，可以成为领域组件，但应明确它属于哪个业务能力。不是每一个可复用组件都必须进入全公司公共包。

文档要解释选择，而不只是展示漂亮截图

一个按钮展示页至少应该让使用者理解何时用它、有哪些状态、怎样提供名称，以及错误用法会带来什么问题。对话框还应说明关闭与焦点恢复，选择组件应说明键盘模式与值的含义。

例子需要覆盖长文本、国际化、空数据、失败、密集布局和窄屏等真实条件。默认状态很好看，不能证明加载状态、输入法和错误提示也正确。

文档与实际组件最好共享可运行示例，减少“文档说支持，代码已改变”的漂移。参考 ARIA 模式也要结合目标浏览器与辅助技术验证，不能把规范示例直接当成经过产品验证的完整组件库。

测试不应只剩截图比较

视觉回归适合发现间距、颜色和布局变化，但看不出键盘是否能进入、名称是否正确、禁用状态是否真的阻止行为。

应根据组件风险检查值与事件契约、焦点和键盘、可访问性信息，以及必要的浏览器集成。基础组件改动影响广，更需要知道升级是否改变了使用者依赖的行为。

自动化通过也不代表所有读屏组合都可用。关键交互仍要有对应环境的人工验证，尤其是复杂弹层、组合框与动态通知。

系统需要有人负责演进

如果组件可以随时改默认行为，却没有版本说明和迁移方式，业务团队会复制旧代码或增加覆盖样式来保护自己，最终又出现多套实现。

可以约定维护者、变更评审、弃用周期和迁移示例；影响广的变更先在真实业务验证，再逐步推广。对于样式覆盖和扩展点，也要提供稳定途径，避免业务长期依赖内部 DOM 结构。

衡量设计系统的价值，应看重复问题是否减少、关键行为是否一致、升级是否可控，以及团队能否更容易做出正确选择。组件数量或 token 数量本身不是完成度证明。
