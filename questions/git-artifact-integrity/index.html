前端发布怎样校验构建产物？文件哈希能证明发布安全吗？

发布时 HTML 和资源可能混版。构建成功、文件完整、来源可信、发布一致是四件不同的事；文件哈希和清单校验只管文件完整，原子切换和回滚解决发布一致。

参考答案

简答

构建命令没报错，只说明构建成功了。发布前还要检查产物完不完整，HTML 里引用的每个资源是不是都在。

文件哈希能证明“这个文件和清单上记的一样”，所以能发现上传漏了或被篡改。可是它证明不了代码本身是安全的，也证明不了产物来自可信的构建。要证明来源，得在受控的 CI 里构建，并生成签名或构建证明，比如 GitHub 的 artifact attestation。

发布过程还要做到原子切换：先把所有带哈希的资源传上去，最后一步才替换 HTML 入口，避免用户拿到新 HTML 却加载不到新资源。

上一版的完整产物要保留下来。出问题时整体切回旧版，而不是一个文件一个文件地恢复。

什么是混版

静态站点由一个入口 HTML 和一批带哈希的 JS、CSS 组成，HTML 写着要加载哪些资源。所谓混版，就是用户拿到的 HTML 和服务器上的资源不是同一个版本。

它有两种出现方式。一种是上传顺序不对：先覆盖了 index.html，资源还没传完，这段时间访问的用户会去请求还不存在的文件。另一种是部署时把旧资源删了：停留在旧页面的用户点开一个懒加载功能，请求的是旧文件名，结果 404。

怎样生成和校验清单

清单就是一份“文件路径 → 哈希”的记录。下面的脚本遍历 dist 目录，给每个文件算 SHA-256：

JavaScript
// scripts/manifest.mjs
import { createHash } from 'node:crypto';
import { readFile, readdir, writeFile } from 'node:fs/promises';
import { join, relative } from 'node:path';

async function* walk(dir) {
  for (const entry of await readdir(dir, { withFileTypes: true })) {
    const full = join(dir, entry.name);
    if (entry.isDirectory()) yield* walk(full);
    else yield full;
  }
}

const root = 'dist';
const files = {};
for await (const file of walk(root)) {
  const hash = createHash('sha256').update(await readFile(file)).digest('hex');
  files[relative(root, file).replaceAll('\\', '/')] = hash;
}
await writeFile('manifest.json', JSON.stringify(files, null, 2));

最后一行的 replaceAll('\\', '/') 是为了让 Windows 上生成的路径也用斜杠，和服务器上的路径对得上。

哈希为什么能发现文件问题？因为内容哪怕只差一个字符，算出来的哈希就完全不同：

JavaScript
import { createHash } from 'node:crypto';

const sha = (text) => createHash('sha256').update(text).digest('hex').slice(0, 12);
console.log(sha('console.log(1)') === sha('console.log(1)')); // true
console.log(sha('console.log(1)') === sha('console.log(2)')); // false

部署脚本上传完以后，按清单逐个下载远端文件或者查询它的哈希，和清单比对。然后再解析 HTML，确认每个 <script src>、<link href> 指向的文件都在清单里。任何一项不对，就停下来，不去切换入口。

哈希证明不了什么

哈希只能说明文件没变样，下面三件事它都管不了。

第一是代码安全。如果某个依赖被投了毒，构建产物会原样带上恶意代码，哈希和清单完全一致。

第二是来源可信。攻击者在自己的机器上也能构建出一份产物，再生成一份匹配的清单。

第三是运行正确。文件都在，不代表功能正常，还需要冒烟测试。

需要证明来源时，要在 CI 里构建，用 actions/attest-build-provenance 这类工具给产物生成签名证明，部署前验证签名和构建它的流水线。

怎样做到原子发布和快速回滚

  1. 资源上传到以版本号命名的目录，或者靠内容哈希文件名，和旧资源共存。
  2. 校验通过后，最后一步才更新 HTML 入口，或者切换 CDN 指向的版本目录。
  3. HTML 设置 Cache-Control: no-cache，带哈希的资源设置长期缓存。
  4. 至少保留上一版的完整产物，回滚时把入口切回旧版本就行。

这几步的关键是：资源先到位，入口最后换。入口一换，用户就整体拿到新版本；回滚时入口一换回，又整体回到旧版本，中间不会出现半新半旧。

常见追问

为什么不用 SRI？

SRI 是给 <script>、<link> 加 integrity 属性，让浏览器加载时校验第三方或 CDN 上的资源没被篡改。它管的是浏览器加载那一刻，部署前校验管的是发布之前，两个阶段的保护可以同时用。

部署到 GitHub Pages 这类平台，怎么保证原子性？

平台会在一次部署完成后整体切换，可以依赖它。如果是自己搭的对象存储，上传顺序就要自己控制。
