前端发布怎样校验构建产物？文件哈希能证明发布安全吗？

从 HTML 与资源混版出发，区分构建成功、文件完整性、来源证明和发布一致性，解释清单校验、原子切换与回滚的边界。

参考答案

简答

  • 构建成功只说明命令没报错；发布前还要检查产物是否完整、HTML 引用的资源是否都存在。
  • 文件哈希证明"文件和清单记录的一致"，能发现上传缺失或被篡改，但不能证明代码本身安全，也不能证明它来自可信的构建。
  • 证明来源需要在受控 CI 中构建并生成签名或构建证明（如 GitHub 的 artifact attestation）。
  • 发布要原子切换：先上传所有带哈希的资源，最后再替换 HTML 入口，避免用户拿到新 HTML 却加载不到新资源。
  • 保留上一版完整产物，回滚时整体切回，而不是逐个文件恢复。

混版问题

静态站点由一个入口 HTML 和一批带哈希的 JS、CSS 组成。如果上传顺序是先覆盖 index.html，资源还没传完，这段时间访问的用户会请求不存在的文件；如果部署时删除了旧资源，停留在旧页面的用户点击懒加载功能也会 404。

生成和校验清单

JavaScript
// scripts/manifest.mjs
import { createHash } from 'node:crypto';
import { readFile, readdir, writeFile } from 'node:fs/promises';
import { join, relative } from 'node:path';

async function* walk(dir) {
  for (const entry of await readdir(dir, { withFileTypes: true })) {
    const full = join(dir, entry.name);
    if (entry.isDirectory()) yield* walk(full);
    else yield full;
  }
}

const root = 'dist';
const files = {};
for await (const file of walk(root)) {
  const hash = createHash('sha256').update(await readFile(file)).digest('hex');
  files[relative(root, file).replaceAll('\\', '/')] = hash;
}
await writeFile('manifest.json', JSON.stringify(files, null, 2));

部署脚本上传完成后，按清单逐个下载或查询远端文件哈希并比对。再解析 HTML，确认每个 <script src>、<link href> 指向的文件都在清单里。任何一项失败就停止切换入口。

哈希不能证明什么

  • 代码安全：如果依赖被投毒，构建产物会忠实包含恶意代码，哈希完全一致。
  • 来源可信：攻击者可以在自己的机器上构建出产物并生成匹配的清单。
  • 运行正确：文件都在不代表功能正常，仍需冒烟测试。

需要证明来源时，在 CI 中构建并用 actions/attest-build-provenance 等工具为产物生成签名证明，部署前验证签名和构建流水线。

原子发布和回滚

  1. 资源上传到以版本号命名的目录，或依靠内容哈希文件名，与旧资源共存。
  2. 校验通过后，最后一步更新 HTML 入口（或切换 CDN 指向的版本目录）。
  3. HTML 设置 Cache-Control: no-cache，带哈希的资源设置长期缓存。
  4. 保留至少上一版完整产物，回滚时把入口切回旧版本即可。

常见追问

  • 为什么不用 SRI？SRI（integrity 属性）在浏览器端校验第三方或 CDN 资源未被篡改，和部署前校验是两个阶段的保护，可以同时使用。
  • 部署到 GitHub Pages 这类平台怎么保证原子性？平台在一次部署完成后整体切换，可以依赖它；自建对象存储时要自己控制顺序。
