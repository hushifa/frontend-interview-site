Web、微信小程序和跨端框架的运行边界有什么不同？

网页跑在浏览器里，小程序跑在平台给的环境里，跨端框架要同时照顾多个平台。从运行环境、组件模型、网络权限、生命周期和发布约束比较 Web、小程序与跨端框架，说明选型依据和迁移成本。

参考答案

简答

最大的区别在运行环境。网页跑在浏览器里，JS 能直接操作 DOM。小程序分成逻辑层和视图层，业务 JS 不在浏览器文档里，没有 document、window，所以依赖 DOM 的库都用不了。组件、样式、网络请求也都要用平台规定的语法和 API，请求的域名还得先在后台配白名单。

跨端框架，比如 Taro、uni-app，是把一套代码编译到多个平台。业务逻辑和大部分组件能复用，可是各平台的能力、审核和性能差异还是在。

生命周期也不同。小程序有应用、页面、组件三层生命周期，页面隐藏了可能还留在页面栈里，所以资源要跟着显示和隐藏去暂停、恢复。

还有发布。小程序和 App 都要过平台审核，回滚也比 Web 慢，所以核心规则必须放在服务端。

三者的运行环境对比

为什么 Web 组件库不能直接搬过去

小程序用 WXML 写模板、WXSS 写样式，支持的选择器和 CSS 能力只是浏览器的一部分。而 Web 组件库通常依赖 DOM 查询、Portal、全局事件和浏览器的焦点模型，这些在小程序里都没有，所以没法直接搬。

跨端框架能把组件名统一起来，可是属性默认值、事件冒泡、尺寸测量的时机，各平台仍可能不一样。实际做法是统一设计 token 和交互规范，再给每个平台写自己的组件适配层。

网络请求和登录有什么不同

小程序用 wx.request 发请求，域名必须是后台配置过的 HTTPS 域名。它没有 CORS 的限制，可是也没有浏览器那样的 Cookie 自动管理，会话要自己维护。

登录时，先用 wx.login 拿到一个临时 code，发给服务端，由服务端去换用户标识和会话。服务端不能相信前端传来的用户 ID 或平台标识。

流式响应、文件上传、WebSocket 在不同平台上的支持和限制都不同。所以请求封装要统一超时、取消和错误格式，不支持的能力要有降级。

页面隐藏以后会发生什么

小程序跳到下一页时，上一页通常还留在页面栈里，只是被隐藏了。

所以会出现这样的问题：上一页开的定时器、WebSocket、定位监听，onHide 时没暂停，就一直在后台跑；用户返回时，onShow 里又注册一次，就重复了。

正确做法是：显示时创建或恢复，隐藏时暂停，onUnload 时释放。

性能要注意什么

逻辑层和视图层之间靠序列化的消息通信，传的数据越大越慢。性能要用开发者工具和真机去量，见《setData 为什么会慢？如何优化小程序的数据更新？》。

权限怎么统一处理

相机、相册、定位、蓝牙这些能力，什么时候弹授权、被拒绝以后怎么再申请，各平台规则都不一样。

所以要在适配层把结果统一成几种：“成功 / 用户取消 / 权限拒绝 / 不支持 / 失败”，业务代码只按这几种结果处理，不要到处判断各平台的错误码。权限说明也要等用户真正要用这个功能时再出现。

怎么选型

内容、表单、列表为主的业务，用跨端框架复用率高，适合多端同时上线。需要 SEO、复杂的 DOM 编辑器或者浏览器扩展的，以 Web 为主。重度依赖系统能力或者高性能动画的，要评估原生或 React Native 这类方案。

面试时可以讲清三件事：复用的是哪部分，比如业务规则、数据模型、请求层、设计 token；哪部分要按平台单独实现；审核和回滚对发布流程有什么影响。

常见追问

小程序里能用 npm 包吗？

能用不依赖 DOM、也不依赖 Node 内置模块的包，而且要先经过开发者工具的“构建 npm”。

小程序和 H5 能共享登录态吗？

不能直接共享 Cookie。通常是服务端把小程序的会话换成一个 H5 能用的短期凭证，再通过 web-view 打开 H5。
