hash 路由和 history 路由的原理是什么？服务器要怎样配置回退？

hash 路由把路径放在

参考答案

简答

前端路由要做到的是：地址栏变了，页面内容跟着变，但浏览器不重新加载页面。实现方式有两种。

hash 路由的地址长这样：/#/user/1。# 后面那段叫片段，它不会随请求发给服务器，改 location.hash 也不会刷新页面，值一变就触发 hashchange 事件，路由监听它来切换页面。

history 路由用 history.pushState(state, '', url) 修改地址栏，同时新增一条历史记录。浏览器不会去加载这个地址，也不会触发 popstate，所以路由库调用完要自己渲染新页面。popstate 只在用户前进、后退切换历史记录时触发。另外 pushState 的地址必须和当前页面同源。

要注意，history 模式下用户一刷新，或者直接打开 /user/1，浏览器就会真的去请求这个路径。静态服务器上没有这个文件，所以要配置成找不到时返回 index.html，交给前端路由处理。

路由还要管理哪些数据、深链接和权限的边界，见《前端路由除切换组件外还需要管理什么？》。这道题只讲两种模式怎样手写，以及服务器怎样配置回退。

hash 路由怎么写

JavaScript
function renderByHash() {
  const path = location.hash.slice(1) || '/';
  render(path);
}

window.addEventListener('hashchange', renderByHash);
renderByHash();

// 跳转
location.hash = '/user/1';

location.hash 读出来是带 # 的，slice(1) 去掉它就是路径。页面第一次打开时 hashchange 不会触发，所以要手动调用一次 renderByHash()。

有个细节：给 location.hash 赋一个和当前相同的值，不会触发 hashchange。

hash 模式的好处是完全不需要服务器配置。代价是地址里带着 #，而且和页内锚点共用同一个片段，没法再用 #section 跳到页面某个位置。

history 路由怎么写

JavaScript
function navigate(url) {
  history.pushState(null, '', url);
  render(location.pathname); // pushState 不会触发 popstate，要手动渲染
}

window.addEventListener('popstate', () => render(location.pathname));

document.addEventListener('click', (event) => {
  const link = event.target.closest('a[href^="/"]');
  // 保留新标签页、下载和其他脚本已处理的点击
  if (
    !link ||
    event.defaultPrevented ||
    event.button !== 0 ||
    event.metaKey ||
    event.ctrlKey ||
    event.shiftKey ||
    event.altKey ||
    link.target ||
    link.hasAttribute('download')
  )
    return;
  event.preventDefault();
  navigate(link.getAttribute('href'));
});

代码分三块。navigate 改地址再渲染；popstate 监听前进后退；最后一块拦截站内链接的点击，阻止浏览器真的跳转，改成调用 navigate。

为什么拦截点击前要判断那么多条件？因为用户按着 Ctrl 或 Cmd 点链接，是想在新标签页打开；带 target 或 download 的链接也有自己的用途；defaultPrevented 说明别的脚本已经处理过了。这些情况都不该拦，交给浏览器原本的行为。

replaceState 的参数和 pushState 一样，区别是它替换当前这条记录，不新增。适合规范化查询参数这类不该多出一条历史的场景。

服务器为什么要配置回退

调用 pushState 时浏览器不会请求新地址。可之后用户刷新页面、复制链接在新窗口打开、重启浏览器恢复标签页，浏览器都会真的去请求 /user/1。所以服务器必须能响应所有前端路由的路径。

Nginx 的常见写法是先找真实文件，找不到再返回入口页：

nginx
location / {
  try_files $uri $uri/ /index.html;
}

回退以后有个副作用：服务器对任何未知路径都返回 200 和入口页。真正不存在的页面，要由前端渲染出 404 界面。还有，静态资源路径写错时，你可能拿到的是一段 HTML 而不是脚本，排查时要留意响应类型。

如果应用部署在子路径下，比如 /app/，那路由库的 base、构建工具的资源前缀都要设成同一个子路径，回退目标也要是这个子路径下的 index.html。托管平台不支持回退配置的话，可以改用 hash 模式。

常见追问

为什么说 history 模式对 SEO 更友好？

每个页面有独立的真实路径，服务端渲染或预渲染时可以按路径输出不同的内容。hash 片段不会发给服务器，服务器没法据此返回不同的页面。

pushState 的第二个参数有用吗？

它是历史遗留的标题参数，浏览器基本都忽略它，通常传空字符串。
