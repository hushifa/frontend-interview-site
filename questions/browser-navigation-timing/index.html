页面导航的关键阶段怎样用 Navigation Timing 分析？

浏览器把一次页面加载从重定向、DNS、建连、请求响应到 load 的每个时间点都记了下来，相邻时间点相减就是各阶段耗时。TTFB 就是 responseStart。

参考答案

简答

用户说页面打开慢，先要知道慢在哪一段：是 DNS 慢、建连慢、服务端慢，还是下载和解析慢。浏览器把这次页面加载的每个关键时间点都记了下来，用 performance.getEntriesByType('navigation')[0] 就能拿到，这条记录的类型叫 PerformanceNavigationTiming。

这些时间点不是 Unix 时间戳，而是从 performance.timeOrigin 开始算的毫秒数，startTime 是 0。相邻两个时间点一减就是这一段的耗时，比如 DNS 是 domainLookupEnd - domainLookupStart。首字节时间 TTFB 就是 responseStart，它包含了重定向、DNS、连接和服务端处理。

还能用 type 字段区分是普通导航、刷新还是前进后退，分别是 navigate、reload、back_forward。

要注意，loadEventEnd 要等 load 回调执行完才有值，在 load 事件里读会得到 0，所以一般用 PerformanceObserver 来读。另外从 bfcache 恢复、SPA 切换路由，都不会产生新记录。

时间点按什么顺序排

代码
startTime → redirectStart/End → fetchStart → domainLookupStart/End
→ connectStart → secureConnectionStart → connectEnd
→ requestStart → responseStart → responseEnd
→ domInteractive → domContentLoadedEventStart/End → domComplete → loadEventStart/End

顺着读就是一次导航的经过：先处理重定向，再查 DNS，然后建 TCP 连接，HTTPS 还要做 TLS 握手，接着发请求、收响应，最后解析文档、触发 DOMContentLoaded 和 load。

建连这一段要分开算。HTTPS 时，connectStart 到 secureConnectionStart 是 TCP，secureConnectionStart 到 connectEnd 是 TLS。

怎样采集这些数据

JavaScript
new PerformanceObserver((list) => {
  const [nav] = list.getEntries();
  const https = nav.secureConnectionStart > 0;
  report({
    type: nav.type,
    redirect: nav.redirectEnd - nav.redirectStart,
    dns: nav.domainLookupEnd - nav.domainLookupStart,
    tcp: (https ? nav.secureConnectionStart : nav.connectEnd) - nav.connectStart,
    tls: https ? nav.connectEnd - nav.secureConnectionStart : 0,
    ttfb: nav.responseStart,
    download: nav.responseEnd - nav.responseStart,
    domContentLoaded: nav.domContentLoadedEventEnd,
    load: nav.loadEventEnd,
  });
}).observe({ type: 'navigation', buffered: true });

为什么不直接在 load 里读？因为 loadEventEnd 要等 load 回调全部执行完才写入，在 load 里读到的是 0。PerformanceObserver 在记录完成后才回调，那时 loadEventEnd 已经有值了。

buffered: true 也很重要。观察者往往是在页面加载后才注册的，加了它，之前已经产生的记录也能拿到。

读数时容易看错的地方

时间值是相对值，不能直接传给 new Date()。要和日志时间对齐，用 performance.timeOrigin + 相对值。

DNS 和 TCP 耗时为 0 很正常，说明连接复用了或者命中了缓存。跨源重定向时，redirectStart 和 redirectEnd 都是 0，看不到重定向花了多久。

DOMContentLoaded 和 load 都不等于业务就绪。首屏数据有没有渲染出来，要用 performance.mark() 自己打点。

预渲染的页面被激活时，activationStart 大于 0，在它之前的阶段用户根本看不到。算用户感知的耗时要减掉 activationStart，而且要和普通导航分开统计。

单次数据波动很大。线上要汇总后看 75 分位，再按设备、网络类型分组。

常见追问

SPA 切换路由能用 Navigation Timing 统计吗？

不能。路由切换不是文档导航，不会产生新的记录。要自己用 performance.mark() 和 measure() 记录。

它和 Resource Timing 是什么关系？

PerformanceNavigationTiming 继承自 PerformanceResourceTiming，所以也有 transferSize、nextHopProtocol 这些字段。另外它的 serverTiming 字段能读到服务端通过 Server-Timing 响应头传来的各阶段耗时，可以和前端数据对着分析。
