HTTPS 相比 HTTP 提供了哪些保障？

HTTPS 通过 TLS 保护通信内容的机密性与完整性，并验证所连接服务器的相应身份。它不证明业务可信、不自动完成用户登录，也不替代应用权限与内容安全；证书、代理终止和资源混用都需要分别判断。

参考答案

简答

  • HTTPS 用 TLS 提供机密性、完整性和服务器身份认证，HTTP 语义本身不变。
  • 握手协商参数、验证证书并通过临时密钥协商建立流量密钥，不是“用服务器公钥加密所有内容”。
  • 证书校验包括信任链、域名匹配和有效期；关闭证书验证不是修复。
  • HTTPS 不隐藏 IP、流量大小等元信息，在 CDN 终止 TLS 时后续链路要另行确认。
  • 还需处理混合内容并配置 HSTS；XSS、授权等应用层问题 HTTPS 无法解决。

普通 HTTP 内容可能被链路上的参与者读取或修改。HTTPS 使用 TLS 保护通信，让客户端能够验证对方身份，并在传输过程中加密和校验应用数据。

HTTP 的方法、状态码、缓存和正文格式仍然存在。变化的是这些内容如何在连接上得到保护，不是接口逻辑自动变成安全业务。

三项保障分别是什么

机密性让没有相应密钥的链路观察者难以读取 HTTP 请求与响应内容。完整性使接收方能够发现不被允许的传输修改，而不是把被篡改的字节当成正常数据继续使用。

服务器身份认证通常通过证书与信任链，把连接目标与所请求域名联系起来，降低中间人冒充目标站点的风险。Web 场景一般验证服务器身份；客户端证书属于另外的可选部署，并不等同于普通网页登录。

这些保障依赖正确配置、可信根与密钥保护。页面有安全连接标识，表示连接通过了相应检查，不代表站点内容、商品或业务行为已经被浏览器背书。

握手建立的是通信保护参数

一次常见 TLS 握手会协商版本与密码参数，验证服务端证书，并通过相应密钥协商建立后续流量密钥。应用数据随后通常使用高效的对称认证加密机制保护。

现代常见握手使用临时密钥协商和签名等机制，不宜继续把整个过程描述成“服务器发一个公钥，浏览器用它加密所有 HTTP 内容”。证书密钥与实际保护应用流量的密钥承担不同角色。

前向保密、会话恢复与早期数据还取决于版本和具体模式。0-RTT 不代表所有第一次访问都没有握手等待，也有重放与适用请求限制。

HTTP/1.1、HTTP/2 的 HTTPS 通常是在 TCP 上使用 TLS；HTTP/3 则把 TLS 1.3 握手与 QUIC 结合。不能把所有 HTTPS 连接都固定画成完全相同的 TCP 分层流程。

证书检查不只是“有没有一张证书”

客户端需要判断证书链能否连接到信任来源、签名与用途等是否符合要求、域名是否匹配，以及证书是否处于有效期。域名匹配依赖相应的主体备用名称等信息，不是看到任意相似名称就通过。

系统时间错误、缺失中间证书、证书过期或连接到了错误主机，都可能导致不同的验证失败。自签名证书并不会因为它能加密流量，就自动获得浏览器对站点身份的信任。

开发测试可以使用专门的本地信任安排，但不应把关闭证书验证当成正式环境修复。真正需要修复的是证书、链路或信任配置，而不是让客户端忽略身份检查。

HTTPS 不会隐藏所有网络元信息

URL 路径、查询参数、HTTP 头和正文属于受保护的应用内容，但连接目标 IP、流量大小和时序等元信息仍可能被观察到。域名信息是否在特定阶段可见，还与 DNS、SNI、ECH 等配置和支持有关。

因此 HTTPS 不是完整的匿名通信方案。反过来，也不能说“查询参数在地址栏里可见，所以在 TLS 链路上仍然是明文”。地址栏、浏览器历史、日志与网络传输，是不同的信息暴露位置。

保护到哪一个终点，要看部署链路

如果 TLS 在 CDN、负载均衡器或代理处终止，该节点可以处理相应 HTTP 内容；它到源站的后续连接是否也加密，需要另行配置与验证。

浏览器与 CDN 之间安全，不自动证明 CDN 到源站的每一段都同样安全。服务器日志、应用代码和终止 TLS 的受信节点看到请求内容，也不属于 TLS 原本要对这些终点隐藏的数据。

这解释了为什么部署排查需要分段确认，而不是只看浏览器地址栏的一个标志。

页面改成 HTTPS 后，子资源也要配套

HTTPS 页面继续加载 HTTP 脚本、接口、图片或 ws 连接，会涉及混合内容限制。浏览器可能根据资源类型与策略升级或阻止访问，不能假定所有旧 URL 都会自动安全转换。

实时连接通常需要相应 wss 支持；Cookie 的 Secure 属性控制安全传输范围，但不替代 HttpOnly、SameSite 或会话权限。CORS 又负责某些跨源读取许可，与加密是不同问题。

许多浏览器能力要求安全上下文，HTTPS 是常见途径。localhost 等开发环境有特定可信例外，不能把本地 HTTP 下可用的结果推广到任意公网 HTTP 页面。

HSTS 可以减少后续降级访问

服务器可以通过可信 HTTPS 响应发送 Strict-Transport-Security，让浏览器在相应期限内对该站点采用 HTTPS。已知策略或预加载可以让后续访问在发出明文 HTTP 前升级，而不只依赖服务器收到 HTTP 后再重定向。

策略包含哪些子域、维持多久以及是否申请预加载，需要与实际部署能力一致。仅仅加一个字符串并不意味着所有浏览器立即获得同样的预加载记录。

应用层问题仍然需要应用层防护

HTTPS 不会阻止站点自己返回恶意脚本，也不能替代 XSS 防护、输入校验、资源授权和可靠的支付逻辑。一个恶意站点同样可以拥有对其自身域名有效的证书。

调试时应分清证书验证失败、混合内容、CORS、Cookie 规则与业务错误。它们都可能让请求不符合预期，但修改 TLS 配置不会自动解决后面的所有层次。
