为什么 z-index 设置很大，元素还是被遮挡？

z-index 只在相应层叠上下文中参与排序，子元素不能用巨大数值跨过祖先与外部兄弟上下文的顺序。定位、裁剪和顶层显示机制也会影响最终结果，需要分别排查。

参考答案

简答

  • z-index 只在同一个层叠上下文内比较，子元素数值再大也不能越过父级上下文的整体层级。
  • 定位元素加非 auto 的 z-index、opacity 小于 1、transform、filter 等都可能建立新的层叠上下文。
  • opacity: 0.99、translateZ(0) 看不出视觉变化，却会改变分组关系。
  • 排查遮挡要找出各自所在的上下文，再决定调整哪一层，而不是继续加大数值。

z-index: 999999 不是全页面通用的最高通行证。浏览器把一部分元素组织成独立的层叠上下文，每个上下文先安排内部的绘制顺序，再把整体放进外层参与排序。

可以把它理解成成组比较：A 组整体在 B 组下面，那么 A 组中的子元素即使排在组内最前，也不能凭自己的数值插到 B 组上面。DOM 层级不完全等同于这棵上下文树，只有满足特定条件的元素才创建新的组。

一个数值很大仍被挡住的例子

HTML
<div class="stage">
  <section class="left">
    左侧区域
    <div class="tip">提示内容，z-index 很大</div>
  </section>
  <section class="right">右侧区域</section>
</div>
CSS
.stage {
  display: grid;
  grid-template-columns: 1fr 1fr;
  width: 360px;
  max-width: 100%;
}

.stage > section {
  min-height: 6rem;
}

.left {
  position: relative;
  z-index: 1;
  background: #e2e8f0;
}

.tip {
  position: absolute;
  top: 2rem;
  left: 3rem;
  width: 16rem;
  z-index: 999999;
  background: #fde68a;
}

.right {
  position: relative;
  z-index: 2;
  background: #bfdbfe;
}

提示框横向伸进右侧区域，但重叠部分仍会被右侧背景盖住。.left 与 .right 分别建立上下文，外层先比较的是 1 和 2。提示框的 999999 只在左侧上下文内有意义，不会拿来与右侧的 2 直接比较。

把 .left 的层级调到右侧之上，能让它连同提示框一起上来。但这也会提高整个左侧区域，不一定符合需求。如果只希望提示框浮到页面其他区域之上，应考虑把提示框移出这个受限上下文。

哪些样式会建立新的上下文

常见情况包括：

  • 文档根元素。
  • position: relative 或 absolute，并且 z-index 不是 auto。
  • position: fixed 或 sticky，即便 z-index 是 auto。
  • Flex 项或 Grid 项设置了非 auto 的 z-index，不要求额外写 position: relative。
  • opacity 小于 1、非 none 的 transform，以及 isolation: isolate。
  • contain: layout、contain: paint 等包含规则，或指定相关属性的 will-change。

这不是所有触发条件的完整清单。例如混合模式、滤镜、裁剪路径等也可能相关，排查时应查看实际计算样式和对应规则。

特别容易忽略的是 opacity: 0.99 与 transform: translateZ(0)：它们可能看不出明显视觉变化，却改变了分组关系。不要为了所谓“开启硬件加速”到处添加 transform，然后只在子元素上不断加大层级。

auto 和 0 不是总能互换

对普通的相对或绝对定位元素，z-index: auto 本身不会创建新的层叠上下文，z-index: 0 则会。两者看上去都像“没有提高层级”，但子元素能参与哪一层的比较可能已经改变。

如果上面例子的 .left 没有其他触发条件，把它改成 z-index: auto 后，它不再以独立上下文约束 .tip。提示框便有机会在更外层与右侧比较。这里不能只删掉某个数值就认定一定解决，因为祖先还可能有 transform、opacity 等触发条件。

同时，z-index 并不对所有普通静态块元素都产生预期效果。普通流的静态元素与 Flex/Grid 项的规则不同，应先判断元素所处的布局身份，再决定是否需要定位。

被盖住和被裁掉，需要不同的处理

元素伸出祖先的 overflow: hidden 或裁剪区域，可能是内容被裁掉，并不是另一个元素画在上面。提高 z-index 不能普遍突破祖先裁剪边界，应该检查裁剪来源与定位包含块，必要时移动挂载位置。

把 z-index 改成负数也不是可靠的隐藏方式。它改变的是当前上下文里的绘制顺序，元素仍然可能占位、被访问或在其他部分可见；还可能落到其他背景后面，让问题更难定位。

浮层可以采用哪一种结构

组件库常通过 Portal 把浮层挂到页面外层，避开业务容器的上下文和裁剪。Portal 本身不是浏览器的新层级：挂载目标仍在普通文档层叠中，还需要设计清楚的层级、定位与焦点管理。

原生模态对话框通过 dialog.showModal() 进入 top layer，显示中的 Popover 等也能进入 top layer。这个顶层显示机制位于普通文档层叠之上，不需要与普通卡片的巨大 z-index 竞争。只写 <dialog open> 或调用非模态 show()，则不能等同于 showModal() 的模态顶层行为。

top layer 也不意味着多个顶层元素可以随意按普通 z-index 排序，更不代表非模态 Popover 自动具有模态对话框的交互语义。需要哪一种浮层，应由内容、焦点、关闭方式与模态需求共同决定。

实际排查可以从被遮挡元素向上找到上下文祖先，再对另一侧做同样检查，找出它们在共同外层中首先分开的两个上下文。比较那一层的顺序，往往比修改最里面那个数字有效得多。
