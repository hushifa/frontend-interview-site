为什么字符串 length 不一定等于用户看到的字符数？

JavaScript 字符串的 length 是 UTF-16 码元数，一个 emoji 可能占两个码元，一个“字符”也可能由多个码点组成。按用户看到的字符截断要用 Intl.Segmenter 的字素簇分割，分词用 word 粒度，字节数用 TextEncoder 统计，比较前按需 normalize。

参考答案

简答

'😀'.length 是 2，一个全家福 emoji '👨‍👩‍👧‍👦'.length 是 11，可它们在屏幕上都只是一个字符。因为 length 数的是 UTF-16 码元，不是用户看到的字符。

所以“字符”至少有四种数法。UTF-16 码元是 length 和 slice 用的；码点是 [...text] 遍历出来的；字素簇是用户眼里的一个字符；UTF-8 字节是存储和传输时的大小。

按“看得见的字符”截断，要用 Intl.Segmenter 的 grapheme 粒度。slice 可能把一个 emoji 从中间切开，[...text] 也可能拆散组合字符和 emoji 序列。中文、日文、泰文词之间没有空格，分词也用 Intl.Segmenter，选 word 粒度并过滤 isWordLike。

还要注意，'\u00E9' 和 'e\u0301' 都显示成 é，但并不相等，比较或去重前要先 normalize('NFC')。

四种数法差多少

下面对几个字符串分别数码元、码点和字素簇，再数一个汉字的字节。结果是 Node 22 实测的。

JavaScript
const graphemes = new Intl.Segmenter('zh-CN', { granularity: 'grapheme' });

for (const text of ['A', '😀', 'e\u0301', '👨‍👩‍👧‍👦']) {
  console.log(text.length, [...text].length, [...graphemes.segment(text)].length);
}
// 1 1 1
// 2 1 1
// 2 2 1
// 11 7 1

'你'.length; // 1
new TextEncoder().encode('你').length; // 3，UTF-8 字节

为什么 😀 的 length 是 2？它的编号超出了 UTF-16 一个码元能表示的范围，只好用两个码元拼起来，这两个码元叫代理对。

'e\u0301' 是字母 e 加上一个组合用的重音符号，两个码点，显示出来是一个 é。全家福更夸张，是四个人的 emoji 用三个连接符拼在一起，一共 7 个码点、11 个码元。浏览器把这些拼在一起显示的整体，叫字素簇，也就是用户眼里的“一个字”。

所以做“昵称最多 20 个字符”这种限制时，先定义清楚字符指的是字素簇，前后端用同一套规则校验。数据库字段按字节限制时，就用 TextEncoder 数字节。

怎样按字素簇截断

下面截取前几个看得见的字符，超出时加省略号。

JavaScript
function truncateText(text, limit) {
  if (!Number.isInteger(limit) || limit < 0) {
    throw new RangeError('保留数量必须是非负整数');
  }
  let count = 0;
  for (const part of graphemes.segment(text)) {
    if (count === limit) return text.slice(0, part.index) + '…';
    count += 1;
  }
  return text;
}

truncateText('A👨‍👩‍👧‍👦B', 2); // 'A👨‍👩‍👧‍👦…'
truncateText('A😀', 2); // 'A😀'，刚好两个，不加省略号
truncateText('你好世界', 2); // '你好…'

全家福被完整保留了，没有被切成半个。这是因为 part.index 是每个字素簇在原字符串里的 UTF-16 下标，交给 slice 时正好落在字素簇的边界上。找到截断点就直接返回，不用把整段文本先转成数组。

这里的 limit 是保留的原文字素簇数，省略号不算在内；limit 为 0 且文本非空时，只返回一个省略号。如果产品要求总长度包含省略号，要另外算额度。HTML 摘要也不能按源码截断，否则会切坏标签和实体，要先提取纯文本再处理。

运行环境没有 Intl.Segmenter 时，可以用维护中的兼容实现。Array.from 只按码点切，会拆散组合字符和 emoji 序列，不能拿来当降级方案。

怎样分词

英文词之间有空格，中文没有，所以分词不能靠 split(' ')。

JavaScript
const words = new Intl.Segmenter('en', { granularity: 'word' });
[...words.segment('Hello, world!')]
  .filter((s) => s.isWordLike)
  .map((s) => ({ text: s.segment, index: s.index }));
// [{ text: 'Hello', index: 0 }, { text: 'world', index: 7 }]

const zh = new Intl.Segmenter('zh', { granularity: 'word' });
[...zh.segment('我喜欢国际化')].filter((s) => s.isWordLike).map((s) => s.segment);
// ['我', '喜欢', '国际', '化']（结果取决于运行时的分词数据）

word 粒度会把标点和空格也切出来，所以要用 isWordLike 过滤，只留下真正的词。

中文的结果把“国际化”切成了“国际”和“化”。分词靠的是运行时自带的语言数据，不保证符合业务词典或搜索引擎的切词规则。另外还有 granularity: 'sentence' 按句子切分，碰到缩写、引号和复杂标点时，要拿目标语言的样本验证。

做搜索高亮时，用 index 和 segment.length 定位原文的区间，再用文本节点和 <mark> 渲染，不要拼进 innerHTML。如果匹配前做了大小写折叠或规范化，字符串长度可能会变，这时要维护新旧位置的对应关系，不能拿新字符串的下标去切原文。

看起来一样的字符为什么不相等

é 有两种写法：一个现成的码点，或者 e 加组合重音。

JavaScript
const composed = '\u00E9';
const decomposed = 'e\u0301';
composed === decomposed; // false
composed.normalize('NFC') === decomposed.normalize('NFC'); // true

两种写法显示一样，=== 却是 false，因为码点不同。normalize('NFC') 把它们统一成同一种写法，之后才能比较。

规范化只处理 Unicode 规定的等价写法。它不会把西里尔字母 а 和拉丁字母 a 当成同一个字符，要防范仿冒用户名，得另外检查。

常见追问

输入框实时限制长度会有什么问题？

中文输入法正在组合拼音时，也就是 compositionstart 到 compositionend 之间，不要截断，否则会把用户的输入打断。等组合结束再检查长度。

Intl.Segmenter 能算出文字在屏幕上占多宽吗？

不能。宽度由字体和渲染决定，它只管怎么切分，要知道宽度得测量实际布局。
