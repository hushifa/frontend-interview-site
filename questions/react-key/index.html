列表中的 key 为什么不能随意使用数组下标？

key 参与 React 对同级元素身份的识别，影响本地状态和 DOM 是否保留。下标标识的是位置，稳定 ID 标识的是记录；重排、插入或删除时，这个差别会直接影响草稿、焦点和 Effect 生命周期。

参考答案

简答

key 告诉 React 同级元素中谁是谁，决定状态和 DOM 是复用还是重建。用数组下标做 key，在插入、删除、重排时，状态会跟着位置走，导致草稿、焦点、输入值错位。应使用稳定、同级唯一的业务 ID；渲染时随机生成的 key 会让组件每次都重建。只有固定不变的静态列表，用下标才安全。

React 更新列表时，需要判断这一轮的每个元素对应上一轮的哪一个。key 为同级元素提供稳定标识，和元素类型、所处树结构一起参与身份判断。

如果 key 使用数组下标，表达的其实是“第几个位置”。当数据重排时，同一个位置换了记录，React 仍可能保留这个位置原有的组件状态，于是上一条记录的草稿、展开状态或未受控输入值跟到了另一条记录身上。

用可编辑草稿看清身份错位

JSX
import { useState } from 'react';

function DraftRow({ item }) {
  const [draft, setDraft] = useState(item.title);
  return (
    <li>
      <span>{item.title}</span>
      <input
        aria-label={`${item.id} 的草稿`}
        value={draft}
        onChange={event => setDraft(event.target.value)}
      />
    </li>
  );
}

export default function QuestionList() {
  const [items, setItems] = useState([
    { id: 'html', title: 'HTML' },
    { id: 'css', title: 'CSS' },
  ]);

  return (
    <section>
      <button type="button" onClick={() => setItems(current => [...current].reverse())}>
        反转顺序
      </button>
      <ul>
        {items.map(item => <DraftRow key={item.id} item={item} />)}
      </ul>
    </section>
  );
}

把 HTML 那行的输入改成“我的 HTML 草稿”，再反转列表。使用 id 时，草稿仍跟随 HTML 记录，只是位置变了。

若把 map 改成使用 index，并写 key={index}，反转后第 0 个位置的组件仍可能保留原草稿，但现在接收到 CSS 的 item。标题与草稿就会错位。问题不是 React 没看到数据变化，而是我们给出的身份信息把“同一位置”当成了“同一记录”。

DraftRow 的状态初始值来自 item.title，只在状态初始化时采用。prop 变化并不会自动重新初始化那份 state，这也使错误 key 下的身份问题更容易观察。

什么样的 key 才稳定

来自数据的数据库 ID、文档 ID 或业务中稳定唯一的键通常合适。需要同时满足：在同一组兄弟元素中唯一，而且同一记录在重排或重新渲染时保持一致。

没有服务端 ID 时，可以在创建记录时生成一个 ID，并随着记录保存。不要在 render 或 map 回调中每次使用 Math.random、Date.now 或新生成的 UUID，否则同一条数据下一轮也会变成全新身份。

不稳定 key 会造成反复卸载与挂载，本地状态丢失、Effect 重建，输入焦点和性能也可能受影响。它不是一个“让 React 更努力刷新”的技巧。

key 的范围是同级列表，不是全站数据库

两个不同列表可以都使用 key="html"，因为它们属于不同的同级集合；同一个列表里重复 key 则会造成身份歧义。

key 应写在 map 返回的最外层元素或组件上。若每项返回多个节点，可以使用带 key 的 Fragment，而不是只给 Fragment 里面的某个孩子加 key 后，就期待外层列表身份也清楚。

key 不是普通 prop，子组件不能依靠 props.key 读取记录 ID。需要 ID 时应另传 item、id 等正常属性。React 的 useId 主要服务可访问关联等稳定 ID 需求，也不应当作列表数据 key 的替代。

改 key 可以有意重置状态，但要知道代价

切换编辑对象时，如果设计上就是希望丢弃旧草稿，可以用编辑对象 ID 作为编辑器 key，使身份切换时重新初始化。它明确表达的是“这是另一个编辑器实例”，不是单纯再执行一次渲染。

组件类型发生改变、节点离开原来的树结构或被真正卸载，也会影响状态保留。相同 key 不是一个全局缓存：某一页的行完全卸载后，再翻回来，并不会仅因为 ID 相同就自动恢复曾经的全部本地状态。

需要跨分页、筛选或卸载继续保存草稿时，应把状态放在合适的上层或持久化结构里，按稳定 ID 管理。key 负责 React 树中的身份关系，不负责所有业务数据的存活期限。

数组下标什么时候风险较低

列表内容和顺序确实固定、不会插入删除重排，而且没有需要跟随记录的本地状态或 DOM 行为时，下标造成的风险较低。问题在于这些条件经常会随着功能迭代失效，例如后来新增排序、搜索、编辑或拖拽。

因此只要数据已经有稳定 ID，就没有必要把身份退回位置。测试时应覆盖首部插入、删除中间项、排序和筛选，并观察草稿、焦点、勾选与展开状态是否仍属于正确记录，而不只是确认列表文字看起来没变。
