HttpOnly、Secure 和 SameSite 分别保护什么？

HttpOnly 让脚本读不到 Cookie，Secure 让 Cookie 只走 HTTPS，SameSite 决定跨站请求带不带 Cookie。各浏览器默认行为不一样，所以要显式写出来。

参考答案

简答

这三个属性各管一件事。HttpOnly 让 document.cookie 读不到这个 Cookie，XSS 就没办法直接把会话偷走。Secure 让 Cookie 只在 HTTPS 请求里发送，防止明文传输时被窃听。SameSite 决定跨站请求带不带这个 Cookie，主要用来防 CSRF。

SameSite 有三个值。Strict 是任何跨站请求都不带；Lax 是只有从别的网站点链接跳过来这种顶层 GET 导航才带；None 是都带，但必须同时设 Secure。

没写 SameSite 时各浏览器的默认行为不一样，Chromium 按 Lax 处理，所以最好显式写出来。会话 Cookie 一般推荐 __Host- 前缀加 Secure; HttpOnly; SameSite=Lax; Path=/。

要注意，HttpOnly 只是让脚本读不到 Cookie，有 XSS 时脚本仍然能借用户的身份发请求，根本上还是要防住 XSS。

推荐写法

http
Set-Cookie: __Host-session=abc123; Secure; HttpOnly; SameSite=Lax; Path=/; Max-Age=86400

名字前面的 __Host- 是一个前缀约定，浏览器会检查：带这个前缀的 Cookie 必须设 Secure、Path=/，并且不能设 Domain。不能设 Domain 就意味着这个 Cookie 只属于当前主机，子域名没办法写一个同名的来覆盖它。另一个前缀 __Secure- 宽松一些，只要求 Secure。

过期时间方面，同时设了 Expires 和 Max-Age 时以 Max-Age 为准。两个都不设，就是会话 Cookie，关闭浏览器后失效。不过浏览器的“恢复上次会话”功能可能把它保留下来，所以不能完全指望它会消失。

SameSite 说的“站”是什么

站点是协议加上可注册域名，也就是常说的 eTLD+1，比如 https://example.com。所以 a.example.com 和 b.example.com 是同站，SameSite 不会拦它们之间的请求；example.com 和 example.org 是跨站。

请求场景StrictLaxNone
同站请求带带带
从其他站点点链接打开不带带带
其他站点的表单 POST不带不带带
其他站点 iframe 或 fetch不带不带带

看这张表会发现 Strict 最安全，那为什么不都用它？因为用户从搜索结果或者别人发的链接点进来，第一个请求不带 Cookie，看起来就像没登录。所以常见做法是会话用 Lax，转账、改密码这类高风险操作再额外校验令牌。

不写 SameSite 会怎样

Chromium 会按 Lax 处理，但有一个例外：刚设置不到 2 分钟的 Cookie，顶层的跨站 POST 也会带上，这是为了兼容一些登录流程。其他浏览器的默认行为又不一样。所以靠默认值不可靠，显式写出来最稳。

第三方 Cookie 现在还能用吗

嵌在别的网站里的 iframe 或请求，要带 Cookie 必须设 SameSite=None; Secure。可是即使这样，浏览器的隐私策略也可能拦下来。Chrome 默认允许第三方 Cookie，用户可以在设置里屏蔽，无痕模式默认屏蔽。Firefox 默认开启全面 Cookie 保护，把第三方 Cookie 按顶层站点分开存储。Safari 的智能防跟踪默认阻止第三方 Cookie。

替代方案有分区 Cookie（Partitioned）、Storage Access API 和 FedCM，见《第三方 Cookie、SameSite 和 Partitioned Cookie 有什么区别？》。

常见追问

单个 Cookie 能有多大？

RFC 6265 要求浏览器每个 Cookie 至少支持 4096 字节，实际的上限也大致在这个范围。

设了 HttpOnly 是不是就安全了？

不是。它只解决了令牌被脚本读走的问题。有 XSS 时，恶意脚本仍然可以在页面里直接发请求，浏览器照样会带上 Cookie，所以根本上要防住 XSS。
