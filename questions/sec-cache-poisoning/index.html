什么是 Web 缓存投毒？如何避免把用户数据缓存给别人？

缓存投毒是攻击者让 CDN 存下一份被他影响过的响应，再发给所有人；缓存欺骗是骗 CDN 存下某个用户的私人页面。根源都是影响响应的输入没进缓存键，或者私有响应没标 private、no-store。

参考答案

简答

CDN 这类共享缓存会把一个响应存下来，发给之后所有请求同一地址的人。缓存投毒就是攻击者构造一个特殊请求，让 CDN 存下一份被他动过手脚的响应，比如页面里的脚本地址被换成了他的域名，之后所有用户都会加载他的脚本。

问题出在缓存键上。缓存键是 CDN 判断“这两个请求算不算同一个”的依据，通常由方法、主机、路径和查询串组成，请求头默认不在里面。如果源站根据 X-Forwarded-Host 这种不在键里的请求头生成内容，攻击者改一下请求头，缓存却认为是同一个地址，就把恶意版本存下来了。

还有一种反过来的叫缓存欺骗。攻击者诱导用户访问 /account/profile.css，应用把它当成 /account/profile 返回了个人数据，CDN 看到 .css 后缀当静态资源存下来，攻击者再去访问就能拿到。

防护上，资源地址不读请求头；私有响应设 Cache-Control: private，完全不能缓存的再加 no-store；CDN 按源站的缓存头决定，不按扩展名强制缓存；CDN 和源站对 URL 的规范化要一致。

投毒是怎么发生的

先看一段有问题的源站代码，它用请求头拼出脚本地址：

JavaScript
// 有问题的写法
const host = req.headers['x-forwarded-host'] ?? req.headers.host;
res.send(`<script src="https://${host}/app.js"></script>`);

正常请求时，这段代码没毛病。可是攻击者可以自己发一个带 X-Forwarded-Host: evil.example 的请求，源站就返回了加载 evil.example/app.js 的首页。CDN 的缓存键里没有这个请求头，它以为这就是 / 的正常响应，于是存了下来。之后所有访问首页的用户拿到的都是这份，都会加载攻击者的脚本。

改法有三种。最好的是资源地址用配置里的固定域名，根本不读请求头。如果确实要用某个请求头，就把它加进缓存键或者 Vary，并且只接受白名单里的值。另外可以在 CDN 边缘直接剥掉不需要的请求头，让它到不了源站。

缓存欺骗是怎么发生的

text
https://app.example/account/settings/avatar.png

很多应用的路由比较宽松，会忽略多出来的路径段，于是这个地址返回的其实是账户设置页。可是 CDN 只看到了 .png，按图片缓存了它。攻击者只要诱导一个已登录的用户点一下这个链接，再自己去访问同一个地址，就拿到了那个用户的设置页。

所以应用对不存在的路径要返回 404，不要宽松匹配。个性化的响应设置 Cache-Control: private, no-store，CDN 尊重源站的 Cache-Control，而不是看到扩展名就强制缓存。带 Authorization 或会话 Cookie 的请求默认不缓存。

为什么不能靠 Vary: Cookie 解决

Vary 告诉缓存“这个请求头不同，响应就不同”，只是声明哪些请求头会改变响应，它不做权限控制。如果写 Vary: Cookie，每个用户的 Cookie 都不一样，缓存几乎就没用了。私人数据正确的做法是标 private，让共享缓存根本不存。

还有哪些东西容易被误缓存

错误页和重定向是常被忽略的。一次 500 或者一个指向攻击者域名的 302 被缓存下来，所有人都会受影响。带个人信息的 JSON 接口也一样。还有按 Accept-Language 或设备类型返回不同内容的页面，如果没加 Vary，就会把中文页发给英文用户这样串内容。

另外 CDN 和源站对 URL 的理解要一致，包括大小写、尾斜杠、编码、路径参数。两边理解不同，就可能出现“CDN 认为是 A，源站返回的是 B”。

怎么验证和应急

看响应是不是来自共享缓存，可以看 Age、Cache-Status 或厂商自己的缓存头，见《Cache-Status 响应头能帮助诊断哪些缓存问题？》。测试时给 URL 加一个随机参数，也就是 cache buster，避免把真实缓存污染了。

发现泄露后，先修好源站的头部，再清除 CDN 缓存。顺序不能反，而且已经缓存的副本不会因为源站改了就自动消失，必须手动清。

常见追问

缓存投毒和普通的缓存配置错误有什么区别？

配置错误是被动地串内容，比如没加 Vary 导致语言串了。投毒是攻击者主动构造请求，故意让缓存存下恶意的响应。

前端能做些什么？

不要让页面输出依赖没验证过的请求头或者 URL 片段，接口按约定返回正确的缓存头，个人数据的接口明确标上 private 或 no-store。
