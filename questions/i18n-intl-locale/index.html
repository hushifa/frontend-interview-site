Intl.Locale 解决什么问题？语言标签应该怎样建模？

Intl.Locale 把 zh-Hant-TW 这样的 BCP 47 语言标签解析并规范化，拆出语言、文字、地区和 Unicode 扩展。maximize 和 minimize 补全或精简子标签；资源匹配要自己实现回退链；书写方向用 getTextInfo 或 textInfo 检测。

参考答案

简答

zh-Hant-TW 这样的字符串叫语言标签，意思是“中文、繁体字、台湾”。它由几段子标签拼成，Intl.Locale 负责把它拆开，变成 language、script、region 这些属性，还会顺手修正大小写和弃用的写法。

建模时要记住，语言、地区和时区是三件事。一个在日本的英语用户，可能要英文界面、日元和东京时区，所以不要用一个字段去推另外两个。

它还有两个常用方法。maximize() 按数据补全子标签，zh 会变成 zh-Hans-CN；minimize() 反过来去掉能推断的部分。两者都只是补全和精简，不是翻译。选哪份翻译资源要自己写回退链，例如 zh-Hant-HK → zh-Hant → zh → 默认语言。

书写方向可以用 getTextInfo().direction 检测，但 Node 22 只有旧的 textInfo 属性，所以两种都要做能力检测。

怎样解析和规范化

下面把一个标签拆开，再看补全、精简和规范化的效果。

JavaScript
const locale = new Intl.Locale('zh-Hant-TW');
locale.language; // 'zh'
locale.script; // 'Hant'
locale.region; // 'TW'
locale.baseName; // 'zh-Hant-TW'

new Intl.Locale('zh').maximize().toString(); // 'zh-Hans-CN'
new Intl.Locale('zh-Hans-CN').minimize().toString(); // 'zh'
Intl.getCanonicalLocales(['EN-us', 'zh-cn', 'iw']); // ['en-US', 'zh-CN', 'he']
new Intl.Locale('not a tag'); // RangeError

maximize() 凭什么知道 zh 就是简体、中国？它查的是 likely-subtags 数据，也就是“只说了语言时，最可能是哪种文字和地区”的统计表。所以它只是猜最常见的情况，不代表用户真的在中国。

getCanonicalLocales 叫规范化，它会把大小写改对，还会把弃用的代码换掉，比如希伯来语的旧代码 iw 变成 he。保存用户偏好时，存规范化以后的结果，之后比较起来才不会出错。

地区子标签不等于用户在哪

en-JP 里的 JP 只说明这是一种语言变体，不代表用户在日本，也不决定货币和时区。

所以在日本的英语用户，可能要英文界面、日元和东京时区。这三项要分别保存，不要从语言标签里推出货币，也不要推出时区。

Unicode 扩展是做什么的

标签后面还能挂上 -u- 开头的扩展，用来指定日历、数字系统这类偏好。

JavaScript
const thai = new Intl.Locale('th-TH', { calendar: 'buddhist', numberingSystem: 'thai' });
thai.toString(); // 'th-TH-u-ca-buddhist-nu-thai'

ca 表示日历，nu 表示数字系统，hc 表示时制。这些键是规范定义好的，不能自己随便加。把这样的 locale 传给 Intl.DateTimeFormat，就会用佛历和泰文数字来显示日期。

怎样选翻译资源

Intl.Locale 只负责解析，不知道你手里有哪几份翻译。下面这个函数自己实现了回退链。

JavaScript
function pickLocale(requested, available, fallback = 'en') {
  for (const tag of requested) {
    const current = new Intl.Locale(tag).maximize();
    const candidates = [current.baseName, `${current.language}-${current.script}`, current.language];
    const hit = candidates.find((c) => available.includes(c));
    if (hit) return hit;
  }
  return fallback;
}

pickLocale(['zh-HK'], ['zh-Hant', 'zh-Hans', 'en']); // 'zh-Hant'

用户要的是 zh-HK，资源里却没有这一份。如果只按语言 zh 去匹配，很可能落到简体上，香港用户会看到简体字。

先 maximize() 一下就不同了。zh-HK 补全成 zh-Hant-HK，候选依次是 zh-Hant-HK、zh-Hant、zh，于是先匹配到繁体资源。

有人会想用 Intl.DateTimeFormat.supportedLocalesOf() 来做这件事。可它只能告诉你运行时支持哪些格式化语言，并不知道你有哪些翻译文件。

怎样检测书写方向

新标准用的是 getTextInfo() 方法，旧版本是 textInfo 访问器，所以要两种都检测。

JavaScript
function getDirection(tag) {
  const locale = new Intl.Locale(tag);
  if (typeof locale.getTextInfo === 'function') return locale.getTextInfo().direction;
  if (locale.textInfo) return locale.textInfo.direction; // 旧版访问器
  return null; // 不支持时由应用的语言配置决定
}

getDirection('ar'); // 'rtl'

两种都不支持时返回 null，这时由应用自己的语言配置决定方向。

常见追问

navigator.language 能直接当界面语言吗？

可以当默认值，但要允许用户手动切换，并把选择保存下来。navigator.languages 还提供了按偏好排好序的完整列表，可以拿来做回退。

SSR 时怎样决定语言？

先看用户保存的设置，其次看 URL 或 Accept-Language 请求头。服务端选定以后，把结果传给客户端，不要两端各自判断，否则可能选出不同的语言。
