Intl.Locale 解决什么问题？语言标签应该怎样建模？

解释 Intl.Locale 对 BCP 47 语言标签的解析、规范化、最大化和最小化，区分语言偏好、内容 locale、地区与时区，并说明方向判断、匹配和持久化边界。

参考答案

国际化系统里经常出现一串看似简单的字符串：zh-CN、en-GB、sr-Latn 或 ar-EG。如果把它们当普通字符串拆分，开发者很容易把语言、脚本、地区、扩展和用户偏好混在一起。例如 en 没有明确地区，zh-Hant 指定了脚本却没有指定地区，而 America/Los_Angeles 是时区，不是语言标签的一部分。

Intl.Locale 提供了一个结构化入口，用来解析和组合 BCP 47 语言标签。它帮助应用读取语言、脚本和地区等组成部分，但它不是翻译器、不是时区对象，也不会替产品决定用户最终使用哪种语言。

JavaScript
const locale = new Intl.Locale('zh-Hant-TW');

console.log(locale.language); // zh
console.log(locale.script);   // Hant
console.log(locale.region);   // TW
console.log(locale.baseName); // zh-Hant-TW
console.log(locale.toString());

对象的属性描述标签中的语义，不代表服务器一定支持该语言，也不代表用户真的能读懂。应用仍要维护可用翻译资源和明确的 fallback 策略。

语言、脚本、地区和时区是不同维度

语言标签的常见组成部分包括语言（language）、脚本（script）和地区（region），还可能有变体和 Unicode 扩展：

JavaScript
const simplified = new Intl.Locale('zh-Hans');
const traditionalTaiwan = new Intl.Locale('zh-Hant-TW');
const calendar = new Intl.Locale('en-US-u-ca-gregory');

console.log(simplified.language, simplified.script, simplified.region);
console.log(traditionalTaiwan.language, traditionalTaiwan.script, traditionalTaiwan.region);
console.log(calendar.calendar); // gregory（是否支持该属性取决于运行时）

地区不一定等于用户当前所在地，脚本也不一定等于单一国家。zh-CN 和 zh-TW 可能使用不同的内容、词汇和日期规则；sr-Latn 与 sr-Cyrl 的主要差异是书写脚本。时区应单独保存和处理，例如 Asia/Tokyo 不能拼进语言标签来代替 timeZone 选项。

表单和账号设置最好分别存储：

JavaScript
const preferences = {
  locale: 'en-GB',
  timeZone: 'Europe/London',
};

这样用户在英国时区使用中文界面，或在中文界面查看纽约业务时间，都不会因为一个字符串字段被迫绑定在一起。

canonicalize、maximize 和 minimize 不是翻译

Intl.getCanonicalLocales() 可以规范化一组 locale 标识，Locale 的 maximize() 和 minimize() 可根据运行时的语言数据补充或移除通常的脚本/地区信息：

JavaScript
const original = new Intl.Locale('zh');
const maximized = original.maximize();
const minimized = maximized.minimize();

console.log(maximized.toString()); // 结果依赖运行时的 likely-subtags 数据
console.log(minimized.toString());

console.log(Intl.getCanonicalLocales(['EN-us', 'zh-cn']));

最大化的结果是“根据语言数据推测一个更完整标签”，不是确认用户所在地区，也不是把 zh 永久改成某个产品地区。最小化则尝试移除可以推断的部分，结果同样依赖 ICU/CLDR 数据。不要把 maximize() 的地区当成地理定位、账单地区或法律辖区。

规范化后的语言标签适合用于 locale matching 和格式化器配置；业务持久化是否保留用户原始选择，取决于产品需求。若用户明确选择 zh-Hant-TW，不能为了节省字符串长度无条件存成 zh，否则可能丢失重要脚本和地区偏好。

Locale 选择和资源回退是两个过程

浏览器可能通过 navigator.languages 提供用户偏好，例如 ['zh-Hant-TW', 'en-US']。应用需要把它与自己实际提供的资源列表匹配：

JavaScript
const supported = ['zh-CN', 'en-US', 'ja-JP'];
const requested = navigator.languages;
const matcher = new Intl.Locale('en-US');

const supportedSet = new Set(supported.map((tag) => new Intl.Locale(tag).baseName));
const selected = requested.find((tag) => {
  try {
    return supportedSet.has(new Intl.Locale(tag).baseName);
  } catch {
    return false;
  }
}) ?? supported[0];

console.log(selected);
void matcher; // 这里仅说明 Locale 对象不等于资源匹配器

示例中的精确匹配很简单，实际产品可能需要按语言、脚本和地区逐级回退，例如先尝试 zh-Hant-TW，再尝试 zh-Hant，最后回退到默认语言。Intl.Locale 负责解析标签，但不会自动加载翻译文件，也不会判断某个 locale 是否存在完整文案。资源系统应明确回退顺序、缺失 key 的处理和审校状态。

不要用 startsWith('en') 代替标签匹配：en、en-GB、en-US 的地区规则可能不同，扩展和脚本也会使简单字符串前缀失去语义。对格式化器可以使用 Intl 的 locale negotiation；对应用翻译资源则按产品定义的支持矩阵处理。

方向信息不能只靠字符串判断

部分运行时提供 locale.textInfo.direction，可以帮助判断文字方向：

JavaScript
const locale = new Intl.Locale('ar-EG');
const direction = locale.textInfo?.direction ?? 'ltr';
document.documentElement.dir = direction;

能力检测是必要的，因为较新的 Locale 信息在旧浏览器或部分 WebView 中可能不存在。方向设置还要和 HTML 的 lang、局部 dir、CSS 逻辑属性、图标方向和混合数字文本一起设计；仅把 dir 改成 rtl 不能保证表单、弹窗和自定义组件正确布局。

语言标签的方向是默认提示，不一定代表每一段用户内容的实际方向。用户输入的阿拉伯文姓名、英文 URL 和数字可能混在同一行，需要使用适当的 Unicode 双向文本处理和局部方向标记。不能因为页面 locale 是 RTL，就把所有字符串都强制套成 RTL。

扩展键不是任意配置对象

语言标签可以包含 Unicode 扩展，例如日历、数字系统和小时周期：

JavaScript
const locale = new Intl.Locale('th-TH-u-nu-thai-ca-buddhist');

console.log(locale.numberingSystem); // thai
console.log(locale.calendar);        // buddhist

这些扩展可以影响 Intl.DateTimeFormat 或 Intl.NumberFormat 的默认行为，但应用仍可通过 formatter options 显式指定设置。不能把扩展键当成任意业务参数塞进 locale；无效或不支持的扩展可能被忽略、规范化或产生不同结果。权限、租户、货币和产品实验开关应使用独立字段。

如果产品允许用户选择数字系统或日历，要保存经过允许列表验证的配置，并在所有格式化器中使用同一套约定。不要因为字符串中包含 u-ca-...，就认为所有日期组件、服务端和导出文件都会自动采用同样的日历。

SSR、缓存和安全边界

Locale 解析不等于可信身份信息。Accept-Language、navigator.languages 和 URL 中的 locale 都可能被用户修改，不能用来决定权限、租户、价格或法律地区。服务端应验证用户选择，敏感业务使用账号和服务器配置确定。

SSR 时服务端和客户端应使用同一个已确定的 locale。服务端根据请求头得到 en-US，客户端又根据浏览器设置选择 zh-CN，会造成首屏翻译和格式化结果不一致。把 locale 作为明确的请求上下文传入渲染和 hydration，而不是依赖各自的机器默认环境。

缓存页面或 API 时，locale 可能是响应变化的输入，需要正确的缓存键或 Vary: Accept-Language 策略；公开页面和用户私有语言偏好不能错误共享。显示名称、日期和数字格式化结果也不应混入用户身份无关的共享缓存而泄露偏好信息。

兼容性和验收

Intl.Locale 在现代浏览器和 Node.js 中普遍可用，但属性、方法和 ICU 数据的支持程度可能不同。使用前应按目标环境查兼容性，并对 textInfo、扩展属性和 maximize() 结果做能力检测。基础标签可以用 Intl.getCanonicalLocales 或受审校的解析库降级，但不要写一个只按连字符切分的伪解析器来处理所有 BCP 47 语法。

验收至少包括：

  • language、script、region、扩展和非法标签；
  • 用户偏好与应用支持列表的回退顺序；
  • SSR、水合、语言切换和缓存键；
  • RTL 方向、混合文本、数字系统和日历扩展；
  • locale 改变时显示名称、日期、数字和排序是否一起更新；
  • 不支持新属性的旧 WebView 是否仍能显示、提交和保存稳定语言代码。

Intl.Locale 的价值是把语言标签从一根难以解释的字符串变成可检查的结构。它帮助应用区分语言、脚本、地区和扩展，但不会替代翻译资源、时间处理、资源匹配或权限模型。把 locale 当作展示和格式化上下文，把业务身份和时区单独建模，后续扩展才不会互相污染。
