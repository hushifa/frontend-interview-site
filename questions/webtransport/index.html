WebTransport 和 WebSocket 怎样选择？

WebTransport 基于 HTTP/3 和 QUIC，支持多条独立的双向流和不可靠的数据报，没有队头阻塞；WebSocket 基于 TCP，只有一条有序可靠的消息通道，但服务端支持更广泛。MDN 标为 Baseline 2026。

参考答案

简答

  • WebSocket：一条 TCP 连接上的有序、可靠消息流，一个消息丢包重传时后面的消息都要等。
  • WebTransport：基于 HTTP/3（QUIC），可以打开多条互不阻塞的流，还能发送不保证到达的数据报（datagram）。
  • 适合 WebTransport 的场景：游戏状态同步、实时音视频控制、大量并发的小请求，最新数据比旧数据更重要。
  • WebSocket 仍是更通用的选择：服务端、代理和负载均衡器普遍支持，基于 TCP 的网络环境更容易连通。
  • MDN 标为 Baseline 2026（2026 年 3 月起主流浏览器可用），服务端需要支持 HTTP/3。

对比

WebSocketWebTransport
传输层TCPQUIC（UDP）

示例

JavaScript
const transport = new WebTransport('https://game.example.com:4433/session');
await transport.ready;

// createWritable() 是现行标准；datagrams.writable 已弃用，只作回退
const datagrams =
  typeof transport.datagrams.createWritable === 'function'
    ? transport.datagrams.createWritable()
    : transport.datagrams.writable;
const writer = datagrams.getWriter();
setInterval(() => {
  writer.write(encodePosition(player));
}, 50);

const stream = await transport.createBidirectionalStream();
const chatWriter = stream.writable.getWriter();
await chatWriter.write(new TextEncoder().encode('hello'));

transport.closed
  .then(() => showOffline())
  .catch(() => reconnect());
  • 位置信息用数据报发送，丢一帧也没关系，下一帧就会覆盖。
  • 聊天消息必须送达，用可靠的流。
  • 每条流独立，一条流丢包不影响其他流。

落地注意

  • 部分企业网络会封锁 UDP，需要准备 WebSocket 作为回退。
  • 检测支持：'WebTransport' in globalThis。
  • 数据报大小受路径 MTU 限制，可以读取 transport.datagrams.maxDatagramSize。
  • WebSocket 的流式接口见《WebSocketStream 怎样处理消息类型与关闭生命周期？》。
