WebTransport 和 WebSocket 怎样选择？

WebSocket 是一条可靠有序的通道，一条消息卡住后面都要等；WebTransport 基于 HTTP/3，能开多条互不影响的流，还能发不保证送达的数据报，但服务端支持还少。MDN 标为 Baseline 2026。

参考答案

简答

WebSocket 是一条 TCP 连接上的有序、可靠消息流。可靠的代价是，一条消息丢包要重传，后面的消息就都得等着，这叫队头阻塞。

WebTransport 基于 HTTP/3，也就是 QUIC 协议。它能开多条互不阻塞的流，一条流丢包不影响别的流；还能发数据报（datagram），不保证送达，丢了就丢了。

所以它适合“最新的数据比旧数据重要”的场景，比如游戏状态同步、实时音视频的控制信号、大量并发的小请求。

但 WebSocket 仍然更通用。服务端、代理和负载均衡器基本都支持它，基于 TCP 的网络也更容易连通。WebTransport 在 MDN 上标为 Baseline 2026（2026 年 3 月起主流浏览器可用），服务端要支持 HTTP/3，有些企业网络还会封 UDP，所以要准备 WebSocket 作为回退。

两者对比

WebSocketWebTransport
传输层TCPQUIC（UDP）
通道一条有序消息流多条独立流 + 数据报
可靠性可靠流可靠，数据报不可靠
背压无，需要自己看 bufferedAmount基于 Streams，自带背压
服务端支持广泛需要 HTTP/3，生态较新

背压是指接收方处理不过来时，让发送方慢下来。WebSocket 没有这个机制，发得太快数据会在浏览器里堆积，要自己看 bufferedAmount 控制。WebTransport 的读写都是 Streams，写入时会自动等待。

一个游戏连接的例子

下面用数据报发玩家位置，用可靠的流发聊天消息。

JavaScript
const transport = new WebTransport('https://game.example.com:4433/session');
await transport.ready;

// createWritable() 是现行标准；datagrams.writable 已弃用，只作回退
const datagrams =
  typeof transport.datagrams.createWritable === 'function'
    ? transport.datagrams.createWritable()
    : transport.datagrams.writable;
const writer = datagrams.getWriter();
setInterval(() => {
  writer.write(encodePosition(player));
}, 50);

const stream = await transport.createBidirectionalStream();
const chatWriter = stream.writable.getWriter();
await chatWriter.write(new TextEncoder().encode('hello'));

transport.closed
  .then(() => showOffline())
  .catch(() => reconnect());

为什么位置用数据报？位置每 50 毫秒发一次，丢一帧没关系，下一帧马上就覆盖了。如果用可靠传输，丢的那一帧要重传，后面的新位置反而被它堵住。

聊天消息必须送到，所以用可靠的流。而且每条流是独立的，聊天流丢包也不会影响其他流。

transport.closed 正常关闭时 resolve，异常断开时 reject，所以可以分别显示“已离线”和尝试重连。

落地时要注意什么

部分企业网络会封锁 UDP，WebTransport 连不上，所以要准备 WebSocket 作为回退。检测浏览器是否支持，用 'WebTransport' in globalThis。

数据报的大小受网络路径的 MTU 限制，单个数据报不能太大，可以读 transport.datagrams.maxDatagramSize 看上限。

WebSocket 的流式接口见《WebSocketStream 怎样处理消息类型与关闭生命周期？》。

常见追问

什么是队头阻塞？

在一条有序的通道里，前面的消息丢包重传时，后面已经到达的消息也不能先交给应用，只能排队等着。WebSocket 跑在 TCP 上就有这个问题。WebTransport 的多条流互相独立，一条卡住不影响其他流。

新项目要不要直接用 WebTransport？

看场景。普通的聊天、通知推送，WebSocket 足够，而且部署简单。只有在很在意延迟、能接受丢数据的场景，比如游戏，才值得上 WebTransport，同时还要保留 WebSocket 回退。
