WebTransport 和 WebSocket 怎样选择？

对比 WebTransport 的多路复用、可靠与不可靠传输和 WebSocket 的成熟性，理解协议与部署边界。

参考答案

WebSocket 提供成熟的双向消息通道，适合聊天、通知、协作等常见业务。WebTransport 面向浏览器与服务器的更细粒度传输，常见部署基于 HTTP/3，提供多条可靠流与不可靠数据报。

这里最重要的区别是：stream 提供可靠有序的字节传输，datagram 不保证可靠送达或顺序。不能把数据报当成另一种必达消息通道。

按消息语义选择传输方式

业务数据常见需求可能的选择
聊天消息、操作确认不能随意丢失，需要应用确认WebSocket 或可靠 stream，并补业务协议
大文件与多个独立任务每个任务内部有序，彼此不必共用一条队列WebTransport 多条 stream
高频实时位置快照新状态能替代旧状态，过期数据价值低在业务允许时使用 datagram

即使底层流可靠，服务端崩溃、权限过期或应用处理失败仍可能发生。发送完成不等于数据库事务已经提交，业务确认、幂等和重连恢复依然需要自己设计。

多路流避免部分跨流等待，但不是无限并行

WebSocket 应用通常在一个有序连接中交错发送消息，大数据可能影响后续小消息及时到达。应用可以做分片与调度，但仍受其传输模型限制。

WebTransport 可以建立单向或双向流，各流内部有序，不要求不同流之间全局有序。基于 QUIC 的独立流能减少丢包重传造成的跨流队头阻塞，但仍共享连接拥塞控制、链路带宽和设备资源。

因此不能说“一个流慢了绝对不影响其他流”，也不能无限创建流来回避背压。服务器可接受的流数量、应用队列和内存都要有边界。

stream 不自带业务消息边界

WebSocket 提供消息事件；WebTransport 可靠流更接近字节流，一次 read 不保证对应一次 write。需要长度前缀、分隔协议或其他明确 framing，处理半包、多包和最大消息长度。

使用 getWriter 写入时应等待适当背压信号与写入结果，并在结束后关闭或中止、释放锁。对端取消某条流和整个会话关闭也要分别处理。

datagram 保留数据报单位，但受最大尺寸等限制，也可能丢失或乱序。实时状态通常需要序号或时间信息丢弃旧包；如果在应用层给所有数据报都补可靠重传，可能已经偏离选择不可靠传输的初衷。

会话建立与业务登录不是一回事

WebTransport 构造后要等待 ready，closed 用于观察会话结束或失败。请求被接受不代表应用层身份验证完成，服务端仍需检查来源和认证方案。

它不能直接连接普通 WebSocket 服务，也不是一个任意 UDP socket。服务端、TLS、协议实现和代理链必须支持相应路径，某些网络对 UDP/HTTP3 的限制也会影响可用性。

不要把长期凭据随意放进 URL，因为可能进入日志。应设计适合协议和部署环境的认证、短期授权及凭据更新方式，并在断线后重新确认权限。

为什么很多项目仍应选择 WebSocket

WebSocket 生态成熟，浏览器与基础设施覆盖广，普通消息业务通常更容易实现、监控和排障。原生 WebSocket 缺少与 Streams 相同的背压接口，应用仍需控制发送量并观察 bufferedAmount，而不是无限 send。

只有确实需要多路独立流、可丢弃数据报或相应传输特性时，WebTransport 的额外复杂度才更可能值得。性能比较应包含服务部署、握手、消息大小、网络条件和浏览器覆盖，而不是只比较理想环境下的一次延迟。

降级也不只是换一个构造函数。若原协议依赖不可靠快照或多个独立流，退回 WebSocket 时需要重新设计排队、丢弃过期状态和消息封装，确保语义仍正确。

两者都不提供完整的实时音视频协商与媒体传输栈；需要摄像头通话、网络自适应等能力时，还应评估 WebRTC，而不是只因名字里有 Transport 就自行重建全部媒体系统。
