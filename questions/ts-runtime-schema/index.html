为什么 TypeScript 不能替代接口数据校验？

静态类型约束已知代码之间的使用关系，接口响应等外部值仍需要运行时解析。校验应同时处理结构、业务约束和转换策略，成功后再向内部代码提供可信类型，并明确失败与诊断方式。

参考答案

后端字段改名、缓存里留着旧版本数据、第三方接口偶尔返回错误结构，都发生在 TypeScript 编译之外。即使前端声明了 User，服务器也不会因为看见这个类型名字，就自动返回符合它的对象。

类型检查可以保证项目内正常受检查的调用关系，不能替你验证网络、存储、URL 参数或其他外部输入的实际内容。

as User 并没有检查任何字段

TypeScript
type User = {
  id: string;
  name: string;
  role: 'reader' | 'editor';
};

function readUnchecked(json: string): string {
  const user = JSON.parse(json) as User;
  return user.name.toUpperCase();
}

JSON.parse 只解析 JSON 语法。输入可以是数字、null、数组，或者 name 为数字的对象。as User 不会生成验证逻辑，后面的 toUpperCase 仍然可能在运行时失败。

给请求封装写 get() 也是同样的问题：如果内部只是把结果断言成 T，类型参数表达的是调用者的预期，不是一次已经发生的校验。

先把边界输入当 unknown，再明确建立 User

下面的解析器按记录字段检查输入的类型和允许值，去掉姓名两侧空白，并创建只含白名单字段的新对象：

TypeScript
type ParseResult<T> =
  | { ok: true; value: T }
  | { ok: false; issues: string[] };

function isRecord(value: unknown): value is Record<string, unknown> {
  return typeof value === 'object' && value !== null && !Array.isArray(value);
}

function parseUser(input: unknown): ParseResult<User> {
  if (!isRecord(input)) {
    return { ok: false, issues: ['用户数据必须是对象'] };
  }
  if (!Object.hasOwn(input, 'id') || typeof input.id !== 'string' ||
      !/^user_[0-9]+$/.test(input.id)) {
    return { ok: false, issues: ['id 必须符合 user_数字 的格式'] };
  }
  if (!Object.hasOwn(input, 'name') || typeof input.name !== 'string' ||
      input.name.trim() === '') {
    return { ok: false, issues: ['name 必须是非空字符串'] };
  }
  if (!Object.hasOwn(input, 'role') ||
      (input.role !== 'reader' && input.role !== 'editor')) {
    return { ok: false, issues: ['role 不在允许范围内'] };
  }

  return {
    ok: true,
    value: { id: input.id, name: input.name.trim(), role: input.role },
  };
}

const raw: unknown = JSON.parse(
  '{"id":"user_1","name":" Lin ","role":"reader","extra":true}',
);
const parsed = parseUser(raw);
if (parsed.ok) console.log(JSON.stringify(parsed.value));
// 输出：{"id":"user_1","name":"Lin","role":"reader"}

返回联合明确区分成功值与失败信息，内部组件拿到 ok:true 后可以按 User 使用。新对象只复制 id、name、role，才真正做到忽略未声明字段，而不是通过 Omit 或断言让它们在类型提示里消失。

这里会拒绝数组与缺失的自身字段，但没有承诺验证任意宿主对象的所有原型或访问器行为。示例面向 JSON 等普通数据边界；若输入本身是能够执行 getter、Proxy trap 的不受控对象，还要另外分析访问行为。

规则中的 user_数字、非空姓名和角色枚举是本例的业务约定。实际接口还可能需要长度限制、版本字段、跨字段关系与更细的错误路径，应由真实契约决定。

网络成功、JSON 解析成功、数据合法是三步

沿用上面的 parseUser，可以在请求边界分别处理这些阶段：

TypeScript
async function loadUser(
  url: string,
  options: Pick<RequestInit, 'signal'> = {},
): Promise<User> {
  const response = await fetch(url, options);
  if (!response.ok) throw new Error(`用户请求返回 HTTP ${response.status}`);

  const input: unknown = await response.json();
  const result = parseUser(input);
  if (!result.ok) {
    throw new Error(`用户数据不符合契约：${result.issues.join('；')}`);
  }
  return result.value;
}

fetch 返回 HTTP 错误响应时不一定拒绝，response.json 也可能因为内容不是有效 JSON 而失败。两步成功后，还需要结构校验。不能把所有问题都归为“接口没返回”或“TypeScript 类型不对”。

真正使用时，调用方还要区分取消、网络故障与契约错误，并决定提示、重试或降级。把不合法结构统一转成空列表，可能会让用户误以为数据确实为空。

结构复杂时，让 schema 成为统一来源

手写守卫适合小而稳定的结构。大量嵌套对象、联合分支、数组和错误路径，可以交给 Zod、Valibot 等适合项目的运行时 schema 工具，并从 schema 推导静态类型，减少两份契约手工同步。

使用库也要确认具体规则：额外字段是拒绝、保留还是剥离？字符串数字是否允许转换？缺失时是否填默认值？转换前的输入类型与转换后的输出类型是否相同？这些都会影响 API 语义，不能只看 parse 没抛错。

强制转换尤其需要谨慎。例如把任意非空字符串转换成布尔值，并不自然等于用户输入的 'false' 应被理解为 false。默认值也可能掩盖后端意外漏字段，必须有明确的兼容策略。

只在不可信边界重复验证必要内容

网络响应、localStorage 恢复、跨窗口消息和用户输入是常见边界。经过解析后，可以让内部函数依靠清楚的类型契约流转，避免每个组件再写一份互不一致的校验逻辑。

但如果内部代码仍会通过可变引用任意修改对象，原本通过的约束也可能被破坏。是否需要只读接口、复制、受控更新或重新验证，要根据对象生命周期决定，不能把一次解析当成永久不变的认证标记。

持久化数据还要考虑版本迁移。旧数据符合旧结构、不符合新结构时，应明确升级、重置或提示，而不是靠断言让它继续冒充新版模型。

校验通过不等于有权限执行操作

字段合法不代表用户拥有对应资源，也不代表字符串里的链接、文件或 HTML 内容在任何使用位置都安全。不同使用场景仍需要授权、编码或相应安全规则。

前端校验主要帮助尽早发现契约问题并改善交互，服务端仍需验证请求。记录错误时可以保留字段路径、版本和必要的诊断码，避免直接把敏感原始数据全部上传。清楚的边界解析，才会让静态类型在后续代码里成为有依据的保证。
