为什么 TypeScript 不能替代接口数据校验？

TypeScript 的类型编译后就被删掉了，接口返回的数据长什么样，它根本看不到，as User 只是一句声明。所以外部数据进来时要当作 unknown，用 schema 或手写函数真正检查一遍。

参考答案

简答

TypeScript 的类型只在编译时存在，编译完就删掉了。后端改了字段、本地缓存里存着旧格式、第三方接口出了异常，这些都发生在运行时，编译器看不到。

所以 JSON.parse(text) as User、fetch<User>() 这种写法不会生成任何校验代码，只是你在告诉编译器“相信我”。数据真不对时，程序往往在很深的地方才崩，很难排查。

正确做法是在信任边界，也就是数据从外面进来的地方，先把它当作 unknown，用 Zod、Valibot 这类 schema 库或手写函数解析，解析通过了，内部代码再依赖类型。类型最好从 schema 推导出来，比如 z.infer<typeof User>，避免类型和校验规则各写一遍、慢慢对不上。

网络请求要分三步检查：HTTP 状态码、JSON 语法、数据结构。前端校验也不能代替服务端校验。

as 只是声明，不是检查

TypeScript
type User = { id: string; name: string; role: 'reader' | 'editor' };

function readUnchecked(json: string): string {
  const user = JSON.parse(json) as User;
  return user.name.toUpperCase(); // name 是数字或缺失时运行时报错
}

这段代码编译完全通过。可要是接口返回的 name 是个数字，或者根本没有 name，运行时就会报“toUpperCase 不是函数”或者“读取 undefined 的属性”。原因是 as User 编译后什么都不剩，它没有检查 json 里到底是什么。

手写一个解析函数

TypeScript
type ParseResult<T> = { ok: true; value: T } | { ok: false; issues: string[] };

function isRecord(value: unknown): value is Record<string, unknown> {
  return typeof value === 'object' && value !== null && !Array.isArray(value);
}

function parseUser(input: unknown): ParseResult<User> {
  if (!isRecord(input)) return { ok: false, issues: ['必须是对象'] };
  const { id, name, role } = input;
  if (typeof id !== 'string') return { ok: false, issues: ['id 必须是字符串'] };
  if (typeof name !== 'string' || !name.trim()) return { ok: false, issues: ['name 不能为空'] };
  if (role !== 'reader' && role !== 'editor') return { ok: false, issues: ['role 不合法'] };
  return { ok: true, value: { id, name: name.trim(), role } };
}

参数是 unknown，所以每个字段都得先检查才能用，编译器逼着你把校验写全。每通过一个 if，对应变量的类型就被收窄一步，最后返回的对象才真正符合 User。

还要注意最后一行是新建对象，只复制了 id、name、role。接口多返回的字段不会混进内部状态，这比直接返回 input 更安全。

用 schema 库

字段一多，手写就很繁琐。schema 库让你只描述一次结构，同时得到校验和类型：

TypeScript
import { z } from 'zod';

const User = z.object({
  id: z.string(),
  name: z.string().trim().min(1),
  role: z.enum(['reader', 'editor']),
});
type User = z.infer<typeof User>;

async function loadUser(url: string, signal?: AbortSignal): Promise<User> {
  const response = await fetch(url, { signal: signal ?? null });
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  const result = User.safeParse(await response.json());
  if (!result.success) throw new Error('用户数据不符合契约', { cause: result.error });
  return result.data;
}

User 这个 schema 既用来运行时校验，又通过 z.infer 推出类型，两者不会写成两套。loadUser 正好对应三步检查：response.ok 看状态码，response.json() 解析 JSON 语法，safeParse 校验结构。

选库或配 schema 时要想清楚几件事：多出来的字段是拒绝、保留还是去掉（Zod 的 object 默认去掉）；'1' 这种字符串要不要自动转成数字；缺失的字段要不要填默认值。

哪些地方需要校验

凡是数据从程序外面进来的地方都要校验：接口响应、WebSocket 消息、postMessage 收到的数据；从 localStorage、IndexedDB 里恢复的数据，旧版本存的格式还要做迁移；URL 查询参数和表单输入。

内部函数之间互相调用，不必每层都重复校验。另外前端校验是为了尽早发现问题、改善交互，服务端仍要独立校验。字段格式合法，也不代表用户有权限做这件事。

常见追问

能不能根据 TS 类型自动生成校验代码？

类型运行时不存在，没法直接拿来校验。常见做法是反过来，从 schema 推导类型；或者用 typia 这类编译插件，在编译时根据类型生成校验代码。

校验失败了怎么处理？

记录出错的字段路径和接口版本，方便排查；给用户显示一个可恢复的错误。不要悄悄返回空数据，那样问题会被藏起来。
