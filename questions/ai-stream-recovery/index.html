AI 流式输出断线后，怎样恢复同一条生成任务？

服务端要把每次生成存成一个可以查询的"运行"，每条事件带递增序号。客户端记下最后处理到第几条，重连时带上这个位置让服务端补发，并自己去重。恢复不了时，让用户自己选择要不要重新生成。

参考答案

简答

能恢复的前提是服务端把每次生成存成一个“运行”，英文叫 run。它有 ID、有状态，还按序号保存了每一条事件。

客户端记住自己最后处理到第几条事件，重连时把这个序号带上，服务端只补发后面的。客户端按“运行 ID 加序号”去重，而且序号必须连续，中间缺了就停下来，去拉一份完整快照。

要分清恢复和重新生成。日志过期了或者运行失败了，就显示已经收到的部分，让用户自己选要不要重新生成，不要自动重发，因为那会生成一个不一样的回答，还要再花一次钱。

最后保存消息时，用运行 ID 做幂等写入，这样就算完成事件重复到达，也不会存出两条消息。

服务端要保存什么

一次生成在服务端大概是这样存的：

text
runId = run_123
1 message-start
2 text-delta "你"
3 text-delta "好"
4 message-complete

事件日志保留一段时间，比如几分钟到几小时，过期以后这个运行就标成“不可恢复”。运行 ID 要做成别人猜不到的，而且每次查询都要校验它是不是属于当前用户。

重连时怎么请求

假设客户端已经处理到第 3 条，重连时这样请求：

http
GET /api/runs/run_123/events?after=3
Accept: text/event-stream

服务端补发序号大于 3 的事件。如果断线期间运行已经结束了，补发完剩下的事件就关闭连接；如果日志已经过期，就返回当前状态，有最终消息的话也一起返回。

SSE 本来有个 Last-Event-ID 请求头，可以用来传这个位置。但它只是个请求头，只有服务端真的保存了事件、并且按 ID 补发，它才有用。另外，用 fetch 实现 SSE 时，浏览器不会自动带这个头，要自己加。

客户端怎么处理收到的事件

下面这个函数接收当前状态和一条事件，返回新状态。注意前面三行判断，它们处理的是重复、乱序和缺口：

JavaScript
function applyEvent(state, event) {
  if (state.status !== 'streaming' || event.runId !== state.runId) return state;
  if (event.seq <= state.lastSeq) return state; // 重复事件
  if (event.seq !== state.lastSeq + 1) return { ...state, status: 'gap' };

  switch (event.type) {
    case 'text-delta':
      return { ...state, text: state.text + event.delta, lastSeq: event.seq };
    case 'message-complete':
      return { ...state, status: 'completed', lastSeq: event.seq };
    default:
      return { ...state, lastSeq: event.seq }; // 本例不渲染的事件只推进游标
  }
}

为什么按序号去重，而不是看文字内容一样不一样？因为模型完全可能合法地连续输出两段一样的文字，比如两个“好”。按内容去重会把正常内容删掉。

这里的序号是我们应用自己定义的连续整数。SSE 规范里事件的 id 是字符串，没有“必须连续”的保证，所以要在协议适配那一层转成整数序号。

出现 gap，说明中间漏了事件。这时候要关闭连接，拉一份运行快照，里面有已经累积的文字和最新序号，然后从快照的位置重新订阅。

如果要把序号存进 IndexedDB，一定要和对应的文字一起存。只存了序号、没存文字，刷新以后会从那个序号往后补，中间那段文字就永远丢了。

界面上怎么显示

情况界面
正在重连保留已有文字，显示“连接中断，正在恢复”
恢复成功继续追加，无需用户操作
运行已完成直接显示最终消息
日志过期或运行失败保留部分文字并标注“未完成”，提供“重新生成”按钮

用户点了重新生成，就会创建一个新的运行，消息记录里要记下新旧运行之间的关系。

重连要用指数退避，就是每次失败后等待的时间翻倍。不然服务端一恢复，大量客户端同时涌进来，又把它压垮了。

常见追问

只把已经收到的文字发给服务端，让它“接着写”行不行？

不行。那其实是一次新的生成，接出来的内容可能和原来的思路对不上，而且又要计费一次。

用户取消怎么记录？

取消请求针对的是运行 ID。服务端收到后写一条终止事件，这样其他标签页恢复这个运行时，也能看到“已停止”。
