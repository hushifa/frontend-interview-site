OpenID Connect 和 OAuth 2.0 分别解决什么问题？

OAuth 2.0 解决的是让第三方应用替用户访问资源，access token 是给 API 用的；OIDC 在它上面加了登录，用 ID Token 告诉应用是谁登录了。应用要校验 ID Token，并用 iss 加 sub 认人。

参考答案

简答

OAuth 2.0 解决的是授权。比如用户允许一个打印网站读取自己网盘里的照片，打印网站拿到 access token，用它调用网盘的 API。可是 OAuth 规范没有定义“用户是谁”，所以客户端不应该从 access token 推断谁登录了。

OIDC 在 OAuth 之上加了认证，也就是“谁登录了”。请求里带上 scope=openid，授权服务器除了 access token，还会额外返回一个 ID Token。它是一个 JWT，里面写的是用户的身份信息。

两个令牌给不同的人看。ID Token 给客户端看，access token 给资源服务器用，不要把 ID Token 当成调用 API 的凭证。

客户端拿到 ID Token 要校验：签名用发现文档里的 JWKS 验证，iss 是预期的发行方，aud 包含自己的 client_id，exp 没过期，nonce 和请求时一致。关联本地账号用 iss 加 sub，email 可能会变，也可能没验证过，不能当唯一标识。

在授权码流程里怎么用

和普通 OAuth 授权码流程比，请求里多了 openid 这个 scope 和一个 nonce：

text
/authorize?response_type=code
  &client_id=shop
  &redirect_uri=https://shop.example/callback
  &scope=openid profile email
  &state=随机值
  &nonce=随机值
  &code_challenge=...&code_challenge_method=S256

用授权码换令牌后，响应里多了一个 id_token：

json
{
  "access_token": "...",
  "id_token": "eyJhbGciOiJSUzI1NiIs...",
  "token_type": "Bearer",
  "expires_in": 3600
}

把 ID Token 解码，载荷大概是这样：

json
{
  "iss": "https://id.example",
  "sub": "248289761001",
  "aud": "shop",
  "exp": 1793000000,
  "iat": 1792996400,
  "nonce": "随机值",
  "email": "user@example.com",
  "email_verified": true
}

每个字段都对应一项校验。iss 说明是谁签发的，aud 说明是发给谁的，exp 是过期时间，nonce 用来确认它属于这一次登录。为什么用 iss 加 sub 认人？因为 sub 只保证在同一个发行方内唯一，换了发行方可能重复，所以两个要一起用。

几个容易混淆的东西

概念用途
state防止回调被伪造（CSRF），客户端自己比较
nonce绑定 ID Token 和本次登录请求，防重放
PKCE防止授权码被截获后兑换，见《OAuth 2.0 的 PKCE 解决了什么问题？》
UserInfo 端点用 access token 获取更多用户信息
发现文档/.well-known/openid-configuration，列出端点和 JWKS 地址

state 和 nonce 最容易搞混。state 是在回调时比对的，确认这次回调是自己发起的；nonce 是写进 ID Token 里的，确认这个令牌是这次登录拿到的，不是别人重放的旧令牌。

拿到 ID Token 之后

拿到 ID Token，只说明身份提供方认证了这个用户。应用还要创建自己的会话，通常是一个 HttpOnly Cookie，并处理过期、登出和账号关联。单页应用推荐通过 BFF 在服务端完成兑换和校验，浏览器不直接持有令牌。

常见追问

能在前端校验 ID Token 吗？

可以在前端解码，拿来显示用户名之类。可是决定权限的校验要放在服务端，前端的判断用户可以改。

社交登录都是 OIDC 吗？

主流的身份提供方大多支持 OIDC。也有一些只提供 OAuth 加自定义的用户信息接口，需要按各自的文档处理。
