OpenID Connect 和 OAuth 2.0 分别解决什么问题？

OAuth 2.0 解决"授权第三方应用访问资源"，access token 是给 API 用的；OIDC 在 OAuth 之上增加身份认证，通过 ID Token 告诉客户端"谁登录了"。客户端要校验 ID Token 的签名、iss、aud、exp 和 nonce，并用 iss 加 sub 识别用户。

参考答案

简答

  • OAuth 2.0：用户授权客户端访问资源，客户端拿到 access token 调用 API。规范没有定义"用户是谁"，客户端不应从 access token 推断登录身份。
  • OIDC：请求中带 scope=openid，授权服务器额外返回 ID Token（JWT），内容是身份声明。
  • ID Token 给客户端看，access token 给资源服务器用，不要把 ID Token 当作调用 API 的凭证。
  • 校验 ID Token：签名（用发现文档中的 JWKS）、iss 是预期的发行方、aud 包含自己的 client_id、exp 未过期、nonce 与请求时一致。
  • 用 iss 和 sub 的组合关联本地账号，email 可能变化或未验证，不能作为唯一标识。

授权码流程中的 OIDC

text
/authorize?response_type=code
  &client_id=shop
  &redirect_uri=https://shop.example/callback
  &scope=openid profile email
  &state=随机值
  &nonce=随机值
  &code_challenge=...&code_challenge_method=S256

换令牌后得到：

json
{
  "access_token": "...",
  "id_token": "eyJhbGciOiJSUzI1NiIs...",
  "token_type": "Bearer",
  "expires_in": 3600
}

ID Token 的载荷示例：

json
{
  "iss": "https://id.example",
  "sub": "248289761001",
  "aud": "shop",
  "exp": 1793000000,
  "iat": 1792996400,
  "nonce": "随机值",
  "email": "user@example.com",
  "email_verified": true
}

几个容易混淆的点

概念用途
state防止回调被伪造（CSRF），客户端自己比较
nonce绑定 ID Token 和本次登录请求，防重放
PKCE防止授权码被截获后兑换，见《OAuth 2.0 的 PKCE 解决了什么问题？》
UserInfo 端点用 access token 获取更多用户信息
发现文档/.well-known/openid-configuration，列出端点和 JWKS 地址

登录之后

拿到 ID Token 只说明身份提供方认证了用户。应用还需要创建自己的会话（通常是 HttpOnly Cookie），并处理过期、登出和账号关联。单页应用推荐通过 BFF 在服务端完成兑换和校验，浏览器不直接持有令牌。

常见追问

  • 能在前端校验 ID Token 吗？可以做展示用途的解码，但决定权限的校验应在服务端。
  • 社交登录都是 OIDC 吗？主流身份提供方大多支持 OIDC，部分只提供 OAuth 加自定义的用户信息接口，需要按各自文档处理。
