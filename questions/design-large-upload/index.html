大文件上传系统怎样设计秒传、服务端合并、存储和限流？

以服务端的上传会话为准：用完整文件哈希做秒传判断，秒传只给当前用户新建引用，敏感场景要求持有证明；分片按序号存储，全部到齐后由服务端合并并校验大小和哈希；分片可放临时存储或对象存储的分片上传接口，未完成的会话按过期时间清理；客户端用并发池限制同时上传的分片数，服务端用 429 和 Retry-After 限流。

参考答案

简答

大文件上传要拆成几个部分来设计：怎样标识一个上传任务、怎样判断能不能秒传、分片存在哪里、什么时候合并、怎样限制并发。浏览器端怎样暂停、续传、显示进度和重试，见《浏览器分片上传如何实现可靠的暂停与续传？》，这道题讲整体系统。

上传任务以服务端的会话为准，记下文件哈希、大小、分片大小和已收到的分片序号。上传前先拿哈希问服务端：已有完整文件就秒传，已有部分分片就只传缺的。算哈希要读完整个文件，crypto.subtle.digest 不支持流式输入，所以大文件通常放到 Web Worker 里，用支持增量计算的库来算。

分片按序号存进临时存储，全部到齐后客户端调用合并接口，服务端按序号拼接，再校验总大小和整体哈希。没完成的会话设过期时间，到期删除分片。并发两头都要管：客户端用固定大小的任务池，同时传 3 到 6 片；服务端超过限额时返回 429，可以带 Retry-After 告诉客户端多久后再试。

要特别注意秒传的安全问题。服务端拿到的只是一个哈希，证明不了客户端真的有这个文件。所以秒传只能给当前用户新建一条引用，必要时让客户端回传服务端随机指定的一段内容。抽样哈希不能拿来判定秒传。

整体流程是怎样的

  1. 选好文件后，在 Worker 里计算文件哈希。
  2. 调用“检查”接口，传上哈希、文件名和大小。返回“已存在”就是秒传，直接结束；否则创建或找回上传会话，返回已经上传过的分片序号列表。
  3. 跳过已有的分片，其余分片放进并发池上传。每个请求带上会话 ID、分片序号，还可以带分片自己的哈希，服务端收到后先校验再落盘。
  4. 全部成功后调用“合并”接口，服务端把分片拼起来并校验，返回最终的文件地址。

分片状态以服务端记录为准。所以刷新页面以后，用户重新选同一个文件，算出同一个哈希，就能接着传。

怎样切分片

JavaScript
const CHUNK_SIZE = 5 * 1024 * 1024;

function createChunks(file) {
  const chunks = [];
  for (let start = 0, index = 0; start < file.size; start += CHUNK_SIZE, index += 1) {
    chunks.push({ index, blob: file.slice(start, start + CHUNK_SIZE) });
  }
  return chunks;
}

每 5MB 切一片，最后一片可能不满 5MB。分片大小是个权衡：太小，请求数太多；太大，一片失败要重传很久。如果传到对象存储，它的分片上传接口通常有最小分片大小和最大分片数的限制，按所用服务的文档来定。

秒传有什么安全问题

算完整文件的哈希要把整个文件读一遍，几个 GB 的文件耗时很明显。于是有人用抽样哈希，只取头、尾和中间几段来算。它可以用来快速提示“这个文件可能传过”，但碰撞概率高，也容易被人故意构造，不能直接据此判定秒传成功。

更根本的问题是：只凭客户端交上来的哈希，服务端没法确认对方真有这个文件。如果谁知道某个文件的哈希，就可能用“秒传”把别人上传的私有文件变成自己的。常见的防护有这些。

秒传成功时，只给当前用户新建一条指向已有存储对象的引用，权限按当前用户算，不返回原上传者的文件地址或元数据。

敏感场景要求“持有证明”。服务端随机指定几个字节区间，客户端读出这些区间的内容或内容的哈希回传，服务端比对通过才算秒传。因为区间是随机的，只知道哈希的人答不上来。

最后，秒传判断只用完整文件的哈希。

并发池怎么写

下面这个函数同时最多运行 limit 个任务，结果按原来的顺序返回。先看它跑起来的效果：

JavaScript
async function runPool(tasks, limit) {
  const results = [];
  let next = 0;
  async function worker() {
    while (next < tasks.length) {
      const index = next++;
      results[index] = await tasks[index]();
    }
  }
  // 任一任务失败时 Promise.all 立即 reject，但其余 worker 仍会继续领取任务
  await Promise.all(Array.from({ length: Math.min(limit, tasks.length) }, worker));
  return results;
}

let running = 0;
let peak = 0;
const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms));
const tasks = [30, 10, 20, 10, 5].map((ms, i) => async () => {
  running += 1;
  peak = Math.max(peak, running);
  await sleep(ms);
  running -= 1;
  return i;
});

console.log(await runPool(tasks, 2)); // [ 0, 1, 2, 3, 4 ]
console.log(peak); // 2

五个任务耗时各不相同，完成的先后顺序是乱的，可结果数组还是 [0, 1, 2, 3, 4]，同时运行的任务最多 2 个。

为什么能做到？池子里开了 limit 个 worker，每个 worker 做完一个任务就马上去领下一个，所以同时在跑的任务永远不超过 limit。next++ 是同步执行的，两个 worker 不会领到同一个任务。结果按领到的序号 index 存放，跟谁先完成没关系。

实际上传时，每个任务里面再包一层重试，重试和暂停的写法见《浏览器分片上传如何实现可靠的暂停与续传？》。还要注意注释里写的问题：这个池子在某个任务失败后不会停，生产代码要加一个停止标志，让 worker 不再领新任务。

服务端怎样合并和存储

分片可以先存在服务端的临时目录或临时存储里，按“会话 ID 加序号”命名。分片乱序到达也没关系，合并时按序号拼接。合并前先确认分片数量齐全，合并后校验总大小和整体哈希，不一致就让客户端重传，校验通过才把文件移到正式存储，并把会话标记为完成。

合并接口要能重复调用。客户端调用合并后可能因为超时没收到响应，再调一次时，服务端发现会话已经完成，直接返回同一个文件地址，不要合并第二遍。

文件很大时，也可以不经过业务服务器，直接传到对象存储。业务服务器只负责管理会话、签发分片上传凭证，合并交给对象存储的分片上传接口完成，见《浏览器直传对象存储时，如何设计安全的分片上传？》。对象存储的分片上传接口通常有最小分片大小和最大分片数的限制，要按所用服务的文档来定。

最后是清理。很多上传会中途放弃，服务端给每个会话设过期时间，到期删除临时分片，否则存储会被半截的文件占满。

服务端怎样限流

客户端的并发池只能约束守规矩的客户端，服务端还要自己限流，比如限制每个用户同时进行的会话数和每秒接收的分片数。超过限额时返回 429 Too Many Requests。MDN 说明 429 表示客户端在给定时间内发送了太多请求，响应里可以带 Retry-After，表示要等多久再发下一个请求。客户端收到 429 后按 Retry-After 或指数退避等待，再重传这一片。

常见追问

为什么不一次性上传整个文件？

单个请求失败就得从头再来，而且很容易碰到网关对请求体大小和超时时间的限制。

能直接传到对象存储吗？

可以。由服务端签发分片上传凭证，前端直接传给对象存储，减轻业务服务器的带宽压力。
