渐进增强和优雅降级怎样影响前端方案选择？

从最低可用任务出发区分两种设计方向，说明静态内容、原生能力、特性检测与运行时失败的关系，并解释怎样避免增强层反而破坏基础功能。

参考答案

简答

  • 渐进增强从基础内容和核心任务开始逐步增加体验，优雅降级从完整体验出发提供替代。
  • 两者是出发点不同，实际项目可以同时采用。
  • 最低标准应对应用户任务，不能是一个永久加载的骨架屏。
  • 静态内容先让 HTML 本身有意义，再用 JavaScript 增强。

同一个页面可能运行在新浏览器、旧 WebView、弱网设备或脚本加载失败的环境中。方案选择不能只问“最好情况下有什么效果”，还要问“少了某项能力，用户还能完成什么”。

渐进增强从基础内容和核心任务开始，再给支持更多能力的环境增加体验。优雅降级通常从完整体验出发，为能力不足或失败的情况提供可接受替代。它们是设计出发点的区别，实际项目可以同时采用，重点是把基础可用性说清楚。

最低标准应该对应用户任务

内容网站的核心可能是阅读、目录导航和分享链接，动画、智能推荐和即时筛选可以作为增强。在线图形编辑器则可能确实依赖 JavaScript，不能要求没有脚本时仍提供完整编辑能力。

但“没有脚本就显示空白”也不是一个经过设计的最低标准。可以明确哪些环境支持编辑，已有内容是否能只读展示，用户的数据如何导出或恢复，以及缺少权限时怎样继续。

基础形态不必拥有全部功能，却应有清楚、可完成的任务，而不只是一个永久加载的骨架屏。

对静态内容，先让 HTML 本身有意义

一篇题解可以先在 HTML 中包含问题、答案和链接，再用 JavaScript 增强搜索、收藏和局部切换。脚本失败时，内容仍然可以阅读，普通链接也能导航。

例如一个简单的补充说明，可以使用原生结构：

HTML
<details>
  <summary>查看补充说明</summary>
  <p>闭包中的函数会继续通过词法环境访问相关绑定，并不是自动复制所有外部变量。</p>
</details>

在支持 details 的环境中，浏览器提供展开与收起等基础行为，不必等待自定义组件初始化后才能读取说明。若改用复杂展示，也应保留内容和语义，而不是让增强脚本成为唯一的数据来源。

服务端渲染或构建时预渲染可以帮助提供基础 HTML，但它们本身也不保证所有交互可用。还要检查禁用脚本、资源加载失败和客户端接管失败时的真实结果。

原生表单的增强有一个前提

常见例子是先让 form 通过 action 提交到真实处理端点，再增强成无刷新提交、错误提示和输入建议。这样用户不依赖增强脚本也能完成相应任务。

但纯静态托管不会因为写了一个 form action，就自动拥有搜索或提交接口。基础路径必须确实存在；如果产品没有后端，可以提供静态分类目录、本地可读内容和明确的功能边界，而不是声明一个根本不存在的回退端点。

增强层也应保留正确的提交语义，例如 method、字段名称和验证规则。只有在自己确实能够处理当前操作时，才阻止原来的行为。

特性检测之后，还要处理运行失败

检测 API 或 CSS 能力通常比根据浏览器名称猜测更直接，例如检查某个方法是否存在，或者使用 CSS @supports。浏览器名称相同，不代表版本、嵌入配置和权限策略都相同。

不过“方法存在”不代表“调用一定成功”。剪贴板可能因权限或用户激活失败，文件选择可能被取消，网络也可能在增强逻辑启动后中断。

因此能力检测决定是否尝试增强，错误处理决定尝试失败后怎么办。复制按钮失败时可以保留可选择的原文和手动复制路径；动画能力不足时可以直接完成状态变化，不必让导航也一起失效。

降级不能制造第二次副作用

异步提交失败后，不能总是立即退回原生表单再提交一次。服务器可能已经接受了第一次操作，只是响应丢失，第二次提交就可能重复创建记录。

对于写操作，应通过幂等、状态查询或明确的用户重试流程判断下一步。对于只读导航或内容获取，回到完整页面导航通常更容易设计，但也需要有正确的目标地址。

增强逻辑的错误边界最好局部化。推荐模块失败可以隐藏推荐并保留正文；非关键第三方脚本失败不应阻止用户操作核心表单。不要让所有组件都依赖一个不相关的初始化 Promise 才能显示。

验证时主动拿掉一些能力

可以从实际风险出发测试：禁用或阻断脚本、拒绝权限、阻止非关键资源、模拟接口失败、关闭动效偏好，或者使用目标旧浏览器。检查用户是否仍能阅读、导航、提交或知道为什么暂时不能继续。

有些增强层会在初始化时先隐藏基础内容，之后出错却没恢复；有些界面只在成功路径取消 loading，失败后永远无法再操作。这些问题不是“浏览器太旧”，而是降级路径没有完成。

渐进增强并不要求代码永远停留在最旧能力上。它要求先识别哪些能力真正决定核心任务，再把更好的体验建立在可解释的依赖和失败处理之上。
