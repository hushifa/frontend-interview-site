渐进增强和优雅降级怎样影响前端方案选择？

从最低可用任务出发区分两种设计方向，说明静态内容、原生能力、特性检测与运行时失败的关系，并解释怎样避免增强层反而破坏基础功能。

参考答案

简答

  • 渐进增强从最基础的可用版本出发（HTML 内容、原生链接和表单），再在支持的环境中叠加样式和脚本功能。
  • 优雅降级从完整体验出发，为能力不足的环境准备退路。
  • 两者的区别在于设计起点：渐进增强保证核心任务始终可用，优雅降级容易遗漏退路。
  • 用特性检测（'share' in navigator、@supports）判断能力，不用浏览器名称或版本号判断。
  • 脚本加载失败、超时或报错也属于"能力不足"，基础功能不应完全依赖 JS 成功执行。

一个搜索表单

HTML
<form action="/search" method="get" id="search">
  <input name="q" type="search" required aria-label="搜索题目" />
  <button>搜索</button>
</form>
JavaScript
const form = document.querySelector('#search');
form.addEventListener('submit', async (event) => {
  event.preventDefault();
  try {
    await showResultsInline(new FormData(form).get('q'));
  } catch {
    form.submit(); // 增强失败时回到原生提交
  }
});
  • 没有 JS 时，表单正常提交到 /search，服务端或预渲染页面返回结果。
  • 有 JS 时，在当前页面显示结果，体验更好。
  • JS 执行出错时回退到原生行为，而不是让按钮无响应。

特性检测

JavaScript
if ('share' in navigator) {
  shareButton.hidden = false;
} else {
  copyLinkButton.hidden = false;
}
CSS
.layout { display: block; }

@supports (display: grid) {
  .layout { display: grid; grid-template-columns: 1fr 3fr; }
}

检测具体能力而不是浏览器，因为同一个浏览器的不同版本、不同设置（如企业策略禁用某些 API）能力不同。

增强层破坏基础功能的例子

  • 用 <div onclick> 代替链接实现导航，JS 加载前无法点击，也不能在新标签打开。
  • 客户端渲染全部内容，脚本加载慢或失败时页面空白。
  • 自定义下拉框替换原生 <select>，却没有实现键盘操作。
  • 加载脚本前用 CSS 隐藏内容，脚本失败后内容永远不显示。

对方案选择的影响

  • 内容型网站（文档、博客、电商详情）适合预渲染加渐进增强，首屏和搜索收录都更可靠。
  • 复杂的交互应用（在线编辑器、设计工具）核心功能本身依赖 JS，更适合明确支持的浏览器范围并对不支持的环境给出提示。
  • 新 CSS 和 Web API 先用特性检测包裹，在支持的环境中启用。

常见追问

  • SSR 就是渐进增强吗？SSR 提供了基础 HTML，但如果交互（按钮、表单）只在水合后才能工作，水合前仍然不可用，需要配合原生表单和链接。
  • 这样会增加多少成本？主要是坚持使用语义化 HTML 和原生控件，这本身也是无障碍的要求。
