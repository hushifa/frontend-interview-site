语义化版本号能否保证升级一定安全？

SemVer 只是发布者的承诺，不是工具保证。文中区分版本号含义、包管理器的版本范围和锁文件，解释 0.x、预发布和构建元数据，以及为什么小版本更新也要验证。

参考答案

简答

语义化版本号写成 MAJOR.MINOR.PATCH 三段。有不兼容的改动升第一段，加了向后兼容的新功能升第二段，只是向后兼容的修复升第三段。

但这只是发布者的承诺，不是工具能保证的。改动兼不兼容是人判断的，判断错、不小心破坏了行为，都很常见。

包管理器靠版本范围决定装哪个版本。^1.2.3 允许升到 2.0.0 之前，~1.2.3 只允许升到 1.3.0 之前；0.x 比较特殊，^0.2.3 只允许到 0.3.0 之前。预发布版本默认不会被普通范围匹配到。

所以升级还是要靠锁文件固定版本、跑测试、读变更日志。自动化工具只负责提出升级。

三段版本号分别代表什么

从 1.4.2 升到 2.0.0，表示公开 API 有不兼容的变化，比如删了函数、改了参数含义。升到 1.5.0，表示加了向后兼容的功能，比如新增一个可选参数。升到 1.4.3，表示向后兼容的问题修复，比如修了一个计算错误。

0.y.z 表示还在初始开发阶段，规范不保证任何稳定性。从 1.0.0 开始，才算定义了公开 API。

版本范围怎样读

package.json 里写的通常是范围，不是一个确切版本。

写 1.2.3 就只装 1.2.3。写 ^1.2.3，允许大于等于 1.2.3、小于 2.0.0 的版本。写 ~1.2.3，允许大于等于 1.2.3、小于 1.3.0。

到了 0.x，^ 会收紧。^0.2.3 只允许大于等于 0.2.3、小于 0.3.0，^0.0.3 只允许 0.0.3 本身。因为 0.x 阶段连次版本都可能不兼容。

预发布版本，比如 1.0.0-rc.1，排在 1.0.0 之前。^1.0.0 不会匹配 1.1.0-beta.0，除非范围本身就写了同一个主次补丁号的预发布版本。

1.0.0+build.5 里 + 后面的部分是构建元数据，比较版本时会被忽略。

为什么小版本也会出问题

最常见的原因是，你依赖了发布者眼里的“内部实现”，比如错误信息的文字、事件触发的顺序、默认样式。发布者改这些时不觉得是破坏性变更。

还有一种情况是，发布者修了一个 bug，可你的代码恰好依赖这个 bug 的行为。

间接依赖也会带来变化，比如依赖的依赖升级了，要求更新的 Node.js 版本，或者换了 peer 依赖、打包格式。

类型声明变严格也会出问题。运行时完全兼容，TypeScript 却编译失败。

怎样安全地升级

先提交锁文件，这样平时安装不会自动拿到新版本。然后用 Renovate 或 Dependabot 定期提升级 PR，一次只升一组相关的依赖。

在 PR 里读变更日志，跑完整的类型检查、测试和构建。大版本升级按官方迁移指南处理，必要时先在分支里试用。

常见追问

自己发布库时，怎样避免误伤使用者？

先明确公开 API 的范围，比如用 exports 和文档写清楚。对行为变化保守一点，拿不准就升主版本，并在变更日志里写清楚。

为什么有的项目所有依赖都写精确版本？

为了完全掌控升级的时机。代价是要更频繁地手动升级。
