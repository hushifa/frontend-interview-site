语义化版本号能否保证升级一定安全？

区分 SemVer 的发布承诺、包管理器的版本范围与锁文件，解释 0.x、预发布和构建元数据，并说明为什么小版本更新仍需要验证。

参考答案

简答

  • 语义化版本 MAJOR.MINOR.PATCH：不兼容改动升主版本，向后兼容的新功能升次版本，向后兼容的修复升补丁版本。
  • 这是发布者的承诺，不是工具保证；判断"兼容"靠人，误判和意外破坏很常见。
  • ^1.2.3 允许 <2.0.0 的所有更新，~1.2.3 只允许 <1.3.0；0.x 版本下 ^0.2.3 只允许 <0.3.0。
  • 预发布版本（如 2.0.0-beta.1）默认不会被普通范围匹配到。
  • 升级仍要靠锁文件固定版本、跑测试、读变更日志，自动化工具只负责提出升级。

版本号的含义

变化含义示例
1.4.2 → 2.0.0有不兼容的公开 API 变更删除函数、改参数含义
1.4.2 → 1.5.0新增向后兼容的功能新增可选参数
1.4.2 → 1.4.3向后兼容的问题修复修复计算错误

0.y.z 表示初始开发阶段，规范不保证任何稳定性。1.0.0 起才定义了公开 API。

范围语法

写法允许的版本
1.2.3只有 1.2.3
^1.2.3≥1.2.3 且 <2.0.0
~1.2.3≥1.2.3 且 <1.3.0
^0.2.3≥0.2.3 且 <0.3.0
^0.0.3只有 0.0.3

1.0.0-rc.1 这类预发布版本排在 1.0.0 之前。^1.0.0 不会匹配 1.1.0-beta.0，除非范围本身就写了同一个主次补丁号的预发布版本。

1.0.0+build.5 中 + 后面是构建元数据，比较版本时会被忽略。

为什么小版本也会出问题

  • 发布者认为的"内部实现"被你依赖了，例如错误信息文本、事件触发顺序、默认样式。
  • 修复 bug 改变了行为，而你的代码恰好依赖那个 bug。
  • 依赖的依赖升级，带来新的 Node.js 版本要求、peer 依赖或打包格式变化。
  • 类型声明更严格，TypeScript 编译失败，即使运行时完全兼容。

怎样安全升级

  1. 提交锁文件，平时安装不会自动拿到新版本。
  2. 用 Renovate 或 Dependabot 定期提出升级 PR，一次只升一组相关依赖。
  3. 在 PR 中阅读变更日志，跑完整的类型检查、测试和构建。
  4. 大版本升级按官方迁移指南处理，必要时先在分支中试用。

常见追问

  • 自己发布库时怎样避免误伤？明确公开 API 的范围（exports、文档），对行为变化保守地升主版本，并在变更日志中写清楚。
  • 为什么有的项目所有依赖都写精确版本？为了完全掌控升级时机，代价是需要更频繁地手动升级。
