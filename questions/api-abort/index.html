AbortController 能取消什么，不能取消什么？

AbortController 只是发一个"取消"通知，fetch、事件监听这类认识 signal 的 API 收到后自己停下。它打断不了正在跑的同步代码，也撤销不了服务端已经执行的操作。

参考答案

简答

比如搜索框，用户连续输入，前一个请求还没回来就该作废了。这时候新建一个 AbortController，把它的 signal 传给 fetch，需要取消时调用 controller.abort()。

它的原理是发通知。abort() 让 signal 变成已取消，并触发 abort 事件。认识这个 signal 的 API 自己停下来：fetch 的 Promise 以 AbortError reject，addEventListener 传了 signal 的监听器会被移除。

另外有两个工具方法：AbortSignal.timeout(ms) 到时间自动取消，AbortSignal.any([...]) 把多个 signal 合成一个，任意一个取消它就取消。

要注意它不是强制中断。正在跑的同步循环它打断不了，请求已经到了服务端，服务端的操作也不会撤销，浏览器只是不再等响应。而且一个 controller 取消后就作废了，下次要新建。

取消过期的搜索请求

下面是最常见的用法：每次搜索前先取消上一次，同时加一个 5 秒超时。

JavaScript
let controller;

async function search(keyword) {
  controller?.abort();
  controller = new AbortController();

  try {
    const response = await fetch(`/api/search?q=${encodeURIComponent(keyword)}`, {
      signal: AbortSignal.any([controller.signal, AbortSignal.timeout(5000)]),
    });
    return await response.json();
  } catch (error) {
    if (error.name === 'AbortError') return null;
    throw error;
  }
}

为什么要取消旧请求？因为请求返回的顺序不一定等于发出的顺序。先搜“re”、再搜“react”，如果“re”的结果后回来，就会把正确结果覆盖掉，这叫竞态。取消旧请求以后，旧结果根本不会被处理。

两种取消的错误名不一样。超时触发时错误名是 TimeoutError，用户主动取消是 AbortError，所以可以分开处理，比如超时提示“网络慢”，主动取消就安静地忽略。

为什么它打断不了同步代码

abort() 本质上是派发一个事件。事件要等当前正在执行的同步代码跑完才有机会处理，所以一段长循环在跑的时候，取消根本插不进来。

JavaScript
const controller = new AbortController();
setTimeout(() => controller.abort(), 0);

const start = Date.now();
while (Date.now() - start < 50) {}
console.log('循环结束时', controller.signal.aborted); // 循环结束时 false

await new Promise((resolve) => setTimeout(resolve, 0));
console.log('之后', controller.signal.aborted); // 之后 true

定时器 0 毫秒后就该取消，可循环跑了 50 毫秒，结束时 aborted 还是 false。因为定时器回调要等同步代码让出线程才执行。改法是把长计算拆开，在循环里主动检查 signal.aborted，或者调用 signal.throwIfAborted()，并且中间要让出线程，取消才有机会发生。

让自己的函数支持取消

自己写的异步函数也可以接收 signal。下面是一个能被取消的 wait：

JavaScript
function wait(ms, { signal } = {}) {
  return new Promise((resolve, reject) => {
    signal?.throwIfAborted();
    const onAbort = () => {
      clearTimeout(timer);
      reject(signal.reason);
    };
    // 正常结束时移除监听，复用同一个 signal 时不会累积
    const timer = setTimeout(() => {
      signal?.removeEventListener('abort', onAbort);
      resolve();
    }, ms);
    signal?.addEventListener('abort', onAbort, { once: true });
  });
}

开头的 throwIfAborted() 处理“传进来时已经取消了”的情况，直接抛出。之后监听 abort 事件，取消时清掉定时器并用 signal.reason reject。正常结束时要把监听移除，否则同一个 signal 被多次使用，监听器会越积越多。

哪些东西取消不了

最容易误解的是请求已经到了服务端。取消只是浏览器不再等待响应，服务端照样把操作做完。所以下单、支付这类写操作，不能指望前端取消，要用幂等键，让服务端识别重复请求，防止重试导致执行两次。

另外，已经开始的同步代码取消不了，上一节讲过。不接受 signal 的第三方 API 也取消不了，因为它根本不会去听这个通知。

常见追问

一个 controller 能重复使用吗？

不能。取消以后它的 signal 永远处于已取消状态，再传给新请求，请求会立刻失败。所以每次新操作都要新建一个 controller。

React 里怎么用？

在 useEffect 里创建 controller，把 signal 传给请求，清理函数里调用 abort()。这样组件卸载或依赖变化时，旧请求会被取消，不会把过期数据写进 state。
