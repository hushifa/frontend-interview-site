Hydration mismatch 为什么发生，应该怎样修复？

从客户端接管现有 HTML 的过程解释不一致，按初始数据、环境差异、HTML 结构和 DOM 修改定位原因，并用时间显示示例区分首次匹配与接管后的正常更新。

参考答案

服务端已经生成了一棵 HTML，客户端 React 需要把组件逻辑连接到这些现有节点上，这个过程就是 hydration。它希望客户端第一次渲染所描述的结构和内容，与浏览器实际拿到的服务端 DOM 对应。

如果服务器输出“未登录”，客户端第一次就渲染“欢迎回来”，或者双方生成了不同的随机 ID，React 便无法把两份结果无歧义地对应起来。它可能报告不一致、进行恢复或重新渲染相应内容，额外开销只是问题的一部分。

比较的是客户端首次渲染，不是页面永远不许变化

可以分清三个阶段：

  1. 服务器生成 HTML 与初始数据快照。
  2. 浏览器解析 HTML，客户端使用同一份初始输入进行 hydration。
  3. 接管完成后，用户操作、Effect 或新数据触发正常更新。

第三阶段显示不同内容很正常。问题在于第二阶段已经与现有 DOM 不一致，不能把这种差异当成一次普通更新处理。

React 不保证会把所有不一致属性自动修好，因此“不报致命错误，页面大致能看”不是修复标准。

先检查四类常见原因

原因例子优先修复方向
初始数据不同服务器与客户端分别请求到不同版本传递并复用对应数据快照
环境或时间不同时区、语言、Date.now、随机值固定初始表示，随后再增强
HTML 结构无效p 内嵌入不允许的块级结构修正结构，检查浏览器解析后的 DOM
接管前 DOM 被改动第三方脚本、扩展或插入逻辑修改节点找到修改来源，明确 DOM 所有权

只比较服务端源码字符串还不够。不合法 HTML 可能已经被浏览器解析器修正，真正 hydration 的对象是修正后的 DOM。

时间显示可以先一致，再本地化

如果服务器按 UTC 格式化、浏览器按本地时区格式化，即使双方拿的是同一时间点，第一次显示也可能不同。可以让初始输出统一使用传入的 ISO 字符串，接管后再显示用户本地时间：

JSX
import { useEffect, useState } from 'react';

export function PublishedTime({ iso }) {
  const [showLocal, setShowLocal] = useState(false);

  useEffect(() => {
    setShowLocal(true);
  }, []);

  const label = showLocal
    ? new Intl.DateTimeFormat('zh-CN', {
        dateStyle: 'medium',
        timeStyle: 'short',
      }).format(new Date(iso))
    : iso;

  return <time dateTime={iso}>{label}</time>;
}

iso 应是已经验证的时间字符串，服务端与客户端必须收到同一值。服务端不运行 Effect，客户端首次也从 false 开始，因此都先输出 iso；随后浏览器中的 Effect 触发本地化更新。

这种两次渲染会有额外成本和可能的文字变化，适合确实需要客户端环境的信息，不应把整站内容都先隐藏到 Effect 之后。若业务要求首屏就是固定时区文案，也可以在两端使用同样的语言和明确的 timeZone，而不必做第二次切换。

typeof window 不会自动保证一致

在 render 中写“有 window 就返回 A，没有就返回 B”，只能避免服务端访问某个浏览器对象，并没有解决两端首次 HTML 不同的问题。

读取 localStorage、视口宽度或客户端权限状态时，也要决定初始表示。可以由服务端提供一致的初始偏好、用 CSS 处理纯布局差异，或在接管后更新只属于浏览器的信息。

需要真正仅客户端运行的功能时，可以使用当前框架支持的客户端边界，但应限定到必要区域。不要为了一个浏览器专属组件，让整页正文失去原本可用的服务端 HTML。

ID、数据与多根节点也需要一致

随机 ID 不适合在两端各生成一次再期待匹配。React 的 useId 可以帮助生成与渲染树相关的稳定标识，但仍需要树结构与相应环境配置一致，多根节点使用的 identifierPrefix 也应对应。

初始状态序列化时要保护用户边界，并使用正确的 HTML 转义方式。把 JSON.stringify 的结果直接拼入任意 script 上下文，不自动保证安全；也不能为了“让状态一致”把服务端秘密一并发给客户端。

若登录状态或数据版本在缓存中混用了，根因可能是缓存策略，而不是组件需要增加更多客户端判断。

suppressHydrationWarning 只适合有限例外

它是针对可解释差异的逃生口，不会让任意子树都安全匹配，也不是深层统一修复开关。使用前应明确哪些差异无法避免、实际 DOM 最终会是什么，以及是否影响交互或可访问性。

大面积增加该属性会把真正的数据与结构问题藏起来。使用 createRoot 重新覆盖已有服务端节点，或过早调用 root.render 让整棵树改走客户端渲染，也只是改变处理路径，不等于已经理解了不一致原因。

排查时保存首轮证据

记录问题页面的初始响应、传给客户端的数据，以及第三方脚本修改前后的 DOM；结合开发环境提示、组件栈和 onRecoverableError 定位具体区域。

然后分别验证直达、刷新、不同语言与时区、缓存命中和登录状态。一次客户端路由切换正常，并不能证明完整文档首次 hydration 也正确。修复应让首轮输入和结构有清楚来源，接管后的差异则作为正常更新处理。
