什么场景值得用 WebGL？GPU 加速有哪些成本？

WebGL 适合大量同构图元的并行绘制，但会带来着色器、资源生命周期和兼容性成本。选型要看瓶颈是否在绘制，以及团队能否维护 GPU 代码。

参考答案

简答

  • WebGL 适合大量同构图元的并行绘制，例如大规模散点、地图瓦片、粒子和三维场景。
  • 几百个节点的图表和普通 UI 用 SVG、Canvas 2D 或 CSS 更简单，也更容易做无障碍。
  • 每帧重建缓冲区或发出大量小 draw call 会让 CPU 先成为瓶颈。
  • 应用要处理上下文丢失，并评估团队维护 GPU 代码的成本。

WebGL 让 JavaScript 组织图形资源和绘制命令，由图形实现执行着色器与光栅化等工作。它能高效处理适合并行的图形计算，但不是把任意 JavaScript 自动搬到 GPU。

画一个三角形时，JavaScript 提供顶点、缓冲区、着色器和状态；GPU 按流水线把几何转换成画布上的颜色。应用仍负责决定画什么、何时更新和如何管理资源。

什么时候值得用 WebGL

适合 WebGL 的是大量同构图元的并行绘制：上万个散点、地图瓦片、粒子、三维场景、图像滤镜。几百个节点的图表、表单动画和普通 UI，用 SVG、Canvas 2D 或 CSS 更简单，也更容易做可访问性。

选型前先回答三个问题：

  • 瓶颈是不是绘制本身？如果慢在数据处理或布局，换 WebGL 不会变快；
  • 团队能否维护着色器、坐标变换和 GPU 资源生命周期？不能的话优先用 Three.js、deck.gl 等高层库；
  • 目标设备是否稳定支持所需的 WebGL 版本、扩展和纹理尺寸？需要通用计算时，再评估 WebGPU。

着色器怎样工作、怎样把两段源码接到一次真正的绘制，见“WebGL 着色器如何工作？如何避免把 GPU 当成黑盒？”。

GPU 加速有数据与同步成本

如果每帧重新创建缓冲区、上传全部几何或发出大量很小的 draw call，CPU 组织命令的成本可能先成为瓶颈。适合时可复用资源、批处理或实例化，减少重复状态切换。

纹理太大、重叠透明层太多或片元着色器过重，则可能受显存、带宽和填充率限制。提高分辨率会增加片元工作，不能只看对象数量。

readPixels 等读回操作还可能导致同步等待，把 GPU 的并行优势消耗在 CPU 等结果上。频繁读取用于每次鼠标移动的精确拾取，要特别评估成本。

上下文丢失和能力差异

浏览器可能因资源压力或设备切换丢失 WebGL 上下文，应用要处理 webglcontextlost 并在恢复后重建资源，具体做法见“WebGL 着色器如何工作？如何避免把 GPU 当成黑盒？”。

浏览器能取得 WebGL 上下文也不保证所有扩展、精度和纹理尺寸都相同。应查询能力、提供降级或错误体验，且不要假定所有环境一定使用同一种硬件加速路径。

Three.js 等库能封装场景、材质和相机，但仍要理解资源释放、纹理大小和绘制成本。选用 WebGL 的理由应是图形需求和测量收益，而不是“用了 GPU 就一定快”。
