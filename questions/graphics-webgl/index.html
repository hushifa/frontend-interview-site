什么场景值得用 WebGL？GPU 加速有哪些成本？

WebGL 适合大量同类图元的并行绘制，例如上万个散点、地图、粒子和三维场景。代价是着色器开发、GPU 资源管理、上下文丢失恢复和设备差异；普通图表和 UI 用 SVG、Canvas 2D 更省事。

参考答案

简答

  • 适合 WebGL：上万个散点或点云、地图瓦片、粒子、三维场景、实时图像滤镜。
  • 不必用 WebGL：几百个节点的图表、表单动画、普通界面，用 SVG、Canvas 2D 或 CSS 更简单，也更容易做无障碍。
  • 先确认瓶颈在绘制。如果慢在数据处理或布局，换成 WebGL 也不会变快。
  • GPU 不是免费的：每帧重建缓冲区、大量小 draw call 会让 CPU 先成为瓶颈；readPixels 会让 CPU 等待 GPU。
  • 要处理上下文丢失：监听 webglcontextlost 并调用 preventDefault()，浏览器才会恢复上下文，恢复后重建全部 GPU 资源。

选型三问

  1. 瓶颈是不是绘制？ 用性能面板看时间花在脚本、布局还是绘制上。
  2. 团队能不能维护 GPU 代码？ 着色器、矩阵、资源释放都需要专门知识。维护不了就用 Three.js、deck.gl、PixiJS 等高层库。
  3. 目标设备支不支持？ WebGL 2 已普遍可用，但扩展、精度、最大纹理尺寸因设备而异，要查询能力并准备降级。

需要通用计算（例如在 GPU 上跑推理或物理模拟）时，再评估 WebGPU。

性能成本在哪里

瓶颈表现处理方式
CPU 提交draw call 太多、每帧重新上传几何合并批次、实例化绘制、复用缓冲区
片元填充全屏特效、多层透明、分辨率高降低渲染分辨率、减少重叠绘制
显存与带宽纹理太大或太多压缩纹理、限制尺寸、及时删除
同步等待每帧 readPixels 做拾取改用颜色拾取缓冲按需读取，或在 CPU 端做空间索引

上下文丢失

JavaScript
canvas.addEventListener('webglcontextlost', (event) => {
  event.preventDefault(); // 不调用就不会触发 webglcontextrestored
  stopRenderLoop();
});

canvas.addEventListener('webglcontextrestored', () => {
  createResources(); // 重新编译着色器、创建缓冲区和纹理
  startRenderLoop();
});

业务数据要保存在 JavaScript 里，GPU 上的缓冲区和纹理只是副本，上下文丢失后它们全部失效。

着色器怎样工作、怎样完成一次绘制，见《WebGL 着色器如何工作？如何避免把 GPU 当成黑盒？》。

常见追问

  • WebGL 和 Canvas 2D 都画在 canvas 上，区别是什么？ Canvas 2D 是即时绘图 API，浏览器负责光栅化；WebGL 让你自己写着色器、管理 GPU 资源，控制力更强，代码量也大得多。
  • 用了 Three.js 还需要懂 WebGL 吗？ 需要了解基本成本：纹理大小、draw call 数量、透明排序和资源释放，否则照样会卡或泄漏显存。
