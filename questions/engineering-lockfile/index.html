为什么需要提交 lockfile？npm ci 和 npm install 有何区别？

解释版本范围与实际依赖树的差别，说明 npm install 何时更新锁文件、npm ci 的一致性检查，以及工具版本、平台和安装脚本仍需单独控制的原因。

参考答案

简答

  • package.json 里写的是版本范围（如 ^1.2.0），不同时间安装可能得到不同版本。
  • lockfile 记录整棵依赖树每个包的确切版本、来源和完整性哈希，提交后所有人和 CI 安装结果一致。
  • npm install 可能根据范围更新锁文件；npm ci 严格按锁文件安装，锁文件和 package.json 不一致时直接报错。
  • npm ci 会先删除已有的 node_modules，适合 CI 和生产构建。
  • 锁文件不固定 Node.js 版本、包管理器版本和平台相关的原生依赖，这些要单独约束。

范围和实际版本

json
{ "dependencies": { "dayjs": "^1.11.0" } }

^1.11.0 允许 1.x 中任何不低于 1.11.0 的版本。今天安装得到 1.11.10，下个月可能得到 1.11.13。间接依赖的范围更多，变化面更大。没有锁文件时，"本地能跑，CI 失败"往往来自这里。

lockfile（package-lock.json、pnpm-lock.yaml、yarn.lock）把一次解析的结果固定下来，同时记录下载地址和 integrity 哈希，安装时校验包内容没有被替换。

npm install 和 npm ci

npm installnpm ci
锁文件不存在解析并生成报错
锁文件与 package.json 不一致按 package.json 重新解析并更新锁文件报错退出
已有 node_modules增量更新先删除再安装
会修改 package.json / 锁文件可能不会

pnpm 对应 pnpm install --frozen-lockfile（CI 环境默认开启），Yarn 对应 yarn install --immutable。

什么时候更新锁文件

  • 新增、删除、升级依赖时由 npm install <pkg> 或 npm update 更新，并和代码一起提交、评审。
  • 合并冲突时不要手工编辑锁文件，先解决 package.json 冲突，再重新运行安装生成锁文件。
  • 库项目同样应提交锁文件，保证自身开发和测试可复现；发布到 npm 后，使用者不会读取库的 package-lock.json。

锁文件管不到的东西

  • Node.js 和包管理器版本：用 engines、.nvmrc、packageManager 字段固定。
  • 安装脚本：postinstall 可能下载二进制文件或执行任意代码，结果受网络和系统影响。CI 可以用 --ignore-scripts 配合白名单降低风险。
  • 平台差异：可选依赖和原生模块会按操作系统和 CPU 选择不同的包。

常见追问

  • 为什么 CI 要用 npm ci？它保证构建用的就是评审过的依赖树，并在依赖声明不一致时尽早失败。
  • 锁文件能防止供应链攻击吗？能防止已固定的包被悄悄替换，但无法阻止你主动升级到一个恶意版本，升级时仍要审查。
