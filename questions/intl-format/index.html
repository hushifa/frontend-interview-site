为什么日期、金额和排序不应该手动拼接格式？

日期顺序、数字分隔符、货币符号位置和字母顺序都随地区变化，手动拼接只能照顾一种习惯。用 Intl.NumberFormat、DateTimeFormat、Collator 按 locale 格式化和排序；存储和接口传原始值，格式化后的字符串只用于显示。

参考答案

简答

同一个 1234.5，美国写作 1,234.5，德国写作 1.234,5；印度写小数字时和美国一样，大数却会写成 12,34,567。手动拼逗号和小数点，只能照顾到其中一种习惯。所以日期、数字、金额和排序都交给 Intl 按 locale 处理。

金额要同时给出 locale 和货币代码。locale 决定怎么写，货币决定用什么符号、默认几位小数。格式化不会做汇率换算。

日期的写法由 locale 决定，时区要另外指定，中文 locale 不会自动用中国时区。排序用 Intl.Collator，加上 numeric: true，item2 才会排在 item10 前面。

要注意，存储和接口里传的是数值、货币代码和语义明确的时间。格式化后的字符串只用来显示，不要再解析回来。

金额怎样格式化

下面三种货币，写法各不相同。结果是 Node 22 实测的。

JavaScript
new Intl.NumberFormat('en-US', { style: 'currency', currency: 'USD' }).format(1234.5); // '$1,234.50'
new Intl.NumberFormat('de-DE', { style: 'currency', currency: 'EUR' }).format(1234.5); // '1.234,50 €'
new Intl.NumberFormat('zh-CN', { style: 'currency', currency: 'CNY' }).format(1234.5); // '¥1,234.50'
new Intl.NumberFormat('zh-CN', { notation: 'compact' }).format(12345678); // '1235万'

德国把符号放在后面，分隔符也和美国反过来。三种货币都自动补成了两位小数，这是货币默认的小数位。最后一行的紧凑写法，中文会用“万”作单位。

写测试时容易在欧元这一行栽跟头。€ 前面那个空格是不换行空格，不是普通空格，直接拿普通空格比较会失败。

还有两件事 NumberFormat 不管。一是汇率：currency 只决定符号和小数位，金额要先按业务汇率换算好再格式化。二是计算精度：它只做显示时的舍入，金额计算要用最小货币单位的整数，或者十进制库，避免浮点误差。

日期为什么要指定时区

同一个瞬间，换个时区显示出来的日期可能都不一样。

JavaScript
const instant = new Date('2026-01-01T00:00:00Z');
new Intl.DateTimeFormat('en-GB', {
  dateStyle: 'short',
  timeStyle: 'short',
  timeZone: 'Asia/Shanghai',
}).format(instant); // '01/01/2026, 08:00'

new Intl.DateTimeFormat('zh-CN', { dateStyle: 'long', timeZone: 'UTC' }).format(instant); // '2026年1月1日'

locale 管的是“日月年怎么排”，时区管的是“现在是几点”，两者互不影响。所以上面英式写法配上海时区，中文写法配 UTC，都是合法的组合。

SSR 时一定要显式传 timeZone。服务端默认常是 UTC，浏览器用的是本地时区，不指定的话两边渲染出来的文字不同，水合会对不上。时区怎样建模，见《时间戳、时区和只有日期的业务值应该怎样区分？》。

排序为什么不能直接 sort

先看默认的 sort() 和 Collator 的差别。

JavaScript
['item10', 'item2', 'item1'].sort(); // ['item1', 'item10', 'item2']
['item10', 'item2', 'item1'].sort(new Intl.Collator('en', { numeric: true }).compare);
// ['item1', 'item2', 'item10']

['a', 'B', 'c', 'Ä'].sort(new Intl.Collator('de').compare); // ['a', 'Ä', 'B', 'c']
['张三', '李四', '王五', '阿明'].sort(new Intl.Collator('zh-CN').compare);
// ['阿明', '李四', '王五', '张三']，按拼音

默认的 sort() 把 item10 排在 item2 前面，因为它按 UTF-16 码元一个字符一个字符地比，1 比 2 小就排前面了。按同样的道理，大写字母会排在所有小写字母前面。Collator 按语言习惯比较，加了 numeric: true 还会把数字当数值看。

Collator 还有个 sensitivity 选项。设成 'base' 时，a 和 Á 比较结果为 0，被当成同一个字母。这适合做搜索匹配，但不适合判断账号是否重复。

想给某一部分加样式怎么办

比如只想把货币符号变小一点，可以用 formatToParts()。

JavaScript
new Intl.NumberFormat('en-US', { style: 'currency', currency: 'USD' }).formatToParts(1234.5);
// [{ type: 'currency', value: '$' }, { type: 'integer', value: '1' }, { type: 'group', value: ',' }, ...]

它把结果拆成带类型的几段，按 type 找到货币符号单独渲染就行。不要用 split(',') 去拆字符串，换个 locale 分隔符就变了。

另外，大量格式化时要复用同一个 formatter 实例。创建实例的开销比调用 format() 大得多。

常见追问

toLocaleString() 和 Intl.NumberFormat 有什么区别？

结果是一样的。区别在于 toLocaleString() 每次调用都要重新处理选项，循环里格式化大量数据时，复用一个 Intl.NumberFormat 实例会更快。

用户输入的本地化数字怎样解析？

Intl 没有通用的反向解析器。输入框尽量用 inputmode="decimal" 并约定格式；或者用 formatToParts 取出当前 locale 的分隔符，再自己解析。
