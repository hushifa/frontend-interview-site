先明确产品形态：增强已有页面、完整单页应用、内容站点、服务端渲染或嵌入式组件。不同形态决定对路由、数据加载、首屏交付与部署能力的需求，不能只比较语法喜好。

框架选型不能只比较 API 数量或示例页面速度，还要看渲染模式、路由和数据获取、部署限制、调试能力、团队经验及升级路径。把必须满足的约束列出来，再比较方案在这些约束下的代价。

再评估团队经验、生态依赖、无障碍能力、升级成本和可观测性。简单内容页面可能不需要完整应用框架，复杂交互也不一定适合只靠模板拼接。

原型验证应覆盖最难的真实场景，例如大表单、弱网、权限和跨端能力。框架官方提供多种使用方式，不代表每种方式都适合当前团队；应记录选择依据和放弃方案的具体原因。

还要比较渲染模型、路由与数据获取、无障碍、测试工具、升级节奏、包体积和招聘成本。内容站点、后台系统、实时协作和跨端应用的约束不同，不应使用同一套评分表得出结论。选型记录应写明未来迁移条件，而不是只记录最终框架名称。

框架名相同的概念也可能有不同语义。回答具体特性时要锁定版本和运行环境，并把迁移成本、生态依赖和失败时的替代方案说清楚。

实际选型时，可以用同一条业务流程做小型验证：路由、表单、数据加载、错误页、构建和部署都跑一遍。示例项目能运行只说明起点可行，不能说明升级、团队协作和生产排障也同样轻松。
