选择前端框架时应该先比较哪些约束？

先把产品形态、渲染方式、部署环境、关键依赖和团队经验这些硬约束列出来，排除不满足的方案；再挑一条真实的复杂业务流程做原型，比较开发效率、性能和维护成本。语法偏好和基准测试排名不应作为主要依据。

参考答案

简答

选框架我不会先比语法或者跑分，而是先看硬约束。比如产品是什么形态：内容站点看重首屏 HTML 和 SEO，后台系统看重表单、权限和长时间运行的稳定性，嵌入别人页面的组件看重体积和样式隔离。

然后看渲染和部署。需要 SSR 就得有 Node 或边缘运行时；如果只能静态托管，就要确认框架的静态导出能覆盖要用的功能。再看关键依赖，组件库、富文本编辑器、图表、国际化、监控 SDK 支不支持目标版本。最后是团队，大家熟不熟、好不好招人、出了问题能不能自己排查。

不满足硬约束的直接排除。剩下的方案，比较的是整套组合，也就是 UI 库、路由、数据层、构建和部署放在一起，而不是只比核心库。

最后挑一条真实的复杂流程做原型，用测量结果来定。

先列出硬约束

硬约束就是“不满足就不能用”的条件，例如：

约束例子
部署只能用静态托管 / 有 Node 服务 / 边缘函数
SEO是否需要搜索引擎收录、社交分享卡片
浏览器是否要支持旧版 WebView
集成是否要嵌入现有页面或微前端
合规无障碍、数据驻留

先做这一步，是为了避免项目做到一半才发现部署环境跑不起来。这种问题越晚发现，代价越大。

常见的起点组合

不同场景下大家常用的组合大致是：

  • 内容为主、少量交互：Astro，或 Next.js / Nuxt 的静态导出。
  • 交互密集的后台：React 配 React Router 或 TanStack Router，或者 Vue 配 Vue Router，再加组件库。
  • 需要 SSR 和 SEO 的应用：Next.js、Nuxt、SvelteKit、React Router 框架模式。
  • 对包体积敏感：Svelte、Solid、Preact。

这些只是起点，帮你缩小范围，最后还是要用原型验证。

原型验证什么

原型不要做 Hello World，要选一条最复杂的真实流程，比如“登录 → 列表筛选 → 编辑表单 → 提交失败重试”。走一遍以后检查这些问题：

  • 直接打开深层 URL、刷新页面是否正常。
  • 表单提交失败后，输入是否保留，重复提交怎么防止。
  • 权限变化后缓存是否失效。
  • 生产构建能否在目标环境部署运行。
  • 在低端设备上的 LCP、INP 和脚本体积。

测量时要把设备、网络和数据量记下来。否则很容易拿一次热缓存下的结果当结论，换个环境就对不上了。

渲染方式和框架是两回事

CSR、SSR、SSG 说的是 HTML 在哪里、什么时候生成，属于交付策略。同一个框架往往同时支持好几种。所以顺序应该是先决定每类页面要用哪种策略，再看框架能不能支持，详见《CSR、SSR、SSG 和混合渲染如何选择？》。

常见追问

团队熟悉的框架不够好，要不要换？

把迁移成本和继续使用的风险都量化出来再决定。不能因为一个框架“新”就迁移。

选型结论怎么写？

写成“在当前约束下，方案 A 的综合成本更低”，并且注明哪些条件变了以后需要重新评估。这样结论有边界，以后情况变了也知道该回头看哪里。
