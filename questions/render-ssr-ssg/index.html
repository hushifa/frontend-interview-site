CSR、SSR、SSG 和混合渲染如何选择？

按页面 HTML 的生成时机比较客户端渲染、请求时渲染和构建时生成，结合内容时效、个性化、交互与部署条件选择组合，并说明缓存和搜索收录的边界。

参考答案

选择渲染方式，先问“用户要看的主要内容在哪里、什么时候变成 HTML”，再问“交互需要下载和执行多少代码”。这两个问题相关，但不是一回事。

例如题解正文很少变化，可以提前生成 HTML；筛选和展开交互仍由浏览器完成。并不需要因为页面有按钮，就把全部内容改成只在浏览器生成。

三种常见方式的差别

方式主要 HTML 的生成时机常见成本与约束
CSR浏览器取得并执行脚本后生成主体界面客户端代码和数据准备可能形成首屏等待
SSR通常在服务器处理请求时生成，也可复用相应缓存需要服务运行与容量，数据等待可能增加响应时间
SSG构建或预生成阶段产生页面文件适合静态托管，内容更新需要重新生成相应产物

实际框架会有不同名称和扩展，不能只凭缩写推断所有缓存行为。SSR 页面被 CDN 缓存后，后续请求也可能直接取到生成好的响应，而不重新执行一次完整渲染。

沿第一次访问看等待发生在哪里

典型 CSR 页面先返回基本文档和脚本入口，浏览器下载脚本、执行应用，再根据需要获取数据与生成内容。如果数据请求必须等大包执行后才开始，容易形成串行等待。

SSR 可以在响应中提供主要 HTML，让用户和抓取程序更早获得内容。但服务器自己也可能在等数据库或接口，若把所有数据都等齐再输出，首字节仍可能很慢。

SSG 则把这部分生成工作提前到发布之前，访问时可以直接分发静态文件。它减少请求时的生成成本，但不适合把每个用户的私有结果都预先生成成公开文件。

这些是时间与职责的分配，不是“SSR 永远更快”或“CSR 一定很慢”的排名。包体积、缓存、数据依赖、设备和部署位置都会影响实际体验。

看得到页面不等于已经完成交互

服务器或构建产出 HTML 后，依赖客户端框架的交互通常还要加载代码并 hydration。SSR 不会自动消除这些 JavaScript，也可能出现内容已经显示、按钮暂时还不能按应用逻辑工作的阶段。

但也不是所有 SSR/SSG 页面都必须 hydration。纯内容和原生链接、表单等可以不依赖整页客户端框架；需要哪些交互，就应评估为哪些部分提供客户端代码。

性能判断应同时看内容出现、布局稳定和输入响应，不能只优化 HTML 到达时间而忽略之后的主线程工作。

内容更新频率决定生成和失效策略

文档、博客和稳定题库适合评估 SSG，更新后重建并发布。规模很大时，还要考虑构建时间、受影响页面数量、资源版本和发布一致性。

库存、报价或登录后的动态页面，需要更明确的时效规则。可以采用请求时渲染、客户端获取，或按业务允许的时间窗口缓存；关键数据仍应在真正执行操作时由服务端校验。

一些框架支持增量、按需或定期重新生成，但通常需要平台或服务端运行能力。把静态文件上传到普通静态托管，并不会自动获得这些更新机制。

个性化内容首先要避免错误共享

SSR 可以根据请求身份生成内容，但缓存键与缓存策略也必须匹配。把用户 A 的个性化 HTML 当成公共响应缓存给用户 B，是安全问题，不是普通的页面刷新延迟。

SSG 产物和客户端包里的数据通常会被访问者取得，不能把私密资料或服务端密钥放进去，再认为源码仓库私有就能保护它们。

常见组合是公共内容预生成，登录后的局部数据按身份获取。是否这样分层，取决于首屏需求与业务安全，而不是所有页面统一选择同一标签。

搜索收录更容易准备好，但不会自动保证

初始 HTML 包含正文、标题、正常链接和相应元信息，通常更方便搜索引擎和其他内容消费者读取。不能绝对断言搜索引擎无法处理 CSR，但执行脚本和等待数据可能有额外限制与延迟。

采用 SSR 或 SSG 后，仍需要正确的状态码、canonical、可访问链接、内容质量和抓取配置。一个预渲染的空壳或统一返回 200 的错误页，并没有因为“服务端渲染”就自然获得良好收录。

混合渲染应该对应页面差异

可以让公开文章采用 SSG，账户页面按需获取私有数据，复杂编辑器主要采用 CSR；某些请求时页面还可以流式输出不同内容区域。

同一应用首次访问可能使用服务端 HTML，后续路由切换由客户端完成，数据与状态规则要能支持这两条入口。刷新、直达深链接、后退和客户端导航都应展示一致的页面身份与错误结果。

选型可以从三个事实开始：内容能接受多旧、是否因用户而不同、部署平台能运行什么。再测量实际的首屏与交互成本，选择足够解决问题的组合，不必为了使用更复杂的渲染名词而增加服务器和维护负担。
