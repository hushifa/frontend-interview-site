CSR、SSR、SSG 和混合渲染如何选择？

按页面主要内容的 HTML 在什么时候生成来区分：CSR 在浏览器中生成，SSR 在每次请求时由服务器生成，SSG 在构建时生成。内容变化频率、是否个性化、是否需要搜索收录和部署条件决定选择；实际项目通常按页面混合使用。

参考答案

简答

区分这三种方式，就看页面主要内容的 HTML 是什么时候、在哪里生成的。CSR 是客户端渲染，服务器只返回一个空壳和脚本，浏览器执行完脚本才出内容。SSR 是服务端渲染，每次请求由服务器现做一份 HTML。SSG 是静态生成，构建时就把 HTML 做好。

各有代价。CSR 只要静态托管，但首屏要等脚本下载执行，搜索收录也多一层不确定。SSR 内容实时、可以个性化，但要运行服务器，首字节时间受数据请求速度影响。SSG 能放 CDN，又快又便宜，但内容更新要重新构建，或者用 ISR 这类增量更新。

有一点容易误解：SSR 和 SSG 让服务器或构建过程承担了渲染，有机会少发 JavaScript。可如果整页还要 hydration，客户端照样得下载执行同一套应用代码，TBT 和 INP 不一定变好。

实际项目一般按页面选。公开的文档和商品页用 SSG 或带缓存的 SSR，个性化页面用 SSR，登录后的后台可以用 CSR。

三种方式放在一起比

CSRSSRSSG
HTML 生成时机浏览器每次请求构建时
首屏内容等脚本执行响应中直接包含响应中直接包含
个性化支持支持需要客户端补充
部署静态托管需要服务器 / 边缘函数静态托管
数据新鲜度实时实时构建时

SSG 的个性化为什么要客户端补充？因为 HTML 在构建时就定了，那时还不知道是谁来访问，只能等页面到了浏览器，再请求用户相关的数据填进去。

不同页面怎么选

文档站和博客用 SSG。内容在构建时就确定了，CDN 直接返回，最快。

电商商品详情页可以用 SSG 或 ISR 生成公共部分。价格、库存变化快，在客户端或请求时再补上。

新闻首页、搜索结果每次都不一样，用 SSR，再配合短时间的 CDN 缓存，减轻服务器压力。

登录后的管理后台不需要搜索收录，交互又多，用 CSR 就够了。

还有哪些更细的组合

这三种之间还有中间形态：

  • ISR，增量静态再生：页面先按 SSG 提供，过期后在后台重新生成，下一位访问者拿到新版本。
  • 流式 SSR：先把页面外壳发出去，慢的部分好了再流式补上，详见《React 流式 SSR 解决什么问题？》。
  • 部分预渲染：静态外壳在构建时生成，动态部分在请求时填充，Next.js 的 Cache Components 就是这样做的。
  • Islands：页面大部分是静态 HTML，只有交互区域加载 JavaScript，详见《Astro Islands 架构怎样减少客户端 JavaScript？》。

容易忽略的成本

SSR 和 SSG 都有 hydration。页面看得见但还点不了的那段时间，长短取决于客户端脚本有多大。

SSR 的服务器要承担渲染开销，流量大了就得加缓存、扩容。

SSG 页面一多，构建时间会变长。可以只预生成热门页面，其余的按需生成。

缓存层的区分详见《SSR 和 SSG 中的缓存层应该怎样区分？》，SEO 相关的要求详见《前端渲染方式怎样影响 SEO 和部署？》。

常见追问

SSR 一定比 CSR 快吗？

不一定。首屏内容通常出来得更早，但服务器响应慢的话，首字节反而更晚；能交互的时间也不一定更早，因为还要等 hydration。

静态托管能做 SSR 吗？

不能。静态托管只能返回事先生成好的文件，没有地方在请求时运行渲染代码。
