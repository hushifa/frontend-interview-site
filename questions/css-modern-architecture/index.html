CSS Modules、层叠层和自定义属性怎样帮助维护样式？

CSS Modules 管理局部类名，@layer 声明覆盖次序，自定义属性传递可被层叠和继承覆盖的样式值。三者可以协作，但都不是对所有样式影响的彻底隔离。

参考答案

一个项目的样式越来越难维护，通常不是同一个问题在反复出现。有时是两个组件都叫 .title，互相污染；有时是组件库规则总盖过业务规则；有时是颜色散落在几十个文件里，改主题要逐个查找。

CSS Modules、层叠层和自定义属性分别处理这三类问题：名字属于谁、冲突时谁优先、样式值从哪里来。 它们可以一起用，不需要把其中一种当成包办所有问题的方案。

CSS Modules：把类名归到组件模块

以 Vite 项目为例，Card.module.css 会按 CSS Modules 处理，导入后得到源类名到构建类名的映射。

CSS
/* Card.module.css */
.card {
  padding: 1rem;
  border: 1px solid var(--border-color, #cbd5e1);
}

.title {
  margin-block: 0 0.5rem;
  font-size: 1.25rem;
}
JSX
import styles from './Card.module.css';

export function Card({ title, children }) {
  return (
    <section className={styles.card}>
      <h2 className={styles.title}>{title}</h2>
      {children}
    </section>
  );
}

另一个文件也可以定义 .title，构建工具会按配置生成不同的局部映射，降低偶然重名的风险。生成后的具体类名格式是构建实现细节，不应该让测试和业务逻辑依赖某段固定哈希。

这仍然是普通 DOM 和 CSS，不是 Shadow DOM。全局 h2 规则依然可能命中标题，祖先的 color 和自定义属性仍然可以继承进去，模块中直接写裸元素选择器也不会自动变成真正的 DOM 隔离。CSS Modules 主要管理局部标识符，不承诺隔绝所有外部样式。

@layer：让覆盖次序成为显式约定

假设第三方组件库有一个很长的按钮选择器，业务方不希望为了覆盖它而写得更长，可以给不同来源安排层次：

CSS
@layer reset, vendor, components, overrides;

@layer vendor {
  .panel .toolbar .button {
    color: #64748b;
  }
}

@layer components {
  .button {
    color: #1d4ed8;
  }
}

假设两条规则都匹配同一个按钮，而且都是普通作者声明，后面的 components 层优先。因此较短的 .button 可以覆盖前一层的长选择器，不需要通过堆叠 class 来赢得选择器特异性比较。

层顺序由首次建立层的次序决定，开头的声明固定了架构。以后在其他文件追加 @layer components { ... }，是给同一层加规则，而不是把该层重新排到最后。

需要注意两个例外：普通的未分层声明高于层内普通声明；!important 的层顺序会反转，早期层的重要声明更优先。因此只把业务代码放进层里、却把组件库留在层外，可能达不到“业务覆盖库”的目的。可以按构建方式把第三方 CSS 导入指定层，例如使用带 layer(vendor) 的 @import，并核对最终产物。

层叠层也不是命名空间：两个层中同名的选择器仍然能匹配同一个元素，只是声明有了明确的排序位置。CSS Modules 和层叠层因而可以协作，前者减少误匹配，后者管理有意发生的覆盖。

自定义属性：把主题值从具体组件中提出来

CSS
:root {
  --surface-color: #fff;
  --text-color: #0f172a;
  --border-color: #cbd5e1;
}

[data-theme="dark"] {
  --surface-color: #0f172a;
  --text-color: #e2e8f0;
  --border-color: #475569;
}

.card {
  color: var(--text-color);
  background: var(--surface-color);
  border-color: var(--border-color);
}

把 data-theme="dark" 放在整个页面或某个区域上，后代卡片就可以继承这一组值。普通的 --name 自定义属性参与层叠并默认继承，组件使用 var() 时读取的是自己所处位置的计算结果，不是构建时简单把一段文本全局替换掉。

语义名字比外观名字更方便换主题。--surface-color 表示表面背景这一用途，换成深色仍然合理；--white 如果后来装入深灰色，名字就与实际语义脱节。另一方面，也不必把每一个只用一次的边距都升级为全局 token，应该暴露确实需要跨组件共享或由外部配置的值。

var 的回退值不是类型检查器

CSS
.card {
  --text-color: 16px;
  color: red;
  color: var(--text-color, blue);
}

--text-color 已有值 16px，所以 blue 不会因为它“不像颜色”就自动启用。替换进 color 后，这个声明在计算值阶段无效；对于可继承的 color，会按相关缺省规则继承，而不是重新返回前面那条 color: red。

var(--name, fallback) 主要处理被引用变量缺失或具有保证无效值等情况，不保证任意已定义值都适合目标属性。需要限定类型时可以考虑 @property，但注册也会改变初始值、继承等规则，必须有意识地设计。

实践中可以把全局主题变量放在统一入口，组件内部用 CSS Modules，第三方、组件和业务覆盖通过层组织。出现样式冲突时，先判断是类名边界、层顺序还是变量作用域出了问题，不要把所有问题都归为“权重不够”。
