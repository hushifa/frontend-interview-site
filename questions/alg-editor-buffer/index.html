文本编辑器为什么不能只用一个字符串保存全文？

字符串不可变，在大文档中间插入一个字符就要复制整段内容。Piece Table 保留原始文本和一个只追加的缓冲区，用片段列表描述当前文档，插入删除只改片段；Rope 把文本拆成平衡树，适合超大文本的随机编辑。数据结构解决存储问题，渲染和协同编辑是另外的层次。

参考答案

简答

  • JavaScript 字符串不可变，每次在中间插入都要生成新字符串，复制量与文档长度成正比；大文件里连续输入时开销明显。
  • Piece Table 由三部分组成：只读的原始文本、只追加的 added 缓冲区、按顺序指向这两个缓冲区的片段列表。插入只追加文本并拆分片段，删除只移除片段，原文从不修改。
  • 片段列表用数组时，定位要遍历片段，复杂度与片段数成正比；VS Code 把片段放进红黑树，按偏移量定位是 O(log n)。
  • Rope 把文本切块放在平衡二叉树的叶子上，插入、删除、按位置访问都是 O(log n)，适合超大文本。
  • 光标、选区、换行索引、语法高亮和协同同步（OT、CRDT）是建立在文本存储之上的独立问题。

不同结构的取舍

结构中间插入内存特点适用
单个字符串复制整段 O(n)最紧凑短文本、表单输入
字符数组移动后续元素 O(n)每个字符一个元素，开销大几乎不用
行数组只复制所在行按行存储，跨行操作麻烦简单的代码编辑器
Piece Table拆分片段，与文档长度无关原文不复制，撤销容易实现VS Code
RopeO(log n)树节点有额外开销超大文本、并发编辑

Piece Table 实现

JavaScript
class PieceTable {
  constructor(text = '') {
    this.original = text;
    this.added = '';
    this.pieces = text ? [{ buffer: 'original', start: 0, length: text.length }] : [];
  }

  get length() {
    return this.pieces.reduce((sum, piece) => sum + piece.length, 0);
  }

  read() {
    return this.pieces
      .map(({ buffer, start, length }) => this[buffer].slice(start, start + length))
      .join('');
  }

  // 在 offset 处切开，返回切点右侧第一个片段的下标。
  #split(offset) {
    let cursor = 0;
    for (let index = 0; index < this.pieces.length; index++) {
      const piece = this.pieces[index];
      if (cursor === offset) return index;
      if (offset < cursor + piece.length) {
        const leftLength = offset - cursor;
        this.pieces.splice(
          index,
          1,
          { ...piece, length: leftLength },
          { ...piece, start: piece.start + leftLength, length: piece.length - leftLength },
        );
        return index + 1;
      }
      cursor += piece.length;
    }
    return this.pieces.length;
  }

  insert(offset, text) {
    if (!Number.isInteger(offset) || offset < 0 || offset > this.length) {
      throw new RangeError('插入位置超出范围');
    }
    if (text === '') return;
    const piece = { buffer: 'added', start: this.added.length, length: text.length };
    this.added += text;
    this.pieces.splice(this.#split(offset), 0, piece);
  }

  delete(offset, count) {
    if (
      !Number.isInteger(offset) || !Number.isInteger(count) ||
      offset < 0 || count < 0 || offset + count > this.length
    ) {
      throw new RangeError('删除范围超出文本');
    }
    if (count === 0) return;
    const start = this.#split(offset);
    const end = this.#split(offset + count);
    this.pieces.splice(start, end - start);
  }
}

const doc = new PieceTable('hello world');
doc.insert(5, ',');
doc.insert(12, '!');
doc.delete(0, 1);
doc.insert(0, 'H');
console.log(doc.read()); // Hello, world!
console.log(doc.added); // ,!H

实测用 2000 组随机插入删除序列，与直接拼接字符串的结果逐步对比，全部一致。

几点说明：

  • 删除时先在两端切开，再移除中间的片段，original 和 added 都不改动，所以撤销只需要恢复旧的片段列表。
  • 这里的偏移量按 UTF-16 码元计算，与 JavaScript 字符串下标一致。真实编辑器还要避免把光标落在代理对或组合字符的中间。
  • 演示版每次操作都遍历片段数组。长时间编辑后片段会越来越多，实际实现会用平衡树按偏移量定位，并缓存每个片段内的换行位置，以便快速按行号跳转。

常见追问

  • 撤销怎样实现？ 每次操作记录被替换的片段，撤销时放回去；因为缓冲区只追加，旧片段指向的文本一直有效。
  • 为什么 contenteditable 不够用？ 它把文档状态放在 DOM 里，浏览器之间的行为差异大，难以控制选区和撤销栈。ProseMirror、Lexical 等编辑器自己维护文档模型，再把结果渲染到 DOM。
  • 大文件怎样渲染？ 只渲染可视区域的行，配合行索引快速找到首行位置，原理和虚拟列表相同。
