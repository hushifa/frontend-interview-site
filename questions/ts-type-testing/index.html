TypeScript 复杂类型应该怎样测试？

公共 API 的类型应像代码一样测试：正向用例检查推断结果是否精确，负向用例用 @ts-expect-error 确认非法调用会报错，再用 Equal 类型或 expectTypeOf 检查类型完全相等以发现退化成 any。类型测试放进与发布一致的 tsc --noEmit 检查，与运行时测试互不替代。

参考答案

简答

  • 正向测试：把结果赋给期望类型的变量，能检查"至少这么精确"，但 any 会让它总是通过。
  • 负向测试：// @ts-expect-error 断言下一行必须有错误，没有错误时它自身报错；@ts-ignore 无条件吞掉错误，不能用于测试。
  • 精确相等：用 Equal<A, B> 工具类型，或 Vitest 的 expectTypeOf(x).toEqualTypeOf<T>()。
  • 测试联合输入、只读输入、空数组、never 等边界，以及从包名导入的真实入口。
  • 类型测试的结果依赖 strict、exactOptionalPropertyTypes 和 TypeScript 版本，配置要与发布时一致。

正向与负向

TypeScript
function wrap<T>(value: T): { value: T } {
  return { value };
}

const literal: 'ready' = wrap('ready' as const).value;

// @ts-expect-error 字符串不能赋给 number
const impossible: number = wrap('text').value;

@ts-expect-error 只证明"有错误"，不证明是预期的那个错误。注释后写清原因，并让每条只覆盖一个表达式。

精确相等

TypeScript
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;

type Cases = [
  Expect<Equal<ReturnType<typeof wrap<number>>, { value: number }>>,
  // @ts-expect-error any 与 number 不相等
  Expect<Equal<any, number>>,
];

普通赋值无法区分 any，这个技巧利用了编译器对两个泛型函数类型是否相同的比较。

用 Vitest

TypeScript
// wrap.test-d.ts
import { expectTypeOf, test } from 'vitest';
import { wrap } from './wrap';

test('wrap 保留输入类型', () => {
  expectTypeOf(wrap(1)).toEqualTypeOf<{ value: number }>();
  expectTypeOf(wrap).parameter(0).toBeUnknown();
});

vitest --typecheck 会对 *.test-d.ts 运行 tsc，不执行代码。tsd、@arethetypeswrong/cli 适合检查发布后的包。

重载与联合

TypeScript
declare function parse(value: string): number;
declare function parse(value: number): string;

const fromText: number = parse('42');
declare const input: string | number;
// @ts-expect-error 没有接受联合的公开签名
parse(input);

如果业务需要接受联合，修改 API 并更新测试，而不是删掉测试。

与运行时测试的分工

类型测试证明编译器接受或拒绝某些写法；运行时测试证明 JavaScript 行为正确。.d.ts 写错时运行时测试发现不了，JSON.parse 的结果是否合法类型测试也管不了。库项目两者都需要。

常见追问

  • 类型测试放在哪里？单独的 *.test-d.ts 或 type-tests/ 目录，并纳入 CI 的 tsc --noEmit。
  • 升级 TypeScript 后测试失败怎么办？逐条看新增或消失的诊断，判断是修正了旧的错误推断还是 API 真的变了，再决定改实现还是改测试。
