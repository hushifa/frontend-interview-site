TypeScript 复杂类型应该怎样测试？

公开 API 的类型也要像代码一样写测试：检查推断结果是否精确，检查非法调用会不会报错，再用精确相等判断防止类型悄悄退化成 any。类型测试和运行时测试互相替代不了。

参考答案

简答

类型测试测的是“编译器接受什么、拒绝什么”。正向测试是把结果赋给期望类型的变量，能检查结果至少这么精确；负向测试是在非法调用上面写 // @ts-expect-error，下一行必须有错误，没有错误它自己就报错。@ts-ignore 不行，它不管有没有错误都吞掉，不能用来测试。

光靠赋值还不够，因为 any 能赋给任何类型，类型退化成 any 了测试照样通过。所以要用精确相等检查，比如自己写一个 Equal<A, B> 工具类型，或者用 Vitest 的 expectTypeOf(x).toEqualTypeOf<T>()。

测试要覆盖边界：联合类型输入、只读输入、空数组、never，还有从包名导入的真实入口。

要注意，类型测试的结果跟 strict、exactOptionalPropertyTypes 和 TypeScript 版本有关，配置要和发布时一致。它也替代不了运行时测试，两者测的是不同的东西。

正向测试和负向测试

TypeScript
function wrap<T>(value: T): { value: T } {
  return { value };
}

const literal: 'ready' = wrap('ready' as const).value;

// @ts-expect-error 字符串不能赋给 number
const impossible: number = wrap('text').value;

第一行是正向测试：结果能赋给 'ready'，说明 wrap 保留了字面量类型。第二行是负向测试：字符串不该能赋给 number，所以这里应该报错；哪天 wrap 改坏了、返回了 any，这一行不再报错，@ts-expect-error 自己就会报“未使用的指令”。

可 @ts-expect-error 只能证明“这里有错误”，不能证明是你预期的那个错误。所以注释后面要写清原因，每条只覆盖一个表达式，免得别的错误混进来。

为什么需要精确相等

TypeScript
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;

type Cases = [
  Expect<Equal<ReturnType<typeof wrap<number>>, { value: number }>>,
  // @ts-expect-error any 与 number 不相等
  Expect<Equal<any, number>>,
];

普通赋值区分不了 any：any 能赋给 number，number 也能赋给 any，看起来“相等”。Equal 这个写法把 A 和 B 各放进一个泛型函数类型里，再比较这两个函数类型。编译器比较这种类型时要求两边完全相同，any 和 number 就会被判为不相等。Expect 只接受 true，结果是 false 就报错。

用 Vitest 写类型测试

TypeScript
// wrap.test-d.ts
import { expectTypeOf, test } from 'vitest';
import { wrap } from './wrap';

test('wrap 保留输入类型', () => {
  expectTypeOf(wrap(1)).toEqualTypeOf<{ value: number }>();
  expectTypeOf(wrap).parameter(0).toBeUnknown();
});

toEqualTypeOf 做的就是精确相等检查。运行 vitest --typecheck 时，它会对 *.test-d.ts 文件跑 tsc，只做类型检查，不执行代码。检查已发布的包，可以用 tsd 或 @arethetypeswrong/cli。

重载和联合要单独测

TypeScript
declare function parse(value: string): number;
declare function parse(value: number): string;

const fromText: number = parse('42');
declare const input: string | number;
// @ts-expect-error 没有接受联合的公开签名
parse(input);

重载函数传联合会报错，这正是它的行为，测试把它锁住了。如果业务确实需要接受联合，应该改 API、同时更新测试，而不是直接删掉这条测试。

和运行时测试怎么分工

类型测试证明编译器接受或拒绝某些写法；运行时测试证明 JavaScript 真正跑起来是对的。.d.ts 写错了，运行时测试发现不了；JSON.parse 出来的数据合不合法，类型测试也管不了。所以写库的项目两种测试都需要。

常见追问

类型测试放在哪里？

放在单独的 *.test-d.ts 文件或 type-tests/ 目录里，并且纳入 CI 的 tsc --noEmit 检查。

升级 TypeScript 以后类型测试失败了怎么办？

逐条看新增或消失的报错，判断是新版本修正了以前错误的推断，还是 API 的行为真的变了，再决定改实现还是改测试。
