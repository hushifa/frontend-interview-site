BFF 聚合接口怎样设计才能避免把前端耦合到后端细节？

以题目详情页聚合多个后端服务为例，BFF 按页面定义输出契约，用整体超时和分支截止时间并行调用下游，区分核心数据与可降级数据，返回前端可恢复的错误，并在缓存、版本和观测上划清边界。

参考答案

简答

题目详情页要显示正文、收藏状态和推荐列表，这三样来自三个后端服务。BFF 就是专门给这个页面准备的一层接口：它去调三个服务，再拼成页面要的样子返回。页面只认 BFF 定的字段，下游改了字段名，在 BFF 里适配就行，前端不用跟着改。

三个下游互不依赖，所以并行调用。整次请求有一个总超时；推荐这类可有可无的数据，再给一个更短的截止时间，超时就返回默认值，并在 warnings 里标出来。

正文这种核心数据失败了，返回明确的错误码；可选数据失败了，页面主体照常显示。

另外要注意，公共数据和个性化数据分开缓存；每个下游的耗时和状态都要记下来，否则页面慢了不知道是谁拖的。

页面拿到的应该是什么样的数据

如果浏览器直接调用三个服务，就要处理三套认证、三种错误格式，还容易形成请求瀑布。BFF 只给页面一个接口，返回页面需要的模型：

json
{
  "question": { "id": "js-event-loop", "title": "事件循环" },
  "bookmarked": true,
  "recommendations": [],
  "warnings": ["recommendations"]
}

字段名、空值怎么表示、分页和错误格式，都由 BFF 这份约定决定，这份约定叫契约。内部 ID、下游令牌和调试堆栈不应该发给浏览器。

怎样并行调用，又不让慢服务拖住页面

下面的代码里，核心的 loadQuestion 直接参与 Promise.all，两个可选分支被 optional 包了一层：

JavaScript
function withDeadline(run, ms, parentSignal) {
  return run(AbortSignal.any([parentSignal, AbortSignal.timeout(ms)]));
}

async function optional(promise, fallback, warnings, name) {
  try {
    return await promise;
  } catch {
    warnings.push(name);
    return fallback;
  }
}

async function loadQuestionPage({ questionId, user, signal }, api) {
  // 客户端断开或整体超时都会取消所有下游调用。
  const page = AbortSignal.any([signal, AbortSignal.timeout(2500)]);
  const warnings = [];

  const [question, bookmarked, recommendations] = await Promise.all([
    api.loadQuestion(questionId, page),
    optional(
      user ? withDeadline((s) => api.loadBookmark(user.id, questionId, s), 800, page) : false,
      false,
      warnings,
      'bookmark',
    ),
    optional(
      withDeadline((s) => api.loadRecommendations(questionId, s), 800, page),
      [],
      warnings,
      'recommendations',
    ),
  ]);

  return { question, bookmarked, recommendations, warnings };
}

用模拟下游实测：推荐服务需要 5 秒时，800 毫秒后被取消，接口约 0.8 秒返回正文、收藏状态和空推荐，warnings 为 ['recommendations']。

你可能会问，Promise.all 不是有一个失败就整体失败吗？没错，所以可选分支被 optional 包住了，出错时它返回默认值而不是抛错。只有核心的 loadQuestion 失败，才会让整个请求失败。

可选分支的截止时间是 800 毫秒，比整体的 2500 毫秒短。如果只有整体超时，一个慢的推荐服务就能把整个页面拖到 2.5 秒。

取消信号要一路传到 fetch、数据库查询这些下游调用里，客户端断开以后服务端才会真的停下来。不过取消只能停止等待，已经发出去的写请求不会被撤销。

出错时前端拿到什么

情况BFF 的响应
题目不存在404，稳定的 code，例如 QUESTION_NOT_FOUND
未登录正文正常返回，bookmarked 为 false，前端显示登录入口
推荐服务失败正文正常返回，推荐为空，warnings 中标记
核心服务超时504 或 503，带 code 和请求 ID，前端可以提示重试

返回给前端的错误包含 code、可以直接显示的 message 和请求 ID。日志里记下游名称、耗时和状态，不记 Cookie、令牌和用户内容。

权限由谁来管

BFF 根据会话决定返回哪些字段，可下游服务仍然要做自己的授权检查，因为调用方可能绕过 BFF 直接访问下游。传给下游的用户身份，由 BFF 根据会话生成，不能取前端提交的 userId。输入校验、SSRF 和请求头转发等问题见《前端工程师编写 Node 服务时需要守住哪些安全边界？》。

缓存和版本怎么处理

公共正文可以按内容版本或短 TTL 缓存；收藏状态是个性化数据，不能放进共享缓存。缓存键要包含语言这类真正影响结果的维度。

BFF 的输出契约独立演进。下游字段改名时，在 BFF 里做适配，并用契约测试提前发现不兼容的改动。

怎样观测和测试

每个下游调用都要记录耗时和结果，并用 trace ID 把前端、BFF 和下游的日志串起来。测试至少覆盖这几种情况：全部成功、可选服务超时、核心服务失败、下游返回格式错误、客户端提前断开。

常见追问

什么时候不该用 BFF？

只有一个后端、页面直接调用就够用的时候，BFF 只会多一层部署和延迟。多个客户端（Web、App）需求差异大、需要聚合多个服务时，才值得引入。

为什么不用 Promise.allSettled？

它会等所有分支都结束，一个慢的可选服务照样能拖住响应。给每个可选分支加截止时间，才能控制总耗时。
