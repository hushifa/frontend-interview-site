浅拷贝、深拷贝和 structuredClone 如何选择？

展开语法和 Object.assign 通常只复制一层可枚举自身属性；嵌套对象仍共享引用。深拷贝则要根据业务决定如何处理循环引用、日期、Map、Set、原型以及函数等特殊值。

参考答案

展开语法和 Object.assign 通常只复制一层可枚举自身属性；嵌套对象仍共享引用。深拷贝则要根据业务决定如何处理循环引用、日期、Map、Set、原型以及函数等特殊值。

在“浅拷贝、深拷贝和 structuredClone 如何选择？”这个问题中，先记录输入、调用顺序和副作用，再观察同步、异步和清理发生的时间；结果相同的写法也要比较可读性和取消方式。这里的 拷贝、structuredClone、引用 不是孤立的 API 名称，而是会共同影响输入、过程和最终结果。

理解这类问题时，可以把过程拆成表达式求值、函数调用、任务排队和副作用清理四步。先写一个只包含关键变量的最小例子，再逐步加入闭包、异常或异步操作，能更容易看出结果是在哪一步产生的。

structuredClone 支持许多结构化数据以及循环引用，还可转移某些可转移对象。它不支持函数和 DOM 节点，也不是保持所有自定义原型、访问器和属性描述符的万能复制。JSON 序列化会丢失或改变 undefined、特殊数值、日期等信息，且不能直接处理循环引用。

状态更新通常只需要复制被修改的路径，而不是每次深拷贝整个状态树。选择方案前应写清楚输入数据的类型边界，以及是否允许原对象失去可转移资源。

可运行示例

JavaScript
const source = { child: { count: 1 } };
const shallow = { ...source };
const deep = structuredClone(source);
shallow.child.count = 2;
console.log(source.child.count);
console.log(deep.child.count);

输出依次为：2、1。

如果几个写法都能得到同样输出，还要比较可读性、执行时机、内存占用和取消方式。涉及 Promise、事件或资源时，完成结果和清理结果要分别验证。

实际项目里，搜索框、定时器、事件监听和请求经常同时存在。先写出每一步的触发顺序，再决定在哪里更新状态、在哪里清理资源，能避免“结果看起来对，但偶尔重复、过期或无法取消”的问题。
