Vue 大型页面应从哪些方面优化更新开销？

更新优化应先定位计算、组件更新、DOM 数量或布局绘制的真实成本，再选择稳定 props、派生数据、浅层状态或虚拟化。缓存与编译优化不能替代清楚的数据边界，也不能用错误的跳过更新换取表面流畅。

参考答案

页面卡顿可能来自不同阶段：输入后执行了昂贵筛选，很多子组件收到变化的 prop，大量 DOM 需要布局，或者只是网络结果尚未到达。先用浏览器 Performance、Vue DevTools 等观察真实交互，再决定改哪一层。

“少渲染几个组件”和“首屏少下载一些 JavaScript”也不是同一个优化。代码分割、静态生成和 SSR 可以改善交付路径，但不能自动解决每次输入时的长任务。

让子组件只接收真正变化的值

列表行如果每行都接收 activeId，那么选中项改变时，所有行都看到这个 prop 改变。可以由父级先算出每行自己的 active，再传给子组件：

vue
<!-- TopicRow.vue -->
<script setup>
import { onUpdated } from 'vue';
const props = defineProps({ id: String, title: String, active: Boolean });
const emit = defineEmits(['select']);
onUpdated(() => console.log('更新行：', props.id));
</script>

<template>
  <button type="button" :aria-pressed="props.active" @click="emit('select', props.id)">
    {{ props.title }}
  </button>
</template>
vue
<!-- Parent.vue -->
<script setup>
import { ref } from 'vue';
import TopicRow from './TopicRow.vue';
const activeId = ref('html');
const topics = [
  { id: 'html', title: 'HTML' },
  { id: 'css', title: 'CSS' },
  { id: 'vue', title: 'Vue' },
];
</script>

<template>
  <ul>
    <li v-for="topic in topics" :key="topic.id">
      <TopicRow :id="topic.id" :title="topic.title" :active="topic.id === activeId"
        @select="activeId = $event" />
    </li>
  </ul>
</template>

从 HTML 切换到 CSS 时，主要变化的是旧行的 active 从 true 变 false、新行从 false 变 true，其余行的相关 props 保持不变。日志可用于观察这个小例子，不应作为整个页面的性能基准。

这不意味着父级无需遍历列表，也不意味着子组件永远不会因自己的响应式依赖而更新。它只是让父级传递的变化范围更符合业务事实。

减少重复计算与无意义的身份变化

筛选、排序和统计通常可以通过 computed 表达，而不是用多个 watch 维护重复结果。依赖不变时可复用计算，相关值变化时再更新。

但每次计算都创建一个新对象或新数组，可能让下游看到新的身份，即使业务内容没变。Vue 的计算稳定性优化也需要结合实际返回值理解，不能假定所有内容相同的新对象都会自动被深度比较并跳过。

频繁传递新配置对象、把整份大数据传给每个小组件，或让一个输入影响整页无关内容，都值得先检查。缩小依赖与组件更新范围，通常比到处添加缓存指令更容易保持正确。

浅层响应式必须配合清楚的更新约定

JavaScript
import { nextTick, shallowRef, watchEffect } from 'vue';

const rows = shallowRef([{ id: 'a', title: '原内容' }]);
const seen = [];
const stop = watchEffect(() => seen.push(rows.value[0].title));

rows.value[0].title = '直接改内部';
await nextTick();
console.log(seen.join(',')); // 原内容

rows.value = [{ ...rows.value[0], title: '替换根值' }];
await nextTick();
console.log(seen.join(',')); // 原内容,替换根值
stop();

shallowRef 不会按深层响应式方式追踪内部对象修改，通常通过替换根值表达新版本。某些场景也可以显式通知，但必须由接口清楚规定，不能一边依赖深层修改一边期待浅层 API 自动发现。

如果其他无关更新顺便重新读取了内部数据，界面可能偶尔显现出那次修改，这不表示它建立了正确的通知关系。浅层 API 适合按不可变方式管理的大结构或外部对象，不是一个加上就必然更快的开关。

大列表首先面对 DOM 规模

几万行即使每行只有很少计算，创建、布局、绘制和保留节点也会有成本。分页或虚拟列表可以减少同时存在的 DOM，但需要处理滚动位置、行高、焦点、键盘导航和动态内容。

虚拟化还可能卸载不可见行，因此本地草稿不能只放在随时会消失的行组件里。需要按稳定 ID 保存在合适位置，并设计返回可见区时怎样恢复。

稳定 key 能保持正确身份，但不能把一万个实际节点变成十个。更新身份和节点数量是不同问题。

v-once、v-memo 需要完整的正确性条件

v-once 适合真正只需要初始呈现的内容，后续相关状态变化不会按普通方式更新这段子树。v-memo 可以按依赖条件跳过一部分更新，但依赖必须包含决定这段内容需要变化的因素。

如果为了少更新而漏掉标题、权限或其他真实依赖，就可能留下旧界面。它们适合测量后确认的局部优化，不应成为修复错误状态设计的默认办法。

大型 v-for 场景还应按文档把指令与列表结构放在正确位置。只看某一次操作快了，不足以证明所有后续变化都仍然正确。

组件库要把插槽成本和性能契约说清楚

表格单元格插槽可能由业务方渲染输入框、图表或编辑器，组件库不能假设它永远是廉价纯文本，也不能为了优化跳过必需的插槽更新。提供分页、虚拟化和按需渲染入口时，应同时说明动态行高、固定列、展开行以及表单草稿的限制。

对于虚拟化的可交互内容，需要明确焦点移出可见范围后的策略，以及总行数和当前位置怎样向辅助技术表达。不能只减少 DOM 数量，却让正在编辑的行被卸载后丢失输入。原生表格与交互式 grid 的键盘契约不同，不应为了虚拟化随意添加 role 后忽略交互实现。

组件库文档可以记录测量所用的数据规模、浏览器与设备条件、插槽类型和推荐使用方式；这不是承诺任意业务插槽都能达到同样速度。回归场景应覆盖筛选、滚动、编辑、错误状态和卸载后的资源回收，不能只比较默认截图。

响应式之外还有很多成本

每帧交替读布局、改样式、再读布局，会造成同步布局压力；复杂阴影、大图片和动画也可能让绘制昂贵。网络瀑布、重复请求和过多依赖则需要数据层与构建层处理。

组件隐藏后仍运行轮询、观察器和计时器，也会消耗资源。优化应包含卸载、停用与后台场景，而不是只测第一次看到页面的速度。

最后建立可重复的交互场景，例如连续输入、切换选中项、滚动大列表或打开复杂面板，比较改动前后的耗时、内存与正确性。优化的结果应是用户更快得到正确反馈，而不是单纯让某个更新计数变小。
