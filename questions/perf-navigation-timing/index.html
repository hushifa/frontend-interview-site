Navigation Timing 的时间点能否代表页面已经可用？

PerformanceNavigationTiming 记录一次文档导航的网络和生命周期时间点，例如 responseStart、domContentLoadedEventEnd、loadEventEnd。通过相应差值可以分析阶段耗时，但不能单独证明页面已经可用。

参考答案

Navigation Timing 记录一次文档导航的网络与生命周期时间点，能帮助回答“时间花在哪个阶段”，但不能单独证明页面已经可用。

例如 HTML 很快加载完成，前端却在 load 之后才请求业务数据；或者内容已显示，但主线程仍被大任务占用，按钮点了没有反应。导航完成、内容出现和交互顺畅是不同维度。

时间点要相减，不能当绝对日期

PerformanceNavigationTiming 的时间值通常相对于当前文档的 timeOrigin，单位是毫秒，并不是 Unix 时间戳。普通导航条目的 startTime 为 0；需要与日志绝对时间关联时，应明确使用 timeOrigin 和相对值，而不是直接把字段传给 new Date。

常用差值可以这样理解：

差值可观察的阶段不能直接推出的结论
responseStart - startTime从导航开始到响应首字节全部时间都由后端计算造成
responseStart - requestStart请求发出到响应开始的等待精确的服务端业务执行时间
responseEnd - responseStart响应主体接收阶段一定只有网络传输成本
domContentLoadedEventEnd - startTime到 DOMContentLoaded 处理完成页面所有图片、数据和组件都就绪
loadEventEnd - startTime到 load 处理完成页面之后不会再加载或卡顿

请求等待可能包含网络往返、代理、缓存或服务端处理；DNS 与连接时间为零或重合，也可能与连接复用有关。应结合环境解释，不能看到一个数字就归因。

等 load 回调结束后再读 loadEventEnd

JavaScript
function readNavigationSummary() {
  const entry = performance.getEntriesByType('navigation')[0];
  if (!entry || entry.loadEventEnd === 0) return null;

  return {
    type: entry.type,
    firstByteMs: entry.responseStart - entry.startTime,
    responseBodyMs: entry.responseEnd - entry.responseStart,
    domReadyMs: entry.domContentLoadedEventEnd - entry.startTime,
    loadMs: entry.loadEventEnd - entry.startTime,
  };
}

function scheduleNavigationReport() {
  // 新任务执行时，当前 load 事件处理才有机会结束。
  setTimeout(() => {
    const summary = readNavigationSummary();
    if (summary) console.table(summary);
  }, 0);
}

if (document.readyState === 'complete') {
  scheduleNavigationReport();
} else {
  window.addEventListener('load', scheduleNavigationReport, { once: true });
}

在 load 监听器自身执行过程中，loadEventEnd 还可能为 0，因为事件处理尚未完成。示例通过后续任务读取，并再次检查完成状态。零值不是“瞬间完成”的通用含义，也可能表示时间点还未发生或信息不可用。

这段代码只输出当前文档的一次摘要，没有实现完整监控上报、重试或所有导航类型统计。

DOMContentLoaded 与 load 都不等于业务 ready

DOMContentLoaded 关注 DOM 解析与相关脚本执行条件，不要求所有图片都加载；load 等待相应依赖资源，但不包含页面此后主动发起的全部异步工作，懒加载资源也不能简单按普通阻塞资源理解。

业务可用应有自己的定义。例如订单列表的数据已经显示且筛选可操作，可以记录对应业务 mark/measure；再结合 LCP、INP 和错误率看用户体验。不要用一个笼统的 ready 标记同时表示网络完成、首屏绘制和全部功能可用。

SPA 与页面恢复要另行处理

普通 SPA 路由切换不会自动创建一条新的文档 navigation entry。反复读取第一条记录，只是在重复报告最初那次加载。路由切换应建立自己的起止标记，并处理并发导航、取消和缓存命中。

从往返缓存恢复页面，也不等于重新经历一次完整文档加载。可以结合 pageshow 的 persisted 等信息识别恢复；预渲染激活还涉及 activationStart。不要把普通导航、恢复和预渲染数据混成同一组再比较平均值。

排查时先确认采集时机和导航类型，再看阶段差值，最后与资源瀑布、主线程轨迹和真实业务指标交叉验证。Navigation Timing 是定位入口，不是页面体验的单一评分。
