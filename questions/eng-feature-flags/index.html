前端功能开关和灰度发布应该怎样设计？

区分功能开关、权限和实验分流，设计前后端一致的灰度判断、缓存更新、紧急关闭和开关清理流程，避免把隐藏按钮误当成安全控制。

参考答案

简答

  • 功能开关把"代码已部署"和"功能已上线"分开，用于灰度、紧急关闭和实验。
  • 开关不是权限：前端隐藏按钮只影响展示，服务端必须独立校验用户能否调用接口。
  • 灰度分流要用稳定的用户标识做哈希，让同一用户每次看到同一版本，前后端用同一份判断结果。
  • 开关值要有默认值和刷新策略，配置服务不可用时也能按安全的默认行为运行。
  • 每个开关都要有负责人和删除时间，发布完成后清掉分支代码。

开关的几种用途

类型目的生命周期
发布开关未完成功能先合入主干，按比例放量短，全量后删除
运维开关故障时关闭高成本功能（如推荐、实时预览）长期保留
实验开关A/B 测试，比较指标实验结束删除
权限/套餐决定谁有资格使用属于业务规则，不应混入开关系统

把这几类混在一个配置里，最常见的后果是"临时开关"活了好几年，或用开关代替权限校验。

分流要稳定且一致

JavaScript
async function bucket(userId, flagKey) {
  const data = new TextEncoder().encode(`${flagKey}:${userId}`);
  const hash = new Uint8Array(await crypto.subtle.digest('SHA-256', data));
  return ((hash[0] << 8) | hash[1]) % 100; // 0–99
}

const enabled = (await bucket(user.id, 'new-checkout')) < rolloutPercent;
  • 用 flagKey 参与哈希，不同开关的放量用户互不相关。
  • 不要用 Math.random()，否则刷新页面就换版本。
  • 放量比例只增不减时，已进入的用户保持在新版本。
  • 更稳妥的方式是由服务端计算结果，随页面数据或接口返回，前端只读取结果。这样前后端判断一致，接口也能按同一结果决定行为。

获取、缓存和失效

  • 首屏需要的开关随 HTML 或首个接口下发，避免页面先渲染旧版本再闪到新版本。
  • 配置服务超时或失败时使用代码里的默认值，默认值应选择保守行为（通常是旧功能）。
  • 长时间打开的页面可以定期刷新开关；紧急关闭需要服务端同时生效，不能依赖前端刷新。
  • 把用户所在分组记录到埋点和错误日志里，否则无法区分问题来自哪个版本。

安全边界

前端开关值可以被用户修改。新功能对应的接口要在服务端检查同一个开关和用户权限；未开放的功能代码如果包含敏感信息（如未公布的价格、内部接口），不应提前打进公开产物。

清理

每个开关登记负责人、用途和计划删除时间。全量后删除开关判断和旧分支代码，并在 CI 中统计长期存在的发布开关。开关组合越多，需要测试的路径越多。

常见追问

  • 灰度期间出问题怎样回滚？把比例调回 0 或打开运维开关，不需要重新部署；前提是新旧版本的数据格式兼容。
  • 开关能代替发布分支吗？可以减少长期分支，但需要配合测试两条路径。
