前端功能开关应该怎样设计？怎样分类、下发和清理？

功能开关把“代码已部署”和“功能已上线”分开。开关按用途分成发布、运维、实验几类，寿命不同，权限不该混进来。首屏开关随页面数据下发，配置服务失败时回到保守的默认值，紧急关闭要在服务端生效；前端隐藏按钮不是安全控制，每个开关都要有负责人和删除时间。

参考答案

简答

功能开关就是在代码里放一个判断，开关打开才走新功能。这样新代码可以先部署上线，等准备好了再打开，“代码已部署”和“功能已上线”就分开了。灰度发布、紧急关闭、A/B 实验都靠它。

开关按用途分几类：发布开关让没做完的功能先合进主干，全量后删除；运维开关在故障时关掉高成本功能，长期保留；实验开关服务 A/B 实验，实验结束删除。权限和套餐是业务规则，不该放进开关。

开关值最好由服务端算好，随首屏数据下发，前后端用同一份结果。开关要有默认值，配置服务挂了，也要按保守的行为运行，通常就是旧功能。

要注意两点。第一，开关不是权限，前端隐藏按钮只影响展示，接口必须在服务端单独校验。第二，每个开关都要有负责人和删除时间，全量以后把旧代码清掉。

开关有哪几种用途

开关按目的大致分几类，它们的寿命也不一样。

发布开关用来让还没做完的功能先合进主干，然后按比例放量，全量以后就该删掉，寿命很短。运维开关用来在故障时关掉高成本的功能，比如推荐、实时预览，它会长期保留。实验开关用于 A/B 测试，比较两组的指标，实验结束就删除。

还有一类经常被混进来，就是权限和套餐，决定谁有资格用某个功能。这其实是业务规则，不应该放进开关系统。

把这几类混在一个配置里，最常见的后果是“临时开关”活了好几年，或者有人拿开关代替权限校验。

按比例放量时怎样判断开关开没开

发布开关常常按比例放量，比如先给 5% 的用户打开。判断方式是用用户 ID 加开关名做哈希，得到 0 到 99 的桶号，桶号小于放量比例就打开。哈希让同一个用户每次落在同一个桶，刷新不会换版本；比例只增不减时，已经打开的用户也不会被关回去。分桶函数和验证示例见《前端怎样做 A/B 实验？分流、曝光和结论判断要注意什么？》。

更稳妥的做法是由服务端算出结果，随页面数据或接口一起返回，前端只读取结果。这样前后端的判断一定一致，接口也能按同一个结果决定行为。

开关值怎样获取和更新

首屏需要的开关，应该随 HTML 或第一个接口一起下发。否则页面会先按旧版本渲染，拿到开关后又闪成新版本。

配置服务超时或失败时，用代码里的默认值。默认值要选保守的行为，通常是旧功能。

页面打开很久的话，可以定期刷新开关。但紧急关闭必须在服务端同时生效，不能指望用户的前端去刷新。

另外，要把用户所在的分组记进埋点和错误日志。否则出了问题，你分不清它来自哪个版本。

为什么隐藏按钮不算安全控制

前端拿到的开关值，用户自己就能改。所以新功能对应的接口，必须在服务端检查同一个开关和用户权限。

还有一点容易忽略：没开放的功能代码如果包含敏感信息，比如还没公布的价格、内部接口，就不该提前打进公开的产物，因为产物谁都能下载。

开关用完怎样清理

每个开关都要登记负责人、用途和计划删除时间。全量以后，把开关判断和旧分支的代码一起删掉，还可以在 CI 里统计那些存在很久的发布开关。

清理很重要，因为开关组合越多，需要测试的路径就越多，代码也越难读。

常见追问

灰度期间出了问题，怎样回滚？

把放量比例调回 0，或者打开运维开关，不需要重新部署。如果是整站版本的灰度，回滚要在入口切流，见《前端怎样做灰度发布和金丝雀发布？出问题怎样回滚？》。前提是新旧版本的数据格式兼容，否则新版本已经写入的数据，旧版本可能读不了。

开关能代替发布分支吗？

可以减少长期存在的分支，大家都往主干合代码。但代价是新旧两条路径都要测试。
