WebCodecs 适合哪些浏览器端音视频场景？

区分 WebCodecs 与 HTMLMediaElement、Media Source Extensions 和 WebRTC，理解编码器生命周期与兼容性边界。

参考答案

WebCodecs 让应用接触编码器、解码器和音视频帧，适合浏览器视频剪辑、转码、帧分析或自定义低延迟媒体管道。它解决的是较底层的编解码控制，不是一套完整播放器或视频会议系统。

如果只是播放一个正常视频文件，video 元素通常更合适；只有需要控制帧级处理和输出时，才值得承担 WebCodecs 的额外复杂度。

文件、编码数据和原始帧是三个层次

MP4、WebM 等是容器，里面保存轨道、时间信息与编码数据；H.264、VP9、AV1 等是视频编码格式；VideoFrame 则表示解码后的帧或送入编码器的原始帧数据。

典型编辑流程是：文件解封装得到编码块，VideoDecoder 产生 VideoFrame，应用处理帧，VideoEncoder 产生编码块，最后重新封装成可播放文件。

WebCodecs 不自动替你完成容器解析和写出。把 MP4 整个 ArrayBuffer 塞进一个 EncodedVideoChunk，并不能让解码器自动理解所有文件结构；编码器输出的多个块直接拼接，也不保证得到有效 MP4。

配置必须对应实际编码数据

创建编码器或解码器时提供输出与错误回调，再按 codec、分辨率和必要的编码配置进行 configure。可以调用相应 isConfigSupported 检查配置，但支持结果不保证资源充足、硬件加速或后续每帧都成功。

解码还可能需要容器提供的初始化描述，以及正确的关键帧、时间戳和块顺序。VideoFrame 与编码块的时间信息通常使用微秒，不能把毫秒直接当微秒，也不能仅根据帧编号猜测可变帧率视频的时间。

有重排序的编码流中，提交顺序、显示顺序和时间戳并非总是简单一一递增，应该由容器解析和编解码规则共同决定。

队列与输出回调是异步的

encode 或 decode 提交工作，不是同步返回结果。输入提交过快时，队列与尚未消费的输出会增长，应结合 encodeQueueSize、decodeQueueSize 及相应通知管理背压。

队列变短不代表所有输出资源已经处理完。输出回调如果把每个 VideoFrame 都放进数组而从不释放，仍然可能消耗大量底层内存。

对不再需要的 VideoFrame 和 AudioData，应调用 close 释放资源引用。需要跨异步阶段保留或转移时，要明确所有权；不能关闭后又在另一个回调里继续使用同一帧。

flush、reset、close 不能互换

flush 用来等待此前排队的相应工作完成并交付输出，不是每一帧都必须调用的“发送按钮”。过度 flush 可能打断流水处理并增加等待。解码器 flush 后对后续关键帧等要求，也应按具体 API 规则处理。

reset 放弃当前待处理状态并回到需要重新配置的状态，不等于正常导出完成。close 释放编解码器资源并结束对象生命周期，关闭后不能继续拿同一个实例提交新工作。

发生错误、用户取消导出或页面离开时，应停止上游生产、清理队列和帧，并处理尚未完成的 Promise。只关闭编码器，却继续从摄像头生成帧，不能完成整个管道的取消。

与其他媒体 API 按职责组合

HTMLMediaElement 提供常见播放、缓冲和控制能力；MSE 让应用向媒体元素提供合适的编码媒体分段；WebRTC 处理实时通信中的连接、传输和相关协商。WebCodecs 提供编解码控制，不能直接替代它们的全部职责。

音视频同步、播放时钟、seek、丢帧、网络重传和文件封装都需要另行设计。若已有成熟库能满足需求，优先复用经过验证的管道，而不是从每个底层接口重新搭一套播放器。

兼容测试应覆盖实际 codec、profile、分辨率、设备和错误路径。API 名称存在不证明所有格式都可用，硬件与软件路径也会影响性能和耗电。真实媒体样本与目标设备验证，不能被一个空配置检测替代。
