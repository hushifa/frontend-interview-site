前端工程师编写 Node 服务时需要守住哪些安全边界？

Node 服务能访问网络、文件系统、子进程和密钥，权限远大于浏览器页面。所有输入和权限都要在服务端重新校验；下游地址由服务端决定以防 SSRF；文件路径和命令不拼接用户输入；请求体、超时和并发都要设上限，日志里不记录凭据。

参考答案

简答

  • 用户可以绕过页面直接调用接口，参数类型、长度、枚举和资源归属都要在服务端重新校验；认证确认身份，授权还要按资源逐项检查。
  • 不接受客户端传来的完整 URL 让服务端去请求，客户端只传业务 ID，由服务端选择固定的上游，否则会出现 SSRF。
  • 文件访问用服务端维护的 ID 映射，外部命令用 execFile 或 spawn 加参数数组，不经过 shell 拼接字符串。
  • 请求体大小、超时、并发和速率都要设上限；同步的重计算和回溯严重的正则会阻塞整个事件循环。
  • 日志和错误响应中不出现令牌、Cookie 和内部堆栈，依赖与生产凭据按最小权限管理。

输入与授权

JavaScript
function parseListQuery(query) {
  const page = Number(query.page ?? 1);
  if (!Number.isSafeInteger(page) || page < 1 || page > 1000) {
    throw new RangeError('page 必须是 1 到 1000 的整数');
  }
  const sort = query.sort ?? 'latest';
  if (!['latest', 'popular'].includes(sort)) {
    throw new RangeError('不支持的排序方式');
  }
  return { page, sort };
}

校验在服务端边界做一次，后续代码只使用校验后的值。客户端提交的 userId、role、价格不能当作事实，应从会话和数据库中取得。

认证回答"你是谁"，授权回答"你能不能操作这条数据"。只校验登录状态而不检查资源归属，用户改一下 URL 里的 ID 就能读到别人的数据，这是最常见的越权漏洞（IDOR）。

SSRF：下游地址由服务端决定

JavaScript
const UPSTREAM = 'https://catalog.internal.example';

async function loadProduct(productId, signal) {
  if (!/^[\w-]{1,64}$/.test(productId)) throw new RangeError('商品编号格式不正确');
  return fetch(`${UPSTREAM}/products/${encodeURIComponent(productId)}`, {
    signal: AbortSignal.any([signal, AbortSignal.timeout(3000)]),
    redirect: 'error',
  });
}

如果接口接受 ?url= 并替用户请求，攻击者就能让服务端访问内网服务或云厂商的元数据地址。确实需要抓取外部 URL 时，要限制协议和目标主机，解析 DNS 后拒绝内网地址段，禁止或逐跳校验重定向，最好再加一层网络出口限制。只检查字符串前缀不够：https://example.com.evil.net 也以 https://example.com 开头。

转发请求头时只带必要的几个。把浏览器的 Cookie、Authorization 原样转给所有上游，凭据就可能发到不该去的服务。

文件与命令

  • path.join(base, userInput) 无法阻止 ../ 穿越。按 ID 查表得到文件名最安全；必须接受路径时，path.resolve 后检查结果仍在允许的目录下，并考虑符号链接。
  • exec(\convert ${name}`) 会经过 shell 解析，name里的;、$()都能执行任意命令。改用execFile('convert', [name])。参数数组能防 shell 注入，但以 -` 开头的参数仍可能被工具当成选项，需要额外校验。
  • 不要用 eval、new Function 或 vm 处理用户数据，vm 不是安全沙箱。

资源上限

风险处理
超大请求体在框架解析前限制大小，例如 1MB，超出直接返回 413
下游不返回每个调用都有超时，整次请求有总预算
正则回溯避免嵌套量词，限制输入长度
暴力请求按 IP 或用户限流
同步重计算移到 Worker，见《Node.js Worker Threads 适合解决什么问题？》

Node.js HTTP 服务器的 requestTimeout 默认 300 秒，headersTimeout 默认 60 秒，限制的是接收完整个请求的时间，用来防慢速请求攻击，处理请求本身的耗时要靠业务代码里的超时来控制。

依赖与密钥

  • 密钥放在环境变量或密钥管理服务中，不提交到仓库，不写进前端构建产物。
  • 锁定依赖版本，在 CI 中运行 npm audit 等检查；安装脚本会以当前用户权限运行，不认识的包要先审查。
  • 错误响应只返回 code 和请求 ID，详细堆栈留在服务端日志里，日志同样要脱敏。

常见追问

  • BFF 已经校验过，下游还要校验吗？ 要。其他调用方可能绕过 BFF 直接访问下游，每个服务都要守住自己的边界。
  • Node.js 的权限模型能防住这些问题吗？ --permission 能限制进程读写哪些文件、能否创建子进程，可以减小漏洞被利用后的影响范围，但不能代替输入校验和授权。
