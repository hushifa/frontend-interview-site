前端工程师编写 Node 服务时需要守住哪些安全边界？

Node 服务能访问网络、文件系统、子进程和密钥，权限比浏览器页面大得多。所有输入和权限都要在服务端重新校验；下游地址由服务端决定以防 SSRF；文件路径和命令不拼接用户输入；请求体、超时和并发都要设上限，日志里不记录凭据。

参考答案

简答

写页面时，代码跑在用户的浏览器里，能做的事有限。写 Node 服务就不一样了，它能读写文件、发内网请求、启动子进程、拿到数据库密码。所以前端在页面上做的校验，到了服务端都要重新做一遍，因为用户完全可以绕过页面直接调接口。参数的类型、长度、取值范围要校验，“这条数据是不是你的”也要逐条检查。

有几类输入绝不能直接用。客户端传来的完整 URL 不能拿去请求，否则就是 SSRF，应该只收业务 ID，由服务端决定请求哪个上游。文件路径用服务端维护的 ID 映射；外部命令用 execFile 或 spawn 加参数数组，不经过 shell 拼字符串。

资源也要设上限：请求体大小、超时、并发和速率。另外同步的重计算和回溯严重的正则会卡住整个事件循环，所有请求都会跟着变慢。

最后，日志和错误响应里不要出现令牌、Cookie 和内部堆栈，依赖和生产凭据按最小权限管理。

为什么页面校验过了，服务端还要再校验

页面上的表单校验只是为了体验，攻击者可以用 curl 直接发请求。所以服务端要在入口把参数校验一遍，后面的代码只用校验后的值：

JavaScript
function parseListQuery(query) {
  const page = Number(query.page ?? 1);
  if (!Number.isSafeInteger(page) || page < 1 || page > 1000) {
    throw new RangeError('page 必须是 1 到 1000 的整数');
  }
  const sort = query.sort ?? 'latest';
  if (!['latest', 'popular'].includes(sort)) {
    throw new RangeError('不支持的排序方式');
  }
  return { page, sort };
}

客户端提交的 userId、role、价格，都不能当成事实，要从会话和数据库里取。

还有一个容易漏的点。认证回答的是“你是谁”，授权回答的是“你能不能操作这条数据”。如果只检查了登录状态，不检查资源归属，用户把 URL 里的 ID 改一下，就能读到别人的数据。这是最常见的越权漏洞，叫 IDOR。

为什么不能让客户端决定请求哪个地址

假设接口接受 ?url= 参数，替用户去抓取内容。攻击者就可以传一个内网地址，或者云厂商的元数据地址，让你的服务器帮他访问本来访问不到的东西。这种攻击叫 SSRF，服务端请求伪造。

稳妥的做法是客户端只传业务 ID，上游地址写死在服务端：

JavaScript
const UPSTREAM = 'https://catalog.internal.example';

async function loadProduct(productId, signal) {
  if (!/^[\w-]{1,64}$/.test(productId)) throw new RangeError('商品编号格式不正确');
  return fetch(`${UPSTREAM}/products/${encodeURIComponent(productId)}`, {
    signal: AbortSignal.any([signal, AbortSignal.timeout(3000)]),
    redirect: 'error',
  });
}

确实需要抓取外部 URL 时，要限制协议和目标主机，解析 DNS 后拒绝内网地址段，禁止重定向或者每一跳都重新校验，最好再加一层网络出口限制。只检查字符串前缀是不够的，https://example.com.evil.net 也是以 https://example.com 开头的。

转发请求头时也只带必要的几个。如果把浏览器的 Cookie、Authorization 原样转给所有上游，凭据就可能被发到不该去的服务。

文件路径和命令为什么不能拼用户输入

先说文件。path.join(base, userInput) 拦不住 ../，用户可以一路往上跳到任意目录，这叫路径穿越。最安全的是按 ID 查表得到文件名；必须接受路径时，path.resolve 之后检查结果还在允许的目录下，并考虑符号链接。

再说命令。exec(\convert ${name}`) 会交给 shell 解析，name里的;、$()都能让攻击者执行任意命令。改成execFile('convert', [name])，参数不经过 shell。不过参数数组只能防 shell 注入，以 -` 开头的参数仍可能被工具当成选项，需要额外校验。

还有，不要用 eval、new Function 或 vm 处理用户数据，vm 不是安全沙箱。

资源要设哪些上限

风险处理
超大请求体在框架解析前限制大小，例如 1MB，超出直接返回 413
下游不返回每个调用都有超时，整次请求有总预算
正则回溯避免嵌套量词，限制输入长度
暴力请求按 IP 或用户限流
同步重计算移到 Worker，见《Node.js Worker Threads 适合解决什么问题？》

Node.js HTTP 服务器的 requestTimeout 默认 300 秒，headersTimeout 默认 60 秒。它们限制的是接收完整个请求的时间，用来防慢速请求攻击。处理请求本身花多久，要靠业务代码里的超时来控制。

依赖和密钥怎么管

密钥放在环境变量或密钥管理服务里，不提交到仓库，也不能写进前端构建产物。

依赖要锁定版本，在 CI 里运行 npm audit 等检查。安装脚本会以当前用户的权限运行，不认识的包先审查再装。

错误响应只返回 code 和请求 ID，详细堆栈留在服务端日志里，日志同样要脱敏。

常见追问

BFF 已经校验过，下游还要校验吗？

要。其他调用方可能绕过 BFF 直接访问下游，每个服务都要守住自己的边界。

Node.js 的权限模型能防住这些问题吗？

--permission 能限制进程读写哪些文件、能不能创建子进程，漏洞被利用以后影响范围会小一些。但它代替不了输入校验和授权。
