跨窗口 postMessage 怎样避免把消息发给错误对象？

发送端应尽量指定准确的 targetOrigin，而不是无条件使用星号。接收端检查 event.origin、必要时检查 event.source，并校验消息结构和允许的操作，不能仅因为收到了消息就执行其中指令。

参考答案

假设主页面嵌入了一个跨源的图表 iframe，图表渲染完成后要告诉主页面“高度是 480 像素”。同源策略不允许双方随意读取彼此的 DOM，但可以通过 postMessage 发送约定好的数据。

风险在于：拿到窗口引用的其他页面也可能发消息；你保存的 iframe 窗口还可能导航到另一个网站。所以安全通信需要同时回答三个问题：要发给哪个源、收到的是哪个窗口发来的、这个消息允许做什么。

发送时把目标来源写准确

图表页面可以这样向主页面发送消息：

JavaScript
window.parent.postMessage(
  { type: 'chart:resize', version: 1, height: 480 },
  'https://app.example.com',
);

第二个参数是目标源，比较时涉及协议、主机和端口，不是某个具体页面路径。浏览器只会把消息交给符合该目标源的接收文档；如果目标窗口已经导航到攻击者的网站，就不会因为你还持有旧窗口引用而把消息交过去。

使用 '*' 会放弃这项目标限制。尤其不要把访问令牌、用户资料等敏感数据用星号发送。省略参数也不等于自动识别对方：当前 API 的默认目标是发送方自己的源，跨源通信应显式填写。

接收时不要只判断消息名称

主页面在 iframe 元素已经存在后安装以下监听器。假设该元素的 ID 是 chart-frame，预期加载 https://charts.example.com：

JavaScript
const chartFrame = document.querySelector('#chart-frame');
const chartOrigin = 'https://charts.example.com';

function handleChartMessage(event) {
  if (event.origin !== chartOrigin) return;
  if (event.source !== chartFrame.contentWindow) return;

  const data = event.data;
  if (data === null || typeof data !== 'object' || Array.isArray(data)) return;
  if (data.type !== 'chart:resize' || data.version !== 1) return;
  if (!Number.isInteger(data.height) || data.height < 100 || data.height > 1200) return;

  chartFrame.style.height = `${data.height}px`;
}

window.addEventListener('message', handleChartMessage);

// 组件卸载或不再使用图表时调用，避免留下重复监听器。
function disposeChartMessages() {
  window.removeEventListener('message', handleChartMessage);
}

这些判断各有用途：

  • origin 检查来自哪个源。必须完整比较，不能用 includes('example.com')，否则 example.com.attacker.test 等地址可能被误认。
  • source 检查是不是预期的那个 iframe 窗口。同一来源可能同时存在多个窗口，来源正确并不代表对象正确。
  • 结构与范围检查限制消息能力。这里最多允许调整一个合理范围内的高度，不允许任意修改 DOM 或执行命令。

postMessage 使用结构化克隆传输数据，可以直接发送对象，不要求先 JSON.stringify。接收后仍应做运行时校验；TypeScript 类型标注无法约束另一个页面实际发来的数据。

来源可信不代表消息内容可以直接执行

不要把消息中的字符串交给 eval，也不要直接赋给 innerHTML。即使来源在白名单中，对方也可能存在漏洞，或者把它收到的用户输入原样转发。通信协议应提供有限操作，例如调整高度、报告选中 ID，而不是提供“执行任意 JavaScript”的入口。

如果消息声称“支付成功”，主页面最多据此刷新订单，真正的支付状态仍应向可信服务查询。页面消息不是服务端业务授权凭证。

窗口导航和异步消息需要另外考虑

event.origin 表示消息发送时的来源，不保证那个窗口现在仍在同一个页面。回复消息前先完成来源和窗口校验，并使用明确的目标源；不要因已验证一次就永久信任窗口后续发来的所有消息。

对于请求与响应，还可加入 requestId 来区分并发请求，结合超时和页面会话标识丢弃旧响应。这些字段负责关联，不替代 origin/source 校验。同一个 iframe 导航后窗口引用可能继续存在，因此 source 相同也不代表文档实例未变。

沙箱 iframe 或 data URL 可能使用不透明源，收到的 origin 会是字符串 "null"。多个不相关文档都可能具有这个值，不能把 "null" 放进普通可信来源白名单。确实需要这种通信时，应另行设计受限能力和通道建立流程，而不是删除校验让它“先跑起来”。
