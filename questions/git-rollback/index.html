静态网站发布失败时怎样安全回滚？

回滚前先判断故障在源码、构建产物、托管配置还是缓存层，再恢复已验证版本并检查入口、资源和关键交互；撤销 Git 提交不等于线上已经恢复。

参考答案

简答

  • 回滚的目标是恢复用户可用的版本，先判断故障在代码、产物、DNS 还是缓存哪一层。
  • 发布记录应关联源码提交、锁文件、构建环境和产物，优先恢复已验证的旧产物。
  • 没有旧产物时，用对应锁文件和环境重新构建，不要按日期猜提交。
  • 共享分支用 revert 创建反向提交，保留历史。

回滚的目标是恢复用户可用性

“回到上一个提交”只是一个可能的手段。用户真正需要的是一个已知可用的网站版本，因此要先判断故障在哪一层：

现象优先检查
页面逻辑错误源码与对应构建产物
JS/CSS 404 或白屏资源前缀、入口和部署目录
域名打不开DNS、证书和托管绑定
新旧资源混用HTML、资源版本和缓存

DNS 出错时，撤销组件代码没有帮助；产物有问题时，也不应随意修改稳定的域名解析。先用正式域名检查状态码、入口 HTML、脚本和样式响应，再决定动作。

先找到真正可复现的上一版

发布记录应关联源码提交、锁文件、构建环境和最终产物。一个旧提交不一定能重新生成原来的文件，依赖、环境变量、外部数据和构建工具都可能变化。若平台保留已经验证的静态产物，直接恢复该产物通常比临时重新构建更可控。

没有旧产物时，使用对应锁文件和构建环境重新生成，并比较入口、资源清单、路由和必要验证文件。不要凭日期猜一个“看起来像上一版”的提交。

共享分支通常用 revert 表达撤销

已经共享的分支通常使用：

bash
git revert <bad-commit>
git push origin main

revert 创建一个新的反向提交，原提交仍在历史中，协作者可以正常同步，也能看出为什么撤销。它可能产生冲突，尤其是后续提交依赖了问题代码；解决后要检查最终 diff 和程序行为。

git reset 再强推会改变共享分支的历史，可能让别人本地分支出现重复提交或丢失工作。个人尚未共享的分支可以按团队规则使用 reset，但不能把它当作线上回滚的默认命令。撤销合并提交还要确认主线父提交，不能凭感觉填写。

源码、产物和线上是三件事

源码仓库出现 revert，不代表网站已经更新。若源码仓库和发布仓库分开，必须明确本次恢复的是哪一份产物，以及发布流程是否使用了它。HTML、JS、CSS、字体、数据和深链接入口应来自配套版本，不能只恢复首页。

恢复后验证正式域名，而不是只看本地开发服务器：检查首页、深链接、脚本样式、资源版本、主要交互和控制台错误。若平台部署有构建缓存，确认新产物确实已经成为当前版本。

缓存会让回滚看起来没有生效

CDN、浏览器和 Service Worker 可能分别保留旧入口或旧资源，已经打开的页面也可能继续使用当前内存中的代码。应使用带版本指纹的资源、正确的入口缓存策略和平台提供的定向失效能力，避免通过清空所有用户存储来“解决缓存”。那可能会删除草稿和偏好。

回滚后应观察新旧版本请求、错误率和资源命中情况。必要时引导用户刷新，但要保留未保存输入，不要无限自动刷新。

代码回滚不会撤销外部副作用

静态前端仍可能调用接口、上传文件或修改服务器数据。恢复旧 JavaScript 不会撤销已经完成的操作，也不保证旧客户端兼容刚升级的后端协议。需要时应先保证后端向前兼容，再通过状态查询、补偿操作或分阶段发布处理数据影响。

安全回滚的证据是：已知可用版本被发布，正式域名和关键路径验证通过，缓存与资源版本一致，监控显示故障下降，并且记录了没有被回滚覆盖的外部副作用。
