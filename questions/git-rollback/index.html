静态网站发布失败时怎样安全回滚？

回滚前先判断故障在源码、构建产物、托管配置还是缓存层，再恢复已验证版本并检查入口、资源和关键交互；撤销 Git 提交不等于线上已经恢复。

参考答案

简答

  • 先止损再排查：最快的回滚方式是把线上切回上一个已验证的构建产物，而不是改代码重新构建。
  • 回滚前判断问题在哪一层：源码、构建产物、托管配置（路由、响应头）还是 CDN 缓存，不同层的回滚方式不同。
  • 源码层面用 git revert 生成反向提交，保留历史；不要在共享分支上用 reset 加强推。
  • 回滚后检查入口 HTML、关键资源和核心流程，并确认 CDN 和浏览器缓存不再提供故障版本。
  • 数据格式或接口已经变化时，单纯回滚前端可能和后端不兼容，要先确认兼容性。

先定位层级

现象可能的层级回滚方式
新功能逻辑错误源码切回旧产物，随后 revert 提交
白屏、资源 404构建产物或部署过程切回旧产物，检查 base / publicPath
深链接 404、缺少响应头托管配置恢复配置，不需要动代码
部分用户仍看到旧或坏版本CDN / 浏览器缓存清除 CDN 缓存，检查缓存头

切回旧产物

能快速回滚的前提是每次发布的产物都被保留：

  • 托管平台：Netlify、Vercel、Cloudflare Pages 等保留每次部署，可以在控制台把某次历史部署重新设为生产版本。
  • 发布仓库（如 GitHub Pages）：在发布仓库中 revert 最近一次发布提交并推送，平台会重新部署上一版文件。
  • 对象存储加 CDN：资源按版本目录存放时，把入口 HTML 指回上一版目录。

这些操作不需要重新安装依赖和构建，几分钟内就能完成。

修复源码

bash
git revert <有问题的提交>
git revert -m 1 <合并提交>   # 撤销一次合并，保留主线一侧
git push

git revert 新增一个反向提交，别人的本地分支不受影响。之后要重新引入这个功能时，需要 revert 这个 revert 提交，或重新提交修复后的代码。

回滚后验证

  1. 用无缓存的方式请求入口 HTML，确认引用的是旧版本资源文件名。
  2. 打开关键页面，检查控制台没有资源加载错误。
  3. 走一遍核心流程，例如登录、搜索、提交。
  4. 如果入口 HTML 在 CDN 上设置了较长缓存，手动清除对应路径的缓存。

常见追问

  • 为什么不直接 git reset --hard 再强推？它会改写共享历史，别人基于新提交的工作会出错，而且托管平台不一定会因此重新部署。
  • 如何减少回滚需求？发布前在预览环境验证、灰度放量、保留旧资源一段时间，见《静态托管发布时为什么要检查资源路径和缓存？》。
