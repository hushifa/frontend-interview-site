静态网站发布失败时怎样安全回滚？

区分恢复代码、恢复构建产物和修复域名配置，说明 revert 的历史语义、回滚目标选择及缓存与旧页面的验证，避免把一次代码撤销当成全部恢复。

参考答案

回滚的目的，是让用户重新获得一个已知可用的版本。它不一定要求把 Git 分支指针移回过去，也不一定需要重新构建所有内容，先要确认故障属于哪一层。

问题更可能需要恢复或修复的对象
新页面代码有缺陷源码变更或相应静态产物
构建参数、资源前缀错误正确构建的产物与部署配置
DNS、证书、域名绑定失败域名和托管配置
新旧资源混用入口、资源版本和相关缓存策略

如果故障来自 DNS，撤销一个组件提交通常没有帮助；如果只是新产物有问题，也不应随意改变已经稳定的域名解析。

先确认“上一版可用”具体是哪一版

应该能从发布记录找到源码提交、构建环境、产物和线上版本的对应关系。一个旧提交不自动等于可以原样复现的旧产物：依赖、外部数据、构建变量或工具环境可能已经变化。

保留经过验证的发布产物，可以更直接地恢复对应文件；只有源码时，则应使用相应锁文件和环境重新构建，并检查结果。不要临时猜一个日期附近的提交就宣布恢复完成。

源码撤销通常可以用新的提交表达

git revert 会创建反向变更的新提交，原来的问题提交仍保留在历史中。这通常更适合已经共享的分支，协作者可以正常继续同步，也能看清为什么撤销。

它与 reset 后强推不是同一件事。后者改变共享分支所指向的历史，可能影响其他人的工作，并不能仅因名字叫“回滚”就认为没有协作成本。

revert 也可能冲突，特别是后续提交已经依赖被撤销的改动。撤销合并提交还涉及选择主线父提交，不能不看历史就随意填写参数。完成后仍需检查实际结果，而不是只看新提交是否创建成功。

恢复源码与恢复线上是两条步骤

源码仓库出现 revert，不代表网站已经更新；还要看发布流程是否使用了对应构建结果。发布仓库与源码仓库分开时，更应明确本次恢复的是哪份产物。

恢复静态文件时，要保证 HTML、脚本、样式和数据来自配套版本。域名文件、必要验证文件或平台配置也应按预期存在，不能只恢复首页后漏掉其他入口。

构建产物可以直接恢复，也可以重新发布对应版本，但都应有清楚的记录。不要把无关手工文件或用户数据混进同步删除范围。

缓存与已打开页面可能延后恢复效果

CDN、浏览器和 Service Worker 可能各自保留不同内容，已经打开的页面也可能继续引用某一版资源。重新发布成功，不保证所有客户端在同一时刻切换。

需要确认入口和资源的实际响应，必要时使用平台提供的针对性失效或恢复机制。不要把清空用户所有本地存储当成常规回滚步骤，否则可能丢掉尚未同步的草稿和偏好。

如果旧页面加载失败后需要刷新，应提供合理恢复路径，并考虑未保存输入；无限自动刷新既难排查，也可能让用户无法处理自己的数据。

回滚不能撤销所有外部副作用

即使是静态前端，也可能连接外部接口、上传文件或修改用户数据。退回旧 JavaScript，不会自动撤销已经完成的服务器操作，也不保证旧客户端仍兼容刚变更的后端协议。

因此回滚方案还要确认数据与接口兼容，必要时由相应服务提供补偿、状态查询或分阶段兼容。不要把代码版本恢复等同于整个系统时间倒流。

恢复后，用正式域名检查首页、深链接、关键资源和主要交互，再观察相关错误是否消失。保留故障线索，才能继续修复根因，而不是仅让下一次发布重复同一个问题。
