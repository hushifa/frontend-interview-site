pnpm workspace 怎样管理多包前端仓库？

解释工作区清单、workspace 协议和本地依赖链接，区分依赖与下游选择器，并说明打包时版本转换、隔离和 CI 冻结安装的作用。

参考答案

简答

  • 根目录的 pnpm-workspace.yaml 用 packages 字段列出工作区包所在目录。
  • 包之间用 workspace: 协议声明依赖，pnpm 只会链接本地包，找不到时直接报错，不会去 registry 下载同名包。
  • 发布或打包时，workspace:*、workspace:^ 等会被替换成真实版本号，使用者拿到的是普通依赖。
  • --filter 选择要执行命令的包，可以带上它的依赖或依赖它的下游包。
  • pnpm 的严格 node_modules 结构让包只能访问自己声明的依赖，可以发现"幽灵依赖"。

基本结构

yaml
# pnpm-workspace.yaml
packages:
  - 'apps/*'
  - 'packages/*'
json
// apps/web/package.json
{
  "name": "web",
  "dependencies": {
    "@acme/ui": "workspace:^"
  }
}

运行 pnpm install 后，apps/web/node_modules/@acme/ui 是指向 packages/ui 的链接，修改组件库源码会直接反映到应用里。

workspace 协议和发布时的替换

假设 @acme/ui 当前版本是 1.5.0：

声明发布后变成
workspace:*1.5.0
workspace:~~1.5.0
workspace:^^1.5.0
workspace:^1.5.0^1.5.0

替换只发生在 pnpm pack / pnpm publish 时，用 npm publish 发布不会转换，使用者会拿到无法安装的 workspace: 字符串。

用 filter 运行任务

bash
pnpm --filter web build          # 只构建 web
pnpm --filter "web..." build     # web 及它依赖的所有本地包
pnpm --filter "...@acme/ui" test # @acme/ui 及所有依赖它的包
pnpm -r build                    # 所有包，按依赖拓扑顺序

改了组件库后用 ...@acme/ui 跑下游测试，可以发现破坏性改动。CI 里还可以结合 --filter "[origin/main]" 只处理相对主分支有改动的包。

严格依赖隔离

pnpm 把真实文件放在全局内容寻址存储中，每个包的 node_modules 只包含它声明的依赖链接。如果 apps/web 代码直接 import 'lodash'，而 lodash 只是 @acme/ui 的依赖，在 pnpm 下会报找不到模块。这能尽早暴露没有声明的依赖，避免发布后在使用者环境里出错。

CI 中的用法

  • 提交 pnpm-lock.yaml，CI 使用 pnpm install --frozen-lockfile（CI 环境下默认开启）。
  • 用 packageManager 字段固定 pnpm 版本。
  • 构建和测试按依赖顺序执行，缓存按包粒度复用。

常见追问

  • 和 npm workspaces 有什么区别？npm 也支持工作区和 --workspace 选择，但不提供 workspace: 协议和严格隔离，默认会把依赖提升到根目录。概念和任务编排见《Monorepo 与 npm workspaces 能解决什么问题？》。
  • 公共依赖版本怎样统一？可以用 pnpm 的 catalog 功能或根目录 overrides 集中管理版本。
