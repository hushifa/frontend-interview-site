pnpm workspace 怎样管理多包前端仓库？

pnpm 用工作区清单列出本地包，用 workspace 协议链接本地依赖。文中区分依赖与下游选择器，讲打包时版本转换、严格隔离和 CI 冻结安装的作用。

参考答案

简答

pnpm 管理多包仓库，先在根目录放一个 pnpm-workspace.yaml，用 packages 字段列出哪些目录是工作区包。

包之间用 workspace: 协议声明依赖。这样 pnpm 只会链接本地的包，本地找不到就直接报错，不会去 registry 下载一个同名包。发布或打包时，workspace:*、workspace:^ 会被换成真实版本号，使用者拿到的是普通依赖。

运行命令时用 --filter 选择包，还能顺带选上它依赖的包，或者依赖它的下游包。

另外，pnpm 的 node_modules 结构很严格，每个包只能访问自己声明过的依赖，所以能发现“幽灵依赖”，也就是没声明却能用的依赖。

基本结构

先在根目录声明工作区，再让应用用 workspace: 协议依赖组件库。

yaml
# pnpm-workspace.yaml
packages:
  - 'apps/*'
  - 'packages/*'
json
// apps/web/package.json
{
  "name": "web",
  "dependencies": {
    "@acme/ui": "workspace:^"
  }
}

运行 pnpm install 以后，apps/web/node_modules/@acme/ui 是一个指向 packages/ui 的链接。所以改了组件库的源码，应用里马上就能看到。

发布时 workspace 协议会变成什么

workspace: 只在仓库里有意义，发出去的包里不能留着它。假设 @acme/ui 当前版本是 1.5.0，发布后的替换规则是：workspace:* 变成 1.5.0，workspace:~ 变成 ~1.5.0，workspace:^ 变成 ^1.5.0，workspace:^1.5.0 变成 ^1.5.0。

要注意，这个替换只在 pnpm pack 或 pnpm publish 时发生。如果用 npm publish 发布，不会转换，使用者会拿到一个装不上的 workspace: 字符串。

用 filter 选择要运行的包

bash
pnpm --filter web build          # 只构建 web
pnpm --filter "web..." build     # web 及它依赖的所有本地包
pnpm --filter "...@acme/ui" test # @acme/ui 及所有依赖它的包
pnpm -r build                    # 所有包，按依赖拓扑顺序

三个点写在哪边，意思不一样。写在后面的 web... 是往“上游”选，带上 web 依赖的包；写在前面的 ...@acme/ui 是往“下游”选，带上依赖它的包。

所以改了组件库以后，用 ...@acme/ui 跑一遍下游测试，就能发现破坏性改动。CI 里还可以结合 --filter "[origin/main]"，只处理相对主分支有改动的包。

严格隔离是怎样发现问题的

pnpm 把真实文件放在一个全局的内容寻址存储里，每个包的 node_modules 只放它声明过的依赖的链接。

假如 apps/web 的代码直接 import 'lodash'，可是 lodash 只是 @acme/ui 的依赖。在 npm 的提升结构下这可能能跑，在 pnpm 下就会报找不到模块。

所以 pnpm 能尽早暴露没声明的依赖，避免发布以后在使用者的环境里才出错。

CI 里怎样用

提交 pnpm-lock.yaml，CI 里用 pnpm install --frozen-lockfile，它在 CI 环境下默认开启。再用 packageManager 字段固定 pnpm 的版本。构建和测试按依赖顺序执行，缓存按包的粒度复用。

常见追问

pnpm 工作区和 npm workspaces 有什么区别？

npm 也支持工作区，也能用 --workspace 选择包。但它没有 workspace: 协议和严格隔离，默认会把依赖提升到根目录。Monorepo 的概念和任务编排见《Monorepo 与 npm workspaces 能解决什么问题？》。

多个包的公共依赖版本怎样统一？

可以用 pnpm 的 catalog 功能，或者在根目录用 overrides 集中管理版本。
