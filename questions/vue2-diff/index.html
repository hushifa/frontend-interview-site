Vue 2 的 diff 算法是怎样比较子节点的？

Vue 2 比较新旧两组子节点时，在两头各放一个指针，先试四种首尾配对，配不上再用 key 去找能复用的旧节点。Vue 3 先跳过首尾相同的部分，再用最长递增子序列减少移动，并靠编译信息跳过不变的内容。

参考答案

Vue 2 已于 2023-12-31 停止维护，本题 Vue 2 部分以 2.7 源码为准。

简答

diff 要回答的问题是：数据变了以后，新旧两组子节点怎么对应，哪些能复用、哪些要移动、哪些要新建或删除。Vue 只在同一个父节点的子节点之间比较，不跨层级。两个节点 key 相同、标签相同等条件都满足，才算“同一个节点”可以复用，源码里这个判断叫 sameVnode，不满足就销毁重建。

Vue 2 的子节点比较在 updateChildren 里。它给新旧两组各放头尾两个指针，一共四个，每轮依次尝试旧头对新头、旧尾对新尾、旧头对新尾、旧尾对新头四种配对。配上了就更新这个节点，必要时移动 DOM，然后指针往中间收。这个办法叫双端比较。

四种都配不上时，就为剩下的旧节点建一张“key → 下标”的表，用新头的 key 去查；查不到就新建。循环结束后，多出来的新节点批量插入，多出来的旧节点批量删除。

Vue 3 换了思路。它先把开头和结尾相同的部分同步掉，中间乱序的部分用最长递增子序列找出不需要动的节点，只移动其余的。再加上编译器生成的 PatchFlags、Block 和静态缓存，运行时能跳过大量不变的内容。

什么样的两个节点算“同一个”

源码中 sameVnode 的条件是：key 相同、asyncFactory 相同，并且标签相同、是否注释节点相同、是否都有 data，input 元素还要求 type 相同（异步占位节点另有判断）。

这里有个关键点。没写 key 时，两边的 key 都是 undefined，也算“相同”。所以同标签的节点会被直接就地复用，不管它们背后对应的是不是同一条数据。列表用下标当 key 或者不写 key 时出现状态错位，原因就在这里。

双端比较怎么走

设 oldStart、oldEnd、newStart、newEnd 四个指针。只要两组都还有没处理的节点，就一直循环（循环开头会跳过之前被置为 undefined 的旧节点）。每轮按下面的顺序尝试：

  1. 旧头 vs 新头：命中就 patch，两个头指针后移。
  2. 旧尾 vs 新尾：命中就 patch，两个尾指针前移。
  3. 旧头 vs 新尾：命中说明这个节点被移到了后面，patch 后把旧头的 DOM 插到旧尾 DOM 的后面。
  4. 旧尾 vs 新头：命中说明这个节点被移到了前面，patch 后把旧尾的 DOM 插到旧头 DOM 的前面。
  5. 都不命中：第一次走到这里时用 createKeyToOldIdx 为剩余旧节点建 key 映射。新头有 key 就查映射，没有 key 就用 findIdxInOld 逐个做 sameVnode 比较。找到且 sameVnode 成立就 patch，把旧位置置为 undefined，把 DOM 移到旧头之前；找不到，或者 key 相同但元素不同，就新建一个插到旧头之前。然后新头指针后移。

循环结束后，如果旧节点先用完，就把剩下的新节点插进去；如果新节点先用完，就把剩下的旧节点删掉。

看一个具体例子，把最后一项挪到最前面：

text
旧：A B C D      新：D A B C
旧头 A vs 新头 D ✗；旧尾 D vs 新尾 C ✗；旧头 A vs 新尾 C ✗
旧尾 D vs 新头 D ✓ → 把 D 移到 A 前面，只移动一次

这个例子里，第四种配对就找到了 D，不需要建映射表。之后剩下的 A B C 每轮都是头对头命中，不再移动。在头尾增删、把一项挪到头或尾这类变化，都能靠首尾配对直接处理。

Vue 3 换成了什么做法

Vue 3 带 key 的子节点比较在 patchKeyedChildren 里，分五步：

  1. 从头开始同步，isSameVNodeType 成立就 patch，直到遇到不同的。
  2. 从尾开始同步。
  3. 如果旧的用完了，挂载剩下的新节点。
  4. 如果新的用完了，卸载剩下的旧节点。
  5. 剩下中间一段乱序的部分：为新节点建 key → 下标映射，遍历旧节点，能复用的 patch，找不到的卸载，同时记录 newIndexToOldIndexMap。只有检测到节点发生了移动，才调用 getSequence 求最长递增子序列；然后从后往前遍历，在子序列里的节点不动，其余节点移动或新挂载。

最长递增子序列是什么意思？把中间这段新节点在旧列表里的位置排出来，其中保持原有先后顺序的最长那一串，彼此之间的相对位置没变，就不用动它们，只需要移动别的节点。这样移动次数最少。

编译器又帮了什么忙

Vue 2 的编译器会标记静态根节点，patch 时跳过它们，但其余动态节点仍然按整棵树比较。Vue 3 的编译结果带了更多提示：

  • PatchFlags：标记节点哪些部分是动态的，比如 TEXT、CLASS、PROPS，patchElement 只更新这些部分。
  • Block：块节点把内部的动态后代收集到 dynamicChildren，更新时只遍历这个扁平数组，不用走整棵子树。
  • 静态缓存（Cache Static，早期版本叫静态提升）：静态节点只创建一次。Vue 3.5 的编译器把它缓存到 _cache 里并标记为 CACHED，更新时完全跳过。

用 @vue/compiler-dom（vue@3.5.x 依赖）编译 <div><p>static</p><span :class="c">{{msg}}</span></div>，输出的关键部分是：

JavaScript
_cache[0] || (_cache[0] = _createElementVNode("p", null, "static", -1 /* CACHED */)),
_createElementVNode("span", { class: _normalizeClass(_ctx.c) },
  _toDisplayString(_ctx.msg), 3 /* TEXT, CLASS */)

静态的 p 只在第一次渲染时创建，之后直接从 _cache[0] 拿；span 后面的 3 表示只有文本和 class 会变。具体的编译策略见《Vue 模板编译如何减少运行时更新工作？》。

常见追问

为什么不推荐用下标当 key？

在中间插入或删除一项以后，下标和数据的对应关系就变了。sameVnode 只看 key，会把原本对应不同数据的节点当成同一个复用，带状态的子组件或者输入框就会错位。

双端比较和最长递增子序列哪个更好？

两者都是减少 DOM 移动的启发式方法。Vue 3 的方案在中间乱序的部分能得到最少的移动次数，但这里不给出普适的性能结论，实际差异取决于列表怎么变。
