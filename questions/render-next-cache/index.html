Next.js App Router 中的几层缓存怎样区分？

Next.js 16 新项目默认开启 Cache Components：数据和组件默认不缓存，用 'use cache' 显式缓存，用 cacheLife 设置时长、cacheTag 打标签，修改后用 updateTag 或 revalidateTag 失效；要请求时数据的部分放进 Suspense 流式输出。未开启时沿用旧模型，fetch 默认不缓存，通过 force-cache 和路由段配置控制。

参考答案

简答

Next.js 16 引入了 Cache Components，配置项是 cacheComponents: true，用推荐配置创建的新 App Router 项目默认开启。在这个模式下，数据请求和组件默认每次请求都执行，不缓存。想缓存，就在函数或组件顶部写 'use cache'，它的参数和用到的闭包变量会自动成为缓存键。

缓存多久用 cacheLife('hours') 这类配置，打标签用 cacheTag('posts')。数据改了以后，在 Server Action 里调 updateTag 立即失效，或者调 revalidateTag(tag, 'max')，先返回旧数据、后台再刷新。

读了 cookies()、headers()、searchParams 或者没缓存的数据的组件，要包在 <Suspense> 里。构建时先生成一个外壳，包含静态内容和已缓存的内容；Suspense 里的部分在请求时再流式补上。这种方式叫部分预渲染，简称 PPR。

没开 Cache Components 的项目用的是旧模型：Next 15 起 fetch 默认不缓存，靠 cache: 'force-cache'、next.revalidate、unstable_cache 和路由段配置来控制。

先看一个博客页

下面这个页面里，文章列表可以缓存，用户的主题偏好要读 cookie，每个人不一样。

TSX
// app/blog/page.tsx
import { Suspense } from 'react';
import { cookies } from 'next/headers';
import { cacheLife, cacheTag } from 'next/cache';

export default function BlogPage() {
  return (
    <>
      <h1>博客</h1>
      <Posts />
      <Suspense fallback={<p>加载偏好…</p>}>
        <Preferences />
      </Suspense>
    </>
  );
}

async function Posts() {
  'use cache';
  cacheLife('hours');
  cacheTag('posts');
  const posts = await db.post.findMany();
  return <ul>{posts.map((p) => <li key={p.id}>{p.title}</li>)}</ul>;
}

async function Preferences() {
  const theme = (await cookies()).get('theme')?.value ?? 'light';
  return <p>主题：{theme}</p>;
}

标题是静态的，Posts 写了 'use cache'，所以这两部分都进了构建时的静态外壳，可以直接从 CDN 返回。Preferences 读了 cookie，构建时没有 cookie 可读，只能在请求时生成，所以要放进 Suspense。用户先看到“加载偏好…”，生成好以后通过流式响应填到这个位置。

数据改了怎样让缓存失效

TypeScript
'use server';
import { updateTag } from 'next/cache';

export async function createPost(formData: FormData) {
  await db.post.create({ data: { title: String(formData.get('title')) } });
  updateTag('posts');
}

Posts 打了 posts 标签，这里一调 updateTag('posts')，它的缓存就失效了。另一个选择是 revalidateTag，两者的区别是：

updateTagrevalidateTag
调用位置只能在 Server ActionServer Action 和 Route Handler
行为立即失效，用户马上看到自己的修改先返回旧数据，后台重新生成
适合用户提交后跳转查看结果CMS webhook、允许短暂延迟的内容

能用标签时优先用标签。revalidatePath('/blog') 会让整个路径的缓存都失效，范围更大。

缓存到底存在哪里

缓存不是只有一处。预渲染的 HTML 在构建时或 ISR 时生成，可以放在 CDN 上。服务端缓存默认在每个实例的内存里，Serverless 环境下实例随时会换，所以可能存不住；用 'use cache: remote' 可以换成共享的缓存处理器。

浏览器里也有一层。客户端导航或预取拿到的结果，会在 cacheLife 的 stale 时间内被复用。'use cache: private' 可以读 cookie，因为生产环境里它的结果不会跨请求存进服务端缓存，只在同一次请求内复用；客户端路由会在 stale 时间内把渲染结果留在浏览器内存里，刷新页面就没了。

另外，每次部署后缓存都会从头开始，因为缓存键里包含了构建 ID。

没开 Cache Components 时怎么控制

旧模型的写法是这样：

TypeScript
await fetch(url); // Next 15 起默认不缓存
await fetch(url, { cache: 'force-cache' }); // 缓存
await fetch(url, { next: { revalidate: 3600, tags: ['posts'] } }); // 定时失效 + 标签

export const dynamic = 'force-dynamic'; // 路由段配置：每次请求都渲染
export const revalidate = 60; // 路由默认的重新验证时间

不是 fetch 的数据源，比如直接查数据库，用 unstable_cache 包一层。要特别注意的是，Next 14 里 fetch 默认是缓存的，从 14 升到 15 时这个默认值反过来了。

个性化数据不能缓存成共享结果

读 cookie 或用户身份的组件，不要用普通的 'use cache' 缓存，否则一个人的结果可能被别人拿到。可以把用户 ID 作为参数传给缓存函数，这样它会成为缓存键的一部分；或者用 'use cache: private'。CDN 层的个性化缓存问题，详见《SSR 和 SSG 中的缓存层应该怎样区分？》。

常见追问

'use cache' 和 React 的 cache 有什么区别？

React 的 cache 只在一次请求里去重，请求结束就没了。'use cache' 是跨请求持久保存的，详见《React 的 cache API 解决什么问题？》。

Math.random()、Date.now() 怎么处理？

如果需要每次请求都不一样，先 await connection()，再把组件放进 Suspense。如果希望所有用户共享同一个值，就放进 'use cache' 里。
