as const、类型注解和 satisfies 有什么不同？

类型注解规定变量采用的静态契约，as const 保留字面量并给相应字面结构增加只读约束，satisfies 检查兼容性同时保留表达式自身的具体推导。上下文类型仍可能影响推导，三者都不等同于运行时冻结或校验。

参考答案

配置对象经常同时有两个需求：写错字段时希望编译器报警，又不想把每个字段都推宽成一个难用的大联合。类型注解、as const 与 satisfies 可以分别帮助解决不同部分，但不能互相当成同义写法。

还要区分 const 变量声明与 as const：const 只限制变量绑定重新赋值，普通对象的属性仍可以修改，因此属性类型仍可能被推宽；as const 进一步影响字面量表达式的类型推导。

类型注解让变量按目标契约使用

TypeScript
type Color = 'red' | 'green';
type RGB = readonly [number, number, number];

const annotated: Record<Color, string | RGB> = {
  red: [255, 0, 0],
  green: '#00ff00',
};

if (typeof annotated.green === 'string') {
  console.log(annotated.green.toUpperCase()); // #00FF00
}

目标契约允许每个颜色是字符串或 RGB 元组。变量采用这份类型之后，读取 green 时不能只凭初始化时看见字符串就在所有使用位置永久忽略另一种可能，使用字符串方法前需要合适的收窄。

这在希望变量以后接受同一契约中的其他合法值时很合理。但如果配置表是固定的，我们可能更希望保留每个属性实际采用的形态。

satisfies 检查形状，同时保留更具体的成员类型

TypeScript
const palette = {
  red: [255, 0, 0],
  green: '#00ff00',
} satisfies Record<Color, string | RGB>;

console.log(palette.green.toUpperCase()); // #00FF00
console.log(palette.red.join(',')); // 255,0,0

编译器检查 palette 是否满足指定键和值的约束，同时保留表达式推导出的更具体结构，所以 green 可以直接用字符串方法，red 也仍有数组/元组能力。

对象字面量中拼错键、缺少必需键或提供不符合类型的值，仍然会被发现。satisfies 不是为表达式生成一个“是否通过校验”的布尔值，运行时的 palette 仍然是原来那个对象。

也不能把 satisfies 看成字段白名单过滤。像其他结构兼容检查一样，已有变量携带额外属性的情形与新鲜字面量检查不同，运行时额外字段不会被自动删除。

它不保证推导与完全没有上下文时一模一样

TypeScript
const request = {
  method: 'GET',
} satisfies { method: 'GET' | 'POST' };

// @ts-expect-error 此处 method 被保留为具体的 'GET'，不能赋成 'POST'
request.method = 'POST';

satisfies 的目标类型可以参与上下文推导。这里 method 得到的是具体字面量 'GET'，而不是一个以后可以随意在 GET、POST 间切换的宽联合。

如果业务需要后续修改为两者之一，直接给变量明确的 { method: 'GET' | 'POST' } 注解可能更符合目的。不能把“保留表达式类型”理解成“它绝不对推导上下文产生任何影响”。

as const 保留字面量，也引入相应只读约束

TypeScript
const point = [10, 20] as const;
const options = { mode: 'compact', enabled: true } as const;

// @ts-expect-error point 是只读元组
point[0] = 30;

// @ts-expect-error options.mode 是只读属性
options.mode = 'comfortable';

point 被推导为 readonly [10,20]，不是普通 number[]；options 中的字面属性也保持具体值并带有只读约束。这有助于构造稳定的字面量联合、路由列表和判别字段。

但 as const 不是执行 Object.freeze。类型约束可以阻止正常 TypeScript 代码这样写，不能让 JavaScript 运行时自动拒绝所有修改。

外部可变对象不会因被引用就全部冻结

TypeScript
const values = [1, 2];
const config = { mode: 'compact', values } as const;

config.values.push(3);
console.log(config.values.join(',')); // 1,2,3
console.log(Object.isFrozen(config)); // false

config.values 这个属性本身受到只读约束，不应被重新指定成另一个数组。但 values 已经是一个外部可变数组，通过这个引用调用 push 仍然允许。把对象放进一个 as const 字面量，不会自动把所有可达数据递归变成不可变对象。

需要只读接口时，应明确用 readonly 类型传递；需要运行时不可变时，还要选择对应的冻结或受控更新策略，并理解它们的深浅边界。

两者组合，适合固定配置表

TypeScript
type Route = {
  path: string;
  method: 'GET' | 'POST';
};

const routes = [
  { path: '/questions', method: 'GET' },
  { path: '/feedback', method: 'POST' },
] as const satisfies readonly Route[];

console.log(routes[0].method); // GET

as const 保留具体路径、方法与只读元组结构，satisfies 再检查整组配置满足 Route 契约。目标也写成 readonly Route[]，明确允许只读输入，而不是要求这个配置必须是可修改数组。

这类配置可以进一步通过类型索引提取合法路径或方法，但类型工具不会替你注册真实路由，也不会生成服务器接口。

as 断言解决的是另一种问题

value as SomeType 告诉编译器按某种类型理解值，可能绕过它原本不能证明的关系。satisfies 则要求当前表达式本身满足目标约束，两者不能互相替代。

已经可信、只是推导能力不足的内部代码可以有针对性地使用断言；接口响应或用户输入仍需要真正解析。JSON.parse 返回的 any 即使参与 satisfies 检查，也不会把未知内容变成经过验证的配置，any 反而可能削弱本来期待的检查。

选择时先问：希望变量以后按照一个宽契约变化，就用清楚的注解；希望固定字面信息，就用 as const；希望在保留具体形态时验证契约，就考虑 satisfies。按目标组合，通常比到处叠加断言更容易维护。
