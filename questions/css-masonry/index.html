CSS Masonry 和传统瀑布流方案应该怎样选择？

原生瀑布流已改为 display: grid-lanes，仍是实验特性，要在普通 Grid 之上渐进增强；多栏布局和 JavaScript 定位各有顺序与性能上的取舍。

参考答案

简答

  • 瀑布流适合高度不一的图片卡片，不适合需要横向比较的数据卡片。
  • 原生方案是 display: grid-lanes：定义 grid-template-columns 后，每个项目放进可用空间最多的那一列。早期草案的 grid-template-rows: masonry 已被替换。
  • grid-lanes 目前是实验特性，属于有限可用，用 @supports (display: grid-lanes) 叠加在普通 Grid 之上。
  • 多栏布局（columns）能做出类似效果，但项目先填满第一列再到下一列，阅读顺序是竖向的。
  • 无论哪种方案，键盘焦点和读屏都按 DOM 顺序，视觉上的“左右相邻”不代表顺序相邻。

原生方案

CSS
.gallery {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(14rem, 1fr));
  gap: 1rem;
}

@supports (display: grid-lanes) {
  .gallery {
    display: grid-lanes;
  }
}

不支持的浏览器显示为普通网格，同一行的卡片顶端对齐，下方留空，内容完整可用。网格轴上的 span 和显式放置照常有效，例如 grid-column: span 2 让某张卡片占两列。

三种方案对比

方案顺序兼容性成本
grid-lanes大体按 DOM 顺序从左到右放入最短列实验特性无 JavaScript
columns先填满第一列，再到下一列全部支持无 JavaScript，新增项目会让各列整体重排
JavaScript 定位完全可控全部支持要在图片加载、窗口变化时重新测量

JavaScript 方案（例如 Masonry.js 或自己计算最短列再绝对定位）每次重排都要先读取元素高度再写位置。读写交替会触发强制同步布局，数据多时要配合虚拟列表。

布局稳定性

HTML
<img src="/cover.webp" width="640" height="480" alt="课程封面" loading="lazy">

给图片写宽高或 aspect-ratio，浏览器在图片到达前就能算出卡片高度，不会因为图片加载而让后面的卡片跳位置。

可访问性

  • 卡片用真实的链接和按钮，不要用只能鼠标点击的 div。
  • 无限加载插入新卡片时，不要把焦点或滚动位置拉回顶部。
  • 如果视觉顺序和 DOM 顺序差异很大，可以考虑按列顺序生成 DOM，或者换成普通网格。

常见追问

  • 为什么不直接用 Grid 加 grid-row: span N？可以按高度估算行跨度来近似瀑布流，但需要 JavaScript 读取每张卡片高度，本质上还是测量方案。
