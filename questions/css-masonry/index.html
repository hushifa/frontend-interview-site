CSS Masonry 和传统瀑布流方案应该怎样选择？

解释 masonry 布局试图解决的列高不齐问题，比较原生 CSS、Grid、JavaScript 和多列布局的顺序、兼容性、性能与无障碍边界。

参考答案

简答

  • 瀑布流适合高度不一的图片卡片，不适合需要横向比较或严格顺序的内容。
  • CSSWG 已把早期的 grid-template-rows: masonry 改为 display: grid-lanes，仍是实验性特性，要用 @supports 渐进增强。
  • 普通 Grid 不会把项目放进最短列，多栏布局按列流动，JavaScript 方案控制力强但要处理重新测量和重排。
  • 视觉顺序可能与 DOM 顺序不同，键盘焦点和读屏按 DOM 顺序；图片要预留尺寸减少布局移动。

图片卡片、文章摘要和作品集经常高度不一，但设计又希望像瀑布一样紧凑排列。最早的实现通常是 JavaScript 测量每张卡片，再把它绝对定位到最短列；这能工作，却要处理图片加载、窗口变化、滚动和大量布局读写。

Masonry 的目标是让布局系统根据项目高度自动放入列中，但它不是“把 Grid 改一个属性就永远兼容”的简单升级。规范、浏览器支持、键盘顺序和视觉顺序都需要一起评估。

先确认内容是否真的适合瀑布流

瀑布流适合图片卡片、灵感墙和不要求严格行列对齐的内容。数据表、财务数字、步骤列表和需要横向比较的卡片通常不适合，因为视觉上同一行的项目高度和位置不一致会增加比较成本。

内容顺序也很重要。用户通常按 DOM 顺序阅读，而 CSS 可能让视觉顺序先填满第一列再进入下一列；屏幕阅读器、键盘焦点和复制内容仍主要依赖 DOM 顺序。视觉上“最短列优先”不一定对应一个清晰的阅读顺序。

原生 Masonry 要按支持情况渐进增强

CSS
.gallery {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(14rem, 1fr));
  gap: 1rem;
}

@supports (display: grid-lanes) {
  .gallery {
    display: grid-lanes;
  }
}

CSSWG 已把早期草案的 grid-template-rows: masonry / align-tracks 改成独立的显示类型 display: grid-lanes（CSS Grid Layout Level 3），MDN 也只记录新语法。定义了 grid-template-columns 就是按列堆叠，定义 grid-template-rows 则按行堆叠；网格轴上的 span 和显式放置仍然有效。目前 MDN 将其标为实验性、未达到 Baseline，所以用 @supports 包住，不支持时回退到普通 Grid，内容仍可阅读。不要沿用旧语法，也不要仅凭开发浏览器支持就宣称生产兼容；各浏览器版本以 MDN 兼容表为准。

Grid、columns 和 JavaScript 的差异

普通 Grid 提供稳定的行列关系，适合需要对齐的卡片；它可以通过固定或估算高度实现近似瀑布，但不会自动把下一个项目放入当前最短列。CSS Multi-column 能产生类似流式排列，却可能按列从上到下再横向移动，阅读和响应式顺序不一定符合用户预期。

JavaScript/绝对定位可以精确控制列、虚拟化和排序，但要处理更多生命周期：图片和字体加载完成后重新测量，容器宽度变化时重排，快速滚动时避免布局抖动，删除或插入项目时保持焦点。频繁读取 getBoundingClientRect() 再写 style，可能造成强制同步布局。

如果内容数量很大，虚拟列表还要维护总高度、滚动锚点和键盘目标；如果页面需要浏览器查找、打印和全文复制，虚拟化或纯视觉瀑布流可能不合适。

图片尺寸和布局稳定性仍要提前处理

无论使用哪种方案，都应在图片或异步内容出现前预留尺寸：

HTML
<img
  src="/images/card.webp"
  width="640"
  height="480"
  alt="课程封面"
  loading="lazy"
>

宽高属性或 aspect-ratio 能让浏览器提前知道占位比例，减少图片到达后的布局移动。它不会保证所有卡片高度相同；瀑布流正是利用高度差，但不能让后续内容突然覆盖按钮或焦点。

字体、展开内容、折叠面板和异步广告也可能改变高度。布局系统会重新计算位置，组件应避免在用户正在阅读时无条件把滚动位置拉回。必要时使用稳定占位、显式加载区域或滚动锚点策略。

可访问性不能只看 DOM 顺序

卡片应使用合适的标题、链接和按钮，图片提供准确替代文本；不要把整个卡片做成只能鼠标点击的 div。键盘焦点应按逻辑顺序移动，即使视觉布局像瀑布；焦点被移动或卡片动态插入时，用户需要知道当前内容变化。

如果设计要求按列浏览或拖拽重排，应提供明确的键盘操作和状态说明。不要依赖 Masonry 的视觉位置推断 aria-posinset 或阅读顺序；这些语义要根据实际内容模型单独计算。

性能比较要看完整代价

原生布局可能减少 JavaScript 测量和主线程工作，但不代表卡片图片、字体和第三方内容变轻。JavaScript 方案可能支持更强的虚拟化和排序，但也可能增加布局读取、事件和内存成本。

测试时观察首次布局、图片到达后的 CLS、快速滚动、容器尺寸改变、低端设备长任务和页面查找行为。用真实数据量和图片尺寸比较，而不是只用十个相同高度的占位块。先确认内容语义、兼容性和顺序，再决定是否值得采用原生实验特性或自定义实现。
