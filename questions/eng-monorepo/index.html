Monorepo 与 npm workspaces 能解决什么问题？

区分仓库组织、工作区链接和任务编排，用应用与组件包示例说明依赖声明、构建顺序、发布验证及逐步采用的边界。

参考答案

应用、组件库和共享工具如果经常需要一起修改，分别放在多个仓库中可能产生很多版本发布与联调步骤。Monorepo 把这些相关项目放进一个仓库，使跨包修改、评审和统一检查更容易组织。

npm workspaces 则是包管理能力：识别工作区中的包、在安装时链接它们，并帮助在指定包中执行命令。它不是 Monorepo 的同义词，也不是完整的构建缓存或发布系统。

一个应用依赖本地组件包的例子

目录可以这样安排：

text
package.json
package-lock.json
packages/ui/package.json
packages/ui/index.js
apps/web/package.json

根 package.json 声明工作区，private 防止误把根包作为普通公开包发布：

json
{
  "name": "demo-workspace",
  "private": true,
  "workspaces": ["packages/ui", "apps/web"]
}

组件包有自己的名称、版本与公开入口：

json
{
  "name": "@demo/ui",
  "version": "1.0.0",
  "type": "module",
  "exports": "./index.js"
}

应用仍应声明依赖，而不是因为处于同一仓库就省略：

json
{
  "name": "@demo/web",
  "private": true,
  "type": "module",
  "dependencies": {
    "@demo/ui": "1.0.0"
  }
}

从根目录安装后，npm 会按工作区规则建立本地链接，应用可以通过包名导入组件包。示例的本地版本与声明一致；不要随意把其他包管理器特有的 workspace: 写法复制过来，而不检查当前 npm 的支持和解析规则。

链接成功，不代表包已经构建好

若 ui 的入口指向 dist/index.js，本地链接只会指向这个包，不会自动替它生成 dist。应用构建前仍需要保证依赖产物存在，或明确采用源码直连的开发方案。

源码直连方便联调，但也可能掩盖发布问题：仓库里可以导入的源码，打包后未必在分发文件中。公开库应检查实际归档内容，并从独立消费者视角验证入口、类型声明和资源文件。

共享一个根 node_modules 也可能掩盖未声明依赖。子包不能因为某个工具恰好由根目录或其他包安装，就把它当成自己的可移植依赖。

多包命令不等于依赖图调度

在各包定义相应脚本后，可以指定 workspace 执行，也可以对工作区批量执行。例如 npm run test --workspace=@demo/ui 只运行指定包，npm run test --workspaces --if-present 跳过没有相应脚本的工作区。

但 npm 的工作区脚本执行不能被直接理解成自动按业务依赖拓扑构建所有包。文档规定的执行顺序与工作区配置有关，不能假定工具会自行分析“应用必须等组件库构建完”。

简单仓库可以显式安排依赖顺序；任务复杂后，再引入任务图、缓存或受影响分析工具。并行执行、缓存恢复和失败传播都需要清楚的规则，不是加一个 workspaces 字段便全部具备。

一个仓库不要求只有一种发布方式

可以统一版本，也可以让各包独立版本；可以只发布应用，也可以把组件库单独发布。Monorepo 决定代码放在哪里，不直接决定包如何对外分发。

独立发布仍要处理版本依赖、变更记录和消费者兼容。统一提交可以让跨包修改在仓库内同时出现，但外部用户升级包的顺序不一定与仓库一致。

如果所有功能都必须同时部署，也不必为了“用了 Monorepo”刻意制造独立发布流程。

共享配置要有边界

Lint、TypeScript 和测试基础配置可以集中维护，但每个包的运行环境可能不同：浏览器应用、Node 工具与可发布库不一定使用同一个编译目标或全局变量。

共享组件也应有明确 API，不能让所有包互相导入私有目录。循环依赖、跨包状态修改和大量根级万能工具，仍然会降低可维护性，只是它们现在位于一个仓库里。

什么时候值得采用

相关包需要频繁协作、统一评审或共享基础设施时，Monorepo 往往有价值。若项目只有一个应用和少量局部组件，先建立清晰模块边界可能已经足够。

随着规模增长，观察安装时间、任务执行范围、构建缓存命中和跨包影响，再逐步增加工具。目标是减少协作与验证成本，不是让一个简单项目先承担大型仓库的所有编排负担。
