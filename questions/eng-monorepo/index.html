Monorepo 与 npm workspaces 能解决什么问题？

区分仓库组织、工作区链接和任务编排，用应用与组件包示例说明依赖声明、构建顺序、发布验证及逐步采用的边界。

参考答案

简答

  • Monorepo 是把多个相关项目放在一个仓库里，解决的是跨项目同时修改、统一工具链和代码共享的问题。
  • 工作区（workspaces）负责把本地包互相链接，省去发布后再安装的步骤。
  • 任务编排工具（Turborepo、Nx 等）负责按依赖顺序构建、并行执行和缓存结果，工作区本身不做这些。
  • 代价是仓库变大、CI 需要按改动范围执行，权限和发布流程也要重新设计。
  • 团队规模小、项目之间几乎不共享代码时，多仓库往往更简单。

解决了什么

  • 原子修改：组件库改了 API，所有使用它的应用在同一个提交里一起改，评审时能看到全部影响。
  • 统一工具：ESLint、TypeScript、测试配置放在根目录共享，避免各项目版本漂移。
  • 本地联调：应用直接使用组件库源码，不用 npm link 或反复发布测试版本。

npm workspaces 示例

json
// 根 package.json
{
  "private": true,
  "workspaces": ["apps/*", "packages/*"]
}
json
// apps/web/package.json
{
  "dependencies": { "@acme/ui": "^1.0.0" }
}

npm install 发现 @acme/ui 是本地工作区包且版本满足范围，就把它链接到 node_modules/@acme/ui。

bash
npm run build --workspace=@acme/ui
npm run test --workspaces --if-present

--workspaces 依次在每个包运行脚本，不会自动按依赖拓扑排序。包多、依赖链长时需要任务编排工具。

任务编排

以 Turborepo 为例，声明 build 依赖上游包的 build，工具会算出执行顺序，并按输入文件哈希缓存输出。改了一个包时，只重新构建它和它的下游，其他包直接命中缓存。

需要额外注意的地方

  • 依赖声明：每个包要在自己的 package.json 里声明用到的依赖。npm 默认把依赖提升到根目录，漏写依赖在本地也能运行，发布后才出错。
  • 构建产物：组件库如果需要先编译，应用开发时引用的是源码还是产物，要在 exports 和构建配置里约定清楚。
  • 发布：多个包的版本号和变更日志可以用 Changesets 管理，发布前在干净环境里安装打包结果验证。
  • CI 规模：按改动范围筛选受影响的包，否则每次提交都全量构建。

逐步采用

可以先把共享配置和一个组件库放进同一仓库，确认链接、构建顺序和发布流程都顺畅，再迁入更多项目。迁移时保留各项目的 Git 历史（如 git subtree）便于追溯。

常见追问

  • 选 npm、pnpm 还是 Yarn 的工作区？pnpm 提供 workspace: 协议和严格隔离，适合包较多的仓库，见《pnpm workspace 怎样管理多包前端仓库？》。
  • Monorepo 一定要用 Nx/Turborepo 吗？包少时 --workspaces 加手动排序足够，包多、构建慢时再引入。
