定高虚拟列表怎样手写？怎样根据 scrollTop 算出要渲染哪几行？

行高固定时，第一个可见行是 Math.floor(scrollTop / rowHeight)，再上下多渲染几行缓冲就是渲染范围。外层用一个总高度等于行数乘行高的容器撑出滚动条，里面只放这十几行，用 transform 挪到对应位置。key 要跟数据 ID 走，每行的实际高度必须严格等于 rowHeight。

参考答案

简答

一个列表有一万行，用户一屏只能看到十几行。虚拟列表的做法是只渲染看得见的这些行，再上下多渲染几行做缓冲，其余的行根本不创建 DOM。

为什么这样能变快？因为创建 DOM、算样式、布局的成本都随行数增长，一万行全渲染就要付一万行的代价，虚拟化以后同时存在的只有几十行。滚动条之所以还正常，是因为外面套了一个和完整列表一样高的占位容器。

行高固定时，计算很简单：第一个可见行是 Math.floor(scrollTop / rowHeight)，总高度是行数乘行高。上下多渲染的几行叫 overscan，能减少快速滚动时的空白，但太多又抵消了收益。

要注意，行的 key 和选中、编辑状态必须跟着数据 ID 走，不能用窗口里的下标。每行的实际高度也必须严格等于 rowHeight，否则越往下滚偏差越大。

怎样算出该渲染哪几行

下面的函数根据滚动位置算出要渲染的范围：

JavaScript
function getWindow({ count, rowHeight, scrollTop, viewportHeight, overscan = 2 }) {
  const totalHeight = count * rowHeight;
  const top = Math.min(Math.max(0, scrollTop), Math.max(0, totalHeight - viewportHeight));
  const first = Math.floor(top / rowHeight);
  const last = Math.ceil((top + viewportHeight) / rowHeight);
  const start = Math.max(0, first - overscan);
  const end = Math.min(count, last + overscan);
  return { start, end, offset: start * rowHeight, totalHeight };
}

console.log(getWindow({ count: 10000, rowHeight: 40, scrollTop: 800, viewportHeight: 400 }));
// { start: 18, end: 32, offset: 720, totalHeight: 400000 }

滚动了 800px，行高 40px，所以第一个看得见的是第 20 行；视口 400px，能看到第 20 到 29 行。为什么结果是 18 到 32？因为上下各多渲染了 2 行 overscan。end 不包含在内，实际渲染的是 items.slice(start, end)，也就是第 18 到 31 行。

offset 是这批行要往下挪多少，等于 start 乘行高，720px。top 那一行把 scrollTop 限制在合法范围里，防止弹性滚动或者数据变少时算出负数或越界。

DOM 结构长什么样

用上面算出的数字，结构是这样的：

HTML
<div class="viewport" style="height: 400px; overflow: auto">
  <div style="height: 400000px; position: relative">
    <div style="transform: translateY(720px)">
      <!-- 第 18 到 31 行 -->
    </div>
  </div>
</div>

最外层是固定高度、可以滚动的视口。中间那层撑到 400000px，让滚动条的长度和完整列表一样。最里面才是真正渲染的十几行，用 transform 挪到它们本该在的位置。

滚动时只需要更新 start 和 end，而且每帧最多算一次，可以放在 requestAnimationFrame 里处理。

有一点很容易出错：每行的实际高度必须真的等于 rowHeight，边框和外边距也要算进去。差一点点，越往下滚误差越大，最后内容和滚动位置就对不上了。行高不固定的情况见《动态高度的虚拟列表怎样处理测量、滚动锚点和焦点？》。

为什么 key 不能用下标

窗口里的第 0 行，滚动之前是数据第 18 行，滚动之后可能是第 25 行。如果用窗口下标当 key，框架会以为还是同一行，只是内容变了，于是把旧行的选中状态、输入框内容留给了新数据。所以 key 和这些状态都要跟着数据 ID。

它解决不了什么

虚拟列表只减少渲染的成本，数据本身仍然全部在内存里，过滤、排序也照样要算。没挂载的行，页面查找、打印和读屏器都碰不到。长列表什么时候该用虚拟列表、什么时候该用分页或时间分片，见《页面要渲染十万条数据，怎样不卡顿？》。

常见追问

用现成的库还是自己写？

生产环境优先用 TanStack Virtual、react-window 这类成熟的库，它们已经处理了测量、滚动到指定项这些细节。

滚动事件里每次都更新状态，会不会太频繁？

滚动事件一帧内可能触发好几次。可以在回调里只记下最新的 scrollTop，用 requestAnimationFrame 每帧算一次范围；算出来的 start 和 end 没变，就不用更新状态，也就不用重新渲染。
