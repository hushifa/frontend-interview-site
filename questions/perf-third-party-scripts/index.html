第三方脚本怎样接入，才能控制性能和安全风险？

页面里直接加载的第三方脚本以页面的身份运行，能读写 DOM、发请求、访问非 HttpOnly 的 Cookie，同时占用带宽和主线程。接入时先决定是否需要、何时加载，用 defer 或延迟加载减少阻塞，用 CSP 限制来源，不可信内容放进跨源 iframe，并为故障准备开关和降级。

参考答案

简答

  • 性能：下载、解析、执行和之后的定时器都占资源，async 和 defer 只避免阻塞 HTML 解析，执行时仍占主线程。
  • 安全：以页面源身份执行的脚本权限与自己的代码相近，供应商被入侵就等于页面被注入。
  • 隐私：需要用户同意的分析、广告脚本，必须在同意后才加载，不能先加载再停止上报。
  • 时机：按价值分级，首屏必需的才同步或 defer，其余在页面加载完成、用户交互或空闲时加载。
  • 故障：脚本加载失败或抛错不能影响核心功能，要有超时、错误隔离和可远程关闭的开关。

加载方式

写法下载执行时机顺序
<script>阻塞解析下载完立即执行按文档顺序
<script async>并行下载完立即执行不保证
<script defer>并行文档解析完成后按文档顺序
动态插入并行下载完执行默认类似 async
JavaScript
// 页面加载完成且浏览器空闲时再加载客服组件
function loadWhenIdle(src) {
  const load = () => {
    const script = document.createElement('script');
    script.src = src;
    script.async = true;
    script.onerror = () => console.warn('客服组件加载失败，不影响主功能');
    document.head.append(script);
  };
  const schedule = () => {
    if ('requestIdleCallback' in window) requestIdleCallback(load, { timeout: 5000 });
    else setTimeout(load, 2000);
  };
  // load 已经触发过时直接调度，否则永远等不到
  if (document.readyState === 'complete') schedule();
  else addEventListener('load', schedule, { once: true });
}

也可以用"外观替身"：先显示一个静态的客服按钮或视频封面，用户点击时才加载真正的脚本或 iframe。

限制权限

  • CSP 的 script-src 只允许确定的来源，见《CSP 的 nonce、hash 与 Report-Only 如何使用？》。
  • 固定版本的文件用 SRI 校验内容；供应商动态加载的子资源无法被 SRI 覆盖。
  • 不需要访问页面的组件（广告、外部表单）放进跨源 iframe，配合 sandbox 和 postMessage 通信。
  • 上报给第三方的数据用白名单字段，不传完整 URL、表单内容和令牌。

测量

  • Performance 面板录制，查看第三方脚本带来的长任务；Long Animation Frames 的 sourceURL 可以按域名归因。
  • 对比开启和关闭某个脚本时的 LCP、INP。
  • 用 DevTools 的请求屏蔽功能模拟供应商宕机，确认页面仍可用。

常见追问

  • 用 preconnect 优化第三方加载值得吗？只对首屏必需的第三方域名值得，其余会浪费连接。
  • 为什么脚本延迟后统计数据少了？延迟加载会漏掉早期离开的用户，要在数据完整性和首屏性能之间权衡，或在服务端补充采集。
