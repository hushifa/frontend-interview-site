第三方脚本怎样接入，才能控制性能和安全风险？

页面里直接加载的第三方脚本以页面的身份运行，能读写 DOM、发请求、读非 HttpOnly 的 Cookie，还占带宽和主线程。接入时先想清楚要不要、什么时候加载，用 defer 或延迟加载减少阻塞，用 CSP 限制来源，不可信内容放进跨源 iframe，并准备好开关和降级。

参考答案

简答

第三方脚本就是统计、广告、客服这类别人家提供的脚本。直接用 <script> 加载进来，它就以我们页面的身份运行，能读写 DOM、发请求、读不是 HttpOnly 的 Cookie，权限和我们自己的代码差不多。

所以风险有三方面。性能上，下载、解析、执行和它之后开的定时器都要占资源，async 和 defer 只是不阻塞 HTML 解析，执行时照样占主线程。安全上，供应商一旦被入侵，就等于我们的页面被注入了代码。隐私上，需要用户同意的分析、广告脚本，必须在同意以后才加载，不能先加载再停止上报。

接入时我会按价值分级：首屏必需的才同步加载或者 defer，其余的等页面加载完、用户交互或者空闲时再加载。权限上用 CSP 限制来源，不需要访问页面的内容放进跨源 iframe。

还要考虑故障。脚本加载失败或者抛错，不能影响核心功能，要有超时、错误隔离和能远程关掉的开关。

几种加载方式有什么区别

先看不同写法对下载和执行时机的影响：

写法下载执行时机顺序
<script>阻塞解析下载完立即执行按文档顺序
<script async>并行下载完立即执行不保证
<script defer>并行文档解析完成后按文档顺序
动态插入并行下载完执行默认类似 async

可以看到，async 和 defer 改变的只是下载时会不会卡住 HTML 解析。脚本最终还是要在主线程上执行，执行时该占多久还是占多久。所以对不急用的脚本，更有效的办法是推迟加载。

怎样推迟到空闲时再加载

下面的函数等页面 load 之后、浏览器空闲时，再插入客服组件的脚本：

JavaScript
// 页面加载完成且浏览器空闲时再加载客服组件
function loadWhenIdle(src) {
  const load = () => {
    const script = document.createElement('script');
    script.src = src;
    script.async = true;
    script.onerror = () => console.warn('客服组件加载失败，不影响主功能');
    document.head.append(script);
  };
  const schedule = () => {
    if ('requestIdleCallback' in window) requestIdleCallback(load, { timeout: 5000 });
    else setTimeout(load, 2000);
  };
  // load 已经触发过时直接调度，否则永远等不到
  if (document.readyState === 'complete') schedule();
  else addEventListener('load', schedule, { once: true });
}

为什么要先判断 document.readyState？因为这个函数可能在 load 事件已经触发以后才被调用，这时再去监听 load，就永远等不到了。

requestIdleCallback 的 timeout 是保底，浏览器一直不空闲时，最多等 5 秒也会执行。不支持它的浏览器退回到 setTimeout。

另一种常见做法叫“外观替身”：先放一个静态的客服按钮或者视频封面图，用户点击时才加载真正的脚本或 iframe。用户不点，就一点都不加载。

怎样限制它的权限

第一道防线是 CSP，用 script-src 只允许确定的来源加载脚本，见《CSP 的 nonce、hash 与 Report-Only 如何使用？》。

固定版本的文件可以用 SRI 校验内容，也就是在标签上写文件的哈希，内容被改了浏览器就拒绝执行。可是供应商脚本再动态加载的子资源，SRI 管不到。

不需要访问页面的组件，比如广告、外部表单，放进跨源 iframe，配合 sandbox，需要通信时用 postMessage。这样它就拿不到我们页面的 DOM 和 Cookie。

上报给第三方的数据也要用白名单字段，不传完整 URL、表单内容和令牌。

怎样测量它的影响

用 Performance 面板录一段，看第三方脚本带来的长任务；Long Animation Frames 的 sourceURL 可以按域名归因。

更直接的办法是对比开启和关闭某个脚本时的 LCP、INP。

还要测故障。用 DevTools 的请求屏蔽功能模拟供应商宕机，确认页面仍然能用。

常见追问

用 preconnect 优化第三方加载值得吗？

只对首屏必需的第三方域名值得。提前建连接本身有成本，用不上的域名提前连了就是浪费。

脚本延迟加载以后，统计数据变少了，怎么办？

延迟加载会漏掉那些很早就离开的用户。这是数据完整性和首屏性能之间的取舍，要么接受，要么在服务端补充采集。
