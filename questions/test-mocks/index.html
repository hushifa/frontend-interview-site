什么时候应该 mock，mock 太多有什么问题？

mock 适合控制外部网络、时间、随机数和难以稳定复现的失败条件，使测试能集中验证目标逻辑。但如果把所有依赖和内部调用都替换，测试可能只证明模拟对象彼此配合，无法发现真实集成问题。

参考答案

测试订单超时提示时，不必真的等待第三方服务偶发超时；测试随机抽样逻辑时，也不应让随机结果决定用例是否通过。Mock 可以控制这些外部不确定性，让测试稳定触发目标场景。

问题在于替换得太深：如果请求函数、数据转换、状态管理和子组件全被替换，测试可能只证明几个假对象按预设方式互相调用，真实代码反而几乎没参与。

选择离目标行为合适的边界

测试纯计算时通常直接传入数据，不需要 Mock。测试组件的错误提示，可以在网络边界提供失败响应，让真实请求处理与 UI 状态继续运行。测试一次通知是否发出，可以替换公开通知接口并检查参数。

替身不一定都用复杂 Mock 框架。一个返回固定值的函数、一个内存仓库或一个可控时钟都可能足够。关键是替身代替了什么真实能力，以及哪些行为仍由真实代码完成。

例如要验证“失败后重试”，可以让依赖第一次拒绝、第二次成功，但仍应验证成功结果和错误恢复。只断言被调用两次，无法证明重试的是正确请求，也无法证明结果最终到达用户。

clear、reset、restore 不要混为一谈

下面是当前 Vitest 行为的独立用例：

JavaScript
import { expect, test, vi } from 'vitest';

test('区分调用记录、替代实现和原始方法', () => {
  const service = { read: () => '真实结果' };
  const original = service.read;
  const spy = vi.spyOn(service, 'read').mockReturnValue('模拟结果');

  expect(service.read()).toBe('模拟结果');
  spy.mockClear();
  expect(spy).not.toHaveBeenCalled();
  expect(service.read()).toBe('模拟结果');

  spy.mockReset();
  expect(service.read).toBe(spy);
  expect(service.read()).toBe('真实结果');

  spy.mockRestore();
  expect(service.read).toBe(original);
});

mockClear 清除调用记录，保留当前实现；mockReset 还重置实现和一次性返回队列，但 spy 仍在对象上；mockRestore 对 spy 恢复原始属性。

对于 vi.fn()，重置后通常回到返回 undefined 的空实现；对于 vi.fn(impl)，当前 Vitest 会回到初始 impl。不能把其他测试工具或旧版本的 reset 规则直接套过来。独立 vi.fn 没有被 spy 替换的对象属性，因此 restore 也不是凭空找回某个真实业务方法。

时间和全局替身更需要清理

假定时器适合测试防抖、超时和重试，但推进计时器不一定等于相关 Promise、网络和组件更新都已经完成。应使用所选工具支持的异步推进方式，并等待可观察结果。

测试结束后恢复真实计时器、全局对象和 spy，避免后面的测试继承冻结时间或错误实现。清理应放在可靠的生命周期钩子或 finally 中，而不是只写在最后一条成功断言后面。

模块级 Mock 还可能有导入提升、模块缓存和 Browser Mode 限制。比如同一模块内部函数之间的直接调用，不一定会经过你替换的导出属性；不要为了绕过这一点就把所有私有函数都暴露成公共 API。

模拟数据必须维护契约

真实接口返回分页对象，Mock 却返回裸数组，可能让测试覆盖了一条根本不存在的成功路径。状态码、错误结构、空结果和字段类型都要与实际契约一致。

但模拟整个真实服务也不是目标。保留完成场景所需的语义，并用少量集成或契约测试确认接口没有分叉。依赖升级时，也要检查替身是否仍符合新版本行为。

判断是否 Mock 过度，可以问：真实依赖改错了，这个测试有机会失败吗？被替换的是不确定边界，还是正要验证的核心逻辑？前者有助于聚焦，后者常让测试产生虚假的安全感。
