什么时候应该 mock，mock 太多有什么问题？

mock 用来替换慢、不稳定或不受控的外部边界，比如网络、时间、随机数和第三方服务。把被测代码自己的模块也 mock 掉，测试就只验证了 mock 本身。每个测试后要清理 mock，模拟数据要和真实契约一致。

参考答案

简答

mock 就是在测试里用一个假的东西替换真实依赖。适合替换的是那些慢、不稳定、结果不受控的外部边界，比如 HTTP 请求、当前时间、随机数、地理位置和剪贴板这类浏览器 API，还有支付等第三方服务。

不适合替换的是被测模块内部的函数、纯计算逻辑、和被测代码一起交付的子组件。这些一旦 mock 掉，测试就变成在“复述实现”：重构一下测试就挂，真正的 bug 却测不出来。

mock 用完要清理。mockClear 只清调用记录；mockReset 还会清掉自定义实现，vi.fn() 会变成返回 undefined，vi.fn(impl) 和 spyOn 回到原来的实现；mockRestore 再把 spyOn 监视的对象恢复成原方法。

还要注意，模拟数据要来自真实契约，比如 OpenAPI 类型或录下来的响应。不然后端接口改了，测试还在通过。

mock 的边界应该放在哪里

下面的函数把 fetch 作为参数传进来，测试时就能换成假的：

TypeScript
// 被测函数
export async function loadUser(id: string, fetcher = fetch) {
  const response = await fetcher(`/api/users/${id}`);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return response.json();
}
TypeScript
import { expect, test, vi } from 'vitest';

test('非 2xx 响应时抛错', async () => {
  const fetcher = vi.fn().mockResolvedValue(new Response(null, { status: 404 }));
  await expect(loadUser('1', fetcher)).rejects.toThrow('HTTP 404');
  expect(fetcher).toHaveBeenCalledWith('/api/users/1');
});

这里只替换了网络这一层，loadUser 自己判断状态码、抛错的逻辑都是真实运行的。通过参数把依赖传进来，这种做法叫依赖注入，它比用 vi.mock 换掉整个模块更直接。而且假 fetcher 返回的是一个真正的 Response 对象，ok 和 status 的行为和浏览器一致：

JavaScript
const response = new Response(null, { status: 404 });
console.log(response.ok, response.status); // false 404

vi.mock 为什么不能直接用外面的变量

TypeScript
vi.mock('./analytics', () => ({ track: vi.fn() }));

vi.mock 会被提升到文件顶部，在所有 import 之前执行。这时文件里其他变量还没定义，所以工厂函数里不能直接用外部变量。确实需要时，用 vi.hoisted 声明，它会跟着一起被提升。

怎样在每个测试后自动清理

TypeScript
// vitest.config.ts
export default defineConfig({
  test: {
    clearMocks: true,
    restoreMocks: true,
  },
});

这两个选项容易被误解。clearMocks 在每个测试前清掉调用记录。restoreMocks 只把 vi.spyOn 创建的 spy 恢复成原方法，不会重置 vi.fn()。如果连 vi.fn() 上的自定义实现也要清掉，改用 mockReset: true。

改了 globalThis、Date 或环境变量时，用 vi.stubGlobal、vi.stubEnv 去改，再配合 unstubGlobals、unstubEnvs 自动还原，不然上一个测试的修改会漏到下一个测试里。

组件里直接调用 fetch 怎么办

如果组件内部直接写了 fetch，没法通过参数替换，可以用 MSW 在网络层拦截。组件代码不用改，同一套处理器还能用在开发环境和浏览器测试里：

TypeScript
import { http, HttpResponse } from 'msw';
import { setupServer } from 'msw/node';

const server = setupServer(
  http.get('/api/users/:id', ({ params }) =>
    HttpResponse.json({ id: params.id, name: '张三' }),
  ),
);

常见追问

怎样判断 mock 是不是太多了？

看两个信号。一是改了一个内部函数的名字，就要同时改很多测试里的 mock；二是测试里设置 mock 的代码比断言还长。出现这两种情况，说明 mock 的边界选得太靠里了，应该退到网络、时间这些外部边界上。
