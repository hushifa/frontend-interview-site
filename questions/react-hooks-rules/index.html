为什么 Hook 通常必须在组件顶层调用？

useState、useEffect 等 Hook 需要稳定的调用结构，让 React 把不同渲染中的状态与对应位置关联。条件应放在 Hook 内部逻辑或组件边界上，自定义 Hook 复用逻辑但不自动共享实例状态，use API 的例外也有自身限制。

参考答案

函数组件每次渲染都会重新执行，但 React 需要知道这一轮的第一个 useState 对应上一轮哪一份状态，第二个 useEffect 又对应哪一段同步关系。稳定的 Hook 调用结构使这种关联可以被维护。

如果某一轮跳过一个 Hook，后面的调用位置可能整体改变，React 就无法按原关系解释这些状态。因此 useState、useEffect 等常规 Hook 不能放进随渲染改变的条件、循环或提前返回之后。

顶层指调用结构，不是只能写在文件最前面

可以在 Hook 前计算普通局部值，也可以在自定义 Hook 中继续调用其他 Hook。关键是不要让常规 Hook 的调用随着分支、循环次数或嵌套回调而改变。

事件处理器、普通工具函数、useMemo 回调和 Effect 回调也不是可以随意调用新 Hook 的位置。事件中可以调用已经取得的状态 setter，但不能等用户点击后才调用 useState 创建一份组件状态。

如果列表有多个需要状态的项目，应渲染多个子组件，让每个组件维护自己的 Hook 结构，而不是在父组件的 map 中直接循环调用 useState。

有条件的外部工作，放到 Effect 内判断

JSX
import { useEffect, useState } from 'react';

export function EscapeHint({ enabled }) {
  const [pressed, setPressed] = useState(0);

  useEffect(() => {
    if (!enabled) return;
    function onKeyDown(event) {
      if (event.key === 'Escape') setPressed(value => value + 1);
    }
    window.addEventListener('keydown', onKeyDown);
    return () => window.removeEventListener('keydown', onKeyDown);
  }, [enabled]);

  if (!enabled) return null;
  return <output aria-label="Escape 次数">{pressed}</output>;
}

enabled 为 false 时，useState 和 useEffect 仍按同样的结构被调用，只是 Effect 不建立监听，组件不输出界面。enabled 变为 false 后，上一轮已经建立的监听也会被清理。

这不同于把整个 useEffect 包在 if (enabled) 里面。条件控制的是是否建立那份外部关系，而不是 React 是否能看到这个 Hook 的位置。

如果设计上希望禁用时把整个状态实例也销毁，可以由父组件决定是否渲染 EscapeHint。重新挂载时状态重新开始，这是组件生命周期选择，而不是有条件调用 Hook。

自定义 Hook 封装逻辑，不自动共享状态

下面继续使用前面的 useState 导入：

JSX
function useCounter(initialValue = 0) {
  const [count, setCount] = useState(initialValue);
  function increment() {
    setCount(value => value + 1);
  }
  return { count, increment };
}

function Counter({ label }) {
  const { count, increment } = useCounter();
  return <button type="button" onClick={increment}>{label}：{count}</button>;
}

export default function Counters() {
  return (
    <section>
      <Counter label="甲" />
      <Counter label="乙" />
    </section>
  );
}

两个 Counter 都调用 useCounter，但各自拥有一份状态。点击甲不会自动增加乙；共享的是逻辑代码，不是某个模块级计数器。

如果真的需要共享同一份状态，可以提升到共同祖先，再通过 props、Context 或合适的外部 store 提供。不能因为 Hook 名字相同，就把它当成单例服务。

自定义 Hook 也受同样的调用规则约束。给普通函数加一个 use 前缀，不会让它在 React 之外合法使用组件状态，只是帮助代码表达用途并让相关 lint 工具识别规则。

提前返回为何特别容易踩坑

一个组件第一次发现数据缺失就提前返回，第二次数据到达后才继续执行 useState，这也改变了调用结构。不是只有显式写在 if 花括号里面的 Hook 才算有条件调用。

可以把需要调用的 Hook 放到提前返回前，并在内部处理缺失数据；也可以把有数据时才需要的完整逻辑拆成一个子组件，由父组件控制是否挂载。选择取决于状态应该保留还是重置。

组件和 Hook 的定义也应保持稳定。每次渲染临时定义一个新的组件类型，可能让 React 把它视为新的身份，导致状态反复重置；不能只检查 Hook 出现的位置，还要考虑承载它的组件身份。

use API 是明确的例外，不是规则废除

React 的 use API 有不同约束，可以在某些条件和循环中读取资源，但仍必须处于 React 允许的组件或 Hook 上下文，也不能用 try/catch 随意包住其读取流程。处理等待与错误需要相应的 Suspense 和错误边界机制。

这个例外不能推广到 useState、useEffect、useMemo 等其他 Hook。判断一个 API 的规则，应阅读对应文档，而不是看到它以 use 开头就推断所有行为完全相同。

稳定顺序只是正确使用 Hook 的一部分

保持调用位置正确，不代表依赖数组、闭包和清理逻辑就一定正确。Effect 可能漏依赖，回调可能读取旧快照，订阅也可能没有解除。这些需要另外的规则和测试。

建议使用官方维护的 Hooks lint 规则，并理解诊断为何出现，而不是大面积禁用检查。重构时把状态来源、条件工作与组件生命周期分清楚，通常就不需要通过动态选择 Hook 或绕过 lint 来维持行为。
