JSBridge 是什么？WebView 页面如何与原生或小程序通信，怎样做安全校验？

JSBridge 是 WebView 里网页和 App 原生代码之间传话的通道。讲清两种调用方向和常见实现（注入对象、消息处理器、URL 拦截），小程序 web-view 的通信限制，以及来源校验、能力白名单和参数校验。

参考答案

简答

App 里经常嵌着网页，网页想调用拍照、分享这类原生能力，就需要一个和 App 传话的通道，这就是 JSBridge。它是双向的：网页调宿主的能力，宿主把结果或事件传回网页。这里的宿主指 App 原生代码或小程序。

网页调宿主常见三种方式：宿主往页面里注入一个 JS 对象，比如 Android 的 addJavascriptInterface；用平台提供的消息接口，比如 Android 的 addWebMessageListener、iOS 的 window.webkit.messageHandlers；或者拦截一个自定义协议的 URL。反过来，宿主调网页就是在 WebView 里执行一段 JS。两边只能传可序列化的数据，异步调用要靠回调 ID 或 Promise 把请求和响应对上。

微信小程序的 web-view 更受限。网页不能直接调小程序 API，只能用 JSSDK 提供的 wx.miniProgram.navigateTo、postMessage 等接口，而且 postMessage 的消息只在后退、组件销毁、分享等特定时机才送到。

安全上要把网页当成不可信的输入。只对可信页面开放 bridge，能拿到来源时逐条检查来源，只开放白名单里的能力，逐个校验参数，敏感操作再加用户确认或服务端校验。

网页怎样调用宿主

最直接的是注入对象。Android 用 webView.addJavascriptInterface(obj, "bridge") 把一个 Java 对象挂到页面上，网页直接调它的方法。官方文档说明了几个细节：对象会注入到页面的所有 frame，包括 iframe；目标 API 17（Android 4.2）及以上时，只有加了 @JavascriptInterface 注解的公共方法能被调用；注入要等到下一次页面加载后才生效；JS 的调用发生在 WebView 的后台线程上。

可是注入对象拿不到“是谁在调用”。所以 AndroidX 提供了带来源的消息接口 WebViewCompat.addWebMessageListener(webView, "bridge", allowedOriginRules, listener)。它只往 origin 符合规则的 frame 里注入对象。网页调用 bridge.postMessage(data)，原生的 onPostMessage 回调能拿到 sourceOrigin 和 isMainFrame，再通过 replyProxy.postMessage 回复。用之前要先用 WebViewFeature.isFeatureSupported(WEB_MESSAGE_LISTENER) 检查支不支持。

iOS 用的是消息处理器。用 userContentController.add(handler, name: "bridge") 安装一个实现了 WKScriptMessageHandler 的处理器，网页调用 window.webkit.messageHandlers.bridge.postMessage(data)，WebKit 就会回调 userContentController(_:didReceive:)。name 在同一个 WKUserContentController 里必须唯一，也不能为空，函数定义在页面默认的 content world，也就是 WKContentWorld.page。

收到的 WKScriptMessage.body 只允许 NSNumber、NSString、NSDate、NSArray、NSDictionary、NSNull 这几种类型。消息上的 frameInfo 表示发消息的那个 frame，可以读到 isMainFrame 和 securityOrigin，后者包含协议、主机名、端口（iOS 9+）。

普通处理器只能收消息，不能直接回复。iOS 14 起可以用带回复的处理器：用 addScriptMessageHandler(_:contentWorld:name:) 安装 WKScriptMessageHandlerWithReply，函数会定义在指定 content world 的所有 frame 里。原生在 userContentController(_:didReceive:replyHandler:) 里调用 replyHandler(reply, nil) 回复；出错时 reply 传 nil，再给一个错误字符串。reply 同样只能是上面那几种类型。不需要回复时，用 WKScriptMessageHandler 就够了。

iOS 还能预先注入脚本，在页面里提前挂好 bridge 的封装。用 WKUserScript(source:injectionTime:forMainFrameOnly:)：atDocumentStart 在文档元素创建后、其他内容加载前注入，atDocumentEnd 在文档加载完成后、其他子资源加载前注入；forMainFrameOnly 为 true 只注入主 frame，为 false 注入所有 frame。官方要求在创建 WebView 之前，就把脚本加到配置的 WKUserContentController 里。

最后一种是 URL 拦截。网页跳转一个自定义协议的地址，比如 myapp://share?...，宿主在导航回调里拦下来解析。这种方式受 URL 长度限制，现在多当兼容方案用。

宿主怎样调用网页

宿主在 WebView 里执行一段 JS，比如调用网页事先挂好的 window.onNativeEvent(json)。

Android 用 evaluateJavascript(script, callback)。它在当前页面上下文里异步执行，必须在 UI 线程调用，回调也在 UI 线程。iOS 用 webView.evaluateJavaScript(script, completionHandler:)，另外还有 async 版本。执行结束后不管成功失败都会调回调，回调总在主线程运行，参数是执行结果或错误。

拼脚本时要先把数据编码成 JSON，不要把字符串直接拼进代码里。否则数据里带个引号，脚本就坏了，还可能被注入代码。

怎样把请求和响应对上

消息接口大多是“发出去就不管”的。网页同时发了好几个请求，宿主回来的结果要知道是哪一个的。常见做法是给每次调用分配一个 ID：

JavaScript
// 网页侧：给每次调用分配 ID，宿主处理完后按 ID 回调
const pending = new Map();
let seq = 0;

export function callNative(method, params) {
  return new Promise((resolve, reject) => {
    const id = ++seq;
    pending.set(id, { resolve, reject });
    window.webkit.messageHandlers.bridge.postMessage({ id, method, params });
  });
}

// 宿主执行 window.__bridgeReply({ id, error, result }) 回传结果
window.__bridgeReply = ({ id, error, result }) => {
  const task = pending.get(id);
  if (!task) return;
  pending.delete(id);
  error ? task.reject(new Error(error)) : task.resolve(result);
};

callNative 把 resolve 和 reject 按 ID 存进 pending，宿主处理完调用 __bridgeReply 带回同一个 ID，就能找到对应的 Promise。

实际项目里还要加超时，清理一直没回的 pending。另外网页如果是在普通浏览器里打开的，宿主根本不存在，也要给出降级。

小程序 web-view 有哪些限制

web-view 加载的网页，要先在小程序管理后台配置业务域名，个人类型的小程序暂不支持。

网页引入 JSSDK 以后，只能用 wx.miniProgram.navigateTo、navigateBack、switchTab、reLaunch、redirectTo、postMessage、getEnv 等接口，以及部分 JSSDK 能力，比如图片、定位、扫一扫。

最容易踩坑的是 wx.miniProgram.postMessage，它不会实时送到。组件的 bindmessage 只在小程序后退、组件销毁、分享、复制链接这些时机才触发，e.detail.data 是多次消息组成的数组。所以需要实时交互时，常见做法是让网页跳转到小程序页面，或者通过服务端中转。

网页可以用 window.__wxjs_environment === 'miniprogram' 或 wx.miniProgram.getEnv 判断自己是不是跑在小程序里。

安全上要校验什么

WebView 里可能加载第三方页面、广告 iframe，页面本身也可能有 XSS。只要 bridge 对所有页面开放，攻击者就能调用宿主的能力。所以要从下面几方面收紧。

先是校验来源。能拿到调用方来源时，就检查发起调用的页面或 frame 的 origin 在不在白名单里。

addJavascriptInterface 会注入到所有 frame，回调里又拿不到调用方的 origin，所以只能靠控制加载哪些页面来限制，比如只加载白名单地址、拦截跳转。需要按来源区分时，改用 addWebMessageListener：用 allowedOriginRules 限定注入范围，官方建议只用 HTTPS 规则，通配符 * 会注入所有 frame，这时消息要当成不可信数据处理；然后在 onPostMessage 里再检查 sourceOrigin 和 isMainFrame。

iOS 在处理器里检查 message.frameInfo.isMainFrame，以及 message.frameInfo.securityOrigin 的协议、主机名、端口。WKUserScript 不需要进 iframe 时，设 forMainFrameOnly: true。

比较来源时，只比 URL 前缀是不够的，https://trusted.com.evil.com 这样的地址就能绕过。应该先解析，再比较协议和主机名。

然后是最小能力。按页面来源开放不同的方法集合，不要提供“执行任意命令”“读写任意文件”这种通用方法。

参数也要逐一校验：类型、长度、枚举值都要查；文件路径、跳转地址同样按白名单检查。

敏感操作要二次确认。支付、获取手机号这类操作，由宿主弹出原生确认框，关键结果以服务端校验为准，不要相信网页传回来的“已支付”。

最后是限制导航。WebView 只允许跳转到白名单域名，防止页面被导航到恶意站点以后，继续使用 bridge。

Electron 里的 preload 和 IPC 是同一类问题，见《Electron 应用的主进程、渲染进程和 IPC 有哪些安全边界？》。

常见追问

怎么判断 bridge 是否已就绪？

宿主注入通常有时间差。可以让宿主在注入完成后派发一个自定义事件，网页监听到这个事件再调用。在微信 web-view 里，可以监听 WeixinJSBridgeReady。

addJavascriptInterface 在旧系统上有什么风险？

官方文档指出，目标 API 16（Android 4.1）及以下的应用，或者运行在 Android 4.2 以下设备上的应用，页面 JS 可以通过反射访问注入的对象，以宿主的权限执行 Java 代码。所以包含不可信内容的 WebView 要格外小心。

用 prompt、alert 拦截来通信可以吗？

早期有人这么做，但它会和真正的弹窗冲突，而且是同步的，会卡住页面。应该优先用平台提供的消息接口。
