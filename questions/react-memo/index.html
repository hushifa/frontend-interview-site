memo、useMemo、useCallback 各自优化什么？

memo 尝试跳过某些父级引起的子组件计算，useMemo 复用计算结果，useCallback 复用函数身份。它们依赖正确的比较与依赖关系，不负责修复状态逻辑，也不能保证组件永远不重新渲染。

参考答案

简答

memo 包裹组件，props 浅比较相等时跳过子组件的重新渲染；useMemo 缓存计算结果；useCallback 缓存函数引用。三者常配合使用：传给 memo 子组件的对象和函数，需要 useMemo/useCallback 保持引用稳定，memo 才有效。它们都是性能优化，不保证不重新执行。接入 React Compiler 后，大多数手写缓存可以省掉。

这三个 API 都与复用有关，但复用的对象不同。memo 包装组件，useMemo 记住一次计算的结果，useCallback 记住一个函数引用。使用时应先知道哪一段工作昂贵，或者哪一个身份变化会触发无用更新。

它们属于性能优化，而不是业务正确性的基础。如果去掉缓存后功能就错了，应该先修复数据流、副作用或依赖，而不是继续增加缓存层。

三种工具分别管哪一层

工具主要复用内容不会自动阻止的事情
memoprops 相同时的组件计算结果自身 state、所读取 Context 等引起的更新
useMemo依赖相同时的计算结果依赖改变、缓存被丢弃或计算本身副作用造成的问题
useCallback依赖相同时的函数身份函数被调用时执行内部逻辑

memo 默认对各个 prop 使用 Object.is 比较，不是对对象内容做深度比较。useMemo、useCallback 的依赖比较也基于值身份与数值规则。

配合使用时，稳定身份才有意义

下面的数据很小，只用于观察身份关系，不代表这种规模必须添加缓存：

JSX
import { memo, useCallback, useMemo, useState } from 'react';

const items = [
  { id: 'html', title: 'HTML' },
  { id: 'css', title: 'CSS' },
  { id: 'react', title: 'React' },
];

const ResultList = memo(function ResultList({ entries, onSelect }) {
  console.log('计算结果列表');
  return (
    <ul>
      {entries.map(item => (
        <li key={item.id}>
          <button type="button" onClick={() => onSelect(item.id)}>{item.title}</button>
        </li>
      ))}
    </ul>
  );
});

export default function SearchableList() {
  const [query, setQuery] = useState('');
  const [dark, setDark] = useState(false);
  const [selected, setSelected] = useState('');

  const entries = useMemo(() => {
    const term = query.toLowerCase();
    return items.filter(item => item.title.toLowerCase().includes(term));
  }, [query]);

  const onSelect = useCallback(id => {
    setSelected(id);
  }, []);

  return (
    <section data-theme={dark ? 'dark' : 'light'}>
      <label>搜索<input value={query} onChange={event => setQuery(event.target.value)} /></label>
      <button type="button" onClick={() => setDark(value => !value)}>切换主题</button>
      <ResultList entries={entries} onSelect={onSelect} />
      <output aria-label="已选项目">{selected}</output>
    </section>
  );
}

query 不变、只切换父级的 dark 时，useMemo 可以返回同一 entries 数组，useCallback 可以返回同一 onSelect，memo 因而有机会跳过 ResultList 的重复计算。

如果每轮都直接 filter，就会创建一个新数组，即使项目内容相同，entries 的引用也不同。如果每次给 memo 子组件传一个新箭头函数，函数 prop 同样变化。只包 memo 却不看传入值，可能看不到预期收益。

示例中的日志只是观察计算，不是提交次数或性能指标。React 仍保留重新渲染的权利，不能把“日志必须永远只出现一次”当作功能契约。

useMemo 不会让计算自动变成后台任务

useMemo 的计算在渲染过程中发生，必须是纯计算。第一次计算、依赖变化或需要重新计算时，昂贵工作仍然会占用执行时间。

因此把一个很慢的循环包进 useMemo，只能减少某些重复执行，不能消除首次成本，也不把它变成 Worker。大数据量还需要考虑算法、分页、虚拟化、任务拆分或真正的后台计算。

也不要用 useMemo 创建需要准确释放的连接或订阅。缓存可能被丢弃，副作用生命周期应由对应机制管理，而不是把缓存值当成永久资源所有权。

useCallback 缓存的是函数，不是调用结果

onSelect 每次被调用仍然会执行 setSelected。它稳定的是传给子组件的函数身份，不是给所有 id 预先缓存执行结果。

在普通代码中，传给 useCallback 的函数表达式仍可能在渲染时被创建，React 再决定返回已有缓存还是这次的函数。因此它常用于减少依赖身份变化，不应被宣传为“完全不创建函数”的工具。

空依赖也不代表函数体自动看到最新状态。本例只使用稳定 setter 和调用参数，所以不需要 query 等依赖；如果函数读取会变化的 props 或 state，就必须按真实关系维护依赖，或重新设计更新方式。

自定义比较函数最容易把旧行为留下来

memo 可以提供比较函数，但返回 true 的含义是新旧 props 会产生相同输出和行为，不只是某个文字字段相同。

如果忽略 onClick 等函数 prop 的变化，子组件可能继续持有捕获旧状态的函数，画面文字看起来正确，点击行为却已过期。深度比较大型对象也可能比重新渲染更慢，尤其结构未来变深时成本更不可控。

通常先减少不必要的大对象 prop、把组件边界和状态放置调整清楚，再决定是否需要自定义比较。不要把所有对象强行 JSON.stringify 后比较，当成通用安全实现。

Context、状态和 JSX 身份也会影响结果

memo 子组件自身的 state 更新不会被 memo 拦住，读取的 Context 变化也应传递进来。父级返回新的 JSX children 时，作为 prop 的 children 身份也可能变化，不能只检查自己显式传入的两个字段。

把状态放得更靠近真正使用它的组件，常常能直接减少受影响的范围，比给整棵页面逐个加 memo 更容易理解。列表 key 不稳定造成的重新挂载，也不是 memo 能修复的问题。

React Compiler 与手工缓存需要看实际配置

启用并正确运行 React Compiler 的项目，可能由编译器自动完成许多记忆化，减少手工 memo、useMemo、useCallback 的需要。但仅仅安装某个 React 版本，不等于整个构建链已经启用编译优化。

无论手工还是自动缓存，都依赖纯渲染和正确数据流。用 Profiler 与真实交互测量计算时间、提交和延迟，确认收益后再保留优化；不要仅凭代码里出现了三个缓存 API，就认定性能一定更好。
