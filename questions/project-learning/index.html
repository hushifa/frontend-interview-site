你平时怎样学习前端？最近在学什么？

说一个最近真实在学的具体主题，讲清楚为什么学、怎样学、学到了什么、用在了哪里。学习方法上强调先看官方文档、动手写例子验证、交叉核对多个来源，并把学到的东西用到工作或个人项目里，而不是罗列看过多少课程和文章。

参考答案

本题是回答思路与示例，不对应某个官方规范。示例中的经历和数字只用来演示怎样表达。

简答

比较好的回答从一个具体主题开始，比如“最近在学浏览器的 View Transitions，因为我们的列表页切到详情页时想做一个过渡动画”。有了主题和原因，面试官就知道你的学习是被实际问题驱动的。

面试官问这道题，是想看你能不能跟上技术变化，以及你学东西的方法靠不靠谱。所以重点不在学了多少，而在怎样学：先看官方文档，再写小例子验证，遇到不确定的地方去查多个来源对照。

最后一定要说学的东西用在了哪里，比如在项目里落地了、写了团队分享、或者做了一个小工具。学了能用出来，才说明真的学会了。

要注意，说到的主题面试官很可能当场追问，所以只说自己真的弄懂了的东西。不要只报一串课程名和博主名，也不要说一个刚听说、讲不出细节的新技术。

一个完整的示例

我平时学东西主要有两个来源：一是工作里遇到的问题，二是关注的技术动态。最近在学的是 View Transitions。起因是我们的商品列表点进详情时，产品想要一个图片放大的过渡效果，我之前用 JS 计算位置做过，代码比较复杂。

我先看了 MDN 上 View Transition API 的文档，了解它怎样给新旧两个画面拍快照、再用 CSS 动画过渡。然后写了一个只有两张卡片的小例子，验证了同文档内的过渡，也看了不支持这个 API 的浏览器要怎样回退。确认可行后，在项目里给详情页加上了，不支持的浏览器直接跳转，不影响功能。

做完以后我在组里做了一次十几分钟的分享，把用法和不支持时的回退方式整理成了文档。

这个回答讲了一个完整的闭环：为什么学、看什么资料、怎样验证、怎样落地、怎样沉淀。面试官接下来问什么都能接住，因为每一步都是自己做过的。示例中的具体技术点换成你自己学过的东西，学过什么就讲什么。

学习方法怎样讲才可信

很多人回答“看文档、看博客、看视频”，这几乎人人都会说。更有说服力的是讲出你怎样判断信息靠不靠谱。

MDN 的 Research and learning 给了几条具体建议：遇到某个工具或产品的问题，先查它的官方文档；看资料时检查发布和更新日期，因为内容可能已经过时；不要只依赖一个来源，要交叉对照。它还提到，用 AI 工具查问题要谨慎，AI 经常给出误导甚至错误的答案，要自己测试并用其他来源验证。你可以用自己的话把这些习惯讲出来，再配一个例子，比如“有次博客上说某个 CSS 属性在 Safari 不支持，我去查了 MDN 的兼容性表格，发现已经支持了，就没再写兼容代码”。

要讲“动手”这一步。MDN 同一篇文章也提醒，复制粘贴自己看不懂的代码会让 bug 更难修，还可能带来安全、性能或无障碍问题，建议至少先弄懂再用，最好学完自己写一遍。面试时说“我会写一个最小例子跑一下”，比说“我看懂了”可信得多。

如果你有系统学习的经历，比如按 MDN 的 Learn web development 把 HTML、CSS、JavaScript 的核心模块走了一遍，也可以提，但它更适合入门阶段。工作几年后，面试官更想听你怎样解决工作中的新问题。

哪些说法要避免

“我每天下班都学到很晚”这类话，面试官无法验证，也听不出效果。

“最近在学 Rust、Go、AI、Web3”，罗列太多主题，每个都讲不深，会显得浮躁。讲一两个就够了。

只说“看过某某课程”而说不出学到了什么，等于什么也没说。

常见追问

你说的这个技术，有什么缺点或者限制？

这是在看你是不是真的用过。讲你实际遇到的限制，比如浏览器支持范围、在哪种场景下效果不好、你是怎样处理的。说不出缺点，面试官会觉得你只是看过介绍。

怎样判断一个新技术值不值得学？

可以说你会看它解决的是不是你正在遇到的问题、主流浏览器或者框架的支持情况、社区和官方是否还在维护。和工作无关又只是热门的东西，先了解它解决什么问题就够，不急着深入。
