Agent 前端界面怎样展示计划、工具调用和人工确认？

建模 Agent 的消息、步骤、工具状态和审批状态，避免只显示一段不可解释的最终文本。

参考答案

Agent 一次任务可能先检索资料，再生成修改方案，等待用户确认，最后调用工具写入。只显示一个旋转图标和最终回答，会让用户无法判断它是在等待网络、等待自己确认，还是已经执行了操作。

界面应展示可核验的运行状态与结果，区分计划、尝试和已完成事实，而不是把模型写出的计划直接勾成完成。

会话、运行和步骤是不同层次

会话保存用户与助手的历史；运行表示一次具体执行尝试；步骤表示模型请求、检索、工具调用或批准等可观察活动。一次运行还可能有并行步骤，因此不一定是一条简单的线性进度条。

每个对象需要稳定 ID，步骤记录开始、结束、状态和关联结果。重试可以创建新的 attempt，避免把第一次失败的记录直接覆盖掉，让用户误以为从未失败。

计划也可能在执行中调整，应说明已发现的新条件，不要给尚未发生的步骤伪造精确进度。若总工作量未知，显示“正在检索资料”比显示没有依据的 87% 更诚实。

状态来自执行事件，不来自模型措辞

模型输出“我已经保存文件”，不能作为保存成功的权威证据。应等待受控执行端返回成功，并关联文件、版本或其他可验证结果。

工具请求的参数仍在流式接收时，不能标为运行中；待批准表示系统正在等待用户，不是模型继续计算；取消请求已发送也不等于所有外部步骤已经停止。

错误状态需要区分可重试失败、用户拒绝、权限不足和结果未知。网络断开时工具可能已经成功执行，显示“连接中断，正在核对结果”有时比直接显示失败更准确。

计划说明不必暴露或编造内部思考

用户需要知道准备做什么、为什么需要某项权限、会影响哪些数据，以及目前有哪些证据。可以用简短的行动摘要、工具记录和来源呈现这些信息。

不应把不可核验的“内部推理过程”当成执行日志，也不必用大量逐字思考文本占据界面。可观察步骤与产物才是恢复、审计和用户理解的可靠依据。

人工确认应嵌在具体动作前

读取公开资料与删除文件的风险不同。需要确认的动作应展示目标、参数与影响，并在执行之前暂停对应步骤。用户同意后，执行端仍要校验当前权限和参数是否变化。

多个并行步骤中，一步待批准不一定意味着所有只读准备都必须停下，但任何依赖该批准的副作用都不能提前发生。界面应表达依赖关系，避免用户以为点一次允许就授权了之后所有动作。

刷新恢复需要服务端事实来源

前端内存里的数组无法证明后台任务是否还在运行。重连时应获取服务端快照或事件序列，根据运行 ID、步骤 ID 和版本合并，处理重复事件与缺口。

如果客户端收到结束事件后又迟到一条旧增量，不应把完成状态倒退成运行中。顺序、幂等与版本规则应由协议明确，而不是按到达顺序随意覆盖。

恢复执行也不同于恢复展示。查看过去步骤不应再次触发工具，重放日志更不能等同于重放副作用。

结果要帮助用户检查，而不是只报“完成”

最终状态可以附上修改摘要、文件链接、验证结果和未完成事项。工具原始输出可能很长或包含敏感内容，应按用途脱敏与折叠，不要把所有日志默认展开。

失败时保留已完成产物与可恢复位置，停止时说明哪些工作已结束、哪些结果仍未知。这样的状态模型才能支持长任务，而不只是让一次演示看起来像在自动执行。
