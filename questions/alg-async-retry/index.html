异步请求重试应该怎样设计？

从失败分类与幂等性出发，给出带次数限制、随机退避和可取消等待的实现，并说明 Retry-After、整体超时、请求重建和重复副作用的处理。

参考答案

一次请求失败后，再试一次可能恢复，也可能让问题更严重。比如临时服务不可用值得稍后重试，密码错误通常不值得原样重复；创建订单超时则更复杂，客户端没拿到结果，不代表服务器没有创建成功。

因此重试的第一步不是写循环，而是确定哪些失败可重试、最多尝试多少次、等待多久，以及重复执行是否安全。

失败类型决定策略，不能只看 catch

fetch 收到 HTTP 404、429 或 503 时，通常仍会兑现为 Response，需要检查状态码后按业务分类。网络断开、CORS、取消、JSON 解析失败和业务错误，也不是同一种原因。

例如某个只读接口可以约定重试 429、502、503、504，但这不意味着所有接口、所有 5xx 都应重复发送。400、权限拒绝和确定的业务校验失败通常需要修改输入或身份状态；用户主动取消更不应被当成下一次重试的理由。

浏览器抛出的 TypeError 也可能来自错误 URL、CORS 或其他不可恢复情况，不能仅凭错误类名就判断一定是临时网络波动。

次数、退避与总预算分别限制什么

maxAttempts=3 表示包含第一次在内最多三次，不是失败后再加三次。指数退避让等待上限逐步变长，随机抖动让不同客户端不至于在同一个时刻一起重试。

还要有最大单次等待和整体等待预算。次数有限并不代表总时间有限：某一次请求本身如果永远不结束，循环仍然可能挂住。

下面先实现一个通用框架：request 接收 attempt 和 signal，shouldRetry 必须同步返回布尔值，默认不重试；getRetryAfter 返回服务端要求的等待毫秒，或者 null 表示没有要求。

JavaScript
function waitForRetry(ms, signal) {
  return new Promise((resolve, reject) => {
    if (signal?.aborted) {
      reject(signal.reason);
      return;
    }

    const timer = setTimeout(() => {
      signal?.removeEventListener('abort', onAbort);
      resolve();
    }, ms);

    function onAbort() {
      clearTimeout(timer);
      reject(signal.reason);
    }

    signal?.addEventListener('abort', onAbort, { once: true });
  });
}

async function requestWithRetry(request, {
  maxAttempts = 3,
  baseDelayMs = 200,
  maxDelayMs = 5000,
  shouldRetry = () => false,
  getRetryAfter = () => null,
  signal,
} = {}) {
  if (typeof request !== 'function' || typeof shouldRetry !== 'function' || typeof getRetryAfter !== 'function') {
    throw new TypeError('请求和重试策略必须是函数');
  }
  if (!Number.isSafeInteger(maxAttempts) || maxAttempts < 1) {
    throw new RangeError('尝试次数必须为正整数');
  }
  for (const delay of [baseDelayMs, maxDelayMs]) {
    if (!Number.isInteger(delay) || delay < 0 || delay > 2_147_483_647) {
      throw new RangeError('等待参数必须是计时器范围内的非负整数');
    }
  }

  let delayCap = Math.min(baseDelayMs, maxDelayMs);

  for (let attempt = 1; attempt <= maxAttempts; attempt += 1) {
    signal?.throwIfAborted();
    try {
      const result = await request({ attempt, signal });
      signal?.throwIfAborted();
      return result;
    } catch (error) {
      signal?.throwIfAborted();
      if (attempt === maxAttempts) throw error;

      const retryable = shouldRetry(error, attempt);
      if (typeof retryable !== 'boolean') {
        throw new TypeError('shouldRetry 必须同步返回布尔值');
      }
      if (!retryable) throw error;

      const retryAfterMs = getRetryAfter(error, attempt);
      if (retryAfterMs !== null && (typeof retryAfterMs !== 'number' || Number.isNaN(retryAfterMs) || retryAfterMs < 0)) {
        throw new TypeError('服务端等待时间必须为非负毫秒或 null');
      }
      if (retryAfterMs !== null && retryAfterMs > maxDelayMs) throw error;

      const jitter = Math.floor(Math.random() * (delayCap + 1));
      await waitForRetry(Math.max(jitter, Math.ceil(retryAfterMs ?? 0)), signal);
      delayCap = Math.min(maxDelayMs, delayCap * 2);
    }
  }
}

抖动在当前上限内选择等待，而不是所有客户端都等完全相同的数值。上限逐轮倍增并截到 maxDelayMs，避免无边界扩大；baseDelayMs=0 时也不会产生指数计算溢出后变成 NaN 的问题。

取消信号既检查在请求前后，也传给等待函数。等待期间取消会清掉计时器并拒绝，不会在用户取消后又自动开始下一轮。拒绝沿用 signal.reason，不能假定所有取消原因都是固定名称的 Error。

Retry-After 不是随便截短到客户端上限

服务器可能要求等待若干秒，或者等待到某个 HTTP 日期。如果它要求一分钟，而客户端只愿意等五秒，不能直接取最小值五秒后就重发。示例选择停止自动重试，把错误交给调用者，让界面决定是否提示稍后再试。

可以用下面的解析器接入常见的秒数和标准 IMF-fixdate 日期格式。无法识别的非空要求返回 Infinity，表示本示例不擅自提前重试；它不是一个穷尽所有历史日期格式的 HTTP 解析库。

JavaScript
function retryAfterMilliseconds(value, now = Date.now()) {
  if (value === null) return null;
  const text = value.trim();
  if (/^\d+$/.test(text)) return Number(text) * 1000;

  const timestamp = Date.parse(text);
  if (!Number.isFinite(timestamp) || new Date(timestamp).toUTCString() !== text) {
    return Infinity;
  }
  return Math.max(0, timestamp - now);
}

日期形式受客户端时钟偏差影响，不能把本机时间当成无误差的服务端时钟。更复杂的客户端可以结合响应 Date 和网络时间设计换算；对于不确定的要求，保守停止比擅自缩短等待更明确。

跨源响应的 Retry-After 还需要正确暴露给脚本读取，开发者工具能看到头不代表 JavaScript 一定能访问它。

把策略用于一个约定可重试的 GET 接口

下面假设 /api/catalog 是只读目录接口，并约定可在相应状态下重新获取。HttpResponseError 是这里定义的应用错误类型，不是浏览器自动生成的 HTTP 异常。

JavaScript
class HttpResponseError extends Error {
  constructor(status, retryAfter) {
    super(`HTTP ${status}`);
    this.name = 'HttpResponseError';
    this.status = status;
    this.retryAfter = retryAfter;
  }
}

async function loadCatalog(signal) {
  const timeout = AbortSignal.timeout(10_000);
  const combined = signal ? AbortSignal.any([signal, timeout]) : timeout;

  return requestWithRetry(async ({ signal }) => {
    const response = await fetch('/api/catalog', { signal });
    if (!response.ok) {
      const error = new HttpResponseError(response.status, response.headers.get('Retry-After'));
      await response.body?.cancel();
      throw error;
    }
    return response.json();
  }, {
    signal: combined,
    maxAttempts: 3,
    shouldRetry: (error) => error instanceof HttpResponseError && [429, 502, 503, 504].includes(error.status),
    getRetryAfter: (error) => retryAfterMilliseconds(error.retryAfter),
  });
}

调用者应捕获 loadCatalog 的拒绝，并按取消、超时或最终 HTTP 错误显示状态。这里明确不自动重试任意网络 TypeError 或 JSON 解析失败，项目若有可靠的错误分类，可以另行扩展策略。

同一个超时信号覆盖这轮获取与退避，底层 fetch 真正使用它。AbortSignal.timeout/any 需要对应环境支持，timeout 也受浏览器活跃时间等规则影响，不是跨冻结或休眠的严格墙上时间保证。

对于通用 request 函数，若它根本不配合 signal，框架不能强行停止其内部工作；甚至一直不结束的 Promise 仍可能让等待无法完成。需要额外停止外层等待时可以设计竞速，但“调用方不再等待”和“内部任务已经取消”仍是两件事。

每轮要重新创建可发送的请求

重试应调用请求工厂，而不是把同一个已经消耗的 Request body 或流反复发送。普通 GET 比较简单，上传流和一次性请求体则需要确认可重放，不能只在 catch 里原样再 fetch 一次。

失败响应也要按需要消费或取消响应体，避免大量失败重试浪费连接和内存。最终错误应保留有用的状态和原因，而不是一律改成“网络错误”，否则用户和日志都无法判断下一步。

写操作的安全性最终由业务保证

超时发生时，服务器可能已经写入成功，只是响应丢失。再次提交订单或支付，会不会产生第二次操作，需要服务端幂等键、状态查询和相应事务保证。

幂等键应标识同一次用户操作，重试沿用同一个键，而不是每一轮都生成新键。取消客户端也不等于撤销服务器操作，必要时还需要查询最终结果或执行业务补偿。

重试还会增加总流量。前端、网关和 SDK 如果各自重试三次，组合后的请求量可能远大于三次。应明确哪一层负责重试、怎样限制并发与总预算，并记录尝试次数和最终原因；不要把重试当成掩盖所有错误的默认动作。
