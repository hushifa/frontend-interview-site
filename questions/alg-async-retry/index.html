异步请求重试应该怎样设计？

只重试过一会儿可能自己好的失败，比如 429、502、503、504；次数要有上限，等待时间每次翻倍再加随机抖动，服务端给了 Retry-After 就照办，等待中途能取消。写操作重试前，服务端必须用幂等键保证重复提交不会做两次。

参考答案

简答

先分清哪些失败值得重试。429、502、503、504 和网络中断，过一会儿可能自己就好了，可以重试。400、401、403、404 和业务校验失败，原样再发一遍也不会成功，不要重试。

次数要有上限，maxAttempts 包括第一次请求。等待时间用指数退避加随机抖动：上限每轮翻倍并封顶，实际等待在 0 到上限之间随机取，这样大量客户端不会在同一时刻一起重试。服务端返回了 Retry-After，等待就不能比它短；它要求的时间超过我们能接受的上限，就不再重试，把错误交给界面。

重试要能取消。每次请求前后都检查取消信号，等待的时候也监听它，用户离开页面以后就不会再发下一轮。

最要小心的是写操作。超时不代表服务端没执行，创建订单这类请求要带一个幂等键，每次重试都用同一个键，由服务端去重。

先分清是什么失败

fetch 有个容易误会的地方：收到 404 或 503，它不会抛错，照样正常返回一个 Response。所以要自己检查 response.ok 和状态码。

反过来，网络断开、被 CORS 拒绝、URL 写错，都会抛出 TypeError。光看错误类型，分不出是“网络抖了一下”还是“地址根本不对”。所以哪些错误能重试，要由调用方按接口的约定告诉重试函数，重试函数自己猜不出来。

一个通用的重试函数

函数的参数约定是这样的：request 接收这是第几次尝试和取消信号；shouldRetry 同步返回要不要重试，默认不重试；getRetryAfter 返回服务端要求等多少毫秒，没有要求就返回 null。

JavaScript
function waitForRetry(ms, signal) {
  return new Promise((resolve, reject) => {
    if (signal?.aborted) {
      reject(signal.reason);
      return;
    }

    const timer = setTimeout(() => {
      signal?.removeEventListener('abort', onAbort);
      resolve();
    }, ms);

    function onAbort() {
      clearTimeout(timer);
      reject(signal.reason);
    }

    signal?.addEventListener('abort', onAbort, { once: true });
  });
}

async function requestWithRetry(request, {
  maxAttempts = 3,
  baseDelayMs = 200,
  maxDelayMs = 5000,
  shouldRetry = () => false,
  getRetryAfter = () => null,
  signal,
} = {}) {
  if (typeof request !== 'function' || typeof shouldRetry !== 'function' || typeof getRetryAfter !== 'function') {
    throw new TypeError('请求和重试策略必须是函数');
  }
  if (!Number.isSafeInteger(maxAttempts) || maxAttempts < 1) {
    throw new RangeError('尝试次数必须为正整数');
  }
  for (const delay of [baseDelayMs, maxDelayMs]) {
    if (!Number.isInteger(delay) || delay < 0 || delay > 2_147_483_647) {
      throw new RangeError('等待参数必须是计时器范围内的非负整数');
    }
  }

  let delayCap = Math.min(baseDelayMs, maxDelayMs);

  for (let attempt = 1; attempt <= maxAttempts; attempt += 1) {
    signal?.throwIfAborted();
    try {
      const result = await request({ attempt, signal });
      signal?.throwIfAborted();
      return result;
    } catch (error) {
      signal?.throwIfAborted();
      if (attempt === maxAttempts) throw error;

      const retryable = shouldRetry(error, attempt);
      if (typeof retryable !== 'boolean') {
        throw new TypeError('shouldRetry 必须同步返回布尔值');
      }
      if (!retryable) throw error;

      const retryAfterMs = getRetryAfter(error, attempt);
      if (retryAfterMs !== null && (typeof retryAfterMs !== 'number' || Number.isNaN(retryAfterMs) || retryAfterMs < 0)) {
        throw new TypeError('服务端等待时间必须为非负毫秒或 null');
      }
      if (retryAfterMs !== null && retryAfterMs > maxDelayMs) throw error;

      const jitter = Math.floor(Math.random() * (delayCap + 1));
      await waitForRetry(Math.max(jitter, Math.ceil(retryAfterMs ?? 0)), signal);
      delayCap = Math.min(maxDelayMs, delayCap * 2);
    }
  }
}

代码有点长，我们按读者会问的问题一个个看。

为什么等待时间要随机？ 设想服务挂了一分钟，几千个客户端同时失败。如果大家都等固定的 200 毫秒再试，服务刚恢复，就会在同一瞬间被几千个请求再打趴下。所以这里的 delayCap 依次是 200、400、800 毫秒……一直涨到 maxDelayMs 封顶，这叫指数退避；每次实际等待的时间在 [0, delayCap] 里随机取，这叫抖动。大家的重试时间就被分散开了。

Retry-After 和随机等待怎么配合？ 取两者中较大的那个，服务端要求的时间是下限。如果服务端要求等的时间比 maxDelayMs 还长，函数直接抛出错误，不自作主张地缩短等待。

取消是怎么做到的？ waitForRetry 在等待期间监听取消信号。一旦取消，就清掉定时器、移除监听器，用 signal.reason 拒绝。另外，有的请求函数本身不理会取消信号，所以请求结束后还会再检查一次，防止用户已经离开了，却把过期的结果当成成功返回。

次数用完了抛什么？ 抛最后一次的真实错误。这样调用方还能看到状态码，而不是一个笼统的“重试失败”。

解析 Retry-After

Retry-After 有两种写法，可以是秒数，比如 120，也可以是一个 HTTP 日期。下面的函数把它统一换成毫秒：

JavaScript
function retryAfterMilliseconds(value, now = Date.now()) {
  if (value === null) return null;
  const text = value.trim();
  // 空头视为服务端没有提出等待要求，交给常规退避
  if (text === '') return null;
  if (/^\d+$/.test(text)) return Number(text) * 1000;

  const timestamp = Date.parse(text);
  if (!Number.isFinite(timestamp) || new Date(timestamp).toUTCString() !== text) {
    return Infinity;
  }
  return Math.max(0, timestamp - now);
}

没有这个头，或者它是空字符串，都说明服务端没提要求，返回 null，交给常规的退避。

那为什么看不懂的值要返回 Infinity，而不是也返回 null？因为服务端明明给了一个等待要求，只是我们解析不了。如果当作没有要求，就可能在服务端让我们等的时候提前发请求。返回 Infinity 以后，它一定超过 maxDelayMs，上面的函数就会停止重试，这样更保守。

用在一个只读接口上

下面把前面两个函数组合起来，加载一个商品目录：

JavaScript
class HttpResponseError extends Error {
  constructor(status, retryAfter) {
    super(`HTTP ${status}`);
    this.name = 'HttpResponseError';
    this.status = status;
    this.retryAfter = retryAfter;
  }
}

async function loadCatalog(signal) {
  const timeout = AbortSignal.timeout(10_000);
  const combined = signal ? AbortSignal.any([signal, timeout]) : timeout;

  return requestWithRetry(async ({ signal }) => {
    const response = await fetch('/api/catalog', { signal });
    if (!response.ok) {
      const error = new HttpResponseError(response.status, response.headers.get('Retry-After'));
      await response.body?.cancel();
      throw error;
    }
    return response.json();
  }, {
    signal: combined,
    maxAttempts: 3,
    shouldRetry: (error) => error instanceof HttpResponseError && [429, 502, 503, 504].includes(error.status),
    getRetryAfter: (error) => retryAfterMilliseconds(error.retryAfter),
  });
}

每次重试都会重新调用一次 fetch。如果请求带了请求体，要保证每次都能重新生成，因为一个流读过一次就不能再发了。

失败的响应调用了 body.cancel()，这是为了把连接释放掉，不然没读完的响应体会一直占着连接。

AbortSignal.timeout 限制的是整个加载过程的总时长，包括所有重试和等待。AbortSignal.any 把它和调用方传进来的取消信号合成一个，哪个先触发都会取消。

写操作为什么不能随便重试

客户端等超时了，可是订单可能已经在服务端创建好了，只是响应在路上丢了。这时直接重试，用户就会下两单。

安全的做法是用幂等键，也就是“同一个键只处理一次”的标记。用户点提交时生成一个键，比如 crypto.randomUUID()；每次重试都在请求头里带上同一个键；服务端记下处理过的键，重复的请求直接返回第一次的结果。

如果服务端不支持幂等键，就不要自动重试写操作。超时以后先去查订单状态，再决定要不要重新提交。

常见追问

前端、网关、SDK 都做了重试会怎样？

次数会相乘。每层重试 3 次，一个用户操作最多会变成 27 次请求。所以要约定好，只让一层负责重试。

浏览器离线时还要重试吗？

不用按退避循环白白消耗次数。可以监听 online 事件，等恢复联网以后再发起请求。

重试和防抖、节流有什么关系？

防抖和节流控制的是用户触发得有多频繁，重试处理的是请求失败以后怎么恢复。它们管的是两件事，经常一起用在搜索框上。
