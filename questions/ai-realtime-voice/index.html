AI 实时语音界面需要关注哪些前端状态？

实时语音同时牵涉麦克风、网络连接、语音转文字、模型生成和声音播放，这些状态要分开记。用户打断时既要清空本地待播的音频，也要通知服务端停止生成；关闭时把整条链路都释放掉。

参考答案

简答

一次语音对话要经过很多步：麦克风采集、网络传输、服务端判断你说完没有并转成文字、模型生成回答、合成语音、浏览器播放。所以连接建立了，不代表模型已经收到了你的声音。

状态至少要分五类分开记：麦克风（权限、是否在采集）、连接、当前是第几轮、生成、播放，再用轮次 ID 把它们关联起来。

传输方式上，WebRTC 自带媒体传输和弱网适应；如果用 WebSocket 传音频，编码、缓冲、播放时间都得自己处理。

最容易做错的是打断。用户插话时，要停止播放、清空待播的音频，同时通知服务端取消生成。只是把扬声器静音的话，模型其实还在后台算。另外，浏览器直连语音服务时，要用服务端签发的短期令牌，不能把长期密钥放进前端。

状态要怎么分

TypeScript
type VoiceSession = {
  mic: 'idle' | 'requesting' | 'denied' | 'capturing';
  connection: 'connecting' | 'open' | 'reconnecting' | 'closed';
  turnId: string | null;
  generation: 'idle' | 'thinking' | 'speaking' | 'cancelled';
  playback: { queued: number; playing: boolean };
};

为什么拆这么细？因为它们会各自变化。比如连接正在重连，麦克风还在采集；模型已经生成完了，播放队列里还有好几段没播。合成一个状态就表达不了。

麦克风指示灯要反映 track 的真实状态，不能只看用户有没有点过按钮。track 是浏览器给你的那一路音频流。权限被拒、设备被别的程序占用、耳机被拔出，都要有文字提示，并且提供文字输入作为替代。

还有一个容易漏的情况：getUserMedia() 是异步的，等它返回时，组件可能已经关掉了。这时要马上把返回的 track 停掉，不然用户已经离开页面，麦克风还在偷偷采集。

转写和轮次怎么处理

语音转文字通常会先给一个临时结果，过一会儿再给修正后的最终结果。所以收到同一轮的新结果时，要按片段 ID 替换掉临时内容，而不是接在后面，不然屏幕上的文字会重复。

判断用户说完没有，一般靠语音活动检测，就是根据声音有没有停下来自动判断。它会被噪声和说话时的停顿干扰，所以可以再提供“按住说话”或者手动结束作为补充。

断线重连以后，可能还会收到上一轮的片段，按轮次 ID 丢掉就行。

用户打断时要做哪些事

第一步，停止当前播放，清空本地缓冲的音频队列。第二步，通知服务端取消当前生成。第三步，如果协议支持，告诉服务端用户实际听到了哪里，这样下一轮的上下文才准确，模型不会以为用户听完了整段回答。

还要知道，打断撤销不了已经执行的工具操作。

播放为什么不能用 setTimeout 衔接

音频是一段一段到达的，要无缝接起来播。setTimeout 的时间不精确，段与段之间会有空隙或重叠。要用 AudioContext 的时间线，按精确的时间点安排每一段的开始。

缓冲区大小要权衡：太小，网络一抖就断断续续；太大，用户打断后要等好一会儿声音才停。

外放时，扬声器的声音可能又被麦克风录进去，模型听到自己的话。所以要开启回声消除，并且在外放、耳机、弱网几种环境下实际测一遍。

关闭会话要释放什么

停止自己创建的 MediaStreamTrack，关闭 RTCPeerConnection 或 WebSocket，停止音频源，清理监听器和定时器。AudioContext 如果还被其他功能共用，就不要直接关掉它。

常见追问

要监控哪些指标？

用户说完到听到第一段回复的延迟、打断后到声音停下来的延迟、播放断续的比例。

音频数据要保存吗？

音频是敏感数据。采集、传输、保存、删除都要有明确的用途，并且告诉用户。
