AI 实时语音界面需要关注哪些前端状态？

从麦克风权限、音频采集、连接状态、打断和播放队列设计实时语音 AI 交互，区分浏览器能力与服务端模型能力。

参考答案

实时语音同时涉及麦克风采集、网络会话、模型处理与扬声器播放。用户可能正在说话时模型还在播放上一段，也可能连接正常但麦克风权限被撤销，所以一个“录音中/加载中”状态无法描述整个系统。

应把输入、连接、生成和播放作为相互关联但独立的生命周期，再用轮次和消息 ID 协调。

先让用户知道声音现在流向哪里

界面需要区分申请权限、设备就绪、正在采集、正在发送、等待回应和正在播放。麦克风图标亮起应反映真实采集状态，而不是只反映用户上次点过按钮。

getUserMedia 返回轨道不代表网络已经建立；连接 ready 也不代表音频播放策略已经允许。用户拒绝或忽略授权、设备被占用、耳机拔出，都应有明确反馈和文字替代入口。

若组件关闭后权限才获得，迟到的 stream 也要及时停止，不能让已经离开的界面继续采集。

WebRTC 和 WebSocket 承担的工作不同

WebRTC 提供实时媒体传输相关能力，包括协商与适应网络条件的机制；WebSocket 更偏通用消息通道，音频编码、分帧、缓冲与播放时钟等可能需要应用和服务协议承担更多工作。

选择应基于目标服务支持与实际链路，而不是只比较 API 调用行数。某个语音服务提供浏览器直连时，还应使用其受限短期凭据方案，不把长期服务商密钥放进前端。

不论哪种传输，服务端的转写、模型与合成仍有独立延迟和错误，网络连接成功不是完整语音链路成功。

语音轮次不是简单的连续字符串

转写通常先给临时结果，随后修正为最终文本；模型输出可能分段合成并播放。应以 turn ID、message ID 和片段序号关联，允许临时转写替换而不是每次都追加。

声音活动检测可以帮助判断开始说话和结束说话，但噪声、停顿与不同语言节奏会影响结果。可提供按键说话或手动结束作为补充，不要把一次短暂停顿永远当作用户已经说完。

网络重连后可能收到重复或过期片段，应按身份去重并拒绝旧轮次继续覆盖新状态。

打断需要同时考虑播放与生成

用户开始说话时，通常希望立即停止听到旧回答。前端需要停止当前播放并清空尚未播放的队列；服务端还需要收到适当的取消或截断通知，避免继续生成无人需要的音频。

只静音扬声器不会停止模型计算，只取消上游也不会自动清空本地已缓冲音频。协议若支持记录已播放位置，应让对话上下文与用户实际听到的部分一致，避免下一轮假设用户已经听完整段解释。

已执行的工具副作用不随打断撤销。语音中说“停”可以停止后续步骤，但发送、付款等动作仍需按业务状态确认。

播放队列要控制延迟与内存

音频片段到达后需要解码、调度和输出。过小的缓冲容易断续，过大的缓冲增加打断延迟；应按协议和播放模型处理时间戳、队列长度与过期片段。

AudioContext 的时间线与页面 setTimeout 不同，不能用普通计时器保证连续音频精确衔接。播放可能受自动播放策略、后台限制或输出设备变化影响，必须处理恢复失败。

回声消除与噪声抑制等约束可以改善体验，但不是所有设备都同样有效。外放声音被麦克风再次拾取时，可能误触发新轮次，需要真实设备测试而非只检查波形是否变化。

结束会话应释放整条链路

停止自己拥有的麦克风轨道，关闭连接或相关通道，停止音源和队列，释放解码资源与监听器，并恢复界面。应用共享 AudioContext 时应按所有权清理，不必每次都关闭其他功能仍使用的上下文。

记录并区分首段可听音频延迟、完整回答时间、打断响应和断续情况。音频数据本身属于敏感内容，采集、传输、保存与删除都应有明确用途与范围。

验收覆盖拒绝权限、用户沉默、连续打断、弱网、耳机切换、页面后台与恢复。模拟输入能验证状态机，但不能证明真实听感、麦克风链路或系统权限体验已经达标。
