AI 实时语音界面需要关注哪些前端状态？

实时语音同时包含麦克风、网络会话、转写、模型生成和音频播放，输入、生成和播放必须分别建模，打断与恢复也要有明确协议。

参考答案

一个“说话”动作跨越多条链路

用户点击开始后，浏览器要申请麦克风、创建音频轨道、建立网络会话，服务端再进行语音活动检测、转写、模型推理和语音合成，最后由浏览器解码并播放。连接已经建立，不代表模型已经收到音频；麦克风已经授权，也不代表扬声器允许播放。

因此不要只维护一个 isRecording。至少要分别表示输入状态、连接状态、当前轮次、生成状态和播放状态，并用 turn ID、message ID 和片段序号把它们关联起来。

权限和设备状态必须可解释

界面应区分请求权限、设备就绪、正在采集、正在发送、等待回应和正在播放。麦克风亮起必须反映真实轨道状态，而不是用户曾经点击过按钮。用户拒绝权限、设备被占用、耳机拔出和系统撤销权限都要有文字提示和输入替代方式。

getUserMedia() 返回 stream 后，组件可能已经被关闭。如果迟到的 Promise 仍返回轨道，应立即停止并释放它，不能让离开的页面继续采集。权限本身也会受浏览器、HTTPS、iframe 权限策略和系统设置影响。

选择 WebRTC 或 WebSocket 要看协议支持

WebRTC 适合实时媒体传输和网络适应，WebSocket 更适合通用消息。用 WebSocket 传音频时，应用或服务协议要自己处理编码、分帧、缓冲、播放时钟和背压；使用 WebRTC 也仍需信令、鉴权和服务端模型协议。

浏览器直连语音服务时，应使用服务端签发的短期、受限凭据，不能把长期服务商密钥打包进前端。连接成功只说明传输层建立，转写、推理和合成仍可能分别失败或超时。

转写和生成要按轮次更新

语音转写常先返回临时片段，再返回修正后的最终文本。前端应根据片段 ID 替换同一轮的临时内容，而不是每次事件都追加，避免文字重复。模型音频也可能分片到达，必须按顺序、时间戳和完成状态排队。

语音活动检测容易受噪声、停顿和语言节奏影响。自动判断结束后，可以提供按键说话或手动结束作为补充；短暂停顿不能永远被当成用户说完。重连后收到重复或旧轮次片段时，应按 turn ID 去重并拒绝覆盖新轮次。

打断要同时停止播放和生成

用户开始说话时，通常希望立即听不到上一段回答。前端要停止当前音频、清空尚未播放队列；服务端还要收到取消或截断通知，停止继续生成。只把扬声器静音不会停止模型计算，只取消服务端也不会清空浏览器已经缓冲的音频。

如果协议支持记录已播放位置，应把用户实际听到的片段告诉服务端，否则下一轮上下文可能假设用户已经听完。打断不能撤销已经执行的工具副作用；付款、发信等动作仍要按独立业务状态确认和补偿。

播放队列要在连续性和延迟之间取舍

音频片段需要解码、排队和按时间线输出。缓冲过小会断续，过大则增加打断延迟和内存。AudioContext 的时间线与 setTimeout 不同，不能用普通计时器保证精确衔接；还要处理自动播放策略、后台限制和输出设备变化。

回声消除、噪声抑制和自动增益可以改善输入，但不同设备效果不同。外放声音被麦克风再次采集，可能触发错误轮次，必须在真实耳机、外放、弱网和后台场景测试。

关闭要释放整条链路

结束会话时，停止自己拥有的 MediaStreamTrack，关闭传输和信令，停止音频源与队列，释放解码资源、监听器和计时器。共享 AudioContext 时按所有权清理，不能关闭仍被其他功能使用的上下文。

监控至少区分首段可听音频延迟、首段转写、完整回答、打断响应和断续率。音频属于敏感数据，采集、传输、保存和删除都要有明确用途。验收覆盖权限拒绝、沉默、连续打断、弱网、耳机切换、后台恢复和设备切换，模拟音频只能验证部分状态机。
