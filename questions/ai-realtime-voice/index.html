AI 实时语音界面需要关注哪些前端状态？

实时语音同时涉及麦克风、网络会话、转写、生成和播放。这些状态要分开建模；用户打断时要同时清空本地播放队列并通知服务端停止生成；关闭时释放整条链路。

参考答案

简答

  • 一次对话经过麦克风采集、网络传输、服务端语音检测与转写、模型生成、语音合成、浏览器播放。连接建立了，不代表模型收到了音频。
  • 至少分开维护输入（权限、采集中）、连接、当前轮次、生成、播放五类状态，并用轮次 ID 关联。
  • WebRTC 自带媒体传输和网络自适应；用 WebSocket 传音频，编码、缓冲、播放时钟都要自己处理。
  • 打断时要停止播放、清空待播队列，并通知服务端取消生成。只静音扬声器，模型仍在计算。
  • 浏览器直连语音服务时，用服务端签发的短期令牌，不要把长期密钥放进前端。

状态模型

TypeScript
type VoiceSession = {
  mic: 'idle' | 'requesting' | 'denied' | 'capturing';
  connection: 'connecting' | 'open' | 'reconnecting' | 'closed';
  turnId: string | null;
  generation: 'idle' | 'thinking' | 'speaking' | 'cancelled';
  playback: { queued: number; playing: boolean };
};

麦克风指示灯反映 track 的真实状态，而不是按钮点击过与否。权限被拒、设备被占用、耳机拔出都要有文字提示，并提供文字输入替代。

getUserMedia() 返回时组件可能已经关闭。这时要立即停止返回的 track，不要让离开的页面继续采集。

转写与轮次

  • 转写通常先给出临时文本，再给出修正后的最终文本。按片段 ID 替换同一轮的临时内容，不要追加，否则文字会重复。
  • 自动判断用户说完（语音活动检测）会受噪声和停顿影响，可以提供"按住说话"或手动结束作为补充。
  • 重连后收到旧轮次的片段，按轮次 ID 丢弃。

打断

  1. 停止当前播放，清空本地缓冲的音频队列。
  2. 通知服务端取消当前生成。
  3. 如果协议支持，告诉服务端用户实际听到了哪里，让下一轮上下文准确。

打断不会撤销已经执行的工具操作。

播放

用 AudioContext 的时间线按顺序衔接音频片段，setTimeout 无法精确衔接。缓冲太小会断续，太大会让打断反应变慢。外放时声音可能被麦克风采集回来，开启回声消除并在外放、耳机、弱网环境下实测。

关闭会话

停止自己创建的 MediaStreamTrack，关闭 RTCPeerConnection 或 WebSocket，停止音频源，清理监听器和计时器。AudioContext 如果和其他功能共用，就不要直接关闭。

常见追问

  • 要监控哪些指标？ 用户说完到听到第一段回复的延迟、打断后停止播放的延迟、播放断续率。
  • 音频数据要保存吗？ 音频属于敏感数据，采集、传输、保存和删除都要有明确用途并告知用户。
