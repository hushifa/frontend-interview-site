触发操作为什么应优先使用 button，而不是可点击的 div？

原生 button 提供按钮语义、焦点和键盘激活等基础行为，减少自行模拟交互时的遗漏。导航应使用带 href 的链接，按钮则仍需明确类型、名称、状态和焦点样式。

参考答案

简答

  • 给 div 加 click 只完成了点击处理，焦点、键盘激活和读屏语义都要另外补。
  • 执行操作用 button，跳转到可定位地址用带 href 的 a。
  • 原生按钮会把 Enter 和空格转成激活行为，不要再在 keydown 里重复调用同一逻辑。
  • 按状态类型选择属性：开关用 aria-pressed，展开用 aria-expanded，复选框用自身的 checked。

给 div 加上 click 监听，只完成了“收到点击事件时运行代码”。用户用 Tab 能不能到达它，用 Enter 或空格能不能激活它，屏幕阅读器会不会把它当成按钮，仍然是没解决的问题。

原生 button 已经提供了这些基础语义和交互规则。使用它不是只为了通过检查工具，而是让鼠标、触摸、键盘和辅助技术都能通过各自习惯的方式完成同一个操作。

先区分操作和导航

提交表单、打开对话框、切换收藏状态，通常用 button。跳转到另一张页面或某个可定位地址，通常用带 href 的 a。即使视觉上都设计成长方形，也应该根据行为选择元素。

HTML
<a href="/questions/js-this/">阅读 this 题解</a>
<button type="button" id="open-settings">打开阅读设置</button>

链接有复制地址、在新标签页打开、浏览器状态栏预览等行为。用 button 加 location.href 模拟导航，会丢掉或需要重做其中一部分；用 href="#" 的链接触发纯操作，则可能额外改变 URL 或滚动位置。

一个开关按钮不需要手写 Enter 与空格

HTML
<button id="favorite" type="button" aria-pressed="false">
  收藏
</button>
JavaScript
const favorite = document.querySelector('#favorite');

favorite.addEventListener('click', () => {
  const pressed = favorite.getAttribute('aria-pressed') === 'true';
  favorite.setAttribute('aria-pressed', String(!pressed));
});

原生按钮会把相应的键盘激活转成按钮激活行为，click 监听器可以处理这些入口，不仅仅处理鼠标。这里用 aria-pressed 表示一个可切换的按下状态，标签“收藏”保持稳定，辅助技术可以结合状态解释它。

不要再不加区分地同时监听 keydown，在 Enter 或空格时又调用一次相同逻辑，否则可能与原生激活重复，出现一次按键切换两次、最后看起来没有变化的问题。不同按键的激活时机也不应该用一个随意的键盘事件处理器模拟。

aria-pressed 不适合所有状态。展开说明通常用 aria-expanded，复选框使用它自身的 checked 状态，异步保存是否完成则需要相应的状态反馈。ARIA 表达的是具体语义，而不是万能的布尔开关。

type 和可访问名称是两项基本配置

在表单中，普通 button 没有明确写 type 时通常会作为提交按钮。非提交操作应写 type="button"，提交表单则写 type="submit"。否则点“打开说明”也可能触发提交和校验，甚至跳转页面。

文字按钮通常可以从文字内容获得可访问名称。只有图标时，应补充名称，例如：

HTML
<button type="button" aria-label="关闭设置">
  <svg aria-hidden="true" focusable="false" viewBox="0 0 24 24"
       width="20" height="20">
    <path d="M6 6 18 18M18 6 6 18" fill="none"
          stroke="currentColor" stroke-width="2" />
  </svg>
</button>

这里 SVG 是装饰，操作名称来自按钮的 aria-label。也可以使用视觉隐藏的文本。不要只依赖鼠标悬停才出现的 title；触屏和不同辅助技术下，它不一定提供同样的可发现体验。

按钮已经有可见文字时，通常不需要再写一个不同含义的 aria-label。覆盖后可能让用户看到“保存”，语音操作和辅助技术却面对另一个名称。名称应尽量与用户看到的操作一致。

disabled 与 aria-disabled 不能互换

disabled 会让原生按钮不可激活，并通常将它移出正常焦点导航；相关表单数据也按禁用控件规则处理。它适合真正不可用的操作，但需要确保用户能理解为什么不可用。

aria-disabled="true" 只向辅助技术表达禁用状态，不会自动阻止点击、键盘激活或代码执行。如果为了让用户仍能聚焦并了解不可用原因而选用它，应用就必须同时阻止实际操作并提供视觉提示，不能只改属性。

异步操作中，也不要只靠禁用按钮解决所有重复请求问题。点击入口、快捷键入口和请求状态都可能参与，业务仍应设计相应的防重复与幂等处理。

自定义外观不必放弃原生行为

CSS
button:focus-visible {
  outline: 3px solid #2563eb;
  outline-offset: 3px;
}

button[aria-pressed="true"] {
  background: #1d4ed8;
  color: white;
}

可以使用 CSS 改颜色、边框、布局和图标，不必为了摆脱默认样式改成 div。保留可见焦点，给触摸操作足够面积，并保证状态不是只有细微颜色差别。

不应在 button 内再嵌套链接、另一个 button 等交互元素。如果整个卡片可导航，同时又有收藏按钮，应把导航和收藏设计成相互独立的可操作元素，避免嵌套交互造成激活目标混乱。

如果确实无法使用原生元素，role="button" 也只补充角色，并不会附赠键盘激活、Tab 顺序或 disabled 行为。还需要处理 tabindex、键盘默认行为、名称、状态和焦点等细节。既然大多数普通操作都能用 button，优先采用原生控件通常更可靠，也更容易维护。
