什么是闭包？它有哪些实际应用？

闭包让函数按创建位置的词法作用域继续访问外层绑定。它可以保存独立状态、提供受控接口和连接回调上下文，但不会默认复制变量快照，也不必然造成内存泄漏。

参考答案

一个函数执行结束后，里面创建的另一个函数仍然可以访问它的局部变量，这就是理解闭包最常见的入口。

更完整地说，闭包是函数与其创建时的词法环境的组合。函数以后在哪里被调用，不会把它原本的变量查找位置改成调用者的局部作用域。它仍然沿定义位置对应的作用域关系寻找名字。

函数已经返回，count 为什么还能用

JavaScript
function createCounter() {
  let count = 0;

  return {
    increment() {
      count += 1;
      return count;
    },
    read() {
      return count;
    },
  };
}

const first = createCounter();
const second = createCounter();

console.log(first.increment()); // 1
console.log(first.increment()); // 2
console.log(first.read());      // 2
console.log(second.increment()); // 1

createCounter 第一次执行时创建一个 count 绑定，以及两个能访问它的方法。外层函数返回的是这些函数所组成的对象。只要这些函数仍然可达，它们需要访问的外层状态就必须继续可用，不会仅因 createCounter 的调用栈帧结束而丢失。

first.increment 和 first.read 访问的是同一个 count，所以一个修改后，另一个能读到新值。第二次调用 createCounter 则创建另一份局部环境，second 不会与 first 共用计数。

这里的 count 没有暴露为 first.count 属性，外部只能通过返回的接口操作它。这是一种封装状态的方法；也可以使用类的私有字段等其他机制，选择取决于代码组织需要。

闭包通常保存访问关系，不是拍一张变量快照

JavaScript
let message = '早上的内容';
const readLive = () => message;

const savedMessage = message;
const readSaved = () => savedMessage;

message = '晚上的内容';
console.log(readLive());  // 晚上的内容
console.log(readSaved()); // 早上的内容

readLive 读取的是 message 这个绑定的当前值，后来赋值会影响结果。readSaved 读取的是另一个绑定 savedMessage，这个绑定保存了当时的字符串值，所以结果不同。

这不是一种闭包“实时”、另一种闭包“不实时”，而是它们引用了不同的绑定。若 savedMessage 保存的是对象引用，那么它也不代表自动获得对象的深拷贝，对象内部属性仍可能被其他代码修改。

函数调用时产生的参数也属于相应调用的局部环境。把一个值作为参数交给函数，再让返回的回调使用该参数，可以有意识地保存那次调用的上下文，但需要清楚值本身是否还引用可变对象。

“陈旧闭包”往往是旧环境仍被使用

JavaScript
function createReader(count) {
  return () => count;
}

const oldReader = createReader(1);
const newReader = createReader(2);

console.log(oldReader()); // 1
console.log(newReader()); // 2

两次调用有各自的 count。创建 newReader 并没有修改 oldReader 所在的旧环境，所以旧函数仍返回 1。它没有忘记更新，也不是 JavaScript 随机缓存了一个错误结果。

这有助于理解 React 等代码中的陈旧回调：不同渲染可能创建不同的局部环境，长期保留的回调可能仍引用某次旧渲染中的值。修复方式要根据所需语义选择重新建立订阅、正确维护依赖、使用合适的更新形式或读取受控的最新引用，不能笼统认为“所有闭包都应改成全局变量”。

为什么回调、工厂函数都经常用到闭包

事件处理器需要记住某个组件的局部状态，防抖函数需要记住上次定时器，函数工厂需要记住配置，这些都可以通过闭包完成。下面把点击次数绑定到两个实际 DOM 元素，并返回清理函数：

JavaScript
function bindCounter(button, output) {
  let count = 0;

  function onClick() {
    count += 1;
    output.textContent = String(count);
  }

  button.addEventListener('click', onClick);

  return function dispose() {
    button.removeEventListener('click', onClick);
  };
}

每次调用 bindCounter 都有自己的一份 count。onClick 记住 output 与 count，dispose 记住 button 与同一个 onClick 引用。正因为保留了正确的函数引用，清理时才能移除原监听器，而不是临时创建一个长得一样但身份不同的函数。

闭包不要求函数一定被返回，也不要求存在异步任务。只要函数按词法作用域使用外层绑定，就涉及这种机制；“返回一个内部函数”只是最容易观察外层调用结束后状态仍被保存的例子。

循环里读到相同结果，问题在共享绑定

用 var 声明的循环变量，多个回调可能共同引用同一个绑定，循环结束后再读取时都看到最后的值。for 循环头的 let 则可以为各次迭代提供独立绑定，所以回调能分别记住各自的迭代值。

这不意味着闭包在循环中失效。恰恰是它忠实地沿着所捕获的绑定去读取，才表现出了共享与独立的区别。即使把回调放进数组，循环后同步调用，也能复现，不一定要用 setTimeout。

闭包与内存泄漏有什么关系

如果一个长期存活的监听器、定时器或订阅引用了某个回调，而回调又访问大型对象或 DOM 节点，这些对象就可能继续可达。组件已经不再需要它们，但引用关系没有清除，才会造成不必要的长期保留。

因此应在生命周期结束时移除监听、取消计时器、解除订阅，并检查缓存和清理函数是否仍被其他地方保存。闭包并不是“函数返回后内存永远无法释放”的机制；相关函数和状态都不再可达时，垃圾回收器仍然可以回收它们。

也不必假定每个闭包都会完整保存外层的所有变量或整份调用栈。具体保留与优化由引擎实现决定，应用能把握的是对象是否仍然可达，以及哪些长期对象持有了这些引用。发现内存持续增长时，应结合堆快照和引用路径找原因，而不是把所有内部函数都删掉。
