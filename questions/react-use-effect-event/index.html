React useEffectEvent 适合解决什么依赖问题？

Effect Event 把 Effect 内不需要重新建立外部关系的事件逻辑分离出来，在调用时读取最新渲染值。它不能隐藏真正的同步依赖，也不是可随意传给按钮、子组件或其他 Hook 的 useCallback 替代品。

参考答案

一个 Effect 订阅窗口变化，订阅是否存在由 enabled 决定；回调发生时，又需要使用最新的 label 写一条记录。label 改变并不意味着应该重建窗口监听，但长期保存普通旧回调又可能读到旧 label。

useEffectEvent 用来表达这种区别：外部同步关系有自己的依赖，事件发生时需要读取的最新值不一定都应该成为重建关系的原因。

保留监听，同时在事件发生时读取最新标签

JSX
import { useEffect, useEffectEvent, useState } from 'react';

export default function ResizeRecord({ label, enabled = true }) {
  const [lastRecord, setLastRecord] = useState('尚无记录');

  const onResize = useEffectEvent(() => {
    setLastRecord(`${label}:${window.innerWidth}`);
  });

  useEffect(() => {
    if (!enabled) return;
    function handleResize() {
      onResize();
    }
    window.addEventListener('resize', handleResize);
    return () => window.removeEventListener('resize', handleResize);
  }, [enabled]);

  return (
    <section>
      <p>当前标签：{label}</p>
      <output aria-label="最后一次尺寸记录">{lastRecord}</output>
    </section>
  );
}

enabled 为 true 时建立监听，为 false 时清理。label 变化后，界面可以显示新标签，但不会仅因 label 改变重新注册这份监听；下一次 resize 到来，Effect Event 使用最新标签记录尺寸。

lastRecord 保存的是上一次事件发生时生成的记录，因此改变 label 不会立刻改写历史记录。这正是“事件时读取”与“依赖变化后重新同步”的区别，而不是漏掉了一次更新。

为什么普通闭包和 useCallback 不能直接替代

如果把读取 label 的普通回调永久留在空依赖 Effect 中，它会保留创建时的渲染环境，可能一直记录旧标签。把 label 加进依赖可以让它更新，但代价是重新建立订阅，这是否合理取决于外部系统。

useCallback 只缓存函数身份，仍然按依赖保存相应闭包。空依赖不会让函数自动读取最新状态，有 label 依赖则会在 label 改变时生成新的函数身份，也不等于这题所表达的分离方式。

Effect Event 则专门服务 Effect 内的事件逻辑。它不是通用缓存函数，也不应把返回函数的身份当作长期稳定的性能契约。

哪些值仍然必须放在 Effect 依赖中

如果 roomId 改变意味着要离开旧聊天室、连接新聊天室，roomId 就是外部连接的真实同步条件。把它藏到 Effect Event 中，然后继续保留旧连接，会得到逻辑错误，即使通知文字能读到最新 roomId 也没有用。

类似地，订阅对象、启用状态、请求地址或真正影响外部配置的值，都应根据实际关系决定是否重新同步。Effect Event 不能用来绕过依赖 lint 规则，也不会证明原先的依赖是不必要的。

一个 Effect 混合了多种不同生命周期时，优先考虑拆分 Effect，把各自需要的依赖与清理讲清楚，再决定是否存在适合提取的事件逻辑。

调用范围是这个 API 的重要限制

Effect Event 应从 Effect 逻辑调用，包括由相应 Effect 建立的监听器或计时器回调。不能在渲染期间执行，也不应把它直接用作普通 UI 的 onClick 处理器，或传给其他组件、其他 Hook 当成通用回调。

在自定义 Hook 中使用时，也应让它留在管理该 Effect 的局部逻辑内。给用户交互的回调需要普通事件处理器或其他恰当设计，而不是因为“能读最新值”就统一替换成 Effect Event。

官方 Hooks lint 规则可以帮助检查这些使用边界。项目还需要实际安装支持 useEffectEvent 的 React 版本与匹配工具，不是加一个同名函数或把旧代码断言过去就具有相同语义。

为什么依赖数组中不写 onResize

Effect Event 按设计属于非响应式的事件逻辑，不应该列入外层 Effect 的依赖数组。这里应让 React 和配套规则按该 API 的语义处理，而不是因为一般函数经常要写进依赖，就机械添加它。

这条特殊规则不适用于所有名字叫 onResize 的普通函数。普通组件内函数的依赖关系仍需要正常分析，不能靠变量名或人为注释获得同样行为。

最新值也不替代任务身份和清理

回调调用时使用最新渲染值，不代表所有已经发出的异步操作都变成最新任务。旧请求晚到、多个事件并发或用户已经离开页面，仍然需要取消、请求标识或生命周期检查。

异步函数一旦开始执行，也有自己的局部值和等待过程；不要把“调用时读取最新值”理解成它在任意 await 之后自动重新定义所有已经计算过的变量。

示例仍然返回 removeEventListener 清理函数。Effect Event 不会帮你自动移除监听或停止计时器，也不改变后台事件的调度规律。

先确定是不是 Effect 的问题

用户点击保存时提交当前表单，通常直接在事件处理器中使用对应状态即可。仅根据 props 计算显示内容，则在渲染中计算。只有确实在维护外部同步关系、又需要把部分事件读取从重建条件中分离时，Effect Event 才体现出价值。

判断标准可以很具体：这个值变化时，外部连接是否应该重建？还是只要求下一次外部事件发生时采用新值？先回答这个问题，比把 useEffectEvent 当成“消除依赖数组的工具”更可靠。
