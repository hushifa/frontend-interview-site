浮点精度、安全整数和 BigInt 有哪些边界？

Number 的二进制浮点表示会带来小数舍入和大整数区分能力的限制，BigInt 则适合精确整数但不支持任意小数。计算、输入解析、比较和序列化都需要维持一致的精度约定。

参考答案

简答

  • Number 是 IEEE 754 双精度浮点数，0.1 + 0.2 不等于 0.3。
  • 超过 Number.MAX_SAFE_INTEGER（2^53 - 1）的整数无法精确表示，应使用 BigInt 或字符串。
  • BigInt 不能与 Number 直接混合运算，也不能被 JSON.stringify 直接序列化。
  • 金额应按最小货币单位用整数计算，展示时再格式化。

JavaScript 的 Number 采用 IEEE 754 双精度二进制浮点表示。它能覆盖很大的数值范围，但可用于表示有效数字的位数有限；许多十进制小数在二进制中无法有限展开，只能保存一个邻近值。

因此问题不只是“计算很大的数会出错”，普通的小数计算也可能在精确比较时出现差异：

JavaScript
console.log(0.1 + 0.2 === 0.3); // false
console.log(9007199254740991n + 2n); // 9007199254740993n
console.log(5n / 2n); // 2n

第一行是浮点舍入导致的可观察结果；后两行使用 BigInt 精确处理整数，但除法结果截断为整数，并不会自动得到 2.5。这是两种数值模型的取舍，不是给 Number 加一个 n 就能解决全部数学问题。

0.1 + 0.2 为什么不能直接精确等于 0.3

0.1、0.2 与 0.3 都需要按二进制浮点规则表示。操作数各自的近似，再经过加法与舍入，得到的数值与字面量 0.3 所对应的近似值并不相同。

这种差异不意味着所有小数都无法精确表示，例如 0.5、0.25 这类以二的幂为分母的数可以精确表示。也不意味着每一次计算都会产生可见的误差，具体取决于数值与运算过程。

toFixed(2) 可以把结果格式化成两位小数的字符串，适合展示，但不能把底层数值模型变成十进制精确计算。把格式化结果再 Number 一次，也只是重新得到一个 Number。

Number.EPSILON 不是万能比较阈值

Number.EPSILON 表示 1 与大于 1 的最小可表示 Number 之间的间隔。数值越大，相邻可表示值之间的绝对距离通常也越大，所以不能要求所有数量级都用同一个 EPSILON 判断误差。

JavaScript
const actual = 0.1 + 0.2;
const expected = 0.3;
const absoluteTolerance = 1e-12;
console.log(Math.abs(actual - expected) <= absoluteTolerance); // true

这个阈值只是本例明确接受的绝对误差，不是所有业务的标准。接近零的量常需要绝对误差限制，不同数量级的量也可能需要相对误差，常见思路是结合“绝对阈值”和“相对阈值乘数值尺度”。

真实选择还取决于单位：地理距离、动画坐标和账户金额不能使用同一套随意设定的容差。NaN、Infinity、极大数差值溢出等情况也要单独处理，不能把一个简单比较函数宣传为适用于所有数值的通用正确性判断。

安全整数不是最大能表示的数

Number.MAX_SAFE_INTEGER 是 2 的 53 次方减 1，也就是 9007199254740991。安全整数范围内的整数可以被精确表示，并能与相邻整数保持可靠区分。

JavaScript
const limit = Number.MAX_SAFE_INTEGER;
console.log(limit + 1 === limit + 2); // true
console.log(Number.isSafeInteger(limit + 1)); // false

超过安全范围后，并不是每个整数都立即无法表示。某些值仍能表示，但相邻整数可能落到同一个 Number 上，作为 ID、计数或金额时就可能发生碰撞。

Number.MAX_VALUE 描述的是更大的有限数值范围，不能替代 MAX_SAFE_INTEGER；Number.isInteger 也只判断当前 Number 是否具有整数值，不能保证原输入在转换过程中没有丢失精度。需要安全整数时使用 Number.isSafeInteger，并确保输入进入 Number 之前也符合要求。

BigInt 要从没有丢失精度的数据创建

JavaScript
console.log(BigInt(9007199254740993)); // 9007199254740992n
console.log(BigInt('9007199254740993')); // 9007199254740993n

第一行的数字字面量先变成 Number，已经无法准确表示原本想写的整数；之后转成 BigInt，只能精确保存那个已经舍入的值，不能恢复丢掉的信息。

大整数 ID 从接口进入前端时，通常应直接以字符串传输并保留，确需整数运算时再转 BigInt。若普通 JSON 数字先被解析为 Number，再转字符串或 BigInt，一般已经错过了保留精度的时机。ID 不需要算术时，保持字符串也更简单。

BigInt 可以处理很大的整数，但仍受内存、计算资源和实现限制。它不能存储小数，也不能直接与 Number 混用算术，例如 1n + 1 会抛 TypeError；Math 的多数 Number 运算接口也不接受 BigInt。需要跨类型转换时，应主动检查是否会截断或超出安全范围。

金额可以用整数最小单位，但解析也必须准确

如果业务明确只接受两位以内小数，可以从字符串直接构造整数分，而不是先把原字符串变成浮点元再乘 100：

JavaScript
function parseCents(text) {
  if (typeof text !== 'string') {
    throw new TypeError('金额必须以十进制字符串提供');
  }
  const match = /^(0|[1-9][0-9]*)(?:\.([0-9]{1,2}))?$/.exec(text);
  if (!match) throw new RangeError('请输入非负金额，最多两位小数');

  const fraction = (match[2] ?? '').padEnd(2, '0');
  return BigInt(match[1]) * 100n + BigInt(fraction);
}

console.log(parseCents('12.30')); // 1230n
console.log(parseCents('0.05')); // 5n

这段示例的契约很窄：非负十进制，不带千位分隔符、空白或多余前导零，最多两位小数，不执行四舍五入。它不负责货币格式化，也不代表所有币种都有两位最小单位。输入长度与金额上限还应根据真实业务限制。

涉及税率、汇率、分摊或中间小数时，还要定义何时舍入、采用哪种舍入规则以及怎样处理尾差。可以使用适当的整数策略或可靠的十进制库，但不能只在最后补一个 EPSILON 就认为满足财务规则。

整数分也要处理分摊余数

100 分分给三份，不能每份都舍成 33 分后丢掉剩余 1 分。下面约定非负整数分，平均分配，余数按固定顺序加给前几份；这是一个明确的业务规则，不是所有结算场景通用的规则。

JavaScript
function splitCents(total, count) {
  if (typeof total !== 'bigint' || total < 0n) throw new TypeError('总额必须为非负 BigInt 分');
  if (!Number.isSafeInteger(count) || count < 1 || count > 10000) {
    throw new RangeError('份数须为 1～10000 的整数');
  }
  const parts = BigInt(count);
  const base = total / parts;
  const remainder = total % parts;
  return Array.from({ length: count }, (_, index) =>
    base + (BigInt(index) < remainder ? 1n : 0n));
}

console.log(splitCents(100n, 3)); // [34n, 33n, 33n]
console.log(splitCents(2n, 3)); // [1n, 1n, 0n]

输出之和严格等于原总额，各份最多相差 1 分。接收者顺序必须稳定，否则重试可能把余数分给另一个人；按比例分摊、负数退款、税费逐项舍入则需要另外定义规则。前端计算可用于预览，最终结算仍由服务端权威流程验证。

序列化必须与服务端约定一致

默认 JSON.stringify 不能直接序列化 BigInt，会抛出 TypeError。可以把明确的大整数或最小单位字段转成十进制字符串，再按接口约定还原；不要把所有看起来像数字的字符串无条件变成 BigInt，否则邮编、验证码等标识会被误处理。

使用 replacer、reviver 或库时，同样需要明确字段和类型协议。最重要的是从输入、存储、计算直到传输，都不要中途偷偷经过一个不能表达所需精度的 Number。
