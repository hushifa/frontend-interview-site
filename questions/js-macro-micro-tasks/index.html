事件循环输出顺序题怎么推？async/await、setTimeout、requestAnimationFrame 谁先执行？

先把每个回调归类：同步代码、微任务（Promise 回调、await 之后的代码、queueMicrotask）、任务（setTimeout 等），再按“同步跑完、清空微任务、取下一个任务”推。new Promise 的执行器和 await 之前的代码都是同步执行的。requestAnimationFrame 回调属于渲染步骤，和 setTimeout 没有固定先后。

参考答案

简答

做输出顺序题，先给每行代码归类，再按事件循环的规则排。规则本身见《事件循环中，任务和微任务按什么顺序执行？》，这里只讲怎么推。

第一类是同步代码，按书写顺序立刻执行。容易看错的是：new Promise 的执行器函数是同步执行的；async 函数在第一个 await 之前的部分也是同步执行的，await 右边的表达式同样会立刻求值。

第二类是微任务：Promise 的 then、catch、finally 回调，await 之后的代码，queueMicrotask 和 MutationObserver 的回调。同步代码跑完后，它们按进队顺序全部执行完，执行中新加的微任务也在这一轮执行。第三类是任务，常说的宏任务，比如 setTimeout 回调，要等微任务清空才轮到下一个。

requestAnimationFrame 单独算。它的回调既不是任务也不是微任务，而是在浏览器更新渲染时调用，所以只能确定它晚于同步代码和已排队的微任务，和 setTimeout(fn, 0) 谁先没有固定答案。

推导的步骤

拿到一道题，按下面的顺序走一遍：

  1. 从上往下只看同步代码，把打印依次写下来。遇到 setTimeout 记进“任务”列，遇到 then 或 await 之后的代码记进“微任务”列。
  2. 同步代码结束后，从微任务列的头开始逐个执行。执行时又产生的微任务追加到这一列末尾，产生的定时器追加到任务列末尾。
  3. 微任务列空了，取任务列的第一个执行，执行完再回到第 2 步。

需要说明的是，规范里没有“宏任务”这个词，对应的是任务（task）。不同来源的任务（比如定时器和点击事件）谁先执行，规范允许浏览器自己选，只有同一个任务源里先进先出。所以题目一般只用定时器来考任务顺序。

经典的 async/await 题

JavaScript
const log = [];
async function async1() {
  log.push('2 async1 开始');
  await async2();
  log.push('6 async1 结束');
}
async function async2() {
  log.push('3 async2');
}
log.push('1 script 开始');
setTimeout(() => {
  log.push('8 setTimeout');
  console.log(log.join(' → ')); // 1 script 开始 → 2 async1 开始 → 3 async2 → 4 Promise 执行器 → 5 script 结束 → 6 async1 结束 → 7 then → 8 setTimeout
}, 0);
async1();
new Promise((resolve) => {
  log.push('4 Promise 执行器');
  resolve();
}).then(() => log.push('7 then'));
log.push('5 script 结束');

按步骤推。同步阶段：先打印 1，setTimeout 记进任务列。调用 async1()，打印 2；await async2() 先同步调用 async2，打印 3；然后 async1 暂停，“6”记进微任务列。new Promise 的执行器同步执行，打印 4，resolve() 后“7”记进微任务列。最后打印 5。

微任务阶段按进队顺序执行，先 6 后 7。最后取任务列的定时器，打印 8。

这里“6”排在“7”前面，是因为 await 一个原生 Promise 时，后续代码在该 Promise 兑现后作为一个微任务恢复，而 async2() 返回的 Promise 已经兑现，所以“6”比“7”先进队。

嵌套的微任务和定时器

再看一道嵌套题：微任务里又安排了微任务和定时器。在 Node.js 里运行，下面的数字就是实际打印顺序：

JavaScript
const log = [];
log.push('1 同步');
setTimeout(() => {
  log.push('5 setTimeout');
}, 0);
Promise.resolve().then(() => {
  log.push('3 then');
  setTimeout(() => {
    log.push('6 then 里的 setTimeout');
    console.log(log.join(' → ')); // 1 同步 → 2 同步 → 3 then → 4 then 里的微任务 → 5 setTimeout → 6 then 里的 setTimeout
  }, 0);
  Promise.resolve().then(() => log.push('4 then 里的微任务'));
});
log.push('2 同步');

为什么“4”能插到“5”前面？“4”是在微任务执行时才加进去的，但微任务检查点会一直跑到队列空为止，所以它还在这一轮里。“6”是微任务里新安排的定时器，只能排到已有的“5”后面。

requestAnimationFrame 排在哪里

requestAnimationFrame(callback) 做的事情很简单：按规范的步骤，它只是把回调存进当前文档的动画帧回调表，返回一个编号。它不往任何任务队列或微任务队列里放东西。MDN 的描述是“在下一次重绘之前调用指定的回调”。

真正调用回调的地方是“更新渲染”。规范的做法是，事件循环发现有文档到了渲染时机，就在渲染任务源上排一个“更新渲染”的任务，这个任务里依次处理 resize、scroll 等步骤，然后对每个文档“运行动画帧回调”，再去算样式和布局。渲染时机多久来一次，规范没有规定固定模型，只举例说 60Hz 时最多约 16.7 毫秒一次，页面不可见时可能更少。浏览器判断渲染不会有可见变化时，还可以跳过这一步。

所以 setTimeout(fn, 0) 和 requestAnimationFrame 谁先，取决于定时器到点和渲染时机哪个先来。用 Chrome 156 的无头模式跑下面这段，三次都得到 sync, micro, qm, timeout, raf, raf-micro：

JavaScript
const log = [];
log.push('sync');
setTimeout(() => log.push('timeout'), 0);
requestAnimationFrame(() => {
  log.push('raf');
  Promise.resolve().then(() => log.push('raf-micro'));
});
Promise.resolve().then(() => log.push('micro'));
queueMicrotask(() => log.push('qm'));

这只能说明这次环境里定时器先到。无头模式没有真实屏幕，渲染不按真实的帧节奏走，换成有界面的浏览器、换一个页面状态，raf 跑到 timeout 前面也是规范允许的。面试时能确定的说法只有：微任务先于两者；两者之间没有固定顺序。

另一个结果可以确定：raf-micro 紧跟在 raf 后面。在同一次渲染里注册两个 rAF 回调，第一个回调里加一个微任务，Chrome 156 的结果是 raf1, raf1-micro, raf2。原因是每个回调都由“调用回调”的算法执行，回调结束、执行栈为空时会做一次微任务检查点，所以回调之间会清空微任务。

常见追问

为什么 setTimeout(fn, 0) 不是马上执行？

它只是让定时器到点后往任务队列里加一个任务，要等当前任务和所有微任务执行完才可能轮到。另外 HTML 规范规定，定时器嵌套超过 5 层且延时小于 4 毫秒时，延时会被提到 4 毫秒。

动画为什么推荐用 requestAnimationFrame 而不是 setTimeout？

rAF 回调在浏览器下一次重绘之前执行，频率跟着渲染时机走，回调里改的样式正好赶上这一帧；定时器的到点时间和屏幕刷新没有关系。另外 MDN 提到，大多数浏览器会在后台标签页和隐藏的 iframe 里暂停 rAF 调用，以节省性能和电量。

Node.js 里也有宏任务和微任务吗？

Node.js 没有渲染步骤，也没有 requestAnimationFrame，它的事件循环分阶段执行，还多了 process.nextTick。细节见《Node.js 事件循环和浏览器有什么不同？nextTick 一定先于 Promise 吗？》。
