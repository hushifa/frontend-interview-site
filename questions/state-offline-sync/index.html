前端离线同步怎样处理重试和数据冲突？

离线同步先把修改写进本地（IndexedDB），待同步的操作放进持久队列，联网后按顺序发送。每个操作带唯一 ID，服务端据此保证幂等；网络错误和 5xx 退避重试，版本冲突不能盲目重试，要合并或让用户选择。

参考答案

简答

离线同步的思路是本地优先：用户改了东西，先写进浏览器里的 IndexedDB，界面立刻更新，不用等网络。还没发出去的修改放进一个待同步队列，这个队列也存在 IndexedDB 里，所以标签页关了、页面被回收了，也不会丢。

每个操作带两样东西：一个客户端生成的唯一 id，和它基于的服务端版本 baseVersion。服务端按 id 去重，同一个操作发了两次也只写一次，这叫幂等。

失败了要分情况。网络错误、超时、5xx、429 这类是暂时的，按指数退避重试；400 这类是请求本身有问题，重试多少次都不会成功，要标记失败；409 是版本冲突，进入冲突处理。

冲突怎么处理要看业务：可以按字段合并，可以后写覆盖，也可以保留两份让用户选。要注意，只有同步成功了，才能把操作从队列里删掉。

队列里的一条记录长什么样

JavaScript
const change = {
  id: crypto.randomUUID(),
  docId: 'note-42',
  baseVersion: 7,
  patch: { title: '新标题' },
  attempts: 0,
  lastError: null,
};

id 用来让服务端去重，baseVersion 表示“我是在第 7 版的基础上改的”，服务端靠它发现冲突。attempts 和 lastError 记录重试了几次、上次为什么失败。

同步循环怎么写

JavaScript
async function flush(queue) {
  for (const change of await queue.list()) {
    let res;
    try {
      res = await fetch(`/api/docs/${change.docId}`, {
        method: 'PATCH',
        headers: { 'Content-Type': 'application/json', 'Idempotency-Key': change.id },
        body: JSON.stringify({ baseVersion: change.baseVersion, patch: change.patch }),
      });
    } catch {
      await queue.retryLater(change); // 网络错误：退避后重试
      return; // 保持顺序，后面的操作暂不发送
    }

    if (res.ok) {
      const { version } = await res.json();
      await queue.remove(change.id);
      await queue.rebase(change.docId, version); // 后续操作基于新版本
    } else if (res.status === 409) {
      await queue.markConflict(change, await res.json());
      return;
    } else if (res.status >= 500 || res.status === 429) {
      await queue.retryLater(change);
      return;
    } else {
      await queue.markFailed(change, res.status); // 4xx：需要人工处理
      return;
    }
  }
}

window.addEventListener('online', () => flush(queue));

注意每个失败分支后面都有 return。为什么一出错就整个停下，而不是跳过这条、接着发下一条？因为同一文档的操作是有先后的，后一条是在前一条的基础上改的。前一条没成功就发后一条，它依据的版本就是错的。

成功的时候，服务端会返回新版本号。rebase 把队列里同一文档后续操作的 baseVersion 更新成这个新版本，下一条才能正确提交。

重试的间隔要逐次加倍，再加一点随机抖动。不加抖动的话，网络一恢复，大量客户端会在同一时刻一起重试，把服务器打垮。

版本冲突怎么处理

服务端发现 baseVersion 和当前版本对不上，说明别人在这期间改过了。这时返回 409，并带上服务端最新的内容。

客户端有几种处理方式。双方改的字段不重叠，就自动合并。改到同一个字段了，就把两个版本都展示出来，让用户选保留哪个。计数器、集合这类数据，可以用 CRDT 库，比如 Yjs、Automerge，自动合并。

“最后写入覆盖”实现起来最简单，可它会悄悄丢掉其他设备上的修改，只适合不重要的数据。

页面关了还能同步吗

Background Sync API 可以在页面关掉以后、网络恢复时，由 Service Worker 触发同步。但它目前只有 Chromium 系的浏览器支持。不支持的浏览器，就在页面打开时、online 事件触发时，以及定时检查时去同步。

还要注意什么

同步状态要让用户看得到：已保存到本地、同步中、同步失败、存在冲突。

几个人共用一台设备时，本地数据库要按用户隔离，登出时清理干净。

浏览器在存储空间紧张时可能会清掉本地数据。重要数据可以调用 navigator.storage.persist() 申请持久化。

常见追问

为什么不能只用一个 isSynced 标记？

它表达不了“本地又有新编辑，同时上一次请求还在重试”这种状态，也存不下待发送的内容是什么。

服务端怎么实现幂等？

把处理过的操作 ID 和处理结果存下来。收到重复的 ID，直接返回之前的结果，不再执行一遍。
