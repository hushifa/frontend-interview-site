Navigation API 解决了传统 History API 的哪些问题？

对比手动拼接的 SPA 路由与统一导航事件，解释拦截、历史条目、取消和提交完成状态，并给出限制路由范围、校验静态数据和防止旧结果覆盖的示例。

参考答案

传统 SPA 路由往往需要自己组合很多入口：拦截链接 click、调用 pushState、监听 popstate、加载新内容，再处理前进后退、取消、滚动和焦点。只监听链接点击，还会漏掉程序发起的导航和历史遍历等场景。

Navigation API 把导航动作、历史条目和异步处理过程放进更统一的模型中。它帮助浏览器理解“应用正在处理一次导航”，而不只是看见 URL 被修改。

核心能力目前已进入 Baseline 2026，不能再笼统称为只在实验浏览器里存在的 API。但旧版本浏览器、内嵌 WebView 和较新的子功能仍要分别核实支持，框架也不一定采用同一套集成方式。

navigate 事件提供了更多导航上下文

通过 window.navigation 可以监听 navigate。事件包含目标 URL、导航类型、是否能拦截、是否是片段变化、下载或表单提交等信息，还有与这次导航关联的 AbortSignal。

event.intercept() 可以把允许拦截的导航交给应用，并转成同文档处理。它不只是在已经发生的同文档路由上加一个回调，也可以把本来可能加载新文档的合适导航转成 SPA 更新。

但不是所有导航都能拦截。应先检查 canIntercept，并只处理应用拥有的路由；跨源链接、下载、原生表单流程和不认识的地址不应被一个全局监听器全部吞掉。

hashChange、downloadRequest、formData 等也有不同含义。尤其 downloadRequest 可能是空字符串文件名，不能只用真假值判断“有没有下载请求”，应按它是否为 null 判断。

一个读取静态 JSON 的最小路由示例

假设 /guide/ 和 /faq/ 都有可直接访问的 HTML 页面，客户端增强时分别读取 /data/guide.json 与 /data/faq.json。JSON 约定为 { "title": "标题", "content": "纯文本正文" }。

下面传入真实的主内容容器。示例只接管这两个没有查询参数的路由，不处理文章 HTML 注入、权限和复杂嵌套路由：

JavaScript
function installArticleNavigation(outlet) {
  if (!('navigation' in window) || typeof AbortSignal.any !== 'function') {
    return () => {};
  }

  const routes = new Map([
    ['/guide/', '/data/guide.json'],
    ['/faq/', '/data/faq.json'],
  ]);
  const lifetime = new AbortController();
  let sequence = 0;

  navigation.addEventListener('navigate', (event) => {
    if (
      event.defaultPrevented ||
      !event.canIntercept ||
      event.hashChange ||
      event.downloadRequest !== null ||
      event.formData !== null
    ) {
      return;
    }

    const url = new URL(event.destination.url);
    const dataUrl = routes.get(url.pathname);
    if (url.origin !== location.origin || url.search || !dataUrl) return;

    const id = ++sequence;
    const signal = AbortSignal.any([event.signal, lifetime.signal]);

    event.intercept({
      async handler() {
        signal.throwIfAborted();
        outlet.setAttribute('aria-busy', 'true');
        try {
          const response = await fetch(dataUrl, { signal });
          if (!response.ok) throw new Error(`页面请求失败：HTTP ${response.status}`);
          const data = await response.json();
          if (!data || typeof data.title !== 'string' || typeof data.content !== 'string') {
            throw new Error('页面数据格式不正确');
          }
          signal.throwIfAborted();
          if (id !== sequence) return;

          const heading = document.createElement('h1');
          const paragraph = document.createElement('p');
          heading.textContent = data.title;
          paragraph.textContent = data.content;
          outlet.replaceChildren(heading, paragraph);
          document.title = data.title;
        } catch (error) {
          if (!signal.aborted && id === sequence) {
            outlet.textContent = '页面加载失败，请重试或刷新页面。';
            document.title = '页面加载失败';
          }
          throw error;
        } finally {
          if (id === sequence) outlet.removeAttribute('aria-busy');
        }
      },
    });
  }, { signal: lifetime.signal });

  return () => {
    sequence += 1;
    lifetime.abort();
    outlet.removeAttribute('aria-busy');
  };
}

组件或路由系统销毁时调用清理函数。缺少这里所需能力时不注册拦截，普通链接继续走文档导航，因此部署必须真的提供这些地址的页面或正确的服务器路由，不能只在首页能打开时就认为深链接可用。

示例通过 textContent 展示数据，不把接口里的字符串直接写进 innerHTML。项目使用成熟框架路由时，也不应再随手添加另一个全局拦截器与它争用导航。

取消旧导航，要同时阻止旧结果提交

新导航开始、用户中止等情况，会让相应旧导航的 signal 取消。示例把它与组件生命周期信号组合后传给 fetch，使离开页面或销毁绑定能停止相关请求。

取得 JSON 以后还检查一次信号和操作序号，是为了防止“请求已经完成，但结果即将提交”这类边界。其他加载器若不支持 AbortSignal，仍需要版本检查，不能只调用 abort 就认定所有异步函数都停止了。

取消是正常的导航竞争结果，不必给用户显示成服务器错误。真正的数据请求失败则应有与目标地址一致的错误界面、重试和日志，而不是留下看起来成功的旧页面内容。

committed 和 finished 表示不同阶段

navigation.navigate() 等方法返回的对象包含 committed 与 finished 两个 Promise。前者关注导航条目的提交，后者关注这次导航处理的完成，两者可能在不同时间完成或失败。

普通 intercept 的 handler 运行时，currentEntry 已经更新，因此 URL 可能先变成新地址，数据稍后才到达。handler 失败并不等于浏览器自动把应用 DOM 和历史状态都回滚成旧页面；示例因此主动显示目标页面的加载错误。

程序化导航要处理相应 Promise 的拒绝，可以按需求分别观察或使用 Promise.allSettled；也可以监听 navigatesuccess、navigateerror 统一反映状态。不要只把“地址栏变了”当成内容加载成功。

较新的 precommitHandler 可以参与提交之前的处理，但它有自己的可取消条件与兼容要求，不能因为核心 Navigation API 可用，就认定所有扩展选项都一致可用。

历史、焦点和滚动也有对应模型

currentEntry 表示当前条目，entries() 可以查看应用可见范围内的条目，条目的 key 可用于相应历史遍历，getState()/updateCurrentEntry() 等能力用于管理关联状态。这不是读取用户全部跨站浏览历史的接口。

条目状态也不等于 URL 中可分享的数据，保存筛选或编辑状态时应区分刷新、链接分享与历史恢复的需求，并使用允许序列化的值。

拦截导航具有默认的焦点与滚动处理，例如完成后处理 autofocus/body 焦点，或恢复历史位置、滚动到片段。选择 manual 会关闭对应默认行为，此时应用要自己承担焦点与滚动的可访问性工作，不能只为了避免滚动就把它永久关闭。

导航 transition 表示条目之间的异步过程，并不自动等于 CSS 动画或 View Transitions 视觉过渡。加载数据、管理历史和播放动画是可以协作但不相同的几层功能。

Navigation API 能减少手动拼接的路由基础工作，但数据缓存、权限、页面错误、组件生命周期和部署深链接仍要由应用设计。选择它或框架封装，应依据目标浏览器与实际路由复杂度，而不只是接口是否新。
