Permissions.query 是申请权限，还是查询权限？

Permissions.query 查询当前上下文对某项能力的权限状态，常见结果是 granted、denied 或 prompt。它本身通常不是弹出授权框的统一申请入口，实际请求权限由相应功能 API 的流程决定。

参考答案

Permissions.query 查询当前上下文对某项能力的权限状态，不是统一的“弹出授权框”方法。真正申请使用能力，通常发生在调用定位、媒体设备等具体 API 时。

可以先查询状态来调整提示，但最终是否成功仍以具体操作结果为准。权限许可与设备可用、文档状态和参数合法性是不同条件。

三种状态应该怎样理解

granted 表示当前报告为允许，denied 表示当前受拒绝或限制，prompt 表示使用时可能需要用户作出选择。prompt 不保证一定显示同一种弹窗，denied 也不保证用户刚刚点击过“拒绝”。

Permissions Policy、上下文安全要求、浏览器设置和用户选择都可能参与结果。例如父页面禁止某个 iframe 使用定位，iframe 查询到 denied，并不能靠不断弹提示解决。

把查询失败与权限拒绝分开

JavaScript
async function getLocationPermission() {
  if (!navigator.permissions?.query) {
    return { state: 'unknown', status: null };
  }
  try {
    const status = await navigator.permissions.query({ name: 'geolocation' });
    return { state: status.state, status };
  } catch {
    return { state: 'unknown', status: null };
  }
}

这里 unknown 是应用自己定义的状态，不是 PermissionStatus.state 的标准值。它表示无法完成查询，不能伪装成 denied，否则可能错误禁用一个实际可用的功能。

不同浏览器支持的 descriptor 不一致，未知名称可能使 Promise 以 TypeError 拒绝。不能因为 navigator.permissions 存在，就认为所有权限名称都可查询。

granted 仍然可能操作失败

定位已允许，但设备无法取得位置；摄像头已允许，但设备被占用或移除；页面状态变化导致 API 不能继续运行——这些都不是简单的权限查询能预先保证的。

业务仍需处理具体 API 的错误和取消，给用户准确下一步：重新尝试、检查设备、选择其他输入方式或查看浏览器设置。不要把任何错误都归类成“请授予权限”。

权限也可能是临时的，用户可以在站点设置中撤销。页面初始化时查一次结果，不能作为整个会话永久成立的授权证明。

状态变化可以订阅，但监听也要释放

query 返回的 PermissionStatus 可以监听 change，并在需要时读取新的 state。组件退出或不再使用功能时移除监听，避免重复绑定和更新已销毁界面。

查询本身是异步的：如果组件在等待期间已经卸载，随后才取得 status，应先检查生命周期再安装监听，不能因为还没拿到对象就漏掉清理。

Permissions API 也不是一个通用撤销入口。应用可以停止摄像头轨道、清除自己的数据或结束会话，但浏览器站点权限设置由相应平台机制管理，不能假设所有权限都能通过同一个 revoke 方法重置。

在用户真正需要功能时解释用途

页面加载时同时申请定位、通知和麦克风，用户难以判断原因，也容易直接拒绝。应围绕明确任务，比如点击“附近门店”时解释定位用途，再调用相应能力。

若用户拒绝，提供手动选择城市等可行路径。反复立即重试不会把 denied 变成可靠的成功状态，可能只增加打扰。

测试时区分 API 不存在、descriptor 不支持、prompt、denied、granted 以及 granted 后操作失败。权限测试替身只能验证界面分支，真实浏览器的提示、策略继承和持久化行为需要单独验证。
