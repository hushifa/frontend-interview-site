aria-live 怎样用于动态状态播报？

解释 live region 的优先级、角色与更新时机，用搜索状态示例处理过期结果，并说明重复消息、aria-busy、焦点与真实读屏测试的边界。

参考答案

简答

  • live region 让动态变化在不移动焦点的情况下通知辅助技术。
  • 大多数“已保存”“找到 N 条结果”用 role="status" 或 polite，只有紧急错误才用 assertive 或 alert。
  • 通知区域应先存在于页面中，之后再更新文字，不要在同一刻创建节点、写入文字并加上 aria-live。
  • 不要重复堆叠多个相同语义的区域，频繁变化的内容应合并或节流通知。

用户提交搜索后，焦点仍在输入框里，旁边的结果数量从 0 变成 8。能看见页面的人容易察觉变化，读屏用户却不一定会自动听到它，也不应该每次更新都被强制移动焦点到结果区。

Live region 用来把这种动态变化暴露给辅助技术，使合适的信息可以在不移动焦点的情况下被通知。它不是语音播放 API，浏览器和读屏如何排队、合并和朗读，仍有实现与用户设置差异。

先选择通知的重要程度

设置常见用途
aria-live="polite"等待合适时机通知，适合搜索结果、保存状态等普通反馈
aria-live="assertive"更高优先级，可能打断当前朗读，只适合确实紧急的信息
role="status"具有状态通知语义，隐含 polite 和 atomic=true
role="alert"具有警报语义，隐含较强的通知优先级，不用于所有普通提示

多数“已保存”“找到若干结果”不需要 assertive。把所有变化都设成紧急通知，会不断打断用户，反而让真正重要的信息难以理解。

role=status 本身已提供相应 live 语义，不必为了保险再堆上多个相同区域。role=alert 与重复的 aria-live 配置在部分组合中还可能产生重复通知。需要冗余属性时应有实际兼容性依据，而不是越多越好。

aria-live=off 也不能简单理解成“这块内容对读屏永远静音”，用户把焦点或阅读位置移到其中时，仍可能按正常阅读规则感知内容。

通知区域最好先存在，再更新文字

辅助技术通常需要先知道“这里是一个 live region”，才能观察后续变化。可靠的基础做法是在初始 HTML 中保留一个空区域：

HTML
<p id="search-status" role="status"></p>
<ul id="search-results" aria-busy="false"></ul>

之后再更新 search-status 的 textContent。不要在同一瞬间创建一个普通节点、写入文字、加上 aria-live，就假定所有组合都必然播报。

如果必须动态建立区域，应让区域有机会先被暴露，再在后续任务中更新内容，但具体效果仍要测试。role=alert 常有特殊处理，有时初始或新插入的警报内容也会被通知；不能把这种特殊情况推广到所有 polite 区域。

区域也不能一直 display:none、hidden 或被 aria-hidden 隐藏，还期待其中的变化正常通知。只想视觉隐藏时，应使用经过验证的 visually-hidden 样式，保留它在可访问性树中的存在。

搜索状态还需要防止旧请求覆盖新消息

下面的辅助函数不发请求，只管理一个明确的状态区域和结果容器。每次真正开始一轮搜索时调用 start，获得对应的 complete/fail；旧搜索结束时不会覆盖新搜索的状态。

JavaScript
function createSearchStatus(status, results) {
  let latest = 0;
  let disposed = false;

  return {
    start(query) {
      if (disposed) throw new Error('搜索状态已销毁');
      const id = ++latest;
      const term = query.trim();
      results.setAttribute('aria-busy', 'true');
      status.textContent = term ? `正在搜索“${term}”。` : '正在更新搜索结果。';

      return {
        complete(count) {
          if (disposed || id !== latest) return;
          if (!Number.isSafeInteger(count) || count < 0) {
            throw new RangeError('结果数量必须是非负整数');
          }
          results.setAttribute('aria-busy', 'false');
          status.textContent = term
            ? `“${term}”找到 ${count} 个结果。`
            : `找到 ${count} 个结果。`;
        },
        fail() {
          if (disposed || id !== latest) return;
          results.setAttribute('aria-busy', 'false');
          status.textContent = '搜索失败，请重试。';
        },
      };
    },
    dispose() {
      disposed = true;
      latest += 1;
      results.setAttribute('aria-busy', 'false');
      status.textContent = '';
    },
  };
}

完成时应先把对应结果更新到界面，再调用 complete，让状态与用户可阅读的内容一致。这个函数只保护状态消息，数据加载和结果列表本身也要处理取消与过期结果，不能以为通知没串就代表数据也没串。

示例使用 textContent，不把搜索词当 HTML 执行。status 保留在结果列表之外，所以清空或重建结果列表时不会把通知区域也销毁；焦点仍由原来的交互逻辑管理。

不要把这段接口直接接到每一个按键上不断通知“正在搜索”。可以按实际提交或适当防抖后的请求阶段更新，查询词较长时也应考虑简洁的反馈文案。

atomic、relevant 和 busy 控制的是不同方面

aria-atomic 决定区域局部变化时，辅助技术是否把整个区域作为一次完整信息呈现。例如“找到 8 个结果”只改变数字时，读出完整短句通常比只读“8”清楚。status 已隐含 atomic=true。

aria-relevant 用来表达哪些变化值得通知，例如新增或文本变化。它不是“用户一定按这个顺序听到所有记录”的队列协议，不应把频繁变动的长列表直接配置为全量紧急播报。

aria-busy 表示区域正在更新，可帮助辅助技术等待更完整的状态。若把 busy 长期留为 true，可能导致通知迟迟不发生。示例把 busy 放在结果列表上，而把需要即时提供的简短状态放在独立区域，避免把“正在搜索”的提示也一起压住。

重复文本和快速更新并不总会逐条播报

连续把同一句“已保存”写进去，可能没有新的有效文本变化，也可能被读屏合并。几个快速更新也未必被逐字逐条读出。

应让业务阶段和消息上下文明确，例如从“保存中”变为“已保存”，而不是靠不停追加空格、清空重写或制造随机字符来强迫朗读。需要重复操作的反馈时，应在目标辅助技术上验证节奏与内容，不宣称某个固定延时对所有组合都有效。

聊天消息、实时日志和 AI 流式文本尤其要避免每个 token 都作为高优先级通知。可以按合适批次或完整消息通知，并让用户控制阅读，不要把整份不断增长的正文塞进 assertive 区域。

通知不能代替名称、错误关联或必要的焦点管理

一次播报结束后，用户仍应能在界面中找到相关结果或错误。字段错误需要与字段关联，保存失败需要可操作的重试路径，不能只瞬间显示一句话然后永远消失。

普通状态不需要把焦点抢到提示上；真正打开一个必须操作的对话框时，也不能只靠 live region 通知而不处理焦点。它们解决的是不同任务。

验证可以先检查可访问性树是否暴露了 status、live、atomic 等信息，再用真实读屏测试首次更新、连续搜索、相同结果、失败、清空和页面切换。属性存在与实际听到什么不是同一项证据，自动化不能替代最终的读屏体验确认。
