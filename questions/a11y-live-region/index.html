aria-live 怎样用于动态状态播报？

页面上的文字变了，读屏用户不一定知道。live region 是页面加载时就存在的容器，内容变化时读屏自动播报；polite 等用户空闲时读，assertive 立即打断。保存成功、搜索结果数用 role="status"，紧急错误用 role="alert"。

参考答案

简答

点了“保存”，页面角落出现“已保存”，看得见的用户马上知道了，可读屏用户的焦点不在那里，什么也听不到。live region 就是解决这个问题的：给一个容器标上 aria-live，里面的内容一变，读屏就自动读出来。

关键是容器要在内容变化之前就在 DOM 里。如果新插入一个带 aria-live 的元素，同时写进文字，很多读屏不会播报。

播报有两种级别。aria-live="polite" 等读屏把当前内容读完再播，适合大多数状态；assertive 会立即打断，只用于必须马上知道的错误。平时更常用角色来写：role="status" 相当于 polite，role="alert" 相当于 assertive。如果希望每次都读出整个区域，而不只是变化的部分，加 aria-atomic="true"。

要注意，播报的文字要简短，不要把整个列表塞进去。焦点已经移到的地方，读屏本来就会读，不用再播一遍。

先看一个例子

下面是保存时的状态提示。容器先放在页面上，保存时只改它的文字。

HTML
<p id="save-status" role="status"></p>
JavaScript
async function save() {
  status.textContent = '正在保存…';
  try {
    await api.save();
    status.textContent = '已保存';
  } catch {
    status.textContent = '保存失败，请重试';
  }
}

<p> 一开始是空的，但它已经在 DOM 里，读屏已经在“盯着”它了。所以后面每次改 textContent，读屏都会依次读出“正在保存”“已保存”。

有一种情况会不播报：连续写入一模一样的文字。部分读屏会认为内容没变，于是不读。需要重复提示时，可以先清空，在下一帧再写入。

不同场景用哪种

场景写法
搜索结果数量role="status"：“找到 12 条结果”
表单保存成功role="status"
会话即将过期role="alert"
购物车数量role="status"，内容写“购物车 3 件商品”
聊天新消息role="log"，新增内容依次播报

购物车那一行写成“购物车 3 件商品”，而不是只写“3”，是因为读屏只读这个区域，单独一个数字用户听不懂。

常见错误

页面上好几个组件各放一个 live region，同时更新时就会互相打断。可以在应用层维护一两个共享的播报区域，统一往里写。

用 assertive 播报普通提示，会打断用户正在听的内容，体验很差。

用 display: none 把区域藏起来，读屏就不会播报了。需要视觉上隐藏时，用 .visually-hidden 这类把元素裁剪到 1px 的样式。

把实时变化的计时器、股价放进 live region，读屏会不停地读，用户什么别的都听不到了。

常见追问

表单错误要不要用 live region？

提交以后，把焦点移到第一个错误字段或错误汇总上，读屏会读出焦点位置的内容，一般不用再播报。边输入边校验的即时提示，可以用 polite 区域。
