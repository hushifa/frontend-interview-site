Tree shaking 如何工作？为什么有些代码无法移除？

从导出使用关系与模块副作用区分两类分析，解释 ESM、sideEffects 和纯调用标注的作用，并说明为什么优化结果必须结合真实构建验证。

参考答案

简答

  • Tree shaking 依赖 ES 模块的静态 import/export，在构建时找出没被使用的导出并删除。
  • 删除一段代码有两个前提：它的导出没人用，并且执行它没有副作用。
  • package.json 的 sideEffects: false 告诉打包工具"整个模块没人用时可以跳过"；/*#__PURE__*/ 标注单个调用没有副作用。
  • CommonJS（require、module.exports）的导出是运行时决定的，通常无法精确摇树。
  • 只有生产构建才会真正删除，结果要看产物验证，不能只凭源码判断。

两类分析

JavaScript
// utils.js
export function used() { return 1; }
export function unused() { return 2; }
console.log('utils loaded'); // 副作用
JavaScript
// main.js
import { used } from './utils.js';
used();
  • 导出级：unused 没被导入，可以删除。
  • 模块级：如果 main.js 一个导出都不用，整个 utils.js 能否跳过？顶层的 console.log 是副作用，打包工具默认会保留这个模块。

为什么有些代码删不掉

  1. 顶层副作用：修改全局对象、注册 polyfill、给原型添加方法、引入 CSS。打包工具无法确认删除后是否安全，只能保留。
  2. 无法判断纯度的调用：export const Button = styled.button(...) 是函数调用，工具不知道它是否修改外部状态。库可以在调用前加 /*#__PURE__*/ 标注，返回值没被使用时就能删掉。
  3. CommonJS：module.exports = {...} 和动态 require 让工具无法静态确定用到了哪些导出。选择依赖时优先使用提供 ESM 入口的版本（如 lodash-es）。
  4. 整体导入后动态访问：import * as utils 后写 utils[name]()，工具无法知道用到了哪个，只能全部保留。
  5. 类和对象的方法：一个类被使用，它的所有方法通常都会保留。

sideEffects 字段

json
{
  "name": "my-lib",
  "sideEffects": ["*.css", "./src/polyfill.js"]
}
  • false：所有模块都没有副作用，未使用的模块可以整个跳过。
  • 数组：列出确实有副作用的文件，其余可以跳过。
  • 声明错误会出问题：CSS 文件被标成无副作用后，import './style.css' 可能被删掉，样式丢失。

怎样验证

  • 运行生产构建（开发模式通常不删代码），用产物分析工具查看某个库最终占了多少体积。
  • 在产物中搜索应被删除的函数名或字符串。
  • webpack 的 optimization.usedExports 会在产物中留下 unused harmony export 注释，可以帮助定位。

常见追问

  • Tree shaking 和压缩是什么关系？标记未使用的导出由打包工具完成，真正删除代码通常由压缩器（Terser、esbuild、Oxc）完成。
  • 为什么按需引入插件还有必要？有些旧库只提供 CommonJS 或依赖副作用注册，按需插件把整体导入改写成单文件导入。
