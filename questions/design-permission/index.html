前端权限控制怎样设计路由、按钮和接口三层？

前端根据服务端下发的权限码控制路由能不能进、菜单与按钮显不显示，并在请求拦截里统一处理 401 和 403。这些都只是展示控制，可以被绕过，真正的授权必须由服务端对每个请求、每个资源校验。

参考答案

简答

前端权限只做展示控制：把没权限的菜单、按钮藏起来，拦住进不去的路由。它的目的是体验，不是安全。

为什么说不是安全？因为代码、接口地址、请求全都在用户手里，前端的判断随时可以绕过。真正的授权必须由服务端对每个请求做，而且不光要看用户有没有这个操作权限，还要看这条具体的数据是不是属于他。

权限数据由服务端下发，一般是角色或权限码列表。前端不要写死“某个角色能做什么”，这样权限调整时只改服务端配置就行。

接口层要统一处理两种状态码。401 表示没登录或登录过期，跳转登录页；403 表示登录了但没权限，给出提示，并刷新一下权限数据。

权限数据长什么样

登录后从服务端拿到权限码列表，前端用一个函数判断：

JavaScript
// 登录后从服务端获取
const session = { userId: 'u1', permissions: ['order:read', 'order:export'] };
const can = (code) => session.permissions.includes(code);

console.log(can('order:export')); // true
console.log(can('order:delete')); // false

为什么用细粒度的权限码，而不是直接判断角色名？因为页面只关心“能不能导出订单”，不关心用户是管理员还是运营。角色和权限码怎么对应，留在服务端管。

列表里没有的权限码，can 一律返回 false，也就是默认不可见、不可进。这和 OWASP 建议的“默认拒绝”是一致的。

路由层怎么做

在路由配置上声明每个页面需要的权限码，在全局导航守卫里检查，不满足就跳到 403 页或首页。

菜单也从同一份路由配置生成。否则很容易出现菜单能看见、点进去却被拦住的情况。

还有一种做法是动态添加路由，只注册有权限的路由，没权限的路由在前端根本不存在。但对应页面的代码分包仍然可能被下载、被阅读，所以这也不算安全保障。

用户用着用着权限被管理员收回了，或者几次导航同时进行时怎么办，见《路由并发导航和权限变化应该怎样处理？》。

按钮层怎么做

把判断封装成一个组件：

JSX
function Can({ code, children, fallback = null }) {
  return can(code) ? children : fallback;
}

<Can code="order:export">
  <button onClick={exportOrders}>导出</button>
</Can>;

封装成组件或者指令，权限判断就不会散落在代码各处。对于重要但当前没权限的操作，也可以显示成禁用状态并说明原因，而不是让功能莫名其妙地消失，具体按产品需求选择。

接口层能做什么

JavaScript
async function request(url, init) {
  const res = await fetch(url, init);
  if (res.status === 401) redirectToLogin();
  if (res.status === 403) {
    toast('没有权限执行该操作');
    refreshPermissions(); // 权限可能已变化，同步最新数据
  }
  return res;
}

前端在接口层能做的，是统一处理错误，不是授权。

授权是服务端的事，每个请求都要校验两件事：当前用户有没有这个操作的权限，目标数据在不在他的范围内。很多越权漏洞就出在只校验了“已登录”，没校验“这张订单是不是你的”，结果改一下 URL 里的订单 ID，就能看到别人的订单。

隐藏字段不等于保护字段

如果接口把手机号、成本价返回给了没权限的用户，前端就算不显示，用户打开开发者工具照样能看到。所以敏感字段要由服务端按权限裁剪掉再返回。

常见追问

权限数据存在 localStorage 里，被用户改了怎么办？

改了也只是多看到几个按钮，点下去接口照样返回 403。这恰好说明授权必须在服务端做。

页面级权限能用 JWT 里的声明吗？

可以用来做展示判断。但服务端校验时要以服务端的权限数据为准，还要考虑令牌没过期、权限却已经变了的情况。

多租户系统要注意什么？

服务端的每个查询都要带上租户条件，前端传上来的租户 ID 不能直接信任。
