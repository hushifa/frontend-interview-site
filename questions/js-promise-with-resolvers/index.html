Promise.withResolvers 适合解决什么问题？怎样避免 deferred 泄漏？

Promise.withResolvers 一次拿到 promise 和控制它的 resolve、reject，适合把"之后某个事件发生"包装成 Promise。它只能成功或失败一次，也不会帮你移除监听器和定时器，这些要自己清理。

参考答案

简答

有时候结果要等之后的某个事件才知道，比如等 Worker 发来“准备好了”，等用户点一下确认。这时想先拿到一个 Promise，等事件发生再去结束它。Promise.withResolvers() 一次返回 { promise, resolve, reject }，正好满足这个需求。它等价于在 new Promise 的执行器里，把 resolve 和 reject 存到外面的变量上，这种拆开使用的写法常叫 deferred。

它适合把一次性事件或者回调 API 包装成 Promise。要注意 Promise 只能结束一次，之后再调 resolve 会被忽略，所以它不能当消息队列用，连续的消息要用队列、异步迭代器或者流。

它也不会帮你取消或清理。监听器、定时器要在 Promise 结束时自己移除，否则回调和它引用的对象会一直留在内存里，这就是 deferred 泄漏。

它是 ES2024 标准化的，主流浏览器和 Node.js 22 都支持。

和以前的写法比有什么不同

JavaScript
let resolveReady;
const ready = new Promise((resolve) => {
  resolveReady = resolve;
});

const { promise, resolve, reject } = Promise.withResolvers();

以前要先声明一个变量，再在执行器里把 resolve 赋值出去，写起来绕一圈。现在一行就能拿到三样东西，效果是一样的。

怎样包装一次性事件，并且清理干净

下面等 Worker 发来 ready 消息，同时设置超时。注意成功、失败、超时三条路径里都调用了 cleanup。

JavaScript
function waitForWorkerReady(worker, timeout = 5000) {
  const { promise, resolve, reject } = Promise.withResolvers();

  const timer = setTimeout(() => {
    cleanup();
    reject(new Error('等待 Worker 启动超时'));
  }, timeout);

  function cleanup() {
    clearTimeout(timer);
    worker.removeEventListener('message', onMessage);
    worker.removeEventListener('error', onError);
  }

  function onMessage(event) {
    if (event.data?.type !== 'ready') return;
    cleanup();
    resolve(event.data.version);
  }

  function onError(event) {
    cleanup();
    reject(event.error ?? new Error('Worker 启动失败'));
  }

  worker.addEventListener('message', onMessage);
  worker.addEventListener('error', onError);
  return promise;
}

为什么要这么麻烦？Promise 结束以后，监听器并不会自己消失。如果不移除，Worker 之后发来的每一条消息都还会调用 onMessage，虽然 resolve 已经没有效果了，但这些函数和闭包里的对象会一直被引用着，回收不掉。所以哪条路径先结束，都要先 cleanup。

怎样支持中途取消

JavaScript
function waitForMessage(target, signal) {
  const { promise, resolve, reject } = Promise.withResolvers();

  function cleanup() {
    target.removeEventListener('message', onMessage);
    signal?.removeEventListener('abort', onAbort);
  }
  function onMessage(event) {
    cleanup();
    resolve(event.data);
  }
  function onAbort() {
    cleanup();
    reject(signal.reason);
  }

  if (signal?.aborted) {
    onAbort();
  } else {
    target.addEventListener('message', onMessage);
    signal?.addEventListener('abort', onAbort, { once: true });
  }
  return promise;
}

调用方传一个 AbortSignal，想放弃等待时调用 abort()，Promise 就以取消原因失败。开头先检查 signal?.aborted，是因为传进来的信号可能早就取消了，这时再去监听 abort 事件永远等不到。signal 也可以不传。

要明白，这里的取消只是“我不等了”，并移除监听器。对方正在做的工作不会因此停下，要靠它自己检查取消状态。

为什么不能用它接收连续的消息

JavaScript
const next = Promise.withResolvers();
next.resolve('第一条');
next.resolve('第二条');
next.promise.then(console.log); // 第一条

resolve 调了两次，可只拿到了“第一条”。Promise 一旦结束，结果就定了，后面的调用全部被忽略。

所以如果用一个 deferred 表示“下一条消息”，消息来得快一点就会丢。需要连续数据时，用 ReadableStream 或者异步生成器，并且给缓冲设一个上限。

常见追问

超时用 Promise.race 够吗？

只能让调用方早点拿到“超时”的结果，被比赛的那个任务其实还在跑。更好的做法是超时后调用 AbortController.abort()，并把 signal 传给下游，让任务真正停下来。

不支持 withResolvers 的环境怎样降级？

用 new Promise 写一个同样的工厂函数就行，在执行器里把 resolve、reject 存出来，和 promise 一起返回。
