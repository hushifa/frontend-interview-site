Context 与 useReducer 适合管理什么状态？

Context 让深层组件不用层层传 props 就能拿到数据，useReducer 把所有改状态的逻辑集中到一个函数里。两个合起来能管中小规模的共享状态，但 Context 一变所有读它的组件都会重新渲染，变化频繁的全局状态更适合用状态库。

参考答案

简答

组件嵌套很深时，一个数据要从顶层一层层传下去，中间的组件根本不用它，也得帮忙传。Context 解决的就是这个：在上面用 Provider 放一个值，下面任意深度的组件用 useContext 直接读最近的那个值。

useReducer 解决的是另一个问题：改状态的逻辑散落在各个事件里，不好维护。它把所有变化集中写在一个 reducer(state, action) 函数里，组件只管 dispatch 一个动作，说明“发生了什么”。

两者常一起用：把 state 和 dispatch 分别放进两个 Context。dispatch 的引用永远不变，只用它的组件不会因为状态变化而重新渲染。

要注意，Context 的值一变，所有读它的组件都会重新渲染，memo 也拦不住。所以它适合主题、语言、当前用户这类不常变的数据。另外 reducer 必须是纯函数，请求、定时器这些副作用要放在事件处理器或 Effect 里。

一个任务列表的完整组合

下面把任务列表的状态和更新逻辑都放进 Provider。注意看 tasks 和 dispatch 是分开放的。

JSX
import { createContext, use, useReducer } from 'react';

const TasksContext = createContext(null);
const TasksDispatchContext = createContext(null);

function tasksReducer(tasks, action) {
  switch (action.type) {
    case 'added':
      return [...tasks, { id: action.id, text: action.text, done: false }];
    case 'toggled':
      return tasks.map((t) => (t.id === action.id ? { ...t, done: !t.done } : t));
    case 'deleted':
      return tasks.filter((t) => t.id !== action.id);
    default:
      throw new Error(`未知动作：${action.type}`);
  }
}

export function TasksProvider({ children }) {
  const [tasks, dispatch] = useReducer(tasksReducer, []);
  // React 19 起可以直接用 <Context value>，旧写法 <Context.Provider value> 仍可用
  return (
    <TasksContext value={tasks}>
      <TasksDispatchContext value={dispatch}>{children}</TasksDispatchContext>
    </TasksContext>
  );
}

export const useTasks = () => use(TasksContext);
export const useTasksDispatch = () => use(TasksDispatchContext);

为什么要拆成两个 Context？因为有些组件只需要“发动作”，不需要读列表，比如添加任务的输入框。它调用 useTasksDispatch()，而 dispatch 从头到尾是同一个函数，所以任务列表怎么变，这个输入框都不会重新渲染。如果把两者塞进同一个 Context，它就会被列表的每次变化牵连。

reducer 里只根据旧状态和动作算出新状态，不发请求、不改外部变量。这样同样的输入总是得到同样的结果，好测试，也不会因为 React 多调用一次而出问题。

为什么 Context 一变就会大面积重新渲染

Context 没有“只订阅一部分”的能力。值换了，React 就通知所有读这个 Context 的组件重新渲染，不管它用到的那个字段有没有变。

最常见的坑是每次渲染都新建 value 对象：

JSX
<UserContext value={{ user, setUser }}>

{ user, setUser } 每次渲染都是一个新对象，即使 user 没变，所有消费者也会重新渲染。改法是用 useMemo 包起来，或者像上面那样拆成多个 Context。

同样道理，一个大 Context 装下全部全局状态，任何字段一变都波及所有人。应该按更新频率和使用范围拆开。真正需要“只订阅状态的某一部分”时，Context 做不到，这就是 Zustand、Redux 这些库的用处，它们基于 useSyncExternalStore 实现了选择器订阅。

什么时候不该用 Context

只隔了两三层的组件，直接传 props 反而更清楚，一眼能看出数据从哪来。

有时还可以用组合绕开传递：中间层不关心数据，就把需要数据的组件作为 children 传进去，数据在外层直接给它。

服务端来的数据，比如列表和详情，最好交给数据请求库，它会处理缓存和失效。手动塞进 Context 就得自己管这些。

常见追问

组件外面没有 Provider，读到的是什么？

读到 createContext(defaultValue) 时传的默认值。上面例子传的是 null，所以没包 Provider 会拿到 null。

use(Context) 和 useContext 有什么区别？

读出来的值一样。区别是 use 可以写在 if 里面条件调用，useContext 是 Hook，只能在顶层调用。
