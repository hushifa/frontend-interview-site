Context 与 useReducer 适合管理什么状态？

Context 负责把某个范围内的值提供给后代，useReducer 负责集中计算状态如何随动作变化。它们可以组合，但 Context 不自动存储数据，reducer 不执行副作用，也不天然等于全局缓存或高性能状态库。

参考答案

Context 与 useReducer 解决的是两个不同问题。Context 让深层组件读取祖先提供的值，减少中间层只为转交而接收 props；useReducer 则把“收到什么动作，下一状态是什么”集中到一个纯函数中。

简单的主题、语言可以只用 Context 配合 state。更新动作多、多个字段需要保持关系时，reducer 更容易把规则组织清楚。它们组合后仍然是组件范围内的状态，不会自动成为跨页面永久存活的全局服务。

用任务列表把数据与动作一起组织

JSX
import { createContext, useContext, useReducer, useState } from 'react';

const TasksContext = createContext(null);
const TasksDispatchContext = createContext(null);

export function tasksReducer(tasks, action) {
  switch (action.type) {
    case 'added':
      return [...tasks, { id: action.id, title: action.title, done: false }];
    case 'toggled':
      return tasks.map(task => task.id === action.id ? { ...task, done: !task.done } : task);
    case 'removed':
      return tasks.filter(task => task.id !== action.id);
    default:
      throw new Error(`未知任务动作：${action.type}`);
  }
}

function TasksProvider({ children }) {
  const [tasks, dispatch] = useReducer(tasksReducer, []);
  return (
    <TasksContext.Provider value={tasks}>
      <TasksDispatchContext.Provider value={dispatch}>
        {children}
      </TasksDispatchContext.Provider>
    </TasksContext.Provider>
  );
}

function useTasks() {
  const tasks = useContext(TasksContext);
  if (tasks === null) throw new Error('任务组件需要 TasksProvider');
  return tasks;
}

function useTasksDispatch() {
  const dispatch = useContext(TasksDispatchContext);
  if (dispatch === null) throw new Error('任务组件需要 TasksProvider');
  return dispatch;
}

function AddTask() {
  const [title, setTitle] = useState('');
  const dispatch = useTasksDispatch();

  function submit(event) {
    event.preventDefault();
    if (!title.trim()) return;
    dispatch({ type: 'added', id: crypto.randomUUID(), title: title.trim() });
    setTitle('');
  }

  return (
    <form onSubmit={submit}>
      <label>任务名称<input value={title} onChange={event => setTitle(event.target.value)} /></label>
      <button type="submit">添加任务</button>
    </form>
  );
}

function TaskList() {
  const tasks = useTasks();
  const dispatch = useTasksDispatch();
  return (
    <ul>
      {tasks.map(task => (
        <li key={task.id}>
          <label>
            <input type="checkbox" checked={task.done}
              onChange={() => dispatch({ type: 'toggled', id: task.id })} />
            {task.title}
          </label>
          <button type="button" onClick={() => dispatch({ type: 'removed', id: task.id })}>删除</button>
        </li>
      ))}
    </ul>
  );
}

function TaskSummary() {
  const tasks = useTasks();
  return <p>共 {tasks.length} 项，完成 {tasks.filter(task => task.done).length} 项</p>;
}

export default function TasksApp() {
  return (
    <TasksProvider>
      <AddTask />
      <TaskSummary />
      <TaskList />
    </TasksProvider>
  );
}

任务名称的编辑草稿只属于 AddTask，因此仍放在局部 state。正式任务列表属于多个组件共同使用的状态，放在共同 Provider 中。完成数量能从 tasks 推导出来，就不再存一份需要手动保持一致的 count。

动作把新增、切换与删除的意图集中表达。ID 在用户提交的事件处理器里生成，reducer 只根据输入返回结果，不读取随机数、不发请求，也不修改原数组。

reducer 是下一状态的计算器

dispatch 把动作交给 React，reducer 计算下一状态。它不会同步改掉当前处理器中已经捕获的 tasks，也不返回一个等待渲染完成的 Promise。

返回下一状态时要保持完整契约。对象状态不能只返回一个零散字段就期待自动浅合并；数组中未修改的项可以共享引用，修改的项则建立新对象。直接 push 原数组再返回原引用，会破坏状态快照和更新判断。

开发检查可能再次调用 reducer 或初始化逻辑，因此它必须保持纯粹。需要服务端保存时，应在合适的事件、数据层或 Effect 中执行，再把结果转换成明确动作，而不是在 reducer 内直接产生副作用。

Context 传递的是值，不是自动存储系统

useContext 读取组件上方最近的对应 Provider。没有 Provider 时才使用 createContext 的默认值；Provider 明确传入 undefined，不会自动改用默认值。

例子用 null 作为缺少 Provider 的信号，让错误更早出现。也可以为主题等场景提供真正合理的默认值，但不应该用一个假的空 dispatch 掩盖 Provider 配置遗漏。

Provider 位于哪里，就决定这份状态能活多久、谁能共享。两个独立 TasksProvider 会有两份任务列表；Provider 卸载后，本地 reducer 状态也不会只因为使用了 Context 就永久保存。

Context 更新与普通父级更新要分别理解

Provider 的 value 通过 Object.is 比较。值发生变化时，读取这个 Context 的消费者需要接收新值，memo 不能阻止它们获得更新的 Context。

把所有状态塞进一个巨大 value 对象，会让只需要一小部分数据的消费者也受到这个 Context 的变化影响。每次渲染都创建新的对象 value，也可能造成不必要的身份变化。可以按职责与变化频率拆分，或者在确有需要时稳定值的引用。

示例把 tasks 与 dispatch 分成两个 Context。dispatch 身份稳定，只派发动作的组件不必订阅 tasks Context 的变化；但这不保证它永远不会因父组件、自己的 state 或其他依赖而渲染。拆分减少的是一类通知来源，不是万能的渲染屏障。

什么情况下不必使用这套组合

只有一两个直接子组件需要的状态，普通 props 通常更清楚。仅为了减少一层传参就引入多个 Context，会增加隐含依赖与测试准备成本。

服务端请求缓存涉及失效、去重、重试和后台刷新；跨标签页同步需要通信和冲突处理；高频外部数据可能需要更细粒度订阅。这些并不由 Context 或 useReducer 自动实现，专门的数据层或外部 store 可能更合适。

选择前先确定数据属于谁、谁需要读取、谁可以发起变化、何时清理或持久化。Context 负责把这份关系提供出去，reducer 负责让更新规则可解释；二者都应服务这个边界，而不是把所有状态一概提升成全局状态。
