Redux 的单向数据流为什么强调 reducer 的纯粹性？

Redux 里状态只能通过 dispatch(action) 改变，reducer 根据旧 state 和 action 算出新 state。reducer 必须是纯函数、不修改原 state，变化才能靠引用比较发现，也才能被记录、重放和测试。Redux Toolkit 用 Immer 让“可变”写法生成不可变更新。

参考答案

简答

Redux 的数据只往一个方向流：组件 dispatch 一个 action，reducer 根据旧 state 和这个 action 算出新 state，store 通知订阅者，组件用选择器读出自己需要的部分，重新渲染。

reducer 必须是纯函数。意思是同样的输入一定得到同样的输出，里面不发请求、不读时间和随机数，也不修改传进来的参数。

为什么这么强调？一是因为 react-redux 靠引用比较判断数据变没变，你原地改了旧 state，引用没变，界面就不更新。二是因为纯函数的结果只取决于输入，每次变化都能被记录、重放和测试。

现在一般用 Redux Toolkit，它的 createSlice 内置了 Immer，可以直接写 state.items.push(x)，Immer 会替你生成新的不可变对象。要注意副作用不能放在 reducer 里，要放进 thunk（createAsyncThunk）或 listener middleware；服务端数据的请求和缓存，推荐用 RTK Query。

原地修改为什么会让界面不更新

先用两个手写的 reducer 对比一下，一个原地改，一个返回新对象：

JavaScript
function badReducer(state, action) {
  if (action.type === 'added') state.items.push(action.payload);
  return state;
}

function goodReducer(state, action) {
  if (action.type === 'added') return { ...state, items: [...state.items, action.payload] };
  return state;
}

const before = { items: [] };
const bad = badReducer(before, { type: 'added', payload: 'a' });
console.log(bad === before); // true
console.log(before.items.length); // 1

const before2 = { items: [] };
const good = goodReducer(before2, { type: 'added', payload: 'a' });
console.log(good === before2); // false
console.log(before2.items.length); // 0

badReducer 确实把数据加进去了，可返回的还是原来那个对象，bad === before 是 true。react-redux 拿新旧引用一比，一样，就认为什么都没变，组件不会重新渲染。而且旧 state 也被改掉了，想回看上一步的状态都找不回来。

goodReducer 返回的是新对象，引用变了，订阅者就知道要更新，旧的 before2 也原封不动。

Redux Toolkit 怎么写

手写展开运算符很繁琐，Redux Toolkit 用 Immer 解决了这个问题：

JavaScript
import { configureStore, createSlice } from '@reduxjs/toolkit';

const bookmarksSlice = createSlice({
  name: 'bookmarks',
  initialState: { ids: [] },
  reducers: {
    toggled(state, action) {
      const id = action.payload;
      const index = state.ids.indexOf(id);
      if (index === -1) state.ids.push(id);
      else state.ids.splice(index, 1);
    },
  },
});

export const { toggled } = bookmarksSlice.actions;

export function makeStore() {
  return configureStore({ reducer: { bookmarks: bookmarksSlice.reducer } });
}

这里的 push、splice 看着是在原地改，其实 state 是 Immer 给的一个草稿。Immer 记下你对草稿做了什么，最后生成一个新的不可变对象，所以结果和 goodReducer 一样。

组件里这样用：

JSX
import { useDispatch, useSelector } from 'react-redux';

function BookmarkButton({ id }) {
  const saved = useSelector((s) => s.bookmarks.ids.includes(id));
  const dispatch = useDispatch();
  return <button onClick={() => dispatch(toggled(id))}>{saved ? '取消收藏' : '收藏'}</button>;
}

为什么用 makeStore() 工厂函数，而不是直接导出一个 store？因为做 SSR 时，每个请求都要创建一个新的 store，否则不同用户会共享同一份状态。

ID 和时间这类不确定的值放在哪

reducer 里不能调用 crypto.randomUUID() 或 Date.now()，可新增待办时确实需要 ID 和创建时间。办法是在创建 action 的时候生成：

JavaScript
const todosSlice = createSlice({
  name: 'todos',
  initialState: [],
  reducers: {
    added: {
      reducer(state, action) {
        state.push(action.payload);
      },
      prepare(text) {
        return { payload: { id: crypto.randomUUID(), text, createdAt: Date.now() } };
      },
    },
  },
});

prepare 在创建 action 时运行，把 ID 和时间放进 payload。reducer 只是把 payload 存进去，本身仍然是确定的。重放同一个 action，得到的 state 完全一样。

派生数据为什么要用选择器

JavaScript
import { createSelector } from '@reduxjs/toolkit';

const selectTodos = (s) => s.todos;
const selectDone = createSelector([selectTodos], (todos) => todos.filter((t) => t.done));

state 里只存原始数据，“已完成的待办”这种派生数据用选择器算。

为什么不在 useSelector 里直接写 s.todos.filter(...)？因为 filter 每次都返回一个新数组，引用每次都不同，组件就会在任何一个 action 之后都重新渲染。createSelector 会记住结果，输入的 todos 没变，就返回上一次的同一个数组。

异步逻辑放在哪

JavaScript
export const fetchTodos = createAsyncThunk('todos/fetch', async (_, { signal }) => {
  const res = await fetch('/api/todos', { signal });
  return res.json();
});

createAsyncThunk 会自动派发 pending、fulfilled、rejected 三个 action，reducer 在 extraReducers 里处理它们。这样请求留在 thunk 里，reducer 依然是纯的。

什么时候该用 Redux

很多组件共享、更新又频繁的客户端状态，并且需要调试工具追踪每一次变化，这时适合 Redux。

如果只是缓存接口数据，用 RTK Query 或 TanStack Query。如果只是少量全局状态，Context、Zustand 更轻。

常见追问

为什么不能在 reducer 里 fetch？

请求是副作用，结果也不确定。记录下 action 再重放的时候，就得不到相同的 state 了。

Immer 有什么限制？

要么修改草稿，要么返回一个新值，两者不能同时做。
