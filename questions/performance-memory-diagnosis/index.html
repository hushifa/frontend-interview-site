前端内存泄漏应该怎样定位？

泄漏就是“不再需要的对象仍然可达，没法被回收”。定位方法是构造可重复的操作闭环（比如打开再关闭面板十次），对比前后两次堆快照，找出数量持续增长的对象，再沿 Retainers 引用链找到是谁留住了它。常见原因是没移除的全局监听、定时器、Observer、订阅和没有上限的缓存。

参考答案

简答

内存泄漏是指一个对象已经用不到了，却还被别的东西引用着，垃圾回收没法回收它。不过内存上涨不一定是泄漏，第一次加载字典、建缓存都是正常增长。要看的是同一个“打开再关闭”的流程重复做几遍以后，回收后的内存基线是不是一直往上抬。

定位用 DevTools 的 Memory 面板。初始化完先拍一张堆快照，然后把这个流程重复 N 次，再拍一张，用 Comparison 视图对比，看哪些构造函数的对象数量随 N 增长。

找到可疑对象以后，看它的 Retainers，也就是谁在引用它，沿着这条引用链一路往上找，通常会找到 window 上的监听器、定时器，或者模块级的数组、Map。

要注意，把 DOM 从页面上移除不等于释放了。只要还有长期存在的引用指向它，比如监听器的闭包、缓存，它就变成 Detached 节点继续占着内存。修复后用同一个流程复测，对象数量不再随次数增长就行，不要求内存精确回到原值。

一个典型的泄漏

下面的面板挂载时给 window 加了 resize 监听，卸载时只把面板从页面上移除了：

JavaScript
function mountPanel(container) {
  const panel = document.createElement('section');
  container.append(panel);

  const onResize = () => {
    panel.dataset.width = String(window.innerWidth);
  };
  window.addEventListener('resize', onResize);

  return () => panel.remove(); // 忘记移除监听，window 通过闭包一直留住 panel
}

面板从页面上消失了，为什么内存还在？因为 window 一直存在，它上面挂着 onResize，onResize 是个闭包，用到了 panel。这条引用链是 window → onResize → panel，所以 panel 一直可达，回收不掉。每打开关闭一次就多留一个，这就是泄漏。

改法是让监听和组件的生命周期一致。这里用 AbortController，卸载时一次性取消：

JavaScript
function mountPanel(container) {
  const panel = document.createElement('section');
  container.append(panel);
  const controller = new AbortController();

  window.addEventListener(
    'resize',
    () => {
      panel.dataset.width = String(window.innerWidth);
    },
    { signal: controller.signal },
  );

  return () => {
    controller.abort(); // 一次性移除所有用这个 signal 注册的监听
    panel.remove();
  };
}

哪些东西需要清理

泄漏的根源几乎都是“注册了，没注销”。下面这些都要在组件卸载时清掉：

来源清理方式
window、document 上的监听removeEventListener 或 AbortSignal
setInterval、setTimeoutclearInterval、clearTimeout
ResizeObserver、IntersectionObserver、MutationObserverdisconnect()
事件总线、状态库订阅调用返回的取消订阅函数
模块级 Map、数组缓存设置容量上限和淘汰策略
URL.createObjectURLURL.revokeObjectURL
WebSocket、媒体流close()、track.stop()

在框架组件里，这些清理写在 useEffect 的返回函数或者 onUnmounted 里。

看快照时要注意什么

快照里每个对象有两个大小。浅大小是对象自己占的大小；保留大小是如果这个对象被回收，总共能释放多少。找泄漏时更该看保留大小，因为一个小对象可能拽着一大片数据。

在类名筛选框里输入 Detached，能找到已经脱离文档的 DOM 节点。它们是线索，但不一定都是泄漏，有的组件是故意缓存起来的。

还有一个坑：控制台里打印过的对象、DevTools 当前选中的元素，也会被留住。所以复测前要清空控制台，否则会把它们误当成泄漏。

如果想知道泄漏的对象是什么时候分配的，可以用 Allocation instrumentation on timeline，它能看到每个时间点分配了哪些至今还活着的对象。

常见追问

闭包一定会导致泄漏吗？

不会。监听器、节点和闭包互相引用也没关系，只要整组都不再可达，垃圾回收能处理循环引用。问题在于有没有长期存在的东西引用着它们，详见《什么是闭包？它有哪些实际应用？》。

WeakMap 能解决缓存泄漏吗？

只适用于以对象为键、希望键被回收时值也跟着回收的场景。它不能替代有容量上限的通用缓存，比如用字符串做键的缓存就用不了 WeakMap。
