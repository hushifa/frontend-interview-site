前端内存泄漏应该怎样定位？

通过增长曲线、堆快照、分离 DOM 和事件监听排查长期页面中的内存泄漏，避免把一次性占用当成泄漏。

参考答案

泄漏表现为执行相同操作后，内存基线持续上升且垃圾回收后也不回落。常见原因包括未清理的事件监听、定时器、Observer、订阅、闭包引用、缓存无限增长和仍被 JavaScript 引用的 DOM。

性能优化先固定场景和指标，再判断瓶颈属于网络、脚本、布局、绘制、内存还是交互延迟。优化前后要使用相同设备、网络和数据量比较，不能只看开发机上的一次耗时。

定位时先重复同一流程并观察内存时间线，再对比堆快照，查看对象保留路径和 detached DOM。快照大小本身不是结论；浏览器缓存、JIT 和一次性资源都可能造成短期波动。

修复要围绕生命周期：组件卸载时取消监听和请求、断开观察器、清理定时器，缓存设置上限和失效策略。修复后要用同一流程复测，确认基线稳定，而不是只看某一次强制回收后的数字。

每个优化都有成本：预加载会增加流量，缓存会增加失效复杂度，虚拟化会改变测量和无障碍行为。上线后还应观察真实用户数据，确认收益没有转移到另一个阶段。

实际优化时先记录基线，再只改一个变量。若首屏变快但首次展开、滚动或弱网体验变差，说明成本只是被推迟；最终要以用户完成任务的时间判断优化是否成立。
