前端内存泄漏应该怎样定位？

泄漏是"不再需要的对象仍然可达，无法被回收"。定位方法是构造可重复的操作闭环（如打开再关闭面板十次），对比前后两次堆快照，找出数量持续增长的对象，再沿 Retainers 引用链找到是谁留住了它。常见原因是未移除的全局监听、定时器、Observer、订阅和无上限的缓存。

参考答案

简答

  • 内存上涨不一定是泄漏：首次加载字典、缓存属于正常增长。要看重复同一个"打开—关闭"流程后，回收后的基线是否持续抬升。
  • 用 Memory 面板：初始化后拍快照，执行 N 次闭环，再拍快照，用 Comparison 视图看哪些构造函数的数量随 N 增长。
  • 选中可疑对象看 Retainers，沿引用链找到根：通常是 window 上的监听器、定时器或模块级的数组、Map。
  • 移除 DOM 不等于释放：只要有长期存活的引用（监听器闭包、缓存）指向它，节点就成了 Detached 节点继续占用内存。
  • 修复后用同一闭环复测，对象数量不再随次数增长即可，不要求进程内存精确回到原值。

典型泄漏

JavaScript
function mountPanel(container) {
  const panel = document.createElement('section');
  container.append(panel);

  const onResize = () => {
    panel.dataset.width = String(window.innerWidth);
  };
  window.addEventListener('resize', onResize);

  return () => panel.remove(); // 忘记移除监听，window 通过闭包一直留住 panel
}

修复：让监听与组件同一生命周期。

JavaScript
function mountPanel(container) {
  const panel = document.createElement('section');
  container.append(panel);
  const controller = new AbortController();

  window.addEventListener(
    'resize',
    () => {
      panel.dataset.width = String(window.innerWidth);
    },
    { signal: controller.signal },
  );

  return () => {
    controller.abort(); // 一次性移除所有用这个 signal 注册的监听
    panel.remove();
  };
}

快照分析要点

  • 浅大小是对象自身的大小，保留大小是该对象被回收后能释放的总大小。
  • 在类名筛选框输入 Detached 可以找到脱离文档的 DOM 节点，它们是线索，不一定都是泄漏（组件可能有意缓存）。
  • 控制台打印过的对象、DevTools 当前选中的元素也会被保留，复测时清空控制台。
  • Allocation instrumentation on timeline 可以看到在哪个时间点分配了哪些仍存活的对象。

常见追问

  • 闭包一定会导致泄漏吗？不会。监听器、节点和闭包互相引用，但整组都不可达时，垃圾回收能处理循环引用。
  • WeakMap 能解决缓存泄漏吗？只适用于以对象为键、希望键被回收时值也跟着回收的场景，不能替代有容量上限的通用缓存。
