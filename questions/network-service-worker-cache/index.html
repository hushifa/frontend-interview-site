Service Worker 缓存更新为什么容易出现旧版本？

理解 install、activate、fetch、缓存版本和 skipWaiting 的关系，设计可回滚的离线资源更新策略。

参考答案

Service Worker 的新脚本下载、安装和激活与已有页面生命周期分开。新 Worker 安装成功后可能等待旧 Worker 控制的页面关闭，缓存版本也需要主动清理，否则用户会继续拿到旧资源。

在“Service Worker 缓存更新为什么容易出现旧版本？”这个问题中，先查看完整请求和响应，再区分连接、协议、缓存、服务端和数据处理问题；重试必须和幂等性一起设计。这里的 Service Worker、Cache Storage、PWA 不是孤立的 API 名称，而是会共同影响输入、过程和最终结果。

网络题可以按请求创建、连接建立、请求发送、响应处理和缓存复用几个阶段分析。调试时应同时查看 URL、方法、请求头、响应头、状态码、重定向和 Timing 面板，不能只看 fetch 是否 resolve。

skipWaiting() 和 clientsClaim() 可以加快接管，但会让同一页面的 HTML、脚本和缓存资源处于不同版本，必须设计兼容协议、刷新提示或原子化资源发布。资源文件使用内容哈希能减少旧文件覆盖，但入口 HTML 和缓存清单仍要同步更新。

缓存策略应区分 HTML、脚本、图片和 API。不要把用户私有响应、错误响应或无限增长的请求全部缓存；要处理配额、失效、离线失败和版本回滚。

缓存、重试、超时和并发控制都要结合业务幂等性设计。前端能改变等待和展示方式，却不能替服务端补上权限、数据一致性或写操作的最终确认。

实际排查接口问题时，先保存一份完整请求和响应，再判断是浏览器策略、连接失败、服务端错误还是数据处理错误。这样可以避免把所有问题都归因于“网络慢”，也方便区分重试是否真的安全。
