Service Worker 有哪些缓存策略？HTML、静态资源和接口分别怎么缓存？

Service Worker 在 fetch 事件里决定每个请求怎么返回。安装时预缓存应用外壳；缓存优先适合带哈希的静态资源；网络优先适合 HTML 入口和要尽量新的数据；先返回缓存再后台刷新适合响应快更重要、稍旧也能接受的内容；POST 和必须最新的数据只走网络。缓存响应前要 clone，只缓存成功的响应。

参考答案

简答

Service Worker 能拦截页面发出的请求，在 fetch 事件里自己决定：从 Cache Storage 拿，还是去网络拿，还是两个都用。MDN 的说法是，缓存策略要在离线可用、响应速度和内容新鲜之间取舍，一个应用通常对不同资源用不同策略。

常用的有这几种。预缓存是在 install 时把应用外壳存好，适合这个版本一定要用、又不会变的文件。缓存优先是先查缓存，没有再去网络并存一份，适合文件名带哈希的 JS、CSS。网络优先是先请求网络，失败了才用缓存，适合 HTML 入口和消息列表这种要尽量新、但旧的总比没有强的内容。

还有一种是先返回缓存、同时在后台请求网络更新缓存，叫 stale-while-revalidate，适合响应快更重要、内容稍旧也能接受的场景。至于 POST 请求，以及商品库存这种宁可失败也不能给旧数据的接口，只走网络。

写的时候要注意两点：Response 的内容只能读一次，存进缓存前要 clone()；只缓存成功的响应，不要把 404、500 也存进去。

先看一个按资源分流的 fetch

下面的 fetch 处理器按请求类型选策略，只处理同源的 GET 请求：

JavaScript
// sw.js
const CACHE = 'static-v42';

async function cacheFirst(request) {
  const hit = await caches.match(request);
  if (hit) return hit;
  try {
    const response = await fetch(request);
    if (response.ok) {
      const cache = await caches.open(CACHE);
      cache.put(request, response.clone());
    }
    return response;
  } catch {
    return Response.error();
  }
}

async function networkFirst(request) {
  try {
    const response = await fetch(request);
    if (response.ok) {
      const cache = await caches.open(CACHE);
      cache.put(request, response.clone());
    }
    return response;
  } catch {
    return (await caches.match(request)) ?? Response.error();
  }
}

self.addEventListener('fetch', (event) => {
  const { request } = event;
  const url = new URL(request.url);
  if (request.method !== 'GET' || url.origin !== self.location.origin) return;

  if (request.mode === 'navigate') {
    event.respondWith(networkFirst(request));
  } else if (url.pathname.startsWith('/assets/')) {
    event.respondWith(cacheFirst(request));
  }
});

没有调用 respondWith() 的请求，比如接口和跨域请求，会按正常方式走网络，Service Worker 不插手。

为什么要 response.clone()？MDN 解释，Response 是流，只能读一次。存进缓存要读一次，返回给页面又要读一次，所以存一份副本，把原件返回。为什么判断 response.ok？fetch 遇到 404、500 也会正常完成，不判断的话，一次服务端出错就会把错误页面缓存下来，之后一直返回它。

缓存优先为什么还要在没命中时去网络？因为缓存可能被浏览器或用户清掉，MDN 也提到了这一点，没有网络回退的话，清过缓存后资源就加载不出来了。

不同资源为什么用不同策略

HTML 入口用网络优先。入口页面里写着当前版本的 JS、CSS 文件名，如果它被缓存优先返回，用户就一直拿到旧页面，新版本的资源也永远不会被请求。断网时再回退到缓存，离线也能打开。

带哈希的静态资源用缓存优先。文件内容一变，构建工具生成的文件名就变，新文件名相当于一个新资源，所以缓存里的旧文件永远不会被当成新内容返回，命中缓存总是对的。

接口数据要看业务。MDN 举的例子是，消息应用的最近消息列表适合网络优先；商品列表过时了会让用户困扰，只走网络更合适；POST 这类请求永远不应该缓存。接口里如果有用户个人数据，还要考虑同一台设备上换账号登录的情况，退出登录时要清掉相关缓存。

stale-while-revalidate 怎样写

这种策略先用缓存快速响应，同时不管有没有命中都去请求网络，拿到新响应后更新缓存，下次访问就是新的了：

JavaScript
async function staleWhileRevalidate(request) {
  const cache = await caches.open(CACHE);
  const networkPromise = fetch(request).then((response) => {
    if (response.ok) cache.put(request, response.clone());
    return response;
  });
  return (await cache.match(request)) ?? networkPromise;
}

缓存更新放在 then 里异步完成，页面不用等网络。代价是用户这一次看到的可能是上一次的内容，所以只适合头像、配置这类稍旧也没关系的资源。

预缓存放什么

install 事件里用 cache.addAll() 预缓存的，应该是这个版本一定会用到、而且不会变的文件，比如应用外壳的 HTML、主 JS 和 CSS。MDN 说明，只要其中一个文件缓存失败，整个安装就失败；反过来，安装成功就说明这些文件都已经在缓存里了。

所以预缓存清单不要放可能 404 的文件，也不要放太多，否则安装慢、容易失败。缓存名带版本号、在 activate 里删掉旧缓存，以及新版本怎样接管页面，见《Service Worker 的安装、激活与缓存更新有哪些坑？》。

常见追问

Service Worker 里的 fetch 会经过 HTTP 缓存吗？

会。Service Worker 里调用 fetch() 也是一次普通请求，同样可能命中 HTTP 缓存。所以网络优先拿到的内容旧，不一定是 Cache Storage 的问题，也要看服务端的 Cache-Control，见《浏览器缓存存放在哪里？请求按什么顺序查找缓存？》。

Workbox 解决了什么？

它把预缓存清单、缓存策略和过期清理这些模板代码封装好了，策略的名字也和上面这些对应。原理一样，出问题时还是按上面的思路排查。
