Service Worker 缓存更新为什么容易出现旧版本？

新的 Service Worker 装好后，默认要等所有旧页面关掉才生效，这期间旧 Worker 继续用旧缓存。再加上缓存名不随版本变、旧缓存没删、引入的脚本被 HTTP 缓存，用户就会长期停在旧版本。

参考答案

简答

Service Worker 是浏览器在页面背后跑的一个脚本，能拦截页面的请求，自己决定从缓存还是网络返回。它的生命周期是 install → waiting → activate。发了新版本，新 Worker 装好后会停在 waiting，只要还有页面被旧 Worker 控制，它就一直等。这期间用户看到的还是旧版本。

更新检测本身也有坑。浏览器会逐字节比对 sw.js。updateViaCache 默认是 imports，意思是 sw.js 本身不走 HTTP 缓存，但 importScripts() 引入的脚本会走。被引入的文件不带版本号，更新就可能不生效。

另外，Cache Storage 和 HTTP 缓存是两套东西，清浏览器缓存清不掉 Cache Storage，必须在代码里删。常规做法是缓存名带版本号，在 activate 时删掉其他版本；HTML 走网络优先，带哈希的静态资源走缓存优先。

skipWaiting() 能让新 Worker 立刻生效，但已经打开的旧页面可能会用新 Worker 去请求已经被删掉的旧资源。所以更稳妥的是提示用户刷新。

一个不容易卡在旧版本的 sw.js

JavaScript
// sw.js
const VERSION = 'v42';
const STATIC_CACHE = `static-${VERSION}`;
const PRECACHE = ['/', '/assets/app.3f9a1c.js', '/assets/app.8b2e.css'];

self.addEventListener('install', (event) => {
  event.waitUntil(caches.open(STATIC_CACHE).then((cache) => cache.addAll(PRECACHE)));
});

self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then((keys) =>
      Promise.all(keys.filter((key) => key !== STATIC_CACHE).map((key) => caches.delete(key))),
    ),
  );
});

self.addEventListener('fetch', (event) => {
  const { request } = event;
  const url = new URL(request.url);
  if (request.method !== 'GET' || url.origin !== self.location.origin) return;

  if (request.mode === 'navigate') {
    // HTML：网络优先，离线时回退缓存
    event.respondWith(fetch(request).catch(() => caches.match('/')));
    return;
  }

  if (url.pathname.startsWith('/assets/')) {
    event.respondWith(caches.match(request).then((hit) => hit ?? fetch(request)));
  }
});

self.addEventListener('message', (event) => {
  if (event.data === 'SKIP_WAITING') self.skipWaiting();
});

每次发版改 VERSION，缓存名就变了。install 时把新资源存进新缓存，activate 时把名字不是当前版本的缓存全删掉。如果缓存名一直不变，旧文件就会永远留在里面。

fetch 里分了两种策略。页面导航是网络优先，有网就拿最新的 HTML，断网才用缓存。/assets/ 下的文件名带哈希，内容不会变，所以缓存优先。

还要注意，它只拦截同源的 GET 请求和明确的静态目录，接口请求一律交给网络，免得把个人数据存进 Cache Storage。

怎么提示用户更新

页面这边监听新 Worker 的状态，装好了就弹个提示：

JavaScript
const registration = await navigator.serviceWorker.register('/sw.js');

registration.addEventListener('updatefound', () => {
  const worker = registration.installing;
  worker.addEventListener('statechange', () => {
    if (worker.state === 'installed' && navigator.serviceWorker.controller) {
      showUpdateBanner(() => worker.postMessage('SKIP_WAITING'));
    }
  });
});

let refreshing = false;
navigator.serviceWorker.addEventListener('controllerchange', () => {
  if (refreshing) return;
  refreshing = true;
  location.reload();
});

为什么要判断 navigator.serviceWorker.controller？因为它存在，说明当前页面已经被一个旧 Worker 控制，这次是更新；不存在就是第一次安装，没必要提示。

用户点了更新，页面给新 Worker 发 SKIP_WAITING，新 Worker 调 skipWaiting() 立刻接管。接管时触发 controllerchange，页面就刷新一次。refreshing 这个标记是防止重复刷新。

出了问题怎么排查

在 DevTools 的 Application → Service Workers 里，可以看到新 Worker 是不是停在 waiting。调试时可以勾选 Update on reload。

在 Application → Cache Storage 里，确认旧版本的缓存有没有被删掉。

线上出了大问题需要紧急下线时，可以部署一个只做清理和 registration.unregister() 的 sw.js，或者返回 Clear-Site-Data: "storage" 响应头。
