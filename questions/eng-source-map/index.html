Source Map 如何帮助定位压缩后代码的错误？

Source Map 把压缩后文件里的行列映射回源码位置。前提是映射、脚本和发布版本来自同一次构建；它只改善调试，不能保密源码，也不修复异常。

参考答案

简答

线上代码压缩以后，报错只会告诉你“第 1 行第 27 列”，根本没法看。Source Map 是一个 JSON 文件，记录了压缩后代码的每个位置对应源码的哪个文件、哪一行、哪一列。

浏览器通过脚本末尾的 //# sourceMappingURL= 注释，或者 SourceMap 响应头找到它，DevTools 就能显示源码。错误监控平台也用它把堆栈还原回源码位置。

前提是映射文件和产物来自同一次构建，所以监控平台要按发布版本上传和匹配。

要注意，公开的 Source Map 一般带着完整源码，谁都能下载，不想公开源码就别部署到公开地址。它只改善调试，不改变代码怎样运行。

Source Map 是怎样还原位置的

先看一段压缩后的代码，末尾的注释告诉浏览器去哪里找映射文件。

JavaScript
// app.3f9a.js（压缩后）
function n(t){return t.map(r=>r*2)}
//# sourceMappingURL=app.3f9a.js.map

映射文件大致长这样：

json
{
  "version": 3,
  "file": "app.3f9a.js",
  "sources": ["src/math.ts"],
  "sourcesContent": ["export function double(list: number[]) { ... }"],
  "names": ["double", "list", "item"],
  "mappings": "AAAA,SAASA,EAAOC,..."
}

sources 列出源文件，names 列出原来的变量名。mappings 是一串经过 Base64 VLQ 编码的数据，记录“生成代码的某个位置，对应第几个源文件的第几行第几列、原名是什么”。

所以报错堆栈里的 app.3f9a.js:1:27，查一下映射就能还原成 src/math.ts:3:12，压缩后的变量名 r 也能还原成 item。

sourcesContent 里放的是源码全文。这就是为什么公开部署 Source Map 等于公开源码。

部署时怎样选

公开部署 .map 并保留注释，任何人都能在 DevTools 里看到源码。

生成 .map 但不部署，只上传到监控平台，线上看不到源码，监控平台仍能还原堆栈。

部署到需要鉴权的内网地址，用 SourceMap 响应头指向它，只有能访问内网的开发者能用。

完全不生成的话，线上错误只能看压缩后的位置。

Vite 的 build.sourcemap 可以设成 true、'inline' 或 'hidden'。'hidden' 会生成 .map 文件，但不在产物里写那行注释，正适合“只上传到监控平台”的做法。

怎样和错误监控配合

构建时生成 Source Map，同时给这次构建一个发布版本号，比如提交哈希。然后把 .map 文件和版本号一起上传到 Sentry 这类平台，再从公开目录删掉。

前端 SDK 上报错误时带上同一个版本号，平台就能按版本找到对应的映射文件，还原堆栈。

版本对不上是最危险的情况。平台可能用错误的映射还原出一个看起来合理、其实完全不对的位置，这比找不到映射更容易误导排查。

常见追问

为什么 DevTools 里还原出来的行号是偏的？

可能是某个构建插件改写代码时，没有生成或传递 Source Map，中间断了一环。也可能部署的 .map 来自另一次构建，跟产物对不上。

生产环境开启 Source Map 会影响性能吗？

浏览器只在打开 DevTools 时才下载映射文件，普通用户不受影响。代价主要是构建时间会略长一点。
