Source Map 的 mappings 字段是怎样记录位置的？

Source Map 是一个 JSON 文件，mappings 用分号分行、逗号分片段，每个片段有 1、4 或 5 个数字，记录生成列号、源文件下标、源码行列号和原名下标。数字存的是相对前一个值的差值，再用 Base64 VLQ 编成短字符，所以文件体积小。

参考答案

简答

线上代码压缩以后，报错只会告诉你“第 1 行第 27 列”。Source Map 是一个 JSON 文件，里面的 mappings 字段像一张对照表，记录压缩后代码的每一段对应哪个源文件、哪一行、哪一列，原来叫什么名字。

这张表按规范分两层组织：分号隔开生成文件的每一行，逗号隔开一行里的每个片段，每个片段有 1、4 或 5 个数字，分别是生成列号、源文件下标、源码行号、源码列号和原名下标。

为了让文件变小，数字存的是相对前一个值的差值，再用 Base64 VLQ 编码：每个字符 6 位，最高位表示后面还有没有字符，第一个字符的最低位表示正负。所以小数字只占一个字母。

要注意，sourcesContent 字段放的是源码全文，公开部署映射文件就等于公开源码；线上怎样只给监控平台用，是另一个问题。

Source Map 是怎样还原位置的

先看一段压缩后的代码，末尾的注释告诉浏览器去哪里找映射文件。

JavaScript
// app.3f9a.js（压缩后）
function n(t){return t.map(r=>r*2)}
//# sourceMappingURL=app.3f9a.js.map

映射文件大致长这样：

json
{
  "version": 3,
  "file": "app.3f9a.js",
  "sources": ["src/math.ts"],
  "sourcesContent": ["export function double(list: number[]) { ... }"],
  "names": ["double", "list", "item"],
  "mappings": "AAAA,SAASA,EAAOC,..."
}

sources 列出源文件，names 列出原来的变量名。mappings 是一串经过 Base64 VLQ 编码的数据，记录“生成代码的某个位置，对应第几个源文件的第几行第几列、原名是什么”。

mappings 这串字母是怎样组织的

ECMA-426 规范规定了 mappings 的结构：分号 ; 隔开生成文件的每一行，逗号 , 隔开同一行里的每个片段（segment），每个片段由 1、4 或 5 个数字组成。

这几个数字依次是：生成代码里的列号；源文件在 sources 里的下标；源码里的行号；源码里的列号；变量原名在 names 里的下标。全部从 0 开始计数。只有 1 个数字的片段表示这段生成代码没有对应的源码，有 5 个数字时才带原名。

为什么不直接写 0,0,2,11,2 这样的明文数字？因为一个压缩文件有成千上万个片段，明文太占地方。所以规范用了两个办法压缩体积。

第一个办法是存差值。生成列号相对同一行上一个片段，每到新的一行重新从 0 算；其余几个字段相对它在前面最后一次出现的值，跨行也不重置。相邻片段的位置通常很接近，差值是很小的数字。

第二个办法是 Base64 VLQ 编码，把小数字变成很短的字符。

Base64 VLQ 怎样把数字变成字母

VLQ 是“可变长度数量”，小数字占一个字符，大数字占几个字符。规范的定义是：每个 Base64 字符代表 6 位，最高位（第 6 位）是继续位，为 1 表示后面还有字符；剩下 5 位存数值，先存低位；第一个字符的最低位是符号位，为 1 表示负数。

下面按这个定义写一个解码函数，看看样例里的片段代表什么：

JavaScript
const chars = 'ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/';

function decodeSegment(text) {
  const values = [];
  let value = 0;
  let shift = 0;
  for (const ch of text) {
    const digit = chars.indexOf(ch);
    value += (digit & 31) << shift;
    if (digit & 32) {
      shift += 5;
    } else {
      values.push(value & 1 ? -(value >> 1) : value >> 1);
      value = 0;
      shift = 0;
    }
  }
  return values;
}

console.log(decodeSegment('AAAA').join(',')); // 0,0,0,0
console.log(decodeSegment('SAASA').join(',')); // 9,0,0,9,0
console.log(decodeSegment('D').join(',')); // -1
console.log(decodeSegment('gB').join(',')); // 16

AAAA 是第一个片段，四个数都是 0：生成代码第 0 列，对应第 0 个源文件第 0 行第 0 列。SAASA 是差值，意思是往后挪 9 列，源码列也往后挪 9 列，并带上 names 里的第 0 个名字。

D 为什么是 -1？D 在字母表里是 3，二进制 000011，继续位是 0，最低位 1 表示负数，去掉符号位剩下 1，所以是 -1。gB 是两个字符：g 是 32，继续位为 1、数值位为 0；B 是 1，左移 5 位得到 32，再去掉符号位就是 16。

所以浏览器查找一个报错位置时，就按行、按片段把差值累加起来，找到这一列对应的源文件、行列号和原名。

浏览器从哪里找到映射文件

ECMA-426 规定了两个入口：产物末尾的 //# sourceMappingURL= 注释，或者 SourceMap 响应头。两者都有时以响应头为准。

sourcesContent 里放的是源码全文，所以公开部署带 sourcesContent 的映射文件，等于公开源码。生产环境怎样生成 hidden source map、按版本上传给监控平台还原堆栈、又不把映射文件公开，见《线上报错怎样用 Source Map 还原，又不把 map 文件公开？》。

常见追问

为什么 DevTools 里还原出来的行号是偏的？

可能是某个构建插件改写代码时，没有生成或传递 Source Map，中间断了一环。也可能部署的 .map 来自另一次构建，跟产物对不上。

为什么列号要从同一行重新算，其他字段却不重置？

规范就是这样定义的：生成列号在每个分号之后重新从整数值开始，源文件下标、源码行列号和原名下标则一直相对上一次出现的值。规范没有解释原因；实际效果是每行开头的列号是个小整数，源码位置则能接着上一行的值算差值。
