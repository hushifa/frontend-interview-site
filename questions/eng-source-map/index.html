Source Map 如何帮助定位压缩后代码的错误？

Source Map 把生成文件中的行列映射回源码位置，前提是映射、脚本和发布版本来自同一次构建；它改善调试，不是源码保密或异常修复机制。

参考答案

简答

  • Source Map 是一个 JSON 文件，记录压缩后代码的每个位置对应源码的哪个文件、哪一行哪一列。
  • 浏览器通过脚本末尾的 //# sourceMappingURL= 注释或 SourceMap 响应头找到它，DevTools 据此显示源码。
  • 映射只有在和对应的产物来自同一次构建时才准确，错误监控平台要按发布版本上传和匹配。
  • 公开的 Source Map 通常包含完整源码（sourcesContent），任何人都能下载，不想公开源码就不要部署到公开地址。
  • 它只改善调试体验，不改变代码的运行行为。

原理

JavaScript
// app.3f9a.js（压缩后）
function n(t){return t.map(r=>r*2)}
//# sourceMappingURL=app.3f9a.js.map
json
{
  "version": 3,
  "file": "app.3f9a.js",
  "sources": ["src/math.ts"],
  "sourcesContent": ["export function double(list: number[]) { ... }"],
  "names": ["double", "list", "item"],
  "mappings": "AAAA,SAASA,EAAOC,..."
}

mappings 用 Base64 VLQ 编码记录"生成位置 → 源文件索引、源码行列、原名称"。报错堆栈里的 app.3f9a.js:1:27 经过查找，就能还原成 src/math.ts:3:12，变量名也能还原为 item。

部署方式的选择

方式效果
公开部署 .map 并保留注释任何人都能在 DevTools 看到源码
生成 .map 但不部署，只上传到监控平台线上看不到源码，监控平台能还原堆栈
部署到需要鉴权的内网地址，用 SourceMap 头指向它只有能访问内网的开发者能用
不生成线上错误只能看压缩后的位置

Vite 的 build.sourcemap 可选 true、'inline'、'hidden'。'hidden' 生成 .map 文件但不在产物中写入注释，适合"只上传到监控平台"的方案。

和错误监控配合

  1. 构建时生成 Source Map，并给这次构建一个发布版本号（如提交哈希）。
  2. 把 .map 文件和版本号一起上传到 Sentry 等平台，然后从公开目录删除。
  3. 前端 SDK 上报错误时带上同一个版本号。
  4. 平台按版本找到对应的映射文件，还原堆栈。

版本对不上时，平台可能用错误的映射还原出看似合理却完全错误的位置，比找不到映射更容易误导排查。

常见追问

  • 为什么 DevTools 里还原的行号偏了？可能是某个构建插件改写代码时没有生成或传递 Source Map，或者部署的 .map 来自另一次构建。
  • 生产环境开启 Source Map 会影响性能吗？浏览器只在打开 DevTools 时才下载映射文件，普通用户不受影响；构建时间会略有增加。
