Playwright fixtures 解决了什么测试维护问题？

fixture 把测试需要的准备和清理封装在一起，测试按名字声明依赖，Playwright 只在需要时创建，并在 await use() 之后自动清理。test 作用域每个测试一份，worker 作用域在同一工作进程内共享。

参考答案

简答

测试函数参数里写的 page、context、request，其实都是 fixture。fixture 就是测试要用的一份准备好的东西，Playwright 负责创建它、交给测试、用完再清理，每个测试拿到的都是全新的一份。

自己写 fixture 用 test.extend。在 fixture 函数里，await use(value) 之前写准备，之后写清理，就算测试失败了，清理也会执行。

它的好处是按需创建：测试参数里没写的 fixture 不会被初始化。fixture 之间还可以互相依赖，Playwright 按依赖顺序创建，按相反顺序拆除。

默认每个测试一份。加上 { scope: 'worker' }，同一个工作进程里的测试就共享一份，适合启动成本高、测试又不会去改的资源，比如只读的测试账号；会被修改的数据还是要用 test 作用域。

自定义一个 fixture

下面的 todo fixture 在测试前通过接口建一条任务，测试结束后再删掉它：

TypeScript
import { test as base, expect } from '@playwright/test';

type Fixtures = {
  todo: { id: string; title: string };
};

export const test = base.extend<Fixtures>({
  todo: async ({ request }, use) => {
    const response = await request.post('/api/test/todos', {
      data: { title: '测试任务' },
    });
    const todo = await response.json();

    await use(todo);

    await request.delete(`/api/test/todos/${todo.id}`);
  },
});

test('完成任务', async ({ page, todo }) => {
  await page.goto(`/todos/${todo.id}`);
  await page.getByRole('checkbox', { name: todo.title }).check();
  await expect(page.getByText('已完成')).toBeVisible();
});

await use(todo) 这一行把任务交给测试，然后停在这里等测试跑完，测试结束后才继续执行下面的删除。

和 beforeEach 里创建、afterEach 里删除相比，好处在哪？一是准备和清理写在同一个地方，不会只改了一半。二是只有参数里写了 todo 的测试才会去创建它，其他测试不受影响。

worker 作用域怎样共享资源

“工作进程”是 Playwright 并行跑测试时开的进程，每个进程依次执行分给它的测试。

TypeScript
export const test = base.extend<{}, { account: { email: string } }>({
  account: [
    async ({}, use, workerInfo) => {
      const email = `user-${workerInfo.workerIndex}@test.local`;
      await createAccount(email);
      await use({ email });
      await deleteAccount(email);
    },
    { scope: 'worker' },
  ],
});

这里每个工作进程用 workerIndex 建一个自己的账号，并行的进程之间互不干扰。同一个进程里的测试是一个接一个串行跑的，它们共享这个账号，所以不能有哪个测试去改它的状态，否则后面的测试会受影响。

自动 fixture

给 fixture 加上 { auto: true }，它会对每个测试自动运行，测试不声明也会跑。适合放统一的日志收集，或者在测试失败时附加额外的信息。

什么时候用普通函数就够了

如果只是封装一组操作，比如“填写登录表单”，写个普通函数或页面对象就行。只有需要生命周期管理，也就是创建了就必须清理，或者要按作用域在多个测试间共享时，才值得写成 fixture。

常见追问

登录状态怎样复用？

常见做法是写一个 setup 项目，登录一次后把 storageState 保存成文件，其他项目在配置里引用这个文件。需要多个角色时，每个角色各保存一个文件。
