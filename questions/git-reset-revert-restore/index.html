git reset、revert 和 restore 有什么区别？

reset 移动当前分支指向的提交，并按 --soft、--mixed、--hard 决定是否同时重置暂存区和工作区；revert 新增一个反向提交来撤销旧提交，不改写历史；restore 只恢复文件内容，不移动分支。已推送到共享分支的提交应使用 revert。

参考答案

简答

这三个命令都叫“撤销”，但撤的东西不一样。git reset <提交> 是把当前分支挪到指定的提交上。--soft 只挪分支，暂存区和工作区都不动；默认的 --mixed 还会重置暂存区，但保留工作区；--hard 三个都重置，没提交的修改会丢。

git revert <提交> 不挪分支，而是新建一个提交，内容正好是旧提交的反向修改。原来的提交还在历史里，所以适合已经推送到共享分支的情况。

git restore 只管文件，不移动分支。默认用暂存区的内容恢复工作区，加 --staged 用 HEAD 恢复暂存区，--source 可以指定从哪个提交取文件。

要注意，reset 改的是本地分支指针。如果被挪走的提交已经推送过，再推送就得强制覆盖远端，会影响其他协作者。

先分清三个位置

Git 的撤销都围绕三个位置：HEAD 指向的提交、暂存区（也叫 index，就是 git add 之后放的地方）、工作区（你正在编辑的文件）。分清一个命令改动了哪几个位置，就分清了这几个命令。

命令移动分支暂存区工作区
reset --soft是不变不变
reset --mixed是重置不变
reset --hard是重置重置
revert新增提交写入反向修改写入反向修改
restore否仅 --staged 时默认

reset 适合整理本地提交

提交还只在本地时，reset 很适合用来整理：

bash
# 撤销最近一次提交，修改仍在暂存区，可以直接重新提交
git reset --soft HEAD~1

# 撤销最近一次提交和暂存，修改留在工作区
git reset HEAD~1

# 丢弃最近两次提交以及工作区的未提交修改
git reset --hard HEAD~2

--hard 丢掉的已提交内容，通常还能通过 reflog 找回，做法见《误删分支或 reset --hard 之后怎样用 reflog 找回提交？》。可是工作区里从来没提交过的修改，不在任何提交里，reflog 也找不回来。

如果担心 --hard 把本地修改冲掉，可以用 git reset --keep HEAD~1。它同样会移动分支、更新工作区，但会保留和这次移动无关的本地修改；如果某个有本地修改的文件也在被撤销的提交里，它会报错停下，不去覆盖。

还有一个后悔药。reset、merge、rebase 这些操作会把移动之前的位置记在 ORIG_HEAD 里。刚 reset 完就想撤回，git reset --hard ORIG_HEAD 能直接回到原位。

revert 适合撤销已经推送的提交

bash
git revert --no-edit HEAD

执行后，历史里多了一个 Revert "..." 提交，文件回到被撤销的那个提交之前的样子。因为它没删任何历史，只是往后加了一个提交，所以可以照常推送；想恢复的话，再 revert 一次这个 revert 提交就行。

撤销合并提交时要加 -m 1，告诉 Git 以哪个父提交为主线。合并提交有两个父提交，不指定的话，Git 不知道“反向修改”该相对哪一边算。

restore 只管文件

git restore 从 Git 2.23 开始提供，把原来 git checkout 里恢复文件的那部分功能单独拿了出来：

bash
git restore src/app.ts            # 放弃工作区修改，回到暂存区的内容
git restore --staged src/app.ts   # 取消暂存，工作区修改保留
git restore --source=HEAD~3 src/app.ts  # 取回三个提交之前的文件内容

被 git restore 覆盖掉的工作区修改没提交过，是找不回来的，执行前要想清楚。

常见追问

已经推送的提交能不能 reset？

技术上可以，但推送时要用 --force-with-lease 强制覆盖，其他人基于旧历史的提交就会和远端分叉。共享分支上应该用 revert。

git reset <文件> 和 git restore --staged <文件> 效果一样吗？

一样，都会让这个文件的暂存内容回到 HEAD 的版本，工作区不变。

线上发布出了问题，revert 就够了吗？

不够。源码回滚以后还要重新构建和发布，线上才会恢复，参见《静态网站发布失败时怎样安全回滚？》。
