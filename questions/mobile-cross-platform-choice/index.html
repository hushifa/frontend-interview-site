小程序跨端和 App 跨端怎样整体选型？Taro、uni-app、Flutter、React Native 各适合什么？

先看产品要落在哪：只做微信等宿主里的小程序，用原生小程序开发；要同时出多家小程序和 H5，用 Taro（React、Vue 写法）或 uni-app（Vue 写法）编译到多端；要独立的 Android、iOS 应用，选 Flutter 或 React Native，它们出的是真正的 App。Taro、uni-app 也能出 App，但平台差异要靠条件编译和各平台专门的写法处理。再看团队技术栈和对原生能力、界面一致性的要求。

简答

公司要做一个外卖产品，问“用小程序、Taro、uni-app 还是 Flutter、React Native”，其实是先问产品落在哪：只在微信里、要同时上多家小程序和 H5，还是要一个用户下载安装的独立 App。小程序跑在微信这类宿主 App 里，不用安装，靠分享和扫码获客；Flutter 和 React Native 做出来的是真正的 Android、iOS 应用。

两类跨端解决的问题不同。Taro 和 uni-app 是“小程序跨端”：用 React、Vue 这类熟悉的写法写一份代码，编译成微信、支付宝、抖音等多家小程序和 H5，也能出 App。Flutter 和 React Native 是“App 跨端”：Flutter 用自己的引擎绘制界面，React Native 运行时创建平台原生视图，目标是一套代码覆盖 Android 和 iOS。

所以选型可以这样排：只做微信小程序、功能轻，用原生小程序开发最直接；要上好几家小程序加 H5，团队写 React 选 Taro，写 Vue 选 uni-app；核心是独立 App，团队熟悉 React 选 React Native，看重各平台界面一致、愿意学 Dart 选 Flutter。

要注意，跨端框架是在各平台能力之上做转换，平台独有的组件和 API 仍要写条件分支，跨的平台越多，能共用的部分越少。小程序还受宿主平台的审核、包体积和 API 限制。

两类跨端各自在解决什么

小程序跨端。 国内的小程序不止微信一家，支付宝、百度、抖音、QQ 等都有自己的小程序平台，写法相近又不完全相同。Taro 的 README 说它是“开放式跨端跨框架解决方案”，支持用 React、Vue 等框架开发微信、京东、百度、支付宝、字节跳动、QQ 小程序以及 H5、React Native 应用。uni-app 官方文档说它是“使用 Vue.js 开发所有前端应用的框架”，用“vue 语法 + 微信小程序 api”，一份代码可以发布到 iOS、Android、鸿蒙 Next、Web 和微信、支付宝、百度、抖音、飞书、QQ、快手、钉钉、淘宝、京东、小红书等小程序。

App 跨端。 Flutter 官方架构文档说，它绕开系统的 UI 控件库，用自己的控件集，用 Impeller 引擎绘制，发布时编译成 x64 或 ARM 机器码，所以各平台外观一致。React Native 官方文档的说法是：你用 JavaScript 写 React 组件，运行时 React Native 创建对应的 Android 和 iOS 视图，外观、手感和其他原生应用一样；新架构从 0.76 起在所有项目中默认开启。

两类的出发点不同。Taro、uni-app 的主战场是小程序，出 App 是附加能力；Flutter、React Native 的主战场是 App，不能直接出小程序。

小程序为什么要单独考虑

微信官方文档说明，小程序把脚本和渲染分开在不同线程，分别叫逻辑层和视图层。视图层用 WebView 渲染，逻辑层用单独的 JS 运行时，每个页面一个 WebView；基础库内嵌在微信客户端里，不同版本的客户端运行不同版本的基础库。

这决定了小程序的边界：没有 DOM 和 BOM，只能用宿主提供的组件和 API，宿主不支持的能力就做不了，发布要过宿主平台审核。所以 Web 代码不能原样搬进小程序，跨端框架要把 React、Vue 的写法转换成小程序能运行的结构。Web、小程序和跨端框架的运行边界见《Web、微信小程序和跨端框架的运行边界有什么不同？》。

平台差异怎样处理

跨端框架都承认平台之间有差别，并提供写差异代码的办法。uni-app 用条件编译，在注释里写平台名，编译到别的平台时这段代码会被去掉：

JavaScript
// #ifdef MP-WEIXIN
wx.requestSubscribeMessage({ tmplIds: ['模板 ID'] });
// #endif

// #ifdef H5
showSiteNotice(); // 网页端改用其他提醒方式
// #endif

#ifdef 表示只在这个平台保留，#ifndef 表示除了这个平台都保留，MP 代表所有小程序，H5（文档推荐写 WEB）代表网页，APP 代表 App。文档还提醒，平台名写错时 #ifdef 里的代码不会生效，#ifndef 里的反而会生效。

这类分支写得越多，“一套代码”的收益就越小。所以选型时要先列出各端都需要、又各端实现不同的功能，比如登录、支付、分享、订阅消息，估计条件分支有多少。

什么情况下选哪一个

先看业务渠道。用户主要从微信群、公众号、扫码进来，用完即走，小程序门槛最低；只做微信一家时，原生小程序开发最直接，没有转换层。要同时上好几家小程序，或者小程序和 H5 共用代码，才值得引入 Taro、uni-app。

再看要不要独立 App。用户要长期使用、需要推送、后台运行、深度调用硬件，就要独立 App，这时 Flutter 和 React Native 是主力选项。团队以 React 为主，React Native 的组件写法、Hooks 都能沿用；团队愿意用 Dart，又看重各平台界面一致、动画流畅，Flutter 更合适。

两者都要时，常见做法是分开选：App 用 Flutter 或 React Native，小程序单独做或用 Taro、uni-app。App 和网页版怎样共用代码，见《Flutter、React Native 和 Web 跨端怎么选？一套代码能同时跑在 App 和浏览器里吗？》。技术选型怎样在面试里讲，见《面试官问“为什么选这个技术栈”，应该怎样回答技术选型？》。

常见追问

Flutter 的性能一定比 React Native 好吗？

不能这样一概而论。Flutter 发布时编译成机器码、自己绘制，避开了和系统控件之间的转换；React Native 新架构也改进了 JS 和原生之间的通信，能同步读取布局。实际性能更多取决于列表、图片、动画怎么写，要用真机和具体页面去测。

Taro 和 uni-app 怎么选？

先看团队写什么。Taro 支持 React 和 Vue 等框架，React 团队能沿用熟悉的组件写法；uni-app 基于 Vue，API 风格沿用微信小程序。再对照两者官方文档列出的目标平台，确认要上的每一家小程序都在支持范围内。

已有原生 App，能逐步引入跨端吗？

可以。Flutter 文档专门有“把 Flutter 嵌入现有应用”的方式，React Native 也支持集成到已有的原生应用。常见做法是先把一两个独立的页面用跨端实现，验证稳定后再扩大范围。
