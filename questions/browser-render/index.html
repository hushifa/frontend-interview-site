浏览器从 HTML 到页面显示，经历哪些主要步骤？

把字节解析、DOM 与样式、布局、绘制、栅格化和合成串成完整过程，并解释资源阻塞、脚本修改、帧更新和用户看到画面之间的关系。

参考答案

浏览器拿到 HTML，并不是把源码直接“画”到屏幕上。它需要先弄清文档有哪些节点、每个节点用什么样式、占多大空间、画在哪里，再生成并显示像素。

可以用下面的主线理解，但不要把它想成每次修改都必须完整重做的固定流水线：

text
HTML 字节 → 解析成 DOM
CSS 资源 → 解析规则并参与样式计算
                 ↓
      确定布局盒子与几何位置
                 ↓
      生成绘制记录 → 栅格化为像素
                 ↓
      合成、提交并显示画面

实际浏览器会并行下载、渐进解析、复用已有结果，也可能在不同线程或进程分担工作。具体内部树结构和线程划分因实现而异，但这些阶段分别解决的问题是相通的。

解析阶段：从文本建立可操作的文档

HTML 响应可以分批到达，浏览器解码后进行标记解析和树构建，逐步生成 DOM，不必总等整个文件下载完才开始处理。解析器也会按照 HTML 规则纠正或补充结构，所以 DOM 未必与手写源码逐字对应，例如隐含元素或不合法嵌套可能被重新组织。

发现外部样式、脚本、图片等资源时，浏览器会安排获取。预加载扫描等机制还可能提前发现后续资源，减少单纯等待主解析器带来的延迟，但无法自动知道所有运行时才拼出的 URL。

遇到普通、没有 async/defer 的外部经典脚本时，HTML 解析可能等待脚本获取与执行，因为脚本能够读取甚至改变后续文档处理。defer、async 和模块脚本有各自的时机与依赖规则，不能只说“所有 JavaScript 都阻塞页面”，也不能说“脚本异步下载就绝不会影响主线程”。

CSS 下载通常不会直接让 HTML 解析器停止构建整个 DOM，但关键样式可能阻塞渲染，某些需要已解析样式的脚本执行也会等待它。于是 CSS、脚本和 HTML 解析之间会形成间接的等待关系。

样式计算：确定每个元素应该是什么样

CSS 规则解析后，浏览器根据选择器匹配、层叠、继承和默认样式等规则，确定元素的计算样式。这里解决的是“字体、颜色、display、宽度规则是什么”，还不等于每个盒子的最终坐标都已算好。

DOM 节点和最终参与布局的盒子不是严格一一对应。display: none 的子树不参与正常的盒子布局；visibility: hidden 通常仍保留布局空间；伪元素和匿名盒子又可能参与渲染，却不是普通 DOM 子元素。

面试中常说的“DOM + CSSOM 生成渲染树”是有帮助的概括，但不要由此推导“一个 DOM 节点一定对应一个合成层”或“不可见的东西就完全没有布局成本”。是否需要布局，还要看具体隐藏方式和浏览器的跳过机制。

布局：求出盒子的大小和位置

布局也常被称为 layout 或 reflow。浏览器要结合父子约束、文本换行、字体度量、Flex/Grid 算法和视口等信息，确定盒子的几何结果。

比如容器变窄，段落需要重新换行，高度可能随之增加，下面的元素位置也要调整。图片没有预留尺寸时，下载后得知固有大小，也可能改变后续布局。字体替换同样可能改变字宽和换行。

布局不一定每次影响整个文档。浏览器会尝试缩小受影响范围，CSS containment 等机制也能在符合条件时帮助隔离工作。但某些相互依赖的尺寸和布局结构仍可能让修改波及很多元素，不能仅凭改了一个 style 就判断成本很小。

绘制和栅格化：从几何结果到像素

有了位置，还需要决定文字、背景、边框、阴影、裁剪等如何按顺序画出来。绘制阶段可以理解为组织绘图记录或指令；栅格化再把相应内容转换成可显示的像素，例如保存到纹理或瓦片中。

这种区分解释了为什么“没有重新布局”也可能昂贵：一个占满屏幕的复杂阴影或绘制效果，即使尺寸不变，也可能需要很多绘制和像素处理。

实现可能把不同部分交给 CPU、GPU 或其他工作线程，不能简单说“paint 都由 CPU 做，composite 都由 GPU 做”就覆盖所有浏览器。资源大小、瓦片划分、图像解码和设备能力都会影响实际成本。

合成：把已有内容组织成最终画面

浏览器可把部分内容分别保存，再根据位置、变换、透明度、裁剪等关系合成画面。如果一个动画能只调整已有内容的合成属性，就可能避免每帧重新布局和绘制，并在合适条件下减少对主线程的依赖。

因此 transform、opacity 常用于动画。但不是所有这类变化都自动成为“纯合成动画”，也不是合成层越多越好：创建和维护层需要内存与管理成本，大纹理还会带来栅格化、上传和带宽压力。

will-change 是提示浏览器准备潜在变化，不是强制硬件加速开关。给大量元素长期设置它，可能浪费资源。是否真正减少了工作，应看当前页面的渲染记录和目标设备表现。

JavaScript 修改 DOM，不等于屏幕马上刷新

脚本修改文本或样式后，DOM 中的新值可能已经可读，但浏览器通常会把相应渲染工作合并到合适的更新机会。如果在同一个同步任务里先显示“处理中”，紧接着进行长时间计算，最后改成“完成”，用户可能一直看不到中间状态。

这不是文字赋值失败，而是主线程尚未给渲染留出合适机会。只加 await Promise.resolve() 也不能保证中间发生一次绘制，因为微任务仍可能在渲染之前连续执行。

requestAnimationFrame() 让回调靠近一次渲染更新执行，适合动画读写的时序协调；但回调本身通常仍在该次画面绘制之前。把巨大计算放进 rAF，照样可能拖延这一帧。处理计算量要靠减少工作、分片让出或 Worker，而不是只更换一个调度 API。

一次更新会走到哪一步，要看它改变了什么

改动可能涉及的工作
改变段落宽度样式、换行与布局，随后可能重新绘制
改变文字颜色样式和相应绘制，通常不改变几何布局
合适条件下的 transform 动画可能主要复用已有内容进行合成
插入大量节点DOM、样式、布局及绘制，影响范围依结构而定

这些是理解成本的方向，不是逐属性的绝对承诺。浏览器有优化和依赖分析，同一种属性在不同结构中可能触发不同工作。

分析实际页面时，在 Performance 时间线中对齐脚本、样式计算、Layout、Paint 和帧呈现，先找耗时最大的阶段。还要结合 LCP、INP、CLS 等用户体验指标：DOM 构建完成、load 触发、某个请求下载结束，都不能单独证明用户已看到稳定且可交互的页面。
