前端怎样进行读屏器和辅助技术的实际验收？

自动化工具（axe 等）只能发现一部分可机器判断的问题；上线前还要用键盘、读屏、放大和减少动态效果实际走一遍关键流程，并把结果记录成可复现的验收项。

参考答案

简答

  • 自动化检查能发现缺失 alt、对比度不足、无名称按钮、ARIA 属性错误等，但无法判断名称是否有意义、焦点顺序是否合理、播报是否及时。
  • 在 CI 中用 axe（例如 @axe-core/playwright）扫描关键页面的主要状态，防止明显问题回归。
  • 人工验收至少覆盖：只用键盘完成流程、读屏走一遍、放大到 200% 和 400%、开启减少动态效果。
  • 读屏组合各有差异，常用的是 Windows 上 NVDA + Chrome/Firefox、macOS 和 iOS 上 VoiceOver + Safari、Android 上 TalkBack + Chrome。
  • 每个问题要记下环境、操作步骤、实际播报和期望结果，便于修复后复测。

自动化扫描

TypeScript
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('设置页没有可自动检测的无障碍问题', async ({ page }) => {
  await page.goto('/settings');
  await page.getByRole('button', { name: '高级选项' }).click();

  const results = await new AxeBuilder({ page })
    .withTags(['wcag2a', 'wcag2aa', 'wcag22aa'])
    .analyze();

  expect(results.violations).toEqual([]);
});

先打开弹窗、展开面板，再扫描，否则只检查了默认状态。确实需要暂时忽略的规则，写明原因和负责人，不要整体关闭。

  • 局部扫描（.include() 某个组件）噪声少、定位快；整页扫描才能发现标题层级、地标和重复 ID 等问题，两者不能互相替代。
  • results.incomplete 里是工具无法自动判断的项，例如部分对比度检查，同样要人工处理。
  • 有 alt 不代表替代文本正确，结构扫描也看不出"点击这里""失败"这类文案是否有用。
  • 不要为了消除警告随意加 ARIA，错误的角色或状态可能比没有 ARIA 更难用。

人工检查清单

键盘

  • Tab 顺序和视觉顺序一致，所有操作都能用键盘完成。
  • 焦点始终可见，不被固定头部遮挡（WCAG 2.4.11）。
  • 弹窗打开时焦点进入，关闭后回到触发按钮。
  • 只有模态对话框需要限制焦点；非模态提示、下拉菜单和组合框各有自己的键盘规则，不要统一套焦点陷阱。

读屏

  • 按标题和地标导航能理解页面结构。
  • 每个控件读出名称、角色和状态，例如“通知，开关，已打开”。
  • 加载完成、保存成功、校验错误能被播报。

视觉

  • 放大到 400% 时内容不需要横向滚动就能阅读（WCAG 1.4.10）。
  • 增大文字间距后内容不重叠、不截断（WCAG 1.4.12）。
  • 开启减少动态效果后没有大幅移动的动画。

什么时候找真实用户

自己用读屏和长期依赖读屏的用户差别很大。核心流程（注册、支付）发布前，邀请使用辅助技术的用户参与测试，能发现清单覆盖不到的问题。

常见追问

  • axe 报告零问题就算符合 WCAG 吗？不算。自动化能覆盖的成功准则有限，符合性需要人工评估，结论要写明测试范围和环境。
