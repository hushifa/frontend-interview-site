如何用可辨识联合避免不合理的状态组合？

给每种状态一个固定的标签字段，比如 status，每种状态只带自己需要的数据，就不会出现“加载中同时又出错”这种组合。按标签 switch 时 TypeScript 会自动缩小类型。

参考答案

简答

拿请求状态举例，很多人会写三个布尔值 isLoading、isSuccess、isError。三个布尔值有 8 种组合，可合法的只有几种，比如“加载中同时又成功”就说不通。可辨识联合的做法是把合法的状态一个个列出来，其他组合根本写不出来。

具体是给每个分支一个字面量类型的标签字段，比如 status: 'success'，这个字段叫判别字段。每个分支只带自己需要的数据，success 分支一定有 data，error 分支一定有 error。

好处是按判别字段 switch 或 if 以后，TypeScript 会把整个对象缩小到对应分支，不用再写 data!。在 default 里把值传给参数类型是 never 的函数，以后新增分支却漏处理了，编译就会报错。

要注意的是，联合只描述“哪些形态合法”，不管状态怎么切换。比如旧请求的结果覆盖了新请求，这种竞态还得靠请求 ID 或取消请求来解决。

用联合描述请求状态

TypeScript
type RequestState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: Error };

function assertNever(value: never): never {
  throw new Error(`未处理的状态：${JSON.stringify(value)}`);
}

function describe(state: RequestState<readonly string[]>): string {
  switch (state.status) {
    case 'idle':
      return '尚未加载';
    case 'loading':
      return '加载中';
    case 'success':
      return `${state.data.length} 项`;
    case 'error':
      return state.error.message;
    default:
      return assertNever(state);
  }
}

在 case 'success' 里可以直接写 state.data，不用判断它存不存在。因为 status 是 'success' 的分支只有一个，TypeScript 根据这个标签就把 state 缩小成了 { status: 'success'; data: T }。

default 里的 assertNever 是穷尽检查。四个分支都处理完以后，state 已经没有可能的类型了，也就是 never，所以能传给 assertNever。哪天新增了一个分支却忘了写 case，state 在这里就不是 never 了，编译直接报错，提醒你补上。

对比一下另一种常见写法 { status: ...; data?: T; error?: Error }。在这种写法里，即使判断了 status === 'success'，data 仍然是可选的，到处都得写 data!。

非法的对象会在构造时报错

TypeScript
// @ts-expect-error success 分支必须提供 data
const missingData: RequestState<string> = { status: 'success' };

说是成功了却没给数据，编译器直接拦下。如果业务确实需要“刷新时还显示旧数据”，正确做法是新增一个分支 { status: 'refreshing'; data: T }，而不是把 loading 硬断言成 success。加完以后，所有用了 assertNever 的 switch 都会报错，正好列出需要更新的地方。

为什么判别关系有时会丢

TypeScript
const state = { status: 'loading' } as const;

如果不加 as const 也不写类型标注，status 会被推断成 string，而不是 'loading'。string 对不上任何一个分支的标签，这个对象就赋不进联合了。

解构也会影响缩小。TypeScript 4.6 起，const { status, data } = state 解构出来的变量，判断 status 以后 data 也能跟着缩小；但解构成 let 时不行，因为 let 变量之后可能被改掉。

联合不等于状态机

先看一个现象：连续搜索 A 和 B，A 的响应慢，后到了。两个结果都是合法的 success，类型上挑不出毛病，可界面显示的是旧的 A。所以要在发请求时记下请求 ID，回来时比对，或者用 AbortController 取消旧请求。

另外，加载状态、编辑状态、在线状态是互不相关的几件事，不要硬塞进同一个联合。外部 JSON 里的 status: 'success' 也不会自动带上 data，进来时要先校验。Error 对象经过 JSON 序列化会丢失信息，跨网络传错误时应该传错误码和消息。

常见追问

判别字段必须叫 type 或 kind 吗？

不必，叫什么名字都行。只要每个分支在这个字段上是不同的字面量类型，TypeScript 就能靠它区分分支。

React 里怎么用？

useReducer 的 state 和 action 都很适合写成可辨识联合。reducer 里按 action.type 去 switch，每个分支里 action 的 payload 会自动缩小成对应的类型。
