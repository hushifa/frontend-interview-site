Service Worker 的安装、激活与缓存更新有哪些坑？

Service Worker 有自己的安装、等待和激活生命周期，注册成功不代表马上接管页面。更新时要处理等待中的新版本、缓存清理和新旧资源混用。

参考答案

简答

Service Worker 是一段在页面背后运行的脚本，能拦截页面发出的请求，决定从缓存还是从网络拿资源，离线访问就靠它。

它有自己的生命周期：注册、安装（install）、等待（waiting）、激活（activate），然后才控制页面。第一次注册的那个页面默认不受它控制，刷新以后才会。

新版本装好以后不会马上生效，要等所有用旧版本的页面都关掉才激活，这是为了避免一个页面用到一半换了缓存逻辑。想马上生效可以用 skipWaiting() 和 clients.claim()，但旧页面可能因此加载到新版本的资源，出现新旧混用。

还有两点要注意：在 activate 阶段删掉旧版本的缓存，缓存名带上版本号；importScripts() 引入的脚本默认还走 HTTP 缓存，所以它们的地址也要带版本号。

先看一个完整的 sw.js

下面这个 Service Worker 做了三件事：安装时预缓存文件，激活时清理旧缓存，请求时先查缓存。

JavaScript
// sw.js
const CACHE = 'app-v3';
const PRECACHE = ['/', '/index.html', '/assets/app.3f9a.js', '/assets/app.8c21.css'];

self.addEventListener('install', (event) => {
  event.waitUntil(caches.open(CACHE).then((cache) => cache.addAll(PRECACHE)));
});

self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then((keys) =>
      Promise.all(keys.filter((key) => key !== CACHE).map((key) => caches.delete(key))),
    ),
  );
});

self.addEventListener('fetch', (event) => {
  if (event.request.method !== 'GET') return;
  event.respondWith(caches.match(event.request).then((hit) => hit ?? fetch(event.request)));
});

install 里预缓存时，只要有一个文件失败，比如 404，整个安装就失败，旧版本继续工作。这是好事，不会装上一个残缺的版本。

activate 时把名字不是 app-v3 的缓存都删掉，所以缓存名要带版本号，否则分不清哪个是旧的。非 GET 请求直接 return，交给网络，不缓存。

浏览器什么时候检查更新

浏览器会逐字节比较 Service Worker 脚本有没有变化。检查的时机有三种：用户在作用域内的页面导航时；距上次检查超过 24 小时后，push、sync 这类功能性事件触发时；页面主动调用 registration.update() 时。

有变化就安装新版本。可是装好的新版本会进入 waiting 状态，已经打开的页面还由旧版本控制。所以“改了代码用户还看到旧版”，多半就是新版本在等。

怎样提示用户刷新

常见做法是发现新版本时弹一个提示，用户点“刷新”才让新版本激活，然后重新加载页面。

JavaScript
// 页面中：发现新版本时提示用户刷新
const reg = await navigator.serviceWorker.register('/sw.js');

reg.addEventListener('updatefound', () => {
  const worker = reg.installing;
  worker?.addEventListener('statechange', () => {
    if (worker.state === 'installed' && navigator.serviceWorker.controller) {
      showUpdateBanner(() => worker.postMessage({ type: 'SKIP_WAITING' }));
    }
  });
});

let reloaded = false;
navigator.serviceWorker.addEventListener('controllerchange', () => {
  if (reloaded) return;
  reloaded = true;
  location.reload();
});
JavaScript
// sw.js
self.addEventListener('message', (event) => {
  if (event.data?.type === 'SKIP_WAITING') self.skipWaiting();
});

为什么要判断 navigator.serviceWorker.controller？因为它有值，说明页面已经被旧版本控制着，这次是更新；没有值就是首次安装，不用提示。

用户点了刷新，页面才发消息让新版本 skipWaiting()。新版本接管后触发 controllerchange，页面重新加载，这样整个页面都换成新资源，不会新旧混用。reloaded 标记是防止重复刷新。

常见的坑

问题原因处理
改了代码用户一直看到旧版新版本在等待，或 index.html 被缓存优先策略返回提示刷新；HTML 用网络优先
直接 skipWaiting 后页面报错旧页面请求的旧 chunk 已被删除缓存激活后刷新页面，或保留旧资源
Service Worker 不更新改的是 importScripts() 引入的脚本，URL 没变；或注册时设了 updateViaCache: 'all'被导入的脚本带版本号，主脚本保持固定 URL
开发时缓存干扰调试旧 Service Worker 仍在控制DevTools 中勾选 Update on reload 或注销
作用范围不对默认作用域是脚本所在目录把 sw.js 放在根目录或设置 scope

第三行要多说一句。注册时有个 updateViaCache 选项，默认值是 'imports'，意思是检查更新时主脚本绕过 HTTP 缓存，但 importScripts() 引入的脚本还走缓存。所以只改了被导入的脚本、地址又没变，浏览器可能发现不了更新。

不同资源用什么缓存策略

HTML 入口用网络优先，离线时再回退到缓存。因为入口要是被缓存住，用户就一直拿到旧页面。

带哈希的静态资源用缓存优先。文件内容一变，文件名就变，相当于一个新资源，所以缓存不会过期出错。

API 数据用网络优先，或者“先返回缓存，再在后台更新”，同时要按用户或租户分开缓存。

常见追问

怎样彻底移除 Service Worker？

部署一个新版本，在 activate 里删掉所有缓存，并调用 self.registration.unregister()。

要不要用 Workbox？

可以。它封装了预缓存清单、缓存策略和过期清理，能少写错。但原理还是上面这套生命周期，出问题时还得按生命周期去排查。
