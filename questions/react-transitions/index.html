useTransition 和 useDeferredValue 能优化哪些卡顿？

Transition 标记可以让步的更新，useDeferredValue 提供某个值的可滞后版本，让紧急交互先反馈。它们调整渲染调度，不自动防抖请求、不减少所有计算，也不能抢占任意长同步函数。

参考答案

输入框需要立即显示用户刚输入的字符，但几千行搜索结果可以稍后更新。如果把所有工作都当作同样紧急，昂贵结果区的重新计算就可能拖慢输入反馈。

useTransition 与 useDeferredValue 用来表达这种优先级差异。它们不是让任务固定等几百毫秒，也不是自动把计算移到 Worker，而是让 React 在适当边界优先处理更紧急的工作。

能控制状态更新的位置，可以使用 Transition

useTransition 返回 isPending 和 startTransition。把相应更新放进 startTransition 的 Action 中，可以标记它们的过渡语义，并通过 isPending 显示相关等待状态。

startTransition 的回调会被调用，并不意味着里面每一句 JavaScript 都被推迟执行。如果先在回调里同步计算很久，再调用 setter，前面那段计算仍然可能占住主线程。

普通快速状态更新未必需要 Transition。应该将它用于允许暂时保留旧界面、又不希望阻塞更紧急交互的工作，而不是给每一个 setState 都套一层。

只有输入值可用时，可以让结果区读取延迟版本

JSX
import { memo, useDeferredValue, useState, useTransition } from 'react';

const topics = ['HTML', 'CSS', 'JavaScript', 'React', 'TypeScript'];

const Results = memo(function Results({ query }) {
  const matches = topics.filter(topic => topic.toLowerCase().includes(query.toLowerCase()));
  return <ul>{matches.map(topic => <li key={topic}>{topic}</li>)}</ul>;
});

export default function SearchDemo() {
  const [query, setQuery] = useState('');
  const deferredQuery = useDeferredValue(query);
  const isStale = query !== deferredQuery;

  return (
    <section>
      <label>搜索<input value={query} onChange={event => setQuery(event.target.value)} /></label>
      <p role="status">{isStale ? '正在更新结果' : '结果已更新'}</p>
      <div aria-busy={isStale} style={{ opacity: isStale ? 0.6 : 1 }}>
        <Results query={deferredQuery} />
      </div>
    </section>
  );
}

输入框直接使用 query，及时接收用户输入；结果区使用 deferredQuery，允许在新的结果尚未提交时暂时显示旧查询对应的内容。isStale 提示用户这份结果还没有追上输入，避免把旧结果误认成最新结果。

数据刻意很小，只用于展示组织方式，不能据此证明需要优化或观察到明显 pending。实际昂贵内容应放在合适的子组件边界，memo 或对应编译优化可以帮助它在紧急渲染中收到相同延迟值时跳过不必要计算。

如果先在父组件执行一个很慢的筛选，再把筛选结果交给 useDeferredValue，昂贵工作已经发生，不能期待延迟返回值把刚才的成本消除。

延迟没有固定时长，也不是请求防抖

useDeferredValue 不定义一个固定的 300ms 等待窗口。React 可以尽快尝试后台渲染，并让新的紧急输入打断相应工作；如果计算本来就很快，差异可能几乎看不见。

默认首次渲染通常使用传入值，后续更新才体现相应滞后机制；提供初始值等扩展用法应按所用版本理解。不要把它当成每次加载都固定慢一拍的工具。

它也不会自动减少网络请求数量。每次输入是否发请求、是否缓存、是否取消旧请求，需要请求层设计。debounce 控制触发频率，Transition 调整 React 更新调度，二者解决的问题不同。

异步 Action 与 await 后的更新要明确

下面沿用前面的导入，用本地延迟观察 pending 与最终更新，不包含网络请求：

JSX
export function AsyncIncrement() {
  const [count, setCount] = useState(0);
  const [isPending, startTransition] = useTransition();

  function increment() {
    startTransition(async () => {
      await new Promise(resolve => setTimeout(resolve, 300));
      startTransition(() => {
        setCount(current => current + 1);
      });
    });
  }

  return (
    <section>
      <output aria-label="计数">{count}</output>
      <button type="button" disabled={isPending} onClick={increment}>
        {isPending ? '处理中' : '延迟加一'}
      </button>
    </section>
  );
}

当前 React 的异步 Action 可以参与 pending 跟踪，但在 await 之后需要作为 Transition 处理的状态更新，仍要按文档用相应 startTransition 标记。示例第二层调用不代表重新等待一次，只标记最终状态更新。

它也不是一个自动排队的业务请求系统。多个异步动作可能按不同顺序完成，旧响应是否还能写入状态，需要请求身份、取消或合适的 Action 状态机制处理。当前实现对多个进行中 Transition 的聚合也有边界，不能把 isPending 当作每项请求独立的状态表。

受控输入本身不应该被延迟

直接控制文本框的状态应保持及时更新，否则用户可能看到输入回退、光标跳动或无法连续编辑。可以延后结果区、预览或其他昂贵内容，不应把同一受控 value 的 setter 当作可随意延后的工作。

用户正在输入时，React 的并发渲染也不是任意抢占式线程。如果某个组件函数内部执行一个很长、不可中断的同步循环，它仍可能阻塞。需要进一步减少计算、拆分任务、虚拟化或使用 Worker，而不是只增加 Transition 标记。

与 Suspense 配合时，要表达旧内容的含义

过渡更新中遇到支持 Suspense 的等待，React 可以在适用条件下保留已显示内容，减少突然切换成大块 loading 的打断。首次加载或新的边界身份等情形仍可能显示 fallback，不能把这理解成“用了 Transition 就再也没有加载界面”。

旧内容应配合清楚的更新反馈，特别是查询条件已经改变时。若数据涉及强一致性要求，也要评估继续展示旧内容是否符合业务，而不是只追求少闪一下。

最后，用真实设备和输入流程测量响应延迟。把某个结果显示得更晚不必然更快，真正的目标是让重要交互先得到反馈，同时保持新旧内容关系清楚、请求结果正确。
