useTransition 和 useDeferredValue 能优化哪些卡顿？

两者都是让 React 先处理打字、点击这类着急的更新，把渲染很慢的部分往后放、还能随时打断。它们只调整渲染的先后，拆不开单个很慢的同步函数，也不会减少网络请求。

参考答案

简答

输入框下面挂着一个很大的列表，每打一个字列表都要重新渲染，输入就会卡。这两个 API 解决的就是这种卡顿：让输入框先响应，列表晚一点更新。

useTransition 返回 [isPending, startTransition]，包在 startTransition 里的状态更新是低优先级的，这种更新叫 Transition。渲染过程中如果来了新的紧急更新，React 会中断它，先处理紧急的。useDeferredValue(value) 从另一个角度做同样的事：它先返回旧值让你渲染，再在后台用新值重新渲染，期间又有新输入就放弃这次渲染。

一般你能控制 setState 的地方用 useTransition，只拿到一个值的地方用 useDeferredValue。注意输入框自己的 value 不能放进 Transition，否则打字会卡住，只把派生的耗时渲染放进去。

它们打断的是 React 的渲染工作。如果某个组件内部有一段几百毫秒的同步计算，照样会卡住主线程。它们也不会自动给网络请求防抖。

用 useDeferredValue 把输入和列表分开

下面的搜索框直接更新 query，列表用的却是延迟版的 deferredQuery：

JSX
import { memo, useDeferredValue, useState } from 'react';

const SlowList = memo(function SlowList({ query }) {
  const items = filterLargeList(query); // 渲染很慢
  return <ul>{items.map((i) => <li key={i.id}>{i.title}</li>)}</ul>;
});

export default function Search() {
  const [query, setQuery] = useState('');
  const deferredQuery = useDeferredValue(query);
  const stale = query !== deferredQuery;

  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <div style={{ opacity: stale ? 0.6 : 1 }}>
        <SlowList query={deferredQuery} />
      </div>
    </>
  );
}

用户打一个字，query 马上变了，输入框立刻显示新字。这时 deferredQuery 还是旧值，SlowList 不用重新渲染。React 随后在后台用新值渲染列表，用户如果又打了一个字，这次后台渲染就被丢掉，换成最新的。

query 和 deferredQuery 不相等，说明列表还是旧的，所以用 stale 把它调暗一点，提示用户结果正在更新。

为什么 SlowList 必须包 memo？因为 query 一变，Search 就会重新渲染。没有 memo 的话，SlowList 会跟着用旧的 deferredQuery 再完整渲染一遍，慢的部分一点没省，延迟就白做了。

用 useTransition 切换标签页

标签页切换时，新页面渲染得慢，我们希望点击马上有反馈，而且点错了能立刻改：

JSX
function Tabs() {
  const [tab, setTab] = useState('about');
  const [isPending, startTransition] = useTransition();

  function select(next) {
    startTransition(() => setTab(next));
  }

  return (
    <>
      <TabButton onClick={() => select('posts')}>文章</TabButton>
      <TabButton onClick={() => select('contact')}>联系</TabButton>
      {isPending && <Spinner />}
      {tab === 'posts' ? <SlowPosts /> : tab === 'contact' ? <Contact /> : <About />}
    </>
  );
}

点“文章”后，SlowPosts 开始在后台渲染，isPending 为 true，显示加载图标，页面仍然能点。这时再快速点“联系”，React 会放弃还没做完的“文章”渲染，直接渲染“联系”。如果不用 Transition，用户得等“文章”渲染完，页面才能响应第二次点击。

和 Suspense 一起用

在 Transition 里切换到一个会进入等待的内容时，React 会继续显示当前已有的内容，不会退回 Suspense 的 fallback。路由跳转通常就利用这一点：新页面数据准备好之前，旧页面一直可见，而不是闪一下加载中。

多个 Transition 共用一个 isPending

同一个 useTransition 返回的 isPending 只表示“有没有正在进行的 Transition”，分不出是哪一个。如果要按条目显示加载状态，比如每一行有自己的保存按钮，就要自己按 ID 记录，或者让每个条目组件各自调用一次 useTransition。

和防抖有什么不同

防抖和节流控制的是函数调用的次数，有固定的延迟，能减少请求。Transition 和 useDeferredValue 调整的是渲染优先级，没有固定延迟，设备快时几乎感觉不到延迟，但不会减少请求。

所以搜索请求还是要防抖，或者交给数据请求库去重；Transition 负责让渲染结果不挡住输入。

常见追问

startTransition 里可以 await 吗？

React 19 起可以传 async 函数。但 await 之后的 setState 要再包一层 startTransition，才会被算作 Transition。

不需要 isPending 的时候怎么写？

可以直接从 react 导入 startTransition 来用，不必调用 Hook。
