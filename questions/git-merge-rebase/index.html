git merge 与 rebase 应该怎样选择？

merge 保留分叉和汇合过程，rebase 重新建立提交的父子关系，让历史变成一条直线。选择时要看分支是否共享、审查需求、冲突成本和回滚方式，而不是只追求直线。

参考答案

简答

merge 和 rebase 都是把两条分支的改动合到一起，最后的代码可以完全一样，区别在历史长什么样。

merge 会新建一个合并提交，它有两个父提交，原来的提交都不动，历史里能看到分叉又汇合的过程。rebase 是把当前分支的提交在新的基础上一个个重新应用一遍，生成新的提交哈希，历史变成一条直线。

因为 rebase 会换掉原来的提交，所以已经推送并被别人使用的分支不要 rebase，否则会改写别人依赖的历史。

常见做法是：在自己的功能分支上用 rebase 跟上主分支，合入主分支时用 merge 或 squash merge。两者在冲突处理和回滚方式上也不一样。

两种历史长什么样

开始时，功能分支从 B 分出来，之后主分支又多了一个 C：

代码
A---B---C          main
     \
      D---E        feature

在 feature 上执行 git merge main（或者在 main 上合并 feature），会多出一个合并提交 M：

代码
A---B---C-------M  main
     \         /
      D-------E    feature

在 feature 上执行 git rebase main，D 和 E 被搬到了 C 后面：

代码
A---B---C          main
         \
          D'--E'   feature

为什么叫 D' 而不是 D？因为提交的哈希是连同父提交一起算的。D' 的改动内容和 D 一样，但父提交从 B 变成了 C，所以它是一个新提交。原来的 D、E 还在仓库里，只是不再有分支指向它们。

两者怎么比

mergerebase
原有提交保留被替换为新提交
历史形状保留分叉和合并点一条直线
冲突处理一次性解决所有冲突每个提交都可能要单独解决
共享分支安全会让别人的本地分支和远端分叉
回滚用 git revert -m 1 <合并提交> 一次撤销整个功能需要逐个撤销提交，或撤销 squash 后的单个提交

冲突那一行值得多说一句。merge 是拿两边的最终结果比一次，有冲突一次解决完。rebase 是一个提交一个提交地重放，同一处冲突可能在好几个提交上反复出现。

什么时候用哪个

自己一个人的功能分支要跟上主分支时，用 git pull --rebase 或 git rebase main，避免出现一堆没意义的合并提交。rebase 之后再推送一个已经推送过的分支，要用 git push --force-with-lease，它会在远端被别人更新过时拒绝覆盖，比直接 --force 安全。

合入主分支时按团队约定。squash merge 让每个 PR 在主分支上只剩一个提交，好读也好回滚；merge commit 则保留完整的开发过程。

多人一起用的分支，只用 merge。

合入前想整理提交，可以用 git rebase -i 合并、重排、改提交信息，前提是这些提交还没被别人用。

rebase 出错了怎么办

冲突解决到一半想放弃，用 git rebase --abort，回到开始之前的状态。

rebase 已经做完才发现有问题，可以用 git reflog 找到 rebase 之前的提交哈希，再 git reset --hard <哈希> 恢复。这会丢掉工作区里没提交的修改，执行前先确认。

常见追问

为什么有人坚持不用 rebase？

一是担心改写历史造成混乱，二是逐个提交解决冲突的成本高。只要不在共享分支上用，风险是可控的。

git pull 默认是 merge 还是 rebase？

默认先 fetch 再 merge。可以用 git config pull.rebase true 改成 rebase。
