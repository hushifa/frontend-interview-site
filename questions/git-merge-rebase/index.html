git merge 与 rebase 应该怎样选择？

merge 保留分叉和汇合过程，rebase 重新建立提交的父子关系。选择时要结合分支是否共享、审查需求、冲突成本和回滚方式，而不是只追求一条直线。

参考答案

简答

  • merge 创建一个有两个父提交的合并提交，原有提交不变，历史保留分叉过程。
  • rebase 把当前分支的提交在新的基础上逐个重新应用，生成新的提交哈希，历史变成一条直线。
  • 已经推送并被别人使用的分支不要 rebase，否则会改写别人依赖的历史。
  • 常见做法：在自己的功能分支上 rebase 主分支保持更新，合入主分支时用 merge 或 squash merge。
  • 两种方式的最终代码可以完全相同，区别在于历史的形状、冲突处理方式和回滚方式。

两种历史

初始状态：功能分支从 B 分出，主分支之后又有了 C。

代码
A---B---C          main
     \
      D---E        feature

在 feature 上执行 git merge main（或在 main 上合并 feature）：

代码
A---B---C-------M  main
     \         /
      D-------E    feature

在 feature 上执行 git rebase main：

代码
A---B---C          main
         \
          D'--E'   feature

D' 和 E' 的内容改动与 D、E 相同，但父提交变了，所以是新的提交。

对比

mergerebase
原有提交保留被替换为新提交
历史形状保留分叉和合并点一条直线
冲突处理一次性解决所有冲突每个提交都可能要单独解决
共享分支安全会让别人的本地分支和远端分叉
回滚用 git revert -m 1 <合并提交> 一次撤销整个功能需要逐个撤销提交，或撤销 squash 后的单个提交

什么时候用哪个

  • 个人功能分支同步主分支：git pull --rebase 或 git rebase main，避免出现大量无意义的合并提交。推送已推送过的分支时用 git push --force-with-lease，它会在远端被别人更新过时拒绝覆盖。
  • 合入主分支：团队约定。squash merge 让每个 PR 在主分支上只有一个提交，便于阅读和回滚；merge commit 保留完整的开发过程。
  • 多人协作的分支：只用 merge。
  • 整理提交：合入前用 git rebase -i 合并、重排、修改提交信息，只在提交尚未被他人使用时这样做。

rebase 出错怎么办

  • 冲突处理中想放弃：git rebase --abort 回到开始前的状态。
  • rebase 完成后发现问题：git reflog 找到 rebase 之前的提交哈希，git reset --hard <哈希> 恢复（这会丢弃工作区未提交的修改，先确认）。

常见追问

  • 为什么有人坚持不用 rebase？担心改写历史造成混乱，以及逐个解决冲突的成本。只要不在共享分支上使用，风险可控。
  • git pull 默认是什么？默认先 fetch 再 merge，可以用 git config pull.rebase true 改为 rebase。
