国际化页面怎样做跨地区测试，避免上线后才发现布局和时间错误？

把语言、地区、时区和书写方向当作四个独立变量，按风险挑代表性组合组成测试矩阵；用伪本地化提前暴露写死宽度和字符串拼接；测试固定 locale 和时区，覆盖夏令时边界；RTL 和读屏要人工检查。

参考答案

简答

国际化测试最常见的误区，是只把浏览器语言切成英文看一眼。其实语言、地区、时区、书写方向是四个独立的变量。浏览器语言是英文，不代表用户在美国，更不代表要用纽约时区。

组合太多，全测不现实，所以按风险挑代表：一种文字较长的语言、一种复杂文字、一种从右到左的语言、一个日期和数字格式不同的地区，再加两个相差较大的时区。

还没拿到真实翻译时，可以先做伪本地化。把文案加长、加上重音字符和边界标记，溢出、截断和写死的字符串马上就能看出来。自动化测试要显式固定 locale 和时区，不依赖运行机器的系统设置，并覆盖夏令时切换和跨午夜。

要注意，方向、焦点顺序、读屏输出和翻译质量，工具判断不了，需要人工检查。

测试矩阵怎样挑

下面每一行都对应一类容易出问题的情况。

维度代表值发现的问题
长文本de-DE按钮、表头、导航溢出
复杂文字ja-JP、th-TH换行、截断、字体回退
RTLar方向、图标镜像、焦点顺序
格式en-IN（数字写作 12,34,567.891）、de-CH千位分隔、日期顺序、货币
时区Asia/Shanghai、America/New_York跨日、夏令时

在这些组合上，再叠加窄屏、200% 字号和读屏器，大部分布局和格式问题都能暴露出来。

伪本地化是什么

伪本地化就是不用真翻译，先用程序把原文“变个样”，看页面扛不扛得住。下面是一个最简单的版本。

JavaScript
// 只变换纯文字片段，变量由调用方另外拼接
function pseudo(text) {
  const accented = text.replace(/[A-Za-z]/g, (ch) => `${ch}̄`);
  return `[${accented}~~~~]`; // 方括号标出边界，波浪线模拟变长
}

它给每个字母加上一个组合用的横线，再在两头加上方括号和波浪线。

方括号是用来找问题的。页面上出现了不带方括号的文字，说明这段文字写死在代码里，没有走翻译。方括号被截掉了一半，说明容器宽度写死了，或者用了截断。

可是真实消息里常带 ICU 语法。这时不能用正则直接处理整条消息，否则变量名和 plural、select 的分支键也会被改掉。要用消息解析器，只改写其中的文字节点。

测试为什么要固定时区

如果测试依赖运行机器的系统时区，本地能过、CI 上就挂。所以格式化时直接把时区传进去。

JavaScript
// 不依赖系统时区，直接在格式化时指定
const format = (date, locale, timeZone) =>
  new Intl.DateTimeFormat(locale, { dateStyle: 'short', timeStyle: 'short', timeZone }).format(date);

format(new Date('2026-01-01T00:00:00Z'), 'en-GB', 'America/New_York'); // '31/12/2025, 19:00'

同一个 UTC 时刻，在纽约还是前一年的 12 月 31 日。这种跨日的情况正是要测的。

用例要包括夏令时切换当天、闰日、跨午夜和月末。时间戳和时区怎样建模，见《时间戳、时区和只有日期的业务值应该怎样区分？》。

Playwright 这类工具可以给每个测试项目设置 locale 和 timezoneId，同一套用例就能在多个地区上各跑一遍。

哪些要人工检查

从右到左的布局先用逻辑属性写对，见《前端页面如何支持从右到左的语言？》。写完以后，还要人工逐项看：箭头和返回图标有没有镜像，方向键的行为对不对，弹出层的位置对不对，数字和英文混排时有没有乱。

翻译质量只能靠母语审校，看句子是否自然、术语是否一致。伪本地化能发现布局问题，但代替不了这一步。

业务规则也要写进测试

税费按哪个地区算，订单时间显示用户的时区还是商家的时区，一周从周几开始，这些都不是技术问题，而是产品规则。所以它们要写进需求，并和后端一起测试。

常见追问

多语言下视觉回归怎么做？

对代表性的语言和书写方向分别截图对比。不同环境的字体渲染会有细微差异，用合理的阈值处理，别让它们一直误报。

缺失翻译怎么测？

构建时先检查各语言的键集合是否齐全。界面测试里再故意删掉一个键，确认回退语言生效，页面上没有出现空白。
