国际化页面怎样做跨地区测试，避免上线后才发现布局和时间错误？

从语言、地区、时区和书写方向的区别出发，设计国际化测试矩阵、伪本地化和可重复的日期数字测试，覆盖布局、排序、无障碍和数据边界。

参考答案

页面在中文环境看起来正常，翻译成德语后按钮文字溢出；订单在东京创建，却在纽约用户页面显示成前一天；阿拉伯语界面方向反过来后，图标和焦点顺序仍然是从左到右。这些问题不是简单替换一份语言 JSON 就能发现，测试必须把语言、地区、时区、数字规则和书写方向分开建模。

语言、地区和时区不是一个变量

zh-CN、en-GB 和 en-US 可能使用不同日期、数字和货币习惯；时区又是用户或业务数据的另一维度。不要把浏览器语言当成用户所在地区，也不要从日期字符串里猜时区。后端应传递明确的时间语义，例如 UTC 时间戳或带偏移的 ISO 字符串，前端根据显示场景选择用户时区或业务时区。

JavaScript
const instant = new Date('2026-01-15T23:30:00Z');

function formatOrderTime(date, locale, timeZone) {
  return new Intl.DateTimeFormat(locale, {
    dateStyle: 'medium',
    timeStyle: 'short',
    timeZone,
  }).format(date);
}

console.log(formatOrderTime(instant, 'en-US', 'America/New_York'));
console.log(formatOrderTime(instant, 'ja-JP', 'Asia/Tokyo'));

测试应固定输入瞬间、locale 和时区，避免依赖运行机器的系统设置。涉及夏令时切换、闰日、跨午夜和历史时区规则时，应使用明确的时区数据库和库版本；不能用固定的 24 * 60 * 60 * 1000 计算所有“天”的长度。

测试矩阵应覆盖真实风险，而不是列出所有语言

可以按风险选择代表组合：

  • 一种短文本语言、一种通常更长的语言，用于发现按钮和表格溢出；
  • 一种使用复杂文字或组合字符的语言，用于检查截断、分词和字体回退；
  • 一种 RTL 语言，用于检查方向、图标、焦点和数字混排；
  • 一个使用不同日期顺序、千位分隔符和货币符号的地区；
  • 至少两个相差较大的时区，并覆盖夏令时边界。

矩阵还要包含窄屏、放大字体、低带宽和屏幕阅读器。翻译条目数量不等于测试覆盖，关键是让每个组件经历不同长度、方向和格式规则。

伪本地化可以提前暴露布局问题

伪本地化可以把字符串加长、替换为带重音字符或包裹标记，帮助发现硬编码宽度、依赖字符长度的截断和拼接语句。测试数据应保持占位符、HTML 转义和复数变量有效；不能简单把每个字符替换成不可读内容，导致测试失去业务意义。

JavaScript
// 只处理纯文字片段，不解析 ICU、HTML 或占位符语法。
function pseudoText(text) {
  return `[${text.replace(/[A-Za-z]/g, (letter) => `${letter}̄`)}]`;
}

// 文字与参数由结构分开，用户名称不参与变换。
function greeting(name) {
  return pseudoText('Hello, ') + name + pseudoText('!');
}
console.log(greeting('小明'));

伪本地化不是翻译质量检查，不能替代母语审校。它的价值是让布局、截断、换行和无障碍名称更早暴露。视觉回归测试应在代表性语言、方向和屏幕宽度下运行，而不是只在默认语言截图。

上述函数仅演示文字节点变换。如果把 Hello {name} 整串传入，变量名也会被改变，因此不能直接批量处理翻译源文件。实际 ICU 消息应由对应消息解析器生成语法树，仅改写 literal 节点，并在 plural/select 的每个分支递归处理文字；保留变量名、选择键、转义和富文本标签。不要用一个正则表达式假装能解析嵌套 ICU 语法。

组合重音字符也不保证明显增加视觉宽度。测试长文案布局时，应另准备明确加长的纯文字片段；组合字符主要用于暴露字符计数和截断问题。该示例返回普通字符串，展示时使用文本节点，不把参数拼成 HTML。

日期、数字和货币必须使用格式化 API

面向用户的本地化展示应优先使用 Intl.DateTimeFormat、Intl.NumberFormat 和 Intl.PluralRules，避免自行拼接日期顺序、分隔符和货币符号。协议字段、文件名或明确要求 ISO 日期的场景仍可使用固定格式，不能把本地化展示字符串反过来当作交换协议。输入必须有正确的数值和时间语义；测试覆盖零、负数、大数、小数、无效值和货币小数位差异。金额计算应使用整数最小单位或精确十进制方案，并处理整数安全范围，不能依赖浮点显示结果。

排序也要明确规则。用户可见文本通常需要 Intl.Collator，而 ID、版本号和金额可能需要不同的排序方式。把“字符串排序”和“用户语言排序”混为一谈，会在不同语言中产生难以解释的顺序。

RTL 不只是把 direction 改成 rtl

布局应优先使用 CSS 逻辑属性，如 margin-inline-start、padding-block 和 inset-inline-end，避免把左、右写死。箭头、返回图标和时间轴可能需要按语义决定是否镜像；品牌图标、播放按钮和数字并非都应反转。键盘方向键、焦点顺序、弹出层定位和滚动条行为要在 RTL 环境逐项验证。

混合文本还会涉及数字、URL、邮箱和英文缩写。不要通过插入不可见控制字符随意修复显示；应使用正确的 Unicode 双向文本处理、语义元素和浏览器能力，并用真实句子测试。

翻译缺失、回退和动态内容

缺少翻译时应有明确回退语言和监控，不能在页面上显示键名或空字符串。动态服务端错误、用户生成内容和富文本要区分翻译资源与不可信内容，插值时保持转义，不能把翻译文件当作可信 HTML 执行。

组件测试应覆盖加载中、缺失键、复数、长文本和异步切换语言。语言切换过程中要避免部分组件已经切换、部分组件仍显示旧语言；可以用版本化资源快照或等待资源加载完成后原子更新界面。

自动化和人工检查如何配合

自动化测试适合固定 locale、时区、方向和格式输入，检查文本存在、ARIA 名称、溢出和关键数字。视觉回归适合发现布局变化，但对字体渲染差异要设置合理阈值。人工检查应覆盖真实任务：填写表单、读表格、切换语言、使用键盘、放大页面和阅读屏幕阅读器输出。

国际化测试还要把产品规则写清楚：税费按哪个地区计算、订单时间显示哪个时区、周起始日是什么、货币是否允许换算。代码格式化正确不代表业务含义正确，后端和产品规则必须共同核对。
