前端组件库怎样设计才能让业务方稳定使用？

组件库的公共 API 不只是 props，还包括默认行为、键盘与焦点、样式扩展方式和发布产物。设计时明确受控与非受控模式、提供稳定的样式入口、把无障碍行为当作契约，再用文档、测试和语义化版本让升级可预期。

参考答案

简答

业务方用组件库，依赖的不只是 props 的类型。默认值、事件什么时候触发、键盘怎么操作、焦点去哪、渲染出什么 DOM、CSS 怎么覆盖，这些都是公共 API，改了任何一项都可能让业务方的页面出问题。

所以设计时有几件事要定清楚。有状态的组件要同时支持受控和非受控：受控是外面传 value 和 onChange，以外面为准；非受控是只给 defaultValue，组件自己管。样式要给明确的入口，比如 CSS 变量、className、data-* 状态属性，别让业务方去依赖内部 DOM 结构或者哈希类名。

无障碍是组件自己的责任。Dialog 的焦点困在弹窗里、关闭后回到原处，Combobox 的键盘导航，这些照着 WAI-ARIA APG 实现，业务方不用再操心。

最后是升级。用语义化版本标出破坏性变更，删东西之前先弃用、给警告，再提供迁移指南，业务方升级时心里才有数。

用变体代替互相冲突的布尔值

先看一个 props 设计上的常见问题：

TSX
// 不好：primary 和 danger 同时为 true 时是什么样？
<Button primary danger small />

// 好：每个维度只有一个取值
<Button variant="danger" size="sm" />

用一堆布尔值，业务方很容易写出组件作者没想过的组合，结果谁也说不清该长什么样。改成 variant、size 这样的枚举，每个维度只能选一个值，冲突从写法上就排除了。

受控和非受控怎样同时支持

受控的意思是，值存在组件外面，组件只负责显示和通知；非受控的意思是，值存在组件里面，外面只给一个初始值。下面这个 Hook 把两种模式合在一起：

TSX
function useControllableState<T>(value: T | undefined, defaultValue: T, onChange?: (v: T) => void) {
  const [inner, setInner] = useState(defaultValue);
  const controlled = value !== undefined;
  const current = controlled ? value : inner;
  const set = (next: T) => {
    if (!controlled) setInner(next);
    onChange?.(next);
  };
  return [current, set] as const;
}

判断依据是 value 有没有传。传了就是受控，组件显示外面的值，改动只通过 onChange 告诉外面，自己不存。没传就是非受控，组件用内部 state，同时也调用 onChange，方便外面监听。

Tabs、Select、Disclosure 这类组件都能用这个模式。简单场景业务方什么都不传就能用，复杂场景又可以完全接管状态。

怎样给样式留稳定的入口

如果业务方为了改颜色，写了 .button > span:first-child 这样的选择器，组件内部结构一调整，他的样式就失效了。所以组件库要主动提供不依赖结构的入口：

CSS
.button {
  --button-bg: #2563eb;
  --button-fg: #fff;
  color: var(--button-fg);
  background: var(--button-bg);
}

.button[data-variant='danger'] {
  --button-bg: #b42318;
}

.button[data-loading] {
  cursor: progress;
}

主题通过改 CSS 变量实现，状态通过 data-* 属性暴露，业务方用的都是约定好的名字。另外，把组件库的样式放进 @layer，业务样式不需要提高选择器优先级就能覆盖它。

无障碍为什么算契约

键盘和读屏用户依赖的是组件的行为，这部分一旦改坏，测试可能都发现不了。所以要把它当成和 props 一样的承诺来维护：

  • 优先用原生元素：按钮用 <button>，链接用 <a>，开关可以用 <input type="checkbox" role="switch">。
  • Dialog 打开时焦点移进去，按 Tab 不会跑出对话框，Esc 关闭，关闭后焦点回到打开它的那个元素。
  • 表单字段的 label、帮助文字、错误信息通过 id 和 aria-describedby 关联起来。
  • 状态不能只靠颜色表达。

文档和测试覆盖什么

文档要写清楚什么时候用、什么时候不用、键盘行为是什么、受控怎么用、样式怎么扩展。Storybook 里把默认、禁用、加载、错误、长文本、窄屏、暗色、RTL 这些状态都摆出来。

测试分几层。组件测试按角色和名称查找元素、模拟用户操作，这样测的是用户能感知的行为，而不是内部实现。视觉回归测试检查样式有没有意外变化，axe 检查结构上的无障碍问题。

发布前检查什么

包能不能被正确使用，也是 API 的一部分：

  • 检查 exports、ESM 产物、类型声明、CSS 文件和 sideEffects 配置，保证按需导入真的有效。
  • React、Vue 这些框架声明为 peerDependencies，避免业务方打包进两份运行时。
  • 发布前用一个独立的示例项目，按真实包名安装并构建一遍。

常见追问

组件库要不要包含业务逻辑？

不要。权限判断、接口调用、业务校验留在应用里，组件库只管交互和展示。否则组件库会跟某个业务绑死，别的团队没法用。

headless 组件库是什么？

就是只提供状态管理和无障碍行为、不带任何样式的组件，比如 Radix UI、Headless UI。样式完全由使用方决定，适合有自己设计规范的团队。
