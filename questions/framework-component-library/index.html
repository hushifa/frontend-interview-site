前端组件库怎样设计才能让业务方稳定使用？

组件库的公共 API 包括 props、默认行为、键盘与焦点、样式扩展方式和发布产物。设计时明确受控与非受控模式、提供稳定的样式入口、把无障碍行为当作契约，用文档、测试和语义化版本保证升级可预期。

参考答案

简答

  • 公共 API 不只是 props 类型，还包括默认值、事件触发时机、键盘操作、焦点行为、DOM 语义和 CSS 覆盖方式，改动任何一项都可能是破坏性变更。
  • 有状态的组件同时支持受控（value + onChange）和非受控（defaultValue）模式，受控时以外部传入的值为准。
  • 样式扩展通过 CSS 变量、className、data-* 状态属性等明确入口提供，不让使用方依赖内部 DOM 结构或哈希类名。
  • 无障碍行为是组件的职责：Dialog 的焦点陷阱和恢复、Combobox 的键盘导航等，参考 WAI-ARIA APG 实现。
  • 用语义化版本标识破坏性变更，先弃用并警告再删除，提供迁移指南。

用变体代替互相冲突的布尔值

TSX
// 不好：primary 和 danger 同时为 true 时是什么样？
<Button primary danger small />

// 好：每个维度只有一个取值
<Button variant="danger" size="sm" />

受控与非受控

TSX
function useControllableState<T>(value: T | undefined, defaultValue: T, onChange?: (v: T) => void) {
  const [inner, setInner] = useState(defaultValue);
  const controlled = value !== undefined;
  const current = controlled ? value : inner;
  const set = (next: T) => {
    if (!controlled) setInner(next);
    onChange?.(next);
  };
  return [current, set] as const;
}

Tabs、Select、Disclosure 等组件都可以用这个模式，使用方既能简单使用，也能完全接管状态。

稳定的样式入口

CSS
.button {
  --button-bg: #2563eb;
  --button-fg: #fff;
  color: var(--button-fg);
  background: var(--button-bg);
}

.button[data-variant='danger'] {
  --button-bg: #b42318;
}

.button[data-loading] {
  cursor: progress;
}

主题通过修改 CSS 变量实现。组件库的样式放进 @layer，业务样式不需要提高优先级就能覆盖。

无障碍契约

  • 优先使用原生元素：按钮用 <button>，链接用 <a>，开关可以用 <input type="checkbox" role="switch">。
  • Dialog：打开时焦点移入，Tab 不离开对话框，Esc 关闭，关闭后焦点回到触发元素。
  • 表单字段：label、帮助文字、错误信息通过 id 和 aria-describedby 关联。
  • 状态不只用颜色表达。

测试与文档

  • 文档写清何时使用、何时不用、键盘行为、受控用法和样式扩展方式。
  • Storybook 覆盖默认、禁用、加载、错误、长文本、窄屏、暗色、RTL 等状态。
  • 组件测试按角色和名称查询元素、模拟用户操作；视觉回归测试检查样式变化；axe 检查结构问题。

发布

  • 检查 exports、ESM 产物、类型声明、CSS 文件和 sideEffects 配置，确保按需导入有效。
  • React、Vue 等框架声明为 peerDependencies，避免打包两份运行时。
  • 发布前用一个独立的示例项目，按真实包名安装并构建。

常见追问

  • 组件库要不要包含业务逻辑？不要。权限判断、接口调用、业务校验留在应用中，组件库只提供交互和展示。
  • headless 组件库是什么？只提供状态和无障碍行为、不带样式的组件（如 Radix UI、Headless UI），样式完全由使用方决定。
