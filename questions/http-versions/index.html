HTTP/1.1、HTTP/2 和 HTTP/3 的主要区别是什么？

三个版本主要改变消息传输与连接组织方式，核心 HTTP 语义仍然相通。HTTP/2 在 TCP 上多路复用，HTTP/3 在 QUIC 上组织独立流，性能收益还取决于丢包、拥塞、服务端与实际资源依赖。

参考答案

GET、状态码、资源表示和缓存等 HTTP 核心语义，并没有随着版本升级全部重写。主要变化是消息怎样编码、多个请求怎样共享连接，以及底层传输怎样处理丢包和连接建立。

因此“升级到 HTTP/3”不等于业务接口重新设计，也不等于所有请求都会立刻更快。

“HTTP/1.1 是文本式”说的是相应消息头结构，不表示它只能传文本，图片和视频等正文同样可以传输。HPACK、QPACK 处理的是头部压缩，正文的 gzip、Brotli 等内容编码是另一层机制。

HTTP/1.1 不是每个请求都重新建连接

HTTP/1.1 支持持久连接，多个请求可以复用连接。也存在流水线机制，允许前一个响应尚未完成时发送后续请求，但响应顺序受约束，前面的慢响应可能挡住后面的结果。

现代浏览器通常不依赖传统 HTTP/1.1 流水线来解决全部并发，而会组织多个连接。常见实现存在每源连接数量限制，但“永远固定六条”不是协议保证，不应当作所有设备与客户端的常量。

过去的域名分片、雪碧图和大量资源合并，有些就是围绕连接与请求成本形成的策略。换用新协议后，应重新测量这些权衡，而不是保留所有旧优化习惯。

HTTP/2 的多路复用解决了哪一层等待

HTTP/2 把请求与响应拆成帧，用流标识区分，同一个连接上可以交错传输多个流的数据。一个响应较慢，不必像传统有序响应那样强制等它完整结束，其他流可以继续使用可用传输机会。

但底层仍是 TCP 的有序字节流。如果丢失了一段 TCP 数据，后续已到达的数据可能要等待重传补齐后才能按序交付，这会影响同一连接上的多个 HTTP 流。

所以“HTTP/2 没有队头阻塞”过于绝对。它改善了 HTTP 消息组织上的阻塞，但没有取消 TCP 层的有序交付约束。

流量控制、并发流上限、服务器调度和共享拥塞状态也仍然存在。一个连接支持多路复用，不代表可以无限制地同时请求所有资源。

HTTP/3 为什么仍然是可靠 HTTP

HTTP/3 使用 QUIC，QUIC 通常通过 UDP 传输，但它自己提供可靠流、丢包恢复、拥塞控制和安全连接等能力。因此不能把“UDP 承载”直接等同于“资源正文可能随意缺字节”。

不同 QUIC 流不再必须共享 TCP 那一条按序交付字节流。某个流的数据丢失，其他流已到达的数据可以继续按各自规则交付，从而减少跨流的传输层队头阻塞。

这并不意味着任何层面都不会等待。单个流自己的顺序、连接级拥塞与流控、头部压缩依赖，以及应用本身的先后关系，都可能继续限制进度。

握手与网络切换也有不同能力

QUIC 将传输建立与 TLS 1.3 握手更紧密结合，在支持的场景下可以减少连接准备开销。会话恢复和早期数据还可能进一步降低等待，但不是所有首次访问都能“零往返”。

0-RTT 等能力还涉及重放风险与服务端策略，不能不加分析地用于任意不可重复的写操作。是否启用、对哪些请求启用，需要协议栈与服务端共同决定。

QUIC 的连接标识也有助于在网络路径变化时维持连接，但迁移仍受路径验证、网络策略与实现影响。切换 Wi-Fi 后不断线是一种可能收益，不是对所有设备和服务的绝对承诺。

为什么启用 HTTP/3 后仍可能看到 HTTP/2

浏览器需要发现并协商可用协议，服务端、CDN 和沿途网络也必须支持。UDP 被限制、连接失败、缓存的协议信息或实现策略，都可能让客户端采用其他可用版本。

普通 fetch 代码不会因为你想用 HTTP/3 就自动控制底层所有协商。应在服务端和托管层配置正确支持，再通过浏览器 Network 的协议列、相关日志与性能数据确认实际连接。

协议升级不能消除应用瀑布

如果页面必须先拿用户信息，才能计算第二个请求地址，后续又等待图片清单，协议再先进也不能自动知道这些业务依赖。过大的 JavaScript、错误缓存、大量不需要的资源和后端慢处理同样需要单独优化。

比较收益时应考虑 RTT、丢包、资源大小、连接是否已建立和客户端支持，而不只看某一次本地刷新。协议改进提供更好的传输工具，资源与数据流设计仍决定用户最后要等多久。
