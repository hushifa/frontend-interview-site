同步错误、Promise 拒绝和全局异常应该怎样处理？

错误处理要沿真实控制流建立边界：同步异常由当前栈上的 catch 处理，异步任务需要通过 Promise 或回调传递失败，全局事件用于兜底观察。恢复、清理和诊断不能简单合并成“所有错误都返回空值”。

参考答案

判断一个 catch 能不能接住错误，首先看错误发生时是否仍在它对应的执行路径里。代码文本写在某个 try 里面，不意味着之后执行的所有回调也自动受这个 try 保护。

同步函数在 try 内抛错，会沿当前调用栈进入 catch；Promise 拒绝则需要在链上连接处理，或在 try 内用 await 等待它恢复为异常。

把拒绝接入正在等待它的边界

JavaScript
async function demonstrate() {
  try {
    await Promise.resolve().then(() => {
      throw new Error('处理失败');
    });
  } catch (error) {
    console.log(error.message); // 处理失败
  } finally {
    console.log('清理'); // 清理
  }
}

demonstrate();

then 回调抛错，会让 then 返回的新 Promise 拒绝。await 等待的是这个 Promise，因此拒绝会在 await 位置恢复为异常，进入当前 catch，最后执行清理。

async 函数内部抛错也通常表现为它返回的 Promise 拒绝。调用方如果既不 await，也不接 catch，这个拒绝不会因为函数名字叫“异步任务”就自动得到处理。给返回 Promise 的函数明确责任边界，是避免未处理拒绝的第一步。

定时器回调为什么不能靠注册时的 try 保护

setTimeout 注册后，当前函数可以先结束。真正的回调在后续任务中执行，它抛出的错误不会穿越时间回到已经结束的外层 try。

如果要把定时器中的工作建模成可等待任务，需要主动将回调失败转成拒绝：

JavaScript
function runTimerTask() {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      try {
        JSON.parse('{broken}');
        resolve();
      } catch (error) {
        reject(error);
      }
    }, 0);
  });
}

runTimerTask().catch(error => console.log(error.name)); // SyntaxError

Promise 构造器会捕获其执行器同步执行期间的抛错，但不会自动捕获执行器所注册的后续定时器回调异常。因此示例中的内层 try/catch 不能随便删掉。

事件监听也是类似边界。一个 async 事件处理器返回 Promise，事件系统通常不会像业务代码一样自动 await 它；需要在处理器内部或明确的调用包装中处理拒绝。仅写 void 来忽略返回值，不会使实际失败消失。

then 的第二个参数不捕获同一 then 成功回调里的错误

JavaScript
const result = Promise.resolve(1).then(
  () => {
    throw new Error('后处理失败');
  },
  () => '已处理原 Promise 的拒绝',
);

result.catch(error => console.log(error.message)); // 后处理失败

两个回调都是对前一个 Promise 的反应。原 Promise 已经成功，就执行第一个回调；这个回调抛错使返回的 result 拒绝，不会再倒回去调用并列的第二个回调。

在整段链尾添加 catch，能处理传递到这里的拒绝，但 catch 自己如果又抛错，也会产生一个新的拒绝。要确保最终负责处理的边界确实观察了最后返回的 Promise，而不只是链条中某个较早的节点。

清理失败也要避免掩盖主要错误

finally 适合恢复加载状态、归还局部资源或移除临时监听。它通常不应该 return 一个业务值或随意抛出另一个错误，否则会覆盖前面的结果或异常。

直接 return 一个尚未完成的 Promise，与在 try 中 return await 它，可能让当前 catch、finally 的作用时机不同。资源需要保持到异步操作结束时，应在相应范围内明确等待。

如果业务执行与清理都可能失败，需要决定主要错误如何传播、清理错误怎样记录。显式资源管理的 SuppressedError 等机制也有自己的规则，不能把不同协议的错误优先级想当然地视为相同。

全局事件是兜底观测，不是业务恢复策略

浏览器的 error 事件可以观察未被正常处理的运行时异常；资源加载失败也有 error 事件，但事件对象与传播方式不同。资源元素的错误通常不冒泡，统一观察时可能需要捕获阶段监听，并区分 ErrorEvent 与图片、脚本等资源元素的事件。

unhandledrejection 用于观察尚未得到相应拒绝处理的 Promise。之后补上处理器还可能触发 rejectionhandled，所以它不总等同于“这个拒绝以后永远不会被处理”。跨源脚本等场景也可能受到错误信息暴露限制，拿不到完整堆栈不必然说明代码没有失败。

全局处理器不知道用户当前操作是否可以重试，也不能自动把页面恢复到正确业务状态。需要恢复的错误，应在能理解上下文的边界处理；全局层负责汇总遗漏和诊断线索。

仅调用 preventDefault 隐藏默认控制台输出，不代表错误已经被修复。日志上报函数自身也要处理失败，避免它再次产生未处理拒绝，形成不断报告自己的循环。

错误信息要帮助定位，也要表达给用户可执行的下一步

网络暂时失败可以提示重试，表单字段错误应定位到字段，取消操作通常不必按系统故障处理；程序状态不符合约束则需要保留诊断信息，而不是统一回退成“成功但没有数据”。

catch(() => []) 只有在业务明确把失败视为可接受的空结果时才合适。否则页面会把“请求失败”伪装成“确实没有记录”，既误导用户，也让监控丢失真实故障。

包装错误时可以使用 Error 的 cause 保留原始原因。记录操作类型、版本、请求关联标识和必要堆栈时，应避免直接上传整个表单、访问令牌或完整敏感响应。错误原因也不保证总是 Error 实例，来自第三方或任意 Promise 的拒绝值应先安全归一化。

最后，浏览器全局错误事件与 Node.js 的未捕获异常、未处理拒绝策略不是同一套接口。不要把前端的全局监听写法或“程序还能继续运行”的观察，直接推广到所有服务端进程；每个运行环境都需要明确最终失败策略。
