同步错误、Promise 拒绝和全局异常应该怎样处理？

try/catch 只能接住当前正在执行的代码抛出的错误，以及在 try 里 await 的 Promise 失败。定时器和事件回调是后来才异步执行的，外面的 try 管不到。全局的 error 和 unhandledrejection 事件只负责兜底上报。

参考答案

简答

同步代码抛出的错误，会沿着调用栈一层层往外传，被最近的 try/catch 接住。Promise 失败，也就是拒绝，要在使用它的地方处理：要么在 try 里 await 它，要么在链的末尾接 .catch()。

容易误会的是回调。定时器、事件监听的回调是之后才执行的，那时注册回调时外面那个 try 早就结束了，所以接不住回调里的错误，要在回调内部自己处理。还有，.then(onOk, onErr) 里的 onErr，接不住同一个 then 里 onOk 抛出的错误。

总有遗漏的错误，所以页面上要用 window 的 error 和 unhandledrejection 事件做兜底上报。但它们只负责记录，真正的恢复，比如提示重试、回退界面，要在了解业务的地方做。

await 怎样把拒绝变成能 catch 的错误

JavaScript
async function demonstrate() {
  try {
    await Promise.resolve().then(() => {
      throw new Error('处理失败');
    });
  } catch (error) {
    console.log(error.message); // 处理失败
  } finally {
    console.log('清理'); // 清理
  }
}

demonstrate();

错误是在 then 回调里抛出的，让这个 Promise 变成了拒绝。await 等到拒绝以后，会把拒绝的原因在这一行重新抛出来，所以 try/catch 能像处理同步错误一样接住它，finally 也照常执行。

反过来，如果调用一个 async 函数，既不 await 也不 .catch()，它失败了就没人处理，会变成未处理的拒绝。

为什么外面的 try 接不住定时器里的错误

JavaScript
try {
  setTimeout(() => {
    throw new Error('稍后失败'); // 外层 try 已经结束，捕获不到
  }, 0);
} catch {}

try 里执行的只是 setTimeout 这一句，它的作用是登记一个回调，登记完就返回了，try 跟着结束。回调要等到之后的任务里才执行，那时调用栈上已经没有这个 try，错误只能落到全局。

如果想让调用方能等待、能捕获，就把回调包装成 Promise：

JavaScript
function runTimerTask() {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      try {
        JSON.parse('{broken}');
        resolve();
      } catch (error) {
        reject(error);
      }
    }, 0);
  });
}

runTimerTask().catch(error => console.log(error.name)); // SyntaxError

注意回调里面还是写了 try/catch。因为 Promise 构造器只会自动捕获执行器函数同步执行时抛出的错误，定时器回调是后来才跑的，不在这个范围里，抛错必须自己 reject。

事件监听也是同样的道理。即使把处理函数写成 async，事件系统也不会等它返回的 Promise，失败了没人管，所以处理函数内部要自己捕获错误。

then 的第二个参数能接住什么

JavaScript
const result = Promise.resolve(1).then(
  () => {
    throw new Error('后处理失败');
  },
  () => '只处理原 Promise 的拒绝',
);
result.catch(error => console.log(error.message)); // 后处理失败

第一个回调抛了错，可第二个回调没有执行，错误被后面的 .catch() 接住了。

因为 then 的两个参数都是针对前一个 Promise 的：前一个成功走第一个，前一个失败走第二个。第一个回调自己抛的错，属于 then 返回的新 Promise，只有后面的步骤能处理。所以通常在链的末尾接一个 .catch()，它能接住前面所有步骤的错误。

全局兜底怎么做

JavaScript
window.addEventListener('error', (event) => {
  report({ message: event.message, stack: event.error?.stack });
});

window.addEventListener('unhandledrejection', (event) => {
  report({ reason: String(event.reason) });
});

error 事件收集没被捕获的同步错误，unhandledrejection 收集没人处理的 Promise 拒绝。用的时候有几点要注意。

图片、脚本这类资源加载失败也会触发 error，但这个事件不会冒泡到 window，所以要在捕获阶段监听，写成 addEventListener('error', fn, true)。

跨源加载的脚本出错时，默认只能看到 Script error.，看不到具体信息。要让 script 标签带上 crossorigin 属性，并且服务器返回 CORS 响应头，才能拿到详情。

一个拒绝先被报成未处理，之后又补上了处理函数，会再触发一次 rejectionhandled 事件。

report 函数自己也要捕获异常。否则上报请求失败，又会产生一个新的未处理拒绝。

业务代码里怎样处理错误

不同的错误要不同处理。网络失败可以提示用户重试，字段校验错误要定位到具体字段，用户主动取消（错误名是 AbortError）通常什么都不用提示。

写 catch(() => []) 要谨慎，只有当“失败”确实等于“没有数据”时才这么写，否则接口坏了，页面却显示一个空列表，用户和开发都发现不了。

包装错误时，用 new Error('加载订单失败', { cause: error }) 把原来的错误保留下来，排查时能看到最初的原因。上报时不要带上令牌和完整的表单内容。

finally 里不要 return，也不要抛新错误，否则会把原来的结果或错误覆盖掉。

常见追问

Node.js 里未处理的拒绝怎么处理？

Node.js 默认会让进程以错误退出。可以监听 process.on('unhandledRejection') 做兜底，这和浏览器的 unhandledrejection 事件不是同一套接口。

React 渲染时出错怎么办？

用错误边界组件，它能接住子组件渲染过程中的错误，显示备用界面。但它接不住事件处理函数和异步代码里的错误，这些还要自己 try/catch。
