同步错误、Promise 拒绝和全局异常应该怎样处理？

try/catch 只能捕获其执行范围内实际抛出的异常；在之后执行的计时器回调中抛错，不会被注册计时器时的 try 捕获。Promise 链需要 catch，async 函数应在调用边界处理返回的 Promise。

参考答案

try/catch 只能捕获其执行范围内实际抛出的异常；在之后执行的计时器回调中抛错，不会被注册计时器时的 try 捕获。Promise 链需要 catch，async 函数应在调用边界处理返回的 Promise。

可以把过程拆成表达式求值、函数调用、任务排队和副作用清理四步。先写一个只包含关键变量的最小例子，再逐步加入闭包、异常或异步操作，能更容易看出结果是在哪一步产生的。

浏览器的 error 与 unhandledrejection 事件可作为兜底观测入口，但不能替代业务层恢复策略。记录错误时应包含操作上下文、版本和必要的堆栈，同时避免泄露访问令牌或敏感表单数据。

区分用户可重试的失败与程序错误：前者给出可执行提示，后者保留诊断信息。不要为了“控制台干净”统一返回成功或空数组，否则会把真实故障伪装成正常业务结果。

如果几个写法都能得到同样输出，还要比较可读性、执行时机、内存占用和取消方式。涉及 Promise、事件或资源时，完成结果和清理结果要分别验证。

在实际项目中，搜索框、定时器、事件监听和请求经常同时存在。先写出每一步的触发顺序，再决定在哪里更新状态、在哪里清理资源，能避免“结果看起来对，但偶尔重复、过期或无法取消”的问题。
