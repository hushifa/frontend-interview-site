Proxy 与 Reflect 能实现什么，存在哪些限制？

Proxy 拦截对象的内部操作，Reflect 提供对应的转发接口。正确处理 receiver 能保留访问器语义，但代理仍受不变量、对象身份、内部槽与私有品牌限制，也不会自动构成完整响应式系统。

参考答案

Proxy 可以在对象被读取、写入、删除、枚举等操作发生时插入逻辑。它不是提前复制对象，也不是为每个属性安装一对 getter/setter，而是为目标对象建立一个代理入口，通过 handler 中的 trap 拦截对应内部操作。

常见用途包括开发期校验、访问记录、惰性包装以及响应式追踪。不过“能拦截 get/set”与“已经做出了完整响应式系统”之间还有很大距离。

一个记录读取并校验价格的代理

JavaScript
const reads = [];
const target = {
  price: 10,
  get total() {
    return this.price * 2;
  },
};

const product = new Proxy(target, {
  get(object, key, receiver) {
    reads.push(String(key));
    return Reflect.get(object, key, receiver);
  },
  set(object, key, value, receiver) {
    if (key === 'price' && (!Number.isFinite(value) || value < 0)) {
      throw new RangeError('价格必须是非负有限数值');
    }
    return Reflect.set(object, key, value, receiver);
  },
});

console.log(product.total); // 20
console.log(reads.join(',')); // total,price
product.price = 12;
console.log(target.price); // 12
console.log(product === target); // false

读取 product.total 先进入 get trap。随后 Reflect.get 找到 total 的 getter，并把 receiver，也就是这次读取的接收者，作为 getter 的 this。getter 中的 this.price 又经过代理，因此记录了 total 和 price 两次读取。

这个例子只记录访问和校验某项赋值，没有实现订阅、更新通知或批处理。数组 reads 本身也会不断增长，只适合演示，不应不加限制地作为长期运行的日志容器。

为什么不直接返回 target[key]

如果在 get trap 中写 return object[key]，total 的 getter 会以原 target 为 this。它内部读取 this.price 就直接读原对象，不再经过代理，因此可能漏掉依赖追踪。

receiver 也不一定永远是代理本身。例如一个对象以该代理为原型，读取继承 getter 时，receiver 可以是那个派生对象。使用 Reflect.get(target, key, receiver) 能保留普通属性访问应有的接收者关系。

Reflect.set 的 receiver 同样会影响 setter 的 this，以及相应属性最终应定义到哪里。只写 target[key] = value; return true，容易绕过这些语义，还可能把一个失败赋值谎报为成功。

Reflect 方法不是“绕过所有代理的魔法出口”。如果把代理本身又传回 Reflect.get，仍然可能再次进入 trap，造成递归。常见转发写法把传入的原 target 交给 Reflect，同时保留 receiver。

Object.keys 不只需要键列表，还要判断自身描述符与可枚举性，因此可能同时涉及 ownKeys 和 getOwnPropertyDescriptor。对象展开还要继续读取属性值。一次高层语法对应多个内部步骤，是设计代理逻辑时容易漏掉的地方。

目标本身不可调用时，单纯添加 apply trap 不会把普通对象变成函数；不可构造的目标也不会仅因提供 construct 就获得构造能力。代理仍必须服从目标所能支持的基本操作种类。

trap 不能随意违背对象不变量

JavaScript
const locked = {};
Object.defineProperty(locked, 'id', {
  value: 7,
  writable: false,
  configurable: false,
});

const proxy = new Proxy(locked, {
  get() {
    return 8;
  },
});

try {
  console.log(proxy.id);
} catch (error) {
  console.log(error.name); // TypeError
}

id 是不可配置、不可写的自身数据属性，代理不能把读取结果任意改成另一个值。浏览器会检查这些不变量，违背时抛错。

类似地，ownKeys 不能随意漏掉不可配置属性；不可扩展目标还会限制报告的键集合。set 等 trap 也有返回值与不变量约束，严格模式下报告失败的赋值会表现为异常。

因此实现“虚拟属性”“只读对象”等方案时，要同时考虑目标的描述符和扩展状态，不能只实现几个最常见的读取分支。

为什么空代理包住 Map 也可能不能正常用

JavaScript
const values = new Proxy(new Map(), {});
try {
  values.set('a', 1);
} catch (error) {
  console.log(error.name); // TypeError
}

Map 方法要求 this 具备相应内部槽，而代理本身不是拥有那些 Map 内部槽的原对象。普通方法调用把代理作为 this，因此即使 handler 为空，也不能把它当成对所有内置对象完全透明的包装。

依赖类私有元素的方法也可能因接收者不具备正确私有品牌而失败。把特定方法绑定到原目标可以解决部分接收者问题，但会改变函数身份和 this 行为，内部访问还可能绕过预期追踪。不能不分析对象类型就把所有函数自动 bind，然后宣称得到了通用代理。

完整系统还要处理身份、深层结构与生命周期

代理和原对象不是同一个身份，放进 Map、Set 或用于严格比较时应明确使用哪一方。直接修改原 target 不会凭空经过代理的 set trap，所以把原对象随处泄漏，会破坏入口校验或追踪约定。

普通代理也不会自动递归包装所有嵌套对象。需要深层追踪时，通常要维护原对象到代理的缓存，避免同一个对象每次读取都生成新代理；还要区分属性新增、更新、删除、数组 length 和集合内部变更等操作。

Proxy.revocable 可以提供撤销后的不可用代理，但撤销并不会取消已经发出的请求，也不会删除外部代码早已持有的原对象引用。代理适合管理受控入口，不能独自作为运行不可信代码的完整沙箱。
