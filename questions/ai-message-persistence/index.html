AI 会话持久化为什么不能只保存最后一段回答？

一条助手回答可能由文本、工具调用、工具结果、引用和附件组成。持久化要保存这些片段及其状态，区分界面展示数据和发给模型的上下文，并处理 schema 升级和附件引用。

参考答案

简答

  • 只存最终文字会丢掉工具调用、工具结果和引用，下次继续对话时模型看不到这些上下文，界面也无法还原。
  • 消息由有序片段组成，消息和片段都有稳定 ID，记录 schema 版本和所属用户。
  • 界面记录不等于模型输入：重新调用模型前，从记录中转换出需要的消息，并在服务端校验角色和来源。
  • 流式回答按检查点保存，关键事件（工具开始、成功、失败）立即落库。
  • 附件保存受控的文件 ID，不保存 blob: URL 或会过期的签名链接。

数据结构

TypeScript
type Message = {
  id: string;
  conversationId: string;
  ownerId: string;
  role: 'user' | 'assistant';
  schemaVersion: number;
  status: 'streaming' | 'complete' | 'interrupted' | 'failed';
  parts: Array<
    | { id: string; type: 'text'; text: string }
    | { id: string; type: 'tool-call'; callId: string; name: string; args: unknown }
    | { id: string; type: 'tool-result'; callId: string; result: unknown }
    | { id: string; type: 'citation'; sourceId: string }
    | { id: string; type: 'file'; fileId: string; mediaType: string }
  >;
};
  • 排序以服务端序号为准，不靠数组下标或客户端时间戳。
  • 重试生成新的尝试记录，不覆盖失败的那次。
  • 工具调用和工具结果按 callId 成对保存。只有调用没有结果，模型 API 通常会拒绝这段历史。

展示数据和模型输入

界面记录里还有上传进度、按钮状态、调试信息等，发给模型时要过滤掉。客户端提交的历史不能直接信任：服务端从数据库读取历史，而不是采用浏览器传来的 role: 'system' 或伪造的工具结果。

SDK 升级可能改变片段类型。旧记录能解析不代表语义一致，按 schemaVersion 写迁移逻辑，并测试旧会话能否展示、继续提问和删除。

流式保存

  • 只在结束时保存，进程中途退出会丢失整段回答；每个 token 都写库，写入量又太大。常见做法是每隔一段时间或一定字数存一次检查点。
  • 写入带消息 ID 和版本号，旧检查点不能覆盖已完成的状态。
  • 界面上"已保存"要区分本地草稿和服务端确认。
  • 刷新后显示"正在生成"之前，先向服务端查询运行状态，恢复流程见"AI 流式输出断线后，怎样恢复同一条生成任务？"。

附件和本地草稿

  • blob: URL 只在当前页面有效，签名 URL 会过期。保存文件 ID，展示时重新申请访问地址。
  • localStorage 或 IndexedDB 里的草稿要按账号隔离，退出登录时清除。
  • 每次读取会话都校验归属。会话 ID 再长也不是权限凭证。

常见追问

  • 历史太长怎么办？ 持久化保存完整记录，发送给模型时再截断或摘要，规则见"为什么不能用字符串长度准确计算 Token 和费用？"。
  • 删除会话要删什么？ 消息、片段、附件文件和相关日志都要按保留策略删除，而不只是在界面上隐藏。
