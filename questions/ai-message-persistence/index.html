AI 会话持久化为什么不能只保存最后一段回答？

完整会话通常包含用户与助手消息、稳定 ID、有序消息片段、工具调用及结果，可能还包含来源和状态信息。只保存最终文字会丢失继续交互所需的结构，刷新后也难以准确恢复中断位置。

参考答案

保存最后一段回答可以恢复一张聊天截图，却不一定能恢复一次对话。工具调用与结果、附件、引用、取消原因和未完成文本都会影响后续交互，单个字符串无法保留这些关系。

首先要区分三件事：恢复历史展示、重新构造模型上下文、恢复仍在执行的任务。它们可能使用同一批数据，但不是同一个操作。

消息应有身份、结构与版本

用户消息、助手消息和工具相关内容需要稳定 ID。一个消息可以有多个按序 part，例如文字、附件引用、工具输入和结果；part 也应有能关联增量更新的身份。

存储记录通常还需要所属会话、用户或租户、创建时间、状态与 schema 版本。时间戳不一定能唯一排序，并发或跨设备时最好有服务端定义的顺序或版本。

数组下标不能作为长期 ID：删除一条历史消息后，后面全部下标变化，迟到增量可能被写进错误对象。重试也应有新的尝试身份或明确替换关系。

UI 消息不应原样当成模型输入

展示记录可能包含上传进度、批准按钮状态、调试信息或资源 URL；模型输入只应包含当前任务需要且接口允许的内容。

重新调用模型前，要验证持久化结构并做明确转换，保持工具调用与结果配对。历史里出现 tool 或 system 角色，也不能直接相信它来自可信执行端，客户端提交的记录需要校验来源与权限。

SDK 升级可能改变 part 类型或状态字段。旧 JSON 能解析，不表示语义兼容；应保留版本和迁移逻辑，并测试旧会话在新版本中的展示与继续使用。

流式保存要权衡丢失窗口与写入成本

只在生成结束后保存，断线或进程退出可能丢掉全部部分结果；每个 token 都写数据库，又会增加压力和无意义版本。

可以按时间、内容量或语义事件保存检查点，工具状态和终止状态则按重要性及时落盘。要明确某一时刻界面已显示的内容是否已经持久化，不能把前端缓存当成服务端提交成功。

写入使用消息 ID、运行 ID 和事件序号等实现幂等，避免重复事件追加两次。并发更新需要版本控制，不能让旧检查点覆盖更新的完成状态。

任务恢复需要服务端持续状态

刷新后显示“正在生成”，不代表后台真的仍在运行。应查询任务状态、恢复令牌或事件位置，并处理任务已结束、过期或不存在。

如果服务端支持重连，客户端按游标补齐缺失事件并去重；如果不支持，就明确保留部分答案并提供重新生成，不要把一次新请求伪装成同一个任务的无缝延续。

恢复历史不能重新执行已经成功的工具。工具的调用标识、批准记录和外部执行结果需要独立保存，副作用重试还要有幂等或状态核对。

附件应保存引用，不保存临时浏览器地址

blob: URL 与当前浏览器资源生命周期相关，不适合作为跨设备历史附件地址。应保存受控文件 ID、必要元数据和权限关系，展示时再申请有效访问方式。

临时签名 URL 也可能过期，不宜当成永久事实保存后永远复用。删除会话时，还要根据数据保留策略处理附件、检索派生数据和任务记录，不能只从消息列表移除一行。

本地草稿与服务端历史承担不同责任

localStorage 或 IndexedDB 可以保存本地草稿，但不自动提供跨设备同步、访问授权或可靠的秘密保护。多个账号共用设备时，还要避免旧草稿泄露给新登录用户。

服务端读取与写入每次都应检查会话归属，不能因为 chat ID 很长就把它当权限凭证。限制记录体积、保护敏感字段，并让用户理解删除和恢复范围。

测试至少覆盖中途断线、重复事件、跨标签页更新、SDK 格式迁移、附件过期和取消后的刷新。能显示最后一句话，只是持久化最浅的一层。
