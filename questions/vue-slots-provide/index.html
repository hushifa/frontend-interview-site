插槽、作用域插槽和 provide/inject 各解决什么问题？

插槽决定组件区域由谁提供内容，作用域插槽让子级把渲染所需数据交给内容提供者，provide/inject 则解决跨层依赖传递。内容作用域、数据所有权和注入的响应式来源需要分别理解。

参考答案

简答

默认插槽和具名插槽让父级向子组件指定区域传入内容，内容在父级作用域中编译。作用域插槽由子组件把数据通过插槽 props 交给父级，用来定制渲染，例如列表项模板。provide/inject 用于跨多层传递依赖，避免逐层透传 props。要让注入的值保持响应，provide 时传 ref 或 computed，并尽量把修改方法也一起提供，让状态由提供者统一管理。

一个列表组件负责布局，但每一行怎样显示由调用方决定，这适合插槽。一个主题值需要经过多层布局组件传给深处按钮，却不想让每一层都转发 theme，这适合 provide/inject。

两者都能让组件协作，但一个主要表达内容组合，另一个主要表达依赖来源。把它们都当成“省传参工具”，容易忽略作用域和所有权。

子组件提供位置与插槽参数

vue
<!-- ItemList.vue -->
<script setup>
const props = defineProps({
  items: { type: Array, required: true },
  label: { type: String, default: '列表' },
});
</script>

<template>
  <ul :aria-label="props.label">
    <li v-for="(item, index) in props.items" :key="item.id">
      <slot name="item" :item="item" :index="index">
        <span>{{ item.title }}</span>
      </slot>
    </li>
  </ul>
</template>

item 是具名插槽，子组件通过插槽参数公开当前记录和索引。调用方没有提供这个插槽时，使用 span 里的默认内容。

普通插槽内容使用定义它的父级作用域，不能无条件访问子组件的内部变量。作用域插槽提供的是明确参数，不是把子组件的全部 setup 状态都开放出去。

跨层主题使用共享注入键

JavaScript
// themeKey.js
export const themeKey = Symbol('阅读主题');
vue
<!-- ThemedButton.vue -->
<script setup>
import { inject } from 'vue';
import { themeKey } from './themeKey.js';

const context = inject(themeKey, null);
if (!context) throw new Error('主题按钮需要上层主题提供者');
const { theme, toggle } = context;
</script>

<template>
  <button type="button" :data-theme="theme" @click="toggle">切换主题：{{ theme }}</button>
</template>
vue
<!-- ThemePanel.vue -->
<script setup>
import ThemedButton from './ThemedButton.vue';
</script>

<template>
  <section>
    <h3>阅读外观</h3>
    <ThemedButton />
  </section>
</template>

ThemePanel 没有接收或转发 theme，深处按钮通过共享的 Symbol 键向上查找。提供者与消费者必须使用同一个键对象；分别写两次 Symbol('阅读主题') 会创建两个不同值，即使描述字符串相同也不能匹配。

父级同时组织内容与修改权限

vue
<!-- Parent.vue -->
<script setup>
import { provide, readonly, ref } from 'vue';
import ItemList from './ItemList.vue';
import ThemePanel from './ThemePanel.vue';
import { themeKey } from './themeKey.js';

const prefix = ref('学习');
const items = [
  { id: 'html', title: 'HTML' },
  { id: 'css', title: 'CSS' },
];
const theme = ref('light');
function toggle() {
  theme.value = theme.value === 'light' ? 'dark' : 'light';
}
provide(themeKey, { theme: readonly(theme), toggle });
</script>

<template>
  <main>
    <button type="button" @click="prefix = '复习'">修改前缀</button>
    <ItemList :items="items" label="定制列表">
      <template #item="{ item, index }">
        <strong>{{ prefix }} {{ index + 1 }} {{ item.title }}</strong>
      </template>
    </ItemList>
    <ItemList :items="items" label="默认列表" />
    <p>父级主题：{{ theme }}</p>
    <ThemePanel />
  </main>
</template>

插槽中的 prefix 来自父级，item 与 index 来自子级传出的插槽参数，两个来源明确地组合在一起。修改 prefix 会更新定制内容，但不会把子组件的默认插槽文本变成同一套自定义内容。

主题则由父级创建，向下提供只读视图和明确的 toggle 方法。深处按钮可以请求切换，但不需要自己决定怎样直接修改父级的任意状态。

注入一个值，不会自动让它变成响应式

provide(key, count.value) 传出的是当时的普通值，之后 count 变化不会凭空把那个数字变成响应式连接。传递 ref、reactive 或 computed 等合适来源，消费者才可以沿关系持续读取变化。

inject 得到 ref 时，在 JavaScript 中仍按 ref 的接口使用；放到模板中则遵循模板解包规则。示例解构出来的 theme 本身就是 ref，所以没有像解构普通 reactive 原始属性那样丢失连接。

readonly 主要限制消费者通过该视图修改，修改逻辑仍放在提供者。它不是权限系统，也不会取消应用中其他可变引用的存在。

最近提供者与默认值应体现契约

同一个注入键有多个祖先提供者时，读取最近的那一个。这适合局部覆盖主题或配置，但也会让来源更隐蔽，组件文档应说明它依赖哪些上下文。

缺失时可以提供合理默认值，也可以像示例一样直接报告使用错误。某个能力如果没有提供者就无法正常工作，不应返回一个悄悄什么都不做的空函数，让失败延迟到更难定位的位置。

应用级 provide 可以为整棵应用提供依赖，但不等于应该把所有状态都放到全局。SSR 还需要按请求隔离用户数据，避免模块级共享对象串用不同请求。

插槽参数也不是任意修改权

通过作用域插槽拿到一个对象，可能仍然是原数据的引用。调用方直接修改它，会影响真实所有者；是否允许这种写法，应由组件契约决定，不能因为“子组件公开了 item”就默认允许随意改动。

复杂组件可以额外公开明确操作函数，例如选中或删除请求，让数据流仍可追踪。动态插槽名、条件插槽和回退内容也应按实际渲染验证，而不是只检查有没有传一个同名模板。

内容高度、CSS 作用范围与逻辑作用域同样不同。插槽内容在哪里定义，决定它能访问哪些变量；最终 DOM 在哪里，仍会影响布局与样式。Teleport 等改变物理位置时，更需要分别看这些关系。

组合得当时，插槽让组件保留布局与行为的可复用性，provide/inject 让稳定依赖跨层可达。两者都应有小而清楚的公开接口，避免把组件变成只有放在某一棵巨大页面树里才碰巧可用的隐式组合。
