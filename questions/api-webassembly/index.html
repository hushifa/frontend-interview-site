WebAssembly 能替代 JavaScript 吗？适合哪些工作？

不能替代。WebAssembly 是浏览器里运行的二进制格式，适合把 C、C++、Rust 写的库或大量计算搬到网页；它不能直接操作 DOM，和 JavaScript 互相调用有开销，通常是两者配合。

参考答案

简答

不能替代，它们是配合关系。WebAssembly（简称 Wasm）是一种紧凑的二进制格式，浏览器把它编译成机器码执行，性能稳定，适合大量数值计算。它和 JavaScript 跑在同一个沙箱里，安全限制也一样。

它的短板是不能直接访问 DOM 和大多数 Web API，要通过 JavaScript 胶水代码去调用。而且 JavaScript 和 Wasm 之间互相调用、复制数据都有开销。

所以它适合“计算重、和页面交互少”的活：图像视频处理、音频编解码、压缩、加密、游戏引擎、CAD，以及把现成的 C++ 或 Rust 库移植到网页。普通界面逻辑、频繁操作 DOM 的代码不适合，跨边界的开销会把收益吃掉。

还要注意，Wasm 默认也在主线程跑，长时间计算一样会卡页面，要放进 Worker。它也不一定比 JavaScript 快。

加载一个 Wasm 模块

下面加载一个图片处理模块，并给它提供一个打印日志的函数。

JavaScript
const { instance } = await WebAssembly.instantiateStreaming(fetch('/image.wasm'), {
  env: { log: (value) => console.log(value) },
});

const result = instance.exports.blur(ptr, width, height);

instantiateStreaming 边下载边编译，不用等整个文件下完。但服务端要返回 Content-Type: application/wasm，否则会失败。

第二个参数叫导入对象，是 JavaScript 交给 Wasm 的函数。Wasm 自己调不了 console.log，要通过这里的 env.log 调回 JavaScript。反过来，Wasm 导出的函数在 instance.exports 上。

一张图片怎么传给 Wasm

Wasm 函数的参数和返回值以数值为主：i32、f32、f64 对应 JavaScript 的 Number，i64 对应 BigInt。externref 可以原样传递 JavaScript 引用，但 Wasm 读不了它内部的结构。所以没法把一个图片对象直接塞进去。

做法是共用一块内存。这块内存叫线性内存（WebAssembly.Memory），可以理解成一个大字节数组：

  1. JavaScript 用 Uint8Array 视图把图片像素写进这块内存。
  2. 把数据所在的位置（偏移量，也就是指针）和长度，作为数字传给 Wasm 函数。
  3. Wasm 在内存里处理完，JavaScript 再从同一块内存里读出结果。

所以收益来自“一次传进大量数据，在 Wasm 里做很多计算”。如果频繁调用小函数，每次都要跨边界，开销反而大。这些胶水代码一般不用手写，Rust 的 wasm-bindgen、C++ 的 Emscripten 会自动生成。

为什么还要配合 Worker

Wasm 默认在主线程执行。一段计算跑 2 秒，页面就卡 2 秒，和 JavaScript 没区别。所以重计算要放到 Web Worker 里。

多线程 Wasm 依赖 SharedArrayBuffer，这要求页面处于跨源隔离状态。

常见追问

Wasm 一定比 JavaScript 快吗？

不一定。JIT 优化后的 JavaScript 在很多场景已经很快了。Wasm 的优势在于性能稳定，不用等 JIT 预热，以及不需要 GC 的数值计算。

WasmGC 是什么？

它让 Kotlin、Dart 这类带垃圾回收的语言能编译成 Wasm，直接用浏览器的垃圾回收，不用把自己的 GC 打包进去。主流浏览器已经支持。
