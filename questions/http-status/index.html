常见 HTTP 状态码应该怎样在前端区分处理？

2xx 成功、3xx 重定向、4xx 是请求方的问题、5xx 是服务器的问题。前端按具体状态码处理：401 去登录，403 提示没权限，429 和 503 等一会再试，其他 4xx 不要重试。

参考答案

简答

状态码的第一位就是大类：2 开头是成功，3 开头是重定向，4 开头是请求方的问题，5 开头是服务器的问题。但前端不能只看大类，要按具体的码决定怎么做。

最常被问的是 401 和 403。401 是“不知道你是谁”，要去登录或刷新令牌；403 是“知道你是谁，但你没权限”，重新登录也没用。

再就是要不要重试。429 和 503 是暂时的，按 Retry-After 等一会再试；400、404、422 这类问题出在请求本身，重试多少次都一样。

还有两个小坑。204 没有正文，直接调 response.json() 会报错。301、302、307、308 这些重定向 fetch 会自动跟随，脚本一般看不到；304 由浏览器缓存自己处理。

常用状态码和前端怎么处理

状态码含义前端处理
200成功读取正文
201已创建可读 Location 头获取新资源地址
202已接受，尚未处理完轮询任务状态或等待推送
204成功，无正文不解析正文
301 / 308永久重定向308 保持方法和请求体
302 / 307临时重定向307 保持方法和请求体
304未修改浏览器复用缓存
400请求格式错误修正请求，不重试
401未认证登录或刷新令牌
403已认证但无权限提示无权限
404资源不存在显示空状态
409冲突，如版本过期提示刷新后重试
422语义校验失败显示字段错误

500服务器内部错误提示稍后再试，可有限重试幂等请求
502 / 504网关错误或超时可有限重试幂等请求
503暂时不可用按 Retry-After 退避

307、308 和 301、302 差在哪

这四个都是重定向，看起来差不多，区别在会不会改请求方法。

历史上，客户端遇到 301 和 302 时，会把 POST 改成 GET 再去新地址，请求体也丢了。307 和 308 是后来专门补上的，明确要求不许改方法、保留请求体。307 是临时的，308 是永久的。所以接口要做重定向时，优先用 307 和 308。

统一处理怎么写

实际项目里一般在请求函数里统一分流：

JavaScript
async function request(url, init) {
  const response = await fetch(url, init);
  if (response.ok) return response.status === 204 ? null : response.json();

  switch (response.status) {
    case 401:
      redirectToLogin();
      break;
    case 429:
    case 503: {
      const seconds = Number(response.headers.get('Retry-After'));
      throw Object.assign(new Error('稍后重试'), { retryAfter: seconds || 5 });
    }
  }
  throw Object.assign(new Error(`HTTP ${response.status}`), { status: response.status });
}

成功时先判断 204，避免解析空正文报错。429 和 503 把等待秒数挂在错误上，交给调用方决定什么时候重试。

这里的 Number(...) 只处理了秒数。Retry-After 还可能是一个 HTTP 日期，这时 Number 得到 NaN，代码退回默认 5 秒。生产代码要两种格式都解析。fetch 本身什么时候进 catch，见《为什么 fetch 收到 404 不一定进入 catch？》。

常见追问

业务错误该用 200 加错误码，还是用 4xx？

用 HTTP 状态码表达协议层的结果，这样监控、缓存和网关都能正确识别。业务上的细节放在响应体里。

跨源重定向会怎样？

fetch 跟随重定向时会重新做一次 CORS 检查，重定向的目标也必须允许这个来源。
