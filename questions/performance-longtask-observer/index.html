Long Tasks API 怎样帮助定位主线程卡顿？

Long Tasks API 能记录主线程连续占用超过 50ms 的时间段，为线上定位输入延迟提供线索；它不是函数调用栈，也不能单独代表 INP 或页面流畅度。

参考答案

简答

  • Long Tasks API 报告主线程超过 50ms 的忙碌区间，但不给出具体函数。
  • 观察器要轻量可清理，回调在任务结束后才收到通知。
  • attribution 不是调用栈，要把长任务与用户操作的 mark 对齐分析。
  • Long Task、TBT、INP 是不同指标；Chromium 中优先用 LoAF。

主线程为什么会让按钮“没有反应”

Long Tasks API 记录主线程连续忙碌超过 50ms 的时间段，告诉你“这里有一段可能影响交互的工作”。它不会直接告诉你是哪一行函数慢，也不会中断已经开始的任务。

建立观察器时要轻量且可清理

JavaScript
function watchLongTasks(onTask) {
  if (
    typeof PerformanceObserver === 'undefined' ||
    !PerformanceObserver.supportedEntryTypes?.includes('longtask')
  ) return () => {};

  const observer = new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
      onTask({
        startTime: entry.startTime,
        duration: entry.duration,
        containers: entry.attribution.map((item) => ({
          type: item.containerType,
          id: item.containerId,
        })),
      });
    }
  });

  observer.observe({ type: 'longtask', buffered: true });
  return () => observer.disconnect();
}

buffered 只能读取当前性能时间线中仍可用的条目，不是完整历史。回调通常在任务结束后才收到通知，不能用它实时打断任务。上报逻辑应放入有上限的队列并批量发送，不能在回调中同步序列化大对象，否则监控本身会增加主线程负担。

组件卸载或页面切换时要断开观察器，避免重复订阅。能力检测失败时应正常降级，不能因为浏览器不支持就阻塞页面功能。

attribution 不是慢函数的调用栈

归属信息有助于区分当前页面、iframe 或容器，但跨源隐私限制可能让信息很少。containerId 也不等于具体业务函数。要知道究竟是 JSON 解析、渲染、布局还是第三方脚本耗时，仍需在实验室用 Performance 面板录制相同操作，查看调用栈和任务内部事件。

线上记录页面类型、应用版本、设备和必要的业务阶段即可。完整容器 URL 可能带查询参数和敏感信息，不应默认上报。在 Chromium 中，Long Animation Frames（LoAF）能把长帧归因到具体脚本，诊断交互卡顿时优先使用；其他浏览器不支持时，再用 Long Tasks 作为降级信号。两者的统计口径不同，不能混成一个数。

把长任务和用户操作对齐

startTime 和 duration 给出一段与当前页面性能时间基准一致的区间。可以把它和点击、输入、路由切换的 mark 对齐，判断用户操作是否落在忙碌区间内：

JavaScript
performance.mark('search-click');
// 更新筛选条件或开始请求

一个 120ms 的长任务不一定影响用户；如果它发生在页面空闲时，优先级可能低于一个 60ms 但正好阻塞输入的任务。只统计长任务数量而不看页面类型和用户操作，会把修复重点放错。

不要把 Long Task、TBT 和 INP 混成一个指标

Long Task 的 duration 是整个忙碌区间。实验室 TBT 可能只累计特定窗口内每个任务超过 50ms 的部分，还受测量窗口和算法影响；把所有 Long Task 相加不能叫 TBT。

INP 关注交互发生到下一次呈现的延迟，除了主线程任务，还受事件处理、布局、绘制和交互选择规则影响。没有 Long Task 不代表 INP 一定好，许多短任务连在一起、布局更新或观测不支持都可能隐藏问题。

从监测到修复要形成闭环

先用 RUM 找出移动端搜索、列表展开等高影响场景，再在受控设备上录制调用栈。修复方向可能是分片、延迟非关键工作、减少同步 JSON 处理、虚拟化列表或移到 Worker。把一个大任务机械地切成很多微任务，也不保证浏览器会及时处理输入和绘制，需要用交互指标验证。

最终应同时观察长任务分布、INP、错误率和功能完成率。Long Tasks API 是定位线索，不是“页面流畅”的单一证明。
