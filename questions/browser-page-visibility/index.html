Page Visibility API 适合处理哪些页面生命周期场景？

document.visibilityState 告诉你页面当前在不在前台，切换时触发 visibilitychange。适合在后台暂停轮询、动画和计时，回来时马上刷新一次。

参考答案

简答

用户切到别的标签页，你的页面还在每 5 秒轮询一次接口，这既浪费流量也浪费电。Page Visibility API 能告诉你页面现在是不是在前台：document.visibilityState 是 visible 或 hidden，变化时触发 visibilitychange 事件。

切换标签页、最小化窗口、锁屏、手机切到后台，都会变成 hidden。

它适合在隐藏时暂停轮询、动画、视频和计时，恢复可见时立刻刷新一次。变成 hidden 时也是保存草稿的好时机。

要注意它说的是整个文档在不在前台，不管页面里某个元素有没有在视口里。判断元素可见用 IntersectionObserver。

先看一个只在可见时走动的时钟

下面的时钟在页面隐藏时停下，回来时马上显示当前时间：

JavaScript
function startVisibleClock(element) {
  let timer;

  const render = () => {
    const now = new Date();
    element.dateTime = now.toISOString();
    element.textContent = now.toLocaleTimeString('zh-CN', { hour12: false });
  };

  const sync = () => {
    clearInterval(timer);
    timer = undefined;
    if (document.visibilityState !== 'visible') return;

    render();
    timer = setInterval(render, 1000);
  };

  document.addEventListener('visibilitychange', sync);
  sync();
  return () => {
    document.removeEventListener('visibilitychange', sync);
    clearInterval(timer);
  };
}

所有逻辑都在 sync 里。页面变成 hidden，它清掉定时器就返回；变回 visible，它先渲染一次，再开新的定时器。

为什么每次都要先 clearInterval？因为 visible 可能连续收到好几次。如果不先清，每次都新开一个定时器，最后会有好几个定时器同时在跑。先清再开，就保证只有一个。

为什么恢复时要立刻 render()？如果只开定时器，要等一秒才更新，这一秒里显示的还是隐藏前那一刻的时间。

最后返回的函数同时移除监听器和定时器，组件卸载时调用它，什么都不会留下。

实际开发中用在哪里

最常见的是轮询接口：隐藏时停止，可见时立即请求一次，再恢复轮询。视频和轮播图也一样，隐藏时暂停。

统计停留时长时，只累计可见的那段时间，否则用户开着标签页去吃饭，停留时长就虚高了。

保存草稿放在变成 hidden 的时候。在移动端，这是最后一个可靠的时机，用户可能接着就把应用从后台杀掉了。

常见追问

document.hidden 和 visibilityState 有什么区别？

document.hidden 是个布尔值，等价于 visibilityState === 'hidden'。两者说的是同一件事，visibilityState 是字符串，读起来更直观。

页面在后台时，定时器和动画会怎样？

会被浏览器限制，requestAnimationFrame 暂停，定时器被节流。详见《页面进入后台后，计时器和动画还会按原速度运行吗？》。
