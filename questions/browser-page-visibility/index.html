Page Visibility API 适合处理哪些页面生命周期场景？

Page Visibility API 感知文档在前台与后台之间的切换，适合暂停非必要工作并在恢复时刷新状态。它不检测单个元素是否可见，也不是可靠的页面关闭或数据保存通知。

参考答案

用户把标签页切到后台时，页面可能仍然存在，脚本和请求也可能继续运行。如果仪表盘还在频繁刷新图表、轮播图继续翻页，就会花费资源做用户暂时看不到的工作。Page Visibility API 让应用知道文档何时可见或隐藏，从而主动调整这些行为。

读取 document.visibilityState 可以获得当前状态，常用的值是 visible 与 hidden；document.hidden 则提供布尔形式。状态变化时，浏览器在 document 上触发 visibilitychange，监听器里再读取当前状态。

“不可见”和“没有焦点”不是同一件事

切换到其他标签页、最小化浏览器等操作通常会让文档进入隐藏状态。但窗口失去焦点时，页面仍可能显示在屏幕上，例如用户在旁边的记事本里输入内容。因此 window.blur 不能替代 visibilitychange。

文档可见也不等于用户正在看某个组件：图表可能在滚动区域下面，弹窗也可能盖住它。需要知道元素是否进入视口，应考虑 Intersection Observer；即便元素进入视口，也不能据此证明人真的注意到了它。

对 iframe，文档可见性通常随父文档变化；仅用 CSS 把 iframe 设为 display: none，不会因此触发该 iframe 文档的可见性事件。嵌入组件不能把这个 API 当成所有隐藏方式的统一通知。

暂停显示时钟，恢复时直接显示真实时间

下面的函数用于已经存在的 <time id="clock"></time>。隐藏时取消定时刷新，恢复时立即读取当前时间，然后继续定期更新。

JavaScript
function startVisibleClock(element) {
  const formatter = new Intl.DateTimeFormat('zh-CN', {
    hour: '2-digit',
    minute: '2-digit',
    second: '2-digit',
    hour12: false,
  });
  let timer;

  function render() {
    const now = new Date();
    element.dateTime = now.toISOString();
    element.textContent = formatter.format(now);
  }

  function syncVisibility() {
    clearInterval(timer);
    timer = undefined;
    if (document.visibilityState !== 'visible') return;

    render();
    timer = setInterval(render, 1000);
  }

  document.addEventListener('visibilitychange', syncVisibility);
  // 组件可能在后台首次创建，注册事件后还要处理当前状态。
  syncVisibility();

  return function dispose() {
    document.removeEventListener('visibilitychange', syncVisibility);
    clearInterval(timer);
  };
}

在 DOM 就绪后，把实际的 <time> 元素传给函数；组件卸载时调用返回的 dispose。首次执行时就读取状态，是因为事件只通知变化，不会自动补发“你现在已经处于后台”的通知。

这里每次读取 new Date()，而不是简单地给旧时间加一秒。浏览器可能延迟计时器回调，隐藏期间也没有执行更新，但恢复时仍然显示真实时间，不必补跑错过的每个 tick。这个例子用于界面时钟，不承诺整秒精确触发，也不适合承担权威计费计时。

请求、媒体和动画需要分别决定策略

后台暂停轮询时，要区分“取消下次定时器”和“取消已经发出的请求”。清除计时器不会停止在途请求；若需要取消，还要传递 AbortSignal，并防止已过期结果在恢复后覆盖新数据。恢复时通常主动刷新一次，再恢复轮询，不要立即补发后台错过的几十次请求。

媒体也不能简单写成“隐藏就暂停，显示就播放”。后台听音乐可能正是用户需要的功能；如果暂停的是视频，还要记录是否由此次隐藏操作暂停，避免返回页面时把用户主动暂停的视频也重新播放。调用 play() 还可能受自动播放策略限制，需要处理返回 Promise 的拒绝。

浏览器通常也会自行节流后台计时器、暂停后台 requestAnimationFrame，但这与应用决定“哪些业务工作值得继续”是两层事情。可见性事件不会自动关闭 WebSocket、停止服务端任务或取消已有的网络请求。

隐藏时保存有价值，但不能等到最后一刻

进入 hidden 常常是移动端应用还来得及观察到的重要时机，可以用来尽早保存小规模的草稿状态、上报一段会话统计。不过用户切换标签页也会进入 hidden，所以它不是“用户关闭网站”的确定信号。

进程可能被操作系统直接终止，不能保证总有事件、也不能保证事件处理器中的异步写入全部完成。重要草稿应在编辑过程中持续或适度防抖保存，恢复时从持久化状态重新加载。统计上报可以按需求考虑 sendBeacon，但成功入队不等于服务端已经收到，更不能把它当成关键业务提交的事务保障。

对于前进后退缓存恢复，还要结合 pageshow 等事件检查状态是否过期。页面重新显示后，不要只恢复动画，还应按业务需求确认数据、登录状态与连接是否仍然有效。
