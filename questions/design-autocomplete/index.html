搜索联想（自动补全）组件要处理哪些问题？

搜索联想要处理四件事：输入防抖减少请求，用 AbortController 取消旧请求并校验返回对应的关键词避免竞态，按关键词缓存结果，再按 WAI-ARIA combobox 模式实现方向键、Enter、Escape 和 aria-expanded、aria-activedescendant 等属性。

参考答案

简答

搜索联想就是用户一边打字，下面一边弹出建议。看着简单，要处理的问题有四个。

第一是请求太多。每敲一个字都请求一次很浪费，所以要防抖，等用户停下来 200 到 300 毫秒再请求。中文输入法正在拼字的时候，也不应该触发搜索。

第二是竞态，也就是旧请求比新请求晚回来，把新结果盖掉。新请求发出时用 AbortController 取消旧的，结果回来时还要再核对一下，它对应的关键词是不是当前输入框里的，不是就丢掉。第三是缓存，按规范化后的关键词缓存结果，用户回删时直接命中，缓存要有容量上限和过期时间。

第四是键盘和无障碍，要按 WAI-ARIA 的 combobox 模式来做。要注意 DOM 焦点一直留在输入框里，用 aria-activedescendant 指向当前高亮的那一项，方向键切换、Enter 选中、Escape 关闭。

防抖时为什么要管输入法

JavaScript
let timer;
input.addEventListener('input', (event) => {
  if (event.isComposing) return; // 组字中不搜索，compositionend 后再处理
  clearTimeout(timer);
  timer = setTimeout(() => search(input.value), 250);
});

每次输入都先清掉上一个定时器，再重新等 250 毫秒，所以只有用户停下来，search 才会真的执行。

那 isComposing 是干什么的？用拼音输入法打“北京”时，输入框里会先出现 bei beij 这些拼音，这个阶段叫组字。这时候去搜索拼音毫无意义，所以直接跳过，等 compositionend 也就是选完字以后再处理。

防抖本身的实现见《怎样实现只在停止调用后执行的防抖函数？》，输入法和竞态放在一起怎么处理，见《中文输入法期间怎样触发搜索？composition 与请求竞态如何一起处理？》。

只取消旧请求为什么还不够

下面是搜索函数，包含了取消、缓存和关键词核对：

JavaScript
let controller;
const cache = new Map();

const normalize = (value) => value.trim().toLowerCase();

async function search(raw) {
  const keyword = normalize(raw);
  if (!keyword) return render([]);
  if (cache.has(keyword)) return render(cache.get(keyword));

  controller?.abort();
  controller = new AbortController();
  try {
    const res = await fetch(`/api/suggest?q=${encodeURIComponent(keyword)}`, {
      signal: controller.signal,
    });
    if (!res.ok) throw new Error(`HTTP ${res.status}`); // 错误响应不进缓存
    const list = await res.json();
    cache.set(keyword, list);
    if (keyword === normalize(input.value)) render(list); // 只渲染当前关键词的结果
  } catch (error) {
    if (error.name !== 'AbortError') renderError();
  }
}

既然每次都 abort() 了旧请求，渲染前为什么还要比较 keyword 和当前输入？因为请求可能在 abort() 之前就已经返回、正在解析了，这时候取消已经来不及。所以渲染之前要再核对一次，确认这份结果对应的还是用户现在输入的词。

还要知道，AbortController 只是让前端不再等这个请求，服务端可能已经处理完了，详见《AbortController 能取消什么，不能取消什么？》。

安全上也有两点。关键词放进 URL 时要用 encodeURIComponent 编码。渲染建议项时用文本节点或框架默认的转义，就算要高亮匹配的片段，也不要拼 HTML 字符串，否则会有 XSS 风险。

缓存要注意什么

缓存的键用规范化后的关键词，也就是去掉首尾空格、统一大小写，这样“ React ”和“react”不会各请求一次。

缓存不能无限长大。Map 会记住插入顺序，可以设个上限，比如 50 条，超了就删最早插入的那条。如果建议数据会变，还要给缓存设过期时间。

键盘和 ARIA 怎么做

combobox 是 ARIA 里“输入框加弹出列表”这种组件的名字。结构大致是这样：

HTML
<label for="city">城市</label>
<input id="city" role="combobox" aria-expanded="true" aria-controls="city-list"
  aria-autocomplete="list" aria-activedescendant="city-opt-2" />
<ul id="city-list" role="listbox">
  <li id="city-opt-1" role="option">北京</li>
  <li id="city-opt-2" role="option" aria-selected="true">上海</li>
</ul>

弹层显示时 aria-expanded 是 true，隐藏时是 false。aria-controls 指向弹出的 listbox，aria-autocomplete="list" 告诉读屏软件，下面的建议是根据输入内容匹配出来的。

为什么焦点要留在输入框，而不是移到选项上？因为用户高亮了一项以后，可能还想继续打字。所以方向键移动时，只更新 aria-activedescendant 和对应选项的 aria-selected，读屏软件会把高亮项读出来，DOM 焦点却不离开输入框。

Enter 接受高亮项，Escape 关闭弹层。输入框原有的文本编辑按键不要拦截。结果数量变了，可以用 aria-live 区域播报，比如“共 5 条建议”。

常见追问

鼠标点选项时，为什么输入框先失焦，弹层就关了？

因为点击时先触发了输入框的 blur，弹层收起来，点击就落空了。可以在选项的 mousedown 上调用 preventDefault() 保住焦点，或者延迟处理 blur。

没有结果时怎么显示？

显示“无匹配结果”，同时让 aria-expanded 和弹层实际显示与否保持一致。

要不要设置最少输入字符数？

结果集很大时可以要求至少输入 1 到 2 个字符，减少太宽泛的查询。
