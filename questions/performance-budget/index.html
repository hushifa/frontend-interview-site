前端性能预算应该怎样制定和落地？

性能预算是"在指定场景下某项指标不能超过的上限"，分为资源预算（JS、CSS、图片体积）、运行时预算（长任务、主线程阻塞）和体验预算（LCP、INP、CLS）。数值来自现有基线和目标，在 CI 中用构建产物和实验室测试检查，线上用 RUM 跟踪趋势。

参考答案

简答

  • 预算必须带条件：哪个页面、什么设备和网络、冷缓存还是热缓存、测哪个指标。
  • 三类预算：资源（首屏 JS 压缩后体积、图片总量）、运行时（Total Blocking Time、最长任务）、体验（LCP、INP、CLS 的 75 分位）。
  • 数值从当前基线出发，结合 Core Web Vitals 的"良好"阈值（LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1）设定，不照搬别人的数字。
  • 设两条线：超过警告线在 PR 中提示，超过阻断线禁止合并，例外要写明原因和复查时间。
  • 体积预算不等于体验：把关键代码改成懒加载，体积达标了，首次交互可能更慢。

预算示例

页面条件预算
首页移动端、4G、冷缓存首屏 JS（gzip）≤ 170 KB，LCP p75 ≤ 2.5s，CLS p75 ≤ 0.1
题目详情直接打开深链接首屏 JS ≤ 150 KB，正文出现 ≤ 2s
搜索真实数据量，连续输入单次输入处理 ≤ 50ms，INP p75 ≤ 200ms

数值只是示例，按项目基线制定。

在 CI 中检查

  • 资源预算：读取构建产物的清单（如 Vite 的 manifest），计算每个入口静态依赖的分块去重后的压缩体积。不要硬编码带哈希的文件名。动态导入的分块单独计入"首次使用该功能"的预算。
  • 实验室预算：用 Lighthouse CI 等工具在固定条件下运行多次取中位数，检查 LCP、TBT、CLS。
  • 交互预算：用 Playwright 等脚本执行关键交互，结合 Performance API 测量处理时间。
JavaScript
// lighthouserc.js（示意）
module.exports = {
  ci: {
    collect: { numberOfRuns: 3, url: ['http://localhost:4173/'] },
    assert: {
      assertions: {
        'largest-contentful-paint': ['error', { maxNumericValue: 2500 }],
        'cumulative-layout-shift': ['error', { maxNumericValue: 0.1 }],
        'total-blocking-time': ['warn', { maxNumericValue: 200 }],
      },
    },
  },
};

实验室测不到真实 INP，只能用 TBT 和脚本化交互作为替代。

超出预算时

  1. 用构建分析工具找出增长来源：新依赖、重复打包的模块、意外的静态导入、polyfill、图片字体。
  2. 判断是否值得：新功能带来的价值能否抵消代价，有没有更轻的替代库。
  3. 处理：按需加载低频功能、替换依赖、压缩资源、移除重复模块。
  4. 确有必要时调整预算，并记录原因。

线上跟踪

CI 只能防止明显退化，真实用户的体验还要看 RUM：按版本对比 75 分位，关注连续多个版本的小幅上涨，见《真实用户监测与实验室性能测试为什么要结合？》。

常见追问

  • 第三方脚本算不算？算。它们同样占用带宽和主线程，应单独设预算并定期复查。
  • 压缩用 gzip 还是 Brotli 算？和线上实际使用的一致，并固定压缩参数，否则前后不可比。
