Web Crypto API 如何正确管理浏览器端密钥？

crypto.subtle 能做哈希、签名、加解密和密钥派生，只在 HTTPS 等安全上下文中可用。生成密钥时把 extractable 设为 false，脚本就拿不到原始字节，这种密钥还能存进 IndexedDB 下次接着用。

参考答案

简答

比如做一个端到端加密的笔记，数据要在浏览器里加密再上传，就要用 Web Crypto。crypto.subtle 提供 digest、sign、encrypt、deriveKey 等方法，它只在安全上下文（HTTPS 或 localhost）中可用。crypto.randomUUID() 也要求安全上下文，只有 crypto.getRandomValues() 没有这个限制。

密钥用 CryptoKey 对象表示。生成时把 extractable 设为 false，这个密钥就不能用 exportKey() 导出，脚本也拿不到原始字节。

CryptoKey 可以被结构化克隆，所以能直接存进 IndexedDB。下次打开页面取出来还能用，而且仍然不可导出。

但要清楚它的边界：浏览器端加密挡不住 XSS。攻击者的脚本虽然导不出密钥，却可以直接拿这个密钥去加解密。还有，用户清除站点数据，密钥就没了，加密的数据也解不开。

用 AES-GCM 加密本地数据

下面生成一个不可导出的密钥，用它加密和解密一段文字。

JavaScript
async function createKey() {
  return crypto.subtle.generateKey({ name: 'AES-GCM', length: 256 }, false, ['encrypt', 'decrypt']);
}

async function encrypt(key, text) {
  const iv = crypto.getRandomValues(new Uint8Array(12));
  const data = new TextEncoder().encode(text);
  const cipher = await crypto.subtle.encrypt({ name: 'AES-GCM', iv }, key, data);
  return { iv, cipher };
}

async function decrypt(key, { iv, cipher }) {
  const plain = await crypto.subtle.decrypt({ name: 'AES-GCM', iv }, key, cipher);
  return new TextDecoder().decode(plain);
}

generateKey 的第二个参数 false 就是 extractable，第三个参数限定这个密钥只能用来加密和解密。

IV 是什么？它是每次加密时混进去的一个随机数，让同样的内容每次加密出来都不一样。AES-GCM 要求同一个密钥下，IV 每次都必须不同，所以每次生成 12 字节随机值，和密文一起保存。IV 不需要保密。

不可导出和防篡改，实际是什么效果

下面这段在 Node 里也能运行，看看导出和篡改分别会怎样：

JavaScript
const key = await crypto.subtle.generateKey({ name: 'AES-GCM', length: 256 }, false, ['encrypt', 'decrypt']);
console.log(key.extractable); // false

try {
  await crypto.subtle.exportKey('raw', key);
} catch (error) {
  console.log('导出失败');
}

const iv = crypto.getRandomValues(new Uint8Array(12));
const cipher = new Uint8Array(
  await crypto.subtle.encrypt({ name: 'AES-GCM', iv }, key, new TextEncoder().encode('hi')),
);
cipher[0] ^= 1;
try {
  await crypto.subtle.decrypt({ name: 'AES-GCM', iv }, key, cipher);
} catch (error) {
  console.log('篡改后', error.name); // 篡改后 OperationError
}

导出不可导出的密钥会直接失败。然后把密文的第一个字节改了一位，再解密，decrypt 没有返回一段错乱的明文，而是直接 reject。因为 AES-GCM 带有校验，数据被篡改或者密钥不对，都会解密失败。所以拿到结果就能确信数据没被改过。

从密码派生密钥

如果想用用户的密码来加密，不能直接拿密码当密钥，要先派生：

JavaScript
async function keyFromPassword(password, salt) {
  const base = await crypto.subtle.importKey('raw', new TextEncoder().encode(password), 'PBKDF2', false, ['deriveKey']);
  return crypto.subtle.deriveKey(
    { name: 'PBKDF2', salt, iterations: 600000, hash: 'SHA-256' },
    base,
    { name: 'AES-GCM', length: 256 },
    false,
    ['encrypt', 'decrypt'],
  );
}

为什么要迭代 60 万次？因为密码通常很短、好猜，迭代次数大，每猜一次密码的成本就高，暴力破解就慢。盐值要随机生成并保存，让相同的密码派生出不同的密钥。

如果已经有一个高熵的密钥，只是想从它派生子密钥，就用 HKDF，不需要大量迭代。

它适合做什么，不适合做什么

适合的场景有：端到端加密的聊天、本地加密的离线数据、校验下载文件的哈希、在浏览器里验证签名。

它不能代替 HTTPS。也不要在前端保存服务端的私钥或 API 密钥，前端代码里的东西用户都能看到。

常见追问

密钥设成不可导出，是不是就安全了？

只防住了“把密钥偷走”。页面有 XSS 时，攻击者的脚本可以直接调用这个密钥加解密，效果差不多。所以它不能代替防 XSS。

用户清除了站点数据怎么办？

存在 IndexedDB 里的密钥也会被清掉，加密的数据就再也解不开了。所以要提前设计备份，或者能从服务端重新同步的流程。
