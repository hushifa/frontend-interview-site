Angular Signals 的依赖追踪与 computed 有什么特点？

Signal 通过读取函数记录响应式消费者，computed 从实际读取到的 Signal 推导并缓存只读结果。依赖会随执行分支变化，但对象突变、异步边界和副作用仍需显式设计。

参考答案

Signal 只追踪发生在响应式上下文中的读取

Signal 不是对所有 JavaScript 变量的全局监控。模板、computed 和 effect 等消费者在执行时调用 count()，Angular 才知道这个消费者依赖当前值；之后通过 set 或 update 改变它，相关消费者才会重新计算或更新。

仅仅在普通函数里提到某个 Signal，或改变一个普通变量，不会自动建立通知关系。

computed 是只读的派生状态

TypeScript
const price = signal(10);
const quantity = signal(2);
const total = computed(() => price() * quantity());

console.log(total()); // 20
quantity.update((value) => value + 1);
console.log(total()); // 30

price 和 quantity 是可写 Signal，total 是只读派生值。computed 通常惰性计算并缓存：第一次读取时求值，依赖没有变化时复用，依赖变化后让缓存失效，下一次读取再计算。

缓存不会把昂贵计算移到后台。对大量数据过滤、排序和格式化仍要测量执行成本，必要时拆分数据或使用更合适的结构。

依赖由当前分支决定

TypeScript
const expanded = signal(false);
const detail = signal('原始内容');
const display = computed(() => expanded() ? detail() : '已折叠');

console.log(display());
detail.set('新内容'); // 折叠时不会触发 display 重新计算
expanded.set(true); // 重新执行后 detail 才进入依赖

第一次执行走折叠分支，没有读取 detail，所以它变化时不会使 display 失效；展开后，detail 加入依赖集合。再次改变分支时，依赖也可能被移除。依赖不是“函数文本中出现过的所有 Signal 永久固定”。

异步 await 或计时器之后的读取不能自动算作同一次同步依赖收集。异步任务需要自己的状态、取消和过期结果处理。

通过写入创建明确的新值

Signal 常用引用相等判断。如果保存数组，直接执行 items().push(value) 没有通过 Signal 写入，消费者不应期待收到更新；把同一引用重新 set 也可能被视为没有变化：

TypeScript
items.update((previous) => [...previous, value]);

asReadonly 只隐藏写入 API，不会递归冻结对象。自定义 equal 可以减少无意义更新，但如果错误地判断两个对象相等，也会隐藏真实变化。复杂嵌套数据需要明确不可变更新、Store 或其他状态策略。

派生不要用 effect 来回同步

如果 total 完全由价格和数量决定，computed 比 effect 读取后再写另一个 Signal 更直接。后者多出一份需要保持一致的状态，还可能产生调度延迟和循环更新。

effect 更适合把状态同步到外部系统，例如日志、非 Angular 图表或浏览器 API。它有自己的创建上下文、调度和清理规则，不应被当作同步函数，也不应拿来传播所有状态。untracked 适合明确排除某个依赖的场景，不能用来掩盖状态设计错误。

模板读取 Signal 时 Angular 可以把它和组件视图关联，但 Signals 不会自动解决请求竞态、共享对象、权限、生命周期或服务作用域。真正可靠的设计仍要把同步派生、异步流程和外部副作用分开。
