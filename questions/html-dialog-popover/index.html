dialog 和 Popover API 应该怎样使用？

dialog 提供对话框语义，showModal 建立模态交互并进入 top layer；Popover API 管理非模态浮层的显示与关闭。应先决定是否阻断背景交互，再设计名称、焦点、关闭路径和数据提交。

参考答案

“出现在其他内容上面”只是视觉特征。一个要求先完成选择才能继续的设置对话框，和一段随时可以打开又关闭的补充说明，交互要求并不相同。

如果背景页面在当前任务完成前不应被操作，可以使用 dialog 的模态模式；如果用户仍可与背景内容交互，Popover API 更适合管理轻量的非模态浮层。二者都能与浏览器的 top layer 机制配合，但顶层显示与模态交互不是同一个概念。

showModal 与 show 的差别

dialog.showModal() 打开模态对话框，将其放入 top layer，浏览器会让对话框以外的相关页面内容处于不可交互的状态，并提供相应的焦点与关闭机制。dialog.show() 打开的是非模态对话框，不会以同样方式阻断背景。

直接添加 open 属性也只是打开非模态对话框，不能把 <dialog open> 当作 showModal 的替代。给普通 div 加遮罩、巨大 z-index 或 aria-modal="true"，也不会自动获得浏览器的模态交互实现。

一个有明确保存与取消语义的设置框

HTML
<button id="open-settings" type="button">阅读设置</button>

<dialog id="settings" aria-labelledby="settings-title">
  <form method="dialog">
    <h2 id="settings-title">阅读设置</h2>
    <label for="density">内容密度</label>
    <select id="density" name="density" autofocus>
      <option value="comfortable">舒适</option>
      <option value="compact">紧凑</option>
    </select>
    <button value="cancel" formnovalidate>取消</button>
    <button value="save">保存</button>
  </form>
</dialog>

<p id="settings-status" role="status"></p>
JavaScript
const opener = document.querySelector('#open-settings');
const dialog = document.querySelector('#settings');
const density = document.querySelector('#density');
const status = document.querySelector('#settings-status');
let savedDensity = 'comfortable';

opener.addEventListener('click', () => {
  density.value = savedDensity;
  // Escape 关闭不应沿用上一次保存留下的返回值。
  dialog.returnValue = '';
  dialog.showModal();
});

dialog.addEventListener('close', () => {
  if (dialog.returnValue === 'save') {
    savedDensity = density.value;
    status.textContent = savedDensity === 'compact'
      ? '已保存为紧凑布局。'
      : '已保存为舒适布局。';
  } else {
    status.textContent = '已取消，设置未改变。';
  }
});

method="dialog" 使表单提交用于关闭所属对话框，而不是把数据发送到某个 URL。触发的提交按钮 value 会作为 returnValue。代码明确区分 save 与其他关闭路径，只有 save 才更新保存值。

每次打开都从已保存值恢复控件，因此用户取消修改后，下次不会看到一个未经保存的旧选择。returnValue 也显式清空，避免先保存、再打开、再按 Escape 时误把之前的 save 当成本次确认。

这个例子只保存当前页面内的设置，没有实现跨刷新持久化或远端请求。需要真正保存时，应把成功和失败流程接进来，而不是一关闭对话框就无条件宣称远端保存成功。

名称、焦点与关闭方式仍需设计

aria-labelledby 让对话框名称来自可见标题。简单设置中，autofocus 可以把初始焦点放到用户马上要操作的控件；长说明或不可逆操作则可能需要不同的初始焦点策略，不应总把焦点放在最危险的确认按钮上。

原生模态对话框默认支持 Escape 等关闭请求，并涉及 cancel 事件。取消该事件的默认行为可以阻止关闭，但不应无理由地把用户困在弹层里。关闭按钮、保存按钮和 Escape 的数据处理应保持一致而明确。

浏览器通常会处理关闭后的焦点恢复，但如果原触发按钮已经被删除或当前流程转到了新页面，应用仍需把焦点安排到合理的位置。不能只因为使用了原生 dialog 就省略真实键盘测试。

formnovalidate 让取消按钮不被表单必填等校验拦住。若对话框表单中有待填写的 required 字段，这个细节尤其重要。dialog.close() 是另一种直接关闭方式，它也不等于用户完成了表单校验或点击了保存。

不要依赖所有浏览器都默认“点遮罩就关闭”。新属性可能提供额外关闭策略，但需要确认目标版本；最基本的实现应始终提供清楚的退出控件。

轻量说明可以只用声明式 Popover

HTML
<button type="button" popovertarget="answer-help">如何阅读题解</button>

<div id="answer-help" popover="auto">
  <p>先理解例子，再修改输入观察结果，不必逐字背诵。</p>
  <button type="button" popovertarget="answer-help"
          popovertargetaction="hide">关闭说明</button>
</div>

支持 Popover API 的浏览器可以直接根据 popovertarget 建立控制关系，不需要手写显示类名切换。auto 浮层支持相应的轻量关闭行为，例如点击外部或 Escape，并且与其他 auto 浮层的打开存在互斥规则及嵌套例外。

popover="manual" 则不提供同样的自动轻量关闭，需要显式控制。选择哪一种应由交互需求决定，不要把“手动”理解成更安全或更高级。

Popover API 创建的是非模态浮层，背景仍可交互。popover 属性本身也不会把一个 div 变成完整的菜单、列表框或工具提示；如果要实现这些控件，仍需相应语义和键盘规则。示例包含关闭按钮，不能随意加一个只适合纯提示内容的 tooltip 角色就结束。

顶层解决覆盖问题，不包办整个弹层

进入 top layer 后，内容不再像普通后代那样受祖先层叠上下文排序的限制，这能避免很多 z-index 无论多大都被盖住的问题。dialog 的模态模式还提供背景交互限制，Popover 则没有同样的模态承诺。

浮层出现在顶层，不代表它已经自动贴到设计稿要求的按钮旁边。尺寸、定位、窄屏溢出和动画仍需要样式设计；若使用 CSS 锚点定位等能力，还应单独检查兼容性。嵌套浮层、关闭顺序、滚动和焦点也应一起验证。

对不支持相关 API 的目标环境，应选择有能力匹配需求的回退实现，或让补充说明保持可读。仅凭样式看起来像弹层，不能证明其键盘和辅助技术体验已经等价。
