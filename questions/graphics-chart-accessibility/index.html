前端图表如何同时满足无障碍和高性能？

从 Canvas、SVG 和 HTML 图表的差异出发，设计可访问的数据替代、键盘操作、动态播报和颜色方案，并说明大数据量下的性能取舍。

参考答案

简答

  • 图表旁边先给出标题、单位、时间范围、关键结论，必要时提供数据表。
  • SVG 不会自动把数据变成可理解的结构，数据点很多时应采用聚合或“当前点详情”模式。
  • 悬停提示不能是唯一的数据入口，颜色也不能是唯一编码。
  • 大数据量时常用 Canvas 或 WebGL 绘制，只为可见范围维护少量可访问节点；实时数据的播报要合并，并尊重减少动态效果的设置。

销售看板把趋势和异常都画在 Canvas 上，视觉用户能看懂，屏幕阅读器却只能读到一个“图表”空容器。鼠标用户还可以悬停查看数据，但键盘用户无法访问某个数据点。图表无障碍不是给 Canvas 加一个 aria-label 就结束，而是要让用户获得同等的结论、数据和操作路径，同时避免把数万个点都变成沉重的 DOM。

先提供可读的数据结论

图表旁边应有标题、单位、时间范围和关键结论。对于静态报告，可以提供一个可展开的数据表；对于实时图表，应提供当前值、变化方向、更新时间和异常说明。表格不是“重复内容”，而是为无法使用图形或需要精确比较的用户提供等价信息。

HTML
<section aria-labelledby="sales-title">
  <h2 id="sales-title">本季度销售额趋势</h2>
  <p id="sales-summary">4 月至 6 月持续增长，6 月比 5 月增加 12%。</p>
  <div
    role="img"
    aria-labelledby="sales-title"
    aria-describedby="sales-summary"
  >
    <canvas id="sales-chart" width="640" height="320"></canvas>
  </div>
  <details>
    <summary>查看详细数据</summary>
    <table>
      <caption>按月份统计的销售额</caption>
      <thead><tr><th scope="col">月份</th><th scope="col">销售额（万元）</th></tr></thead>
      <tbody>
        <tr><th scope="row">4 月</th><td>80</td></tr>
        <tr><th scope="row">5 月</th><td>92</td></tr>
        <tr><th scope="row">6 月</th><td>103</td></tr>
      </tbody>
    </table>
  </details>
</section>

如果图表本身只是装饰，应该使用空的替代文本或从辅助技术树中隐藏；如果图表承载业务结论，就必须提供有意义的名称和描述。不要把所有数据拼成一个很长的 aria-label，这会让阅读顺序和定位都变差。

SVG 可以表达结构，但不能自动获得语义

SVG 中的坐标轴、折线和标记默认不会变成屏幕阅读器能理解的表格。可以给整个图表提供标题和描述，并将需要交互的数据点做成可聚焦元素；但如果数据点很多，逐点暴露会让键盘操作变得不可用。应根据任务选择聚合、筛选或“当前点详情”模式。

HTML
<svg role="img" aria-labelledby="chart-title chart-desc" viewBox="0 0 640 320">
  <title id="chart-title">每月销售额</title>
  <desc id="chart-desc">销售额从 4 月 80 万元增长到 6 月 103 万元。</desc>
  <!-- 视觉路径和网格线可以设置 aria-hidden="true" -->
</svg>

role="img" 适合把整张图作为一个整体说明。如果用户需要逐点探索，就不能只把整个 SVG 当成单一图片，还要设计焦点管理和详情区域。使用 ARIA 角色时要遵循原生 HTML 语义优先原则，并在目标屏幕阅读器上实测；错误的角色组合可能比没有角色更难理解。

键盘交互要有清晰的焦点模型

悬停提示不能是唯一的数据入口。下面是一种可探索图表的交互设计，不是所有图表的统一 ARIA 键盘标准；静态图配摘要和数据表不需要人为增加一套方向键操作。若选择逐点探索模式，应明确并验证：

  • Tab 进入图表控件或数据选择器；
  • 方向键在数据点、系列或时间粒度之间移动；
  • Enter 或空格打开当前点的详细信息；
  • Escape 关闭浮层并把焦点还给触发控件；
  • 当数据点很多时提供搜索、缩放或按区间跳转，而不是要求逐个经过。

详情浮层不能只依赖鼠标坐标。可以用共享的数据模型让鼠标与键盘选择同一个数据点，避免只靠像素位置生成详情。若焦点元素已有完整可访问名称，再同时使用 live region 可能重复播报；只有信息无法通过焦点语义表达时才补充 polite 播报，并控制更新频率。是否重绘整张图取决于绘制成本，应测量后优化，不能为了少重绘保留错误的选中状态。

如果图表包裹在 role="img" 中，应把它当作一个整体的非交互图像，不把需要键盘访问的按钮或数据点藏在其中。逐点探索应采用与实际控件相符的结构，或把选择器与详情放在图像外部；不能仅给 SVG 点添加 tabindex 就认为读屏器能理解操作。

颜色不是唯一编码

用红绿两条线表示状态时，色觉差异用户可能无法区分。应同时使用线型、点形状、纹理、直接标注或文字状态，并确保文字与背景满足 WCAG 对比度要求。对比度工具只能检查颜色关系，不能证明图表整体可读；细线、半透明区域和重叠点还需要人工检查。

大数据量下的性能取舍

让每个点都成为 DOM 元素会带来布局、样式和辅助技术树的成本；把所有点画进 Canvas 又会失去天然语义。常见折中是：视觉层使用 Canvas 或 WebGL，交互层只维护当前可见范围和少量可访问节点，数据表按分页或抽样提供完整查询。抽样必须说明规则，不能让抽样后的趋势掩盖异常数据。

绘制层和语义层应分离。数据更新时先更新用于表格和播报的模型，再按可见区域重绘画布；不要从 Canvas 像素反推屏幕阅读器内容。命中测试可以把指针坐标映射到最近数据点，但键盘路径应使用同一份数据模型，避免鼠标和键盘显示不同结果。

实时数据、动画和减少动作

实时图表应告诉用户更新时间、暂停状态和数据是否延迟。动画不能是理解数值变化的唯一方式；用户启用 prefers-reduced-motion: reduce 时，应减少或关闭过渡，并保留最终状态。快速变化的数据不应每帧触发播报，可按固定时间窗口合并为“过去 10 秒最高值”和“当前趋势”等摘要。

常见误区和选型

  • 只给 Canvas 写 aria-label：无法提供数据点、单位和操作细节。
  • 只做鼠标悬停：触摸和键盘用户无法稳定查看数据。
  • 用颜色区分全部系列：色觉差异和低对比度环境下会丢失信息。
  • 把数万行数据一次性放进隐藏表格：可能让页面和辅助技术都变慢，应分页或按需展开。
  • 把自动扫描通过当成无障碍完成：屏幕阅读器顺序、焦点、缩放和动态更新必须人工验证。

选择 Canvas、SVG 或 HTML 时，应先看交互和数据量：少量、需要逐元素操作的图表可以优先 SVG 或 HTML；大量点位通常用 Canvas/WebGL，再补充结构化数据和键盘控制；只展示一张结论图时，语义化标题、摘要和数据表比复杂 ARIA 更可靠。
