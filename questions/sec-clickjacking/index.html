怎样用 frame-ancestors 限制页面被嵌入？

点击劫持可能把真实页面嵌入透明或伪装的框架，让用户误点敏感操作。CSP 的 frame-ancestors 指令定义哪些祖先来源可以嵌入当前页面；'none' 禁止嵌入，'self' 允许相同来源。

参考答案

点击劫持不一定需要往你的页面注入脚本。攻击者可以把真实的账户页面放在 iframe 里，再用透明度、遮罩和定位把其中的“确认”按钮放到诱导用户点击的位置。用户以为在点抽奖按钮，实际点到的却是另一个站点上的敏感操作。

攻击者即使受同源策略限制、读不到 iframe 的内容，也可能通过这种视觉欺骗利用用户点击。因此，“别人读不到我的页面”与“别人不能嵌入我的页面”是两件事。

规则应由被嵌入的页面声明

假设 account.example.com 不允许任何页面嵌入自己，应在它的 HTML 响应中设置：

http
Content-Security-Policy: frame-ancestors 'none'

如果只允许同源页面嵌入，可以使用 'self'。如果业务要求让特定管理平台嵌入，则显式列出来源：

http
Content-Security-Policy: frame-ancestors 'self' https://admin.example.com

这里的 'self' 指被保护页面自己的源，不是整个 example.com 下的任意子域。不要为了省事允许所有 HTTPS 来源；那相当于也允许攻击者自己的 HTTPS 网站嵌入。

frame-ancestors 检查的是整个祖先链。若 A 嵌入 B，B 再嵌入受保护的 C，即使 B 在 C 的许可名单里，只要 A 不满足 C 的规则，C 仍然不能正常嵌入。只看直接父页面会漏掉这一层。

frame-src 管的是相反方向

可以把两个指令分别读成：

  • frame-src：我这个页面可以往自己的 iframe 里加载谁？
  • frame-ancestors：谁可以把我这个页面放进它的框架里？

例如，后台需要嵌入报表服务，但后台本身不能被其他站点嵌入：

http
Content-Security-Policy: frame-src https://reports.example.com; frame-ancestors 'none'

这两个要求并不冲突。报表能否成功显示，还要看报表响应自身是否允许该后台嵌入；父页面的许可不能覆盖子页面的拒绝。

容易配错的几个位置

frame-ancestors 必须通过响应头发送，放进 HTML 的 CSP meta 标签无效。它也不会回退到 default-src，所以 default-src 'none' 并不表示“禁止其他页面嵌入我”。

应检查实际文档响应，而不只是代码仓库里的配置。例如反向代理可能没有把配置应用到登录页、错误页或某些静态路由。使用无法配置此响应头的静态托管服务时，增加一个 meta 标签不能补上这个能力，需要使用支持响应头的托管或代理层。

旧的 X-Frame-Options: DENY、SAMEORIGIN 可以表达禁止嵌入或仅允许同源嵌入，但不适合配置多个合作方来源。不要使用已废弃的 ALLOW-FROM 来实现现代白名单。若为了兼容同时发送两类头，应让意图一致，并确认目标浏览器的实际行为。

验证时真的把页面放进 iframe

先在开发者工具的 Network 中确认最终 HTML 响应含有预期策略，再分别从合法来源、非法来源和多层嵌套场景尝试加载。被阻止时，控制台通常会给出违反 frame-ancestors 的提示；只在浏览器地址栏直接打开页面，不能证明防嵌入规则有效。

限制嵌入也不能替代敏感操作自身的防护。服务端仍需鉴权，高风险操作可以要求再次确认或重新认证。frame-ancestors 主要处理“真实页面被借来诱导点击”，不负责修复页面内部的 XSS，也不保证用户一定理解正在确认的业务操作。
