Cache-Control 的 immutable、stale-while-revalidate 和 no-store 怎样选择？

带哈希的静态资源用长 max-age 加 immutable；允许短暂旧数据的接口或页面用 stale-while-revalidate；含敏感数据、绝不能落盘的响应用 no-store。需要每次确认最新但允许存储时用 no-cache。

参考答案

简答

  • immutable：告诉浏览器新鲜期内内容不会变，刷新页面时也不必重新验证。只用于 URL 带内容哈希的文件。
  • stale-while-revalidate=N：过期后 N 秒内先返回旧副本，同时在后台验证更新，用一次旧数据换掉等待时间。
  • no-store：不允许任何缓存存储响应，用于银行流水、一次性令牌等敏感内容。
  • no-cache：允许存储，但每次使用前都要向服务器验证，适合 HTML 入口。
  • private 只允许浏览器缓存，public 和 s-maxage 面向 CDN 等共享缓存。

典型配置

http
# /assets/app.3f9a1c.js
Cache-Control: public, max-age=31536000, immutable

# /index.html
Cache-Control: no-cache
ETag: "v42"

# /api/articles（可接受一分钟内的旧数据）
Cache-Control: public, max-age=60, stale-while-revalidate=300

# /api/me
Cache-Control: private, no-cache

# /api/payment-token
Cache-Control: no-store

选择时问三个问题

  1. 内容会不会在同一个 URL 下变化？不会变（哈希文件名）就长期缓存加 immutable；会变就要设计新鲜期或每次验证。
  2. 用户能接受多旧的数据？不能接受就 no-cache；能接受几分钟就 max-age 加 stale-while-revalidate。
  3. 内容是否因人而异或敏感？因人而异至少要 private，防止 CDN 缓存给别人；敏感到不能落盘就用 no-store。

部署时的坑

  • HTML 被长期缓存后，用户会一直加载旧入口和旧资源，发版无效。HTML 用 no-cache。
  • 新版本上线后删掉旧的哈希文件，已经打开的旧页面懒加载旧分块时会 404。旧资源应保留一段时间。
  • no-store 会让页面无法进入部分浏览器的往返缓存（bfcache），不要给普通页面滥用。
  • CDN 可能有自己的缓存规则，会覆盖或忽略源站头部，要在 CDN 侧确认。

常见追问

  • max-age=0 和 no-cache 有区别吗？效果接近，都是立即过期需验证；no-cache 语义更明确。
  • stale-if-error 是什么？源站出错时允许在指定时间内返回旧副本，提高可用性，支持情况因缓存实现而异。
