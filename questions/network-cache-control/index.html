Cache-Control 的 immutable、no-store 等指令怎样选？

带哈希的静态资源用很长的 max-age 加 immutable；可以接受一点旧数据的用 stale-while-revalidate；敏感数据用 no-store；要求每次确认最新但允许存的用 no-cache。

参考答案

简答

选指令其实就是回答一个问题：这份响应能放心用多久。

文件名带内容哈希的 JS、CSS，内容永远不会变，就给很长的 max-age 加 immutable。immutable 告诉浏览器，在新鲜期内连刷新页面都不用去验证。HTML 入口会变，用 no-cache，意思是可以存，但每次用之前都要问服务器。

能接受一点旧数据的接口，可以加 stale-while-revalidate=N：过期后 N 秒内先把旧副本给用户，同时在后台去更新，用一次旧数据换掉等待时间。

银行流水、一次性令牌这种敏感内容，用 no-store，任何缓存都不许存。另外，private 表示只能存在用户浏览器里，public 和 s-maxage 是给 CDN 这类共享缓存看的。

一套典型配置

http
# /assets/app.3f9a1c.js
Cache-Control: public, max-age=31536000, immutable

# /index.html
Cache-Control: no-cache
ETag: "v42"

# /api/articles（可接受一分钟内的旧数据）
Cache-Control: public, max-age=60, stale-while-revalidate=300

# /api/me
Cache-Control: private, no-cache

# /api/payment-token
Cache-Control: no-store

/api/articles 这一条可以这样读：60 秒内直接用缓存；过期后的 300 秒内，先返回旧副本，同时后台去拿新的；再往后就得等新响应了。/api/me 是每个人不一样的数据，所以加 private，不让 CDN 存。

选的时候问自己三个问题

第一，同一个 URL 下内容会不会变？文件名带哈希就不会变，长期缓存加 immutable。会变的话，就要设计新鲜期，或者每次都验证。

第二，用户能接受多旧的数据？一点都不能接受，就用 no-cache；能接受几分钟，就 max-age 加 stale-while-revalidate。

第三，内容是不是因人而异，或者很敏感？因人而异至少要加 private，防止 CDN 把一个人的数据缓存给别人。敏感到连硬盘都不能落，就用 no-store。

部署时容易踩的坑

最常见的是 HTML 被长期缓存。用户一直拿着旧 HTML，它引用的也是旧资源，发版就等于没发。所以 HTML 用 no-cache。

第二个是删旧文件删得太早。新版本上线后，有人还开着旧页面，旧页面懒加载时请求的是旧的哈希分块，文件已经删了就会 404。旧资源应该再保留一段时间。

第三个是滥用 no-store。它会让页面进不了部分浏览器的往返缓存（bfcache），前进后退都要重新加载，普通页面别随便加。

还有，CDN 可能有自己的缓存规则，会覆盖或忽略源站的头，要去 CDN 那边确认。

常见追问

max-age=0 和 no-cache 有区别吗？

效果接近，都是一拿到就过期、用之前要验证。no-cache 的意思表达得更明确。

stale-if-error 是什么？

源站出错时，允许在指定时间内返回旧副本，提高可用性。支不支持要看具体的缓存实现。
