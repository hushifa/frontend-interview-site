HTTP 内容协商会怎样影响前端资源和接口响应？

解释同一个 URL 如何选择不同语言、格式和压缩表示，区分 Accept 与 Content-Type，并用缓存串语言的例子说明 Vary、版本验证和显式资源地址的作用。

参考答案

简答

  • 服务器根据 Accept、Accept-Language、Accept-Encoding 等请求偏好选择表示，偏好不等于服务器必须转换。
  • q 值只表达偏好程度；Accept-Encoding 讲的是内容编码，不是 chunked 分帧。
  • 按请求头返回不同内容时必须设置正确的 Vary，否则缓存会串内容。
  • 变体过多会切碎缓存，应把请求头归一到少量实际提供的变体。

同样请求 /help，中文用户可能希望看到中文，英文用户希望看到英文；同样请求一张图片，支持 AVIF 的浏览器可能得到 AVIF，另一个客户端得到 JPEG。URL 代表一个资源，但返回的具体表示可以不同。

内容协商就是客户端表达自己能接受什么，服务器结合已有资源和自身规则选择一种表示。前端需要关心两件事：最后实际拿到的是什么，以及缓存有没有把别人的那种表示错误地复用过来。

请求偏好与实际内容要分开看

请求信息表达的意思对应的响应信息
Accept可接受的媒体类型，如 JSON、HTML、WebPContent-Type 声明实际正文的媒体类型
Accept-Language语言偏好，如中文优先、英文其次Content-Language 声明内容面向的语言
Accept-Encoding可接受的内容编码，如 br、gzipContent-Encoding 声明实际采用的内容编码

Accept-Encoding 讨论的是 gzip、Brotli 等内容编码，不是 HTTP/1.1 的 chunked 传输分帧，也不是字符集。Content-Type: application/json 和 Content-Encoding: gzip 可以同时存在，意思是 JSON 表示经过 gzip 编码后传输。

尤其容易混淆的是 POST 请求中的这两个头：

http
POST /api/reports HTTP/1.1
Host: example.com
Content-Type: application/json
Accept: application/pdf

{"month":"2026-09"}

请求的 Content-Type 说明“我发给你的正文是 JSON”，Accept 说明“我希望你返回 PDF”。它们可以完全不同。设置 Accept: application/json 也不会自动把请求体序列化，设置 Content-Type 更不会自动执行 JSON.stringify()。

q 值表示偏好，不是服务器必须执行的转换指令

例如：

http
Accept: application/json, text/html;q=0.8
Accept-Language: zh-CN, zh;q=0.9, en;q=0.7

省略 q 时通常按 1 处理，范围是 0 到 1。在按这些偏好协商时，JSON 的偏好高于 HTML，q=0 表示相应匹配项不可接受。出现通配符和更具体的媒体类型时，还要按匹配具体程度处理，不能简单把所有 q 排序后取第一项就称为完整协商算法。

服务器只能选择它能提供的表示。它可能根据约定回退到默认语言，也可能在无法满足媒体格式要求时返回 406 Not Acceptable；HTTP 也允许服务端选择忽略某些偏好而使用默认响应。因此客户端应检查实际响应，而不是因为自己写了 Accept 就直接认定返回一定是 JSON。

415 Unsupported Media Type 主要表示服务器不接受本次请求正文的媒体类型或相关内容编码，和“没有符合 Accept 的响应格式”不是同一问题。

语言偏好也不是地理位置、国籍或权限依据。浏览器配置可能与用户当前想看的语言不同，应允许用户显式选择，并让应用约定的显式选择优先于自动猜测。

为什么 Vary 少写一个字段就可能串内容

假设服务器根据 Accept-Language 返回不同语言，但缓存只按 URL 复用响应：

  1. 第一个用户请求 /help，偏好中文，缓存保存中文内容。
  2. 第二个用户请求同一个 URL，偏好英文。
  3. 缓存认为地址相同，就直接把中文交给第二个用户。

如果响应会根据该请求头改变，应发送：

http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Language: zh-CN
Cache-Control: public, max-age=300
Vary: Accept-Language

Vary 告诉缓存：重用这个响应时，除了通常的缓存键，还要核对影响表示选择的请求头。它不是告诉缓存“看看响应里的 Content-Language 是否相同”，而是声明选择时使用了哪些请求头。

若还根据 Accept-Encoding 压缩、根据 Accept 选择媒体类型，就要把相应维度也正确反映出来。代理/CDN 可能有额外的缓存键配置、归一化规则和支持范围，不能只看源站写了 Vary 就假定整条链路一定按预期工作。

Vary 也不负责登录隔离。私有资料不应因为增加 Vary: Cookie 就放心进入公共缓存；应先明确 private、no-store 等策略和共享缓存限制。不同用户返回不同敏感内容，是安全设计问题，不只是多一个缓存维度。

变体越多，缓存越容易被切碎

Accept-Language 可能有许多不同排序和 q 值。如果每种字符串都形成单独的缓存变体，即使最终只提供中文和英文，也可能产生大量重复内容。Vary: User-Agent 更容易因客户端版本差异导致低命中率。

因此只把真正影响表示选择的头加入 Vary，不要把所有请求头都列进去。需要归一化语言或设备类别时，应由了解协商规则的服务端/CDN 实现，并保证缓存选择规则和实际响应一致。

对于长期可链接的页面，显式使用 /zh-CN/help/、/en/help/ 可能更容易维护、缓存和分享；用户偏好可以用于首次选择或跳转，不必让同一 URL 永远隐式代表多种语言。图片也可以通过 <picture>、srcset 给浏览器选择明确资源地址，而不是所有格式都靠服务器猜测。

压缩、验证器和前端读取的边界

浏览器通常自动发送 Accept-Encoding 并处理支持的内容解码，脚本不能像在任意 HTTP 客户端中那样自由设置这个受控请求头。因此网络传输的压缩字节数，与 response.text() 得到的字符串长度不是同一个量。

不同表示的验证器也要匹配实际字节和语义。例如强 ETag 用于判断表示数据是否相同，不能给两份不同的编码字节随便复用同一个强标签。否则条件请求、范围下载或缓存验证可能作出错误判断。与语言、格式有关的 Vary 规则在后续验证响应中也要保持一致。

排查“接口偶尔返回错误格式”时，可以对比完整请求的 Accept 系列头、实际 Content-Type、Content-Encoding、Content-Language、Vary，以及 CDN 的缓存行为。仅把浏览器缓存清空一次，可能暂时绕过错误，却没有修复变体被混用的原因。
