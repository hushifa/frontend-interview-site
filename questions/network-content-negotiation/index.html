HTTP 内容协商会怎样影响前端资源和接口响应？

同一个 URL 可以按请求头返回不同版本：Accept 挑格式，Accept-Language 挑语言，Accept-Encoding 挑压缩方式。服务器必须用 Vary 说明依据了哪些头，否则缓存会把一个版本发给所有人。

参考答案

简答

同一个 URL，服务器可以根据请求头返回不同的版本，这叫内容协商。客户端用 Accept 说想要什么格式，Accept-Language 说想要什么语言，Accept-Encoding 说支持哪些压缩。还可以用 q 值排先后，比如 zh-CN,zh;q=0.9,en;q=0.8，意思是最想要简体中文，其次中文，再次英文。

服务器挑一个版本返回，再用 Content-Type、Content-Language、Content-Encoding 说明实际给的是什么。

最关键的一点是 Vary。服务器看了哪些请求头来做选择，就要在 Vary 里列出来，缓存才会按这些头分开存。不写的话，CDN 可能把英文版发给所有人。

还有个常被混淆的地方：Accept 说的是“我想要的响应格式”，Content-Type 说的是“这段正文本身是什么格式”，所以请求和响应都可以带 Content-Type。

压缩是怎么协商的

http
GET /app.js
Accept-Encoding: gzip, br, zstd

HTTP/1.1 200 OK
Content-Encoding: br
Vary: Accept-Encoding

浏览器说自己支持 gzip、br、zstd，服务器选了 br，并用 Vary: Accept-Encoding 告诉缓存：这个响应是按压缩方式选出来的，不支持 br 的客户端不要给它这份。

Chrome、Firefox 等浏览器通常只在 HTTPS 连接上才在 Accept-Encoding 里带 br，具体以浏览器实现为准。zstd 也已经有多个浏览器支持，服务器可以按请求头去选。静态资源最好在构建时就预先压缩好，省掉每次请求动态压缩的 CPU。

为什么语言协商容易出问题

http
GET /pricing
Accept-Language: en

HTTP/1.1 200 OK
Content-Language: en
Cache-Control: public, max-age=600

这个响应少了 Vary: Accept-Language。CDN 只按 URL 存，第一个来的是英文用户，它就把英文页缓存给了所有人，中文用户也看到英文。

那加上 Vary 是不是就好了？也不完全。Accept-Language 的组合很多，每种都单独存一份，命中率会下降。而且用户没法手动切换语言，搜索引擎也很难分别索引各个语言版本。

所以面向用户的页面，更推荐用 URL 区分语言，比如 /en/pricing、/zh/pricing，配合 hreflang 标注。Accept-Language 只用在第一次访问时，建议跳转到哪个语言。

图片格式也能协商

浏览器请求图片时，Accept 里会写上支持的格式，比如 image/avif,image/webp,*/*。服务器或 CDN 可以据此返回 AVIF 或 WebP，同时加上 Vary: Accept。

前端也可以不依赖服务端，用 <picture> 在 HTML 里列出几种候选格式，让浏览器自己挑。

常见追问

接口返回的是 HTML 而不是 JSON？

可能是请求没设 Accept，也可能是网关出错返回了一个 HTML 错误页。前端解析前先检查 Content-Type。

服务器没有客户端能接受的版本时返回什么？

可以返回 406 Not Acceptable，但多数服务器会直接返回默认版本。
