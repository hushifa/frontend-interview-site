可访问的 Combobox 需要哪些键盘和 ARIA 行为？

从输入框、列表框、展开状态和活动选项说明自定义下拉搜索控件的可访问实现边界。

参考答案

Combobox 是“可编辑输入框 + 可选结果列表”的组合控件。它的无障碍信息不能只靠一个 role 表达，而要让辅助技术知道输入框的名称、列表是否打开、列表在哪里以及当前键盘光标对应哪一个选项。一个最小的结构大致如下：

HTML
<label for="city">城市</label>
<input
  id="city"
  role="combobox"
  aria-autocomplete="list"
  aria-expanded="true"
  aria-controls="city-options"
  aria-activedescendant="city-option-0"
  value="北京"
>
<ul id="city-options" role="listbox">
  <li id="city-option-0" role="option" aria-selected="true">北京</li>
  <li id="city-option-1" role="option" aria-selected="false">北海</li>
</ul>

aria-expanded 要随着弹层真实状态变化，aria-controls 要指向当前存在的列表，aria-activedescendant 则必须指向列表中可见且稳定的选项 ID。使用这种方式时，DOM 焦点仍然留在输入框，键盘移动的是“活动选项”；如果实现选择把焦点直接移到列表项，就必须另外处理焦点返回、Tab 离开和 Escape 关闭，不能两套方案混用。

键盘行为要形成完整闭环。输入框获得焦点后，用户应能用 ArrowDown 打开或移动到结果，用 ArrowUp 反向移动，用 Enter 确认当前选项，用 Escape 关闭列表并保留合理的输入值，Tab 则应按预期离开控件。具体按键细节要根据使用的 ARIA 模式和产品需求核对，但每个状态都要有可到达、可取消和可恢复的路径。

过滤结果是异步变化时，活动选项不能因为结果刷新而指向已经删除的节点。没有结果、正在加载、加载失败和结果过期都应该有明确的界面状态；如果列表内容会动态改变，还要避免在用户按下 Enter 的瞬间提交了旧结果。选中值、输入文本和当前活动项是三个不同概念，不应只用一个字符串状态代替它们。

如果需求只是从一组固定选项中选择，原生 select 通常更可靠，浏览器和辅助技术会替你处理大量键盘与焦点细节。只有确实需要搜索、异步结果或自定义交互时才值得实现 Combobox，并且要用键盘、触摸、鼠标和屏幕阅读器分别走完整流程；自动化检查通过，只能说明部分属性存在，不能证明控件真的可用。
