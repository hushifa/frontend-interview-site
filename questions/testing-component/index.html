前端组件测试应该围绕哪些用户行为？

组件测试应按用户的方式操作组件：找到控件、输入、提交，然后断言用户能看到的结果，包括加载、成功、失败和重试；内部 state、类名和私有函数不应出现在断言里。

参考答案

简答

  • 测试越像用户的使用方式，越能证明功能可用；Testing Library 的指导原则就是这句话。
  • 断言用户能感知的结果：显示的文字、控件是否禁用、焦点位置、调用了外部回调。
  • 不断言内部 state、Hook 调用次数、DOM 层级和类名，这些在重构时会变化，用户却感觉不到。
  • 加载、成功、空结果、失败和重试分别写用例，异步结果用 findBy* 等待，不用固定时长的 sleep。
  • 外部依赖（请求、时钟、路由）通过 props、Context 或模块 mock 替换，组件自己的逻辑保持真实。

被测组件

TSX
import { useState, type FormEvent } from 'react';

type State =
  | { kind: 'idle' }
  | { kind: 'loading' }
  | { kind: 'success'; items: string[] }
  | { kind: 'error' };

export function SearchBox({ search }: { search: (q: string) => Promise<string[]> }) {
  const [keyword, setKeyword] = useState('');
  const [state, setState] = useState<State>({ kind: 'idle' });

  async function submit(event: FormEvent) {
    event.preventDefault();
    setState({ kind: 'loading' });
    try {
      setState({ kind: 'success', items: await search(keyword) });
    } catch {
      setState({ kind: 'error' });
    }
  }

  return (
    <form onSubmit={submit}>
      <label htmlFor="kw">关键词</label>
      <input id="kw" value={keyword} onChange={(e) => setKeyword(e.target.value)} />
      <button type="submit" disabled={state.kind === 'loading'}>搜索</button>
      {state.kind === 'loading' && <p role="status">搜索中</p>}
      {state.kind === 'error' && <p role="alert">搜索失败，请重试。</p>}
      {state.kind === 'success' && (
        <ul aria-label="结果">
          {state.items.map((item) => <li key={item}>{item}</li>)}
        </ul>
      )}
    </form>
  );
}

测试

TSX
import { render, screen, within } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { expect, test, vi } from 'vitest';

test('提交关键词后显示结果', async () => {
  const user = userEvent.setup();
  const search = vi.fn().mockResolvedValue(['事件循环']);
  render(<SearchBox search={search} />);

  await user.type(screen.getByRole('textbox', { name: '关键词' }), '事件');
  await user.click(screen.getByRole('button', { name: '搜索' }));

  const list = await screen.findByRole('list', { name: '结果' });
  expect(within(list).getByText('事件循环')).toBeVisible();
  expect(search).toHaveBeenCalledWith('事件');
});

test('失败后保留输入并可以重试', async () => {
  const user = userEvent.setup();
  const search = vi.fn()
    .mockRejectedValueOnce(new Error('网络错误'))
    .mockResolvedValueOnce(['闭包']);
  render(<SearchBox search={search} />);

  await user.type(screen.getByRole('textbox', { name: '关键词' }), '闭包');
  await user.click(screen.getByRole('button', { name: '搜索' }));
  expect(await screen.findByRole('alert')).toHaveTextContent('搜索失败');
  expect(screen.getByRole('textbox', { name: '关键词' })).toHaveValue('闭包');

  await user.click(screen.getByRole('button', { name: '搜索' }));
  expect(await screen.findByText('闭包')).toBeVisible();
});

listitem 的名称不能从内容计算，所以先按名称找到列表，再用 within 找文字。查询选择的原则见《Testing Library 查询方式为什么优先按用户可见语义？》。

userEvent 会依次触发聚焦、键盘、输入等事件，比 fireEvent.change 更接近真实操作，也能发现焦点和提交行为的问题。

  • 示例的 search 通过 props 注入，测试直接传 vi.fn()；依赖藏在模块里时用 vi.mock，放在 Context 里时用测试专用的 Provider 包裹。
  • 输入框写成 type="search" 时角色是 searchbox，查询要改成 getByRole('searchbox')，不要为了让测试通过而改组件的语义。
  • toBeVisible、toHaveValue、toHaveTextContent 来自 jest-dom，要在 Vitest 的 setup 文件中引入 @testing-library/jest-dom/vitest。
  • findBy* 之外的异步断言可以用 waitFor，回调里只放断言，不要在里面点击或提交。

哪些断言容易变脆

  • expect(wrapper.state.kind).toBe('error')：内部状态。
  • container.querySelector('.search-box__error')：类名。
  • expect(useEffectSpy).toHaveBeenCalledTimes(2)：渲染实现。
  • 整个组件的 DOM 快照：任何结构调整都会失败，审查者往往直接更新快照。

组件测试的边界

组件测试证明组件自身的交互逻辑，不能证明真实路由、后端接口、浏览器布局和多个页面组合正确。关键流程还需要端到端测试，见《如何减少 Playwright 端到端测试的不稳定？》；外观变化用截图测试，见《视觉回归测试如何减少无意义的截图差异？》。

常见追问

  • 自定义 Hook 怎样测？优先通过使用它的组件测试；Hook 本身是公共库接口时，用 renderHook 测试返回值和更新。
