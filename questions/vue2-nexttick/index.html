Vue 2 的异步更新队列和 nextTick 降级策略是怎样实现的？

Vue 2 把需要更新的 watcher 去重后放进队列，在 nextTick 里统一执行，执行前按 id 排序，保证父组件先于子组件。nextTick 优先用 Promise，不行再依次退到 MutationObserver、setImmediate、setTimeout。

参考答案

Vue 2 已于 2023-12-31 停止维护，本题以 Vue 2.7（vuejs/vue main 分支）源码为准。nextTick 的日常用法见《修改状态后，为什么有时需要 await nextTick()？》。

简答

数据一变，依赖它的 watcher 不会马上执行，而是调用 queueWatcher 进入一个队列。同一个 watcher 按 id 去重，一轮里只会进一次，所以同一事件里改十次数据，组件也只渲染一次。

第一次有 watcher 入队时，Vue 用 nextTick(flushSchedulerQueue) 安排一次刷新。刷新前按 id 从小到大排序（带 post 标记的排在最后），因为 id 是按创建顺序分配的，这样就保证了父组件先于子组件、用户写的 watcher 先于渲染 watcher。

nextTick 本身是把回调存进一个 callbacks 数组，同一轮只调用一次 timerFunc 统一执行。timerFunc 按环境降级：原生 Promise.then → MutationObserver → setImmediate → setTimeout(fn, 0)，前两个是微任务，后两个是宏任务。

有一个细节常被问到：nextTick 的回调和 flushSchedulerQueue 在同一个数组里按注册顺序执行。所以在修改数据之前注册的 nextTick 回调，读到的还是旧 DOM。

watcher 怎么入队和去重

queueWatcher 用 has[id] 记录哪些 watcher 已经在队列里了。

已经在队列里就直接返回，这就是官方文档说的“同一个 watcher 被多次触发，只会被推入队列一次”。不在刷新过程中时直接 push 到队尾；如果正在刷新，就按 id 插到合适的位置，如果已经越过了它该在的位置，就紧接着执行。另外有一个 waiting 标记，保证每轮只调用一次 nextTick(flushSchedulerQueue)。

刷新时为什么要排序

源码注释列出了排序的三个目的：

  1. 组件从父到子更新。父组件总是先于子组件创建，所以 id 更小。
  2. 组件的用户 watcher（watch 选项、$watch）先于渲染 watcher 执行，因为它们创建得更早。
  3. 如果父组件的 watcher 执行时把子组件销毁了，子组件的 watcher 可以直接跳过。

循环里没有缓存 queue.length，因为执行过程中可能有新的 watcher 插进来。执行每个 watcher 前，先把 has[id] 清空，这样它在执行中又被触发时还能再入队。可是如果一直这样循环，就成了死循环，所以开发环境下同一个 watcher 再次入队超过 MAX_UPDATE_COUNT（100）次，Vue 会警告“You may have an infinite update loop”并中止。

队列跑完后，先调用 activated 钩子，再倒序调用组件的 updated 钩子。

nextTick 为什么要降级

next-tick.ts 在模块加载时就选定了 timerFunc：

条件实现类型
原生 Promise 可用p.then(flushCallbacks)，iOS 上额外 setTimeout(noop) 以绕过 UIWebView 的问题微任务
非 IE 且有原生 MutationObserver监听一个文本节点，修改其内容触发回调微任务
原生 setImmediate 可用setImmediate(flushCallbacks)宏任务
都不可用setTimeout(flushCallbacks, 0)宏任务

优先用微任务，是因为微任务在当前代码执行完后、浏览器绘制前就会执行，更新能赶在用户看到画面之前完成。源码注释还记录了一段历史：2.5 曾经混用宏任务和微任务，结果在重绘前改状态（比如 out-in 过渡）和事件处理中都出了问题，之后改回全部用微任务。代价是微任务优先级太高，可能插在连续事件之间，甚至同一事件的冒泡过程之间执行。

MutationObserver 排在 Promise 后面，是因为它在 iOS ≥ 9.3.3 的 UIWebView 中有问题，在 IE11 中也不可靠。

不传回调、并且环境支持 Promise 时，nextTick() 会返回一个 Promise。

回调注册的顺序决定能不能读到新 DOM

下面在修改数据前后各注册一个 $nextTick，再加一个普通的 Promise.then：

JavaScript
// vue@2.7.16，在浏览器中运行
const vm = new Vue({ data: { n: 0 }, template: '<p>{{ n }}</p>' }).$mount();
const out = [];

vm.$nextTick(() => out.push('先注册: ' + vm.$el.textContent));
vm.n = 1; // flushSchedulerQueue 排在上一个回调之后
vm.$nextTick(() => out.push('后注册: ' + vm.$el.textContent));
Promise.resolve().then(() => out.push('Promise.then'));
out.push('同步: ' + vm.$el.textContent);

setTimeout(() => console.log(out));
// ['同步: 0', '先注册: 0', '后注册: 1', 'Promise.then']

很多人以为 $nextTick 里一定能读到新 DOM，可是“先注册”那个回调读到的是 0。原因是 callbacks 数组按注册顺序排：先是“先注册”的回调，然后 vm.n = 1 让 flushSchedulerQueue 排进来，再是“后注册”的回调。执行到“先注册”时，DOM 还没刷新。

那 Promise.then 为什么最后执行？因为第一次调用 $nextTick 时，timerFunc 已经用 Promise.resolve().then 安排了 flushCallbacks。后面这个 Promise.then 排在它之后，而 flushCallbacks 会一口气把数组里三个回调全跑完。

常见追问

为什么不每次修改都同步渲染？

同一个事件里的多次修改会合并成一次渲染，避免重复计算和 DOM 操作。同步渲染的话，改几次就要渲染几次。

测试中想同步更新怎么办？

源码里开发环境设置 config.async = false 时，会直接同步执行 flushSchedulerQueue。这是给测试工具用的，不要在业务代码里用。

Vue 3 有什么不同？

Vue 3 不再做降级，直接基于 Promise 安排刷新。
