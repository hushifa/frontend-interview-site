前端构建产物应该怎样分析体积？

产物分析要把文件大小、网络传输、解析执行和真实入口联系起来，找出不必要的提前加载、重复依赖和错误分块，再用同口径数据验证收益。

参考答案

简答

分析体积，先看首屏入口实际加载了哪些 chunk，再看总大小。总产物再大，用户第一次打开时用不到的部分，影响其实有限。

要同时看三个数：原始大小影响解析和执行，压缩后的传输大小影响下载，请求数量影响调度开销。

常见的问题有三种：首屏引入了只在某个页面才用的大依赖，同一个依赖被打包了好几份，分块切得太碎或者太粗。

优化以后，要用同样的构建方式和测量方法对比，并在 CI 里设体积预算，防止以后又涨回去。

用什么工具看

webpack 可以输出 stats JSON，也就是加 --json，再用 webpack-bundle-analyzer 画成图。Vite 和 Rolldown 可以用 rollup-plugin-visualizer 一类插件生成树图，vite build 的终端输出也会列出每个 chunk 的大小和 gzip 后的大小。

光看构建分析还不够，还要打开浏览器 DevTools。Network 面板告诉你首屏真正请求了什么，Coverage 面板告诉你加载的代码有多少根本没执行。

所以两边要结合着看：构建分析回答“包里有什么”，DevTools 回答“用户实际下载和执行了什么”。

按什么顺序排查

先看首屏入口。入口 chunk 加上它同步依赖的 chunk 一共多大？里面有没有只在弹窗、图表、编辑器里才用的库？有的话，改成动态导入。

再看大依赖。日期库、图标库、工具库是不是整包引入了？可以换成按需导入或者更小的替代品。还要检查是不是用到了 CommonJS 版本，因为那样 tree shaking 会失效。

然后看重复依赖。同一个包的多个版本同时出现，比如有两份 lodash，通常是因为不同依赖要求的版本范围不一致。可以用包管理器的去重功能或 overrides 解决。

接着看分块策略。变化频繁的业务代码和稳定的第三方库分开，有利于缓存。可是把所有第三方库合成一个巨大的 vendor 块，每个页面都得下载一堆用不到的库。

最后别忘了非 JS 资源。内联进 JS 的图片、字体、大 JSON，也会让脚本变大。

怎样确认优化有效

比较时口径要固定：同一种构建模式、同样的压缩方式、同一个入口。否则数字变小可能只是换了统计方法。

关注用户能感受到的指标，比如 LCP、INP 和首屏 JS 执行时间，而不是只看文件少了多少 KB。

最后在 CI 里设预算，比如入口 JS gzip 后不超过某个值，超了就让构建失败或者给出警告。

常见追问

gzip 以后已经很小了，还需要优化吗？

需要。gzip 只减少下载量。浏览器拿到以后要先解压，再解析、执行原始大小的代码。在低端手机上，这部分耗时常常比下载还长。

分块是不是越细越好？

不是。请求太多会增加调度开销，HTTP/2 下也一样有成本。应该按页面和功能的边界来分块。
