前端构建产物应该怎样分析体积？

产物分析要把文件大小、网络传输、解析执行和真实入口联系起来，找到不必要的提前加载、重复依赖和错误分块，再用同口径数据验证收益。

参考答案

简答

  • 先看首屏入口实际加载了哪些 chunk，再看总产物大小；总大小对用户体验的意义有限。
  • 同时关注三个数字：原始大小（影响解析执行）、压缩后传输大小（影响下载）、请求数量。
  • 常见问题是：首屏引入了只在某个页面用到的大依赖、同一依赖被打包多份、分块太碎或太粗。
  • 优化后用同样的构建和测量方式对比，并在 CI 设置体积预算防止回退。

用什么工具看

  • webpack：输出 stats JSON（--json），用 webpack-bundle-analyzer 可视化。
  • Vite / Rolldown：使用 rollup-plugin-visualizer 一类插件生成树图；vite build 的终端输出也会列出各 chunk 的大小和 gzip 大小。
  • 浏览器 DevTools 的 Network 面板和 Coverage 面板：看首屏真正请求了什么、加载后有多少代码没被执行。

构建分析告诉你"包里有什么"，DevTools 告诉你"用户实际下载和执行了什么"，两者要结合。

按顺序排查

  1. 首屏入口：入口 chunk 和它同步依赖的 chunk 加起来有多大？里面有没有只在弹窗、图表、编辑器里才用的库？这些应改为动态导入。
  2. 大依赖：日期库、图标库、工具库是否整包引入？换成按需导入或更小的替代品。检查是否命中了 CommonJS 版本导致 tree shaking 失效。
  3. 重复依赖：同一个包的多个版本（如两个 lodash）同时出现，通常来自依赖的版本范围不一致，可以用包管理器的去重或 overrides 解决。
  4. 分块策略：变化频繁的业务代码和稳定的第三方库分开，利于缓存；但把所有第三方库合成一个巨大的 vendor 块，会让每个页面都下载用不到的库。
  5. 非 JS 资源：内联进 JS 的图片、字体、大型 JSON 也会增加脚本体积。

衡量收益

  • 固定比较口径：同一构建模式、同样的压缩方式、同一个入口。
  • 关注用户指标：LCP、INP 和首屏 JS 执行时间，而不是只看文件变小了多少 KB。
  • 在 CI 中设置预算，例如入口 JS gzip 后不超过某个值，超出时构建失败或给出警告。

常见追问

  • gzip 后很小，还需要优化吗？需要。浏览器要解压后解析和执行原始代码，低端手机上这部分耗时常常超过下载。
  • 分块越细越好吗？不是。请求过多会增加调度开销，HTTP/2 下也一样有成本，应以页面和功能边界分块。
