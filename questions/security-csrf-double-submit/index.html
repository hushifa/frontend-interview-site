Double Submit Cookie 能怎样防御 CSRF？

了解双重提交令牌、SameSite 和服务端校验的关系，避免把一个普通 Cookie 当成 CSRF 防护。

参考答案

Double Submit Cookie 让服务端把随机令牌写入 Cookie，同时要求客户端把同一令牌放入请求头或请求体；服务端比较两份值。攻击者可以诱导浏览器发送 Cookie，但通常不能读取并复制同源页面中的令牌。

在“Double Submit Cookie 能怎样防御 CSRF？”这个问题中，先画出用户输入、第三方内容、接口响应和权限边界，再决定编码、校验和授权放在哪里；客户端检查不能代替服务端约束。这里的 CSRF、Cookie、Web 安全 不是孤立的 API 名称，而是会共同影响输入、过程和最终结果。

安全问题先画出数据流和信任边界：哪些值来自用户、第三方页面、接口响应或浏览器存储，哪些代码拥有真正的权限。防护措施应放在能控制风险的边界上，客户端校验主要用于改善体验，不能代替服务端校验和授权。

令牌必须不可预测、绑定合适的会话或使用签名防篡改，且服务端要校验请求来源、方法和业务权限。仅设置一个可读 Cookie、只检查存在性，或把令牌放进 URL，都不能构成可靠防护。

SameSite、Origin/Referer 校验和自定义请求头可以形成纵深防御，但不能因为启用了其中一项就忽略服务端鉴权与状态变更保护。

验证修复时要覆盖正常流程、攻击输入、错误提示和日志脱敏。安全配置还会受到部署代理、响应头、Cookie 属性和跨域策略影响，不能只在组件代码里判断“已经安全”。

实际落地时，攻击输入往往会经过多个层：URL、表单、接口响应、富文本和第三方窗口。每一层都应明确编码、解析和授权责任，不能因为上游做过一次校验就把数据标记为可信。
