Double Submit Cookie 能怎样防御 CSRF？

服务端下发一个令牌 Cookie，前端读出来再放进请求头一起提交，服务端比较两者。恶意网站能让浏览器带上 Cookie，却读不到它的值，也就填不出请求头。令牌最好与会话绑定并签名。

参考答案

简答

服务端下发一个装着随机令牌的 Cookie，前端发修改请求时，把这个 Cookie 的值读出来，再放进 X-CSRF-Token 请求头里。服务端比较 Cookie 里的值和请求头里的值，一致才处理。

为什么这样能防 CSRF？因为 Cookie 是浏览器自动带的，可请求头必须由页面脚本主动设置。恶意网站受同源策略限制，读不到你网站的 Cookie，也就不知道该往请求头里填什么。

可是只比较“两者相等”的朴素做法有漏洞。如果攻击者能通过子域名或中间人往浏览器里写一个 Cookie，他就可以写一个自己知道的值，再在请求里提交同样的值。所以 OWASP 推荐签名版：令牌是用服务端密钥对“会话标识加随机数”算出的 HMAC，服务端验证签名，并确认令牌属于当前会话。

要注意，这个 Cookie 要让前端读，所以不能设 HttpOnly，但会话 Cookie 仍然要 HttpOnly。它要和 SameSite、Origin 校验一起用。如果服务端本来就有会话存储，同步令牌模式更简单。

请求长什么样

http
POST /api/profile HTTP/1.1
Cookie: __Host-session=s3ss10n; __Host-csrf=7f3a.c9e1
X-CSRF-Token: 7f3a.c9e1
Content-Type: application/json

同一个值出现了两次，一次在 Cookie 里，一次在请求头里，这就是“双重提交”这个名字的来历。

前端怎么带上令牌

JavaScript
function readCookie(name) {
  const prefix = `${name}=`;
  const item = document.cookie.split('; ').find((part) => part.startsWith(prefix));
  return item ? decodeURIComponent(item.slice(prefix.length)) : null;
}

export async function postJSON(url, body) {
  const token = readCookie('__Host-csrf');
  if (!token) throw new Error('缺少 CSRF 令牌，请刷新页面');

  return fetch(url, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', 'X-CSRF-Token': token },
    body: JSON.stringify(body),
  });
}

前端做的事很简单，读 Cookie、放进请求头。安全性全靠一点：只有你自己网站的脚本能读到这个 Cookie。

服务端怎么签名和验证

下面是 Node 的示意代码。令牌格式是“随机数.签名”，签名把会话标识也算了进去：

JavaScript
import { createHmac, randomBytes, timingSafeEqual } from 'node:crypto';

const SECRET = process.env.CSRF_SECRET;

function sign(sessionId, nonce) {
  return createHmac('sha256', SECRET).update(`${sessionId.length}:${sessionId}:${nonce}`).digest('hex');
}

export function issueToken(sessionId) {
  const nonce = randomBytes(16).toString('hex');
  return `${nonce}.${sign(sessionId, nonce)}`;
}

export function verify(sessionId, cookieToken, headerToken) {
  if (!cookieToken || cookieToken !== headerToken) return false;
  const [nonce, mac] = cookieToken.split('.');
  if (!nonce || !mac) return false;
  const expected = Buffer.from(sign(sessionId, nonce));
  const actual = Buffer.from(mac);
  return expected.length === actual.length && timingSafeEqual(expected, actual);
}

签名为什么能堵住朴素版的漏洞？攻击者就算能往浏览器写 Cookie，他也没有服务端密钥，算不出合法的签名。而且签名里含会话标识，拿自己账号的令牌放到别人的会话里也通不过。用测试密钥实际运行，给 alice 签发的令牌，verify('alice', t, t) 返回 true，换成 verify('bob', t, t) 就返回 false。

代码里还有两个细节。签名输入带了长度前缀，避免不同的会话标识和随机数拼出同一个字符串。比较用 timingSafeEqual，耗时不随内容变化，防止攻击者通过响应时间一点点猜出签名。生产环境优先用框架自带的 CSRF 中间件。

还要注意什么

Cookie 用 __Host- 前缀，它要求 Secure、Path=/、不能设 Domain，这样子域名就没法覆盖它。令牌只保护修改操作，GET 本来就不该改数据。登录和登出之后重新签发令牌。

最后，有 XSS 时这套机制会失效，因为恶意脚本跑在你的页面里，可以直接读到令牌。

常见追问

已经设了 SameSite=Lax，还要这个吗？

SameSite 拦不住同站子域名发来的请求，而且依赖浏览器的实现。令牌是额外的一层保证。

同步令牌模式是什么？

服务端把令牌存在会话里，页面通过模板或接口拿到令牌，提交时和会话里的值比较。它不需要用 Cookie 承载令牌，也就没有 Cookie 被写入伪造值的问题。
