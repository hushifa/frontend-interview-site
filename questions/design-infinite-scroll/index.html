无限滚动和虚拟列表怎样选型？怎样触发加载并恢复滚动位置？

无限滚动管“什么时候加载下一页”，虚拟列表管“数据太多时只渲染看得见的部分”，数据量大时两者组合。用 IntersectionObserver 观察列表底部的哨兵元素触发加载，返回列表时用缓存数据和记录的位置手动恢复滚动。

参考答案

简答

无限滚动和虚拟列表解决的是两个不同的问题。无限滚动决定什么时候加载更多数据；虚拟列表决定渲染多少 DOM，只画用户看得见的那几条。累计的条目多到 DOM 拖慢滚动时，两者就要一起用。

触发加载，一般在列表末尾放一个空元素当“哨兵”，用 IntersectionObserver 观察它，快滚到它时就加载下一页，rootMargin 可以让它提前触发。这比监听 scroll 事件再自己算位置开销小。加载还要防重入：请求进行中或者已经没有更多数据时不再触发，失败了要给重试入口。

恢复滚动位置有个前提，就是数据得还在。从详情页返回时，先用缓存把已经加载的几页恢复出来，再滚到记录的位置。单页应用往往要把 history.scrollRestoration 设成 'manual'，自己控制恢复的时机。

要注意，无限滚动不是万能的。需要页脚、需要按页定位、需要分享具体位置的场景，用分页或“加载更多”按钮更合适。

怎样选型

场景方案
几十到几百条、结构简单普通渲染 + 分页或无限滚动
数据持续追加、条目可能上千无限滚动 + 虚拟列表
需要定位第 N 页、分享链接、访问页脚分页或“加载更多”按钮

虚拟列表的原理见《定高虚拟列表怎样手写？怎样根据 scrollTop 算出要渲染哪几行？》，条目高度不固定时怎样测量、怎样处理滚动锚点，见《动态高度的虚拟列表怎样处理测量、滚动锚点和焦点？》。

怎样触发加载

下面这个函数观察哨兵元素，看到它就调用 loadMore：

JavaScript
function observeSentinel(sentinel, loadMore) {
  let loading = false;
  let done = false;

  const observer = new IntersectionObserver(
    async ([entry]) => {
      if (!entry.isIntersecting || loading || done) return;
      loading = true;
      try {
        done = !(await loadMore()); // loadMore 返回是否还有下一页
      } finally {
        loading = false;
      }
      if (done) observer.disconnect();
    },
    { rootMargin: '0px 0px 400px 0px' }, // 距底部 400px 时提前加载
  );

  observer.observe(sentinel);
  return () => observer.disconnect();
}

loading 防止上一页还没回来又发一次请求，done 表示已经没有下一页，这时直接断开观察。rootMargin 的底部设成 400px，相当于把视口往下延长了 400px，哨兵离底部还有 400px 时就开始加载，用户不容易看到空白。

这里有个容易踩的坑。IntersectionObserver 的回调只在元素的交叉状态变化时触发。如果加载的一页数据太少，没能把哨兵推出视口，哨兵就一直处在“可见”状态，状态没变，回调也就不会再触发，列表就卡住不加载了。所以加载完以后，要检查哨兵是否还在可视范围内，必要时接着加载。

如果列表是在某个滚动容器里而不是整个页面滚动，要把 root 设成那个容器。IntersectionObserver 能做什么、不能证明什么，见《IntersectionObserver 适合做什么，能否证明用户看到了内容？》。

返回列表时怎样恢复滚动位置

用户从详情页返回，如果列表重新从第一页请求，原来滚到的那条数据根本就不存在，自然没法恢复位置。所以做法是这样的：

  1. 离开前，把已加载的数据、页码和滚动位置存到状态管理或 sessionStorage 里。如果是虚拟列表，记录第一个可见条目的 ID 和偏移量，比记录像素值更稳定。
  2. 返回时，先用缓存渲染出来，再滚到记录的位置，之后按需在后台刷新。
  3. history.scrollRestoration 默认是 auto，浏览器可能在异步内容还没渲染出来时就尝试恢复，结果失败。设成 manual 以后，由应用在渲染完成后自己滚动。

如果是整页导航，并且命中了 bfcache，也就是浏览器把整个页面原样留在了内存里，那包括滚动位置在内的状态都会完整保留，不用额外处理。

无障碍和体验要注意什么

加载中和加载失败都要有看得见的提示。失败时给一个重试按钮，而不是悄悄停下来不加载了。

读屏用户看不到列表变长了，可以用 aria-live 区域播报“已加载 N 条”。

键盘用户要能跳过列表，到达后面的内容。无限滚动会让页脚永远够不着，必要时把页脚的链接放到别的地方。

常见追问

为什么不用 scroll 事件？

scroll 触发很频繁，要节流，而且每次都要读取布局信息。IntersectionObserver 由浏览器异步计算交叉状态，开销更小。

向上加载历史消息时，怎么保持当前看的位置不动？

插入之前记下 scrollHeight，插入之后把增加的高度加到 scrollTop 上。也可以用 CSS 的滚动锚定。

新数据插到列表头部，导致后面翻页时出现重复怎么办？

用游标分页代替页码分页，再按 ID 去重。
