Angular Hydration 解决什么问题？

Hydration 让客户端 Angular 复用服务端渲染出的 DOM，而不是销毁后重新创建，从而避免页面闪烁、减少重复工作。它要求服务端和客户端渲染出相同的 DOM 结构，直接操作 DOM 的代码需要改写或跳过。

参考答案

简答

服务端渲染出 HTML 以后，浏览器已经能看到页面了。如果没有 hydration，客户端 Angular 启动时会把这份 HTML 丢掉，再自己重新渲染一遍，页面可能会闪一下，LCP、CLS 这些指标也会受影响。Hydration 的意思是不丢，直接复用已有的 DOM 节点，只把事件监听和状态接上去。

开启方法是在启动时加 provideClientHydration()。前提是服务端和客户端渲染出的 DOM 必须一致。不一致时 hydration 会失败，抛出 DOM 不一致的错误，这要当 bug 修。只有加了 ngSkipHydration 的组件，才会销毁后重新渲染。

最常见的不一致来源是直接操作 DOM，比如用 document、innerHTML 或者第三方库改结构。这种代码要改成 Angular 的 API，暂时改不了就给组件加 ngSkipHydration。

还有两个增强功能。事件重放会记下脚本加载完之前用户的点击，hydration 完成后再派发一次；增量 hydration 配合 @defer，让一部分区域按需激活。Angular v22 起，provideClientHydration() 默认开启增量 hydration，并自动带上事件重放；更早的版本要分别加 withEventReplay() 和 withIncrementalHydration()。

怎样开启

TypeScript
import { bootstrapApplication, provideClientHydration, withEventReplay } from '@angular/platform-browser';

bootstrapApplication(App, {
  providers: [provideClientHydration(withEventReplay())],
});

加上 withEventReplay() 是因为页面可见以后，脚本可能还没加载完。用户这时点了按钮，如果没有事件重放，这次点击就丢了。

这是 v22 之前的写法。v22 起只写 provideClientHydration() 就行：增量 hydration 默认开启，它依赖事件重放，所以会把事件重放一起打开，已有的 withEventReplay() 可以删掉。不想要增量 hydration 时，写 provideClientHydration(withNoIncrementalHydration(), withEventReplay())，事件重放仍然保留。

两端为什么会不一致

先看一个时钟组件：

TypeScript
@Component({
  template: `<p>{{ now }}</p>`,
})
export class Clock {
  now = new Date().toLocaleTimeString(); // 服务端和客户端时间不同
}

服务端渲染时算了一次时间，过了一会儿客户端又算一次，两次结果肯定不同，DOM 里的文字就对不上了。

这类问题有几种常见来源，改法也不一样：

  • 时间、随机数：在服务端生成，通过 TransferState 或接口数据传给客户端；或者只在浏览器里更新，放进 afterNextRender。
  • 浏览器专属 API：window、localStorage 在服务端不存在，也放进 afterNextRender 里执行。
  • 不合法的 HTML 嵌套：比如 <p> 里放 <div>。浏览器解析 HTML 时会自动把结构修正掉，结果实际 DOM 和 Angular 以为的不一样。

暂时改不了的组件怎么办

可以先跳过它：

HTML
<legacy-chart ngSkipHydration />

这个组件会在客户端重新渲染，适合暂时没法改造的第三方组件。这个属性只能加在组件的宿主元素上。

增量 hydration 是什么

普通 hydration 要把整页的组件代码都下载下来才能激活。增量 hydration 让某些区域晚一点再激活：

HTML
@defer (hydrate on viewport) {
  <app-comments />
}

服务端照常把评论区的 HTML 输出来，用户能直接看到内容。等评论区滚进视口，客户端才去加载它的代码并 hydration。这样首屏要下载和执行的 JavaScript 就少了。

常见追问

开启 hydration 后，HTTP 请求会在客户端再发一遍吗？

不会。开启 hydration 后，HttpClient 默认会缓存服务端发出的 GET 请求结果并传给客户端，客户端直接用，不再请求一次。

和 React 的 hydration 有什么共同点？

原理类似，都要求两端渲染出的结构一致，不一致的排查思路也差不多，详见《Hydration mismatch 为什么发生，应该怎样修复？》。
