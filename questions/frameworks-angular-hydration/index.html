Angular Hydration 解决什么问题？

Hydration 让 Angular 客户端复用服务端已经生成的 DOM，再接管状态和事件，减少重复渲染；它要求两端结构一致，也不替代权限、缓存和第三方 DOM 管理。

参考答案

简答

启用 provideClientHydration() 后，Angular 客户端会复用 SSR 生成的 DOM，而不是销毁重建，避免闪烁并改善 LCP。前提是服务端和客户端渲染出的 DOM 结构完全一致：直接操作 DOM 的代码和第三方库会导致不匹配，可以用 ngSkipHydration 跳过。较新版本还支持增量 hydration，配合 @defer 按需激活。

为什么服务端 HTML 还不够

SSR 可以让浏览器先看到标题、列表和基本布局，但这些 HTML 只是结果，不包含 Angular 在浏览器中运行所需的状态、事件和生命周期。客户端如果把服务端节点全部销毁再重建，会浪费已经完成的渲染工作，也可能造成内容闪烁。

Hydration 的目标是让 Angular 根据同一份组件结构找到现有 DOM，复用它并补上事件、状态和框架管理关系。它不是把服务端内存搬进浏览器，也不是让客户端不再执行组件代码。

两端必须生成同一棵可匹配的树

服务端输出三行列表，客户端第一次计算却只有两行，节点就无法正确对应。模板中直接使用 Math.random()、当前时间、浏览器时区或只在客户端存在的登录状态，都会造成内容差异。

更稳妥的做法是让服务端确定初始数据，并把必要的非敏感状态传给客户端；或者先输出稳定占位符，等接管后再更新。不能把内部令牌和完整用户记录塞进 HTML，因为页面内容已经对浏览器可见。

浏览器还会修正不合法 HTML。模板源码看起来相同，不代表解析后的 DOM 相同；CDN 也不能随意删除 Angular 用来定位节点的注释和结构信息。应检查最终响应和浏览器中的 DOM，而不只是比较模板文本。

事件接管有一个时间窗口

页面已经显示不代表已经可交互。客户端脚本尚未下载或 hydration 尚未完成时，用户可能点击按钮。Angular 的事件回放能力可以保存部分早期事件，等接管完成后再处理，但它不是所有拖拽、连续输入和第三方事件的通用录像。

登录、支付、提交表单等关键操作不能只因为想减少首屏脚本就延迟到点击后才加载。增量 hydration 适合把评论、折叠面板等非首要区域延后，但要测量用户第一次操作的等待时间。

第三方 DOM 库必须明确所有权

编辑器、地图和图表库经常需要自己创建或移动节点。不要让它们在 Angular 接管前修改 Angular 管理的区域。更安全的方式是让 Angular 只管理外层容器，第三方库只拥有一个内部节点，并在销毁时释放实例和监听器。

如果某个组件暂时无法复用，可以局部使用 ngSkipHydration 隔离，但这会牺牲 SSR 复用收益并增加客户端重新渲染工作。它适合迁移边界，不适合掩盖随机数据、错误嵌套或缓存混用户等根因。

如何排查 mismatch

先固定时间、语言、用户和实验分组，检查服务端响应 HTML 与客户端首次状态；再逐层禁用第三方 DOM 操作，确认是结构差异还是生命周期问题。typeof window !== 'undefined' 只能避免服务端访问浏览器 API，不能保证两端输出相同。

排查时不要只看控制台。还要记录 HTML 到可交互的时间、首个点击是否成功、重复请求、主线程长任务和内存变化。服务端缓存如果把一个用户的 HTML 发给另一个用户，hydration 本身无法修复这个安全问题。

稳定的 hydration 方案必须同时满足：内容一致、事件能及时接管、缓存不泄露用户数据、第三方库有清晰边界，并且在不支持或失败时仍有可用的客户端渲染路径。
