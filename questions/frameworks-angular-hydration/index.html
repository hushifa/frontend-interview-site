Angular Hydration 解决什么问题？

理解服务端 HTML 与客户端事件接管的关系，处理 Hydration 不匹配、跳过策略和浏览器 API 边界。

参考答案

服务端渲染先把内容变成 HTML，用户不必等客户端应用全部启动才看到页面。但浏览器拿到 HTML 后，Angular 仍需要建立组件状态、绑定和事件处理。

Hydration 尝试复用已有 DOM 完成接管，减少先销毁服务端内容再重建的成本。它不是把整个服务端内存搬到浏览器，也不代表客户端完全不需要执行组件代码。

复用要求两边理解同一棵结构

服务端输出了三行列表，客户端初始状态却只有两行，框架就无法按预期对应节点。随机值、不同时间、语言或时区、登录数据差异，都可能造成结构或显示不一致。

Angular 的 hydration 还依赖它生成的注释和相关 DOM 结构信息。CDN 或压缩工具如果随意移除必要注释、改写空白或结构，可能让原本正确的输出失去匹配条件。

浏览器也会修正不合法 HTML，例如某些错误嵌套会被重新组织。源码看起来相同，不代表解析后的 DOM 与服务端假设一致，因此要检查最终页面结构，而不只比较模板字符串。

直接操作 DOM 容易抢在框架之前改结构

第三方库插入、移动或删除节点，或代码通过 innerHTML 重写 Angular 管理区域，都可能让 hydration 找不到预期节点。

应优先用模板与框架管理状态。确实需要浏览器专属库时，在合适的渲染生命周期后初始化，并明确它拥有的 DOM 区域，不要在客户端接管前修改框架正在匹配的树。

仅仅判断 typeof window !== 'undefined' 可以避免服务端访问不存在的对象，却不保证两端输出一致。如果服务端渲染 A、浏览器立即渲染 B，仍然可能出现 mismatch。

先可见与先可交互不是同一个时刻

HTML 已显示时，客户端事件可能还没接好。事件重放可以捕获部分早期原生事件，等 hydration 完成后再处理，改善用户提前点击的体验。

但它不是任何交互都能无限保存的通用机制，也不代表网络和脚本加载成本消失。支持事件、增量 hydration 的启用方式和默认行为要按项目 Angular 版本核对。

增量 hydration 可以让特定区域按触发条件延后接管，减少一次性客户端工作；同时也要评估该区域首次操作的等待与事件处理。不能只追求初始脚本少，却让关键按钮迟迟不能响应。

数据传递与缓存需要保护用户边界

服务端获取的数据可以通过相应传递与缓存机制减少客户端重复请求，但进入 HTML 或客户端可读载荷的数据不再是秘密。不能把内部令牌或完整用户记录一并传给页面。

响应缓存若混淆不同用户，可能导致数据泄露，这不是 hydration 能修复的问题。服务端初始状态与客户端首轮状态应来自一致且有权限的数据，同时有明确更新规则。

SSR 何时认为应用稳定，关系到输出和清理。在 Zoneless 等模式下，自定义异步任务要按当前框架机制纳入需要的稳定性管理，不能假定所有 Promise 都自动被等待。

跳过是局部迁移手段，不是隐藏问题

ngSkipHydration 可以用于合适的组件宿主，让相关子树不按普通方式复用，而采用对应的重新渲染路径。它会牺牲复用收益，也不能随意加在任何普通元素上当作消除报错的万能属性。

如果某个旧组件暂时无法兼容，可以局部隔离并安排修复；若整页都跳过，就应重新审视 SSR 与客户端接管方案，而不是继续宣称享受完整 hydration 优势。

验证应检查服务端 HTML、客户端控制台、早期点击、慢脚本、不同用户与语言，以及第三方 DOM 库初始化。构建成功只证明代码能生成，真实 DOM 复用和交互时机仍需浏览器场景验证。
