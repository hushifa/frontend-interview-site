React useId 解决什么 ID 生成问题？

useId 为组件内部的可访问关联生成实例级 ID，并在匹配的服务端与客户端树中支持 hydration 一致性。它不提供业务实体身份，不适合作为列表 key 或持久化标识，多根应用还需要协调前缀。

参考答案

封装一个输入组件时，label 需要通过 htmlFor 指向 input，说明文字又可能通过 aria-describedby 与它关联。如果在组件里写死 id="email"，页面放两份组件就会出现重复 ID，标签和说明可能关联到错误位置。

useId 主要解决这种组件内部关联，不是为数据库记录或用户会话生成新的业务身份。

一份组件，多次使用仍有各自的关联

JSX
import { useId, useState } from 'react';

function EmailField({ label, name }) {
  const id = useId();
  const inputId = `${id}-input`;
  const hintId = `${id}-hint`;

  return (
    <div>
      <label htmlFor={inputId}>{label}</label>
      <input id={inputId} name={name} type="email" aria-describedby={hintId} />
      <p id={hintId}>请输入完整的邮箱地址。</p>
    </div>
  );
}

export default function ContactFields() {
  const [revision, setRevision] = useState(0);
  return (
    <section>
      <p>显示版本：{revision}</p>
      <EmailField label="联系邮箱" name="contactEmail" />
      <EmailField label="备用邮箱" name="backupEmail" />
      <button type="button" onClick={() => setRevision(value => value + 1)}>刷新显示</button>
    </section>
  );
}

每个 EmailField 调用 useId，得到属于该组件实例的关联前缀，再派生 input 与提示文字的不同 ID。两份组件不会因为复用同一段代码就共享同一个硬编码 ID。

父级重新渲染时，同一组件实例的关联仍保持稳定。name 则继续表达表单提交字段名，与 DOM 的 id 是不同职责，不应拿生成的 ID 自动替代稳定的接口字段名。

为什么不用随机数或模块级计数器

渲染时使用随机数，会让同一组件不同渲染拿到不同 ID，也难以使服务端 HTML 与客户端首次输出一致。模块级自增计数器则容易受到执行顺序、多根应用和不同服务器请求的影响。

useId 根据 React 所管理的组件树关系生成适合这种关联的 ID。即使服务端生成与客户端 hydration 的执行顺序不完全一样，只要对应树结构符合要求，React 就能保持需要的匹配。

但它不能修复所有 hydration 问题。服务端和客户端渲染了不同组件、不同条件分支或不同文本，仍然可能不匹配；不能一加 useId 就忽略整个初始界面的一致性。

多个相关元素可以共用一个前缀

输入、说明、错误信息通常属于同一组件，用一次 useId 再拼接不同后缀即可。重点是每个实际 DOM 元素的完整 ID 唯一，关联属性指向真实存在的目标。

条件错误提示可以按状态显示，并相应调整 aria-describedby，而 useId 本身仍应按 Hook 规则在顶层调用。不能在“有错误时”才临时插入这个 Hook，改变调用结构。

这个 Hook 只是生成关联标识。标签文案是否清楚、错误是否可读、焦点是否合理，以及控件是否使用正确原生语义，仍需独立设计。

它与列表 key 的职责不同

key 帮助 React 判断同级数据项身份，应该来自那条记录的稳定业务标识。useId 是组件实例里的关联工具，不能在 map 中动态调用它给每项生成 key，也不能用它替代服务端 ID。

当列表重排时，React 先需要正确的 key 来保留对应组件实例；如果这个身份关系已经错误，组件内生成的 ID 不会倒过来替你修复列表映射。

同一个 ID 也不应该写进数据库、跨请求缓存键或长期分享协议。组件卸载重建、树结构改变或根配置变化后，不应再把旧值视为外部系统可依赖的永久标识。

同页多个 React 根要协调 identifierPrefix

页面上有多个独立 createRoot 或 hydrateRoot 时，可以给各自设置不同的 identifierPrefix，避免独立应用生成的关联 ID 相互冲突。

若某个根来自服务端渲染，服务端渲染 API 与客户端 hydrateRoot 需要使用对应一致的前缀。前缀属于根级协议，不是仅在客户端临时补一个随机字符串就足够。

不同框架可能封装了根与服务端入口，需要通过框架支持的方式配置，不应绕开框架再创建第二个重复根。

不依赖 ID 的字符串格式

生成值应被当作不透明标识。不要解析里面的字符来推导组件层级，也不要假定它一定只有字母数字。若手动拼 CSS 选择器，应按需使用 CSS.escape；通过 document.getElementById 查询则不需要把它先解释成选择器语法。

useId 在一般同步组件中可用于相应服务端渲染流程，但当前 API 对异步 Server Component 等场景仍有约束，应按所用 React 版本文档处理。它不是任意函数都能调用的全局 ID 工具。

验证时可以重复放置组件、触发无关重渲染，再检查 label、描述文字和 input 是否仍正确关联。需要 SSR 的页面还应真正执行 hydration，确认初始 ID 与前缀匹配，而不是只看客户端页面没有报重复 ID。
