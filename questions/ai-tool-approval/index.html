模型提出工具调用后，前端应该怎样展示和确认？

工具调用表示模型提出带参数的操作请求，不代表操作已执行，更不代表获得用户权限。界面应区分参数接收中、参数就绪、等待确认、执行中、成功、失败和拒绝等状态，并用调用 ID 关联同一操作。

参考答案

模型提出工具调用，只说明它生成了一个操作建议。参数可能错误，目标可能超出用户权限，也可能受到外部资料里的恶意指令影响，因此不能把“模型选择了工具”直接等同于“系统已经获得执行授权”。

前端的作用是帮助用户理解具体动作并作出必要选择；真正执行前的身份、参数和资源权限校验必须在受控执行端完成。

先区分参数准备与执行状态

工具参数可能流式到达。接收中只能展示预览，完整并通过格式校验后，才能形成可确认的调用。随后可以进入待确认、执行中、成功、失败、被拒绝或已取消等状态。

每次调用需要稳定 call ID，确认、执行日志和结果都关联它。不要因为文本里出现“正在发送邮件”就先显示发送成功，也不要因为流断开就假定邮件没有发送。

具体 SDK 的工具 part 状态可以提供基础信息，但应用仍需建模真实副作用与审批记录，不能只用一个 loading 字段包住整个过程。

确认内容要让用户能判断影响

“允许调用 sendEmail 吗”通常不够。应展示收件人、主题、正文或摘要、附件以及使用哪个账号发送。删除操作需要展示具体对象与数量，金额操作需要展示币种、金额和对象。

对长参数可以提供摘要与可展开的完整细节，但不能隐藏决定风险的部分。对于批量操作，明确这是批准全部集合还是其中某项，避免用户只看到第一条却批准了全部。

已有会话授权可以减少重复确认，但必须有清楚范围。读取某个文件夹的许可，不应自然扩展成删除文件或向外发送内容。

同意必须绑定实际执行参数

如果用户确认的是 A 收件人与一份正文，模型随后改成 B 收件人或增加附件，旧同意不应继续有效。可以将审批绑定到调用 ID、规范化参数或参数摘要、用户身份与有效期，并由执行端保存验证。

浏览器传来的 approved: true 不能成为唯一依据，用户可以自己构造请求。确认记录还应在服务端与当前任务、权限和参数对应，必要时再次检查资源版本，避免批准后目标对象已发生重要变化。

这也是为什么“用户在聊天里说过可以”不一定能批准所有后续动作：要结合上下文确定它到底覆盖什么，而不是让模型自行扩大解释。

执行前仍要独立授权与校验

Schema 校验检查参数形状，权限检查确认用户有权操作资源，业务检查确认金额、库存、状态等允许执行。三者都不能由确认弹窗替代。

高风险操作应使用最小权限凭据，限制目标与可调用能力。模型不能选择任意 shell、SQL 或内网地址，然后靠一个泛化“确认”按钮就获得全部能力。

对重复点击、网络重试和恢复执行，应有幂等设计。界面禁用按钮能减少误操作，但不能保证服务端只收到一次请求。

结果未知时先核对，不盲目重试

提交后连接中断，外部系统可能已经完成写入。直接再次执行可能重复付款、发信或建单。应根据调用标识查询状态，必要时明确显示“结果待确认”。

用户取消也只能阻止尚未执行的步骤，已经完成的副作用需要专门补偿或撤销流程。不能把关闭确认框当作所有执行链路都已停止。

成功结果应显示真实产物、目标或外部记录，失败应给出可理解原因并保留诊断标识。工具返回文本仍按不可信内容处理，不允许它冒充新的用户授权。

可靠的审批流程既不会要求用户反复批准已经明确授权的低风险动作，也不会把一次模糊同意当成无限权限。核心是具体、可核验且与执行保持一致。
