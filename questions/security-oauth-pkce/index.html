OAuth 2.0 的 PKCE 解决了什么问题？

PKCE 让发起授权的客户端生成一个随机 code_verifier，授权请求只发送它的 SHA-256 摘要 code_challenge，换取令牌时再提交原值。即使授权码在回调中被截获，攻击者没有 code_verifier 也换不到令牌。RFC 9700 要求公共客户端必须使用 PKCE，机密客户端推荐使用。

参考答案

简答

  • 问题：浏览器单页应用和移动应用是公共客户端，无法保存 client_secret。授权码可能通过重定向、日志、恶意应用注册的同名回调被截获，攻击者拿去就能换到令牌。
  • PKCE 把授权码和"发起这次授权的那个客户端实例"绑定：只有持有 code_verifier 的一方能完成兑换。
  • code_challenge_method 用 S256；plain 会把原值暴露在授权请求里，RFC 9700 指出目前只有 S256 能避免这一点。
  • RFC 9700 规定：公共客户端必须（MUST）使用 PKCE；机密客户端推荐（RECOMMENDED）使用；授权服务器必须支持 PKCE。
  • 它不替代 state（防 CSRF）和回调地址精确匹配，也不认证客户端身份。

流程

  1. 客户端生成 43–128 个字符的随机 code_verifier，计算 code_challenge = BASE64URL(SHA256(code_verifier))。
  2. 跳转授权：/authorize?response_type=code&client_id=...&redirect_uri=...&state=...&code_challenge=...&code_challenge_method=S256。
  3. 回调拿到 code，校验 state。
  4. 换令牌：POST /token，参数包括 grant_type=authorization_code、code、redirect_uri、code_verifier。
  5. 授权服务器重新计算摘要，与第 2 步保存的 code_challenge 比较，一致才签发令牌。

生成参数

JavaScript
function base64url(bytes) {
  return btoa(String.fromCharCode(...bytes)).replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}

export async function createPkce() {
  const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));
  const digest = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(verifier));
  return { verifier, challenge: base64url(new Uint8Array(digest)) };
}

verifier 保存在 sessionStorage 中直到回调完成，用完即删。crypto.subtle 只在安全上下文（HTTPS 或 localhost）可用。

RFC 9700 的其他相关要求

  • 不应再使用隐式流程（response_type=token），改用授权码加 PKCE。
  • 授权服务器校验回调地址必须用精确字符串匹配（localhost 回调的端口号除外）。
  • 签发给公共客户端的刷新令牌必须做发送方约束（如 DPoP）或启用轮换。

前端令牌存放

浏览器中直接持有访问令牌，XSS 可以读取。更安全的方案是 BFF：由同源后端作为机密客户端完成授权码兑换，浏览器只持有 HttpOnly 会话 Cookie。

常见追问

  • 有了 PKCE 还需要 state 吗？需要。state 防止攻击者把自己的授权码注入受害者的回调，PKCE 防止截获的授权码被兑换。
  • 和 OIDC 的关系？OIDC 在 OAuth 之上加了身份认证，同样使用授权码加 PKCE，见《OpenID Connect 和 OAuth 2.0 分别解决什么问题？》。
