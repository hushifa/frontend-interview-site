OAuth 2.0 的 PKCE 解决了什么问题？

PKCE 让客户端先生成一个随机密码，授权时只发它的摘要，换令牌时再交出原值。授权码就算被截走，攻击者没有原值也换不到令牌。RFC 9700 要求公共客户端必须使用。

参考答案

简答

浏览器里的单页应用和手机 App 叫公共客户端，代码在用户手里，存不住 client_secret。可是 OAuth 授权码流程里，授权码会经过重定向回到客户端，可能出现在日志里，也可能被恶意 App 注册的同名回调截走。攻击者拿到授权码，就能去换令牌。

PKCE 的做法是：客户端先生成一个随机字符串，叫 code_verifier，授权请求里只发它的 SHA-256 摘要，叫 code_challenge。换令牌时再提交原值，授权服务器重新算摘要比对。只截获授权码没用，因为攻击者手里没有 code_verifier。

RFC 9700 规定，公共客户端必须使用 PKCE，机密客户端推荐使用，授权服务器必须支持。摘要方法用 S256，plain 会把原值直接暴露在授权请求里。

要注意它管不了的事。它不认证客户端是谁，也不替代回调地址的精确匹配。至于防 CSRF，只有确认授权服务器支持 PKCE 时才能靠它，不能确认时仍然要用 state 或 OIDC 的 nonce。

流程是怎样的

  1. 客户端生成 43 到 128 个字符的随机 code_verifier，计算 code_challenge = BASE64URL(SHA256(code_verifier))。
  2. 跳转授权：/authorize?response_type=code&client_id=...&redirect_uri=...&state=...&code_challenge=...&code_challenge_method=S256。
  3. 回调拿到 code，校验 state。
  4. 换令牌：POST /token，参数包括 grant_type=authorization_code、code、redirect_uri、code_verifier。
  5. 授权服务器重新计算摘要，与第 2 步保存的 code_challenge 比较，一致才签发令牌。

关键在第 2 步和第 4 步的不对称。第 2 步经过浏览器地址栏，可能被人看到，但发的只是摘要，从摘要反推不出原值。第 4 步才交出原值，而这一步是客户端直接请求授权服务器的。所以它把授权码和“发起这次授权的那个客户端实例”绑在了一起。

生成参数

JavaScript
function base64url(bytes) {
  return btoa(String.fromCharCode(...bytes)).replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}

export async function createPkce() {
  const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));
  const digest = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(verifier));
  return { verifier, challenge: base64url(new Uint8Array(digest)) };
}

32 个随机字节经过 base64url 编码，正好是 43 个字符，落在规范要求的范围里。用 Node 22 实际运行，verifier 和 challenge 的长度都是 43。

verifier 存在 sessionStorage 里，等回调完成就删掉。另外 crypto.subtle 只在安全上下文里能用，也就是 HTTPS 或 localhost。

RFC 9700 还有哪些相关要求

不应该再用隐式流程，也就是 response_type=token，改用授权码加 PKCE。授权服务器校验回调地址时，必须用精确的字符串匹配，只有 localhost 回调的端口号例外。签发给公共客户端的刷新令牌，必须做发送方约束（比如 DPoP）或者启用轮换。

令牌放在前端安全吗

浏览器直接持有访问令牌时，一旦有 XSS 就会被读走。更安全的方案是 BFF，也就是一个同源的后端，由它作为机密客户端完成授权码兑换，浏览器只持有一个 HttpOnly 的会话 Cookie。

常见追问

有了 PKCE 还需要 state 吗？

RFC 9700 的规定是：确认授权服务器支持 PKCE 时，客户端可以靠 PKCE 防 CSRF；无法确认时必须用 state 或 nonce。很多应用仍然保留 state，顺便带上登录前所在的页面信息。

PKCE 和 OIDC 是什么关系？

OIDC 在 OAuth 之上加了身份认证，同样使用授权码加 PKCE，见《OpenID Connect 和 OAuth 2.0 分别解决什么问题？》。
