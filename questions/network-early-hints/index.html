HTTP 103 Early Hints 适合怎样的加载优化？

服务器生成 HTML 需要时间时，可以先发一个 103 响应，带上 preconnect 和 preload 的 Link 头，让浏览器在等待期间提前建连、下载关键资源。它取代了已被 Chrome 移除的 HTTP/2 Server Push。

参考答案

简答

  • 103 是信息性响应，在最终的 200 之前发送，主要携带 Link 头（preconnect、preload），也可以带 Content-Security-Policy 约束这些预加载。
  • 浏览器收到后立即处理其中的 preconnect 和 preload，利用服务器"思考时间"提前加载。
  • 适合首字节慢的页面，例如服务端渲染要查数据库；首字节本来就快的静态页面收益很小。
  • 浏览器只处理第一个 103 响应；建议只在 HTTP/2 及以上发送，旧客户端可能处理不好信息性响应。
  • Server Push 是服务器主动推送资源，浏览器无法判断是否已有缓存，常常浪费带宽，Chrome 已移除；103 只发提示，由浏览器决定是否下载。

响应示例

http
HTTP/2 103
Link: <https://cdn.example>; rel=preconnect; crossorigin
Link: </assets/app.css>; rel=preload; as=style

HTTP/2 200
Content-Type: text/html
Link: </assets/app.css>; rel=preload; as=style

<!doctype html>...

最终响应仍需要正常引用这些资源，103 只是提前启动。

提示什么

  • 适合：首屏 CSS、关键字体、首屏主图、关键第三方域名的 preconnect。
  • 不适合：因用户而异的资源、可能不会用到的资源。103 在路由和数据确定前发送，提示内容应该对所有访问这个 URL 的用户都成立。

部署要点

  • 多数情况由 CDN 生成 103：CDN 记住源站上次 200 响应里的 Link 头，下次请求时先发 103。
  • 最终响应如果是跨源重定向，浏览器会丢弃这次 103 的提示。
  • 103 中可以带 Content-Security-Policy，浏览器处理提示时会遵守。

验证效果

  • DevTools Network 中资源的 Initiator 会显示来自 Early Hints。
  • 对比开启前后的 LCP 和资源开始时间，用真实用户数据确认收益。

常见追问

  • 为什么不直接在 HTML 头部写 preload？HTML 本身还没生成，103 能比 HTML 更早到达浏览器。
  • 浏览器支持怎样？各浏览器的支持范围和限制不同，部署前查看 MDN 的兼容表；不支持的浏览器会忽略 103，不会出错。
