HTTP 103 Early Hints 适合怎样的加载优化？

服务器生成 HTML 要花时间时，可以先回一个 103，带上 preconnect 和 preload 提示，让浏览器趁等待先建连、先下关键资源。它取代了已被 Chrome 移除的 HTTP/2 Server Push。

参考答案

简答

服务端渲染的页面，服务器可能要查几百毫秒数据库才能吐出 HTML。这段时间浏览器什么都做不了。103 Early Hints 就是让服务器先回一个“提前提示”，在最终的 200 之前发出。

103 是信息性响应，主要带 Link 头，写上 preconnect 和 preload。浏览器收到后马上处理，利用服务器“思考”的时间提前建连、下载关键资源。它也可以带 Content-Security-Policy，约束这些预加载。

所以它适合首字节慢的页面。首字节本来就很快的静态页面，收益很小。

要注意，浏览器只处理第一个 103；建议只在 HTTP/2 及以上发，旧客户端可能处理不好信息性响应。另外，它和 Server Push 不一样：Push 是服务器硬塞资源，浏览器没法说“我已经有缓存了”，常常浪费带宽，Chrome 已经移除；103 只发提示，下不下由浏览器决定。

响应长什么样

http
HTTP/2 103
Link: <https://cdn.example>; rel=preconnect; crossorigin
Link: </assets/app.css>; rel=preload; as=style

HTTP/2 200
Content-Type: text/html
Link: </assets/app.css>; rel=preload; as=style

<!doctype html>...

同一个请求先后收到两个响应。103 让浏览器先去连 CDN、先下 CSS；等 200 和 HTML 到了，CSS 可能已经下好了。

最终的 HTML 里仍然要正常引用这些资源。103 只是让下载提前开始，不能代替引用。

该提示哪些资源

适合放进 103 的，是首屏 CSS、关键字体、首屏主图，以及关键第三方域名的 preconnect。

不适合的，是因人而异的资源，以及可能用不上的资源。原因是 103 发出去的时候，服务器还没确定路由和数据，所以提示的内容必须对所有访问这个 URL 的用户都成立。

部署时要注意什么

大多数情况下 103 是 CDN 生成的。CDN 记住源站上一次 200 响应里的 Link 头，下次有请求进来，先替源站发出 103。

如果最终响应是一个跨源重定向，浏览器会丢掉这次 103 的提示。

103 里带的 Content-Security-Policy，浏览器处理提示时会遵守。

怎么验证效果

在 DevTools Network 面板里，资源的 Initiator 会显示来自 Early Hints。然后对比开启前后的 LCP 和资源开始时间，用真实用户数据确认收益。

常见追问

为什么不直接在 HTML 头部写 preload？

因为 HTML 本身还没生成出来。103 能比 HTML 更早到达浏览器。

浏览器支持情况怎样？

各浏览器支持的范围和限制不同，部署前查 MDN 的兼容表。不支持的浏览器会忽略 103，不会出错。
