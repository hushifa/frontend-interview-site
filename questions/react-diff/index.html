React 的 diff 算法怎样处理单节点和多节点？key 起什么作用？和 Vue 有什么不同？

React 只比较同一层的节点，类型不同就整棵替换。单节点时按 key 和类型在旧子节点里找能复用的；多节点时先从左往右按位置比，遇到 key 对不上就把剩下的旧节点放进 Map，按 key 查找，并用 lastPlacedIndex 判断谁需要移动。Fiber 没有反向指针，所以 React 不做双端比较；Vue 3 从两端同步，再用最长递增子序列减少移动。

参考答案

简答

状态更新后，React 要拿新渲染出的元素和上一次的 Fiber 树比较，决定哪些节点复用、哪些新建、哪些删除、哪些移动。完整的树比较算法复杂度是 O(n³)，React 用两个假设把它降到 O(n)：类型不同的元素会产生不同的树；开发者可以用 key 告诉 React 哪些子元素在多次渲染之间是同一个。

所以 React 只比较同一层。同一位置上类型变了，比如 div 换成 span、Counter 换成 p，整棵子树直接卸载重建，里面的 state 也一起丢掉。类型相同就复用节点，只更新属性，再接着比较子节点。

子节点分两种情况。新的只有一个节点时，React 在旧子节点里找 key 相同的；key 相同、类型也相同就复用，其余旧节点删掉。新的是数组时，React 先从左往右按位置逐个比，遇到 key 对不上就停下，把剩下的旧节点放进一个按 key 索引的 Map，再逐个查找。判断移动时它记录一个 lastPlacedIndex，复用的节点在旧列表里的位置比它小，就标记为需要移动。

和 Vue 3 最大的不同在多节点。React 源码注释写明，Fiber 没有指向前一个兄弟的指针，所以不从两端搜索，只往右走。Vue 3 先同步首尾相同的部分，中间乱序的部分用最长递增子序列找出不动的节点。另外 Vue 有编译器提供的 PatchFlags，能跳过不变的内容，React 运行时则要完整比较，React Compiler 是在组件层面做缓存，减少的是重新渲染。

类型不同为什么整棵重建

react.dev 讲状态保留时说得很直接：同一个组件渲染在树的同一个位置，它的 state 就保留；同一个位置换成了别的组件，React 会丢掉它和整棵子树的 state。

这就是第一个假设的后果。React 不会去比较 <Counter> 和 <p> 里面有没有相似的结构，类型一变就当成两棵完全不同的树。所以文档提醒，不要在组件里面定义组件。每次渲染都会得到一个新的函数，类型每次都不同，React 每次都会重置下面所有的 state。

单节点怎么比

新的子节点只有一个元素时，源码走 reconcileSingleElement。它遍历旧的子节点：

  • key 不同，删掉这个旧节点，继续看下一个兄弟；
  • key 相同、类型也相同，复用它，并删掉剩下的所有兄弟；
  • key 相同但类型不同，说明不可能复用了，把它和剩下的兄弟全部删掉，新建一个。

为什么 key 相同而类型不同就直接放弃？因为在同一层里 key 应该唯一，key 对上了却类型不同，后面不可能还有能复用的节点。

多节点怎么比

新的子节点是数组时，源码走 reconcileChildrenArray，大致分三步。

第一轮从左往右，把新旧节点按位置一对一比较，key 相同就更新。遇到 key 不同就跳出循环。大多数更新只是改了某几项内容，顺序没变，这一轮就能处理完。

如果新的已经走完了，剩下的旧节点全部删除。如果旧的走完了，剩下的新节点全部新建插入。

两边都没走完，说明有插入、删除或移动。React 把剩下的旧节点放进 Map，key 作为键，没写 key 的用下标。然后继续遍历新节点，在 Map 里查能复用的旧节点，查到就从 Map 里拿掉。遍历完 Map 里还剩的，就是要删除的。

移动的判断在 placeChild 里。React 记录 lastPlacedIndex，表示已经处理的、不需要移动的节点里，旧下标最大的那个。复用的节点旧下标比它小，说明它原来在某个“不动的节点”前面，现在跑到后面去了，要标记移动；否则就不动，并把 lastPlacedIndex 更新为它的旧下标。

下面按这个规则模拟三种变化：

JavaScript
function reactMoves(oldKeys, newKeys) {
  const oldIndex = new Map(oldKeys.map((key, i) => [key, i]));
  let lastPlacedIndex = 0;
  const result = [];
  for (const key of newKeys) {
    if (!oldIndex.has(key)) {
      result.push(`${key}:插入`);
      continue;
    }
    const index = oldIndex.get(key);
    if (index < lastPlacedIndex) {
      result.push(`${key}:移动`);
    } else {
      lastPlacedIndex = index;
      result.push(`${key}:不动`);
    }
  }
  return result.join(' ');
}

console.log(reactMoves(['A', 'B', 'C', 'D'], ['A', 'C', 'B', 'D'])); // A:不动 C:不动 B:移动 D:不动
console.log(reactMoves(['A', 'B', 'C', 'D'], ['D', 'A', 'B', 'C'])); // D:不动 A:移动 B:移动 C:移动
console.log(reactMoves(['A', 'B', 'C'], ['A', 'X', 'B', 'C']));      // A:不动 X:插入 B:不动 C:不动

第一行交换了 B 和 C，只有 B 被移动。第三行在中间插入 X，原有的节点都不用动。

第二行值得注意。只是把最后的 D 挪到最前面，按理说移动一次就够了。可是 React 先遇到 D，旧下标 3，lastPlacedIndex 变成 3，后面 A、B、C 的旧下标都比 3 小，于是三个都被标记为移动。这就是只往右走的代价，源码注释也承认这种做法处理不好反转这类情况，但它认为这种情况不常见。

key 起什么作用

从上面的过程可以看出，key 是 React 认出“这还是原来那个节点”的唯一依据。

react.dev 说明，不写 key 时 React 默认用数组下标。下标只表示位置，列表头部插入一项，所有项的下标都变了，React 会把第一项的 state 和 DOM 给新插进来的那一项用，输入框内容就会错位。也不要用 Math.random() 这类每次都变的值，否则 key 永远对不上，每次都要重建所有组件和 DOM，用户的输入也会丢失。key 只要在兄弟节点之间唯一就够了，不同数组里可以重复。下标作 key 的具体问题见《列表中的 key 为什么不能随意使用数组下标？》。

和 Vue 的 diff 有什么不同

两者的基本规则相同：只比较同一层，类型和 key 都相同才复用。区别主要在多节点的比较策略。

React 的源码注释说明了原因：Fiber 的兄弟节点之间只有指向下一个的 sibling 指针，没有指向上一个的，所以不从两端搜索，先试试只往右走能走多远。Vue 的子节点是数组，可以从两头比较。Vue 2 用双端比较，Vue 3 先同步首尾相同的部分，中间乱序的部分求最长递增子序列，子序列里的节点不动，只移动其他的。像上面“D 挪到最前面”的例子，Vue 3 只会移动 D 一次，见《Vue 3 的快速 diff 是怎样用最长递增子序列减少移动的？》。

另一个区别在编译期。Vue 的模板编译器会把“哪些节点不变、哪个属性会变”写进渲染函数，运行时能跳过大量比较，见《Vue 模板编译如何减少运行时更新工作？》。React 的 JSX 编译后就是普通的函数调用，diff 要在运行时完整比较。React Compiler 做的是自动缓存组件和计算结果，减少不必要的重新渲染，并不改变 diff 本身。

常见追问

diff 的结果是马上改 DOM 吗？

不是。diff 发生在渲染阶段，只在 Fiber 上打标记，比如插入、移动、删除。等整棵树处理完，提交阶段才统一操作真实 DOM。两个阶段的区别见《React 的虚拟 DOM 是什么？Fiber 解决了什么问题？》。

想让一个组件重置 state，可以利用 diff 规则吗？

可以。给它换一个 key，React 会认为这是一个不同的节点，卸载旧的、挂载新的，state 就重置了。react.dev 在讲重置状态时就用这个办法。
