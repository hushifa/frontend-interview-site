异步迭代器和 for await...of 适合处理什么数据？

异步迭代把下一项数据建模为可等待的结果，适合分页、流和逐步产生的数据。for await...of 顺序消费结果，但不会自动限制生产者内部缓存，也不会替底层网络实现取消。

参考答案

简答

  • 异步迭代器的 next() 返回 Promise，for await...of 逐个等待结果，适合分页、流式响应和逐块读取。
  • 消费是顺序的，不会自动并发处理各项。
  • 提前 break 会调用 return() 关闭迭代器，循环会等待清理完成。
  • 背压需要生产者按需产出，写了 for await 不等于自动具备背压。

普通数组已经有全部元素，普通迭代器可以同步给出下一项。分页接口、网络流或异步生成的数据则不同：下一项可能还要等请求、读取或计算完成。

异步迭代器把“给我下一项”定义成一个可等待的过程。数据源提供 Symbol.asyncIterator，返回的迭代器通过 next 产生 Promise 结果，兑现后得到 { value, done }。for await...of 帮助消费者等待并检查这些结果。

async Generator 是一种直观的生产者

JavaScript
async function* pages() {
  yield [1, 2];
  await Promise.resolve();
  yield [3];
}

async function readPages() {
  for await (const page of pages()) {
    console.log(page.join(','));
  }
}

readPages();
// 输出：1,2
// 随后输出：3

消费者没有一次拿到完整数组，而是先得到第一页，再请求后面的数据。真实分页生产者可以在每次需要下一页时请求接口，并根据服务端的游标或完成标志结束；这里用就绪数据演示协议，不包含网络请求。

调用 async Generator 函数先得到异步生成器对象，next 才推动执行。函数体可以 await 异步操作，也可以 yield 一项结果。它仍然不是独立线程，里面长时间的同步计算依然会阻塞所在执行环境。

顺序消费不等于“自动并发所有处理”

for await...of 会等待本次 next 的结果，然后执行循环体，再继续请求下一项。如果循环体中也 await 某项处理，那么通常是这项处理结束后才请求下一项。

如果循环体只是启动一个异步函数却没有等待它，那些处理仍然可能同时在途，错误也可能没有被当前循环观察。需要并发处理时应明确管理任务集合与并发上限，而不是误以为 for await 自带并发池。

与 Promise.all 等待一组已启动任务相比，异步迭代很适合总量尚不确定、希望边到达边处理的数据。但如果传进来的是一个已经创建了大量请求 Promise 的数组，那些请求仍然已经启动，顺序 await 不会倒过来限制其启动数量。

从 ReadableStream 读取时，锁和取消要分别处理

下面的包装器拥有传入流的读取锁。正常读到结束时释放锁；消费者提前退出或读取流程异常时，尝试取消后续读取，并在 finally 中释放锁。

JavaScript
async function* readChunks(stream) {
  const reader = stream.getReader();
  let completed = false;

  try {
    while (true) {
      const { done, value } = await reader.read();
      if (done) {
        completed = true;
        return;
      }
      yield value;
    }
  } finally {
    try {
      if (!completed) await reader.cancel();
    } finally {
      reader.releaseLock();
    }
  }
}

async function demonstrateStream() {
  const stream = new ReadableStream({
    start(controller) {
      controller.enqueue(new Uint8Array([1, 2]));
      controller.enqueue(new Uint8Array([3, 4]));
    },
    cancel() {
      console.log('数据源已取消');
    },
  });

  for await (const chunk of readChunks(stream)) {
    console.log([...chunk].join(',')); // 1,2
    break;
  }
  console.log(stream.locked); // false
}

demonstrateStream();
// 完整输出顺序：1,2 → 数据源已取消 → false

break 触发异步关闭，进入生成器 finally；循环等待这段清理结束后才继续，因此最后读取 stream.locked 为 false。

releaseLock 只是解除当前 reader 对流的占用，并不等于取消底层数据生产。这里显式调用 cancel，是因为包装器约定提前结束就不再需要后续数据。若调用者还希望把未消费部分交给其他 reader，就应选择不同的所有权和取消策略。

取消本身也可能失败，生产代码应决定如何记录清理错误，避免丢失主要错误上下文。内层 finally 确保即便取消 Promise 拒绝，也仍尝试释放锁。

背压不是只要写 for await 就自动完整实现

消费者一次请求一项，有助于表达按需获取，但生产者仍可能在内部预取多页、提前缓冲大量字节，甚至完全忽略需求不断推送。缓冲区大小、highWaterMark、拉取策略和外部服务行为，都会影响实际内存与吞吐。

示例中的流在 start 时就排入两块数据，说明队列中可以提前存在内容。网络流的一块字节也不保证恰好是一行文本、一个 JSON 对象或一条业务消息；解码和协议分帧仍需单独处理跨块边界。

消费者把所有结果 push 进数组，也会重新累积全部内存。若目标是流式处理，应尽可能及时处理或写出已经消费的数据，而不是最后才一次性汇总。

关闭迭代器不保证立即打断正在等待的 next

for await 的 break 要等执行进入循环体后才有机会发生。如果当前 next 一直等待底层请求，外部用户点击取消，不会自动使这段等待结束。async Generator 的 return 请求也可能排在尚未完成的操作之后，不能当成抢占式中断。

需要及时取消，应把 AbortSignal 或数据源自己的取消入口连接到那项等待，让它能够结束或拒绝。收到拒绝后再按生产者的 try/finally 收尾；服务端任务是否真的停止，又是另外的协议问题。

各条关闭路径的区别见《JavaScript 迭代器关闭和 return 方法有什么作用？》；生产者应对自己获取资源后的失败负责。

同步迭代器也能被消费，但适配细节有边界

for await...of 找不到 Symbol.asyncIterator 时，可以使用同步 Symbol.iterator 并进行异步适配。同步迭代器产出的 Promise 值会被等待，所以拿一个普通的 Promise 数组也能逐项得到兑现值。

这与“自定义异步迭代器的 value 无论嵌套多少层都自动解包”不是同一保证。自定义异步协议主要等待 next 返回的结果对象；应清楚定义 value 的类型，async Generator 的 yield 则有其等待语义。

同步生成器 yield 一个被拒绝的 Promise 时，关闭行为存在规范更新与运行时支持差异：当前 ECMAScript 异步适配算法安排在相关拒绝路径上关闭同步迭代器，但一些较旧实现可能没有执行同步生成器 finally。部分 Node.js 22 版本在这一场景下不会执行 finally，依赖该行为前应在目标运行时实测。

因此管理真实异步资源时，优先使用 async Generator 并在内部 await、try/finally 中明确处理失败，或对目标运行时单独验证清理路径，不要只看成功遍历例子就认定跨环境资源管理已经可靠。
