设计 token 为什么比散落的颜色变量更适合大型前端项目？

用主题按钮说明基础值、语义与组件映射，解释 token 和 CSS 自定义属性的关系、继承时的求值边界，以及怎样避免无意义的抽象层。

参考答案

简答

  • 设计 token 是设计决策的命名数据（颜色、间距、字号等），由同一份来源生成 CSS、iOS、Android 等多个平台的代码。
  • 常见分层：基础 token（blue-600）→ 语义 token（color-action-primary）→ 必要时的组件 token（button-bg）。
  • 组件引用语义 token，换主题时只改语义层的映射，组件代码不用动。
  • CSS 自定义属性是 token 在 Web 端最常见的输出形式，能在运行时切换主题。
  • 分层要有实际用途，不需要为每个组件都建一层 token。

散落的变量有什么问题

CSS
.button { background: #2563eb; }
.link   { color: #2563eb; }
.badge  { background: var(--blue); }

同一种"主操作色"出现了多种写法。要改品牌色或加深色模式时，只能全局搜索，还分不清哪些 #2563eb 是主操作色、哪些只是恰好相同的蓝色。

分层示例

CSS
:root {
  /* 基础 token：可用的原始值 */
  --blue-600: #2563eb;
  --blue-400: #60a5fa;
  --gray-50: #f9fafb;
  --gray-900: #111827;

  /* 语义 token：表达用途 */
  --color-action-primary: var(--blue-600);
  --color-surface: var(--gray-50);
  --color-text: var(--gray-900);
}

[data-theme='dark'] {
  --color-action-primary: var(--blue-400);
  --color-surface: var(--gray-900);
  --color-text: var(--gray-50);
}

.button {
  background: var(--color-action-primary);
  color: var(--color-surface);
}

深色主题只覆盖语义层，.button 不需要任何修改。

求值时机

自定义属性在使用它的元素上计算。上例中 --color-action-primary: var(--blue-600) 定义在 :root，子元素继承的是 :root 上已经算好的值。如果在某个子树里重新定义 --blue-600，子树中的 --color-action-primary 不会跟着变，因为它已在 :root 解析完毕。需要在局部换主题时，应在该元素上重新声明语义 token。

单一来源与生成

大型项目通常把 token 写在 JSON 中，由 Style Dictionary 等工具生成 CSS 变量、Sass 变量、TypeScript 常量和移动端资源。W3C 社区组 Design Tokens Community Group 在 2025 年 10 月发布了格式规范的首个稳定版，设计工具和代码工具可以用同一种格式交换 token。

避免过度抽象

  • 只有一个组件用到的值不必做成全局 token。
  • 组件 token 只在需要单独调整某个组件、又不影响其他组件时才加。
  • 名称描述用途（color-danger），不描述外观（color-red），否则换颜色时名字就错了。

常见追问

  • token 和 Tailwind 主题配置是什么关系？Tailwind 主题本身就是一套 token，可以由同一份来源生成。
  • 怎么防止开发者直接写颜色值？用 Stylelint 规则禁止在业务样式中出现硬编码颜色。
