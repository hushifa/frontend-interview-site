浏览器端 AI 为什么用了 WebGPU 或 Worker 仍可能卡顿？

总耗时包含模型下载、加载初始化、数据预处理、推理和结果后处理。首次运行与后续运行也可能不同。只看模型核心推理耗时，会漏掉下载、内存分配和 CPU/GPU 之间的数据复制成本。

参考答案

WebGPU 和 Worker 分别改变计算执行位置或组织方式，但用户等待的是完整任务：模型下载、初始化、预处理、推理、后处理和界面更新。只优化其中一段，其他部分仍可能让页面卡顿。

例如模型核心计算只需 30 毫秒，但每次输入都重新建立会话并复制几百 MB 数据，用户仍可能等待数秒。

先区分冷启动与热运行

第一次任务可能需要下载权重、编译或准备执行图、分配内存和初始化 GPU 管线。后续任务复用这些资源，速度会明显不同。

报告性能时至少分别记录首次可用时间、模型已就绪后的单次延迟和完整用户流程。不能只运行十次后挑最快结果，再把它叫作用户首次体验。

缓存命中也要说明条件：网络缓存、模型缓存、会话复用和运行时内部优化不是同一种缓存。用户换设备、清理存储或模型升级后，冷启动成本会重新出现。

Worker 优先改善主线程可响应性

把预处理和推理组织放到 Worker，可以减少主线程连续占用，让滚动与输入有机会及时处理。但线程启动、消息复制与结果传回仍有成本，总任务时间可能不变甚至略增。

大数组应评估 transferable 的所有权转移或其他合适共享方式，避免每次消息都复制完整数据。转移后发送方不能继续按原样使用同一块存储，不能为了少复制破坏数据生命周期。

如果每个请求都新建 Worker、加载同一模型，再处理一次输入就销毁，会丢掉复用收益。通常需要有上限的长期实例或队列，而不是无限并发创建。

GPU 只有在工作匹配时才有收益

模型算子支持、精度、形状、设备驱动和显存都会影响执行路径。部分算子落回 CPU、频繁 GPU 读回或小任务调度，可能抵消并行计算优势。

尽量保持能连续计算的数据在合适的设备侧，减少不必要往返。但这需要运行时与模型支持，不是把 Tensor 标成 GPU 就能自动省掉所有复制。

浏览器绘制与推理也可能争用 GPU。即使推理不在主线程，重负载仍可能影响动画、耗电和温度。低端设备上的持续运行表现，比短时间峰值吞吐更重要。

量化与模型缩小都要重新评估质量

量化可减少权重体积和部分内存需求，但速度取决于后端是否有高效支持。某种量化格式更小，不代表该设备推理一定更快。

准确率、生成质量和特殊输入表现也可能变化。应使用真实任务样本比较，而不是只看模型文件减少多少。可以采用小模型、短上下文或降低输入分辨率，但要说明对能力的影响。

生成模型的上下文越长，还可能增加预填充成本和 KV cache 占用；输出长度则影响持续解码时间。单看“每秒 Token”会漏掉首 Token 等待，反过来也不能只看首 Token 就忽略长回答总时间。

控制队列，避免旧任务挤占新输入

用户连续提交时，无上限并发可能导致内存峰值和设备争用。应限制并发、对过期任务取消或丢弃结果，并按模型运行时实际能力判断能否中止正在执行的计算。

取消前端 Promise 不保证 GPU 内核立即停止；如果运行时只能在阶段间检查信号，界面和队列设计应体现这个延迟。不要在用户每次输入一个字符时无节制启动完整推理。

复用会话也要配合资源释放。输出张量、图像、Worker 和 GPU 对象如果持续累积，会让越用越慢的问题被误认为模型本身变慢。

诊断时记录各阶段耗时、输入规模、设备与后端、内存峰值和主线程轨迹，结合运行时 profiling 查看真实瓶颈。比较同一设备和任务条件，确认优化没有以质量下降、流量增加或首次等待恶化为代价。
