浏览器端 AI 为什么用了 WebGPU 或 Worker 仍可能卡顿？

用户等的是下载、初始化、预处理、推理、后处理和渲染加在一起的时间。Worker 只是让主线程不卡，WebGPU 只加速它支持的运算；会话复用、数据拷贝、任务排队和量化同样影响体验。

参考答案

简答

因为用户等的不只是推理。从下载模型、初始化、预处理，到推理、后处理、渲染，每一段都要时间，瓶颈经常不在推理本身。所以第一步是分阶段计时。

Worker 解决的是主线程被堵住的问题，它不会让计算变快，消息传递和数据拷贝反而会多花一点时间。大数组可以用 Transferable 直接转交过去，避免复制。WebGPU 也只加速它支持的运算，碰到不支持的运算回退到 CPU、中间结果频繁从显卡读回来、任务太小，都可能让它比 WASM 还慢。

量化能把模型变小，但会不会变快，要看后端对这种精度支不支持，质量也可能下降，要拿真实样本验证。

用户连续输入时，只保留最新的任务，旧任务取消或丢弃，不然任务会排队、互相抢设备。

慢在哪里，先对照现象

现象常见原因
每次推理都慢每次都重新创建会话或 Worker
首次特别慢、之后正常权重下载和 GPU 着色器编译，属于冷启动成本
推理快但界面卡后处理或大量 DOM 更新在主线程
GPU 比 CPU 还慢算子回退、张量在 CPU 和 GPU 之间来回复制、批量太小
越用越慢张量、会话、图像对象没有释放

表里的“算子”指模型里的基本运算，比如矩阵乘法；“张量”是传给模型的多维数组。

如果是生成文字的模型，还要分开看两个指标。第一个字出来要多久，主要看输入有多长，因为模型要先把整段输入处理一遍，这一步叫预填充。总共要多久，还要看输出多长，因为后面是一个 token 一个 token 地生成，这一步叫解码。只看“每秒多少 token”，会忽略用户等第一个字的那段时间。

连续输入时只处理最新的任务

用户每敲一个字就推理一次，旧任务还没算完新任务就来了，结果一个个排队，越来越慢。下面的写法每来一个新任务就取消上一个：

JavaScript
let current = null;

async function inferLatest(input) {
  current?.abort();
  const controller = new AbortController();
  current = controller;

  try {
    const result = await inferenceWorker.run(input, controller.signal);
    return controller.signal.aborted ? null : result;
  } catch (error) {
    if (controller.signal.aborted) return null; // 被新任务取代，不算错误
    throw error;
  }
}

取消以后，计算会立刻停下来吗？通常不会。运行时一般只在阶段之间检查取消信号，已经交给 GPU 的计算会跑完。所以资源不会马上释放，但界面不用等它，返回 null 直接忽略就行。

Worker 传数据时要注意拷贝

postMessage 默认会把数据复制一份传给 Worker。图片像素这类大数组，复制一次就要不少时间。可以把它作为第二个参数传进去，直接转移所有权：

JavaScript
// 主线程：转移 ArrayBuffer 的所有权，避免复制
worker.postMessage({ pixels: buffer }, [buffer]);
// 之后 buffer.byteLength 变为 0，主线程不能再使用它

转移以后，主线程这边的 buffer 就空了，不能再用。

Worker 和模型会话都应该一直留着复用，不要用一次建一次。并发用一个有上限的队列来控制。

怎么确认优化真的有效

要在同一台设备、同样的缓存条件下，对比各阶段的耗时，同时记下内存峰值、主线程长任务和输出质量。拿高端台式机已经热起来的数据，去推断低端手机第一次打开的表现，结论通常不成立。

常见追问

SharedArrayBuffer 能用来共享张量吗？

可以，这样主线程和 Worker 能直接读写同一块内存，不用复制。但页面要开启跨源隔离，也就是配置 COOP 和 COEP 两个响应头，而且读写同步要自己处理。

GPU 能同时渲染页面和推理吗？

可以，但它们抢的是同一块显卡。推理负载高的时候，页面动画的帧率可能会下降。
