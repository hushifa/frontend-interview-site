浏览器端 AI 为什么用了 WebGPU 或 Worker 仍可能卡顿？

用户等待的是下载、初始化、预处理、推理、后处理和渲染的总和。Worker 只让主线程不被阻塞，WebGPU 只加速部分算子；会话复用、数据拷贝、任务队列和量化取舍同样决定体验。

参考答案

简答

  • 先分阶段计时：下载、初始化、预处理、推理、后处理、渲染。瓶颈常常不在推理本身。
  • Worker 解决的是主线程卡顿，消息传递和数据拷贝还会增加少量总耗时。大数组用 Transferable 转移所有权可以避免拷贝。
  • WebGPU 只加速它支持的算子。算子回退 CPU、中间结果频繁读回、任务太小，都可能让它比 WASM 还慢。
  • 量化缩小体积，但速度取决于后端是否高效支持该精度，还可能降低质量，要用真实样本验证。
  • 连续输入时只保留最新任务，过期任务取消或丢弃，避免排队和设备争用。

常见的慢在哪里

现象常见原因
每次推理都慢每次都重新创建会话或 Worker
首次特别慢、之后正常权重下载和 GPU 着色器编译，属于冷启动成本
推理快但界面卡后处理或大量 DOM 更新在主线程
GPU 比 CPU 还慢算子回退、张量在 CPU 和 GPU 之间来回复制、批量太小
越用越慢张量、会话、图像对象没有释放

生成模型还要分开看两个指标：首 token 时间主要由输入长度决定（预填充），总时间还取决于输出长度（逐 token 解码）。只看每秒 token 数会忽略首字等待。

只处理最新任务

JavaScript
let current = null;

async function inferLatest(input) {
  current?.abort();
  const controller = new AbortController();
  current = controller;

  try {
    const result = await inferenceWorker.run(input, controller.signal);
    return controller.signal.aborted ? null : result;
  } catch (error) {
    if (controller.signal.aborted) return null; // 被新任务取代，不算错误
    throw error;
  }
}

运行时通常只在阶段之间检查取消信号，已经提交给 GPU 的计算会跑完。所以取消后资源不会立刻释放，界面不必等待它。

Worker 与数据传递

JavaScript
// 主线程：转移 ArrayBuffer 的所有权，避免复制
worker.postMessage({ pixels: buffer }, [buffer]);
// 之后 buffer.byteLength 变为 0，主线程不能再使用它

Worker 和会话都应常驻复用，用有上限的队列控制并发。

验证优化是否有效

在同一台设备、同样的缓存条件下对比各阶段耗时，同时记录内存峰值、主线程长任务和输出质量。用高端桌面机的热启动数据去推断低端手机的冷启动表现，结论通常不成立。

常见追问

  • SharedArrayBuffer 能用来共享张量吗？ 可以，但页面要启用跨源隔离（COOP 和 COEP），并且自己处理读写同步。
  • 能不能让 GPU 同时渲染页面和推理？ 可以，但会争用同一块 GPU，推理负载高时动画帧率可能下降。
