浏览器端 AI 为什么用了 WebGPU 或 Worker 仍可能卡顿？

总耗时包含模型下载、加载初始化、数据预处理、推理和结果后处理。首次运行与后续运行也可能不同。只看模型核心推理耗时，会漏掉下载、内存分配和 CPU/GPU 之间的数据复制成本。

在“浏览器端 AI 为什么用了 WebGPU 或 Worker 仍可能卡顿？”这个问题中，先把消息、模型流、工具调用、审批和最终状态分开建模，再处理断线、取消和重试；模型输出和工具结果都必须当作不可信数据。这里的 WebGPU、Worker、量化 不是孤立的 API 名称，而是会共同影响输入、过程和最终结果。

AI 界面至少要区分用户消息、模型流、工具调用、工具结果、审批、取消、重试和最终状态。每一步都应有稳定 ID 和可恢复的状态，不能把网络片段直接拼成可信业务对象。

Worker 可以把部分重计算移出主线程，提高界面响应，但不保证模型本身算得更快。WebGPU 是否更合适也取决于模型与设备，部分算子和特性存在支持限制。ONNX Runtime Web 的 WASM 多线程还依赖跨源隔离等环境条件。

量化可以降低部分模型的体积和资源需求，但实际速度与质量应按任务验证。工程上应选择合适模型、控制会话生命周期，并衡量缓存和数据传输开销。监测首个可用结果、完整任务时长、内存及交互响应，不用单一跑分替代用户体验。

补充参考：Transformers.js · 官方说明。

模型输出、检索内容和工具结果都属于不可信输入。密钥、权限和不可逆操作必须留在受控边界，前端负责展示确认和错误恢复，服务端负责最终授权、校验和执行记录。

实际 AI 界面要把每次生成当成一个可追踪任务，而不是一段字符串。用户刷新、断网、取消或重新发送后，仍要能判断哪些内容已经保存、哪些工具已经执行、哪些结果只能作为候选信息展示。
