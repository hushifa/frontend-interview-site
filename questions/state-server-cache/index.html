为什么要用 TanStack Query 或 SWR 管理服务端状态？

服务端数据真正的来源在服务器，前端拿到的只是某一刻的缓存副本，会过期、会被别人改。TanStack Query 和 SWR 按 key 缓存请求结果，负责去重、过期判断、重新获取、重试和失效后刷新，组件只声明需要哪份数据。它们不适合存放纯客户端的界面状态。

参考答案

简答

服务端状态和界面状态不是一回事。弹窗开没开，只有前端知道；订单列表的数据，真正的版本在服务器上，前端拿到的只是某一刻的副本，可能已经过期了。所以要决定什么时候重新获取，修改以后哪些缓存要作废。

TanStack Query 和 SWR 都是按 key 缓存的。用同一个 key 的组件，共享同一份数据和同一个进行中的请求；key 变了，就自动请求新数据。

两者的默认行为不太一样。TanStack Query 默认 staleTime 是 0，数据一到手就算过期，组件挂载、窗口重新聚焦、网络恢复时会在后台重新获取；没有组件使用的缓存 5 分钟后回收；失败的查询默认重试 3 次。SWR 的思路是“先返回缓存，再重新验证”，窗口聚焦、网络恢复时可以重新验证，短时间内相同 key 的请求会去重；key 传 null 就不发请求，用来做条件请求。

要注意，修改数据以后要让相关缓存失效。TanStack Query 用 queryClient.invalidateQueries，SWR 用 mutate。

自己用 useEffect 请求有什么问题

用 useEffect 加 useState 请求数据，问题会一个个冒出来。每个组件各请求各的，好几处用同一个接口就重复请求。切换参数时，旧响应可能晚到，把新数据盖掉。回到页面时数据不会自动刷新。修改了数据，还得手动通知所有用到它的地方。

把这些逻辑搬进全局 store，也只是换了个地方写，问题一个没少。查询库就是把这些事统一做掉了。

TanStack Query 怎么用

JSX
import { keepPreviousData, useQuery, useMutation, useQueryClient } from '@tanstack/react-query';

function useTodos(filter) {
  return useQuery({
    queryKey: ['todos', filter],
    queryFn: ({ signal }) =>
      fetch(`/api/todos?filter=${encodeURIComponent(filter)}`, { signal }).then((res) => {
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        return res.json();
      }),
    staleTime: 30_000, // 30 秒内视为新鲜，不因挂载或聚焦重新请求
    placeholderData: keepPreviousData, // 切换 filter 时先显示上一份结果，避免闪回加载态
  });
}

function useAddTodo() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: async (todo) => {
      const res = await fetch('/api/todos', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(todo),
      });
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      return res.json();
    },
    // 前缀匹配：所有以 ['todos'] 开头的查询都会失效并重新获取
    onSuccess: () => queryClient.invalidateQueries({ queryKey: ['todos'] }),
  });
}

queryKey 里要包含 queryFn 用到的所有参数。这里 queryFn 用了 filter，key 里就要有 filter。漏了的话，参数变了 key 却没变，拿到的还是旧缓存。

为什么 queryFn 里要自己判断 res.ok 再抛错？因为 fetch 遇到 4xx、5xx 并不会 reject，只有网络错误才会。不抛错，查询库就以为请求成功了，既不会进入错误状态，也不会重试。

新增待办成功后，invalidateQueries 让所有以 ['todos'] 开头的查询失效，于是列表会重新获取。另外，返回的结果默认做结构共享：新数据和旧数据内容一样的部分，会保留原来的引用，组件就不会白白重新渲染。

一个查询要等另一个查询的结果时，用 enabled 控制什么时候执行：

JSX
const { data: user } = useQuery({ queryKey: ['user', email], queryFn: getUserByEmail });
const userId = user?.id;
const { data: projects } = useQuery({
  queryKey: ['projects', userId],
  queryFn: () => getProjectsByUser(userId),
  enabled: !!userId, // userId 就绪前不请求，状态为 pending、fetchStatus 为 idle
});

userId 还没拿到时，第二个查询不发请求，状态是 pending，fetchStatus 是 idle，意思是“还没数据，但也没在请求”。

前面用到的 placeholderData: keepPreviousData，作用是新 key 的数据到达之前，继续显示上一次成功的结果，而不是闪回加载状态。isPlaceholderData 可以告诉你当前显示的是不是占位数据。分页和筛选切换很适合这样用。

SWR 怎么用

JSX
import useSWR from 'swr';

const fetcher = async (url) => {
  const res = await fetch(url);
  if (!res.ok) throw new Error(`HTTP ${res.status}`); // 抛错后 SWR 才会进入 error 状态
  return res.json();
};

function Profile({ userId }) {
  // userId 为空时 key 为 null，不发请求
  const { data, error, isLoading, mutate } = useSWR(userId ? `/api/users/${userId}` : null, fetcher);
  // ...修改成功后调用 mutate() 重新验证这一个 key
}

fetcher 同样要自己抛错，道理和上面一样。userId 为空时 key 是 null，SWR 就不发请求。

useSWR 返回的 mutate 已经绑定了当前 key，调用它就重新验证这一份数据。要更新别的 key，用 useSWRConfig() 拿到全局的 mutate，再把 key 传进去。revalidateOnFocus、revalidateOnReconnect、dedupingInterval 这些选项控制重新验证和去重，默认值以 SWR 官方 API 文档为准。

和全局 store 怎么分工

服务端数据交给查询库。弹窗开关、表单草稿、主题这类只存在于客户端的状态，仍然放在组件状态或 store 里。怎么选 store，见《Zustand、Jotai 和 Redux Toolkit 应该怎样选择？》。

常见追问

staleTime 和 gcTime 有什么区别？

staleTime 决定数据多久之后算过期、需要重新获取；gcTime 决定没有组件使用的缓存，多久之后从内存里删掉。

乐观更新怎么做？

修改之前先把预期的结果写进缓存，失败了就回滚到之前的快照。不管成功还是失败，最后都让缓存失效，以服务器的数据为准。

快速切换参数，会不会出现旧响应覆盖新数据？

不会。查询库按 key 存放结果，旧 key 的响应写进旧 key 的缓存，不会显示到新 key 上。
