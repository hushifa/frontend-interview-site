前端故障注入应该怎样设计才有价值？

故障注入就是在测试里故意制造慢响应、错误状态码、网络中断、资源加载失败、存储不可用等情况，看页面能不能显示正确状态、允许重试并恢复。要先列出真实会发生的故障，再逐个注入并检查恢复结果。

参考答案

简答

故障注入就是在测试里故意把东西弄坏，看页面撑不撑得住。第一步是想清楚故障会出在哪一层：接口可能慢、返回 5xx 或 4xx、格式不对；网络可能断开或超时；静态资源，比如脚本和图片，可能 404；浏览器能力也可能不可用，比如存储满了、权限被拒。

Playwright 里用 page.route 延迟或修改响应，用 route.abort() 模拟请求失败，用 context.setOffline(true) 模拟断网。

验证时不能只看“出现了错误提示”，还要看用户能不能重试、填的内容有没有保留、会不会重复提交。前端还有一个特有的故障：发布新版本后，旧页面去加载的异步模块已经 404 了，页面要能提示用户刷新。

这些故障都只在测试环境里注入。在生产环境做混沌实验是另一回事，要严格限定范围，并且能随时停下来。

慢响应怎样测

TypeScript
test('慢请求显示加载状态，并能取消', async ({ page }) => {
  await page.route('**/api/report', async (route) => {
    await new Promise((resolve) => setTimeout(resolve, 3000));
    await route.fulfill({ json: { rows: [] } });
  });

  await page.goto('/report');
  await expect(page.getByRole('status')).toHaveText('加载中');
  await page.getByRole('button', { name: '取消' }).click();
  await expect(page.getByRole('status')).toHaveText('已取消');
});

处理器先等 3 秒再返回，测试就有时间检查“加载中”是否出现、取消按钮是否有效。如果接口在测试里总是瞬间返回，加载状态和取消功能就永远测不到。

接口返回了 200，却不是 JSON

TypeScript
await page.route('**/api/orders', (route) =>
  route.fulfill({ status: 200, contentType: 'text/html', body: '<html>网关错误</html>' }),
);

代理或 CDN 出问题时，接口可能返回状态码 200，内容却是一段 HTML 错误页。前端如果只看状态码，接着调用 response.json()，就会抛出解析错误：

JavaScript
const response = new Response('<html>网关错误</html>', { status: 200 });
try {
  await response.json();
} catch (error) {
  console.log(response.ok, error.name); // true SyntaxError
}

ok 是 true，解析却失败了。如果代码没有捕获这个错误，页面可能直接白屏。所以这种情况要单独注入一次，确认页面能给出提示。

新版本发布后旧页面加载不到分块

TypeScript
await page.route('**/assets/*.js', (route) => {
  if (route.request().url().includes('Settings')) return route.abort();
  return route.continue();
});
await page.goto('/');
await page.getByRole('link', { name: '设置' }).click();
await expect(page.getByText('页面已更新，请刷新')).toBeVisible();

这个测试模拟的是：部署新版本时旧版本的分块文件被删了，用户还停在旧页面上，点“设置”时懒加载路由失败。期望的结果是页面提示用户刷新，而不是什么反应都没有。

浏览器存储不可用

TypeScript
await page.addInitScript(() => {
  Storage.prototype.setItem = () => {
    throw new DOMException('quota exceeded', 'QuotaExceededError');
  };
});

addInitScript 会在页面脚本运行之前执行，这里把 setItem 换成一个总是抛错的函数。localStorage 写满了或者在隐私模式下不可用时，草稿保存这类功能应该提示用户，而不是让整个页面报错。

注入以后要检查什么

每个故障用例都要回答三个问题：

  • 用户看到了什么提示，有没有说清楚下一步该怎么做？
  • 故障消除以后，比如第二次请求成功了，页面有没有回到正常状态？
  • 有没有留下重复的数据、一直转圈的加载状态或者错误的缓存？

接口模拟的基本用法见《Playwright 接口模拟怎样覆盖成功和失败场景？》。

常见追问

这和单元测试里模拟 fetch 失败有什么区别？

单元测试验证的是某个函数的错误处理。在浏览器里注入故障，还能发现加载状态、焦点、整页渲染和缓存层这些单元测试看不到的问题。
