前端故障注入应该怎样设计才有价值？

故障注入是在测试中故意制造慢响应、错误状态码、网络中断、资源加载失败、存储不可用等情况，验证页面能显示正确状态、允许重试并恢复；要先列出真实会发生的故障，再逐个注入并检查恢复结果。

参考答案

简答

  • 先确定故障发生在哪一层：接口（慢、5xx、4xx、格式错误）、网络（断开、超时）、静态资源（脚本、图片 404）、浏览器能力（存储已满、权限被拒）。
  • 用 page.route 延迟或修改响应，route.abort() 模拟网络失败，context.setOffline(true) 模拟断网。
  • 验证的不只是“出现错误提示”，还要检查用户能否重试、输入是否保留、重复提交是否被阻止。
  • 发布新版本后旧页面请求的异步模块可能 404，这是前端特有的故障，要测试页面能提示刷新。
  • 故障注入只在测试环境进行，生产环境做混沌实验需要严格的范围控制和随时停止的能力。

慢响应

TypeScript
test('慢请求显示加载状态，并能取消', async ({ page }) => {
  await page.route('**/api/report', async (route) => {
    await new Promise((resolve) => setTimeout(resolve, 3000));
    await route.fulfill({ json: { rows: [] } });
  });

  await page.goto('/report');
  await expect(page.getByRole('status')).toHaveText('加载中');
  await page.getByRole('button', { name: '取消' }).click();
  await expect(page.getByRole('status')).toHaveText('已取消');
});

错误格式不符合预期

TypeScript
await page.route('**/api/orders', (route) =>
  route.fulfill({ status: 200, contentType: 'text/html', body: '<html>网关错误</html>' }),
);

代理或 CDN 出问题时，接口可能返回 200 和一段 HTML。前端直接 response.json() 会抛出解析错误，页面要能处理这种情况，而不是白屏。

资源加载失败

TypeScript
await page.route('**/assets/*.js', (route) => {
  if (route.request().url().includes('Settings')) return route.abort();
  return route.continue();
});
await page.goto('/');
await page.getByRole('link', { name: '设置' }).click();
await expect(page.getByText('页面已更新，请刷新')).toBeVisible();

模拟部署后旧版本的分块文件已被删除，懒加载路由失败的情况。

浏览器能力

TypeScript
await page.addInitScript(() => {
  Storage.prototype.setItem = () => {
    throw new DOMException('quota exceeded', 'QuotaExceededError');
  };
});

localStorage 写满或在隐私模式下不可用时，草稿保存功能应提示用户而不是让整个页面报错。

检查恢复

每个故障用例都要回答：

  • 用户看到了什么提示，是否说明了下一步怎么做？
  • 故障消除后（例如第二次请求成功），页面是否回到正常状态？
  • 有没有留下重复的数据、残留的加载状态或错误的缓存？

接口模拟的基本用法见《Playwright 接口模拟怎样覆盖成功和失败场景？》。

本题的故障都在测试环境里注入。在生产环境做混沌实验是另一类工作，要限定影响的用户比例和时间窗口，并能随时停止。

常见追问

  • 和单元测试里模拟 fetch 失败有什么区别？单元测试验证某个函数的错误处理；浏览器里的故障注入还能发现加载状态、焦点、整页渲染和缓存层的问题。
