Playwright 视觉回归的差异阈值和基线怎样维护？

通过稳定环境、截图范围和差异阈值捕获视觉回归，同时避免把字体和动画波动当成真实缺陷。

参考答案

视觉测试失败后，最重要的问题是“差异为什么出现”，而不是“怎样让 CI 变绿”。基线代表团队确认过的外观预期；把每次新截图自动覆盖进去，会让视觉回归失去判断标准。

在环境和数据已经稳定的前提下，再讨论阈值、差异分析与基线更新，才能避免把真实问题当作噪声消掉。

三种阈值不是同一个参数

Playwright 的截图断言可以使用如下选项，具体数字应根据被测范围与真实噪声选择：

TypeScript
await expect(page.getByTestId('summary-card')).toHaveScreenshot('summary-card.png', {
  threshold: 0.15,
  maxDiffPixels: 20,
});

threshold 控制对应像素间允许的感知颜色差异，在比较阶段决定哪些像素算不同；maxDiffPixels 控制允许不同的像素数量；maxDiffPixelRatio 则以整张图片的比例表达数量容忍。

threshold 为 0.15 不表示允许 15% 像素错误。一个很大的全页截图即使只允许很小比例，也可能容忍局部按钮消失涉及的大量像素。因此应结合截图面积和关键区域，而不是复制一个统一的大阈值到所有场景。

如果字体整体变化产生大片差异，先检查字体和运行环境。靠放宽阈值掩盖它，可能同时放过文字截断与位置错误。

失败时一起看三张图

基线图描述预期，实际图描述当前渲染，差异图突出变化位置。三者结合才能看出是整个页面偏移、某个元素变化还是局部抗锯齿噪声。

例如差异图显示后半页全部偏移，根因可能是顶部某段文字多换了一行；不能把每个受影响组件都当成独立失败。若只有数字不同，则检查时间和数据是否固定。若出现整片空白，先排查资源加载与错误状态，而不是批准新图。

还应查看对应的 trace、控制台和业务断言。截图测试的失败可能源于页面根本没准备好，这时更新像素基线解决不了问题。

基线更新是一项需要说明的代码变化

确认 UI 改版符合预期后，可以按测试工具提供的更新方式生成新图，再把基线差异作为评审内容。评审应说明修改了哪些状态、视口和主题，而不是只提交一批难以追溯的 PNG。

应尽量只更新本次明确变更的用例，不要把其他失败一起批量接受。第一次生成基线同样需要检查，因为工具只能记录当前外观，不知道设计是否正确。

不同浏览器项目和平台要有明确的基线归属。浏览器或字体升级导致大量合理变化时，可以单独安排一次受控更新，避免与业务改版混在一起难以审查。

覆盖状态比堆截图数量更重要

一个日期选择器可以按关闭、打开、选择完成和错误状态建立少量关键基线，再覆盖最容易出问题的窄屏或长文案。并不需要机械穷举所有日期与所有像素尺寸。

暗色主题、RTL、文本放大等是否进入矩阵，应由产品支持范围和风险决定。截图太多但没有明确目标，会增加维护噪声；只截图默认空页面，又可能完全漏掉真实交互状态。

截图名应反映场景，fixture 数据应可复现。删除功能时清理相应旧基线，避免仓库保留没人再运行的“历史正确答案”。

对噪声的修复也要验证没有掩盖回归

使用 mask、注入测试样式或阈值调整后，检查关键区域是否仍然受测。可以有意识地制造一个小的布局错误，确认断言能失败，再撤销验证改动。

不要把测试环境专用 CSS 改得与生产布局完全不同，否则得到的稳定截图可能已经不是用户看到的页面。必要的稳定化应尽量局部，并记录它排除了什么。

可靠的视觉测试既能发现应发现的变化，也不会要求人每天批准大量无关差异。稳定输入、明确场景、合理阈值与认真审核缺一不可。
