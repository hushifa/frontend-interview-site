CORS 携带凭据时有哪些限制？

跨源请求要带 Cookie，前端需设 credentials 为 include，服务端必须返回具体的 Access-Control-Allow-Origin（不能是 *）和值为 true 的 Access-Control-Allow-Credentials。即使 CORS 通过，Cookie 也可能因 SameSite 或第三方 Cookie 策略不被发送。

参考答案

简答

  • fetch 默认 credentials: 'same-origin'，跨源时要显式设为 'include'；XMLHttpRequest 用 withCredentials = true。
  • 携带凭据时，Access-Control-Allow-Origin、Allow-Headers、Allow-Methods、Expose-Headers 都不能用 *，必须写具体值。
  • 服务端还要返回 Access-Control-Allow-Credentials: true，按白名单回显 Origin 并加 Vary: Origin。
  • 凭据本身不触发预检，是否预检仍看方法、请求头和 Content-Type。
  • CORS 只决定能否读取响应；Cookie 能否发出取决于 SameSite、Secure 和浏览器对第三方 Cookie 的策略。

示例

JavaScript
const response = await fetch('https://api.example.com/profile', {
  credentials: 'include',
});
http
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
Vary: Origin

有预检时，预检响应同样要带这两个头：

http
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: PUT
Access-Control-Allow-Headers: content-type, x-csrf-token

Cookie 为什么还是没带上

原因说明
SameSiteapp.example.com 调 api.example.com 是同站，Lax 可以带；调 api.other.com 是跨站，需要 SameSite=None; Secure
第三方 Cookie 被浏览器限制跨站时 Safari 默认阻止，Firefox 按顶层站点分区，Chrome 用户可能手动屏蔽
Cookie 的 Domain、Path 不匹配检查 Application 面板中 Cookie 的属性
非 HTTPSSecure Cookie 只在 HTTPS 发送

最稳妥的做法是让 API 和页面同站（例如都在 example.com 下），或者通过同源的反向代理访问 API。

安全风险

  • 不加白名单、直接回显任意 Origin 并允许凭据，等于让任何网站都能以用户身份读取接口数据。
  • 白名单用完整的源精确匹配，不要用 endsWith('example.com')，evilexample.com 也能匹配。
  • Origin: null 可能来自沙箱 iframe 或本地文件，不要放进白名单。
  • CORS 通过不等于请求合法，修改操作还需要 CSRF 防护和服务端鉴权。

常见追问

  • 为什么预检请求不带 Cookie？规范规定预检请求永远不带凭据，所以预检接口不能要求登录。
  • 用 Authorization 头代替 Cookie 呢？它是标准请求头，但不在 CORS 安全列表中，会触发预检，需要在 Allow-Headers 中列出，不受 SameSite 影响。
