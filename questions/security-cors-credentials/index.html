CORS 携带凭据时有哪些限制？

说明 credentials、Access-Control-Allow-Origin、预检和 Cookie 属性之间的关系，避免把 CORS 当成服务端鉴权。

参考答案

跨源请求是否能被 JavaScript 读取，由服务端 CORS 响应头决定。请求携带凭据时，服务端不能把 Access-Control-Allow-Origin 设为 *，必须返回明确的源，并设置 Access-Control-Allow-Credentials: true；客户端也要显式使用 credentials: 'include' 或对应配置。

在“CORS 携带凭据时有哪些限制？”这个问题中，先画出用户输入、第三方内容、接口响应和权限边界，再决定编码、校验和授权放在哪里；客户端检查不能代替服务端约束。这里的 CORS、Cookie、跨域 不是孤立的 API 名称，而是会共同影响输入、过程和最终结果。

安全问题先画出数据流和信任边界：哪些值来自用户、第三方页面、接口响应或浏览器存储，哪些代码拥有真正的权限。防护措施应放在能控制风险的边界上，客户端校验主要用于改善体验，不能代替服务端校验和授权。

预检请求会先询问方法、请求头和凭据策略，服务端必须正确响应允许的源、方法和请求头。CORS 只控制浏览器脚本读取响应，不能替代服务端身份认证、CSRF 防护或资源权限检查。

Cookie 还受 SameSite、Secure、第三方 Cookie 策略和域名范围影响。调试时要分别查看预检、实际请求、响应头和浏览器 Cookie 决策，不能只看到服务端返回 200 就认为跨域成功。

验证修复时要覆盖正常流程、攻击输入、错误提示和日志脱敏。安全配置还会受到部署代理、响应头、Cookie 属性和跨域策略影响，不能只在组件代码里判断“已经安全”。

实际落地时，攻击输入往往会经过多个层：URL、表单、接口响应、富文本和第三方窗口。每一层都应明确编码、解析和授权责任，不能因为上游做过一次校验就把数据标记为可信。
