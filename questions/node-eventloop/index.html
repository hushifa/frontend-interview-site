Node.js 事件循环和浏览器有什么不同？nextTick 一定先于 Promise 吗？

Node.js 由 libuv 驱动按阶段运行的事件循环，timers、poll、check 等阶段轮流执行，每个回调之后先清空 nextTick 队列再清空微任务队列。nextTick 与 Promise 的先后取决于当前代码是否已在微任务中运行，CommonJS 与 ES 模块入口的结果不同。

参考答案

简答

浏览器的事件循环要兼顾页面渲染，Node.js 不用渲染，它的事件循环由 libuv 实现，按几个固定的阶段一圈圈转：timers 跑到期的定时器，poll 处理 I/O，check 跑 setImmediate，还有 pending callbacks 和 close callbacks。

在这些阶段之外，还有两个队列：process.nextTick 队列和 Promise 的微任务队列。每执行完一个回调，Node.js 先清空 nextTick 队列，再清空微任务队列。

所以 nextTick 一般先于 Promise，但不是一定。在 CommonJS 文件里，顶层的 nextTick 先执行；在 ES 模块里，模块本身就是在微任务里执行的，顶层的 Promise 回调反而先于 nextTick。

还有一个常考点：在主模块里，setTimeout(fn, 0) 和 setImmediate 谁先执行是不确定的；但在 I/O 回调里，setImmediate 一定先执行。

事件循环分哪几个阶段

Node.js 的事件循环每一圈按顺序经过下面几个阶段，每个阶段处理自己那一类回调：

阶段运行的回调
timers到期的 setTimeout、setInterval
pending callbacks上一轮推迟的部分系统级回调
poll取回新的 I/O 事件并执行对应回调；没有其他工作时在这里等待
checksetImmediate
close callbacks例如 socket 的 close 事件

nextTick 队列和微任务队列不属于任何阶段。Node.js 每执行完一个回调就清空它们一次。所以如果在 nextTick 回调里不停地再调用 process.nextTick，事件循环就一直停在原地，进不了下一个阶段，I/O 回调永远得不到执行。

同样的代码，为什么 .cjs 和 .mjs 输出不一样

下面四行代码，分别存成 .cjs 和 .mjs 运行：

JavaScript
process.nextTick(() => console.log('nextTick'));
Promise.resolve().then(() => console.log('promise'));
setTimeout(() => console.log('timeout'));
setImmediate(() => console.log('immediate'));

在 Node.js 22 上的输出：

text
// a.cjs
nextTick
promise
timeout
immediate

// a.mjs
promise
nextTick
timeout
immediate

前两行的顺序反过来了。这是为什么？

CommonJS 的模块体就是一段普通的同步代码。它执行完以后，Node.js 按规矩先清空 nextTick 队列，再清空微任务队列，所以 nextTick 在前。

ES 模块不一样，它的求值本身就发生在一个 Promise 任务里。模块体执行完的时候，Node.js 正处在清空微任务队列的过程中，同一轮排进去的 Promise 回调会接着执行。nextTick 只能等这一轮微任务清空之后才轮到。

这个差异说明，业务逻辑不应该依赖 nextTick 和 Promise 谁先谁后。如果只是想“等当前操作结束再执行”，优先用 queueMicrotask，它在浏览器和 Node.js 里语义一致。

setTimeout 和 setImmediate 谁先执行

在主模块里，setTimeout(fn, 0) 实际上按 1 毫秒处理。事件循环进入 timers 阶段时，如果这 1 毫秒还没到，就先跳过，跑到 check 阶段执行 setImmediate。所以两者的先后取决于进程启动有多快。上面的例子在本机多次运行都是 timeout 在前，但这个顺序没有保证。

换到 I/O 回调里，结果就确定了：

JavaScript
const fs = require('node:fs');

fs.readFile(__filename, () => {
  setTimeout(() => console.log('timeout'));
  setImmediate(() => console.log('immediate'));
});
// immediate
// timeout

原因是 I/O 回调运行在 poll 阶段，poll 后面紧跟着就是 check 阶段，所以 setImmediate 一定先执行。setTimeout 要等转到下一圈的 timers 阶段。

常见追问

为什么不要用大量 nextTick 递归？

因为 nextTick 队列在进入下一个阶段之前会一直执行到空。递归添加的话队列永远空不了，所有 I/O 都会被卡住。

CPU 密集任务放在 setImmediate 里分片可以吗？

可以让出事件循环，让别的回调有机会执行，但总耗时并没有减少。长时间的计算更适合交给 Worker Threads，见《Node.js Worker Threads 适合解决什么问题？》。

浏览器里有 nextTick 吗？

没有。浏览器只有微任务和任务，渲染时机由浏览器自己决定。
