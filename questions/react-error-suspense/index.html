Error Boundary 和 Suspense 分别处理什么？

Error Boundary 为后代的相关错误提供恢复界面，Suspense 为支持其协议的等待提供加载回退。失败、等待和空数据是不同状态，边界范围、重试条件及服务端行为都需要明确设计。

参考答案

一个区域正在等待模块加载，和它已经抛出错误，应该给用户不同反馈。Suspense 处理支持其机制的等待，Error Boundary 处理 React 相应流程中的错误；没有记录则通常是一个正常业务状态，不应该自动变成这两者中的任何一种。

它们都可以提供 fallback，但触发原因和恢复方式不同。

Error Boundary 捕获后代错误并替换这部分界面

JSX
import { Component, Suspense, lazy, useState } from 'react';

class ErrorBoundary extends Component {
  state = { failed: false };

  static getDerivedStateFromError() {
    return { failed: true };
  }

  componentDidCatch(error) {
    console.error('内容渲染失败：', error);
  }

  render() {
    if (this.state.failed) {
      return (
        <section role="alert">
          <p>这部分内容暂时无法显示。</p>
          <button type="button" onClick={this.props.onRetry}>重试</button>
        </section>
      );
    }
    return this.props.children;
  }
}

function Content({ broken }) {
  if (broken) throw new Error('演示渲染错误');
  return <p>内容正常显示</p>;
}

export default function ErrorDemo() {
  const [broken, setBroken] = useState(false);
  const [attempt, setAttempt] = useState(0);

  function retry() {
    setBroken(false);
    setAttempt(value => value + 1);
  }

  return (
    <section>
      <button type="button" onClick={() => setBroken(true)}>触发渲染错误</button>
      <ErrorBoundary key={attempt} onRetry={retry}>
        <Content broken={broken} />
      </ErrorBoundary>
    </section>
  );
}

点击按钮只是更新 broken，真正的异常在下一次 Content 渲染时抛出，边界因此显示自己的回退。getDerivedStateFromError 负责决定回退状态，componentDidCatch 可以记录诊断信息。

这里重试先把错误原因修正为 false，再更换边界身份使其重建。如果只清空边界状态，却继续传入必然抛错的 broken=true，下一次仍然会失败。

实际项目不必都通过 key 重置，也可以使用库提供的 reset 机制或自行设计状态恢复，但都需要明确是否清理旧子树、如何处理用户未保存内容。

哪些错误不会被普通边界自动接住

边界可以处理后代渲染及 React 管理的相关生命周期错误，但不负责捕获任意普通事件处理器或独立 setTimeout 回调里的异常，也不能捕获它自己的回退界面内部再发生的错误。

事件提交、普通 Promise 和计时器工作仍需在对应调用边界处理。现代 React 的 Action、useTransition 中的相应错误或 useActionState 抛错可以按其专门路径进入 Error Boundary，所以也不能反过来概括成“所有异步错误都绝不会到边界”。

判断时应看任务有没有连接到 React 支持的错误流程，而不是只看函数前面有没有 async。意外的代码错误与可预期的字段校验失败，也应使用不同的产品反馈。

Suspense 不会自动观察所有请求

下面沿用前面的导入，用本地延迟模拟 lazy 模块变得可用，便于观察加载回退：

JSX
const DelayedPanel = lazy(() => new Promise(resolve => {
  setTimeout(() => {
    resolve({ default: function Panel() { return <p>面板已就绪</p>; } });
  }, 300);
}));

export function LoadingDemo() {
  return (
    <Suspense fallback={<p role="status">正在准备面板</p>}>
      <DelayedPanel />
    </Suspense>
  );
}

lazy 等待一个带有 default 组件的模块结果，未就绪时由附近的 Suspense 显示 fallback。真实的代码分割常采用动态 import，而不是本例中的模拟模块对象。

模块就绪后 React 再尝试渲染内容。lazy 声明应保持在合适的模块级等稳定位置，不要每次父组件渲染都重新创建一个新的 lazy 组件身份。

普通 useEffect 中启动的 fetch 不会因为外面包了 Suspense，就自动让边界显示加载状态。Effect 在提交之后执行，普通请求没有参与渲染阶段的等待协议。应使用框架集成、lazy、use 读取合适资源等支持方式，而不是随意把所有 Promise 当成同一种机制。

加载失败通常需要两个边界协作

模块或支持的资源等待期间使用 Suspense；最终失败时，需要相应 Error Boundary 告诉用户这部分内容出了问题。可以在一个可独立理解的区域外放错误边界，再在内部安排加载边界。

只放 Suspense，不能保证所有错误都显示成它的 loading；只放 Error Boundary，也不会自然替你设计等待中的界面。

lazy 会缓存相应加载过程与结果，加载失败后仅仅重新渲染或改一个外部 key，不一定重新发起模块加载。重试可能需要框架支持、重新建立合适资源或刷新页面，必须结合失败原因设计，不能给一个实际上无效的按钮随便写上“重试”。

边界范围应该与用户理解的内容区域对应

把整页都包在一个大加载边界里，一个小图表等待也可能替换整页；把每个小文本都拆成独立边界，又可能出现大量零碎占位和跳动。

通常按用户可以独立阅读、独立失败或独立等待的区域组织，例如主内容、侧栏推荐或独立面板。错误边界也应让未失败区域尽量继续工作，并提供回到安全位置的入口。

如果已经显示的内容在更新时再次等待，Transition 或延迟值在适用条件下可以帮助保留旧内容，而不是立即切回 fallback。但首次显示、新边界身份和其他情形仍有不同规则，应明确“旧内容正在更新”的状态。

服务端流程不是普通客户端边界的直接复制

经典的客户端 Error Boundary 并不在服务端渲染时以同样方式捕获并恢复所有错误。流式服务端渲染和框架可以借助 Suspense 的回退、客户端重试等机制处理部分服务端失败，但需要遵循具体渲染协议。

不能只在浏览器里验证一个错误按钮，就认定服务器首屏失败、hydration 或资源缓存失效都已经处理。相反，服务端曾使用某个加载回退，也不必然意味着客户端最终无法成功显示内容。

回退界面本身也需要可用

加载提示应说明当前在等什么，错误提示应提供可执行的下一步，普通空结果则应说明确实没有内容。必要时处理焦点、读屏提示与恢复后的上下文，而不只是把整个区域替换成一行技术堆栈。

日志需要保留版本与操作上下文，但不要直接向用户展示内部敏感数据。边界的价值是限制失败影响并支持恢复，不是把异常静默吞掉，让页面表面上没有白屏却失去真实功能。
