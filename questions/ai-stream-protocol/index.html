AI 流式响应为什么不能每收到一块就 JSON.parse？

网络读取的 chunk 是字节分块，不保证对应一个字符、一条 SSE 事件或一个完整 JSON。一个消息可能跨多个块，一块也可能包含多个事件。需要按字符编码和协议边界增量解析，不能把 reader.read 的每个 value 直接当…

参考答案

网络 chunk 是传输与缓冲形成的字节块，不是模型的一次 token，也不是一条业务事件。服务端一次写出完整 JSON，浏览器仍可能分几次读到；多次服务端写入也可能合并在一个读取结果中。

因此直接对每个 reader.read 的 value 解码后 JSON.parse，会在半个字符、半条消息或多条消息粘连时失败。

至少有三层边界

第一层是字节到字符。中文或 emoji 的 UTF-8 编码可能跨块，需要 TextDecoder 的流模式或 TextDecoderStream 保留未完成字符。

第二层是传输协议。SSE 用行与空行组织字段和事件，支持 LF、CRLF 等换行方式；多个 data 行需要按规则合并，注释、id 和 retry 也有各自含义。简单 split('\n\n') 无法完整覆盖它。

第三层才是业务 payload。只有取得一条完整 SSE 事件的数据后，才能按约定解析 JSON 并验证事件类型与字段。SSE data 本身不保证是 JSON，某些服务的结束标记也不是标准 JSON。

让成熟解析器处理 SSE framing

下面使用 eventsource-parser，示例协议约定每个带 data 的事件都包含一个 JSON 值。它只负责传输解码与分帧，业务 schema 校验留给 onEvent：

JavaScript
import { createParser } from 'eventsource-parser';

async function consumeJsonSse(response, onEvent) {
  if (!response.ok || !response.body) throw new Error('流式响应不可用');
  const reader = response.body.getReader();
  const decoder = new TextDecoder('utf-8', { fatal: true });
  let receivedBytes = 0;
  let completed = false;
  const parser = createParser({
    onEvent(event) {
      onEvent({ id: event.id, event: event.event, data: JSON.parse(event.data) });
    },
  });

  try {
    while (true) {
      const { value, done } = await reader.read();
      if (done) {
        parser.feed(decoder.decode());
        completed = true;
        break;
      }
      receivedBytes += value.byteLength;
      if (receivedBytes > 2 * 1024 * 1024) throw new Error('示例流超过 2 MiB 上限');
      parser.feed(decoder.decode(value, { stream: true }));
    }
  } finally {
    try {
      if (!completed) await reader.cancel();
    } finally {
      parser.reset();
      reader.releaseLock();
    }
  }
}

onEvent 在这个例子中约定同步处理，不应启动无限个未等待的异步任务。需要耗时处理时，应建立有界队列与消费机制。2 MiB 是示例的整条响应上限，不是通用模型响应限制，也不等于所有内存占用上限。

解析器只在完整事件边界交付数据。连接突然结束时，半条事件不应被“猜着补齐”后当成成功结果。还需要业务终止事件来判断回答是否真正完成，EOF 本身不证明正常结束。

如果实际服务使用 [DONE] 或其他非 JSON 约定，应在业务适配层识别，不要把例子的 JSON.parse 原样套上去。使用 AI SDK 的 UI 消息协议时，优先使用匹配版本的 SDK 解码与 transport，不能混用不同供应商的事件格式。

文本、工具与引用应该走不同状态更新

一条流可能包含文本 delta、工具参数增量、执行结果、引用、错误和结束信息。收到工具事件时不能把整个 JSON 字符串追加进回答正文；收到错误后也不能继续标记为完整成功。

建议用消息 ID、part ID 和必要的序号定位更新目标。不同 part 的增量分别累积，完成后再冻结或转为可持久化结构。工具参数还没接收完整时，不应因为局部 JSON 看起来可解析就提前执行。

EventSource 与 fetch 流并非任意互换

原生 EventSource 适合它支持的 SSE 连接方式，并具有相应重连机制；fetch 可以支持自定义方法、请求体和头，但读取流时要自己管理解析、取消与恢复。使用 fetch 实现 SSE，不会自动继承 EventSource 的所有行为。

即使事件有 id，也不意味着服务器保留了可恢复历史。要续传，必须约定恢复位置、保留期限、去重和任务身份。断线后重新发起生成，可能得到另一份回答，不能伪装成原流无缝继续。

测试应把同一段协议字节在任意位置切开，覆盖多字节字符、CRLF、多行 data、多个事件同块和尾部截断。只用服务端恰好一写一读的演示，最容易漏掉真实网络边界问题。
