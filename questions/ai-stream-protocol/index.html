AI 流式响应为什么不能每收到一块就 JSON.parse？

reader.read 拿到的是网络随便切开的字节块，一块不一定是一个完整字符、一条事件或一段完整 JSON。要先按流解码成文字，再按 SSE 规则切成事件，最后才解析和校验每个事件。

参考答案

简答

因为网络切块的位置是随机的。一条事件可能被拆成好几块，好几条事件也可能挤在一块里，连一个中文字或 emoji 都可能被拆在两块之间。拿一块去 JSON.parse，经常是半截 JSON，直接报错。

正确的做法分三层：先把字节解码成文字，用 TextDecoder 并加上 stream: true；再按 SSE 的规则把文字切成一条条事件；最后把每条事件的 data 解析成 JSON。

切事件这一步，不要只用 split('\n\n')。SSE 支持 LF 和 CRLF 两种换行、一条事件多行 data、还有注释行，用成熟的解析器更可靠。

还要注意，连接结束不等于生成完成。要以协议里的结束事件为准，没收到结束事件就当作被截断了。

为什么一块不对应一个字

网络传输的是字节，常用汉字在 UTF-8 里占 3 个字节，常见的 emoji 占 4 个。网络完全可能在一个字的中间切开，比如前 2 个字节在这一块，最后 1 个在下一块。

如果每块单独解码，半个字会变成乱码。TextDecoder 加上 { stream: true } 以后，它会把不完整的字节先留着，等下一块来了拼上再输出。

一个可用的读取函数

下面用 eventsource-parser 4.x 的 createParser({ onEvent }) 来切分 SSE 事件。这个例子约定服务端最后发一个 [DONE] 表示结束。这只是本例的约定，不同服务商的结束方式不一样。

JavaScript
import { createParser } from 'eventsource-parser';

async function consume(response, onEvent) {
  if (!response.ok || !response.body) throw new Error('流不可用');
  const reader = response.body.getReader();
  const decoder = new TextDecoder('utf-8', { fatal: true });
  let completed = false;

  const parser = createParser({
    onEvent(event) {
      if (completed) return;
      if (event.data === '[DONE]') {
        completed = true;
        onEvent({ type: 'done' });
        return;
      }
      onEvent({ id: event.id, event: event.event, value: JSON.parse(event.data) });
    },
  });

  try {
    while (!completed) {
      const { value, done } = await reader.read();
      if (done) {
        parser.feed(decoder.decode()); // 冲刷解码器里剩余的字节
        if (!completed) throw new Error('连接结束但没有收到结束标记');
        break;
      }
      parser.feed(decoder.decode(value, { stream: true }));
    }
    await reader.cancel(); // 收到结束标记后丢弃剩余字节
  } catch (error) {
    await reader.cancel(error).catch(() => {});
    throw error;
  } finally {
    reader.releaseLock();
  }
}

parser.feed 可以接收任意长度的文字，它会自己攒着，攒够一条完整事件才调用 onEvent。所以 JSON.parse 拿到的一定是一条完整事件的 data。

读到 done 时还调了一次不带参数的 decoder.decode()，这是为了把解码器里剩下的字节吐出来。之后如果还没收到 [DONE]，说明连接是中途断掉的，要当成错误。

出错时调用的是 reader.cancel()，它会关闭底层的流。finally 里的 releaseLock() 只是解除读取器和流的绑定，不会关闭连接，两者不能互相替代。

生产环境还要限制单条事件和总字节数，防止异常的流把内存吃光。

不同类型的事件怎么累积

一条 AI 流里通常混着文字增量、工具调用参数、引用、错误和结束事件，要分开处理。

文字增量按消息 ID 和片段 ID 追加。工具参数按调用 ID 累积，要等参数完整、并且通过 Schema 校验以后才能执行。半截 JSON 就算碰巧能解析，也不算完成，比如 {"count": 1 后面可能还有 0}。错误事件一到，这次生成就标成失败，后面不再追加文字。

用 AI SDK 这类库时，解码器要和服务端的协议版本对上，不要混用不同服务商的事件格式。

怎么测试

把同一段流在任意字节位置切开，再喂给解析器。至少覆盖这些情况：emoji 被切断、CRLF 换行、多行 data、多条事件挤在同一块、非法 JSON、只来了半条事件就断开。

只在本地测是不够的。本地服务器往往一次写出、浏览器一次读到，这些切块问题根本不会出现。

常见追问

为什么不直接用 EventSource？

EventSource 只支持 GET，不能自定义请求头和请求体。AI 接口一般要用 POST，还要带认证头，所以多数是用 fetch 自己解析。代价是断线重连也要自己处理。
