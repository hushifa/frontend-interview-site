AI Prompt Caching 对前端请求设计有什么影响？

Prompt Caching 通常复用请求中稳定前缀的处理结果，可能降低重复计算成本，但不等于复用上一条答案，也不能替代权限隔离和对话持久化。

参考答案

简答

  • Prompt Caching 复用请求中稳定前缀的处理结果，不复用上一条答案。
  • 稳定内容放在前面，会变化的问题和检索结果放在后面，才能形成相同前缀。
  • 自动缓存和显式断点是各厂商自己的机制，不是通用标准。
  • 未命中时应用仍要正常工作；缓存不能代替租户权限隔离。

它缓存的不是上一条回答

提示词缓存通常复用重复输入前缀的处理结果。系统规则、稳定工具定义和固定背景如果在多次请求中保持一致，服务商可能不必每次从头处理它们；当前用户问题和新增输出仍然需要计算。

因此缓存命中不代表答案被直接返回，也不保证下一次输出相同。排队、网络、工具调用和输出长度仍会决定用户等待时间。

请求结构决定有没有可复用前缀

假设每次请求都把时间戳、随机 ID 或变化的工具定义放在最前面，后面的长文档就难以形成相同前缀。通常可以让稳定部分保持顺序，把会变化的用户问题和临时检索结果放在后面：

下面以 Anthropic Messages API 为例。工具定义放在顶层 tools 字段，而不是写成一条 system 消息；缓存前缀按 tools → system → messages 的顺序计算，某一层变化会让它和之后的缓存全部失效。

JavaScript
function buildRequest({ systemRules, tools, history, question, documents }) {
  return {
    model: 'claude-opus-5-5',
    max_tokens: 1024,
    tools,
    system: [
      // 断点放在最后一个跨请求保持不变的块上
      { type: 'text', text: systemRules, cache_control: { type: 'ephemeral' } },
    ],
    messages: [
      ...history,
      { role: 'user', content: buildQuestion(question, documents) },
    ],
  };
}

默认缓存有效期 5 分钟，每次命中会刷新；可以设 ttl: '1h'，但写入价格更高。响应的 usage 里，cache_creation_input_tokens 是写入缓存的量，cache_read_input_tokens 是命中读取的量；两者都为 0，通常是前缀短于模型的最小可缓存长度。OpenAI 等服务是按前缀自动缓存，不需要标记断点，字段和计费方式也不同。

不能为了命中率把本来与用户身份绑定的权限约束挪成所有用户共享的内容，也不能为了稳定前缀保留不再适用的背景。正确性和最小权限优先于命中率。

“看起来相同”不等于缓存键相同。角色、内容块顺序、工具配置、模型版本、系统参数和服务商的断点规则都可能影响命中。应查看目标服务最终接收的结构和返回的缓存 usage，而不是只看前端字符串。

自动缓存和显式断点不是通用标准

有的服务自动识别前缀，有的要求 cache_control 或内容块级断点；有效期、最小长度、可缓存内容和读写价格也不同。不能把一个供应商的字段复制到另一个模型，就认为都支持同样语义。SDK 还可能改写请求，必要时检查最终网络载荷和文档版本。

缓存写入可能收费，读取也未必免费。只有一次请求、很少重复或前缀很短时，启用缓存可能增加成本而没有收益。应按请求类型比较缓存读、写、未命中的实际 usage 和延迟。

命中和未命中都必须保持正确

模型版本变化、系统提示词更新、工具定义变化、缓存过期和平台调度都会导致未命中。未命中时应用仍应正常生成，只是成本或延迟不同，不能把缓存当作业务数据来源。

Prompt Cache 也不是对话数据库。页面刷新或跨设备恢复时，历史必须从自己的持久化系统读取，再按当前权限和版本构造请求。不能假设服务商会永久保留之前的上下文。

系统提示词和工具配置可以版本化，用于解释命中变化；但不要每次请求无意义地改变版本字段，否则会主动破坏复用。用户权限、租户和数据版本变化时，宁愿失去命中也不能复用错误上下文。

缓存不是权限隔离

不能因为平台声称按账户或组织隔离，就把用户 A 的私有资料放进可能被用户 B 复用的前缀。应用仍要在构造提示词和检索上下文前完成租户过滤，限制敏感字段和保留期限。缓存命中也不应被前端用来推断其他用户是否发过某段内容。

生产监控可以分别记录输入输出用量、缓存读写、模型版本、前缀版本、首 Token 延迟和完整响应时间，但默认不要记录完整私有提示词。优化顺序应是先保证权限和答案正确，再稳定结构，最后用实际 usage 证明成本和延迟确实下降。
