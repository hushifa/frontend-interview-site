TypeScript 库发布时怎样组织类型声明和入口？

在 package.json 的 exports 里给每个入口同时写上类型声明和 JS 文件，types 放第一位；声明文件的模块格式要和对应的 JS 一致。发布前把打好的包装到一个独立项目里，按包名导入验证。

参考答案

简答

发布一个 TS 写的库，使用者既要拿到能运行的 JS，也要拿到 .d.ts 类型声明。现在的做法是在 package.json 的 exports 里，给每个入口写一个条件对象，types 指向声明，default 指向 JS，并且 types 要写在第一位，因为 TypeScript 是按顺序匹配条件的。

声明的模块格式必须跟 JS 一致。在 "type": "module" 的包里，.js 是 ESM，对应的 .d.ts 也按 ESM 解释；CommonJS 入口要配 .d.cts。只写一份声明给两种格式共用，CommonJS 使用者拿到的默认导出类型就是错的。

写了 exports 以后，没列出来的子路径使用者导入不了，所以公开的子路径要一个个声明。.d.ts 里也不能引用 paths 别名或只在仓库里才有的类型，用到的第三方类型包要放进 dependencies 或 peerDependencies。

发布前最可靠的检查，是用 npm pack 打出包，在一个独立项目里安装，分别用 moduleResolution: bundler 和 nodenext 跑一遍类型检查。

只发 ESM 时怎么写

json
{
  "name": "@example/count-label",
  "version": "1.0.0",
  "type": "module",
  "files": ["dist"],
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "default": "./dist/index.js"
    }
  }
}

"." 代表包的主入口，使用者写 import ... from '@example/count-label' 时就走这里。TypeScript 先匹配到 types，拿 index.d.ts 当类型；运行时 Node 或打包工具匹配到 default，加载 index.js。files 限定只发布 dist 目录。

配套的 tsconfig 用 module: nodenext、declaration: true、outDir: dist。现在的 Node.js 已经允许 require 加载不含顶层 await 的 ESM，所以新库只发 ESM 通常就够了。

同时发 ESM 和 CommonJS

json
{
  "exports": {
    ".": {
      "import": {
        "types": "./dist/esm/index.d.mts",
        "default": "./dist/esm/index.mjs"
      },
      "require": {
        "types": "./dist/cjs/index.d.cts",
        "default": "./dist/cjs/index.cjs"
      }
    }
  }
}

import 和 require 两个条件各自配一套 JS 和声明。为什么不能共用一份 .d.ts？因为 TypeScript 会按 ESM 去理解它，可 CommonJS 消费者实际拿到的是另一种格式的模块，默认导出的形状对不上。Are the Types Wrong 这个工具把这种情况叫 “Masquerading as ESM”。

双格式还有一个风险：同一个进程里两份代码都被加载了，各自有一份模块状态，单例会变成两个，instanceof 判断也会失效。这叫双包风险，也是推荐新库只发 ESM 的原因之一。

子路径要一个个声明

json
{
  "exports": {
    ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" },
    "./utils": { "types": "./dist/utils.d.ts", "default": "./dist/utils.js" },
    "./package.json": "./package.json"
  }
}

这样使用者可以导入 @example/count-label/utils。要是有人写 import '@example/count-label/dist/internal.js'，就会因为不在 exports 里而失败。这看起来是限制，其实是好事：内部文件没人能直接依赖，你就可以放心重构。

发布前怎么检查

  1. npm pack --dry-run 看实际会打包哪些文件。
  2. npx publint 检查 exports 写的路径和文件是否对得上。
  3. npx @arethetypeswrong/cli --pack 检查各种解析模式下类型是否正确。
  4. 在独立项目里 npm install ../count-label-1.0.0.tgz，用包名导入，运行 tsc --noEmit 和真实代码。

最后一步最关键。在库自己的仓库里测试，走的是相对路径，exports 写错了也发现不了；只有装成依赖、按包名导入，才是使用者真正的路径。

类型也是版本契约的一部分

删掉一个导出的类型、把参数收窄、调换重载顺序，都可能让使用者编译失败。所以这些改动要按语义化版本算作破坏性变更。复杂的公开类型可以写类型测试锁住，见《TypeScript 复杂类型应该怎样测试？》。

常见追问

还需要顶层的 types 字段吗？

只是为了不支持 exports 的旧解析模式 node10 才保留。TypeScript 7 已经删除了这个模式。

typesVersions 是做什么的？

它给不同版本的 TypeScript 提供不同的声明。现在主要用来在旧解析模式下兼容子路径。
