TypeScript 库发布时怎样组织类型声明和入口？

库发布需要同时提供可解析的 JavaScript 入口、与模块格式匹配的声明入口，以及完整的产物依赖。应从实际安装包验证消费者，而不是只检查源码仓库里的路径别名和类型编译。

参考答案

简答

  • 用 package.json 的 exports 为每个入口声明 types、import、require 条件，types 条件放在最前。
  • ESM 和 CommonJS 双格式包需要分别提供对应的声明文件。
  • 声明文件不能引用消费者无法安装的依赖或仓库内的路径别名。
  • 发布前在独立项目中按真实包名安装并检查类型与运行结果。

发布 TypeScript 库，至少需要回答两件事：运行时加载哪个 JavaScript 文件，编译器读取哪份类型声明。两份入口必须描述同一套公开 API，并且消费者不应依赖库作者本机的源码路径或工作区别名。

最有效的验证方式，是把实际打包得到的包放进一个独立消费者，再按真实包名导入、检查和运行。

先做一个边界清楚的 ESM 包

下面以只承诺 ESM 导入的工具库为例。源码提供一个函数与它的选项类型：

TypeScript
// src/index.ts
export interface FormatOptions {
  suffix?: string;
}

export function formatCount(value: number, options: FormatOptions = {}): string {
  if (!Number.isSafeInteger(value) || value < 0) {
    throw new RangeError('数量必须是非负安全整数');
  }
  return `${value}${options.suffix ?? ' 项'}`;
}

使用项目选定并安装的 TypeScript 开发依赖构建，tsconfig.json 可以明确输出目录与声明：

json
{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2022"],
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "strict": true,
    "declaration": true,
    "noEmitOnError": true,
    "rootDir": "src",
    "outDir": "dist"
  },
  "include": ["src"]
}

package.json 将运行入口与类型入口一起暴露：

json
{
  "name": "@example/count-label",
  "version": "1.0.0",
  "type": "module",
  "files": ["dist"],
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    }
  },
  "scripts": {
    "build": "tsc -p tsconfig.json"
  }
}

构建后应实际存在 dist/index.js 和 dist/index.d.ts。顶层 type:module 让这些 .js 与 .d.ts 采用 ESM 语义。types 提供类型入口， exports 条件则服务遵循现代包解析的消费者，类型条件放在适当的前置位置。

FormatOptions 只存在于类型层，不会成为 JavaScript 中可读取的接口对象。消费者应使用 import type 导入它，真正调用 formatCount 则需要值导入。

exports 封装了公开路径，不是列出目录就结束

设置 exports 后，未声明的子路径可能不再允许被消费者按包名深层导入。包中实际有某个内部文件，也不意味着 包名/dist/internal.js 就是受支持的公共入口。

如果要公开额外功能，应增加明确子路径及其类型和运行入口。以后调整内部文件结构时，消费者依赖这些稳定入口，比直接依赖 dist 布局更容易维护。

老版本工具不一定使用同样的 exports 解析规则，因此声明支持范围时应实际测试目标。不要为了让一个工具勉强工作而让 types、exports 和真实模块格式互相矛盾。

双格式包需要分别匹配声明格式

如果确实承诺同时支持 import 与 require，可以为它们提供分开的入口。例如发布结构采用 .mjs、.cjs 时，对应声明可采用 .d.mts、.d.cts：

json
{
  "exports": {
    ".": {
      "import": {
        "types": "./dist/esm/index.d.mts",
        "default": "./dist/esm/index.mjs"
      },
      "require": {
        "types": "./dist/cjs/index.d.cts",
        "default": "./dist/cjs/index.cjs"
      }
    }
  }
}

这只是入口组织示例，必须由构建流程真正生成四个相互对应的文件，并从两类消费者验证。不能把同一份按 ESM 解释的声明随意指给 CommonJS 分支，然后认为“反正内容都是函数签名”就完全等价。

还有其他合法组织方式，例如在子目录通过 package.json 明确模块格式，关键是让运行时代码与声明的格式一致。现代 Node 能 require 某些同步 ESM，也不等于一个包无需验证就可以对所有 CommonJS 用户承诺兼容。

双构建还可能在同一进程中形成两份模块状态，影响单例、类身份与缓存。如果没有实际兼容需求，单一格式通常更容易保持一致。

声明不能泄漏开发环境专属路径

源码里通过 paths 或工作区别名导入的类型，可能原样进入 .d.ts。消费者没有同样的别名配置，就会出现“库自己能编译，安装后找不到类型”的问题。

如果公开声明引用了另一个包的类型，那个包需要通过合适的依赖或 peer 关系对消费者可用，不能只因为作者在 devDependencies 安装过就认为发布后也存在。只供内部测试使用的依赖则不应无意成为公共签名的一部分。

自动推导有时会暴露内部实现类型。发布前应查看生成声明，给公共边界适当的显式签名，避免使用者被迫理解一串未公开的内部路径或复杂类型。

从实际安装包验证，而不是从源码直接引用

可以先用 npm pack 在本地生成包，再检查内容清单，确认入口、声明和必要资源都在里面，源码测试、临时文件或本机配置没有误入。

把包安装到独立消费者后，至少检查以下路径：运行时按包名导入函数；TypeScript 能推导返回值并拒绝错误参数；import type 能找到公开类型；承诺的子路径可用；未公开内部路径没有被当成隐含 API。

若支持 CommonJS、不同 moduleResolution 或一定范围的 TypeScript 版本，应分别准备消费者。仓库内 monorepo 链接可能直接指向源码，掩盖产物缺失，不能替代安装包测试。

files 字段可以限制发布内容，但仍要看 pack 的实际清单。declarationMap 若要帮助跳回源码，还需要确保映射目标可用；只发布地图却遗漏其指向内容，不能保证消费者体验。

类型兼容也是版本契约的一部分

运行函数名字没变，类型参数、重载顺序、返回联合或可选属性的变化，也可能让使用者升级后无法编译。类型修正可能是合理的，但仍应按公开兼容承诺评估与说明。

构建成功只能证明作者环境完成了构建，声明生成成功只能证明产生了文件。最终可信的发布证据，是消费者从包入口拿到正确类型，并能运行到对应的真实实现。
