ReadableStream 的 tee 分流有什么代价？

tee() 把一个流拆成两个读取相同数据的分支；两个分支的读取速度不同时，快的一边读到的数据要为慢的一边缓存在内存里。只有两个分支都取消，源流才会被取消。

参考答案

简答

  • stream.tee() 返回两个新的 ReadableStream，原流被锁定，之后只能读这两个分支。
  • 拉取速度由读得快的分支决定，慢的分支没读的数据在内存中排队，不会对源流产生背压。
  • 只取消一个分支不会停止源流，两个分支都取消后，源流才收到取消。
  • 适合"同一份响应既写入缓存又交给页面"这类两边都会读完的场景；一边可能长期不读时不要用 tee。

典型用法：Service Worker 边返回边缓存

JavaScript
self.addEventListener('fetch', (event) => {
  event.respondWith(
    (async () => {
      const response = await fetch(event.request);
      if (!response.ok || !response.body) return response;

      const [forPage, forCache] = response.body.tee();
      const cache = await caches.open('v1');
      event.waitUntil(cache.put(event.request, new Response(forCache, response)));
      return new Response(forPage, response);
    })(),
  );
});

这里更常见的写法是 response.clone()，它内部也是 tee，代价相同。

内存问题

JavaScript
const [fast, slow] = hugeStream.tee();
await consume(fast);

slow 一直不读，fast 读过的每一块都留在 slow 的队列里，最终整个响应都留在内存中。

规避方式：

  • 两个分支并发消费：await Promise.all([consume(a), consume(b)])。
  • 某个分支不再需要时立即 cancel()，队列会被丢弃。
  • 只需要计算摘要或进度时，用 TransformStream 在一条管道里顺带处理，不分叉：
JavaScript
let bytes = 0;
const counter = new TransformStream({
  transform(chunk, controller) {
    bytes += chunk.byteLength;
    controller.enqueue(chunk);
  },
});
await response.body.pipeThrough(counter).pipeTo(destination);

错误传播

源流出错时，两个分支都会出错。一个分支的消费方出错不会影响另一个分支，但要记得取消它，否则缓存会持续增长。
