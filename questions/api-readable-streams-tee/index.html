ReadableStream 的 tee 分流有什么代价？

tee() 把一个流复制成两个分支。两边读得一快一慢时，慢的那边没读的数据全堆在内存里；只取消一边不会停掉源流，两边都取消才会。

参考答案

简答

一个流只能被读一次。如果同一份响应既要交给页面、又要写进缓存，就用 stream.tee()，它返回两个新的 ReadableStream，两边读到的是同样的数据。原来的流会被锁住，之后只能读这两个分支。

代价在内存。源流的拉取速度由读得快的那一边决定，慢的那一边没读的数据会在它的队列里排队，不会让源流放慢，这叫没有背压。一边一直不读，整个响应最后都会堆在内存里。

取消也要注意。只取消一个分支，源流不会停；两个分支都取消了，源流才收到取消。

所以 tee 适合“两边都会读完”的场景，比如 Service Worker 边返回边缓存。一边可能长期不读，就不要用 tee；只是想顺便统计字节数，用 TransformStream 在一条管道里处理更好。

典型用法：Service Worker 边返回边缓存

下面把响应体分成两份，一份给页面，一份写进缓存。

JavaScript
self.addEventListener('fetch', (event) => {
  event.respondWith(
    (async () => {
      const response = await fetch(event.request);
      if (!response.ok || !response.body) return response;

      const [forPage, forCache] = response.body.tee();
      const cache = await caches.open('v1');
      event.waitUntil(cache.put(event.request, new Response(forCache, response)));
      return new Response(forPage, response);
    })(),
  );
});

为什么不直接把 response 同时交给页面和缓存？因为响应体是一个流，读过一次就没了。所以要先分成两份。实际中更常见的写法是 response.clone()，它内部也是用 tee 实现的，代价一样。

两边读得不一样快会怎样

先看一个会出问题的写法：

JavaScript
const [fast, slow] = hugeStream.tee();
await consume(fast);

fast 被读完了，slow 一直没人读。可是 fast 读过的每一块，都要给 slow 留一份，因为 slow 以后可能会读。所以这些数据全堆在 slow 的队列里，最后整个响应都留在了内存中。

为什么源流不等一等慢的那边？因为 tee 的设计是按快的一边拉数据，慢的一边只是缓存，不会反过来让源流暂停。

改法有三种。第一，两个分支同时消费：await Promise.all([consume(a), consume(b)])。第二，某个分支不再需要时立刻 cancel()，它的队列会被丢掉。第三，如果只是想计算摘要或进度，就别分叉，用 TransformStream 在一条管道里顺带处理：

JavaScript
let bytes = 0;
const counter = new TransformStream({
  transform(chunk, controller) {
    bytes += chunk.byteLength;
    controller.enqueue(chunk);
  },
});
await response.body.pipeThrough(counter).pipeTo(destination);

数据流过 counter 时顺便累加字节数，原样往下传，全程只有一份数据。

只取消一个分支，源流会停吗

不会。下面这个例子在 Node 里能直接运行：

JavaScript
const source = new ReadableStream({
  pull(controller) {
    controller.enqueue(1);
  },
  cancel(reason) {
    console.log('源流被取消', reason);
  },
});
const [a, b] = source.tee();

a.cancel('a');
await new Promise((resolve) => setTimeout(resolve, 10));
console.log('只取消了 a');
await b.cancel('b');
// 只取消了 a
// 源流被取消 [ 'a', 'b' ]

取消 a 以后，源流的 cancel 没有被调用，因为 b 还可能要读。等 b 也取消了，源流才收到取消，取消原因是两个分支各自的原因合成的数组。

出错时会怎样

源流出错时，两个分支都会出错。但一个分支的消费方自己出错，不会影响另一个分支。这时候要记得把出错那边的分支取消掉，否则另一边继续读，这边的队列会一直增长。

常见追问

response.clone() 和 tee 有什么关系？

clone() 内部就是对响应体做 tee。所以克隆以后两份都要读完，或者把不用的那份取消，否则一样会把数据堆在内存里。

只想显示下载进度，需要 tee 吗？

不需要。用一个 TransformStream 接在管道中间，每块经过时累加 byteLength 再原样传下去，不用分叉，也没有额外的内存占用。
