网络与安全面试题

前端网络面试题，涵盖 HTTP 缓存、HTTPS、HTTP/2 与 HTTP/3、跨域 CORS、请求状态码、Fetch 异常、WebSocket 和 SSE。共 22 道题。

  • 强缓存与协商缓存如何配合？

    浏览器先看缓存是否新鲜，新鲜就直接使用（强缓存）；过期后带上 ETag 或 Last-Modified 发条件请求，服务器回 304 时复用本地正文（协商缓存）。

  • 什么是跨域？CORS 为什么需要服务端配合？

    协议、主机、端口任一不同就是跨源。浏览器默认不让脚本读取跨源响应，CORS 让服务器用响应头声明允许哪些来源读取；它保护的是用户浏览器里的数据，不是服务器的访问控制。

  • HTTPS 相比 HTTP 提供了哪些保障？

    HTTPS 是 HTTP 跑在 TLS 上。TLS 提供机密性、完整性和服务器身份认证；TLS 1.3 用一次往返完成握手，默认具备前向保密。它不保证网站本身可信，也不替代应用层的登录和权限。

  • HTTP/1.1、HTTP/2 和 HTTP/3 的主要区别是什么？

    三者的请求方法、状态码、头部语义相同，区别在传输。HTTP/1.1 一个连接同时只处理一个请求；HTTP/2 在一条 TCP 连接上多路复用；HTTP/3 改用基于 UDP 的 QUIC，消除了 TCP 层的队头阻塞，并把握手合并为一次。

  • HTTP 方法的安全性和幂等性是什么意思？

    安全方法不修改服务器状态（GET、HEAD、OPTIONS、TRACE），幂等方法重复执行多次和执行一次效果相同（安全方法加上 PUT、DELETE）。POST 和 PATCH 都不保证幂等，重试前需要幂等键等机制。

  • 常见 HTTP 状态码应该怎样在前端区分处理？

    2xx 成功、3xx 重定向、4xx 客户端问题、5xx 服务端问题。前端要按具体状态码决定行为：401 重新登录、403 提示无权限、429 和 503 按 Retry-After 退避、其他 4xx 不要重试。

  • 为什么 fetch 收到 404 不一定进入 catch？

    fetch 只在拿不到响应时拒绝 Promise，例如网络中断、CORS 拦截、请求被取消。404、500 都是正常响应，需要检查 response.ok 自己抛错；读取正文和解析 JSON 是另外的失败点。

  • WebSocket 适合什么场景，连接断开后怎样恢复？

    WebSocket 适合低延迟、双向、高频的通信，如聊天和协同编辑。它不自带重连、心跳和消息确认，恢复要分两步：用退避重连恢复连接，再用消息序号补齐断线期间的数据。

  • SSE 与 WebSocket 有什么区别？

    SSE 是服务器到浏览器的单向文本事件流，基于普通 HTTP，EventSource 自带断线重连和事件 ID 续传；WebSocket 是全双工连接，支持二进制，重连和消息确认都要自己做。

  • dns-prefetch、preconnect 和 preload 应该怎样选择？

    dns-prefetch 只提前解析域名，preconnect 提前完成 DNS、TCP 和 TLS，preload 提前下载当前页面一定会用到的具体资源。提示越重成本越高，只用于确定的、关键的少数资源。

  • HTTP Range 请求适合什么场景？

    Range 请求只取资源的一段字节，用于断点续传、视频拖动和读取大文件的局部。服务器支持时返回 206 和 Content-Range，不支持时返回完整的 200，范围无效时返回 416；配合 If-Range 防止文件更新后把新旧内容拼在一起。

  • fetchpriority 能解决资源加载优先级问题吗？

    fetchpriority 只调整已经被发现的资源在同类资源中的相对优先级，最常见的用途是给首屏主图设 high、给轮播里看不到的图片设 low。资源发现太晚、被懒加载或网络本身慢，它都解决不了。

  • Service Worker 缓存更新为什么容易出现旧版本？

    新 Service Worker 安装后默认要等所有旧页面关闭才激活，期间旧 Worker 继续用旧缓存响应；importScripts 引入的脚本被 HTTP 缓存、缓存名不随版本变化、activate 时没清旧缓存，都会让用户长期停在旧版本。

  • Cache-Control 的 immutable、stale-while-revalidate 和 no-store 怎样选择？

    带哈希的静态资源用长 max-age 加 immutable；允许短暂旧数据的接口或页面用 stale-while-revalidate；含敏感数据、绝不能落盘的响应用 no-store。需要每次确认最新但允许存储时用 no-cache。

  • HTTP 103 Early Hints 适合怎样的加载优化？

    服务器生成 HTML 需要时间时，可以先发一个 103 响应，带上 preconnect 和 preload 的 Link 头，让浏览器在等待期间提前建连、下载关键资源。它取代了已被 Chrome 移除的 HTTP/2 Server Push。

  • HTTP 内容协商会怎样影响前端资源和接口响应？

    同一个 URL 可以按请求头返回不同表示：Accept 选格式，Accept-Language 选语言，Accept-Encoding 选压缩方式。服务器必须用 Vary 声明依据了哪些请求头，否则缓存会把一种表示返回给所有人。

  • Cache-Status 响应头能帮助诊断哪些缓存问题？

    RFC 9211 定义的 Cache-Status 让每一层缓存在响应上写一条记录，说明是否命中、为什么转发到上游、是否存储。比只看 Age 或厂商私有头（如 X-Cache）更标准，适合排查 CDN 多层缓存。

  • DNS、TCP 和 TLS 握手分别会给页面增加哪些等待？

    新连接要依次经历 DNS 解析、TCP 握手和 TLS 握手，之后才能发 HTTP 请求。TLS 1.3 加 TCP 至少两个往返，HTTP/3 合并为一个。Navigation Timing 和 Resource Timing 的时间戳可以把每一段拆出来测量。

  • CDN 和反向代理缓存异常应该怎样排查？

    把链路拆成浏览器、CDN 边缘、中间层、反向代理和源站，逐层比对响应头和缓存键，找出是哪一层返回了旧内容或错误响应。关键证据是 Age、Cache-Status 或厂商缓存头、ETag 和 Vary。

  • 前端网络问题应该怎样按协议层排查？

    前端看到的"请求失败"可能出在 URL、DNS、连接与 TLS、HTTP、浏览器策略（CORS、CSP、混合内容）、缓存与 Service Worker、数据解析中的任何一层。先在 DevTools 里保存原始证据，再从下往上逐层排除。

  • 浏览器分片上传如何实现可靠的暂停与续传？

    服务端创建上传会话并记录已收到的分片；浏览器用 File.slice 切片、限制并发上传、失败重试。暂停就是取消进行中的请求，续传时先向服务端查询已完成的分片，只补传缺失部分，全部完成后由服务端合并并校验。

  • 浏览器直传对象存储时，如何设计安全的分片上传？

    业务服务器负责鉴权、创建上传会话、为每个分片签发短期预签名 URL 并在最后合并；浏览器直接把分片 PUT 到对象存储。安全边界在签名范围、过期时间、对象键由服务端决定，以及合并前的校验和未完成上传的清理。
