性能优化面试题

前端性能优化面试题，围绕长任务、懒加载、preload、虚拟列表、真实用户监测、Navigation Timing 和 Resource Timing 分析页面加载与交互。共 16 道题。

  • LCP、INP、CLS 分别衡量什么？

    LCP 看主要内容多快出现，INP 看点击、按键后页面多快有反应，CLS 看内容有没有意外跳动。良好阈值按真实用户的 75 分位评估，实验室诊断和现场采集要配合着看。

  • 首屏加载慢应该怎样优化？

    先量再改：用 TTFB、FCP、LCP 判断慢在哪一段，再把 LCP 拆成首字节、资源加载延迟、资源加载耗时、元素渲染延迟四段，按“服务器与网络 → 关键资源发现 → 资源体积 → 渲染阻塞”的顺序排查。良好阈值是 TTFB 0.8 秒、FCP 1.8 秒、LCP 2.5 秒，看真实用户的第 75 百分位。

  • 虚拟列表通过什么方式减少渲染成本？

    虚拟列表用一个和完整列表一样高的占位容器保留滚动范围，只渲染视口及上下少量缓冲区里的行，滚动时替换内容。它减少的是 DOM 数量和每次更新的渲染工作，不会减少已加载到内存的数据，也不会加快过滤计算。

  • 页面要渲染十万条数据，怎样不卡顿？

    一次性插入十万个 DOM 节点会让主线程长时间被占住，页面卡死。能分页就分页；必须一次展示时用虚拟列表，只渲染可视区域的几十条；只是数据多、必须全部插入时，用时间分片把插入拆成很多小批次，每批在 requestAnimationFrame 或 setTimeout 里执行，让浏览器在批次之间响应输入和绘制。

  • 什么是长任务，为什么会影响交互响应？怎样观测和拆分？

    主线程上连续执行 50ms 以上的任务就是长任务。它执行期间用户输入只能排队、渲染也被推迟，表现为点了没反应、INP 变差。可以用 PerformanceObserver 观察 longtask 或更详细的 long-animation-frame 来定位，再通过减少工作、分片让出主线程或移到 Worker 来优化。

  • 懒加载为什么有时反而让首屏和首次交互变慢？

    懒加载只是把下载和执行往后挪，用户马上要用的东西就会在第一次用时多等一轮。首屏 LCP 图片加 loading="lazy" 会推迟请求；点击后才依次下载组件、数据和依赖，会形成串行瀑布。

  • 动态高度的虚拟列表怎样处理测量、滚动锚点和焦点？

    行高不固定时，先用估计高度算位置，行挂载后用 ResizeObserver 测出真实高度，按数据 ID 缓存，再修正后面各行的偏移。前面的内容高度变了，要按锚点行补偿滚动位置；被卸载的行会丢掉焦点和输入状态，要单独保留。

  • 前端内存泄漏应该怎样定位？

    泄漏就是“不再需要的对象仍然可达，没法被回收”。定位方法是构造可重复的操作闭环（比如打开再关闭面板十次），对比前后两次堆快照，找出数量持续增长的对象，再沿 Retainers 引用链找到是谁留住了它。常见原因是没移除的全局监听、定时器、Observer、订阅和没有上限的缓存。

  • 一个线上页面变慢后应该怎样完成性能诊断闭环？

    先用 RUM 按页面、版本、设备拆分，找出谁变慢、哪个指标、从哪个版本开始；再在实验室固定条件复现，用瀑布图查 LCP、用 Performance 面板查 INP；按瓶颈修复，最后用对照测试和分批发布确认真实用户数据变好。

  • 真实用户监测与实验室性能测试为什么要结合？

    实验室测试（Lighthouse、WebPageTest、DevTools）条件固定，适合复现、找原因和发布前拦截退化；RUM 采集真实用户在各种设备、网络和交互下的数据，反映体验分布。INP 这类交互指标只能靠 RUM 拿到真实值，两者回答不同问题，不能互相替代。

  • Resource Timing 为什么有些跨源字段是零？

    跨源资源没有返回 Timing-Allow-Origin 时，DNS、连接、请求、响应这些细分时间和 transferSize、nextHopProtocol 都会被置零或置空；encodedBodySize、decodedBodySize、responseStatus 要看是否以 CORS 模式请求并通过检查。transferSize 为 0 也可能是命中了本地缓存，要结合其他字段区分。

  • 前端性能预算应该怎样制定和落地？

    性能预算就是“在指定场景下某项指标不能超过的上限”，分资源预算（JS、CSS、图片体积）、运行时预算（长任务、主线程阻塞）和体验预算（LCP、INP、CLS）。数值从现有基线和目标出发，在 CI 里用构建产物和实验室测试检查，线上用 RUM 跟踪趋势。

  • INP 很高时，如何定位到底是哪一段交互变慢？

    INP 衡量点击、轻触和按键到下一帧绘制要多久，≤200ms 良好、>500ms 较差，按 75 分位评估，2024 年取代 FID 成为 Core Web Vitals。每次交互拆成输入延迟、处理时间、呈现延迟三段，用 Event Timing 或 web-vitals 库找到最慢的交互和慢在哪段，再对症优化。

  • 如何用 Long Animation Frames API 定位卡顿来源？

    Long Animation Frames（LoAF）记录超过 50ms 才渲染完的帧，带上渲染、样式布局的开始时间和这一帧里跑过的脚本列表。每个脚本给出调用者、来源 URL、函数名和强制布局耗时，比 Long Tasks API 更能回答“是谁让这一帧变慢”。它不是 Baseline，要做特性检测。

  • 第三方脚本怎样接入，才能控制性能和安全风险？

    页面里直接加载的第三方脚本以页面的身份运行，能读写 DOM、发请求、读非 HttpOnly 的 Cookie，还占带宽和主线程。接入时先想清楚要不要、什么时候加载，用 defer 或延迟加载减少阻塞，用 CSP 限制来源，不可信内容放进跨源 iframe，并准备好开关和降级。

  • Speculation Rules API 的预取和预渲染有什么区别？

    用 <script type="speculationrules"> 告诉浏览器哪些链接可以提前处理。prefetch 只下载目标页面的 HTML，不下载子资源；prerender 在看不见的地方把页面完整加载并执行，点过去几乎立刻显示。eagerness 控制触发时机。它不是 Baseline，不支持的浏览器会忽略规则。
