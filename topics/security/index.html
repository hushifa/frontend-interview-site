前端安全面试题

前端安全面试题，围绕 CSP、Cookie 安全属性、postMessage、Trusted Types、frame-ancestors 和原型污染，理解浏览器安全机制与防护边界。共 28 道题。

  • XSS 有哪几种？前端怎样防范？

    XSS 是攻击者的脚本混进了你的页面，以你的源的身份运行，能读页面、发请求、读没设 HttpOnly 的 Cookie。按恶意内容的来源分存储型、反射型和 DOM 型。防范靠默认按文本输出、必须渲染 HTML 时先净化、校验链接协议，再用 CSP 和 HttpOnly 兜底。它和 CSRF 的区别在于攻击代码在哪里运行。

  • HttpOnly、Secure 和 SameSite 分别保护什么？

    HttpOnly 让脚本读不到 Cookie，Secure 让 Cookie 只走 HTTPS，SameSite 决定跨站请求带不带 Cookie。各浏览器默认行为不一样，所以要显式写出来。

  • HTTPS 握手中，中间人攻击是怎样被防住的？

    中间人可以截获连接，却拿不到网站证书对应的私钥。浏览器校验证书链能追到受信任的根 CA、证书上的域名与访问的域名一致，再验证服务器用私钥对握手内容做的签名，冒充者就会在握手时失败。证书防不住的是用户一开始就走 HTTP 被降级，这要靠 HSTS 和预加载列表。

  • 用了 HTTPS 还要在前端加密吗？接口加签和防重放怎样设计？

    HTTPS 已经保证传输中的数据不被偷看和篡改，前端再加密一层防不住用户自己、恶意脚本和拿到代码的人，因为前端代码和里面的密钥都会被下载到用户手里。接口签名是按约定把参数、时间戳和随机 nonce 拼成字符串算签名，服务端校验签名、拒绝过期时间戳和重复 nonce，用来防篡改和防重放。能签名的密钥必须在服务端或用户自己的会话里，不能写死在前端代码中。

  • Cookie-Session 和 JWT 登录有什么区别？前端的 Token 应该存在哪里？

    Session 方案把登录状态存在服务端，浏览器只拿一个会话 ID 放在 Cookie 里；JWT 把用户信息签名后交给客户端，服务端验签即可，不用查会话。JWT 签发后难以提前作废，存在 localStorage 会被 XSS 读走，所以常见做法是短期 Access Token 加 HttpOnly Cookie 里的 Refresh Token。

  • Access Token 过期后，前端怎样做无感刷新？

    在请求层统一拦截 401：先用 Refresh Token 换一个新的 Access Token，再重发原请求。多个请求同时 401 时只发一次刷新，其余请求共用这次刷新的结果；刷新失败就清掉登录状态、跳转登录页。服务端每次刷新都换发新的 Refresh Token 并作废旧的，旧令牌被重复使用时就能发现泄露。

  • Referrer-Policy 是什么？默认会把哪些信息发给其他网站？

    Referer 请求头告诉目标服务器请求是从哪个页面来的，Referrer-Policy 决定这个头里带多少信息。浏览器默认用 strict-origin-when-cross-origin：同源发完整地址，跨源只发源，从 HTTPS 降到 HTTP 不发。

  • 登录密码怎样传输和存储？用了 HTTPS 还需要在前端哈希密码吗？

    密码在传输中靠 HTTPS 保护，TLS 提供机密性和完整性。前端先哈希一次并不能替代 HTTPS，因为服务端收到的哈希值就成了新的“密码”，被截获照样能登录。真正要做好的是服务端存储：用 Argon2id、bcrypt 或 PBKDF2 这类慢哈希，每个密码一个随机盐，不能用 MD5、SHA-256 这类快速哈希，更不能可逆加密。

  • 接口防刷怎样做？限流、验证码和风控里前端负责什么？

    防刷的判断和拦截必须在服务端：按账号、IP 等维度限流，超限返回 429；登录失败次数按账号计数；可疑请求再要求验证码或多因素认证。前端代码会被绕过，只能做配合：防重复点击、处理 429 和 Retry-After、在服务端要求时展示验证码、提示保持通用。OWASP 也说明验证码会被破解，不能单独依赖。

  • CSP 的 nonce、hash 与 Report-Only 如何使用？

    CSP 用响应头告诉浏览器哪些脚本可以执行。nonce 是每次响应换一个的随机标记，hash 是固定脚本内容的指纹；新策略先用 Report-Only 只报告不拦截，确认没问题再强制执行。

  • 跨窗口 postMessage 怎样避免把消息发给错误对象？

    发消息时 targetOrigin 写具体的源，不用 '*'；收消息时先核对 event.origin 和 event.source，再检查消息格式。消息内容一律当不可信数据处理。

  • Double Submit Cookie 能怎样防御 CSRF？

    服务端下发一个令牌 Cookie，前端读出来再放进请求头一起提交，服务端比较两者。恶意网站能让浏览器带上 Cookie，却读不到它的值，也就填不出请求头。令牌最好与会话绑定并签名。

  • CORS 携带凭据时有哪些限制？

    跨源请求要带 Cookie，前端要设 credentials 为 include，服务端要返回具体的 Allow-Origin 和 Allow-Credentials: true。就算 CORS 通过了，Cookie 也可能因为 SameSite 或浏览器的第三方 Cookie 策略没被发出去。

  • 怎样用 frame-ancestors 限制页面被嵌入？

    点击劫持是把你的页面藏进透明 iframe，骗用户点到敏感按钮。被嵌入的页面用 CSP 的 frame-ancestors 声明谁能嵌入自己，它只能写在响应头里。

  • 原型污染为什么常出现在动态属性赋值和深合并中？

    属性名由外部输入决定时，写到 __proto__ 上就等于改了所有普通对象共享的原型。防法是拦掉危险的键、用没有原型的对象或 Map 存动态键，并且只按白名单取字段。

  • OAuth 2.0 的 PKCE 解决了什么问题？

    PKCE 让客户端先生成一个随机密码，授权时只发它的摘要，换令牌时再交出原值。授权码就算被截走，攻击者没有原值也换不到令牌。RFC 9700 要求公共客户端必须使用。

  • 前端依赖供应链风险应该怎样防范？

    依赖的代码会在安装、构建和运行时执行，坏包可能是仿冒的、维护者账号被盗后发的，或者和内部包同名。防范要从选包、锁版本、限制安装脚本、隔离 CI 密钥一直做到保护自己的发布流程。

  • 前端项目如何防范依赖混淆攻击？

    依赖混淆是攻击者在公共 npm 上发一个和你内部包同名的包，让安装器装错。防法是内部包统一用组织作用域并指向私有仓库、私有代理不回退到公共仓库、提前占住作用域名，再按锁文件安装。

  • 前端文件上传有哪些安全边界？

    前端的类型和大小检查只是为了体验，攻击者可以绕过页面直接调接口。真正的防线在服务端：限大小、按内容识别、随机命名，并把用户文件放在隔离的域名下，防止被当成页面执行。

  • OpenID Connect 和 OAuth 2.0 分别解决什么问题？

    OAuth 2.0 解决的是让第三方应用替用户访问资源，access token 是给 API 用的；OIDC 在它上面加了登录，用 ID Token 告诉应用是谁登录了。应用要校验 ID Token，并用 iss 加 sub 认人。

  • iframe sandbox 的权限组合有什么风险？

    只写 sandbox 不加值时限制最严，iframe 不能跑脚本、提交表单、弹窗或跳走整个页面，每加一个 allow-* 就放开一项。同源内容同时放开脚本和同源时，脚本能直接拆掉自己的沙箱。

  • CSP Report-Only 和违规报告怎样用于安全治理？

    新策略先用 Report-Only 下发，只收集违规、不拦截；把报告按页面、指令和资源归类，改完代码再切换成强制执行。正式策略和下一版的 Report-Only 策略可以同时存在。

  • Trusted Types 会自动过滤所有危险 HTML 吗？

    不会。Trusted Types 只是让 innerHTML 这类危险入口拒收普通字符串，必须交给它由策略生成的值；真正的净化要靠策略里你自己写的代码，比如 DOMPurify。

  • 第三方 Cookie、SameSite 和 Partitioned Cookie 有什么区别？

    SameSite 决定跨站请求带不带 Cookie，第三方 Cookie 能不能用还要看浏览器的隐私策略。Partitioned 让嵌入组件在每个网站里各有一份独立的 Cookie，适合不需要跨站共享登录态的场景。

  • WebAuthn 和 Passkey 登录的安全边界是什么？

    WebAuthn 让设备里的认证器保管私钥，对服务端发来的一次性挑战签名，服务端用注册时存的公钥验证。凭证绑定站点域名，钓鱼网站用不了。Passkey 是基于它的无密码登录，服务端仍要严格验证，并设计好账号恢复。

  • Permissions Policy 怎样限制页面和 iframe 的设备能力？

    页面用 Permissions-Policy 响应头声明自己和哪些来源的 iframe 能用摄像头、麦克风、定位这类能力，iframe 还要在 allow 属性里被单独委托。策略只决定有没有资格，真正使用还要用户点同意。

  • 什么是 Web 缓存投毒？如何避免把用户数据缓存给别人？

    缓存投毒是攻击者让 CDN 存下一份被他影响过的响应，再发给所有人；缓存欺骗是骗 CDN 存下某个用户的私人页面。根源都是影响响应的输入没进缓存键，或者私有响应没标 private、no-store。

  • 什么是 XS-Leaks？前端如何减少跨站状态被推断？

    XS-Leaks 不读跨站响应的内容，而是看浏览器能观察到的差异，比如加载成功还是失败、花了多久，从而猜出用户在目标网站的状态。防护靠 SameSite Cookie、COOP、frame-ancestors、CORP 和 Fetch Metadata 拦截跨站请求。
