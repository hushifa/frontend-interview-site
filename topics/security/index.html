前端安全面试题

前端安全面试题，围绕 CSP、Cookie 安全属性、postMessage、Trusted Types、frame-ancestors 和原型污染，理解浏览器安全机制与防护边界。共 21 道题。

  • XSS 和 CSRF 有什么区别？分别如何防范？

    XSS 是攻击者让恶意脚本在你的页面里执行，能读取页面数据并以用户身份操作；CSRF 是别的网站诱导浏览器向你的站点发请求，借用自动携带的 Cookie。XSS 靠输出编码、净化和 CSP 防，CSRF 靠 SameSite、CSRF 令牌和来源校验防。

  • CSP 的 nonce、hash 与 Report-Only 如何使用？

    CSP 用响应头告诉浏览器哪些脚本可以执行。nonce 是每次响应随机生成的标记，hash 是固定脚本内容的摘要，'strict-dynamic' 把信任传给已授权脚本加载的脚本；新策略先用 Report-Only 观察，再强制执行。

  • HttpOnly、Secure 和 SameSite 分别保护什么？

    HttpOnly 禁止 JavaScript 读取 Cookie，降低 XSS 窃取会话的风险；Secure 只在 HTTPS 下发送 Cookie；SameSite 控制跨站请求是否携带 Cookie，用于防 CSRF。各浏览器在 SameSite 默认值和第三方 Cookie 上行为不同，所以应显式设置。

  • 跨窗口 postMessage 怎样避免把消息发给错误对象？

    发送时 targetOrigin 写成具体的源，不用 '*'；接收时校验 event.origin 和 event.source，再校验消息结构，只执行白名单内的操作。消息内容一律当作不可信数据。

  • Trusted Types 会自动过滤所有危险 HTML 吗？

    不会。Trusted Types 在 CSP 强制下让 innerHTML 等危险入口拒绝普通字符串，必须传入由策略创建的可信类型；真正的净化由策略里的代码（如 DOMPurify）完成。它把分散的风险点集中到少数策略里审查。

  • 怎样用 frame-ancestors 限制页面被嵌入？

    点击劫持把真实页面放进透明 iframe，诱导用户点击敏感按钮。被嵌入的页面用 CSP 的 frame-ancestors 声明谁可以嵌入自己：'none' 禁止，'self' 只允许同源，也可以列出具体来源。它只能通过响应头设置。

  • 原型污染为什么常出现在动态属性赋值和深合并中？

    当属性路径由外部输入控制时，obj[key1][key2] = value 或递归深合并可能经由 __proto__ 或 constructor.prototype 写到 Object.prototype 上，让所有普通对象"继承"攻击者的值。防御是限制可写的键、用无原型对象或 Map，以及只按白名单提取字段。

  • OAuth 2.0 的 PKCE 解决了什么问题？

    PKCE 让发起授权的客户端生成一个随机 code_verifier，授权请求只发送它的 SHA-256 摘要 code_challenge，换取令牌时再提交原值。即使授权码在回调中被截获，攻击者没有 code_verifier 也换不到令牌。RFC 9700 要求公共客户端必须使用 PKCE，机密客户端推荐使用。

  • 前端依赖供应链风险应该怎样防范？

    依赖代码会在安装、构建和运行时执行，风险包括恶意包、维护者账号被盗后发布的恶意版本、拼写相似的仿冒包和依赖混淆。防范要覆盖选包、锁定版本、限制安装脚本、隔离 CI 密钥、审查升级和保护自己的发布流程。

  • 前端文件上传有哪些安全边界？

    前端的 accept、大小和类型检查只改善体验，攻击者可以直接调用接口绕过。安全边界在服务端：限制大小、按内容识别并重新编码文件、用随机名称存储、在隔离的域名下提供下载，并防止 HTML、SVG 被当作页面执行。

  • CORS 携带凭据时有哪些限制？

    跨源请求要带 Cookie，前端需设 credentials 为 include，服务端必须返回具体的 Access-Control-Allow-Origin（不能是 *）和值为 true 的 Access-Control-Allow-Credentials。即使 CORS 通过，Cookie 也可能因 SameSite 或第三方 Cookie 策略不被发送。

  • OpenID Connect 和 OAuth 2.0 分别解决什么问题？

    OAuth 2.0 解决"授权第三方应用访问资源"，access token 是给 API 用的；OIDC 在 OAuth 之上增加身份认证，通过 ID Token 告诉客户端"谁登录了"。客户端要校验 ID Token 的签名、iss、aud、exp 和 nonce，并用 iss 加 sub 识别用户。

  • CSP Report-Only 和违规报告怎样用于安全治理？

    先用 Content-Security-Policy-Report-Only 下发新策略，只收集违规不拦截；按页面、指令和资源聚合报告，修正依赖后再切换为强制执行。正式策略和下一版的 Report-Only 策略可以同时存在。

  • WebAuthn 和 Passkey 登录的安全边界是什么？

    WebAuthn 让认证器持有私钥、对服务端的一次性挑战签名，服务端用注册时保存的公钥验证；凭证绑定 RP ID，浏览器写入真实来源，所以钓鱼站点无法使用。Passkey 是基于它的无密码体验，可能跨设备同步。服务端仍要严格验证挑战、来源和标志位，并设计好账号恢复。

  • Double Submit Cookie 能怎样防御 CSRF？

    服务端下发一个 CSRF 令牌 Cookie，前端读取后再放进请求头提交，服务端比较两者。攻击者能让浏览器自动带上 Cookie，却读不到它的值，也就填不出请求头。令牌应与会话绑定并签名，Cookie 用 __Host- 前缀，防止子域名写入伪造值。

  • Permissions Policy 怎样限制页面和 iframe 的设备能力？

    页面用 Permissions-Policy 响应头声明自己和各来源的 iframe 能否使用摄像头、麦克风、地理位置等能力；iframe 还要在 allow 属性中被委托。策略只决定"有没有资格"，实际使用还需要安全上下文和用户授权。

  • iframe sandbox 的权限组合有什么风险？

    空的 sandbox 属性施加全部限制：内容被当作唯一的不透明源，不能运行脚本、提交表单、打开弹窗或导航顶层页面；每加一个 allow-* 就撤掉一项限制。同源内容同时开 allow-scripts 和 allow-same-origin 时，脚本可以直接移除自己的沙箱。

  • 什么是 Web 缓存投毒？如何避免把用户数据缓存给别人？

    缓存投毒是让 CDN 等共享缓存存下一份被攻击者影响的响应，再分发给其他用户；缓存欺骗则是诱导共享缓存存下某个用户的私有响应。根源都是影响响应的输入没有进入缓存键，或私有响应缺少 private、no-store。

  • 什么是 XS-Leaks？前端如何减少跨站状态被推断？

    XS-Leaks 不读取跨站响应内容，而是利用浏览器可观察的差异（加载成功或失败、耗时、iframe 数量、窗口导航）推断用户在目标站点的状态，例如是否登录、搜索是否有结果。防护靠 SameSite Cookie、COOP、frame-ancestors、CORP 和基于 Fetch Metadata 的资源隔离策略。

  • 前端项目如何防范依赖混淆攻击？

    依赖混淆是攻击者在公共 npm 上发布与公司内部包同名的包，让安装器错误地取到它。防御核心是内部包统一使用组织作用域并把作用域映射到私有仓库、私有代理不向公共上游回退、在公共仓库注册同名作用域，并用冻结的锁文件安装。

  • 第三方 Cookie、SameSite 和 Partitioned Cookie 有什么区别？

    SameSite 决定跨站请求是否带 Cookie；第三方 Cookie 是否可用还取决于浏览器策略，Chrome 默认允许，Firefox 按顶层站点分区，Safari 默认阻止。Partitioned（CHIPS）让嵌入组件拿到一份按顶层站点隔离的 Cookie，适合不需要跨站共享身份的嵌入场景。
