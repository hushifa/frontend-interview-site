前端安全面试题

前端安全面试题，围绕 CSP、Cookie 安全属性、postMessage、Trusted Types、frame-ancestors 和原型污染，理解浏览器安全机制与防护边界。共 16 道题。

  • CSP 的 nonce、hash 与 Report-Only 如何使用？

    CSP 通过响应策略限制允许加载或执行的资源，降低部分内容注入风险。nonce 为符合策略的脚本提供一次响应相关的许可，hash 则根据脚本内容识别允许的片段。

  • HttpOnly、Secure 和 SameSite 分别保护什么？

    HttpOnly 限制 JavaScript 通过 Cookie API 读取对应 Cookie；Secure 限制其在符合要求的安全传输场景发送；SameSite 控制部分跨站请求中 Cookie 的携带行为。它们解决不同问题，需要和会话、CSRF 与 CORS 策略一起设计。

  • 跨窗口 postMessage 怎样避免把消息发给错误对象？

    发送端应尽量指定准确的 targetOrigin，而不是无条件使用星号。接收端检查 event.origin、必要时检查 event.source，并校验消息结构和允许的操作，不能仅因为收到了消息就执行其中指令。

  • Trusted Types 会自动过滤所有危险 HTML 吗？

    不会。Trusted Types 把进入特定注入入口的数据集中到策略中处理，例如生成 TrustedHTML 后交给 innerHTML。策略里的转换或净化逻辑仍由应用定义；原样返回任意字符串的策略不会神奇地消除 XSS。

  • 怎样用 frame-ancestors 限制页面被嵌入？

    点击劫持可能把真实页面嵌入透明或伪装的框架，让用户误点敏感操作。CSP 的 frame-ancestors 指令定义哪些祖先来源可以嵌入当前页面；'none' 禁止嵌入，'self' 允许相同来源。

  • 原型污染为什么常出现在动态属性赋值和深合并中？

    当攻击者能控制对象属性路径，代码又沿着该路径访问并赋值时，可能写到共享原型上。常见入口包括 proto，以及 constructor.prototype 等路径，结果会影响后续通过继承查找属性的其他对象。

  • OAuth 2.0 的 PKCE 解决了什么问题？

    从授权码拦截风险理解 code_verifier、code_challenge 与回调校验，区分 PKCE 和客户端身份认证。

  • 前端依赖供应链风险应该怎样防范？

    从依赖选择、锁文件、安装脚本、更新审查和发布权限说明前端项目的供应链安全边界。

  • 前端文件上传有哪些安全边界？

    说明前端校验、服务端校验、文件名、大小、内容类型和存储隔离之间的关系，避免把客户端限制当成安全防护。

  • CORS 携带凭据时有哪些限制？

    说明 credentials、Access-Control-Allow-Origin、预检和 Cookie 属性之间的关系，避免把 CORS 当成服务端鉴权。

  • OpenID Connect 和 OAuth 2.0 分别解决什么问题？

    区分 OAuth 的授权和 OIDC 的身份认证，理解 ID Token、UserInfo 与 access token 的用途边界。

  • CSP Report-Only 和违规报告怎样用于安全治理？

    通过 Content-Security-Policy-Report-Only 观察潜在违规，再逐步收紧策略，避免上线即阻断真实资源。

  • WebAuthn 和 Passkey 登录的安全边界是什么？

    区分公钥凭证、挑战、RP ID 和用户验证，理解前端调用 WebAuthn 不等于完成账号安全设计。

  • Double Submit Cookie 能怎样防御 CSRF？

    了解双重提交令牌、SameSite 和服务端校验的关系，避免把一个普通 Cookie 当成 CSRF 防护。

  • Permissions Policy 怎样限制页面和 iframe 的设备能力？

    用 HTTP 头和 iframe allow 属性控制摄像头、麦克风、地理位置等能力，理解策略继承和权限提示的关系。

  • iframe sandbox 的权限组合有什么风险？

    理解 sandbox 默认限制、allow-scripts、allow-same-origin 和 allow-top-navigation 的组合边界。
