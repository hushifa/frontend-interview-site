状态与路由面试题

前端路由与状态管理面试题，围绕浏览器导航、Pinia 的 state、getter 与 action，以及 Redux 单向数据流和纯函数 reducer。共 11 道题。

  • Vuex 的 state、getter、mutation、action 和 module 分别做什么？

    Vuex 把共享状态放进一个 store。state 存数据，getter 是派生数据，mutation 是唯一修改 state 的地方且必须同步，action 处理异步再提交 mutation，module 把大 store 按业务拆开。新项目官方推荐 Pinia。

  • Vue Router 有哪些导航守卫？完整的导航流程是怎样的？

    导航守卫是路由跳转过程中的钩子，分为全局守卫（beforeEach、beforeResolve、afterEach）、路由独享的 beforeEnter 和组件内守卫。Vue Router 4 推荐用返回值控制跳转：返回 false 取消，返回路由地址重定向，不返回或返回 true 放行。

  • 前端路由除切换组件外还需要管理什么？

    路由让 URL 成为界面状态的来源，路径和查询参数决定显示什么，刷新、分享、前进后退都能恢复。hash 模式不需要服务器配置；history 模式地址更干净，但服务器要把未知路径回退到入口页。导航时还要处理参数校验、数据加载、错误页、标题、焦点和滚动位置。

  • Redux 的单向数据流为什么强调 reducer 的纯粹性？

    Redux 里状态只能通过 dispatch(action) 改变，reducer 根据旧 state 和 action 算出新 state。reducer 必须是纯函数、不修改原 state，变化才能靠引用比较发现，也才能被记录、重放和测试。Redux Toolkit 用 Immer 让“可变”写法生成不可变更新。

  • Pinia 中 state、getter 和 action 应如何分工？

    state 存原始数据，getter 是带缓存的派生值，action 封装修改数据的业务操作，可以是异步的。从 store 解构 state 和 getter 要用 storeToRefs 保持响应性，SSR 中每个请求要用独立的 Pinia 实例。

  • Zustand、Jotai 和 Redux Toolkit 应该怎样选择？

    Zustand 用一个 hook 暴露整个 store，组件通过选择器订阅需要的部分，不需要 Provider；Jotai 把状态拆成原子，组件按原子订阅，派生原子自动追踪依赖；Redux Toolkit 要求通过 action 和纯 reducer 修改状态，约束最多，自带 DevTools、thunk 和开发期检查。服务端数据交给查询库，三者只管客户端状态。

  • 为什么要用 TanStack Query 或 SWR 管理服务端状态？

    服务端数据真正的来源在服务器，前端拿到的只是某一刻的缓存副本，会过期、会被别人改。TanStack Query 和 SWR 按 key 缓存请求结果，负责去重、过期判断、重新获取、重试和失效后刷新，组件只声明需要哪份数据。它们不适合存放纯客户端的界面状态。

  • MobX 和 Redux 的思路有什么不同？

    MobX 让状态成为可观察的可变对象，组件和 computed 在执行时读到哪些属性就自动订阅哪些，改了属性就只更新用到它的地方；Redux 把状态放在一个不可变的 store 里，只能 dispatch 一个描述“发生了什么”的 action，由纯 reducer 算出新状态，组件靠 useSelector 比较选出的值决定是否更新。MobX 写起来直接、代码少，Redux 更显式，变化可记录、可回放，适合要求严格追踪的团队。

  • 前端离线同步怎样处理重试和数据冲突？

    离线同步先把修改写进本地（IndexedDB），待同步的操作放进持久队列，联网后按顺序发送。每个操作带唯一 ID，服务端据此保证幂等；网络错误和 5xx 退避重试，版本冲突不能盲目重试，要合并或让用户选择。

  • 路由并发导航和权限变化应该怎样处理？

    用户快速切换页面时，旧导航的请求可能比新导航晚返回，把页面覆盖掉。每次导航要能取消旧请求，并在写入结果前确认它仍属于当前导航。前端守卫只控制界面跳转，权限变化后要清空缓存的数据，接口必须由服务端校验。
