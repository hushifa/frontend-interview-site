测试面试题

前端自动化测试面试题，涵盖组件测试、Playwright 端到端测试、Mock、接口模拟、视觉回归、无障碍检查和代码覆盖率。共 17 道题。

  • 组件测试为什么应优先测试用户可见行为？

    测试应描述用户能看到和做到的事情，例如输入条件后出现正确结果，而不是依赖组件内部状态名或私有方法。这样重构实现时，只要行为没变，测试就不应大面积失效。

  • 如何减少 Playwright 端到端测试的不稳定？

    测试应互相独立，明确准备所需数据，不依赖前一个测试留下的登录态或执行顺序。尽量只控制自己的系统，对不可控第三方请求使用受控替代，避免外部变化导致偶发失败。

  • 什么时候应该 mock，mock 太多有什么问题？

    mock 适合控制外部网络、时间、随机数和难以稳定复现的失败条件，使测试能集中验证目标逻辑。但如果把所有依赖和内部调用都替换，测试可能只证明模拟对象彼此配合，无法发现真实集成问题。

  • 视觉回归测试如何减少无意义的截图差异？

    视觉回归比较当前渲染结果与审核过的基线，适合发现布局、文字和样式变化；稳定输入和明确截图范围比盲目放宽像素阈值更重要。

  • Playwright 接口模拟怎样覆盖稳定的成功和失败场景？

    可以在页面发出请求之前注册 route，通过 fulfill 返回受控数据，测试成功、空结果、错误提示等界面行为。也可以先 route.fetch 获取真实响应，再修改部分内容，不过此时测试仍依赖实际服务。

  • 自动化无障碍检查为什么不能替代人工体验？

    自动化工具擅长发现缺少名称、错误 ARIA 和部分对比度问题，但无法判断任务是否易懂、焦点是否合理或读屏用户能否顺利完成流程。

  • 为什么 100% 代码覆盖率也可能漏掉严重问题？

    覆盖率只说明哪些代码被执行过，不能证明结果正确、边界完整或异步时序安全。测试质量取决于独立断言、风险场景和统计范围。

  • Playwright fixtures 解决了什么测试维护问题？

    理解 fixture 的依赖、作用域和自动清理，用共享测试上下文减少重复登录与环境初始化。

  • Testing Library 查询方式为什么优先按用户可见语义？

    从 getByRole、getByLabelText 和 getByTestId 的优先级理解稳定组件测试，避免把实现细节写进断言。

  • 属性测试和示例测试应该怎样搭配？

    用不变量和生成数据覆盖输入空间，同时保留易读的示例测试表达具体业务场景。

  • Playwright 视觉回归的差异阈值和基线怎样维护？

    通过稳定环境、截图范围和差异阈值捕获视觉回归，同时避免把字体和动画波动当成真实缺陷。

  • Playwright route 的处理链与拦截范围怎样设计？

    使用 route.fulfill、continue 和 abort 构造稳定的成功、失败和慢响应场景，避免测试依赖真实后端偶然状态。

  • 前端契约测试应该验证什么？

    契约测试验证消费者和服务提供者对请求、响应和错误结构的共同约定，区别于单纯 Mock 和端到端测试，并说明 Schema、版本兼容和运行时数据校验的关系。

  • 前端故障注入应该怎样设计才有价值？

    通过受控地制造超时、断网、错误响应、资源失败和存储异常，验证界面是否能恢复；故障注入必须可重复、有范围，并区分客户端失败与服务器副作用。

  • 前端组件测试应该围绕哪些用户行为？

    以表单组件为例，用用户可见的名称、输入、提交和错误状态组织测试，区分组件契约与实现细节，并说明异步更新、Mock 和无障碍断言的边界。

  • 前端怎样测试定时器、重试和超时，避免 Fake Timers 造成假通过？

    解释宏任务、微任务和真实时钟的关系，设计可控的定时器测试，覆盖轮询、指数退避、AbortSignal 和测试环境清理。

  • 变异测试如何发现“覆盖率很高但测试没测到重点”？

    解释变异测试通过故意修改代码来检查测试是否能失败，覆盖变异算子、等价变异、前端交互边界和实际落地成本。
