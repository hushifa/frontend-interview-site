Git 与部署面试题

前端 Git 与部署面试题，涵盖 merge、rebase、GitHub Actions 和静态网站发布，理解提交历史、自动化流程、资源路径与缓存。共 11 道题。

  • 前端 CI/CD 流水线怎样设计？

    合并请求上跑安装、检查、测试和构建，只读权限、不碰密钥；合并到主分支后构建一次，把产物交给部署 job，部署 job 绑定 environment，由保护规则控制谁能发、何时发，用 concurrency 防止两次部署同时进行。缓存只用来加速，产物才是部署的依据。

  • git merge 与 rebase 应该怎样选择？

    merge 保留分叉和汇合过程，rebase 重新建立提交的父子关系，让历史变成一条直线。选择时要看分支是否共享、审查需求、冲突成本和回滚方式，而不是只追求直线。

  • git reset、revert 和 restore 有什么区别？

    reset 移动当前分支指向的提交，并按 --soft、--mixed、--hard 决定是否同时重置暂存区和工作区；revert 新增一个反向提交来撤销旧提交，不改写历史；restore 只恢复文件内容，不移动分支。已推送到共享分支的提交应使用 revert。

  • 前端怎样做灰度发布和金丝雀发布？出问题怎样回滚？

    金丝雀发布先让一小部分用户用新版本，对比新旧版本的错误率和关键指标，没有退化再逐步放大比例。前端要让同一用户稳定命中同一版本，新旧两版的静态资源同时可用，接口对两版都兼容。回滚就是把流量切回旧版本，新版资源要保留到旧页面不再请求它们。

  • 前端项目怎样用 Docker 和 Nginx 部署？Nginx 常用配置有哪些？

    用多阶段 Dockerfile：第一阶段用 Node 镜像安装依赖并构建，第二阶段只把 dist 复制进 nginx 镜像。Nginx 里常配四样：try_files 把 history 路由回退到 index.html，gzip 压缩文本资源，入口 HTML 设 no-cache、带哈希的资源设长缓存，location /api/ 用 proxy_pass 反向代理到后端。注意 add_header 只在当前层没有 add_header 时才继承上一层。

  • 误删分支或 reset --hard 之后怎样用 reflog 找回提交？

    reflog 在本地记录 HEAD 和各分支每次移动前后指向的提交。提交被 reset 或分支被删除后，只要对象还没被垃圾回收，就能在 reflog 里找到哈希，再用 reset 或新建分支指回去。reflog 只存在于本地仓库，不会随推送同步。

  • git cherry-pick 和 git bisect 分别解决什么问题？

    cherry-pick 把指定提交引入的修改重新应用到当前分支，生成哈希不同的新提交，常用来把修复移植到发布分支。bisect 在一个已知正常、一个已知有问题的提交之间二分查找，定位第一个引入问题的提交，可以配合脚本用 bisect run 自动执行。

  • GitHub Actions 中 workflow、job、step 和 runner 是什么关系？

    用一个前端检查流程讲清 workflow、job、step、runner 四个层级，执行环境怎样隔离、数据怎样传递，区分顺序、缓存与产物，并说明检查成功不等于已经部署。

  • 静态托管发布时为什么要检查资源路径和缓存？

    静态部署把构建文件交给托管平台，浏览器仍要按正确的路径前缀拿到入口、脚本和数据。资源路径、深链接、缓存和发布版本要一起验证。

  • 静态网站发布失败时怎样安全回滚？

    回滚前先判断故障出在源码、构建产物、托管配置还是缓存层，再恢复已验证的版本，并检查入口、资源和关键交互。撤销 Git 提交不等于线上已经恢复。

  • 前端发布怎样校验构建产物？文件哈希能证明发布安全吗？

    发布时 HTML 和资源可能混版。构建成功、文件完整、来源可信、发布一致是四件不同的事；文件哈希和清单校验只管文件完整，原子切换和回滚解决发布一致。
