架构设计面试题

前端架构设计面试题，讨论设计系统、组件规范、异步状态建模、渐进增强与优雅降级，关注项目长期维护。共 12 道题。

  • 微前端适合解决什么组织和部署问题？

    微前端主要解决多个团队要独立开发、独立部署的组织问题。构建时集成、运行时集成与 iframe 各有取舍，要提前考虑契约、共享依赖、故障隔离、样式隔离和回滚的成本。

  • 怎样避免加载、成功和失败状态互相矛盾？

    不要用 loading、success、error 几个独立布尔值，改成一个 status 字段表示互斥状态，用纯状态转换函数集中处理事件，并拒绝过期请求的完成事件。刷新中保留旧数据要单独表达，外部副作用不归状态机管。

  • 设计系统为什么不能只有一套视觉样式？

    设计系统除了视觉样式，还要规定组件怎么交互、用什么语义元素、参数怎么定，也就是组件契约。token、业务组件、文档测试和版本迁移各管一摊。

  • 设计 token 为什么比散落的颜色变量更适合大型前端项目？

    设计 token 是给设计决策起名字的数据，分基础值、语义和组件三层，组件只引用语义层，换主题只改映射。Web 端常输出成 CSS 自定义属性，要注意继承时的求值边界，也别加没用的抽象层。

  • 前端大型项目怎样划分功能边界？

    按一起变化的业务能力组织模块，每个模块只通过公开接口对外，依赖方向单向，每份状态只归一个模块。用订单功能说明怎样逐步拆分，而不是制造新的耦合。

  • 事件驱动 UI 怎样避免状态互相覆盖？

    改成发事件并不能自动避免覆盖，要区分命令、事件与状态所有者。用可取消的最新搜索控制器给每次请求一个身份，丢弃过期结果，并弄清重复事件、DOM 事件和隐式总线的边界。

  • 前端插件系统怎样设计才能保持可维护？

    插件系统要有一份稳定的插件契约，宿主通过 API 对象做能力注入，管好激活和停用的生命周期，契约带版本保证兼容，并做故障隔离。受信任插件可以同进程运行，不可信插件要放进 iframe/Worker。

  • 低代码和 Schema 驱动 UI 怎样保持可维护与安全？

    Schema 驱动 UI 用 JSON 描述页面，渲染器只用注册过的组件，逻辑用声明式条件或注册函数名表达，不在配置里执行任意 JavaScript。Schema 要带版本做数据迁移，配置校验也不能当成权限控制。

  • 前端 API 如何演进，才能兼容旧客户端并安全迁移？

    前端发布后旧页面和旧 App 会长期存在，API 要同时服务新旧客户端。字段增删、错误格式、分页都要按兼容方式演进，配合版本、弃用通知、缓存处理和灰度发布分阶段迁移。

  • 多租户前端怎样设计，才能避免配置和数据串租户？

    多租户前端要管好租户上下文：租户身份和权限由服务端判断，缓存键都带上租户，切换租户时清掉旧数据，主题和路由按租户加载。还要用两个租户的账号测试隔离。

  • 渐进增强和优雅降级怎样影响前端方案选择？

    渐进增强先保证最基础的版本能用，再在支持的环境里加功能；优雅降级先做完整体验，再给弱环境准备退路。判断能力要用特性检测，脚本运行失败也算能力不足，增强层不能破坏基础功能。

  • 实时协同编辑应该怎样设计状态和冲突解决？

    实时协同要分清传输、操作、权威状态和临时的 presence（光标、在线成员）。冲突解决可以用版本检查、OT 或 CRDT，还要处理离线、权限、操作顺序和资源成本。
